globally set** and causes genuine build corruption under the sustained
7-agent concurrent load today — confirmed via `E0786: found invalid
metadata files for crate 'tokio'` (`failed to mmap rmeta metadata`),
`E0463: can't find crate for shamir_engine`, `STATUS_STACK_BUFFER_OVERRUN`
linker crashes, and a **phantom `error[E0599]: no method named 'iter_ops'
found for &shamir_tx::StagingStore`** that recurred repeatedly on
`shamir-engine` builds even with `RUSTC_WRAPPER=""` and a dedicated
`CARGO_TARGET_DIR` — confirmed genuinely absent from source every time
(`grep` always finds `pub fn iter_ops` in `staging_store.rs`) and confirmed
to self-resolve after freshly rebuilding `shamir-tx` alone first. This is
disk-I/O-contention-class corruption from ~7-8 concurrent heavy
`cargo`/`nextest` processes (my own verification builds + each sm-agent's
own internal gate runs) hammering the machine simultaneously — NOT a code
regression, and NOT something isolating `CARGO_TARGET_DIR` alone fixes
(sccache is a SEPARATE global cache keyed independently of target-dir).
Mitigation adopted for the rest of this segment: `RUSTC_WRAPPER=""` for
every orchestrator-run verification command, plus willingness to retry
once or twice before concluding a failure is real. This does NOT
retroactively cast doubt on earlier-merged work — sccache corrupts
compile/link artifacts, not already-passing runtime test *behavior*, so
tasks merged before this discovery (#1173–#1179, #1181–#1192... actually
#1181 is not yet done, correction: #1173–#1179, #1182–#1192) remain
trustworthy.
