# Q5-d bench cells — wasm compile cold/warm with a REAL disk cache, and database boot with K functions

## Context

Owner ruling (DEC-3 Q5, bench policy by @oh): before deciding whether the wasm disk-cache tier stays, the
repository needs honest cells that measure it. Today they do not:

- `crates/shamir-engine/benches/backend/wasm_invoke.rs` group 4 (`wasm_compile_cached/cold_cache`,
  `wasm_compile_cached/warm_cache`) builds its engines with `WasmEngine::new()`, which has NO compilation
  cache (`crates/shamir-wasm-host/src/wasm/wasm_engine.rs`: `new()` = no persistent cache;
  `with_compile_cache(dir)` = the incremental `DiskCacheStore` cache under `<dir>/cache/wasm`). So
  "cold" and "warm" are the same uncached compile and the header comment ("AOT disk cache") is false.
- The WAT module is a 3-function identity module; a cache decision needs modules whose compile time is
  large enough to matter (64 and 256 exported functions).
- Group 3 (`wasm_startup_compile_k`) also uses `new()` and a trivial module.

The benches are run only in CI (`hot-path-ab` workflow, manual dispatch) — never locally. Your job is the
source change; the numbers come later.

Read first: `crates/shamir-engine/benches/backend/wasm_invoke.rs` (whole file),
`crates/shamir-wasm-host/src/wasm/wasm_engine.rs` and `.../compile_cache.rs` (how the cache dir is used,
what a hit means, `cache_hits` is test-only), `crates/shamir-db/benches/engine_perf.rs` and
`engine_perf/common.rs` (fixture helpers), `bench-iters.txt` header, `scripts/bench/bench_ab.toml`.

## Scope (exact)

1. `wasm_invoke.rs`: replace group 4 with four cells, built from a generated WAT module with N exported
   functions (a small helper `module_with_functions(n)` returning a `String`; N = 64 and 256; each
   function is a distinct tiny body, e.g. an arithmetic expression with a per-function constant, so the
   module does not dedupe; keep `memory`, `shamir_alloc`, `shamir_call` exports so it stays a valid
   engine module):
   - `compile_cold/fn64`, `compile_cold/fn256`: per iteration a FRESH empty temp data dir and a fresh
     `WasmEngine::with_compile_cache(dir)`; the timed part is exactly one `WasmFunction::from_wat(...)`
     compile (cache miss + store). Use `bench_batched` with the dir/engine created in the untimed setup
     and kept alive until after the timed call (drop the temp dir after timing).
   - `compile_warm/fn64`, `compile_warm/fn256`: setup creates a temp dir, compiles the module ONCE with an
     engine on that dir (seeding the cache), drops that engine, and builds a SECOND fresh
     `WasmEngine::with_compile_cache(same dir)` (a new process-like engine that has no in-memory state);
     the timed part is one `from_wat` compile that must be served by the disk cache.
   - Keep the process isolated: nothing may leak between iterations (fresh dir each iteration).
   - Remove the stale `wasm_compile_cached/*` cells and fix the file header list (item 4) and the group
     comments so they describe exactly what is measured. Group 3 stays but also gets a one-line comment
     that it measures an UNCACHED compile on purpose.
   - Add a sanity assertion in the setup of the warm cells (outside the timed region) that the cache
     directory contains cache entries after seeding (it proves the cell measures the cache; use the
     directory listing, not a test-only hook), with a clear panic message.
2. `crates/shamir-db/benches/engine_perf.rs`: add `boot_k_functions/{k}` for K = 16 and 64 — the time to
   open an existing on-disk `ShamirDb` that has K registered wasm functions (cold = empty compile cache
   dir, warm = cache seeded by a first open). Study how functions are registered at boot in
   `crates/shamir-db` / `shamir-engine` (grep `create_validator_from_wasm`, the function registry, and
   how the compile cache directory is chosen from the data dir) and reuse the existing public paths; if
   the boot path does not compile registered functions eagerly, say so in the final message and instead
   provide the cell that exercises the first call of each of the K functions after open. Put any new
   helper in `engine_perf/common.rs` or a new file under `engine_perf/` (keep every folder at <= 7
   entries and every file under 1000 lines).
3. `bench-iters.txt` is regenerated by CI calibration (a later PR). Do NOT hand-edit it and do NOT
   delete the entries of the removed cells either: the calibration PR owns that file. Mention in your
   final message which stale keys exist in it.
4. Do not touch `scripts/bench/bench_ab.toml`, thresholds, workflows, or any non-bench source; do not add
   dependencies (`tempfile` is already a dev-dependency of `shamir-engine`; check `shamir-db` and add
   nothing if it is missing — report instead).
