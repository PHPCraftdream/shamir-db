## Findings to fix (P1 first)

1. **`core/protocol/session/__tests__/identity.test.ts`**: the fake `Platform.openSocket()` returns `{ socket, binding }` (a native-link shape) instead of a `Socket`; `dialEndpoint` wraps the returned value as the socket and `WsFramer` calls `socket.onMessage`, which the object lacks (the double cast hides the contract violation). Also `setup()` pushes the scripted responses before any handler is installed, and the fake's `pushFrame()` calls the (still empty) handler and keeps no queue, so every response is lost. Rebuild the fake against the real `Socket` interface in `core/support/platform.ts` (read how `resume-local.test.ts` / `resume-proof.test.ts` / `connect-local.test.ts` script their sockets and copy the working pattern): queue frames until a handler is installed, return a real `Socket` shape from the platform double, no casts that hide a mismatch.
2. **Circular oracle in the same file**: the fake `sha256` is an FNV stand-in and the signed fixture is built with the production `buildIdentityInput`, so "captured pin equals SHA256(pub_key)" and the transcript layout are not independently proven. Use the real SHA-256 (`@noble/hashes` is already a dependency of the package; check `package.json`) or the Node built-in only inside the test, and build the identity transcript bytes in the test by hand from the Rust reference (`crates/shamir-connect/src/common/user/identity.rs`, `build_identity_input`, and the domain tag in `common/primitives/domain_tags.rs`) with at least one hard-coded expected byte vector.
3. **`src/__tests__/connection/session/e2e-browser-resume.test.ts:32,44`**: `firstTicket` is declared `Uint8Array | null` but receives `resumptionTicket()` (`Uint8Array | undefined`): strict-mode type error. Fix the type.
4. **Same e2e, browser entry on Node**: it calls the browser entry without a Node-side WebSocket adapter. `BrowserPlatform` uses the global `WebSocket` and cannot send an `Origin` or trust the harness's self-signed certificate. Read `src/__tests__/connection/token/e2e-browser.test.ts` (it installs an adapter that supplies Origin and CA) and reuse exactly that approach (and its cleanup) for this test.
5. **Existing fixtures now fail** because verification of `identity_sig` is mandatory: `core/client/__tests__/connect-local.test.ts` (~214-229: the IPC happy path supplies an all-zero 64-byte `identity_sig`) and `core/protocol/session/__tests__/resume-proof.test.ts` (~84-88, 167-172: the resume-success fake lacks `sha256`, which the changed `session/resume.ts` now calls). Update those fixtures minimally so the existing cases pass for the right reason (a valid signature produced in the test with the real Ed25519 / SHA-256 helpers; add the missing primitive to the fake). Search for every other fixture that returns an `auth_ok` (grep `server_signature` / `identity_sig` under `src/**/__tests__` and `src/__tests__`) and fix them all the same way; do not weaken verification in production code to make a fixture pass.
6. **README**: `crates/shamir-client-ts/docs/README.md` (~187-195, the browser resume example) passes `client.trustedPin()` (the SHA-256 hash) as `serverPubKey`; resume expects the RAW public key (`client.serverPubKeyPin()` returns it). Fix the example and say which is which.
7. **`src/core/types/connection.ts` (~119-124)**: the TLS option doc still says "no `identity_sig` pin check in TS (task #622)". Update it to the new behaviour.
