## Goal

The napi column of the support matrix: from Node, through the existing `shamir-client` npm package surface, the user can

- connect with the SCRAM session over TCP+TLS (exists), **native WebSocket** (`connectWs`), **plain loopback TCP** (`connectPlain`), **IPC** (`connectLocal`: Unix socket / Windows Named Pipe);
- **resume** a session with a ticket over TCP+TLS, WebSocket and plain TCP (ticket as `Buffer`; the Rust side uses `resume_secure` / `resume_ws_secure` which verify the pinned server identity before the ticket is sent);
- use an **API token** over REST (`ShamirTokenHttpClient`: ping and execute and the other `TokenHttpClient` calls that make sense) and over the native WebSocket (`connectTokenWs` returning a client with the same data-plane methods as `ShamirClient`, plus an `authKind` getter that returns `"scram"` or `"token"`);
- **log in** with user name and password and get an API token (`login()`).

Naming follows the existing camelCase convention of `ConnectOptions` (`#[napi(object)]`). Every new option object that carries a secret (password, token) must NOT derive `Debug`, and the secret is wrapped by `secrets::protect` / the existing `secrets.rs` helpers immediately; errors never echo input (read `src/tests/error_wire.rs` and `src/tests/secrets_lifecycle.rs` for the conventions and mirror them). Document in the JS typings that a JavaScript string cannot be wiped.
