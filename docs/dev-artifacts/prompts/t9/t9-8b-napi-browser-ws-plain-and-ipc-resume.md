## What to build (deviations only with a written reason in the report)

1. **Rust side** in the existing layout, mirroring `connectWs` / `connectPlain` / `connectLocal` / `resume` / `resumeWs` (same option-object style, `Buffer` ticket normalised and wiped through `secrets::protect`, no `Debug` on secret-carrying option objects, errors never echo input, the same shared connect/resume time budget helpers). `connect_variants/` has 6 entries: add exactly ONE file there (`connect_ws_browser.rs`, which makes 7); the new resume entry points go into the existing `resume/` folder (`ws_browser.rs`, `plain.rs`, `local.rs`; it has 4 entries today) and the new option objects into `options/` (`browser.rs`, `resume_local.rs`). `Origin` is a required string option of the browser entry points.
2. **JS wrapper** `js/wrapper.js` / `js/wrapper.d.ts`: the four entry points in the style of the existing ones (the `d.ts` documents that a JavaScript string/Buffer cannot be wiped; `authKind` stays as is). Hand-edit ONLY `js/wrapper.*` and `src/`; `native/index.js` and `native/index.d.ts` are generated by `napi build` and are committed by the orchestrator from the CI artifact (the `node-binding` job uploads them on drift): do NOT hand-edit them.
3. **Resume rules** (server anti-downgrade, `check_anti_downgrade`: a resume is refused when the channel binding is WEAKER than at authentication; strengths: plain 0x00 = 0 < browser 0x02 = 1 < TLS exporter 0x01 = 2). Allowed: plain -> plain, plain -> native, browser -> browser, local IPC -> local IPC. Refused: native TLS ticket -> plain, native TLS ticket -> browser profile. The tests assert the allowed cases succeed and the refused cases fail with an error (never a panic or a hang). Do not test browser -> native (depends on a server setting).
