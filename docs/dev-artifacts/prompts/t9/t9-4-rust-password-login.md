## Goal

A function that signs in with user name and password over the server's HTTP listener and returns an ordinary reusable API token, usable with `TokenHttpClient` and `Client::connect_token_ws`:

```rust
pub async fn login(opts: LoginOptions) -> Result<LoginOutcome, ClientError>
```

New public items (all `#[non_exhaustive]` with constructors, re-exported from `lib.rs`): `LoginOptions { endpoint: TokenEndpoint, username: String, password: Zeroizing<String>, scope: LoginScope, listener_id: Option<[u8; 16]>, connect_timeout, request_timeout }`, `LoginScope { label, mode, channels, databases }` (default label `http-login`, read-only, channels REST, databases `None`; mode and channels are small public enums that mirror the wire strings `read_only|read_write` and `rest|ws|both`), `LoginOutcome { token: ApiToken, id: [u8; 16], owner: String, scope: LoginScope, created_at_ns: u64, expires_at_ns: u64 }`. `Debug` of options and outcome never prints the password or the token (the password is `Zeroizing` and is wiped as soon as the client key is derived).

## What to build (follow design section 6 and the spec; deviations only with a written reason in the report)

1. **Flow.** Normalise the user name locally (use the same normaliser the server uses; find it under `shamir_connect::common`, `NormalizedUsername`), sort and dedup databases and compute the scope bytes with `shamir_connect::server::http_login::encode_scope`; 32-byte non-zero nonce from `shamir_connect::common::crypto::try_random_array`; the expected `security` class comes from the ENDPOINT, never from the challenge (https -> 0x01, loopback plain http -> 0x00; https behind a proxy (0x02) needs an explicit option only if `TokenEndpoint` already has one, otherwise leave it out and say so in the report); `POST /shamir/v1/auth/begin` on a FRESH connection; strict challenge parsing (`deny_unknown_fields`, `kdf == "argon2id"`, `argon2_version == 0x13`, protocol version 1, binding mode 3), reject a class mismatch, check the optional `listener_id` pin; `build_transcript` validates the KDF limits BEFORE Argon2 (check how, and map its error to `ClientError::Handshake` without echoing server bytes); Argon2id and key derivation on `spawn_blocking`; proof = `client_key XOR HMAC(stored_key, transcript)` using `common::scram::DerivedKeys`; `POST /shamir/v1/auth/finish` on a fresh connection; verify `constant_time_eq(server_signature, build_server_signature(..))` FIRST and, on mismatch, wipe the token and return `ClientError::Handshake("login: server signature mismatch")`; then check token id == returned `id` (`shamir_connect::server::token::parse_token`), echoed scope fields equal the request, `expires_at_ns > created_at_ns`. Server errors map through the existing T9-3a status mapper (`transport/token/status.rs`): `Http { status, code, retry_after }`. No Ed25519 pin on this path: TLS (WebPKI via `TokenTrust`) authenticates the server; the T9-3a TLS connector and hyper http1 helpers (`transport/token/{tls,http_conn}.rs`) are reused, not copied. `Connection: close` responses are normal here (the spec forces it): one request per connection.
2. **Secrets.** The password, derived keys, proof, the token string and every intermediate buffer are zeroized after use; none of them appears in `Display`, `Debug`, error values, `tracing` output or panics. The success body carries the token as a string: parse it into `ApiToken` immediately and wipe the raw body.
3. **Layout.** `client/handshake/token/` holds `mod.rs` and `bearer.rs` now (limit 7 entries): new files `login.rs` (the flow), `login_wire.rs` (begin/finish structs and strict decoders), `login_options.rs` (options, scope and outcome types; one primary export per file, so split further if needed, staying within 7 entries). `client/session/token/` and `client/transport/token/` are at 7 entries and must not grow. `handshake/tests/` gets `login_tests.rs` (unit). `tests/matrix/token/` gets `login.rs` (integration; it has 4 entries now). Limit 1000 lines per file, `mod.rs` re-exports only, no inline `#[cfg(test)]` modules, no local `use`. Narrowest visibilities; the new public items are only the ones listed in Goal; list every other widening in your report.

## Tests (CI-only; they must exercise the real paths)

- Unit (`handshake/tests/login_tests.rs`, against a local fake `tokio::net::TcpListener` plaintext loopback endpoint like `transport/token/tests/fake_server.rs`): strict challenge decoder (unknown key, missing key, wrong `kdf`, wrong `argon2_version`, wrong binding mode, wrong sizes, trailing bytes); class mismatch refusal (a fake server answering `security = 0x01` on a loopback http endpoint); `listener_id` pin mismatch; a server signature that does not match is refused and no token escapes; token id != `id` refused; echoed scope mismatch refused; a 401 and a 429 map to `Http { .. }`; the begin request body is exactly the keys of spec 1.1 (decode it in the fake server). For the happy path of the unit tests use `shamir_connect::server::http_login::build_server_signature` with the keys derived from a fixed password and the KDF parameters the fake server announces (small test parameters if the `build_transcript` limits allow; check the minimums).
- Integration `tests/matrix/token/login.rs` (reuse `token/common.rs`; add helpers there without changing existing behaviour): the live server fixture needs a login-enabled HTTP listener and a user with a known password. Read `crates/shamir-server/tests/e2e/http_login/` for the working server-side setup (listener settings, `login_enumeration_hardening`, how users are seeded with the default KDF tuple, how the listener id is exposed) and COPY the calls instead of inventing signatures. Cases: successful login over TLS (trust = the server's `cert.pem`) returns a token that works with `TokenHttpClient::ping` and `Client::connect_token_ws`; a wrong password gives `Http { status: 401, .. }` (check the real status and code in `TOKEN_LOGIN_HTTP.md` and the e2e tests); an unknown user gives the same status as a wrong password; a read-write scope request is refused unless the server flag allows it (see the spec, "approved global flag"; check the real behaviour in the e2e tests); the listener-id pin match and mismatch; plaintext loopback login works.
- Do not edit existing tests except to add the new `mod login;` line and the fixture additions.
