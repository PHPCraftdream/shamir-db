## Findings, ranked

- **P2 — CONFIRMED: debris cleanup deletes foreign regular files by name alone.** `ret/ownership.rs:23–53` unlinks any same-filesystem plain regular direct entry starting with `.shamir-retention-staged-`. It does not check contents or distinguish an actual tempfile name from a user name; `ret/prune.rs:108–138` does this before the root cap and before validating the fresh copy. **Scenario:** an existing root contains `.shamir-retention-staged-notes`, an operator’s regular file predating the upgrade. The first pass deletes it even if that pass later refuses the fresh snapshot. The prefix was not previously reserved and the new guide still says foreign files are not deleted (`guide:1455–1458`). A stable directory, symlink or Windows reparse point is preserved; a failed unlink is counted as an ordinary entry and can trip the cap. Cleanup does not follow links, but the metadata check and unlink are separate pathname operations. Production retention discovery is the only root-entry classifier I found that recognizes this prefix; the boot test’s retained-path listing excludes the marker, not staged names (`server/engine/server/server_launcher/tests/backup_schedule_tests.rs:159–165`).
- **P2 — CONFIRMED on Unix: another runner can unlink an in-flight sidecar.** Admission serializes one registry (`sched/registry.rs:347–370,738–749`), not the destination. The launcher constructs a registry per server and the maintenance lock is on **`data_dir`**, not the backup root (`server/engine/server/server_launcher/launch.rs:265–281`, `support/durable_stores.rs:44–55`). The root’s exclusive lease is taken only for snapshot deletion, not cleanup or tagging (`ret/prune.rs:132–138,202–205,280–308`). **Scenario:** two servers under the same account, with disjoint data directories, are configured for the same private backup root. A flushes a named sidecar temp; B scans and unlinks it before A’s persist. Unix `rename` then fails and A’s pass stops. If the pre-copy marker was healthy, A’s fresh copy is left untagged without an adoption record. Two independent registries in one process have the same gap; two runs in **one** registry do not. The guide forbids sharing the root, but the code does not enforce the “one runner owns the root” premise of cleanup. **INFERRED on Windows:** successful removal of the live staging pathname can likewise fail the subsequent persist; if removal is denied, B counts the entry. Neither path writes a torn sidecar: pinned `tempfile` uses Unix `rename` or Windows `MoveFileExW(MOVEFILE_REPLACE_EXISTING)`, not an in-place write.
- **P2 — CONFIRMED: the digest rejects changed manifest bytes at the two checks, not a changed tree or a late foreign tag.** `ret/preflight.rs:37–53,125–137` verifies the tree and hashes the exact manifest bytes used. The adoption loop rereads the sidecar, then the manifest, but does not reverify payloads or bind the directory identity (`ret/prune.rs:219–260`). Deletion later checks only root/child disposition and the reader lease (`:275–308`). **Scenario:** after the scan, replace the tracked directory with a plain directory containing the original `manifest.json`, an untagged sidecar and different payload bytes. The late digest still matches; the replacement is tagged and, with a newer fresh copy and `keep_last = 1`, deleted. A foreign tag present at either sidecar read is refused; one installed after the late read can be overwritten by `persist`. There is also an earlier window: `sched/registry.rs:578–632` opens the manifest **after** protocol success, so a valid replacement made before capture supplies the recorded digest. These scenarios violate the guide’s immutable, single-writer root contract. They do not defeat a cooperating reader’s lease, but they disprove the stronger “exact output” claims in `ret/preflight.rs:20–26` and `sched/schedule/retention_pass.rs:7–17,52–63`. A byte-identical copy with matching payloads is also indistinguishable by design; a digest is not directory identity or proof of ownership. A replacement already bearing this scheduler’s tag remains subject to normal owner selection, independent of adoption.
- **P3 — CONFIRMED: failed bounded capture falls back to an unbounded read on the same run.** `sched/registry.rs:626–632,708–715` uses `None` both for “capture not attempted” and “capture refused.” **Scenario:** a successful marker-broken run produces a manifest just over 16 MiB. Capture refuses and no provenance is recorded, but progress attribution immediately reads the entire manifest via `sched/progress_attribution.rs:20–24`. This does **not** authorize adoption; it contradicts the one-bounded-read/no-second-read claim for marker-broken completion. The writer’s pre-existing self-verification reads are separate and were not made bounded by this commit.
- **P3 — CONFIRMED: the guide and comments still overstate several guarantees.** In addition to the foreign-file statement, `guide:1356–1361,1366–1370` says pre-swap refusal leaves `data_dir` untouched. Configured CLI file logging can create a file inside it before any restore check; a filesystem-root target can also get staging inside itself with best-effort cleanup (`sync/restore.rs:375–396,785–793`). These underlying issues are deferred; the unqualified wording is the finding. `sched/registry.rs:555–561,580–583` says a markerless output must never be tagged and describes the private self-check as leasing the fresh child; in fact later adoption can tag it and the self-check takes **no** lease. `sched/schedule/retention_pass.rs:253–259` says a late cancellation loses nothing observable: cancel after protocol success with a healthy marker and the completed copy is neither tagged nor recorded. `ret/prune.rs:76–81` also promises work on the next repaired pass where the code only offers a retry.

No P0 or P1 found within the supported stable-marker, direct-child reader contract. On that path, initial source `NotFound` refuses without reopening the original pathname; `verify_manifest` holds the shared handle through verification, and restore holds it through its last source copy, then checks the **verified** manifest’s file list against staging before the legacy probe, replay or swap (`sync/snapshot_lease.rs:63–85,98–132`; `sync/offline.rs:603–628`; `sync/restore.rs:282–308,368–466`). Pinned `fs4` 0.12.0 uses per-open-handle `flock` on Unix and the same byte range for shared/exclusive `LockFileEx` on Windows. Contention skips deletion; other lock errors count as failures and do not authorize removal.

## Layout and fixture lessons

Count every folder you add to with `ls` (many are at 7 entries: `python -I scripts/ci/check_layout.py` counts only tracked files, recheck after staging); at most 1000 lines per file, one primary item per file, `mod.rs` re-exports only (the rust-guard structure gate allows nothing else in a `mod.rs`: shared helpers go in a named file), tests in `tests/` folders, no inline `#[cfg(test)]` modules, no local `use`, no new `#[allow]`. Persistent stores, every `TempDir` alive for the whole test, close handles and wait for the server task to finish before reopening a directory (Windows holds Fjall locks until the dropped engine's background handles finish: reopen with a bounded retry on `Locked` only, like `init_waiting_for_locks` in the function-family crash tests), handshakes not sleeps, every await bounded by a generous timeout (at least 120 s: a hang detector, the Windows runner is up to 10x slower), a batch is at most 50 queries, per-session request rate limit 500 req/s (never poll in a tight loop: pace status polls at 20 ms or more), set `argon2_concurrent_max` and `auth_init_rate_per_second` to 64 in fixtures that open several sessions, debug-test stacks are small (call concrete handlers through `Box::pin`, run deep tests on a roomy thread, `on_big_stack`), assert on invariants and sets, `shamir-test-diag` marks for flake-prone tests.

## Rules that bind the change

* Machine memory: at most ONE cargo command at a time machine-wide (other executors run: if a cargo run is already in progress wait for its notification, never poll), ALWAYS as `bash <orch>/cg.sh env RUSTC_WRAPPER= CARGO_TARGET_DIR=<artefacts>/target-exec/<WORKTREE-SLUG> wnice -p idle -c 50 -t 8 -m 50 -- cargo ... -j 1 > <logfile OUTSIDE the repository> 2>&1` (the wrapper serializes cargo across executors and the target directory is PER WORKTREE (two worktrees sharing one directory made cargo reuse each other's compiled crates and invalidated the gates): use exactly the directory named for THIS worktree and no other, never run `cargo clean`, never create a local `target/` folder; never `-j 2`; never piped through `tail`/`head`; `cargo fmt` rejects `-j`: run it with `CARGO_BUILD_JOBS=1` under the same wrapper); every worker you spawn must be told the same, and no worker may run cargo at all: only you, the top executor, run `check`/`clippy`/`fmt` under these rules (workers edit files and read code only).
* Leave no scratch files in the tree and none outside it (edit only paths inside this worktree).
* Wrap-up: the hard limit is 150 minutes. At about 105 minutes (70%) stop adding scope, bring the change to a compiling, formatted, clippy-clean state and write the final report (what is done, what is missing, what each check printed); a run that hits the limit without a report is lost work.
