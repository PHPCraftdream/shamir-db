## Binding decisions (decided by the orchestrator; do not redesign; no change of an existing wire tag, error code, message or of the semantics of the owner's existing `RollbackTx` and `CancelCursor`)

* **H1 (P1) — a cancelled interactive transaction must RELEASE its pessimistic record locks.** Round 1 only drops the registry's `Arc`; the locks live in the per-table `MvccStore` and are released only by the explicit `release_pessimistic_locks(&tx, &repo)` (defined `crate::tx::commit` in `shamir-engine`, `pub(crate)`; used by the batch error arm in `query/batch/exec/batch_execute/transactional.rs` and by the commit tails). `TxContext` has no `Drop` that does it (see the header of `execution_deadline.rs`). The brief of round 1 said "stop and list an engine-layer need": that need is now APPROVED, in this smallest form: expose ONE engine function with a narrow signature (re-export from `shamir-engine`, doc comment, no change to the behaviour of any existing caller) that performs the same release for an interactive transaction, and call it from the cancel path after the removal succeeded. Cancel must NEVER wait for the owner's in-flight request (D20, no await under the registry shard lock, no gate or commit lock). Handle the two cases explicitly and test both: (a) no request is running on the transaction (its context lock is free: take it with a non-blocking attempt): release the locks and roll back right in the cancel call; (b) a request is running (it holds the context lock): mark the transaction cancelled in a flag the running request checks at its existing checkpoints and on its exit path, the exit path releases the locks and ends; the cancel answers `cancelled` at once and the transaction can no longer be reached through the registry in either case. If (b) needs more than "a flag plus one call on the request's exit path", do NOT build more: answer `not_cancellable` for a transaction with a request in flight (the operator cancels that request with `CancelRequest` first), say so in the guide and the report, and test it (`not_cancellable` is already a refusal outcome that is counted and audited). Report, with `path:line`, whether the owner's ordinary `RollbackTx`, the reaper and the session-close path release these locks; do NOT change those paths in this round (the orchestrator opens a follow-up task from your evidence).
* **H2 (P1) — authorization and removal must name the SAME transaction.** Handles are minted per repo and can be reused after removal, so "authorize on an activity row, then remove by the number" can remove a replacement transaction that belongs to another user. Fetch the registry entry (its `Arc`) ONCE, authorize against the owner recorded in that entry, then remove with the registry's identity-checked removal (as `tx_rollback` uses `remove_owned`; add one small method to the registry if the existing one cannot express the whole decision). The outcome must come from the SAME decision as the removal, not from a second read: one registry call returns a typed result (removed / refused because it is committing / already gone or replaced) taken under the one shard lock, and the handler maps it to `cancelled` / `already_committing` / `already_finished`. A handle whose identity changed between the authorization and the removal answers `already_finished` and leaves the replacement alone. Fix the doc comment that says "No lock is taken": the registry's own shard lock is taken; say what is true (no gate or commit lock, no await while it is held). Test (the mutant is "remove by number"): a transaction of user A is authorized, then replaced under the same handle by one of user B before the removal (use a registry-level test seam or a direct registry test; if the interleaving cannot be forced through the handler, test the registry method and the handler's mapping separately and say so): B's transaction survives and A's caller gets `already_finished`.

## Findings

- **P1 — Cancellation leaves the record lock it was asked to release.** `crates/server/shamir-server/src/engine/db_handler/repo_admin/activity/cancel.rs:207–210` only drops the registry’s `Arc`. The lock holder lives in the table’s `MvccStore`, which retains its own references (`crates/storage/shamir-tx/src/mvcc_store/mvcc_locks.rs:140–153`). Waking a waiter requires removal through the explicit release path (`mvcc_locks.rs:246–265`); the engine explicitly documents that `TxContext` has no drop implementation that does this (`crates/engine/shamir-engine/src/query/batch/exec/execution_deadline.rs:14–20`). Dropping staged state and releasing the snapshot are not equivalent to releasing record locks. The registration-failure example drops a *fresh* transaction before it can hold any (`crates/server/shamir-server/src/engine/db_handler/repo_admin/tx_handlers.rs:111–135`). The brief required reporting an engine-layer prerequisite rather than claiming this was covered. The new waiter test is non-vacuous and is expected to fail against this implementation.

- **P1 — Authorization and removal are not tied to the same transaction.** `activity/cancel.rs:196–207` authorizes using an activity row, then removes by numeric handle only. Handles are minted per repo and can be reused after removal (`crates/server/shamir-sync/src/sync/durability/tx_registry.rs:49–62,675–695`). If the authorized transaction ends and another user’s transaction takes that handle before removal, the cancellation can remove the replacement using stale authorization. This is a source-level concurrency finding, not a reproduced incident. The same registry already uses identity checks for stale rollback and reaping. The cancellation path also takes the existing shard lock, contrary to its own “No lock is taken” claim, and reads the refusal reason separately from the removal decision (`activity/cancel.rs:177–182,207–215`; `tx_registry.rs:666–672,811–827`).

- **P2 — The race and audit tests miss important failures.** `crates/server/shamir-server/tests/admin/activity/cancel_commit_test.rs:23–29,326–382` accepts `AlreadyFinished | tx_not_found` with no third remover or expected expiry, masking a lost cancellation outcome. Its concurrent loop also runs on a current-thread fixture without a handshake at the contested transition; the ordered phases test both results, but do not prove actual overlap. `crates/server/shamir-server/src/engine/db_handler/repo_admin/activity/tests/cancellation_tests.rs:517–567` tests the real audit writer and payload, but calls the enqueue helper directly; deleting the audit call from either handler would leave it green. The counter tests verify the four internal slots and real `/metrics` binding, but only `already_finished` and a successful `CancelTx` are exercised through dispatch. The token-matrix edit adds classification arms, not requests to the fixture list (`crates/server/shamir-server/tests/e2e/token_matrix/gaps/privilege.rs:211–224,253–271`).

- **P2 — Wire validation and fixture requirements are incomplete.** The new discriminators can be repeated and overwritten in the buffered map before `deny_unknown_fields` sees them (`batch_op.rs:370–376`); the builder, serde round-trip, and HMAC tests meaningfully assert valid shapes and policy, but do not exercise malformed or duplicate new discriminators. The rollback, cursor and permission tests do assert real post-state or typed errors; however, the extended permission test still uses an in-memory store and 60-second calls (`crates/server/shamir-server/tests/admin/activity/permission_denial_activity.rs:66–80`; `crates/server/shamir-server/tests/admin/activity/common.rs:55–68,128–144`). The launcher test genuinely scrapes HTTP, but uses an in-memory data repo and injected sessions rather than client connections, with Argon2 cap 4 and default auth-init rate 10, not 64 (`crates/server/shamir-server/src/engine/server/server_launcher/tests/cancel_counter_tests.rs:95–119,274–290`; `crates/server/shamir-server/src/boot/config.rs:429–430`).

- **P2 — The guide promises behavior the code does not provide.** `docs/guide-docs/guide/07-operations.md:3257–3263` says the owner’s legacy `CancelCursor` returns `cursor_not_found`; it still returns `CursorClosed` unconditionally (`crates/server/shamir-server/src/engine/db_handler/cursor_handlers/fetch.rs:607–624`). The guide also promises lock release and claims an unprivileged caller cannot distinguish unknown IDs from existing foreign IDs (`07-operations.md:3249–3254,3275–3280`), but unknown targets return `already_finished` while foreign targets return `permission_denied`. The documented choice to let an already-running `TxExecute` continue is real, but its retained `Arc` can defer snapshot release until that call exits (`tx_handlers.rs:309–379`); `cancelled` is not a cleanup acknowledgement for in-flight work.
