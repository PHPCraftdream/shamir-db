## What (this step only)

1. **P1: a clock error can suspend configured retention for years.** `audit_appender/rotation.rs` names a new archive `max(now, largest existing suffix + 1)`, but retention (~lines 171-203) treats that suffix as WALL-CLOCK time for the age rule: after one rotation while the clock was years ahead, every later archive inherits a future-looking timestamp, the sweep stops at the first future-dated archive and retains even independently age-eligible archives after it; writes then create archives with no count or disk cap until the clock catches up plus `retention_days`. The old sweep skipped a future-dated file and still considered the others, and the old mtime fallback is gone. Keep what is right (a contiguous oldest prefix is removed; the newest archive that holds the rotation boundary stays; names stay strictly increasing) but stop using the name as an age clock: take the age of an archive from a source that does not depend on the name (the file's modification time, or the timestamp of its last record if the record carries one: read the format and choose the cheaper reliable one), treat an archive whose age is in the future as NOT eligible without stopping the sweep over the older eligible prefix, and keep the prefix contiguous (never remove an archive that is younger than one you keep). Test: a future-named archive followed by correctly aged older and newer archives: the eligible contiguous prefix is removed, the rest stays, and the result boots with a usable anchor.
2. **P2: every retention-enabled rotation rereads and decodes the first full record of every archive under the persistence gate** (`rotation.rs` ~63, 150, 181; `recovery.rs` ~335, 355; boot reads each first row twice). Over N rotations without pruning the first-record reads grow quadratically while producers wait on the gate. Order retention candidates by the strictly increasing name suffix (names are now monotonic by construction; boot recovery keeps ordering by first sequence and is the authority), read at most what the age decision needs, avoid listing the directory twice, and do not hold the persistence gate across archive reads that can run before it is taken. Boot must read each archive's first row once. Test: a counting seam proves a no-prune rotation reads no archive body.
3. **P2: the offline token CLI prepares secret output BEFORE the maintenance lock** (`token_cli/commands/create.rs` ~27, 40, 87, 107, 177; `secret_output.rs` ~11, 39). Take the lock first (a live server gives the existing immediate refusal and nothing was created), and refuse a secret output path that resolves to the audit log, any of its archives or anything under the audit directory prefix namespace `audit.log*` (typed error, nothing written). Also keep a permission error distinct from lock contention in the lock error text (the CLI currently converts every lock error to "requires a stopped server"). Tests: output equal to `audit.log` with a missing active file is refused and the log is untouched; a lock refusal creates no output file; a permission error is not reported as contention.
4. **P3: the raw appender checkpoint API is less strict than recovery** (`audit_appender.rs` ~343, 788, 874; `recovery.rs` ~262, 465): `stored_position()` turns a malformed existing row into `None` and `write_checkpoint()` can then overwrite it, and a fresh raw store accepts an invalid genesis tuple that recovery refuses. Make a malformed existing checkpoint a typed error that is preserved for diagnosis, and refuse an invalid tuple at write. Test for each.
5. **P3: an archive suffix of `u64::MAX` boots but the next rotation disables auditing** (`rotation.rs` ~89, `recovery.rs` ~305, `audit_appender.rs` ~689-711): recovery must refuse such a suffix at boot with the typed error (so the failure is at start, not at the next rotation, and not after new records were synced), or rotation must handle exhaustion without latching; choose the narrower and test it. ## Layout and fixture lessons

Count every folder you add to with `ls` (many are at 7 entries: `python -I scripts/ci/check_layout.py` counts only tracked files, recheck after staging); at most 1000 lines per file, one primary item per file, `mod.rs` re-exports only (the rust-guard structure gate allows nothing else in a `mod.rs`: shared helpers go in a named file), tests in `tests/` folders, no inline `#[cfg(test)]` modules, no local `use`, no new `#[allow]`. Persistent stores, every `TempDir` alive for the whole test, close handles and wait for the server task to finish before reopening a directory (Windows holds Fjall locks until the dropped engine's background handles finish: reopen with a bounded retry on `Locked` only, like `init_waiting_for_locks` in the function-family crash tests), handshakes not sleeps, every await bounded by a generous timeout (at least 120 s: a hang detector, the Windows runner is up to 10x slower), a batch is at most 50 queries, per-session request rate limit 500 req/s (never poll in a tight loop: pace status polls at 20 ms or more), set `argon2_concurrent_max` and `auth_init_rate_per_second` to 64 in fixtures that open several sessions, debug-test stacks are small (call concrete handlers through `Box::pin`, run deep tests on a roomy thread, `on_big_stack`), assert on invariants and sets, `shamir-test-diag` marks for flake-prone tests.

## Rules that bind the change

* Machine memory: at most ONE cargo command at a time machine-wide (other executors run: if a cargo run is already in progress wait for its notification, never poll), ALWAYS as `bash <orch>/cg.sh env RUSTC_WRAPPER= CARGO_TARGET_DIR=<artefacts>/target-exec wnice -p idle -c 50 -t 8 -m 50 -- cargo ... -j 1 > <logfile OUTSIDE the repository> 2>&1` (the wrapper serializes cargo across executors and the shared `CARGO_TARGET_DIR` keeps registry dependencies compiled once for all executors: never run `cargo clean`, never set another target dir; never `-j 2`; never piped through `tail`/`head`; `cargo fmt` rejects `-j`: run it with `CARGO_BUILD_JOBS=1` under the same wrapper); every worker you spawn must be told the same, and no worker may run cargo at all: only you, the top executor, run `check`/`clippy`/`fmt` under these rules (workers edit files and read code only).
* Leave no scratch files in the tree and none outside it (edit only paths inside this worktree).
* Wrap-up: the hard limit is 150 minutes. At about 105 minutes (70%) stop adding scope, bring the change to a compiling, formatted, clippy-clean state and write the final report (what is done, what is missing, what each check printed); a run that hits the limit without a report is lost work.
