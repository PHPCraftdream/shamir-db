# Brief: ARGON2-GATE — make `argon2_concurrent_max` real: gate the server-side Argon2id key derivation (user creation, password change) with the boot semaphore, a typed busy refusal, the pool series, and a truthful guide

## Why (verified facts, re-open every path before relying on it)

`launch.rs` (`crates/server/shamir-server/src/engine/server/server_launcher/launch.rs`, search `Argon2Semaphore::with_capacity(config.argon2_concurrent_max)`) creates the boot's Argon2 semaphore and hands it to the listeners and to the sync `ConnectionContext`, but NOTHING in production ever acquires it: a SCRAM login verifies a proof with HKDF and HMAC only and runs no Argon2id (see the comment at `crates/server/shamir-sync/src/sync/connection/handshake.rs` around "6. Verify the proof": the semaphore "stays reserved for gating genuine server-side Argon2id (e.g. user-creation key derivation)"). The only server-side Argon2id is `derive_scram_record` (`crates/server/shamir-server-security/src/security/user_directory/derive_scram_record.rs`: `spawn_blocking` around `DerivedKeys::derive`, no limit), reached from the wire `CreateScramUser` handler (`crates/server/shamir-server/src/engine/db_handler/handlers/admin.rs`), the `UserAdminPort::create_user` implementation (`crates/server/shamir-sync/src/sync/ports.rs` and its server-side adapter) and the boot bootstrap of the first administrator (`crates/server/shamir-server/src/boot/bootstrap.rs`; a one-shot at boot, stays ungated). So the configured limit protects nothing, while the operations guide (`docs/guide-docs/guide/07-operations.md`, the config table row `argon2_concurrent_max` "Лимит одновременных Argon2-верификаций" and the memory formula row `Argon2 peak = argon2_concurrent_max × memory_kb × 1.05`) promises a limit of concurrent verifications. An operator or a script that creates many users at once can start an unbounded number of ~128 MB derivations. R4a step 2b also refused to add an Argon2 pool series for exactly this reason ("the boot semaphore has no production acquisition caller").

## What (this step only)

1. **Gate the derivation.** The same `Arc<Argon2Semaphore>` that `launch.rs` already creates (one pool, not a second one) must reach the two non-boot callers of `derive_scram_record` (find the narrowest wiring through the existing handler state and the port adapter; read how the semaphore already reaches `ListenerCtx` and `ConnectionContext`). Acquire the permit INSIDE the `spawn_blocking` closure, around the KDF call only (spec §8.1 in the semaphore's own docs: the permit is held only for the duration of the KDF, never across an `.await`), with a bounded wait (`acquire_until` with a fixed deadline of a few seconds; pick the value, name it as a constant with a one-line reason; no new configuration key). On timeout (or a failing clock, which the semaphore already reports the same way) the derivation is REFUSED with a typed busy error, never queued forever and never a panic; the permit is released on success, failure and panic (the RAII guard already does it: prove it with a test). The plaintext password buffer stays zeroized on every path.
2. **Typed refusal surface.** Reuse the existing typed busy convention if one exists (`server_busy` is named in the semaphore docs; grep for how connection and rate-limit refusals are coded and for the client-visible error codes list) so a client sees a stable code and a safe message, not the internal string `Err(String)` mapped to `code: "query"`. The wire `CreateScramUser` path and the `UserAdminPort::create_user` path (its `PortError`) both map it. Any new wire code is added to the SAME places an existing code is added (error code enum, client mapping, docs table); list every place you touched. No secret, no user name beyond what the existing error already carries.
3. **The pool series.** Add the series R4a step 2b could not add, now that a real acquirer exists, as unlabelled series sampled at scrape time exactly like the load series of step 2b (`crates/server/shamir-server-security/src/security/observability/` export modules and the registration pattern in `observability/mod.rs`; the load series source is `server_launcher/support/load_metrics.rs`): `shamir_argon2_permits_capacity`, `shamir_argon2_permits_available` and a counter `shamir_argon2_busy_refusals_total` (a plain atomic owned next to the semaphore wiring; counts only refusals of item 1). Read the step-2b code and tests first and follow them exactly (naming, unit-less gauge rules, duplicate-name and label checks in the scrape tests, the engine metrics catalogue `docs/dev-artifacts/design/engine-metrics.md`, the guide's metric table). Do not add any other series.
4. **Truthful guide.** In `07-operations.md` correct the config-table row and the memory-formula row: the limit applies to server-side key derivations (creating a user, changing a password), NOT to logins (a login does no Argon2id on the server; the client derives), state the refusal behaviour and the three new series; keep the formula as the peak memory of concurrent derivations. Russian, same style as the file. Also fix any other sentence in the guides that promises a limit of login verifications (grep `Argon2` across `docs/guide-docs/`).
5. **Tests (CI-only; add to existing `tests/` folders, registered in their `mod.rs`).** (a) Semaphore-level: capacity 1, a derivation holds the permit while a second call times out with the typed busy error, and succeeds after the first finishes; the permit count returns to capacity after success, after a derivation error and after a panicking closure (inject through a small seam only if one already exists; otherwise prove release by the RAII path with a unit test on the gate helper). (b) Handler-level: `CreateScramUser` against a server fixture with `argon2_concurrent_max: 1` and the pool pre-occupied through the fixture's handle returns the typed busy code, and succeeds when free. (c) Port-level: `UserAdminPort::create_user` maps the refusal to its `PortError`. (d) The three series appear exactly once, unlabelled, in a real `/metrics` scrape, with `capacity` equal to the configured limit, `available` equal to capacity at rest and the counter increasing by one per refusal (extend the step-2b scrape test pattern; do not create new fixtures if one exists). Bounded awaits of at least 120 s; no sleeps as synchronization; fixtures that open several sessions set `argon2_concurrent_max` and `auth_init_rate_per_second` to 64 EXCEPT the new tests that need a tiny pool.

## Do not

Gate the login path or change SCRAM, change a KDF parameter or default, add a config key, change `Argon2Semaphore` itself unless a missing method is strictly needed (list it), gate the boot bootstrap, add a dependency, touch the shell, or widen an existing item beyond what the wiring needs (list every widening before doing it). Do not edit `launch.rs` beyond the minimal hand-over of the existing `Arc` (it is close to the 1000-line limit unless the FILE-HEADROOM-b split has landed: check `wc -l` first and keep it unchanged in length if it is above 950).
