## Why

An operator must be able to inspect a server from wherever the server exposes it: the native WSS endpoint with SCRAM, or, with a provisioned API token, the HTTPS REST endpoint and the token WSS listener on a strictly read-only subset. PR1 covered TLS-TCP and IPC with SCRAM; PR2 completes the secure transport matrix and the catalogue.

## What (this step only = PR2)

1. **Native WSS + SCRAM** (T3 of §3.1): through the existing Rust client library and its handshake (`crates/client/shamir-client`), verified pin required exactly as for TCP (a profile carries the captured pin; mismatch or absence is a hard typed refusal; no `--accept-new-host`; no resume). Reuse the PR1 SCRAM connector structure; add the WSS transport selection to the profile format ONLY as the design states (read the profile allowlist of §4.1 and extend `connect/profile.rs` strictly: unknown fields stay refused).
2. **Token sessions** (T7): `shell/connect/token.rs` (the PR2 row: `connect/` goes from 3 to 4 entries; recount with `ls`). The token is a provisioned API token entered like the PR1 secrets (TTY without echo, `--secret-stdin`, `--secret-fd`, `--secret-env`; never on argv; zeroized; never in output, error text, a profile or any file), used over HTTPS REST and over the native token WSS listener (read how the existing clients/servers speak both: `crates/net/shamir-transport-http`, `crates/net/shamir-transport-ws`, `crates/server/shamir-server-security/src/security/perimeter/http_rest/`, the token store and scope code; use the existing client-side token support if one exists, otherwise the narrowest code that uses the existing wire, no new crate). Sessions are stateless: no resume, no reconnect, one-shot per command in batch.
3. **The read-only subset (§3.3) is enforced by the shell AND proven against the server:** over a token session the shell sends ONLY `ping`, `db list`, `repo list`, `table list`, `index list`, `function list`, `table describe`, `table schema`, `data head`, `data count` (the last two arrive in a later step: here the subset allowlist exists and refuses everything not in it; commands that do not exist yet are simply absent); every other command gets the typed refusal `token_request_denied` with the fixed message of the design, exit 4, without any network request. `db list` follows §3.3 exactly (server-enforced; the shell does not send more).
4. **Every typed refusal of the PR2 row**, each with a test: plaintext incl. loopback; token over IPC; token over TLS-TCP SCRAM; SCRAM-only refusal scaffolding; browser/HTTP-login deferrals; no-pin; token outside the subset. The exact fixed messages of §3.3's table. Exit codes per §5.
5. **`repo describe`** completes the catalogue: map it to the existing server operation the design names (read §4.3; if the mapping does not exist in the code, STOP that command with a typed "unsupported" refusal and report the exact evidence).
6. **Tests (CI-only; `tests/admin/shell/transport.rs` and `tests/admin/shell/harness.rs` are 993 lines each on the current master, so do NOT grow them past 1000: put the new scenarios into new topical test files, and where a folder is already at 7 entries turn one file into a folder (declarations-only `mod.rs` plus topic files) so the entry count holds; re-count with `ls` after `git add -A`):** scripted one-shot scenarios "connect → ping → catalogue → describe" on WSS+SCRAM and on a token over HTTPS REST and over the token WSS listener against the real server binary or the in-process launcher the PR1 tests use (read `tests/admin/shell/harness.rs` first: boot fixtures, how profiles and pins are provisioned; add token provisioning through the existing token admin operations via the typed builders), the typed-refusal probes of item 4, a token session refused for every command outside the subset with ZERO requests reaching the server (assert on a counting proxy or the server's own counters, not on the reply alone), the secret-leak byte-scan over stdout, stderr, argv, profile and absence of history with a unique canary token per run (extend the PR1 scan to the token path), malicious-peer reflection scans for the new commands' output. Three-OS runtime proof is a later `workflow_dispatch` on the same head: say in the report which commands the orchestrator must dispatch.

## Do not

Add a registry dependency (declare only workspace-internal edges, each justified), implement anything of PR3–PR6 (`status`, `data`, rights, activity, backups, versions, schedule, export), implement resume or `--accept-new-host`, read the data directory, bypass the server's authorization, print server error strings or peer-supplied text raw, keep any history, accept a secret on argv, or construct wire values by hand (client library and builders only). Do not widen an existing item beyond what the shell needs (list every widening before doing it). Remember what PR1's CI taught: the Unix-only code is compiled only in CI and the Windows-only code only on this Windows machine: every `cfg(unix)`/`cfg(windows)` item gets its cfg on the item AND its imports and helpers; no doc comment (`///`) on an `extern` block or a macro invocation; `CStr::to_str()` returns a `Result`; `rustix` 1.1.6 features as declared in the manifest; read every Unix region twice for unused items under `-D warnings`.


## Layout and fixture lessons

Count every folder you add to with `ls` (many are at 7 entries: `python -I scripts/ci/check_layout.py` counts only tracked files, recheck after staging); at most 1000 lines per file, one primary item per file, `mod.rs` re-exports only (the rust-guard structure gate allows nothing else in a `mod.rs`: shared helpers go in a named file), tests in `tests/` folders, no inline `#[cfg(test)]` modules, no local `use`, no new `#[allow]`. Persistent stores, every `TempDir` alive for the whole test, close handles and wait for the server task to finish before reopening a directory (Windows holds Fjall locks until the dropped engine's background handles finish: reopen with a bounded retry on `Locked` only, like `init_waiting_for_locks` in the function-family crash tests), handshakes not sleeps, every await bounded by a generous timeout (at least 120 s: a hang detector, the Windows runner is up to 10x slower), a batch is at most 50 queries, per-session request rate limit 500 req/s (never poll in a tight loop: pace status polls at 20 ms or more), set `argon2_concurrent_max` and `auth_init_rate_per_second` to 64 in fixtures that open several sessions, debug-test stacks are small (call concrete handlers through `Box::pin`, run deep tests on a roomy thread, `on_big_stack`), assert on invariants and sets, `shamir-test-diag` marks for flake-prone tests.

## Rules that bind the change

* Machine memory: at most ONE cargo command at a time machine-wide (other executors run: if a cargo run is already in progress wait for its notification, never poll), ALWAYS as `bash <orch>/cg.sh env RUSTC_WRAPPER= wnice -p idle -c 50 -t 8 -m 50 -- cargo ... -j 1 > <logfile OUTSIDE the repository> 2>&1` (the wrapper serializes cargo across executors; never `-j 2`; never piped through `tail`/`head`; `cargo fmt` rejects `-j`: run it with `CARGO_BUILD_JOBS=1` under the same wrapper); every worker you spawn must be told the same, and no worker may run cargo at all: only you, the top executor, run `check`/`clippy`/`fmt` under these rules (workers edit files and read code only).
* Leave no scratch files in the tree and none outside it (edit only paths inside this worktree).
* Wrap-up: the hard limit is 150 minutes. At about 105 minutes (70%) stop adding scope, bring the change to a compiling, formatted, clippy-clean state and write the final report (what is done, what is missing, what each check printed); a run that hits the limit without a report is lost work.
