# Brief: R2d-FIX-C — scheduled retention must never delete a snapshot that `restore` or the standalone verifier is still reading: a cross-process read lease

Path prefixes used below: `sync/` = `crates/server/shamir-sync/src/sync/durability/backup/`; `sched/` = `crates/server/shamir-server/src/boot/config/diagnostics/backup_online/`; `server/` = `crates/server/shamir-server/src/`. Re-open every path and line before relying on it (lines drift). Verified by a read-only trace of the landed code on 2026-11-21; not yet reproduced: the first test proves it in CI.

## Why

Scheduled retention (`sched/schedule/retention/prune.rs`) verifies an owned snapshot and then calls `remove_dir_all` on it IN PLACE. Nothing tells it that another process is reading that snapshot: the registry permit (`sched/registry.rs`) is an in-process atomic taken by backup WRITERS only; the restore liveness probes (`sync/restore.rs`, `sync/offline/source_lock.rs`) concern the TARGET data directory; the Fjall locks restore uses for replay live under STAGING; the ownership tag proves provenance, not reader activity; the tag sidecar's atomic replace is not a rename-before-delete of the snapshot. Failing sequence: a valid owned scheduled snapshot `A` falls outside the newest-`N` after `B` is published; in another process an operator runs `restore --from A` into a different, stopped target (or calls `verify_manifest(A)`, `sync/offline.rs`), the reader loads the manifest and pauses before opening a listed payload; the scheduled worker verifies `A` in its own pass and deletes it; the reader resumes and `File::open` or `symlink_metadata` fails. Restore then either refuses before swapping (clean `RestoreError::Io`, staging cleaned) or, worse, when a directory disappears BEFORE enumeration (restore copies the directory walk, not the verified file list, and does not re-hash staging) restore can publish an INCOMPLETE target, for example missing the `users` directory contents, with no error. On Unix an open descriptor keeps one file's bytes readable but not the other pathnames; on Windows `remove_dir_all` retries sharing violations per file and can fail after deleting others. The guide's workaround (copy a snapshot out of the managed root first, `docs/guide-docs/guide/07-operations.md` around the "copy-out" paragraph) does not protect the copy-out itself.

## What (this step only)

1. **A cross-process read lease on a managed root.** One stable lock file per managed backup root, OUTSIDE the deletable children (for example a reserved file name at the root that retention never lists or deletes, created owner-private when scheduled retention is enabled and by a reader that finds none), using the OS advisory file locking the codebase already uses (`fs4` is used by `maintenance_lock.rs`: reuse it, add no dependency). Readers take a SHARED lease: `restore --from <snapshot>` from before its first read of the snapshot through its last source copy, and the standalone verifier (`verify_manifest` entry points in `sync/offline.rs`) from before the first read through the last. Retention takes a NON-BLOCKING EXCLUSIVE lease per candidate before deleting and SKIPS busy snapshots (counted in its existing outcome as skipped-in-use, not an error; the next pass retries). A snapshot path that is not inside a managed root (an exported copy) keeps lock-free reads: decide the managed-root test with the same ownership rule retention already uses, and say what you chose. A lease must never hold the registry permit or block a backup writer. The restore path must also re-check, after enumeration and before the swap, that the staged tree contains every file the verified manifest lists (a cheap listing comparison, no re-hash) and refuse with a typed error otherwise: this closes the incomplete-publish hole even for unmanaged sources.
2. **Existing managed roots** (created before this change) get the lease file provisioned lazily; behaviour for roots without the file is "provision, then proceed". Windows and Unix both covered; no `cfg` item without its imports and helpers.
3. **Tests (CI-only; registered in their `tests/mod.rs`).** `retention_skips_snapshot_while_verify_is_reading` in `sched/schedule/retention/tests/prune_tests.rs`, reusing `private_root`, `copy` and `retain` (lines ~27-110 there): two copies, `keep_last = 1`; a test-only rendezvous after the real reader has loaded the old snapshot's manifest and before its first payload open; assert prune deletes ZERO while the lease is held and the resumed verifier succeeds; after the reader ends assert the next pass deletes the old copy. Before the fix the first pass deletes it. Restore-side: the staged-listing re-check refuses when a listed file is missing from staging (inject by removing a file of the snapshot between verification and enumeration through an existing test hook or the smallest new one, listed in the report); the lease is released on every error path (drop-based). A two-process style test is not required: two handles on the same lock file in one process are enough if the lock primitive is per-handle (say so and prove it in the test).
4. **Guide.** In the backup section of `07-operations.md` (Russian): restore and verify of a snapshot that lives in a managed root are safe against retention (retention skips it while a reader holds it); remove or reword the copy-out workaround to what is now true; unmanaged copies are unaffected.

## Do not

Hold a lock across `.await` in the server, block the scheduler runtime thread (retention runs on its native worker: keep the non-blocking try), change retention's selection rules, ownership tagging or budget (a separate task owns them), touch the shutdown path or the audit code, add a dependency or config key, or widen an item beyond what the lease needs (list every widening).

## Layout and fixture lessons

Count every folder you add to with `ls` (many are at 7 entries: `python -I scripts/ci/check_layout.py` counts only tracked files, recheck after staging); at most 1000 lines per file, one primary item per file, `mod.rs` re-exports only (the rust-guard structure gate allows nothing else in a `mod.rs`: shared helpers go in a named file), tests in `tests/` folders, no inline `#[cfg(test)]` modules, no local `use`, no new `#[allow]`. Persistent stores, every `TempDir` alive for the whole test, close handles and wait for the server task to finish before reopening a directory (Windows holds Fjall locks until the dropped engine's background handles finish: reopen with a bounded retry on `Locked` only, like `init_waiting_for_locks` in the function-family crash tests), handshakes not sleeps, every await bounded by a generous timeout (at least 120 s: a hang detector, the Windows runner is up to 10x slower), a batch is at most 50 queries, per-session request rate limit 500 req/s (never poll in a tight loop: pace status polls at 20 ms or more), set `argon2_concurrent_max` and `auth_init_rate_per_second` to 64 in fixtures that open several sessions, debug-test stacks are small (call concrete handlers through `Box::pin`, run deep tests on a roomy thread, `on_big_stack`), assert on invariants and sets, `shamir-test-diag` marks for flake-prone tests.

## Rules that bind the change

* Machine memory: at most ONE cargo command at a time machine-wide (other executors run: if a cargo run is already in progress wait for its notification, never poll), ALWAYS as `bash /d/system_artefact/orch/cg.sh env RUSTC_WRAPPER= CARGO_TARGET_DIR=D:/system_artefact/target-exec wnice -p idle -c 50 -t 8 -m 50 -- cargo ... -j 1 > <logfile OUTSIDE the repository> 2>&1` (the wrapper serializes cargo across executors and the shared `CARGO_TARGET_DIR` keeps registry dependencies compiled once for all executors: never run `cargo clean`, never set another target dir; never `-j 2`; never piped through `tail`/`head`; `cargo fmt` rejects `-j`: run it with `CARGO_BUILD_JOBS=1` under the same wrapper); every worker you spawn must be told the same, and no worker may run cargo at all: only you, the top executor, run `check`/`clippy`/`fmt` under these rules (workers edit files and read code only).
* Leave no scratch files in the tree and none outside it (edit only paths inside this worktree).
* Wrap-up: the hard limit is 150 minutes. At about 105 minutes (70%) stop adding scope, bring the change to a compiling, formatted, clippy-clean state and write the final report (what is done, what is missing, what each check printed); a run that hits the limit without a report is lost work.
