# Brief: R5 DESIGN — the administrative shell (operator tool for a running server)

This is a DESIGN task: the deliverable is one design document (and a plan of PR-sized implementation steps). No production code, no tests, no new crate in this step.

Read first: `docs/dev-artifacts/release-1/05-admin-cli.md` (the plan: groups of commands, interactive and batch modes, "no arbitrary data queries", requirements, stages R5a–R5c, open questions), `docs/dev-artifacts/release-1/README.md` (the release gates), and the already-landed designs whose commands the shell must expose: `docs/dev-artifacts/design/online-backup.md` (R2a: admin operations `StartBackup` / `BackupStatus` / `CancelBackup`; offline `restore` / `verify` commands), `docs/dev-artifacts/design/operational-views.md` (R4b: `ListActivity`, cancellation, shape statistics; being implemented now: `ListActivity` first), `docs/dev-artifacts/design/app-schema-migrations.md` (R1c: `status` / `plan` / `apply` are client-library operations on a migration set compiled into the application: the shell can only show `status` of the journal, it cannot apply), `docs/dev-artifacts/design/format-stamp.md` (R1: epoch, offline migration of the format), the logical export/import design under `docs/dev-artifacts/design/` (R3: offline export/import commands, an online export operation still to come) and `docs/dev-artifacts/design/engine-metrics.md` (R4a). Look at the design documents already in `docs/dev-artifacts/design/` for the house style (summary with a decision table, OBSERVED facts with `path:line` evidence, options, PROPOSED design, tests and acceptance, a PR-sized implementation plan, open questions each with a default answer, a self-review/findings section) and follow it. Write the document in English at `docs/dev-artifacts/design/admin-shell.md`.

## What the design must settle (each as a numbered decision with the rejected alternatives and why)

1. **Packaging:** a separate executable versus a subcommand of `shamir-server` versus a new crate in the `client` or `devtools` group. Evidence to gather from the code: the server's existing subcommands (`crates/server/shamir-server/src/main.rs`), the single-binary and size goals in `CLAUDE.md` ("one binary, under 50 MB, no external runtime dependencies"), the layer rule (the shell is a CLIENT: it uses `crates/client/shamir-client` and the normal protocol, never the data directory, except the commands that by nature run with the server stopped, which stay server subcommands and which the shell only explains), the group limit of 7 crates per group, and how CI selects crates by directory. State the effect on build time and dependency count.
2. **Connection and authentication:** every transport and every login method the Rust client supports today (enumerate them from `crates/client/shamir-client`, `crates/net/*` and the TypeScript client's docs `TRANSPORT_SPEC.md` / `TOKENS.md`: token handshake versus the full secure session handshake; TCP, WebSocket, HTTP, local IPC / Unix socket / named pipe, and whatever else exists). Say which combinations the shell supports in each stage and which are refused with what message; connection profiles (where stored, with which file permissions, never containing secrets); secret entry without echo and never through command-line arguments or history; environment variable and file-descriptor options for scripts.
3. **Command surface:** the full command tree mapped to existing server operations. For EVERY command give the server operation it calls (a `BatchOp`/admin op or client method that exists today, or one that is promised by a named pending task: R4b cancel, export online op, R2d schedule), the permission it needs, whether it is destructive, and its R5a/R5b/R5c stage. Groups from the plan: connection, state (version, format epoch, uptime, replication role and lag), catalogue (databases, repos, tables, indexes, functions; describe table and schema), rights (users, groups, resource rights, owner and mode), activity (sessions and requests, cancel a request), backups (start, status, cancel; verify and restore as explained offline commands; schedule state), versions (format stamp, schema-migration journal status), export/import, diagnostics (integrity, WAL and durability info), and the three narrow data views (show a record by key, first N records, count). Identify the operations that DO NOT EXIST yet and are needed by the commands (list them as prerequisites, each with the task that owns it, or as new work items for this release); do not design around imaginary operations.
4. **Modes and output:** interactive versus batch; the machine-readable output format (decide: JSON lines, with a stable documented schema versioned like the wire formats, plus human tables for interactive use), exit codes (a table), non-interactive confirmation flags for destructive commands, quiet/verbose, color handling, behaviour when output is a pipe. History: whether to keep one, where, and how secrets are kept out of it.
5. **Safety:** destructive-command confirmation (interactive prompt versus explicit flag in batch), how the shell proves it adds nothing beyond the logged-in user's rights (every call goes through the server's normal authorization; no client-side privilege), audit visibility, timeouts and cancellation of long commands, and what it prints on a follower versus a leader.
6. **Dependencies:** list every external crate the shell would need (argument parsing, line editing, table rendering, terminal handling) and prefer what the workspace already depends on; for each NEW crate state why, its license against `deny.toml`, its maintenance status (the advisory gate rejects unmaintained crates: check) and its effect on binary size; the cooldown rule (a new registry version younger than 3 days needs an exception). If a dependency-free approach is reasonable for a stage, say so. NO dependency is added by this step.
7. **Testing and acceptance:** CI-only tests per stage (a scripted batch test against a real server on each transport the stage supports; permission-denied tests; destructive-confirmation tests; output-schema golden tests; secret-leak byte-scan tests on output, history and process arguments), the per-stage acceptance of the plan made observable, and the three-OS expectations (terminal handling on Windows, named pipes versus Unix sockets).
8. **Implementation plan:** at most 4–6 PR-sized steps with, for each: crates and folders touched with entry counts of every folder you propose to add to (several are at the 7-entry limit: count with `ls` and name the concrete home of every new file), the prerequisite operations, the tests, the dependencies (if any) and the order relative to the pending release tasks (R4b steps 2–4, R2d, the export online operation). Mark which steps can start now and which wait for which task.
9. **Open questions** for the owner, each with the default answer you recommend.
