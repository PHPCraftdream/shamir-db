# Brief: R5-2b — fix the confirmed defects of the secure shell transports (independent review of the landed R5-2)

Re-open every path and line before relying on it (lines drift). R5-2 (secure shell transports: native WSS + SCRAM, tokens over HTTPS REST and token WSS, typed refusals, `repo describe`) is landed. A read-only reviewer traced the landed code end to end; the findings below are CONFIRMED by trace but NOT reproduced at runtime: every fix gets a regression test whose red state is observed in CI. Read the design `docs/dev-artifacts/design/admin-shell.md` (transports, tokens, profiles, exit codes section 5) and the committed R5-2 brief `docs/dev-artifacts/prompts/release/61-r5-2-secure-transports.md` first. Shell code: `crates/server/shamir-server/shell/`; shell tests: `crates/server/shamir-server/tests/admin/shell/`; SDK token transport: `crates/client/shamir-client/src/client/transport/token/`.

## What (this step only)

1. **P1: interactive WSS dies while the operator is at the prompt.** `shell/parser.rs` `build_runtime` creates a CURRENT-THREAD runtime and the interactive loop blocks on synchronous terminal input OUTSIDE `block_on`; the SDK reader task (`client/session/client.rs`, spawned) that answers the server's WebSocket Ping with a Pong is therefore suspended between commands. Both WSS listeners ping every 30 s with a 10 s Pong deadline (`shamir-tunables`; `sync/connection/session/writer_task.rs` closes with 4003). Failing sequence: connect over WSS, leave the prompt idle about 40 s, run `ping`: the session is already closed. Fix so background tasks keep running while the shell waits for input (for example a runtime whose worker thread drives spawned tasks, or reading the terminal on a dedicated thread; choose the narrowest change, keep batch mode behaviour and exit codes identical; `block_on` futures need not be `Send`, spawned SDK tasks already are). Test (CI-only): a scripted interactive session over the real WSS listener that stays idle longer than the ping interval plus the pong deadline (read the tunables; use a test-only override of the heartbeat tunables if one exists, otherwise one bounded idle of the real interval is acceptable with a generous timeout) and then runs `ping` successfully; it must fail on the parent commit.
2. **P2: `repo describe` fails for a valid large WAL-retention budget.** The server returns a `u64` budget through `QueryValue::from(u64)`; values above `i64::MAX` become `Big`, serialized as a decimal STRING (`shamir-types` `value.rs`), decoded by the client as `Str`, and `shell/commands/catalogue.rs` (around the budget field) rejects `Str` with exit 5. Accept a decimal string for that field (and any other `u64` field of the description; list which) and render it as a number in the output; refuse non-decimal text with the existing typed error. Test: a unit test of the mapping with `u64::MAX` and with a malformed string.
3. **P2: misclassified failures.** (a) A token issued for REST only, used on the token WSS upgrade, gets a typed `token_channel_denied` (403) from the server, but the SDK decodes it as `ClientError::Db` (`client/transport/token/status.rs`) and the shell's generic 403 arm never sees it: it falls through to `server_error`, exit 5 (`shell/connect/scram.rs`, the error mapping around lines 280-350). Map it to the permission refusal (exit 4, fixed text, NO reflection of server text). (b) A native WSS upgrade rejected before SCRAM (for example a listener on another path) is wrapped as `Handshake` and reported as `authentication_failed`, exit 3 (`client/transport/dial_ws.rs`, `shell/connect/scram.rs`): classify it as a connection failure, not an authentication failure; do not change real authentication failures. Tests: one per mapping using the existing fixtures (a REST-only token on the WSS listener; a profile whose WSS address points at a path the listener does not serve, if the fixture allows; otherwise a unit test of the classifier with the exact SDK error values, and say so).
4. **P2: deadlines match the documented phases.** `shell/connect/token.rs` puts the TLS handshake inside the remaining 10 s DIAL budget while the explicit `connect` authentication Ping in `parser.rs` gets a fresh 60 s request budget: a slow TLS handshake is refused early, a peer that completes TLS and never answers the Ping can hold `connect` about 60 s. Read the design for the documented phases and align the code (each phase bounded, none unbounded); a 408 from the REST server after the request was dispatched must be exit 7 (unknown outcome), not generic exit 5 (`transport-http/src/server/service.rs`, `shell/connect/scram.rs`). Tests: unit tests of the budget accounting and of the 408 mapping.
5. **P2: a relative `ca_path` follows the process working directory.** `shell/connect/token.rs` opens a relative profile `ca_path` against the CWD (and follows links, checking only that the target is a regular file): the same protected profile can select a different trust anchor when started from another directory. Fix in `token.rs` (NOT in `profile.rs`, which is exactly 1000 lines: do not grow it): resolve a relative `ca_path` against the profile file's own directory, or refuse relative paths with a typed profile error (choose what the design says; if the design is silent choose refusal and note it for the guide), and keep the existing protected-file checks. Test: a profile with a relative `ca_path` started from two different working directories gives the same result (or the same typed refusal).
6. **P3: test gaps that make green meaningless.** (a) The scripted REPL helper in `tests/admin/shell/secure_transports.rs` manufactures an empty `stdout` instead of capturing it, so its leak scan of stdout is vacuous: capture the real output. (b) The operator-home file scan rejects only names containing `history`: scan the CONTENTS of every file the shell created under the operator home for the canary token, password and its suffix, regardless of the file name; add the same post-run scan to the new SCRAM-over-WSS probes. (c) No test exercises the auth-specific `SHAMIR_SHELL_TOKEN` route: add one probe that proves the variable is read for the token transport only and never echoed. (d) `DescribeRepo` over a token session is refused by the CLIENT allowlist and also by the SERVER (`token_request_denied`, `shamir-server-security` `http_rest/scope.rs`): add a direct SDK control that sends `DescribeRepo` with a token on both endpoints and expects the server refusal, so removing the server refusal turns a test red.

## Layout and fixture lessons

Count every folder you add to with `ls` (many are at 7 entries: `python -I scripts/ci/check_layout.py` counts only tracked files, recheck after staging); at most 1000 lines per file, one primary item per file, `mod.rs` re-exports only (the rust-guard structure gate allows nothing else in a `mod.rs`: shared helpers go in a named file), tests in `tests/` folders, no inline `#[cfg(test)]` modules, no local `use`, no new `#[allow]`. Persistent stores, every `TempDir` alive for the whole test, close handles and wait for the server task to finish before reopening a directory (Windows holds Fjall locks until the dropped engine's background handles finish: reopen with a bounded retry on `Locked` only, like `init_waiting_for_locks` in the function-family crash tests), handshakes not sleeps, every await bounded by a generous timeout (at least 120 s: a hang detector, the Windows runner is up to 10x slower), a batch is at most 50 queries, per-session request rate limit 500 req/s (never poll in a tight loop: pace status polls at 20 ms or more), set `argon2_concurrent_max` and `auth_init_rate_per_second` to 64 in fixtures that open several sessions, debug-test stacks are small (call concrete handlers through `Box::pin`, run deep tests on a roomy thread, `on_big_stack`), assert on invariants and sets, `shamir-test-diag` marks for flake-prone tests.
