## Binding design (decided by the orchestrator; do not redesign, do not add a configuration key)

* **D1 — bounded admission BEFORE the blocking pool.** `ScramDerivationGate` gets an admission counter: a request is admitted only while fewer than `2 × capacity` derivations are admitted (running or waiting for a permit; `capacity` is the configured `argon2_concurrent_max`, saturating multiplication); beyond that it is refused at once with the same typed `Busy`, counted once, and nothing is submitted to the blocking pool. The admission ticket is an RAII value owned by the blocking job (not by the async future), so it is released when the job ends even if the request future was dropped.
* **D2 — the 3-second wait is measured from admission.** The absolute deadline is computed at admission (before `spawn_blocking`) and passed to the semaphore, so time spent queued in the runtime's blocking pool counts against it; an unreadable clock or an overflow at admission is a counted `Busy` as before.
* **D3 — the semaphore's wait loop is exact.** In `shamir-connect` (`server/limits/argon2_semaphore.rs`, whose only production caller is now this gate): the release path synchronises with the waiters' mutex before notifying (no missed wake-up between a waiter's availability check and its timed wait); the waiter checks the deadline BEFORE a late acquisition attempt (a waiter resumed after the deadline returns `None`, it never starts a derivation); the length of one timed wait is bounded by a monotonic remaining-time measure so a clock stepped backwards cannot extend it beyond one polling slice (keep the existing injectable-clock test seam working; if a fully monotonic rewrite is disproportionate, bound each slice and say so).
* **D4 — what the series mean.** `shamir_argon2_busy_refusals_total` counts refused requests (admission refusals plus acquisition timeouts/clock failures), one per refused request, not delivered responses; `capacity − available` is an estimate of running derivations, not an exact holder count.

## Appendix — the reviewer's report (verbatim)

VERDICT: FAIL

The branch gates both live SCRAM account-creation paths with the same boot semaphore. It does not bound the backlog ahead of that semaphore, and some callers lose the typed refusal. Findings below are **confirmed by source tracing**, not by running the server or tests. Reviewed `origin/master...HEAD` at `5206c5bbc` against the committed brief `docs/dev-artifacts/prompts/release/72-argon2-gate.md`.

## Findings

1. **P1 — CONFIRMED: Argon2 waiters can occupy the shared blocking pool, and queue time is outside the three-second deadline.** `crates/server/shamir-server-security/src/security/user_directory/derive_scram_record.rs:71–80` submits every request to Tokio before admission; `crates/server/shamir-server-security/src/security/user_directory/scram_gate.rs:87–102` starts the deadline only once that job runs, after salt generation. Neither the foreground nor Windows-service runtime overrides Tokio’s default of **512 blocking workers**, independent of `argon2_concurrent_max` (`crates/server/shamir-server/src/main.rs:344–348`, `crates/server/shamir-server/src/boot/policy/windows_service.rs:152–157`). With capacity one, a sufficiently large concurrent provisioning burst can leave one derivation running and the remaining blocking workers waiting. Additional creations then queue without their deadline running; unrelated WAL fsync and HTTP-login verifier lookup queue behind them (`crates/storage/shamir-wal/src/segment/wal_segment.rs:478–502`, `crates/server/shamir-server-security/src/security/perimeter/http_login/service/begin.rs:265–278`). Blocking audit submissions share that pool too; the online backup runner itself has a dedicated thread (`crates/server/shamir-server/src/engine/db_handler/repo_admin/repo_audit.rs:302`, `crates/server/shamir-server/src/boot/config/diagnostics/backup_online/registry.rs:363–365`). The native connection cap and 32 in-flight slots per connection bound *live dispatches* when the cap is enabled, not detached jobs or the Tokio queue. There is no Argon2-specific waiter bound. A bounded queue or admission before submission would protect unrelated blocking work.

2. **P2 — CONFIRMED: the semaphore can miss a wake-up and admit after its deadline.** `crates/net/shamir-connect/src/server/limits/argon2_semaphore.rs:101–118,128–133` checks availability under the waiter mutex, but release increments and notifies without taking that mutex. If release lands between the last failed check and `wait_timeout`, the waiter can sleep for up to another one-second polling slice even though a permit is free. The timed recheck prevents a permanent lost-wake deadlock; the holder also needs no other blocking task to finish. But the loop tries acquisition **before** checking expiry, so a waiter resumed after three seconds can still start a KDF. Moreover, `UnixNanos::try_now()` uses `SystemTime`, not a monotonic clock (`crates/net/shamir-connect/src/common/runtime/time.rs:24–36`): a backward clock step extends the elapsed wait without producing a clock error. These are inherited semaphore mechanics made live by this branch, not a hard three-second admission guarantee.

3. **P2 — CONFIRMED: transactional `CreateUser` can lose the busy code or appear to succeed.** With an existing table read to select the repository and a signed create in a strict transactional batch, the port’s `ServerBusy` reaches `BatchError` but is converted to `Ok(..., transaction.status = "aborted")`, with the error debug-formatted into the reason rather than emitted as a stable code (`crates/engine/shamir-engine/src/query/batch/exec/batch_execute/transactional.rs:237–301`, `crates/engine/shamir-engine/src/query/batch/runner/query_runner/helpers.rs:155–160`). Rust and TypeScript `execute` return that batch normally; Node encodes it as success too. A provisioning caller checking only that the call resolved can report success for an account that was not created. Worse, a transactional `ForEach` body’s abort metadata is discarded by `execute_planned_batch_impl`, so the outer request can resolve with an empty iteration result and no abort metadata to inspect (`crates/engine/shamir-engine/src/query/batch/exec/batch_execute/executor.rs:414–452`, `crates/engine/shamir-engine/src/query/batch/runner/query_runner/arms_read.rs:450–495`). Ordinary nontransactional errors and interactive `TxExecute` preserve the code.

4. **P2 — CONFIRMED: two other response boundaries drop the classification.** First, a signed nontransactional create with the pool held and `max_result_size: 1` is refused and counted, but native `Execute` replaces the encoded busy reply with `result_too_large`; only cancellation bypasses that final size check (`crates/server/shamir-server/src/engine/db_handler/repo_admin/execute.rs:218–221,318–365`). Second, an authorized stored function that provisions a user through `db_execute` reaches the same gated port, but the WASM host stringifies the gateway error and the outer `Call` builds a `QueryError` with `code: None`. The client gets `query`, not a retryable busy error (`crates/engine/shamir-db/src/shamir_db/shamir_db/db/db_gateway.rs:150–172,264–282`, `crates/wasm/shamir-wasm-host/src/wasm/bindings/db.rs:194–198`, `crates/engine/shamir-db/src/shamir_db/execute/core/function_invoker.rs:45–53`). Neither is a KDF bypass.

5. **P2 — CONFIRMED: the protocol still gives client implementers the wrong account-creation contract.** `docs/guide-docs/client-server-protocol-spec/AUTH_PROTOCOL.md:13–15,682–701` still says passwords never leave the client and shows `createUser` sending prederived keys. The live `CreateScramUser` request carries a password string and an HMAC field, and the server derives the keys (`crates/query/shamir-query-types/src/wire/db_message.rs:86–105`, `crates/server/shamir-server/src/engine/db_handler/handlers/admin.rs:80–98,150–163`). A client built from §12.1 cannot create the user. The same spec says self-service password change was removed (`AUTH_PROTOCOL.md:799,879`), despite the live `ChangePasswordChallenge`/`ChangePasswordVerify` arms. Its `server_busy` examples at `:98,900` promise `retry_after`; the new post-auth DB refusal carries only code and message.

6. **P3 — CONFIRMED: operational docs overstate what the signal and memory estimate mean.** `docs/guide-docs/guide/07-operations.md:247,864–870,1894–1905` and both boot call sites agree about what is gated. The fixed, nonconfigurable three seconds is a nominal *permit wait after the blocking job starts*, not a request deadline. `capacity × kdf_defaults.memory_kb × 1.05` is a reasonable estimate for **gated KDF working memory**, not peak process memory: waiters do not allocate an Argon2 matrix, but queued jobs keep passwords and task state, and active waiters use thread stacks. Bootstrap rotation, follower-side SCRAM, and SQL Argon2 can add memory independently. `docs/dev-artifacts/design/engine-metrics.md:95` also overstates `capacity − available` as a holder count: a failed optimistic decrement can temporarily hide a free permit until the increment restores it. The `server_busy` table entry is not exhaustive: session-slot admission already emits that code without incrementing the Argon2 counter (`crates/server/shamir-server/src/engine/db_handler/repo_admin/activity/requests.rs:70–84`). The TypeScript classification also marks that existing code retryable; neither SDK retries automatically, and replaying a mixed batch is not safe merely because `.retryable` is true.

7. **P3 — CONFIRMED: remaining guide drift can send operators to the wrong settings or metrics.** `docs/guide-docs/architecture/LOGIC_FLOW.md:85–91` puts gated user creation on the login path; it runs **after** authentication, whereas the first bootstrap-token login can trigger an **ungated** rotation. `AUTH_PROTOCOL.md:511` describes only random-password bootstrap, but there is also explicit-password boot. `docs/guide-docs/client-server-protocol-spec/IMPLEMENTATION_GUIDE.md:168–176` places the renamed top-level key inside `[kdf]`; `:624,637` lists two unexported Argon2 series; `:647–655` lists the refusal counter under gauges and attributes increases only to timeout/saturation, although clock failure also counts. The component and initial-auth diagram edits correctly move the gate off SCRAM. The old story is still implied by `AUTH_PROTOCOL.md:226` (mismatched login forces Argon2 on the server), `diagrams/10-session-lifecycle.md:16` (native pre-auth `server_busy`), and the four shipped `deploy/server*.example.ktav` comments (`:53`, `:52`, `:52`, `:61` in the general, small, medium, and large profiles respectively). Actual HTTP/token admission has separate busy responses; those should not be removed or relabelled as Argon2 refusals.
