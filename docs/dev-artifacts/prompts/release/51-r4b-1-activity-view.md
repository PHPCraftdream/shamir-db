# Brief: R4b step 1 — the activity view: minted session handle and request id, in-flight table, `ListActivity` operation (types, builder, Rust client, server handler, permission), activity gauges

Design (settled, read first): `docs/dev-artifacts/design/operational-views.md` — §0 decisions D1–D5, D13, D14, D19, D20; §1 (map of what exists: request travel, identifiers, registries, admin dispatch, primitives to reuse); §2 (activity view: the four row kinds, hot-path cost, privacy rule, paging); §5.1–§5.4 (surfaces, permission default, client methods, metrics); §6 (the tests named `activity_view_under_load`, `activity_privacy_no_literals_or_credentials`, `permission_denial_activity`); §7 step 1 (this step) and the notes on steps 2–4 that this step must NOT do. Release gate it serves: "the operator can find a stuck query" (`docs/dev-artifacts/release-1/04-observability.md`, acceptance R4b-1). The design's `path:line` citations are from before several landed PRs: re-open every cited file and trust the code, not the line numbers.

## Why

Today the server knows everything an operator needs (sessions, interactive transactions, cursors) but exposes none of it, and running batches are not tracked at all. Without a safe listing there is nothing to cancel in the next step. The listing must be cheap on the hot path, bounded, lock-free for the reader, and must never leak credentials or query literals.

## What (this step only)

1. **Minted session handle (D3).** `SessionStore` (`crates/net/shamir-connect/src/server/state/`, `session.rs` and its store) assigns a non-secret numeric handle from an `AtomicU64` at `insert` and keeps it alongside the 32-byte key; expose a read accessor. The handle is what rows and (later) cancel targets use; the 32-byte token and its 8-byte prefix NEVER appear in any new row, log line or metric label.
2. **`RequestExecId` and the in-flight table (D5, D2, D8 groundwork).** In the server db handler (`crates/server/shamir-server/src/engine/db_handler/`) mint `RequestExecId(pub u64)` from a handler-local `AtomicU64` (like `next_cursor_id`) when a BATCH is admitted; the client `rid` stays optional and is carried alongside, not replaced. Add a lock-free in-flight table (`scc::HashMap` or `DashMap` with `shamir_collections::THasher`, per the project ideology; no `Mutex`/`RwLock`, no `len()` on scc maps) whose entry holds: id, session handle, user, db, op-kind summary (kind NAMES only: `read` / `write` / `tx_open` / `admin:<op>`; derived from the already-parsed operation discriminant, never from arguments), start timestamp (`AtomicU64`), and a state word `AtomicU8` with `Running` and `Done` ONLY in this step (the `Running → Committing` / `Cancelled` CAS wiring is step 2; do not add it, but leave the word and its documented encoding so step 2 only adds transitions). Registration is one insert and deregistration one removal, done by an RAII guard so a panic or early return cannot leak an entry. `AtomicUsize` mirrors next to each registry (requests, sessions, interactive transactions, cursors) feed the gauges; gauges never call `len()`.
3. **Types, builder and client.** New typed admin `BatchOp` `ListActivity` with DTOs in `crates/query/shamir-query-types` (the `ListActivityReq { scope: All | Own, kind: Sessions | Transactions | Cursors | Requests | All, limit, continuation }` and `ActivityPage { rows, continuation }` of §5.1; follow the existing admin op / `DbResponse` conventions of the recent `StartBackup` / `ApplicationSchemaStatus` additions for the op kind classification, the response variant and the serde shape), builders in `crates/query/shamir-query-builder/src/wire/` (find the right module; the design suggests a new `admin/` module mirroring `token_admin/`; respect the 7-entry limit), and the Rust client method `list_activity` in `crates/client/shamir-client` following the naming of its neighbours. NO TypeScript client in this step (a separate step follows the TypeScript migration client to avoid conflicting edits). Rows: SESSIONS (minted handle, user, transport, created-at, age from `last_activity_ns`, open tx count, open cursor count), TRANSACTIONS (tx handle, owning session handle, user, state `active` / `awaiting_commit` / `expired_pending_reap`, idle time), CURSORS (cursor id, owning session handle, user, table NAME only, pinned snapshot version, open duration), REQUESTS (id, session handle, user, db, op kind, state `running` / `done`, elapsed). Sources are the existing registries (`SessionStore`, `TxRegistry` in `crates/server/shamir-sync/src/sync/durability/tx_registry.rs` — it lives in the server layer, `CursorRegistry` in the server crate) plus the new in-flight table: no new source of truth.
4. **Privacy (D3).** Rows carry ids, actor, db, op kind, timing and state only — never filter values, literals, row data, message bodies, canonical query bytes, the bearer token or its prefix. This is a tested property (item 7), not a convention.
5. **Paging and bounds (D4).** Opaque continuation token (registry kind + last-seen key + snapshot sequence), `limit` with a global cap on rendered rows per call (default 256), copy-on-iterate (snapshot the keys of the requested kind, sort, render up to the limit, continue past the last key); the reader holds no lock a writer takes; a momentarily torn snapshot is acceptable and documented. Per-session cap aligned with the existing admission caps.
6. **Permission (D13, D19, §5.2).** New `ResourcePath::ActivityView` global-singleton variant (follow the `WasmCompiler` precedent in `crates/foundation/shamir-types`; a `shamir-types` change, list it as a widening). `scope: All` (other users' work) requires `ActivityView` + `Action::Manage` through the normal `authorize_access` path, NOT the coarse admin gate; add the op to the coarse-gate exemption list the way the design says. `scope: Own` is open to any authenticated user and returns only rows whose user matches (read-only). Follower behaviour: read-only listing is allowed on a follower (state it and test it).
7. **Metrics (§5.4, this step's part).** Gauges `shamir_active_requests`, `shamir_active_sessions`, `shamir_active_transactions`, `shamir_active_cursors` exported through the server's existing observability render path (the pattern of the recent query-metrics and backup-metrics exports in `shamir-server` / `shamir-server-security`), reading the mirrors, no per-user or per-session labels. Cancellation counters and `shamir_shapes_tracked` belong to later steps: do not add them.
8. **Tests (CI-only, deterministic; names of design §6 as the starting set).** `activity_view_under_load` (`shamir-server` `tests/`: 50 concurrent sessions / transactions / cursors; `ListActivity` returns a consistent bounded page; the continuation walks to exhaustion; every counted row is accounted for), `activity_privacy_no_literals_or_credentials` (a query containing distinctive literals plus a live session: the serialized activity DTOs contain none of the literals, not the 32-byte token and not its 8-byte prefix, by byte scan), `permission_denial_activity` (ordinary user `scope: All` → `permission_denied`; `scope: Own` → own rows only), in-flight RAII (an aborted/panicking request leaves no entry; a completed request is removed), gauge/mirror agreement, the DTO serde round trip and builder golden shape in the query crates, the session-handle uniqueness/monotonicity test in `shamir-connect`. Follow the existing test layouts and fixtures (`crates/server/shamir-server/tests/`, `.../db_handler/tests/`); read them before writing.

## Do not

Add cancellation of any kind (no `CancelRequest`, no `cancelled` code, no CAS on the state word, no wake primitive), shape statistics, wait-state recording, the TypeScript client, guide text (the operator guide is written in the last R4b step; metric descriptions belong to the metrics-guide task), or a new dependency; touch the hot path beyond one insert and one removal per batch; call `len()` on an scc map; put any credential material in a row, a log line or a label; construct wire values by hand (builders only); widen an existing item beyond what the new code needs (list every widening, expected: `ResourcePath` variant, `SessionStore` accessor, op-kind classification tables, the coarse-gate exemption).

## Layout — plan it BEFORE coding (many folders are at the 7-entry limit)

Count with `ls` every folder you add to (`shamir-query-types` `src/admin/types/` and `src/ops/batch/ops/`, `shamir-query-builder` `src/wire/`, `shamir-connect` `src/server/state/`, `shamir-server` `src/engine/db_handler/` and its `handlers/`, `shamir-client` `src/` and `src/client/` — several are exactly 7). A new sibling in a full folder is an eighth: put new code in a new topical subfolder that has room, or make a rename-only move in its own described change (git-detectable renames, no behaviour change, re-exports keeping public paths). `python -I scripts/ci/check_layout.py` counts only TRACKED files, so re-check after the orchestrator's `git add`. At most 1000 lines per file, one primary item per file, `mod.rs` re-exports only, tests in `tests/` folders (no inline `#[cfg(test)]` modules), no local `use`, no new `#[allow]`.

## Test fixture checklist (every item failed in CI on earlier steps)

* Keep every `TempDir` alive for the whole test; close handles before reopening a directory; one runtime per test; handshakes not sleeps; every await bounded; a batch is at most 50 queries; distinct aliases.
* Debug-test stacks are small: do not call the giant `execute_admin` directly from a test thread; keep async runners small and `Box::pin` large awaits; deep real-server tests run on a roomy thread (`on_big_stack` pattern of the `shamir-db` schema-migration tests) or use the e2e harness's runtime.
* Concurrent outcomes: assert on invariants and sets, never on a join order or exact counts of racing operations.
* A new test that can flake carries failure-only diagnostics (`shamir-test-diag` `FlakeGuard`, `with_watchdog`).

## Rules that bind the change

* Machine memory: at most ONE cargo command at a time, always as `RUSTC_WRAPPER= wnice -p idle -c 50 -t 8 -m 50 -- cargo ... -j 1`; never pipe cargo output through `tail`/`head` — redirect to a file outside the repository and read it. Leave no scratch files in the tree.
* Wrap-up: by 150 minutes bring the change to a compiling, formatted, clippy-clean state and stop; say in the final report what is missing.

## Policy (verbatim, binding)

Compilation, builds and tests run on GitHub CI, not on this machine. Banned locally: `cargo test`, `cargo nextest`,
`./scripts/test.sh`, `cargo build`, `cargo run`, `cargo bench`, `cargo doc`, npm/tsc builds, any build or test run.
Allowed locally only: `cargo check -p <crate> --all-targets`, `cargo clippy -p <crate> --all-targets -- -D warnings`,
`cargo fmt -p <crate>` (and `-- --check`), `python -I scripts/ci/check_layout.py`.

⛔ NEVER run `git reset` / `checkout` / `clean` / `stash` / `restore` / `rm`, or any git command that mutates the working
tree or index. Only edit files; the orchestrator commits. (For file moves use a plain filesystem move and say so in the report;
the orchestrator stages them so git detects the renames.)

## Observable acceptance

`cargo fmt`, `cargo clippy --all-targets -- -D warnings` for every touched crate (expected: `shamir-types`, `shamir-connect`, `shamir-query-types`, `shamir-query-builder`, `shamir-client`, `shamir-server`, possibly `shamir-server-security` and `shamir-sync`) are clean; layout limits hold with counts reported; `ListActivity` returns the four row kinds from the existing registries plus the in-flight table with minted ids only, pages with a continuation and a cap, enforces the `Own` / `All` permission split, and carries no credential or literal (byte-scan test); the four gauges are exported from the mirrors; the in-flight entry carries the state word with `Running` / `Done` and is removed by RAII on every exit path; no hot-path lock was added.
