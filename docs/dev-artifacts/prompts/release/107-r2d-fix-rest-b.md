## Why

1. **The inherited copy path can silently omit files and silently fail cleanup** (`sync/online/copy_engine.rs`, `sync/online/protocol.rs`). A directory-entry or metadata I/O error while enumerating a source directory can drop a file from the listing: the manifest is generated from what was listed and verification checks the manifest, not completeness against the source. A failed destination `create_dir`/`File::create` returning `NotFound` is treated as a vanished SOURCE file (the tolerated race) instead of a destination error. A direct write or fsync failure propagates, but when the removal of the partial tree also fails the cleanup error is discarded.
2. **Scheduled failures can expose filesystem paths** (`sched/registry.rs`, `sched/admin_port.rs`, `sync/online/copy_engine.rs` error rendering). A destination write failure can put the absolute SOURCE path into `BackupStatus.last_error` for a scheduled run, and the scheduled preflight can forward the configured path in an overlap error. `BackupStatus` is a privileged response, but a scheduled run has no operator who asked for a path and the same text reaches logs and status.
3. **The failure streak and the copy outcome are published too late and too loosely** (`sched/registry.rs`, `sched/schedule/runner.rs`, `sched/metrics.rs`). After three failures a successful copy updates `last_success` at once, but a long retention pass keeps the failure streak active until the registry sends completion; an unwind AFTER protocol success closes the completion channel and counts the copy as failed. The guide also calls the legacy duration gauge "last finished" in one section and "last successful" in another; the implementation is success-only. The new counters saturate and use `absolute`; the new gauges go through the shared recorder and can be overwritten by an older concurrent scrape.
4. **The stale alert can stay silent through repeated restarts without a single backup** (`deploy/alerts/shamir-backup.rules.yml`, `sched/metrics.rs`, `sched/schedule/runner.rs`). With the documented default `run_on_start = false`, a 24-hour interval and a server restarted every 12 hours no tick is ever reached and every restart resets the in-memory fallback timestamp before the 36-hour alert threshold. A forward wall-clock step at success followed by a correction can also suppress staleness until the future timestamp is reached.
5. **The tests miss the production lifecycle and the alert inputs** (`server/engine/server/server_launcher/tests/` backup schedule tests, `sched/schedule/tests/`, `scripts/ci/tests/gates/test_backup_alert_rules.py`). The live test substitutes the production spawn callback and cancels its own scheduler before calling shutdown, so removing the production join is not detected; the unit shutdown test makes its own child token, so it does not verify the registry's production token binding. The rule test checks the text of the expressions and metric names found in the source, so a gauge that is always zero still passes. The live fixture relies on two real seconds between ticks and on second-resolution wall-clock names.

## What (this step only; do the items in this order, stop adding scope at 60 minutes)

1. **Copy path errors (finding 1).** In the source enumeration of `copy_engine.rs` propagate every directory-entry and metadata error EXCEPT an explicitly tolerated source disappearance (`NotFound` of an entry that vanished between listing and open, as today); a destination-side `create_dir`/`File::create`/rename/fsync error is a destination error with its own typed variant or kind (never mapped to "source vanished"); when a copy fails and removing the partial tree also fails, report the cleanup failure SEPARATELY from the original failure (the original error stays the primary one; the cleanup failure is added as a bounded, path-free reason in the typed error or the status stage). The existing fault-injection seams of the copy tests are the place for tests: an enumeration error is a typed failure and no manifest is produced; a destination `mkdir` failure is a destination error; a removal failure after a failed copy is reported. Keep every existing behaviour of a healthy copy and of the tolerated source race.
2. **Path-free scheduled errors (finding 2).** Every failure of a SCHEDULED run (preflight, copy, verify, retention warning that reaches status) is rendered from a stage name plus a bounded reason (an enum or the I/O error KIND name, never the OS error text and never the error chain's `Display`) before it is stored in `last_error`, logged by the scheduler or turned into a metric label. A configured destination or source path never appears in these strings. The manual admin backup path and the intentional path fields of the privileged `BackupStatus` response stay as they are (say so in the report with `path:line`). Tests: a canary path component placed in the destination and in the source tree, a failing scheduled run through each failure stage that is reachable in tests, and an assertion that `last_error` and the captured log lines contain the stage and the kind and NOT the canary.
3. **Copy outcome and failure streak (finding 3).** The outcome of the copy (success or failure) is published at protocol completion, BEFORE retention starts: the failure streak resets and `last_success` advances at that moment; admission stays held through retention (verify: it already is; a manual copy and the next tick are still refused while retention runs). A panic or unwind in retention after a successful protocol is a RETENTION failure (the existing retention failure counter), never a copy failure and never a lost completion. Render the new gauges from the scrape's own snapshot (or document precisely why the shared recorder cannot go backwards: decide, state the decision) and keep the counters monotonic. Align the guide: one meaning for the duration gauge ("last SUCCESSFUL copy"), everywhere it appears.
4. **Restart-independent staleness evidence (finding 4).** Keep the cadence in memory. Persist the wall time of the last successful scheduled (or manual) copy durably in an EXISTING small durable store of the server (find the smallest suitable one, for example the server meta store; do not scan the backup destination at boot and do not add a dependency or a config key), write it at copy success (not at retention end), seed `shamir_backup_last_success_timestamp_seconds` from it at boot, and clamp a value in the future to "now" when it is read so a forward clock step cannot hide staleness. State in the guide that a restored data directory carries the persisted value of the backup it came from. Update the alert guidance (`deploy/alerts/shamir-backup.rules.yml` comments and the guide triage text) to say what the persisted evidence means; the thresholds stay.
5. **Tests that prove the lifecycle and the alert inputs (finding 5).** (a) First read what ORDERED-SHUTDOWN's tests (`server_launcher/tests/shutdown/`) already prove about the scheduled worker and do not duplicate them. A live test that uses the PRODUCTION spawn path: park a real scheduled worker inside a copy or a retention step (an existing pause seam or a test hook), start the production shutdown, assert that shutdown WAITS for the worker (the worker's cleanup is observable) and that the registry's production cancellation token, not a test token, is what stops it. Mutant: remove the production join. (b) For every alert input (`shamir_backup_last_success_timestamp_seconds`, the consecutive-failure gauge, the retention-failed counter) assert its live type and a non-vacuous value on the real `/metrics` route after the matching event (a success moves the timestamp, a forced failure moves the streak, a retention failure moves the counter). (c) Do NOT add `promtool` or any CI tool in this step: the repository has none; if you think evaluating the rule file needs one, say so in the report (the orchestrator asks the owner). (d) Inject the UTC naming time together with the tick time in the live fixture so that it does not rely on two real seconds; the admin timestamp assertion must not depend on the wall clock not stepping back.
6. **Guide (Russian, `docs/guide-docs/guide/07-operations.md`, the scheduled backup section) and design (`docs/dev-artifacts/design/backup-schedule.md`).** Describe exactly what the code does after items 1 to 5: the path-free scheduled errors and their stage/kind vocabulary, the cleanup-failure report, when the streak resets, the duration gauge meaning, the persisted last-success evidence (and its restored-directory caveat), the shutdown ordering that already landed, and the triage steps for `BackupFailing`, `BackupStale` and `BackupRetentionFailing` as they are named in the alert file.
