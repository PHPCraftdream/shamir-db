## Why

Applications written in TypeScript ship the same ordered, checksummed migration set as Rust ones, against the same journaling, fencing and reconciling server. The checksum the TypeScript client computes for a body MUST be byte-for-byte the checksum Rust and the server compute, otherwise a set authored in one language drifts against a journal written by the other. The shared vector file is the contract; this step makes TypeScript pass it and gives TypeScript applications the same safe path (compare before sending, one ordinal, never resend after an uncertain outcome).

## What (this step only)

1. **Migration set in the TS client.** A typed migration-set object: stable id, ordinal, display name, function dependencies, an ordered list of typed operations covering EXACTLY the 19 admitted operation kinds (table create/drop/rename; index create/drop/rename; schema set/add/remove; function create/drop/rename/check/alter; validator create/drop/rename/bind/unbind). Operations are composed with the EXISTING builders in `src/core/builders/ddl/` (`ddl-schema.ts`, `ddl-index.ts`, `ddl-func.ts`, `ddl-misc.ts`) plus thin migration-specific wrappers; the DTO shapes are already in `src/core/types/schema/ddl.ts`. Set construction validates (ordinals contiguous from 1, unique ids, admitted kinds only, the same body rules as the Rust model) and throws a typed error. No filesystem discovery, no raw wire objects, no callbacks.
2. **Canonical encoder v1 in TypeScript.** `canonicalBody(body)` and `checksum(body)` = SHA-256 over `domain_separator || canonical_version(u16 BE) || canonical_body` exactly as `canonical/body.rs`. Reuse the existing TS mirror of the per-operation HMAC encodings (`src/core/protocol/hmac.ts`: `canonicalBatchOp`) for the operations Rust encodes through `crate::hmac::canonical_batch_op` (drop table/index/function/validator, create function/validator); add encoders for the rest from `canonical/ddl.rs`. Do not change `hmac.ts` behaviour (its own tests stay green). SHA-256 comes from a dependency the package already has (`@noble/hashes`, or the existing `Platform.sha256`); NO new dependency. Pitfalls named by the vector notes: every length/count is u32 BE; u64/i64 need `bigint`-safe encoding (`DataView.setBigUint64`), never `number` arithmetic above 2^53; f64 rule bounds are bit-exact including negative zero (`DataView.setFloat64`, no normalization); strings are UTF-8 with no normalization (`TextEncoder`); dependency rows and each dependency-name list are sorted by UTF-8 BYTES, not by JS string comparison (UTF-16 order differs for astral characters); operations keep authored order; optional values are `0` or `1 || value`.
3. **Wire builders for the three admin operations.** `ApplicationSchemaStatus`, `ApplicationSchemaPlan` and `ApplyApplicationSchemaMigration` do not exist in the TS types yet (no `schema_migration` hit under `src/`). Add the TS DTO types and builder entry points producing EXACTLY the serde wire shape of the Rust DTOs in `.../protocol/` (`request.rs`, `status.rs`, `plan.rs`, `apply.rs`, `admin_op.rs`) and the Rust wire builders; check whether these operations carry a session HMAC tag in Rust and mirror that precisely. The status result includes the additive `fence_generation` (number/bigint per the package's existing u64 convention) and `applied` (id, ordinal, 32-byte checksum) fields added in step 3a. This is a widening of the TS batch-op union: list it.
4. **Client operations** (a migration client object composed over a `DbHandle`/`ShamirClient`; do NOT grow `client.ts` or `db.ts` unless unavoidable): `status(db)`: compares the journal with the local set — applied prefix (verify every applied entry id/ordinal/checksum against the local set), next local ordinal, DRIFT, GAP, local set shorter than the journal, in-flight owner/status, in-doubt operation index and reason; pure read. `plan(db)`: the server plan for the next ordinal; never writes. `applyNext(db)`: refuses BEFORE any send on drift, a gap, a changed checksum of an applied body, or nothing left; otherwise sends exactly ONE next ordinal with the expected predecessor and the fence generation read from status (a non-empty journal reported WITHOUT `applied`/`fence_generation` is an unsupported-server error, never guessed).
5. **No blind retry (§5.3).** A transport error, timeout or close after an apply was sent returns/throws a dedicated typed error carrying "outcome unknown; query status" plus an attempt token, and does NOT resend. IMPORTANT to verify in `src/core/client/client.ts` and the protocol/session layers: that no code path (reconnect, resume ticket, timeout "retryable" classification at `client.ts` ~l.320 / ~l.393, subscription router) can resend an apply request or tell the caller to; the apply path must ignore any `retryable` flag on errors. `resolveUnknownApply` runs `status` for the same migration id: applied with the same ordinal and checksum → success; in-flight / in-doubt → the typed in-doubt error with the server's reason; not applied → tells the caller it is safe to call `applyNext` again (the identical-body server resume is reachable through `applyNext`; document it).
6. **Typed errors.** One TS error class/union mapping the stable server codes of §5.3 (`schema_migration_in_progress`, `_in_doubt`, `_checksum_mismatch`, `_gap`, `_predecessor_mismatch`, `_follower_read_only`, `_durability_unavailable`, `_postcondition_failed`, `_identity_mismatch`) and the `schema_migration_operation_deferred:` prefix, keeping the server message; an unknown typed operation from an old server becomes a distinct unsupported-server error. Follow the package's error conventions (`src/core/support/errors.ts`). No fallback to individual DDL calls anywhere.
7. **Vector test against the shared file.** `crates/query/shamir-query-builder/tests/fixtures/schema_migration_canonical_vectors.json` (4 cases, every one of the 19 kinds, dependency ordering, optional fields, ordering/ordinal pin set) is read by the TS test directly from that path (relative to the test file; do not copy or fork the file); for every case rebuild each body from the TS typed builders using the structured `args` (absent arg = DTO default), assert canonical bytes hex and SHA-256 hex equal the file.
