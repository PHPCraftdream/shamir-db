## Why

The independent reviews of R2d (steps A and B) and of the ordered shutdown left CONFIRMED defects, missing oracles and imprecise texts that were deliberately not fixed at landing. Each item below is a confirmed finding: fix it, do not defer it. One of them is a performance defect by the project rule ("a slow test is a bug"): a scheduled run of a TINY data directory costs about 18 s on the Ubuntu runner and about 50 s on the Windows runner.

## What (fix in this order; for each item write the failing test first where a test is possible)

### A. Scheduled-run cost (P2/performance)
1. One scheduled copy of a tiny directory costs 18 s (ubuntu) and 50 s (windows) in the live tests (`server/engine/server/server_launcher/tests/backup/`: 15-21 s and 52-64 s per test, against the 180 s kill). Find where the time goes with evidence (the CI logs of the last full run and the code: two-pass copy with per-file and per-directory fsync, destination re-authentication, a self-verify with a full re-hash, sharing-violation retries at 5 x 100 ms on Windows, the scheduler's own minimum waits, engine open, capture barrier, seal budget) and remove what is not needed WITHOUT weakening a guarantee (durability of the published bytes, the self-verification, the ordered shutdown). Say per candidate what you measured or read and what you changed; a change that the code cannot justify by reading is not made.

### B. Open items of step B (from the independent review and my own read of the test split)
2. Panic after the published outcome is counted twice: `server/boot/config/diagnostics/backup_online/registry.rs` (around the publication of the outcome and `RunGuard::Drop`, which calls `note_finished(true, ...)` after a panic between the publication and the end of the retention pass): the scheduler notes `Completed` while `failed_total` and `active` are closed as a failure, contradicting the module's own statement ("a panic there is ONE retention failure, never a copy one"). Count once; test with an injected panic seam in the retention pass.
3. An unreadable armed-at row is treated as absent and re-armed with the current time on every boot (`.../backup_online/metrics.rs`, `arm_schedule_clock`: `if let Ok(Some(..))`), which resurrects the original stale-alert defect; the guide and the alert comment call the row the durable FIRST arming unconditionally. On a read error do not overwrite (use `now` for this boot without writing), warn without a path, and say so in the guide.
4. The process-global `schedule_enabled` is derived from `schedule_started_timestamp_seconds`, which is only ever set (`enable_schedule`): a second launch in the same process without a schedule keeps `schedule_enabled == 1` and `BackupStale` can fire for a schedule-less server (impossible in a fresh process, possible in tests and embedding). Reset it in `install_backup_meta_store` when no schedule is configured; test.
5. The live tests: (a) no live test has two successful runs, so "the last-success stamp of run N does not regress below run N-1" is asserted nowhere on the real route: add it to the failure test if it costs no extra run (keep the stamp observed at the second success), else cover it at the unit level of the evidence cell (`fetch_max`); (b) the retention test drains and ignores the outcomes, so a mutant that turns a retention failure into a failed run is not caught: assert that the outcome of the obstructed run is a success; (c) `arm_retention_end_observer` in `backup_alert_retention_tests.rs` duplicates `support::arm_run_observer`: one helper; (d) `BOUND` equals `WATCHDOG` (120 s): take `BOUND` below the watchdog so the await's own message wins.
6. Guide and design, neighbours of fixed sentences (reported by the step B round-4 executor): `docs/guide-docs/guide/07-operations.md` around line 1601 assumes the disarm write succeeded (it is best-effort: a failed removal keeps the OLD arming time on a re-add); around 1565-1568 (outcome published at protocol completion) the runner-panic and replacement-record exceptions are missing; around 1559-1561 (`running` held to the end) the unwind exception is missing; the design `backup-schedule.md` around line 169 ("zero only when no schedule was ever armed") misses the arm-then-remove and unreadable-row exceptions. Re-read each against the code and write what is true.

### C. Retention budget and tests (FIX-REST step A tail)
7. The pass budget is charged BEFORE the cheap rejects, so a rejected candidate (corrupt stamp, listed cache blob, unlisted file next to a big payload) can consume budget for files the verifier never opens (`server/.../schedule/retention/prune.rs` and `budget.rs`): charge after the cheap rejects, keeping the budget an upper bound of real reads; update the guide's statement.
8. A handcrafted v2 copy can LIST `backup.meta.json`: the verifier hashes it, tagging then changes the hashed bytes (the production writer excludes root control files): refuse such a manifest, or exclude the control file from the hash set consistently: say which and why; test.
9. The budget tests do not pin the exact boundary (4096-byte slack, one payload of margin; sentinel bytes, a duplicate manifest debit and a missing stamp debit can pass) and the refusal test also passes on the old overcharging implementation: tighten the boundary tests so each named mutant fails. Fixture duplication between `prune_budget_tests.rs` and `prune_tests.rs`: one shared test-only fixture module; one-line `json!` literals against the multiline rule.
10. Guide and design wording (verify each against the code): 1000 is a POLICY limit, not a consequence of 4096; "only `keep_last` determines deletions" omits the fresh-copy protection and eligibility; "only tagged candidates" versus the adoption of a recorded untagged candidate; the design names `verify_manifest` but retention calls `verify_retention_candidate`; 4096 counts the fresh child and non-exempt entries (not the lease marker or removed debris); the million cap is per tree entries; the byte text omits the bounded control-file reads, the extra byte per bounded read and the adoption rereads; a healthy fresh copy that exceeds a retention cap before tagging stays untagged without a crash; manual recovery should point at the quiescence precautions; `ReadWritePaths=` is not needed for an already writable disjoint subtree; offline commands validate only syntax.

### D. Ordered shutdown tail (ORDERED-SHUTDOWN review rv-shutdown-1)
11. P1(U): cancelled tasks in the queue of the blocking pool keep references to the writer until a worker takes them out; the final close runs in the same pool (a saturated pool can time out before the close starts); the release barrier only warns. Make the final close independent of a saturated pool (a dedicated thread or a reserved path) or prove by reading why it cannot starve, and make the barrier's outcome observable in the shutdown report.
12. P2(U): the shares map entry is created BEFORE the global slot is reserved (not strictly <= 256 in the window); synchronous `scc` operations and the registry lock sit on the response path; `close()` can return between the flag check and the spawn (the guarantee is narrower than stated); an already accepted refused checkpoint can run after the final close (an ordering hole; anchor corruption not found); a rollback of the observability binding leaves a live poller (pre-existing). Fix each that the code confirms; say per item what you changed or why it cannot happen.
13. P2(D): one flusher error is reported twice; an ordinary background error does not reach the report when the close is skipped; the completion of the task wrapper does not prove that blocking work stopped; the public strict shutdown calls `blocking_io` before the strict branch (`block_in_place` inside a `LocalSet`).
14. Tests: test (c) can time out at a stage before `join_schedule` and misses the mutant "wait after flush" (use a stage marker: the step-B round-4 marker `arm_scheduled_join_probe` in `server/engine/server/server_handle.rs` is the pattern); the rollback tests do not catch the mutant "skip the audit teardown" and `listener bind` matches any Bind; the fixture does not isolate ports 7331-7333; the audit test does not force the periodic checkpoint or an in-flight flusher; add tests for: skipped final close, a panicking flusher, the normal order, "cleanup error is logged". `registry.rs` is about 998 lines: any new code goes into a new file.
15. Code and guide: cancelling the retention hashing (retention side only), synchronous GC of the counters and the `server_meta` write; the guide's remaining imprecisions around lines 1125, 1127-1129, 2119-2122 and the comments at `server_handle.rs:227`, `runtime.rs:118`, `durable_stores.rs:55`, `audit_appender.rs:792`.

## Review lessons (apply before you report; every one of these defect classes was found by independent reviews of earlier steps)

* An oracle that cannot fail: for every new test name the mutant it kills (the code line you would remove or flip) and why the test fails on the parent commit. A test that passes without the fix is not a test of the fix.
* A fixture that clears its own fault, a negative control that cannot go red, a sleep used for synchronization (handshakes, injected clocks and bounded awaits only), an unbounded await in test setup, a `TempDir` that is dropped before the test ends.
* A statement in the guide, a design text or a comment that exceeds what the code does: every sentence you write or leave must match the code you can point to by `path:line`.
* A test or a mechanism cited in the report that does not exist: before the final report grep EVERY test name you cite, in the changed files, and print the grep result per name.
* The rust-guard `structure` gate fails the change when the visibility of an EXISTING item is widened (new items are fine) and on any new `#[allow]`, inline `#[cfg(test)]` module, local `use` or logic in a `mod.rs`: avoid all of them; list every widening and every new cross-module item in the report.
* A finding fixed at one site while its sibling sites keep the defect: for each fix grep the whole class (same helper, same pattern, same file family) and either fix every site or say why a site is different.
