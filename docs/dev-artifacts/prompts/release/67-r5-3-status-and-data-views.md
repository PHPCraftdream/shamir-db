## Why

An operator needs to see what state a server is in (version, on-disk format epoch, uptime, role, replication gap, WAL and durability state) and to look at a few rows of data safely, from the shell, with no way to widen what the server's authorization already allows.

## What (this step only = PR3)

1. **P1 `status`.** A new typed, read-only, top-level `DbRequest` variant and its `DbResponse` DTO in `crates/query/shamir-query-types` (`wire/db_message.rs`: re-count the file's lines; it was 537 with room) carrying exactly the fields of §4.2: server binary version; the observed format epoch AND stamp outcome captured BY THE LAUNCHER AT BOOT via the existing on-disk stamp `inspect` while the boot lock is held (never the bare getter's outcome-only value, never a process constant, never a disk read by the shell or at request time); monotonic uptime; replication role from the node's configured mode at launch; the replication gap as the exported snapshot carries it, labelled `gap_versions_merged`, documented as a merged non-authoritative aggregate per repository with `age: unknown` always (no timestamp plumbing); WAL watermark/pending/commit telemetry with the semantics of `durability_export.rs`; effective vs stored durability per repository. Handler in a NEW file `REPO_ADMIN/operator_state.rs` of `crates/server/shamir-server/src/engine/db_handler/repo_admin/` (the design names it; declare it through the same mechanism the neighbours use; the folder goes from 4 to 5 entries: recount with `ls`) with only thin dispatch edits in `handler.rs`/the gate file (the gate file is near 1000 lines: factor into `operator_state.rs`, never grow it past the cap), wired by the server launcher. Permission: superuser-class read exactly as the design table says; a token session never reaches it.
2. **P2 `data get`.** A new typed top-level `DbRequest` variant (NOT a `BatchOp`; `BatchOp` is at its line cap) for an exact-key point read: `Database` `Read` THEN `Table` `Read` with the ancestor check done before any lookup, reusing the real two-call ACL of `authorize_cursor_read` in `cursor_support.rs`; no cursor is created and no cursor path is engaged. A new top-level variant does NOT inherit the batch gates by magic: the handler must explicitly apply the same repository quarantine as the batch path, a typed-key size cap, and the existing server result-size and in-flight response controls (read how the batch path and `enforce_page_budget` apply them and mirror exactly). KEY is a Base58 `RecordId` (parse with the existing decoder; a malformed key is a typed refusal, not a panic and not a scan). Response: the one record (as the batch read returns it) or a typed `not_found`.
3. **Perimeter and client obligations.** Add BOTH new variants to the exhaustive token-perimeter match (`shamir-server-security` `http_rest/scope.rs`) as `Denied("token_request_denied")`; add them to the Rust client's exhaustive response mapping and add typed methods (`status`, `get_record` or the names the neighbours suggest) in the existing client files: `crates/client/shamir-client/src/client/api.rs` is 918 lines (cap 1000) and `client/src/client/` is at its 7-entry limit: no new file there; if the cap is threatened, factor into an existing file. Builders: through `shamir-query-builder` (builder-only rule: no raw wire values anywhere). Check every other exhaustive `match` over `DbRequest`/`DbResponse` in the workspace (server dispatch, the HMAC/policy tables, TS and Node bindings only if they match exhaustively in Rust) and list each edit.
4. **Shell commands** (new file `shell/commands/state.rs`: `commands/` goes from 2 to 3 entries; recount with `ls`): `status` (prints the documented fields; the gap line shows the field name `gap_versions_merged` and the caveat, never the word "lag"); `replication subscriptions` (the EXISTING `ReplicationStatus` admin op through the existing batch path: no wire change; project the record fields as documented in the design golden output); `data count DB REPO TABLE` (`Query::select([count_all])` via the builder; the result reports whether the O(1) counter path or a scan ran if the response carries that, otherwise state the caveat in the help text); `data head DB REPO TABLE N` (plain first-N read in server scan order through the streaming/limit route; shell-side caps on rows, bytes and wall time with documented defaults and typed truncation markers; no ordering promise, never `ORDER BY`); `data get DB REPO TABLE KEY` (P2); `version show` (P1 view: the observed epoch and outcome from `status`; no disk read by the shell). Token sessions: re-read §3.3 and implement EXACTLY its read-only subset (it lists `data head` and `data count`; `status`, `data get`, `replication subscriptions` and `version show` are not in it): everything outside the list is refused with the fixed message, exit 4, with zero requests sent. Output follows §5: JSON Lines v1 `result` records, no raw server strings, no server error chains, peer-supplied text only through the existing sanitizer.
5. **Tests (CI-only; `tests/admin/shell/state_data.rs` is ADDED here: the folder goes from 4 to 5 entries per the design; recount with `ls`, `mod.rs` declarations only).** On the harness of PR1/PR2 (`harness.rs`: boot fixtures, profiles, pins, token provisioning): `status` on SCRAM transports with golden structure (observed epoch equals the epoch of a fixture data directory stamped at boot, uptime monotonic, role, the merged-gap caveat text); a token session gets `token_request_denied` for `status` and `data get` with ZERO requests reaching the server (assert on the server's counters or a counting proxy, not on the reply); `data count`/`data head`/`data get` golden outputs and bounded-budget assertions (a table larger than the head cap truncates with the marker; the byte and wall caps fire; a malformed KEY, an unknown table, a missing record, a user without `Read(table)` and a user with `Database` read but no `Table` read each give the right typed refusal and exit code); P2 isolation: a quarantined repository refuses `data get` like the batch path; the typed-key cap; a `data get` does not create or consume a cursor (assert the cursor registry count before and after); `replication subscriptions` golden against a configured subscription fixture; wire/serde and builder tests for the two new variants, exhaustive-match tests (the existing policy tests that enumerate variants must be extended and must FAIL if a variant is missing); the secret-leak byte-scan and the malicious-peer reflection scans extended to the new commands' output. ## Do not

Implement anything of PR4–PR6 (rights, activity, backups, versions beyond `version show`, schedule, export), change the replication owner's code for provenance or sample age (Q8 default), read the data directory from the shell or at request time for `status`, add a registry dependency, grow `BatchOp` or the gate file past their caps, print server error strings or peer-supplied text raw, construct wire values by hand, keep any history, accept a secret on argv, or widen an existing item beyond what the step needs (list every widening before doing it). Remember what earlier CI runs taught: Unix-only code is compiled only in CI and Windows-only code only on this machine: every `cfg(unix)`/`cfg(windows)` item gets its cfg on the item AND its imports and helpers; no doc comment (`///`) on an `extern` block or a macro invocation; `CStr::to_str()` returns a `Result`.

## Layout and fixture lessons

Count every folder you add to with `ls` (many are at 7 entries: `python -I scripts/ci/check_layout.py` counts only tracked files, recheck after staging); at most 1000 lines per file, one primary item per file, `mod.rs` re-exports only (the rust-guard structure gate allows nothing else in a `mod.rs`: shared helpers go in a named file), tests in `tests/` folders, no inline `#[cfg(test)]` modules, no local `use`, no new `#[allow]`. Persistent stores, every `TempDir` alive for the whole test, close handles and wait for the server task to finish before reopening a directory (Windows holds Fjall locks until the dropped engine's background handles finish: reopen with a bounded retry on `Locked` only, like `init_waiting_for_locks` in the function-family crash tests), handshakes not sleeps, every await bounded by a generous timeout (at least 120 s: a hang detector, the Windows runner is up to 10x slower), a batch is at most 50 queries, per-session request rate limit 500 req/s (never poll in a tight loop: pace status polls at 20 ms or more), set `argon2_concurrent_max` and `auth_init_rate_per_second` to 64 in fixtures that open several sessions, debug-test stacks are small (call concrete handlers through `Box::pin`, run deep tests on a roomy thread, `on_big_stack`), assert on invariants and sets, `shamir-test-diag` marks for flake-prone tests.

## Rules that bind the change

* Machine memory: at most ONE cargo command at a time machine-wide (other executors run: if a cargo run is already in progress wait for its notification, never poll), ALWAYS as `bash <orch>/cg.sh env RUSTC_WRAPPER= CARGO_TARGET_DIR=<artefacts>/target-exec wnice -p idle -c 50 -t 8 -m 50 -- cargo ... -j 1 > <logfile OUTSIDE the repository> 2>&1` (the wrapper serializes cargo across executors and the shared `CARGO_TARGET_DIR` keeps registry dependencies compiled once for all executors: never run `cargo clean`, never set another target dir; never `-j 2`; never piped through `tail`/`head`; `cargo fmt` rejects `-j`: run it with `CARGO_BUILD_JOBS=1` under the same wrapper); every worker you spawn must be told the same, and no worker may run cargo at all: only you, the top executor, run `check`/`clippy`/`fmt` under these rules (workers edit files and read code only).
* Leave no scratch files in the tree and none outside it (edit only paths inside this worktree).
* Wrap-up: the hard limit is 150 minutes. At about 105 minutes (70%) stop adding scope, bring the change to a compiling, formatted, clippy-clean state and write the final report (what is done, what is missing, what each check printed); a run that hits the limit without a report is lost work.

## Policy (verbatim, binding)

Compilation, builds and tests run on GitHub CI, not on this machine. Banned locally: `cargo test`, `cargo nextest`,
`./scripts/test.sh`, `cargo build`, `cargo run`, `cargo bench`, `cargo doc`, npm/tsc builds, any build or test run.
Allowed locally only: `cargo check -p <crate> --all-targets`, `cargo clippy -p <crate> --all-targets -- -D warnings`,
`cargo fmt -p <crate>` (and `-- --check`), `python -I scripts/ci/check_layout.py`.

⛔ NEVER run `git reset` / `checkout` / `clean` / `stash` / `restore` / `rm`, or any git command that mutates the working
tree or index. Only edit files; the orchestrator commits. (For file moves use a plain filesystem move and say so in the report;
the orchestrator stages them so git detects the renames.)
