# Brief: R2d-FIX-REST step A — scheduled retention must make progress under its own budget, record ownership before it can fail, and stop advertising a policy it does not have

Path prefixes used below: `sync/` = `crates/server/shamir-sync/src/sync/durability/backup/`; `sched/` = `crates/server/shamir-server/src/boot/config/diagnostics/backup_online/`; `server/` = `crates/server/shamir-server/src/`. Re-open every path and line before relying on it (lines drift). The findings come from the independent review of the landed R2d code (read-only trace, 2026-11-21; not reproduced: the tests below prove them in CI). Three other findings of that review are already fixed and are NOT part of this step: the restored manifest files (FIX-B), the snapshot read lease (FIX-C) and the shutdown ownership (ORDERED-SHUTDOWN). Another step (not yet written) owns the path-free scheduled errors, the metric/guide disagreements, the stale-alert evidence and the inherited copy-path I/O errors: do not touch `sched/registry.rs`, `sched/adapter.rs`, `sched/metrics.rs` or `sync/online/`.

## Why

1. **Retention can stop for good while copies keep being written.** `sched/schedule/retention/prune.rs` verifies every owned candidate and the fresh copy inside ONE pass bounded by `Budget` (`retention/budget.rs`: 1 TiB, 1,000,000 entries, 4,096 root entries, 100,000 tree entries). The byte charge is paid up to three times per payload file: `walk` (`retention/preflight.rs`) charges the size of every regular file it visits, the claimed-files loop charges each manifest file again, and the WAL loop charges every WAL segment a third time, although the verifier reads each file once. A tagged 300 GiB copy plus the fresh 300 GiB copy already exceeds 1 TiB: `prune_inner` returns `Refusal::Budget` BEFORE `tag_fresh`, so the fresh copy stays untagged and is later skipped as foreign (`untouched`); the next pass meets the same tagged copy plus a new fresh one and fails the same way, so nothing is ever pruned while the scheduler keeps reporting successful copies. The only signal is the existing alert `BackupRetentionFailing` (`deploy/alerts/shamir-backup.rules.yml`), which the guide does not tie to this situation. `keep_last = 4096` is accepted by `sched/schedule/config.rs` although the first pass that needs to prune sees at least 4,097 root entries and fails on the entry cap.
2. **Ownership is recorded only at the END of a successful scan.** The fresh copy is tagged after the whole root has been classified. Any refusal in between (budget, a cancelled pass, an unreadable foreign entry classified as incomplete) leaves a verified copy of this server unmarked, and a crash between protocol success and the tag does the same; such a copy is never adopted or pruned.
3. **`retention.max_age_days` has no effect.** It is parsed and validated (`schedule/config.rs`), never read by `prune_inner` (the newest-N floor decides everything); the guide admits it adds no deletions, but the plan and the config advertise an age policy.
4. **The shared config validation blocks disaster recovery.** `Config::validate` (`server/boot/config.rs`) calls `BackupScheduleConfig::validate`, which checks the destination filesystem (`verify_private_dir`, disjointness); every subcommand that loads the production config, `restore --from` included, therefore fails when the original backup mount is absent or not private, although restore never uses it.
5. **The shipped systemd unit makes the guide's destination read-only** (`deploy/shamir-db.service` uses `ProtectSystem=strict`; a destination outside the unit's writable paths fails every run at `mkdir`; the guide section "Online-копии по расписанию" does not say so).

## What (this step only)

1. **Charge each payload byte once.** Charge exactly the bytes the verifier reads, once per file: the claimed-files charge stays (or the walk charge, pick ONE and justify it in the report), the WAL-segment re-charge and the walk charge of files that are never read go away; unknown files in a candidate that will be refused still cost nothing beyond their directory entry. Keep the entry caps and the 1 TiB pass cap. Update the comments that describe the accounting.
2. **Tag the fresh copy before the scan.** After the root, lease-marker and fresh-name checks and before the directory scan: classify the fresh copy exactly as today (child check, sidecar, `verified_time`, tag it with `tag_fresh` after the late root and child re-checks), then scan the other entries, skipping the fresh name. A scan refusal (budget, cancellation, incomplete entry) now leaves the fresh copy tagged and owned; a fresh copy that cannot be verified is still not tagged. The adoption of recorded provenance matches, the selection and the deletion loop keep their rules. State in the report how this changes the order of the existing `retention_before_adoption` trace point and the tests that depend on it.
3. **Bound `keep_last`** in `schedule/config.rs` validation: at most 1000, with a message that names the bound and why (root entry cap 4,096 shared with foreign entries). Reject larger values with `ConfigError::Validation`.
4. **Remove `max_age_days`** from `BackupRetentionConfig` (and from its validation and every fixture, test and guide/design mention): the config is strict (`deny_unknown_fields`), so a config that still sets it fails to start with the unknown-field error, which is the honest outcome for a key that did nothing; the guide says so under a short "изменение" note. Do not invent an age policy.
5. **Backup filesystem validation only at server launch.** Split `BackupScheduleConfig::validate` into the pure syntax checks (interval, window, `keep_last`, absolute destination without `..`) that stay in `Config::validate`, and the filesystem checks (`verify_private_dir`, disjointness from `data_dir`) that run only where the server resolves the schedule for launch (`resolve` and its caller); trace every caller of `Config::validate` and say which subcommands now skip the filesystem check. A restore with a production config whose backup mount is missing must pass validation; a server launch with it must still refuse with the same typed error as before.
6. **Guide (Russian, `docs/guide-docs/guide/07-operations.md`, scheduled-backups section).** The real retention limits (1 TiB of verification reads per pass, `keep_last` at most 1000, 4,096 root entries including foreign ones, 100,000 entries per copy) and what happens beyond them (retention stops with a warning, copies keep being written, the counter `shamir_backup_retention_failed_total` and the alert `BackupRetentionFailing` are the signal, the operator frees space by moving or removing old copies by hand and retention resumes on the next run); a verified copy left without an ownership tag by a crash is never adopted: move or delete it by hand; the `ReadWritePaths=` drop-in for the destination (example with a placeholder path); `max_age_days` is gone. No private paths.
7. **Tests (CI-only; registered in their `tests/mod.rs`).** In `sched/schedule/retention/tests/prune_tests.rs` (reuse `private_root`, `copy`, `retain`, `Budget::with_bytes`): (a) a root with two owned copies whose total payload is a little under the budget passes where the three-fold charge refused it (set the budget to just above one pass of true reads); (b) a scan that ends in `Refusal::Budget` (tiny budget for the OTHER candidates) still leaves the fresh copy tagged, and the next pass adopts nothing and treats it as owned; (c) an unverifiable fresh copy is not tagged. Config tests in `server/boot/config/tests/backup_schedule_tests.rs`: `keep_last = 1001` refused, `keep_last = 1000` accepted, a config with `max_age_days` refused as unknown field, restore-style validation with a missing destination passes while the launch-time resolution refuses. Each new test must fail on the parent commit; name in the report the mutant each one catches.

## Layout and fixture lessons

Count every folder you add to with `ls` (many are at 7 entries: `python -I scripts/ci/check_layout.py` counts only tracked files, recheck after staging); at most 1000 lines per file, one primary item per file, `mod.rs` re-exports only (the rust-guard structure gate allows nothing else in a `mod.rs`: shared helpers go in a named file), tests in `tests/` folders, no inline `#[cfg(test)]` modules, no local `use`, no new `#[allow]`. Persistent stores, every `TempDir` alive for the whole test, close handles and wait for the server task to finish before reopening a directory (Windows holds Fjall locks until the dropped engine's background handles finish: reopen with a bounded retry on `Locked` only), handshakes not sleeps, every await bounded by a generous timeout (at least 120 s: a hang detector, the Windows runner is up to 10x slower), assert on invariants and sets, `shamir-test-diag` marks for flake-prone tests.

## Rules that bind the change

* Machine memory: at most ONE cargo command at a time machine-wide (other executors run: if a cargo run is already in progress wait for its notification, never poll), ALWAYS as `bash <orch>/cg.sh env RUSTC_WRAPPER= CARGO_TARGET_DIR=<artefacts>/target-exec/<worktree-slug> wnice -p idle -c 50 -t 8 -m 50 -- cargo ... -j 1 > <logfile OUTSIDE the repository> 2>&1` (the wrapper serializes cargo across executors: never run `cargo clean`, never `-j 2`, never piped through `tail`/`head`; `cargo fmt` rejects `-j`: run it with `CARGO_BUILD_JOBS=1` under the same wrapper); every worker you spawn must be told the same, and no worker may run cargo at all: only you, the top executor, run `check`/`clippy`/`fmt` under these rules (workers edit files and read code only).
* Leave no scratch files in the tree and none outside it (edit only paths inside this worktree). No private machine paths in any file you write (docs, comments, tests, fixtures): use placeholders.
* Wrap-up: the hard limit is 150 minutes. At about 105 minutes (70%) stop adding scope, bring the change to a compiling, formatted, clippy-clean state and write the final report (what is done, what is missing, what each check printed); a run that hits the limit without a report is lost work.
