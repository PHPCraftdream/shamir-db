## Binding design (decided by the orchestrator; do not redesign, do not add a configuration key, do not change any wire tag or error code)

* **D5 — the budget is anchored at admission on BOTH clocks (review finding 1, P2).** Today the deadline is a wall-clock (`SystemTime`-based) value computed at admission, but the monotonic measurement in the semaphore starts only when the blocking job reaches the semaphore, after the blocking-pool queue and the salt generation. A backward wall-clock step while the job is queued therefore restores expired budget. Decision: capture a monotonic `std::time::Instant` at admission together with the wall-clock deadline, pass BOTH to the job (one small value type, for example an admission-deadline struct owned by the gate and passed by value; no global state), and let the semaphore's remaining budget be the SMALLER of the wall-clock remainder and the monotonic remainder measured from the admission instant (not from semaphore entry). An unreadable clock, an overflow, or an already expired budget stays a counted `Busy` and never starts a KDF. Keep the injected-clock seam of the semaphore usable by the tests (extend it, do not remove it). A forward step must still only shorten the wait.
* **D6 — a waiter that gives up must hand the wake-up on (review finding 2, P2).** The release path takes the waiter mutex before incrementing and notifying (keep that), but `notify_one` can be consumed by a waiter that wakes just before its deadline and then returns `None` without acquiring, leaving another admitted waiter asleep next to a free permit until its own final slice ends. Decision: every exit of the wait loop that does not take the permit while it was the notified waiter (pre-acquisition expiry included, not only the post-acquisition path) must pass the notification on (`notify_one` for the next waiter) while holding the same synchronisation the release path uses, or the equivalent that provably cannot lose a wake-up; walk EVERY `return`/`break` of the loop and state in a code comment why none can strand a waiter. Spurious wake-ups stay harmless.
* **D7 — the blocking pool is bounded, not isolated (review finding 3, P2): documentation and a comment only, no code change.** The admission cap is `2 × argon2_concurrent_max` (valid range up to 1,024, so up to 2,048 admitted jobs) while Tokio's default blocking-pool limit is 512 threads (`crates/server/shamir-server/src/main.rs` and the Windows service runtime build the runtime with the default), so for a capacity above 256 the gate's backlog alone can fill the shared blocking pool and queue unrelated blocking work (WAL sync, HTTP verifier lookups) behind it. State this exactly, with the threshold, in the operations guide next to the setting and in the capacity guide, and in a short comment at the admission cap in the code. Do NOT add a separate pool, a new bound or a config key. Also correct the capacity guide's recommended `argon2_concurrent_max` values for the small hosts (the `16 / 32 / 64` settings for `2 / 4 / 8 GB` leave no RAM headroom at the documented 128 MiB cost even before the `× 1.05` factor): recompute them from the guide's own formula so that the estimate fits with headroom, in the same style as the four shipped deploy profiles, which are internally consistent. And say that login does NOT take an Argon2 permit (not that login is "unaffected").
* **D8 — the regression tests must be able to fail (review finding 4, P2).** Fix the oracles the reviewer named, with no sleeps used as synchronisation, every wait and join bounded (a hang detector of at least 120 s, never an unbounded join), and no frozen-clock configuration that can wedge the test if the permit never returns:
  1. The wake test in the semaphore tests: signal only AFTER the releasing thread has dropped its permit, assert the result of the timed wait (a waiter must have been notified before its slice ended, not merely succeeded on the next poll); it must fail if the release path stops taking the mutex before notifying.
  2. A handoff test for D6 with the injected clock: capacity two, two permits held, two admitted waiters; release one permit at the instant the first waiter's deadline is reached; assert that the second waiter (whose deadline is later) acquires promptly rather than after its own final slice, and that exactly one permit is accounted.
  3. A test for D5 through the injected clock seam: the wall clock moves BACKWARD while the job is "queued" before it enters the semaphore; assert the budget was not restored (a refusal, no KDF started) because the monotonic remainder from the admission instant is spent.
  4. A public-path test for the gate's job (D2/D5): a job that resumes after its admission deadline must be refused with the typed busy outcome, counted once, with zero KDF runs and the ticket released; it must FAIL if the public job recomputes a fresh deadline (the current test feeds `run` an already expired value by hand, which would still pass).   6. Keep every existing assertion; do not weaken or delete a test (compare test names against the previous round). Do not add a test that only passes when the real clock behaves.

## Appendix — the independent reviewer's report (verbatim)

VERDICT: FAIL

Reviewed `origin/master...HEAD` at `c9e908b0a` against briefs 72 and 89. The two provisioning paths share one boot gate, admission is atomic and precedes blocking-pool submission, and both paths preserve the typed refusal before inserting a user. ## Findings

1. **P2 — CONFIRMED: a backward clock step while a job is queued can let it start a KDF after its three-second admission budget.** `crates/server/shamir-server-security/src/security/user_directory/scram_gate.rs:89–95` records a `SystemTime`-based deadline. `derive_scram_record.rs:76–86` sends only that deadline to the job. The monotonic measurement starts in `crates/net/shamir-connect/src/server/limits/argon2_semaphore.rs:95–105,156–167`, **after** the blocking queue and salt generation. If a job queues for four real seconds while the wall clock moves back five seconds, the semaphore sees four seconds *remaining* and can grant a free permit immediately. The one-second polling slice does not bound that error. With a steady clock, queue time is correctly charged. The guide’s “not a request deadline” caveat is correct; it does not explain that a clock step **before semaphore entry** can extend the permit budget by more than a slice (`07-operations.md:874`, `AUTH_PROTOCOL.md:512`).

2. **P2 — CONFIRMED: the release mutex closes the original check-to-sleep race, but an expiring waiter can consume the only wake-up.** `argon2_semaphore.rs:169–177,199–200,210–223` uses `notify_one`. At capacity two, two KDFs can hold permits while two admitted jobs wait. If a release wakes A just before A’s deadline and A regains the mutex just after its deadline, A returns `None` before acquiring and does not notify B. If the other KDF keeps running, B can stay asleep until its own final slice expires and return `Busy` despite a free permit. The post-acquisition expiry path *does* drop a permit and notify; the pre-acquisition expiry path does not. Spurious wakes are rechecked, but do not guarantee progress in this case.

3. **P2 — CONFIRMED: the blocking-pool backlog is bounded, not isolated.** This is a residual limit of D1, not an admission-counter bypass. The valid range reaches 1,024 (`crates/server/shamir-server/src/boot/config.rs:439–440,469–477`), so `scram_gate.rs:102–116` can admit 2,048 jobs. Both server runtimes use Tokio’s default blocking-pool limit of 512 (`main.rs:344–348`, `boot/policy/windows_service.rs:152–157`). At a valid high setting, provisioning alone can fill that pool and queue unrelated WAL sync and HTTP verifier lookups behind it (`crates/storage/shamir-wal/src/segment/wal_segment.rs:478–502`, `crates/server/shamir-server-security/src/security/perimeter/http_login/service/begin.rs:258–278`). `CAPACITY_PLANNING.md:34` correctly says there is no isolation. `IMPLEMENTATION_GUIDE.md:658` should say login **does not take an Argon2 permit**, not that login is unaffected. The same capacity guide’s recommended `16 / 32 / 64` settings for `2 / 4 / 8 GB` hosts leave no RAM headroom at the documented 128 MiB cost, even before the guide’s `× 1.05` factor (`CAPACITY_PLANNING.md:23,156–179`). The four shipped profiles have lower, internally consistent estimates.

4. **P2 — CONFIRMED: the regression suite does not prove the two main timing fixes.** `argon2_semaphore_tests.rs:32–78` signals **before** the releaser drops its permit, ignores the timed-wait result, freezes both clocks, and accepts eventual success. Reverting release synchronization can lose the notification and still pass on the next poll. If no permit ever returns, those frozen clocks and the unbounded thread joins can wedge the test. The companion at `:82–87` proves the injected callback holds the mutex; it does not prove an actual waiter was notified. Separately, `user_directory/tests/gate_tests.rs:212–232` manually feeds `run` an already-expired value; it still passes if the **public** blocking job recomputes a fresh deadline. The queued-cancellation test accepts either KDF success or expiry and therefore does not close that gap. The live scrape test also accepts an immediate `Busy` under contention; it does not establish that an admitted waiter actually waited.

5. **P3 — CONFIRMED: protocol cleanup is incomplete, although the new account-creation payload is correct.**
   - `AUTH_PROTOCOL.md:98,888–890` still presents native auth-phase `server_busy`/`rate_limited` with `retry_after` as live outcomes. Native pre-auth throttling records `auth_attempts_total{result="rate_limited"}` and closes without that body; the handshake error path has no live native busy producer (`shamir-sync/src/sync/connection/handshake.rs:729–757,893–932`). The corrected lifecycle diagram at `diagrams/10-session-lifecycle.md:16` and reserved WS code at `TRANSPORT_WS.md:79` agree with the implementation. `diagrams/01-initial-auth.md:74` still implies a returned `rate_limited` error. Keep the separate HTTP login and bearer admission responses.
   - `AUTH_PROTOCOL.md:687–695` correctly shows the inner `op`/`kind`, password string, required hex confirmation tag, `user_created` with a binary 16-byte ID, and busy code/message without `retry_after`. For an independent client, make explicit that these are MessagePack **bytes inside** `req`/`res`, not nested envelope maps (`shamir-connect/src/common/messages/envelope.rs:23–32,154–162`; `TRANSPORT_TCP.md:78–91` still shows maps). The HMAC description should say **confirmation**, not independent request authentication: the key is derived from the session ID, adds no authentication strength beyond it, and does not cover the password (`crypto.rs:151–161`, `shamir-query-types/src/security/hmac.rs:112–121,152–158,694–706`). The canonical lengths and list count are `u32` big-endian. Also, an overlength normalized username returns `invalid_username`, not the `createUser_failed` still listed at `AUTH_PROTOCOL.md:146` (`handlers/admin.rs:106–115`).
   - `AUTH_PROTOCOL.md:13–15,108–124,586–600` should label the challenge/response bootstrap exchange as **library-only** beside the live boot modes. A client following §11.3 against a launched server will not get a bootstrap challenge: native dispatch selects resume or SCRAM, while random-token boot creates the verifier server-side, writes a token file, and uses a fixed 24-hour TTL (`handshake.rs:822–881`, `boot/bootstrap.rs:54–61,122–165`). `IMPLEMENTATION_GUIDE.md:233–276` already makes the library/live distinction. Its top-level Argon2 setting is now correct, but its TOML sketch is not a deployable config; use the KTAV examples. Its `:141–142` still promises a subnet memory-quota `server_busy`/`Retry-After` path with no matching live setting or native handler.
   - `SECURITY_MODEL.md:58` and `IMPLEMENTATION_GUIDE.md:804` retain the “pre-Argon2id” server-side binding-check rationale. The check is before challenge; the server would not run a password KDF even on a matched login. The same old story remains in `argon2_semaphore.rs:1–18`, `shamir-connect/src/common/model/error.rs:68–73`, and `shamir-funclib/src/functions/crypto/core.rs:76–85`. `07-operations.md:866` correctly lists clock failures as counter inputs, but its interpretation column should not diagnose sustained growth solely as capacity pressure. The metrics catalogue already gets this right.

## Layout and fixture lessons
