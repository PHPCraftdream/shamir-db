## Binding design (decided by the orchestrator; do not redesign, no new config key, no wire change)

The path is `crates/engine/shamir-engine-table/src/table_manager/accessors/table_manager_validators.rs` (bind and unbind of a validator on a table: save the envelope into the info store, flush, publish the live snapshot, with a compensation after a failed flush), its facade callers in `crates/engine/shamir-db/src/shamir_db/db/validator/validator_management.rs`, the declarative activation callers (`schema_management.rs`, `execute/admin_ddl/admin_schema.rs`), the migration binding handler (`execute/admin_db/schema_migration/function_family/binding.rs`) and the holder scan (`validator/binding_scan.rs`).

* **F1 — the compensation is part of the operation.** After a failed flush the compensating write (the previous logical envelope) is CHECKED, and then FLUSHED itself, with a small bounded number of attempts (three, no sleeps used as a delay: an immediate retry; the failure is typically persistent or gone at once). The result of the compensation is never ignored. If the compensation write or its flush still fails, the operation returns a typed error that says the binding state of the table is IN DOUBT (fixed message, no table path), AND the manager enters the in-doubt state of F2.
* **F2 — in doubt means fail closed.** The table manager gets a shared in-doubt flag (an atomic on the state the clones share). While it is set: (a) bind and unbind of validators on that table refuse with the typed in-doubt error until the process restarts (a restart re-reads the envelope, which is the recovery path; state that); (b) the holder scan treats that table as holding EVERY validator identity, so replace, rename and drop of any validator is refused by the existing typed refusal (do not add a new table name to an error text: the foreign-table disclosure of the fourth review must stay closed); (c) ordinary reads and writes are NOT blocked (the live vector is the last coherent state). The scan reads the flag on the table's manager if it is initialised; a cold manager has no flag (a restart clears it by definition). Keep the cost on the write hot path at zero (the flag is read only by bind/unbind and by the scan).

## Findings, ranked

1. **P1 — CONFIRMED: failed BIND can still leave the orphan it reports rolling back.** `ET/table_manager/accessors/table_manager_validators.rs:64–94` saves the new envelope, flushes, and only then publishes the live snapshot. On a flush error it re-encodes the old **live vector**, calls `set`, ignores the result, and never flushes the compensation. `MemBufferStore::flush` drains to backing **before** calling the inner flush; `set` queues a dirty value and can itself fail on a backing read (`S/stores/storage_membuffer/store_impl.rs:99–117,301–304`; `S/stores/storage_membuffer/core.rs:265–284,695–715`). On raw Fjall, the compensating `set` can fail at the existence probe or insert; even a successful set is not a confirmed sync (`S/stores/storage_fjall/store.rs:141–152,283–296`).

   **Failing scenario:** The first `SET TABLE SCHEMA` writes a binding for a new validator ID into backing, then the sync fails. The schema caller removes the new artifact and restores the old catalogue row, but the binding compensation is only queued or failed. An independent reader can still see the orphan; a restart that recovers the new envelope but not its compensation loads the orphan into the manager. A schema retry after that reopen mints another ID and appends it, rather than removing the first; writes can fail with `ValidatorFailure::Missing` (`V/../schema_management.rs:642–645,683–727`; `DB/execute/admin_ddl/admin_schema.rs:489–496,563–576`; `ET/table_manager/admission/domain/barrier/write_domain_barrier.rs:206–212`; `ET/table_manager/accessors/table_manager_validators.rs:398–404`). A successful same-process retry can overwrite the stray envelope from the unchanged live vector; that does not make the failed attempt atomic.

2. **P1 — CONFIRMED, new split state: failed UNBIND can leave a live holder invisible to the fence.** `ET/table_manager/accessors/table_manager_validators.rs:124–151` saves the removal, publishes it live, and flushes. ## Callers, scan and seed boundaries

- **What is restored:** On BIND error the live vector never changes; on UNBIND error the original `Arc` is republished. For an absent envelope, compensation writes a **present empty** envelope, not absence. For an empty or non-empty envelope it reconstructs the previous logical list *if the live vector was coherent*, not the old bytes: `MetaEnvelope::new` generates a new timestamp (`ET/support/validator_bound/persistence.rs:21–36`; `crates/index/shamir-index-core/src/model/meta/meta_envelope.rs:45–55`). Migration evidence distinguishes `never-saved` from saved-but-`absent` (`M/function_family/binding.rs:35–46,345–348`).
- **Serialization and callers:** Facade bind/unbind, schema activation, and holder admission share replication control. Repository admission precedes `bindings_lock`; clones share the lock and snapshot. Another facade bind or a scan cannot interleave inside compensation, but the backing store can still be wrong **after** unlock, and the background drain is not covered by that lock. Ordinary wire calls propagate the error before reverse updates and release their reservation. `SET TABLE SCHEMA`, `ADD SCHEMA RULE`, and `REMOVE SCHEMA RULE` restore the previous artifact or remove a fresh registration, then attempt a separate catalogue rollback (`DB/execute/admin_ddl/admin_schema.rs:563–576,758–777,900–920`). Declarative retry is therefore conditional, not a repair of orphan IDs. Migration BIND remains deferred; migration UNBIND records in doubt on handler error. Resume explicitly flushes the original info handle and checks the live binding, stored binding, registry reference and catalogue reference. Exact original state permits replay; a mismatch after reopen refuses rather than silently completing (`M/function_family/binding.rs:67–85,148–222`). Schema-rule resume is different: it checks catalogue rules, not the runtime binding, and can skip reactivation if catalogue compensation failed and the desired rules are still present (`M/apply/apply_operations.rs:817–852`; `M/apply/ddl_postconditions.rs:37–66`).
- **What the scan sees:** It walks configured tables in loaded repos and reads only the mapped `__info__` envelope (`E/repo/instance/repo_instance/catalog.rs:153–175`). A matching ID counts even if the manager is cold or the reverse row is missing. Empty, missing-key, missing-store and lazy never-initialized cases contribute no holder; decode and backend errors propagate. A successful table rename copies the source info store, flushes the destination, then publishes the fresh mapping; the scan follows that mapping (`E/repo/instance/repo_instance/catalog.rs:620–667,694–696`; `E/repo/instance/repo_instance/table_store/copy.rs:7–22`). A nonexistent path is not walked; a recreated path contributes only its own envelope. Internal-store matches contribute DROP evidence, not reservation identities. The documented detection loss is precise: a genuinely lost envelope or sidecar now looks like a never-bound table **even with a matching reverse reference**. No loss of an intact, visible matching envelope was found in the scan change itself.
- **Publication:** The installer calls `check_seed_target` and then `register_seed_image`; registration checks again, including when an embedder calls it directly. No second supported seed publisher writing a database row was found. Logical import uses checked CREATE (`crates/server/shamir-server/src/boot/config/diagnostics/logical/logical_import/load/stage_load.rs:78–85`). The raw trusted `SystemStore::save_database` and `save_database_meta` APIs remain unguarded upserts (`DB/system_store/catalogue/ops.rs:37–56,776–788`); those can write rows directly, but neither publishes a live database into `dbs`. This is not a new bypass in the seed path.

Allowed locally only: `cargo check -p <crate> --all-targets`, `cargo clippy -p <crate> --all-targets -- -D warnings`,
`cargo fmt -p <crate>` (and `-- --check`), `python -I scripts/ci/check_layout.py`.

⛔ NEVER run `git reset` / `checkout` / `clean` / `stash` / `restore` / `rm`, or any git command that mutates the working
tree or index. Only edit files; the orchestrator commits. (For file moves use a plain filesystem move and say so in the report;
the orchestrator stages them so git detects the renames.)
