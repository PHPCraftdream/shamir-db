# Brief: BACKUP-AUDIT-CONSISTENCY — an online copy must capture `audit.log` and the audit checkpoint store consistently, so a restored directory boots

Re-open every path and line before relying on it (lines drift). Verified by a read-only trace of the landed code on 2026-11-21 (finding 6 of the audit-chain review); not yet reproduced: the first test proves it in CI. The online copy engine lives in `crates/server/shamir-sync/src/sync/durability/backup/online/` (`protocol.rs`, `copy_engine.rs`), the restore side in `.../backup/restore/` (`catalogue.rs`), the audit appender and its recovery in `crates/server/shamir-server-security/src/security/observability/logging/audit_appender.rs`, `audit_appender/recovery.rs` and `audit_appender/checkpoint.rs`. The audit chain restart fix has LANDED (the recovery routine exists on master: read it, `recovery.rs`, before designing anything).

## Why (confirmed by trace)

The residual pass of the online copy (`protocol.rs` around the residual copy, `copy_engine.rs` around the per-file rehash) copies and hashes `audit.log`. If, after that file was copied and hashed, an audit flush and a checkpoint land BEFORE the checkpoint journal's final hash / re-copy, the snapshot holds the EARLIER log and the LATER anchor (checkpoint). The manifest authenticates every file individually, so manifest verification passes; the staged restore (`restore/catalogue.rs`) checks only the engine catalogue, not the audit chain; the first full boot of the restored directory then refuses with `AnchorPastTail` (the checkpoint claims a log position beyond the log's verified tail). The restored copy of a healthy server is therefore not bootable without a manual repair.

## What (this step only)

1. **Reproduce deterministically in CI first.** A test at the lowest level that can drive the real copy engine over a real audit appender (decide from the code: a `shamir-sync` integration test with the real online-copy protocol over a data directory that contains a real audit log and checkpoint store written by the real appender, or a `shamir-server` test through the server's backup operation): a test-only hook (or an existing hook; read the copy engine's test seams first) pauses the copy exactly between "`audit.log` copied and hashed" and "checkpoint journal final re-copy", then the test appends audit events, flushes and writes a checkpoint through the REAL appender, releases the copy, restores the resulting copy into a fresh directory and opens it through the REAL audit recovery: it must succeed. On the parent commit this test must FAIL with the `AnchorPastTail` refusal (say so in the report; CI observes it). Rendezvous with channels or barriers, never sleeps; bounded waits of at least 120 s; every holder released and joined before asserting.
2. **The fix, in the copy engine, never in the recovery rules.** The invariant to establish: in the captured snapshot the anchor never points beyond the captured log tail (anchor <= log tail). The audit appender flushes the log BEFORE a checkpoint is written, and the log is append-only, so capturing the checkpoint store FIRST and the log SECOND (both inside the same bounded residual pass, the log's copy and hash taken after the anchor store's) yields a log that is at least as long as the anchor; or, if the engine's structure makes that ordering impossible, re-copy and re-hash the log after the anchor store inside the same pass. Choose by reading the code (how the residual pass orders the audit files, how the checkpoint journal's final re-copy works, what the manifest records and verifies) and state the choice and why the other option was rejected. The manifest must still describe exactly the bytes that were copied (hashes taken from the final copy, never from an earlier read); a log that grows after capture is not an inconsistency, an anchor beyond the log tail is. Do NOT change the audit recovery rules, the HMAC chain, the log format, the checkpoint format, the manifest format or its version, or any wire operation; do not add a dependency or a configuration key.
3. **A second test for the other direction and for a quiet server.** (a) A copy taken while NO audit activity happens still restores and boots (regression lock for the new ordering); (b) a copy taken while audit events keep arriving (several flush + checkpoint cycles during the pass, driven deterministically through the hook, not by timing) restores and boots, and the restored log verifies up to the anchor. Each assertion names the mutant it catches (the old ordering, a manifest that records the pre-capture hash).
4. **Restore-side check (only if cheap and sound).** If the staged restore can verify the audit anchor against the log tail with the EXISTING recovery routine without opening the live audit store (read how `restore/catalogue.rs` validates the catalogue and what the verify step already reads), add that check so an inconsistent copy that was produced by an OLDER server version is refused at restore time with the typed restore refusal instead of at the first boot; if it cannot be done without duplicating the recovery rules, do not do it and say so in the report (a later task may).
5. **Guide.** In the backup section of `docs/guide-docs/guide/07-operations.md` (Russian): the capture order of the audit files in an online copy and the invariant (the anchor never ahead of the log), what the operator sees if an inconsistent copy from an older version is restored (item 4 or the first-boot refusal and the manual remedy the guide already describes for `AnchorPastTail`: find it and link to it; if none exists, say that none is promised), and that the audit log may be longer than the anchor in a copy (normal). Every statement must match the code.
