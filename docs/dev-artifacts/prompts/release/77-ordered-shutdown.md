# Brief: ORDERED-SHUTDOWN — one bounded, truthful teardown: the scheduled-backup worker and the audit drain/flush are owned OUTSIDE the shutdown deadline, errors reach `ShutdownReport`, and the refusal-audit queue is fair per principal

Path prefixes used below: `sched/` = `crates/server/shamir-server/src/boot/config/diagnostics/backup_online/`; `server/` = `crates/server/shamir-server/src/`; `sec/` = `crates/server/shamir-server-security/src/security/observability/logging/`. Re-open every path and line before relying on it (lines drift). Verified by two read-only traces of the landed code on 2026-11-21; not yet reproduced: the first tests prove it in CI. Two independent reviews (the scheduled backup R2d and the refusal audit of R4b step 2) found the same family of defects; this task fixes the family in one change.

## Why (confirmed by trace)

**Audit teardown (`server/engine/db_handler/repo_admin/repo_audit.rs`, `server/engine/server/server_handle.rs`, `sec/audit_appender.rs`, `server/boot/scheduler.rs`, `server/engine/server/server_launcher/launch.rs`).** `CancelRefusalAudit::close` stops new reservations; its 3-second `drain` only waits for the accepted-job count to reach zero, and on expiry logs and returns without aborting jobs or returning an error. A checkpoint holds the chain gate and then the appender persistence gate across the log flush and a Fjall `SyncAll`; the appender's background flusher takes that SAME gate before it checks its stop flag; shutdown awaits the flusher join and then takes the gate again for the explicit final flush; the contended acquisition is a synchronous `Mutex::lock()` (run inline or via `block_in_place`) with no deadline. So a stalled checkpoint sync stalls shutdown, and the existing 30-second `serve` timeout (`server/boot/runtime.rs`) starts only after a successful launch (both launch rollback branches in `launch.rs` repeat `drain -> appender shutdown -> scheduler shutdown` with no deadline at all), cannot preempt a synchronous lock or sync inside a poll, and a returned report does not bound process exit (foreground `main.rs` and the Windows service `server/boot/policy/windows_service.rs` drop the runtime normally, which waits for outstanding blocking work). The scheduler is not stopped by the root shutdown token (it has its own broadcast sent only by `Scheduler::shutdown`). Both the flusher's join result and the final flush result are discarded: a write or sync error is latched and later flushes return it, but `ShutdownReport::is_clean()` (`crates/engine/shamir-db/src/shamir_db/shamir_db/catalog/shutdown_report.rs`) stays true and the exit code 0. A refusal-audit job that is still QUEUED when the drain expires keeps the appender and its Fjall store alive past `ServerHandle::shutdown`'s release timeout. One authenticated principal can fill the 256 shared refusal-audit slots (`repo_audit.rs`, `activity/cancel.rs`) with repeated refusals on its own request while the writer is stalled, so another operator's refusal goes unrecorded though the reply is correct.

**Scheduled-backup worker (`sched/registry.rs`, `sched/schedule/runner.rs`, `sched/schedule/retention/preflight.rs`, `sync/offline/v2_verify.rs`).** Normal shutdown cancels the root token and awaits the scheduled task and the in-flight run before repositories flush: it DOES drain. At the 30-second deadline, however, `finish_shutdown` drops the shutdown future and with it the scheduler await; the native worker thread (its `JoinHandle` is discarded; completion is signalled by a oneshot after protocol, retention, final progress collection and drops) keeps running, and an embedding process that continues sees filesystem I/O and DB references outlive `serve`. Retention's verification hashes (`hash_file_streaming`) have no cancellation check between reads, only around `verify_manifest`.

## What (this step only)

1. **One shared audit-teardown deadline** for the three callers (normal stop and both launch rollbacks): signal the scheduler BEFORE joining it, close appender admission, move the checkpoint / flusher / final-flush BLOCKING work off the async poll path (spawn it as a blocking job and await the join handle with the deadline), and discard queued refusal-audit jobs that have not started when the drain expires. A timeout stops waiting; it does not cancel an in-flight `fsync` (say so in the guide).
2. **Truthful report.** Return the appender's flusher-join and final-flush results and record them in `ShutdownReport` (a typed audit-flush error and an audit-timeout error, exit code 70 where the report is unclean); on rollback log the cleanup error and preserve the ORIGINAL boot error. The cancellation reply and the refusal itself stay independent of the audit outcome.
   The clean-close audit anchor write is part of this: the audit appender (landed with the audit chain restart, `FjallAuditAppender::last_failure()` in `shamir-server-security`) latches an error when the final anchor/meta write at close fails but the server still reported a clean shutdown. Read that latched error after the final flush and surface it in `ShutdownReport` as a typed audit-anchor error (unclean, exit code 70) on all three callers; do not change the appender's anchor rules, the HMAC chain or the log format.
3. **Own the scheduled worker outside the deadline.** Keep the scheduled drain handle and the data-directory ownership in a place the shutdown timeout cannot drop (`server/boot/runtime.rs`, `server_handle.rs`): the deadline marks the report unclean, but the EMBEDDING shutdown path still awaits scheduled cleanup before returning; if the executable keeps forced-exit behaviour, make that a distinct policy chosen by the foreground and service callers (`main.rs`, `windows_service.rs`). Add cooperative cancellation checkpoints between chunks inside retention's verification hashing ONLY through the retention-side call path (do not change the shared verifier `sync/offline/v2_verify.rs` for other callers: another task, the snapshot lease, touches `sync/offline.rs`).
4. **Per-principal fairness of the refusal-audit queue.** A non-waiting per-principal share below the global cap of 256 (name the share, justify it), and a single consumer if that also bounds blocking-thread use; a refusal that finds no slot is counted as dropped exactly like today's global-cap drop.
5. **Tests (CI-only; registered in their `tests/mod.rs`; no sleeps as synchronization; awaits bounded at 120 s or more).** (a) `shutdown_reports_audit_timeout_while_checkpoint_holds_gate`: reuse the real launcher refusal-drain fixture (`server/engine/server/server_launcher/tests/activity_gauge_binding_tests.rs`, the test `graceful_shutdown_drains_accepted_cancel_refusal_before_final_audit_flush`) and the appender test's `gate_acquired_hook` pattern (`sec/tests/audit_appender_tests.rs`): hold a REAL checkpoint inside the appender gate on a separate thread (test-only plumbing to arm the hook across the crate boundary, listed in the report); assert the audit stage reports an audit timeout and teardown advances to repository teardown BEFORE the test releases the gate; an independent watchdog; always release and join before asserting. (b) `shutdown_report_is_unclean_when_audit_flush_fails`: same launcher, one buffered event, the existing `fail_next_flush` fault armed for shutdown; assert an audit flush error in `report.errors()` and exit code 70. (c) `shutdown_deadline_does_not_abandon_scheduled_worker`: reuse `launch_with_backup_test` and `finish_shutdown`'s short or paused deadline pattern (`server/tests/boot/shutdown_truth_tests.rs`); park the REAL native runner at retention verification with a rendezvous, let the deadline fire, assert the embedding shutdown future stays pending until the worker is released, then an unclean deadline report and a drained worker. (d) Both launch-rollback paths use the shared deadline (inject a failing bind). (e) Fairness: one principal cannot take more than its share while the writer is gated; another principal's refusal is still recorded. (f) the existing tests that these changes make wrong are corrected, never weakened.
6. **Guide.** In `07-operations.md` (Russian): the drop count is process-local job failures and rejections, not "records missing on disk"; the 3-second constant bounds only the drain wait, the shared deadline bounds teardown; what the report says on an audit timeout or flush error; a timeout does not cancel an in-flight fsync.

## Do not

Change the audit format, HMAC chain, the boot-time chain recovery (another task owns the audit-setup hunks of `launch.rs`: edit only the teardown hunks), retention's selection rules or ownership, the snapshot lease, any wire operation, add a dependency or config key, or widen an item beyond what this needs (list every widening). Do not "fix" the races by only changing the 3-second constant, by reordering alone, or by wrapping the current synchronous flush in `timeout`.
