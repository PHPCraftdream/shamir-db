## What (this step only), by reviewer finding number

1. **Finding 1 (P1): an identical retry can acknowledge `Applied` before it is durable.** In `execute/admin_db/schema_migration/apply/apply.rs` (about lines 136-181) the retry tries to release the fence only if it can reserve a matching `InDoubt` marker; when the original runner is still `Live` the reservation fails and the retry returns `applied` without the event being durable (`journal.rs` publishes the transaction before its explicit durability tail, so with a buffered WAL a retry can read the visible `Applied` before the original syncs it). Fix so that NO acknowledgement of `Applied` or of `FenceReleased` is returned before the event it reports is durable (the retry waits for or performs the durability tail of the event it observed, or refuses with the existing in-progress code while the original runner is live); keep the in-memory gate semantics. Test: a two-runner interleaving (a test-only rendezvous between publish and the durability tail) in which the retry must not report success before the sync completes.
2. **Finding 3 (P1): replacing a bound validator crosses a target fence.** `execute/core/admin_dispatch.rs` (~117-130) sends ordinary registration DDL through the serving check only; `admin_validator.rs` forwards `replace`, and `validator_management.rs` swaps the artifact under the same ID while keeping the bindings, so a replacement served by a free database changes the validation behavior of tables in a fenced database without consulting it. Make `replace` (and any other registration operation that changes the artifact of an ID which has bindings: drop and rename of a bound validator, if they are reachable) take the target admission of EVERY database that binds the validator, with the same shared reservation, refusal codes and ordering as bind/unbind (read how bind/unbind do it and reuse it; lock order stays deterministic, one identity at a time, no cycle). Global functions have global names and no single target: keep them out and say so. Test: replace a validator that a fenced database binds, served by a free database, refused; the same replace with no bindings or only free bindings succeeds.
3. **Finding 5 (P2): the startup error translation covers the wrong boundary.** `system_store/store.rs` (~183-210, 244-264) translates any `UniqueIndexCreationFailed` from the WHOLE system repository into journal damage: a unique-rebuild failure of another system table (for example one an embedder installed on `users_table`) is misdiagnosed as journal corruption. Restrict the translation to the journal table (identify the failing table by the error's own table identity or by opening the journal partition directly; do not match on message text). The second half of the finding (a journal row with undecodable record bytes makes the backfill fail with `Codec`, which cold replay wraps into `Internal`, so no migration durability code): map a codec failure during the journal's own index rebuild to the same typed refusal when the failing table is the journal. Tests: one for each direction.
4. **Finding 6 (P2): same-database explicit DDL lost whole-batch refusal.** `fence.rs` (~398-415) skips explicit targets even when they equal the serving database; a nontransactional batch served by fenced B can now create a free C and then fail on `CHMOD B` or `DROP DATABASE B`, leaving C created, while the runbook (`docs/guide-docs/guide/07-operations.md` ~2075-2082) promises whole-batch refusal for operations on the serving database; same-database rename/drop also changed from the live/reserved code `schema_migration_in_progress` to `schema_migration_in_doubt`. Restore the old behavior for explicit targets equal to the serving database (refuse the whole batch before the first effect with the old code) while keeping the new foreign-target coverage. Test: the batch above leaves nothing created.
5. **Finding 7 (P2): PLAN can issue the next plan while the preceding migration still owns the fence.** `plan.rs` (~81-136) checks only `history.unresolved`; an `Applied` tail without `FenceReleased` is not in that list, so after reopening with ordinal 1 `Applied` and no release a direct PLAN for ordinal 2 returns a plan while STATUS reports in doubt and APPLY refuses. Make PLAN refuse with the same code as STATUS/APPLY in that state. Test: reopen with an `Applied` tail, direct PLAN refused.

## Findings

1. **P1 — CONFIRMED: an identical retry can acknowledge `Applied` before it is durable.** `crates/engine/shamir-db/src/shamir_db/execute/admin_db/schema_migration/apply/apply.rs:136–181` attempts release only if it can reserve a matching `InDoubt` marker. If the original runner is still `Live`, reservation fails and the retry returns `applied` anyway. `system_store/catalogue/schema_migrations/journal.rs:755–769` publishes the transaction before its explicit durability tail. With buffered WAL, a retry can finish its initial identity flush **before** the original publishes `Applied`, then read the newly visible event **before** the original syncs it. The retry reports success; power loss can leave only `OperationComplete` on reopen. Retaining the in-memory gate is safe for admission, but does not make that acknowledgement durable.

2. **P1 — CONFIRMED: ordinary DDL admitted before the fence can invalidate recovery’s proof of ownership.** `crates/engine/shamir-db/src/shamir_db/execute/repo_admin/db_execute.rs:140–169` checks the serving fence once. `execute/admin_ddl/admin_table_index.rs:342–378` then resolves and checks the index without reserving the database or rechecking the fence. An ordinary `CREATE INDEX i` can pass entry and pause. Apply records `pre_state=absent` for its own `CREATE INDEX i`, then stops before the effect. The ordinary request can still create `i` with a **different definition**. Resume accepts it by name and journals completion: `execute/admin_db/schema_migration/apply/apply_operations.rs:695–719` → `apply/ddl_postconditions.rs:120–144`. This is a pre-existing admission-only limitation, now documented, but the recovery code still relies on the stronger guarantee that no other writer could have created the object.

3. **P1 — CONFIRMED: replacing a bound validator still crosses a target fence.** `crates/engine/shamir-db/src/shamir_db/execute/core/admin_dispatch.rs:117–130` sends ordinary registration DDL through the serving check only. `execute/admin_ddl/admin_validator.rs:36–65` forwards `replace`; `shamir_db/db/validator_management.rs:373–386,403–412` swaps the artifact under the same ID and retains bindings.
