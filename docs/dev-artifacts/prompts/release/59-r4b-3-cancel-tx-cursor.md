## Why

Release gate: "an operator can find and cancel a stuck query". A transaction that stays open (an abandoned interactive session holding a pinned snapshot and record locks) is the other half of "stuck": step 2 cancels running batches, this step lets an operator end an open transaction or release an open cursor of another session safely and see that it happened.

## What (this step only = §7 row 3)

1. **`CancelTx`.** Typed `BatchOp` + DTO in `shamir-query-types` (`CancelTx { tx_handle }`, outcome = the existing `CancelOutcome` of step 2: `cancelled | already_finished | already_committing | not_cancellable`; a typed `BatchOp` classification, activity name, HMAC canonical encoding and exhaustive matches exactly as step 2's `CancelRequest` did — find them by following that op through the code), builder in `shamir-query-builder`, `Client::cancel_tx` in `shamir-client` (the Rust client only; the TypeScript client is a separate task), server handler. Semantics: the target is an OPEN interactive transaction named by the minted handle shown in `ListActivity`; cancel = remove it from the registry and drop the owning `Arc<Tx>` so the existing RAII rollback releases the snapshot, the record locks and the one-per-session tx slot (design 3.4 items 1–2, the registration-failure path in `tx_handlers.rs` already proves drop-of-`Arc<Tx>` is a correct rollback). A transaction that is currently COMMITTING (the D8 word of the request executing its commit, or the tx's commit phase) is refused with `already_committing` — one CAS decides, as in step 2; read how the interactive commit path (`interactive_tx.rs`, the twin CAS site) interacts with the registry entry and make the registry-removal path respect it. A handle that no longer exists answers `already_finished`; a tx with an in-flight request on it: decide and document the precedent (default: the cancel removes the registry entry; the running request notices at its next checkpoint through its own cancel word and answers `cancelled`; never a half-applied commit). The owner session's next use of the cancelled handle gets the existing typed "transaction not found / closed" error: prove it with a test and say so in the guide.
2. **Cursors.** `CancelCursor` already exists for the OWNING session and treats a cross-session cancel as already closed (`cursor_registry.rs`, `fetch.rs`). Add the operator twin with the same permission rule as `CancelTx` (own cursor: authentication only; foreign cursor: `ActivityView:Manage` through the normal authorization path): a typed op named in the style of the others (decide the name, for example `CancelCursorAdmin { cursor_id }`; do NOT change the semantics of the existing session-scoped `CancelCursor`), same `CancelOutcome` (`cancelled` / `already_finished`; `not_cancellable` does not apply to cursors: say so), registry removal releasing the pinned snapshot by the existing drop path. Builder, Rust client method (`cancel_cursor_admin` or the name you chose), handler, tests.
3. **Activity states.** Make the rows tell the truth about what step 3 changes: a transaction row's state follows the real registry state (`active` / `awaiting_commit` / `expired_pending_reap` exist from step 1: verify each is actually produced; if `awaiting_commit` is never set, wire it or document it as not produced — do not claim states the code cannot show), a cancelled tx disappears from the next listing, a cancelled cursor likewise. No new row fields unless the design requires them (list any).
4. **Permission and audit (same as step 2).** Own transaction/cursor: any authenticated user, but the cancel arrives on ANOTHER session of the same user (a session cannot cancel through the connection whose request is in flight: design D20 — the lock-step connection); cross-user: `ActivityView:Manage` via the normal `authorize_access` path; the ops are added to the coarse-admin-gate exemption exactly as `CancelRequest` is; refusals (`already_committing`) and every successful cross-user cancel append to the audit chain through the existing admin-op audit path with operation names `cancel_tx` / the cursor op's name and a details payload of the target handle/id and the outcome only (no user text, no literals, no tokens). Followers: the ops are allowed on a follower for the follower's own operator transactions; replication-apply is not a registry transaction, nothing to refuse (state this in the report).
5. **Metric.** `shamir_cancellations_total{result="cancelled|already_finished|already_committing|not_cancellable"}` (counter, four fixed label values, no per-user or per-session labels), exported through the server's existing observability path like the activity gauges; every outcome of every cancel op of steps 2 AND 3 increments exactly one label (step 2 did not add the counter: wire its `CancelRequest` outcomes to it too; this is the one edit to step 2's code allowed).
6. **Tests (CI-only; the named ones of design §6 for this step plus):** `cancel_interactive_tx_rolls_back` (staged writes invisible to a fresh snapshot, the registry slot reusable by the same session, the pinned snapshot released: refcount returns to baseline), a tx holding record locks cancelled → a second transaction blocked on those locks proceeds, `cancel_tx_vs_commit_race` (cancel racing the commit CAS: exactly one outcome; if `already_committing` the commit completes and reports normally; assert on the SET of outcomes, never the interleaving), cursor cancel releases the pin, the owner's next use of the cancelled handle/cursor errors typed, `permission_denial_activity` extended with `CancelTx`/the cursor op (ordinary user cross-user → `permission_denied`, own → allowed), wire/serde/builder/HMAC-policy tests like step 2's, the counter test through the real launcher `/metrics` route, and an audit test. Real-server tests use TWO sessions. Persistent stores, every `TempDir` alive for the whole test, bounded awaits (at least 120 s), handshakes not sleeps, `argon2_concurrent_max` and `auth_init_rate_per_second` 64 in multi-session fixtures, poll pacing at least 20 ms, `shamir-test-diag` marks on the race tests.
7. **Guide (Russian, `docs/guide-docs/guide/07-operations.md`, extend the activity/cancel subsection step 2 added):** how to find and cancel an open transaction or cursor of another session (list → cancel from a second session), what the owner sees afterwards, what a cancel cannot do (a committing transaction), the outcomes table now covering the three ops, permissions, the metric. Typed-client examples only. Every statement must match the code.
