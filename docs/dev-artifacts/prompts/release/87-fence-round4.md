## Admission and lock trace

- **Inventory and writers.** The inventory is configured tables of all *loaded* databases and repos, not initialized `TableManager`s (`E/db_instance/db_instance.rs:146–159`; `crates/engine/shamir-engine-table/src/support/storage/catalog.rs:205–241`). It sees lazy, never-opened, and just-registered tables on those handles. It does not inspect durable catalogue-only repos that boot skipped for an unavailable factory (`DB/shamir_db/core.rs:447–515`). Normal CREATE TABLE and inline CREATE REPO tables use replication control and start with no caller-supplied validator IDs (`DB/execute/admin_ddl/admin_table_index.rs:48–106`; `DB/execute/admin_db/admin_db_repo.rs:314,419–436`). `CreateTableOp` has an optional declarative `schema` field, but this handler does not activate it; the separate schema DDL does so under control. Explicit bind/unbind write under the same control lock as registration. Typed APPLY checks binding scope, defers bind before acquisition and again before replay, and sends unbind through the same locked facade (`M/apply/apply.rs:383–386,429–455`; `M/apply/apply_operations.rs:520–530`). Logical import rejects validator and binding items (`crates/server/shamir-server/src/boot/config/diagnostics/logical/logical_import/load/preflight.rs:48–69`); seed installs declarative bindings in a private image under offline maintenance ownership (`crates/server/shamir-sync/src/sync/replication_seed/install/installer.rs:112–129,137–185`). Replication apply routes row `Put`/`Delete`, not validator binding envelopes (`E/tx/replication/apply_replicated.rs:151–197`). None of these checks makes two buffer handles coherent.
- **Lock order and cancellation.** Database lifecycle takes namespace → replication control → slot; cascade enumerates children before claiming its slot and mutating them (`DB/execute/admin_db/admin_db_repo.rs:100–103,169–233,633–652`). Bind/ACL admission returns a slot guard without keeping control; the metadata mutator can reacquire control. APPLY takes the existing server-wide function-family CAS before control, reserves the serving slot and foreign slots under control, then drops control before journal-admin acquisition. The capability retains RAII slot guards and an atomic flag, **not** a mutex or a map shard guard. The effect reacquires control after the intent append has released journal-admin (`M/apply/apply.rs:471–557`; `M/function_family/gate.rs:17–35`; `J/journal.rs:290–293,445–448,509–512`; `V/validator_rename.rs:88–110`). Two active A→B/B→A rename migrations cannot enter that sequence together; a family or slot conflict returns immediately rather than waiting. I found no lock cycle or retry loop in these paths. Existing mutually dependent **durable** markers would be an admission conflict, not a mutex deadlock.
- **Early exits.** A scan error or foreign refusal before acquisition drops any earlier foreign reservations and removes the fresh serving reservation, or restores its previous marker on resume. The namespace CAS is published only after the slots are held, with no await before guard construction. On cancellation or panic unwind after construction, `Drop` releases the foreign slots before clearing the flag. Once journal commit can detach, the tracked serving generation intentionally becomes in doubt; the control row and event are staged in the same transaction. This is not a reservation leak (`V/migration_admission.rs:93–99,136–175`; `M/fence.rs:343–352,385–397`; `J/journal.rs:714–766`). A fresh foreign refusal leaves the **journal** untouched, but identity lookup has already synced and the metadata scan can create keyspaces as noted above.
- **PLAN and retries.** Fresh history with no slot and durably released history with no marker pass state classification. `Failed` does not release the fence. A visible `FenceReleased` with a retained marker still blocks STATUS/PLAN and the next APPLY; an identical matching-tail APPLY can sync and acknowledge without clearing that marker. A matching `Applied` marker can take the release-only route. An old `Applied` snapshot followed by a vacant slot can conservatively refuse once after release. The matching-tail acknowledgement still checks the acquisition generation, not the incremented release generation (`M/apply/apply.rs:195–286`; `M/fence.rs:169–190,248–259`; `J/history.rs:232–297`).

## Layout and fixture lessons

Count every folder you add to with `ls` (many are at 7 entries: `python -I scripts/ci/check_layout.py` counts only tracked files, recheck after staging); at most 1000 lines per file, one primary item per file, `mod.rs` re-exports only (the rust-guard structure gate allows nothing else in a `mod.rs`: shared helpers go in a named file), tests in `tests/` folders, no inline `#[cfg(test)]` modules, no local `use`, no new `#[allow]`. Persistent stores, every `TempDir` alive for the whole test, close handles and wait for the server task to finish before reopening a directory (Windows holds Fjall locks until the dropped engine's background handles finish: reopen with a bounded retry on `Locked` only, like `init_waiting_for_locks` in the function-family crash tests), handshakes not sleeps, every await bounded by a generous timeout (at least 120 s: a hang detector, the Windows runner is up to 10x slower), a batch is at most 50 queries, per-session request rate limit 500 req/s (never poll in a tight loop: pace status polls at 20 ms or more), set `argon2_concurrent_max` and `auth_init_rate_per_second` to 64 in fixtures that open several sessions, debug-test stacks are small (call concrete handlers through `Box::pin`, run deep tests on a roomy thread, `on_big_stack`), assert on invariants and sets, `shamir-test-diag` marks for flake-prone tests.

## Rules that bind the change

* Machine memory: at most ONE cargo command at a time machine-wide (other executors run: if a cargo run is already in progress wait for its notification, never poll), ALWAYS as `bash <orch>/cg.sh env RUSTC_WRAPPER= CARGO_TARGET_DIR=<artefacts>/target-exec wnice -p idle -c 50 -t 8 -m 50 -- cargo ... -j 1 > <logfile OUTSIDE the repository> 2>&1` (the wrapper serializes cargo across executors and the shared `CARGO_TARGET_DIR` keeps registry dependencies compiled once for all executors: never run `cargo clean`, never set another target dir; never `-j 2`; never piped through `tail`/`head`; `cargo fmt` rejects `-j`: run it with `CARGO_BUILD_JOBS=1` under the same wrapper); every worker you spawn must be told the same, and no worker may run cargo at all: only you, the top executor, run `check`/`clippy`/`fmt` under these rules (workers edit files and read code only).
