## What (this step only)

1. **P1 (findings 1 and 2 of the report, one root cause): the set of databases that bind a validator is read from reverse metadata that is not authoritative.** `validator_management.rs` (~873-889, 954-984) writes the table's own binding first, then updates `bound_in` best-effort and still returns success when that save fails; on reopen the registry restores its reverse references only from the validator catalogue (`core.rs` ~599-617), while the table restores its binding from its own info record. The new database-rename re-key (`db_management.rs` ~331-367, 399-472; `schema_management.rs` ~902-964) moves the database, repo and table rows first and then saves the `bound_in` rows one by one, so a failure between them leaves a stale `old/...` reference. Successful `RENAME TABLE` and `RENAME REPO` also leave stale child components (`table_management.rs` ~428-457, `db_management.rs` ~796-858), so a later unbind under the new name does not remove the old reference and a later DROP is falsely refused as still bound. Consequence: replace, rename or drop of a bound validator reserves nothing (or the wrong identity) and swaps or removes the artifact that a fenced database's table still invokes. Fix by making the binding set used for admission AUTHORITATIVE: derive the databases that bind a validator from the tables' own persisted bindings at admission time (this is a rare DDL path; state its cost and that it opens no more than the metadata it needs), and use the SAME derivation for the "still bound" refusal of DROP and for rename. The reverse index may stay as a cache but nothing that decides admission or refusal may rely on it alone; a stale or missing reverse row must neither admit nor falsely refuse. Keep the lock order (one identity at a time, deterministic, no cycle) and the TOCTOU argument (derivation happens under the same replication-control serialisation as bind/unbind). Tests (no failure-injection seam needed): (a) bind in B, clear or omit the reverse reference in the catalogue record, close and reopen, fence B, replace and rename and drop served by A are all refused with B's target code; (b) rename a database, table and repo that hold a binding and show admission reserves the NEW identity and does not reserve a recreated free `old`; (c) a stale reverse row naming a nonexistent database neither blocks a legitimate replace nor admits a bound one. If you can inject the seventh-write failure cheaply, add it; otherwise say why the crafted-state tests cover it.
2. **P1 (finding 3 of the report): the `__system__` exemption is broader than the internal system store.** `validator_management.rs` (~102-109) drops the system database name from the admission set unconditionally, but wire CREATE DATABASE validates only characters, so a user database named `__system__` can be created (`admin_db_repo.rs` ~33-74, `db_management.rs` ~119-166), bound to a validator and fenced, and its bindings are then ignored. Choose the narrower sound fix and state it: refuse creating or renaming a user database to the reserved name with a typed validation refusal (existing databases with that name keep working and are NOT exempted from admission), or tell the internal store from a user database by identity instead of by name. Test: the user-database case is refused or reserved, and the internal store's own validators still work.
3. **P2 (finding 4 of the report, first half): a migration-owned validator rename strands its serving database on a foreign admission conflict.** `apply.rs` (~414-454) and `apply_operations.rs` (~348-384, 448-461) write `Started` and `OperationIntent` before the new binding-holder reservation; if `v` is bound in a fenced B, a rename migration served by A returns A's `schema_migration_in_doubt`, leaves A fenced although the rename never ran, and `preserve_family_denial` preserves only `access_denied`. (The second half of that finding, the non-atomic live/durable rename, is pre-existing: report only.)

## Disposition of the first review

- **1 — FIXED for typed APPLY.** The latest matching `Applied` or `FenceReleased` checks the **Applied acquisition generation**, correctly not the incremented release generation. A live owner or matching release reservation refuses with `schema_migration_in_progress`. A matching `Applied` marker takes the release path; that path syncs before and after its transaction. All other matching-tail acknowledgements call the shared journal sync, even if the slot is now vacant. Failure retains an existing marker; the next matching-tail retry still takes a sync path. An older ordinal skips that sync only after a validated later history proves it was released, and the next acquisition itself preflushes the journal. The original runner still awaits both durable tails before success. A healthy runner drops the slot; no permanent `in_progress` loop found. A visible release after a failed tail can be acknowledged after a successful sync **without clearing the marker**; reopening is still needed to resume normal admission (`M/apply/apply.rs:185–277,536–555`; `M/fence.rs:169–190,248–259,385–397`; `J/journal.rs:290–293,501–581,752–766`; `M/apply/apply_operations.rs:57–66,157–192`).
- **3 — PARTIALLY.** With complete metadata, ordinary replace/rename deduplicate and sort **database names**, resolve each to an identity, and fail immediately on the first occupied slot. Earlier reservations unwind before any write. Bind/unbind and registration use the same replication-control lock, so a successful facade bind cannot insert itself between discovery and mutation. I found no lock cycle in the traced handlers: lifecycle takes namespace → replication control → slot; ACL/bind admission returns a slot guard after dropping control, and can then reacquire control for the write; registration never waits on an occupied slot; APPLY drops control before taking journal-admin. Registry writer guards are synchronous and do not cross an await. These facts do not make the reverse metadata authoritative or the rename failure paths atomic. Direct embedder mutation APIs explicitly skip fence reservations (`validator_management.rs:24–41,311–324,444–482,571–601,712–752,845–887,921–937`; `DB/execute/core/admin_dispatch.rs:230–282`; `M/apply/apply.rs:484–509`).

The exhaustive `contextualize_db_error` match and cold replay preserve the wrapper. A user-table rebuild error still propagates before the repo is published; a lazily opened table still fails at lookup. The public Rust enum gains a variant, so downstream exhaustive Rust matches must account for it. I found no unhandled exhaustive match in the paths traced. `IndexRebuildFailed`, `Codec`, `Internal` and `UniqueIndexCreationFailed` have no stable `DbError::code()`; only the journal translation supplies the existing migration code. Server boot reports it in `BootError::ShamirDbInit`, not an HTTP response. No HTTP status or wire mapping changed (`crates/index/shamir-index-core/src/backend.rs:110–151`; `crates/storage/shamir-storage/src/core/error.rs:26–33,303–329`; `crates/engine/shamir-engine/src/db_instance/db_instance.rs:62–78`; `crates/server/shamir-server/src/engine/server/server_launcher/launch.rs:269`; `crates/server/shamir-server/src/engine/db_handler/handler.rs:698–714`).

Names are exact, case-sensitive strings; query aliases are not database aliases. `RENAME B TO X` is caught at entry; `RENAME X TO B` cannot replace an existing B.
