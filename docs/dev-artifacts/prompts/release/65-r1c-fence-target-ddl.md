Origin of this task: the independent review of R1c step 4 (2026-11-19); the gaps are pre-existing design holes, NOT regressions of that step, and they do not block the migration feature (migrations are not released; the holes need administrator rights on both databases) — but the fence is a safety claim and must be true before the release gate.

## Why

The fence says: while a migration owns a database, no other path may write to it or change its structure. Today the guard is keyed by the NAME of the database serving the request. An operation that is served by database A but whose explicit target is database B (bind/unbind of a validator through another database, rename/drop paths that name a target, anything that resolves a target by name inside the admin dispatcher) is checked against A's gate and marker, not B's, so it passes straight through B's live fence or B's in-doubt marker. Second, the gate and the marker are two separate in-memory states keyed by NAME, read non-atomically: a resume can remove the marker and install the gate between the two reads, and a rename/drop admitted while the target was free is not serialized against a migration reserving the target right after. Third, a few startup journal edge cases classify damage inconsistently.

## What (this step only)

1. **One atomic fence state per target.** Replace the pair "gate map + marker set" read separately with ONE per-target state (`live{generation}` / `reserved` / `in_doubt`, absent = free) behind a single lock-free structure with compare-and-set transitions, keyed by the database's stable identity (`DatabaseIdentity`) with the name only as the lookup (a rename must not leave the state behind or let a new database inherit it: decide and document what a rename of a fenced database does — it is refused today by the lifecycle guard, keep that, and prove the key survives or is refused consistently). Every transition the code makes today (reserve before the durable CAS, hold with the durable generation, release, in-doubt seeding at open, resume clearing the marker and installing the live state) becomes one atomic step on that state; the read side (`maintenance_fence_refusal`, lifecycle refusal, status reporting) reads the state ONCE. Keep the stable wire codes and messages exactly (`in_progress` for reserved/live, `in_doubt` for the marker, the lifecycle refusal code). Keep the RAII guard semantics (drop before `hold` cancels the reservation; a run that exits after `hold` with the durable fence still owned leaves the in-doubt marker).
2. **Check the TARGET of every operation in ONE shared place.** Find every admin operation and DDL path that carries or resolves a target database different from the serving one (read the whole admin dispatch; the known cases are validator bind/unbind and the rename/drop family, but enumerate by reading, with a table in the report: operation → how the target is named → where the check now happens → test). Put the check in one shared function of the admin dispatcher that takes the resolved target identity and the operation's mutability class (read-only operations pass; writes, DDL and `CallOp` are refused exactly as for the serving database), and call it from that single point rather than at each handler. An operation that cannot be routed through the shared point is listed with its blocker. Cascades (drop of a database that owns child objects) re-check after the children are enumerated and BEFORE the first mutation, and the check and the mutation are not separated by a window in which a migration can reserve the target: if the shared state offers a "reserve for lifecycle" transition (a lifecycle op takes the target's state as `reserved-by-lifecycle`, so a migration cannot reserve it meanwhile and the lifecycle op is refused if the state is not free), use it and release it on every exit path; say what you chose and why.
3. **Startup journal edge cases** (each a typed outcome with a test; the rule of the landed design stands: any DETECTABLE journal damage fails the WHOLE open with the typed `schema_migration_durability_unavailable` error): (a) a unique-index rebuild failure of the journal at open (`catalog_access` → `identity_migration`) surfaces as `UniqueIndexCreationFailed` without that code in the diagnostics: map it; (b) the identity probe of the journal event (`journal/event.rs`) treats ANY deserialization error as a successful routing check: a field truncated after a foreign identity was read becomes a per-database error instead of failing the whole open — tighten the probe so that only a CLEAN "foreign identity" verdict counts as routing, everything else is damage; (c) the lower scanner skips a malformed physical record id before the journal can classify it: report it as damage to the journal reader when the record belongs to the journal table; (d) a durable `Applied` event followed by a crash before `FenceReleased` is not classified as unresolved by the startup snapshot: classify it (the fence is still owned) so the in-doubt marker is seeded. If any of (a)–(d) turns out to need an engine-table or storage change beyond a typed error mapping, STOP that item, list exactly why, and continue with the others.
4. **Guide (Russian, the migrations runbook section of `docs/guide-docs/guide/07-operations.md`).** State precisely: the fence guards the target database of every operation, not only the serving one; at an early refusal before the gate is reserved no fence and no marker remain; what each state means to an operator and how each clears. Every statement must match the code.
5. **Tests (CI-only; add to the existing migration test folders, no new top-level test file unless a folder limit forces it).** For EACH operation of the item-2 table: refused with the right code while the target holds a live gate, a reserved gate, and an in-doubt marker, accepted when free, and never refused when only the SERVING database is fenced and the target is free. The race tests: resume vs rename/drop of the same target (no interleaving lets a lifecycle op pass a gate or a marker; use the persistent stores and the failure-injection seams of the R1c step 4 tests, assert on the SET of outcomes, never on the join order), reserve vs reserved-by-lifecycle, two appliers. The four startup cases of item 3 through reopen tests (persistent stores; every `TempDir` and engine handle alive for the whole test; close handles and wait for the engine's background tasks before reopening a directory; reopen with a bounded retry on the typed `Locked` error only, like `init_waiting_for_locks` in the function-family crash tests). Flake diagnostics (`shamir-test-diag` `FlakeGuard`) on every race test; every await at least 120 s.
6. **CI selection:** check `scripts/ci/matrix/` selects the changed crates' tests on the three OS; widen only where a target is not selected, and list it.

## Do not

Change the durable journal format, the canonical body, the stable codes and messages of the wire, the apply/resume semantics visible to clients, add a persistent marker (the marker stays in-memory only; it is re-seeded from the journal at open), add a dependency, weaken an assertion, use sleeps for synchronization, change the migration operations' admitted set, or widen an existing item beyond what the new code needs (list every widening). A `Mutex`/`RwLock` is not acceptable for the per-target state: lock-free map plus compare-and-set (`dashmap` entry API under `THasher` as the current gate already is, or `scc`), no `len()` on `scc` maps. The state is touched only by migration/lifecycle admission and by the batch entries' refusal check: the check on the batch hot path must stay one lookup of a map that is EMPTY in the common case (keep the empty-map fast path the current code has, say how).


## Layout and fixture lessons

Count every folder you add to with `ls` (many are at 7 entries: `python -I scripts/ci/check_layout.py` counts only tracked files, recheck after staging); at most 1000 lines per file, one primary item per file, `mod.rs` re-exports only (the rust-guard structure gate allows nothing else in a `mod.rs`: shared helpers go in a named file), tests in `tests/` folders, no inline `#[cfg(test)]` modules, no local `use`, no new `#[allow]`. Persistent stores, every `TempDir` alive for the whole test, close handles and wait for the server task to finish before reopening a directory (Windows holds Fjall locks until the dropped engine's background handles finish: reopen with a bounded retry on `Locked` only, like `init_waiting_for_locks` in the function-family crash tests), handshakes not sleeps, every await bounded by a generous timeout (at least 120 s: a hang detector, the Windows runner is up to 10x slower), a batch is at most 50 queries, per-session request rate limit 500 req/s (never poll in a tight loop: pace status polls at 20 ms or more), set `argon2_concurrent_max` and `auth_init_rate_per_second` to 64 in fixtures that open several sessions, debug-test stacks are small (call concrete handlers through `Box::pin`, run deep tests on a roomy thread, `on_big_stack`), assert on invariants and sets, `shamir-test-diag` marks for flake-prone tests.

## Rules that bind the change

* Machine memory: at most ONE cargo command at a time machine-wide (other executors run: if a cargo run is already in progress wait for its notification, never poll), ALWAYS as `bash <orch>/cg.sh env RUSTC_WRAPPER= wnice -p idle -c 50 -t 8 -m 50 -- cargo ... -j 1 > <logfile OUTSIDE the repository> 2>&1` (the wrapper serializes cargo across executors; never `-j 2`; never piped through `tail`/`head`; `cargo fmt` rejects `-j`: run it with `CARGO_BUILD_JOBS=1` under the same wrapper); every worker you spawn must be told the same, and no worker may run cargo at all: only you, the top executor, run `check`/`clippy`/`fmt` under these rules (workers edit files and read code only).
* Leave no scratch files in the tree and none outside it (edit only paths inside this worktree).
* Wrap-up: the hard limit is 150 minutes. At about 105 minutes (70%) stop adding scope, bring the change to a compiling, formatted, clippy-clean state and write the final report (what is done, what is missing, what each check printed); a run that hits the limit without a report is lost work.
