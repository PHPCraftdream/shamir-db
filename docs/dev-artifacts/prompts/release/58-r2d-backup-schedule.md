# Brief: R2d — built-in backup schedule, retention policy, copy metrics and the alert rule (design addendum + implementation, small)

Plan (read first): `docs/dev-artifacts/release-1/02-online-backup-and-encryption.md` §4 "R2d. Расписание и хранение" and §6 acceptance, `docs/dev-artifacts/release-1/04-observability.md` row "Копии" (last successful copy time, duration, size; R2d). Landed foundations you build on (re-open every path before relying on it): the online copy engine and protocol in `crates/server/shamir-sync/src/sync/durability/backup/online/`, the server registry/adapter/session machinery in `crates/server/shamir-server/src/boot/config/diagnostics/backup_online/` (`StartBackup`/`BackupStatus`/`CancelBackup`, the destination root rules, the one-in-process-copy permit, the metrics), the manifest and `verify`, restore, the existing `shamir_backup_*` metrics, and the guide section "копия без остановки" in `docs/guide-docs/guide/07-operations.md` §8. The design of the online copy: `docs/dev-artifacts/design/online-backup.md` (open question Q6: destination retention is append-only in R2a and pruning is R2d).

## Why

Release gate: "an operator gets a restorable copy without stopping the server, on a schedule, with retention and an alert when copies stop". R2a delivered on-demand online copies through admin operations; R2d makes the server take them by itself, keep a bounded number, and tell the operator when they stop.

## What (this step only)

1. **A short design addendum first** (`docs/dev-artifacts/design/backup-schedule.md`, English, at most ~150 lines, committed in the same change): the configuration surface, the scheduler's relation to the existing one-copy permit and registry, the retention rules and their safety proof, the metrics, the alert rule, the failure modes, and what is deliberately NOT done (object-storage delivery: the operator's tools take the directory; point-in-time restore R2b; encryption R2c). Decisions you must record: (a) configuration lives in the server config next to the existing backup destination settings, disabled by default; fields: `interval` (humantime-style string already used by the config, minimum 1 minute is refused below), optional daily `window` (`HH:MM-HH:MM` local, overnight allowed: a run is only STARTED inside the window), `run_on_start` (default false: the first run is one interval after boot), `retention.keep_last` (default 7, minimum 1) and optional `retention.max_age_days`; validation at boot refuses nonsense (zero, window equal ends, keep_last 0, a destination that is missing, inside the data directory, or not private by the existing destination rules); (b) the scheduler is a server task that starts a copy through the SAME in-process path the admin operation uses (same permit, same registry, same protocol, same failure isolation), as a system actor with no session; a start while an admin copy is running is skipped and counted (never queued twice, never concurrent); the schedule state is in memory only; (c) shutdown cancels a running scheduled copy cooperatively and the scheduler stops without leaving partial output (the existing failure isolation applies).
2. **Retention** (after every SUCCESSFUL scheduled copy, and only then): list the destination root, consider only direct child directories whose name matches the copy-directory naming and whose manifest PARSES and VERIFIES (the existing `verify`, bounded); order by the manifest creation time; never delete the copy just created, never delete when fewer than `keep_last` verified copies would remain, delete older verified copies beyond `keep_last` and, if `max_age_days` is set, those older than it but never below `keep_last`; leave every directory that is not a verified copy (foreign files, partial or unverifiable directories, copies of another server) UNTOUCHED and report their count in the status/metrics. Deletion removes the whole copy directory with the existing safe-removal helper, one at a time, cancellable, and a failed deletion is logged (payload-free) and counted, never fatal. Prove by tests that a destination containing foreign files and an unverifiable copy keeps them, that `keep_last` is honoured, and that retention never runs after a failed copy.
3. **Metrics** (names in the reserved `shamir_backup_*` space; labels only `kind`/`result` as the existing ones; follow the export path of the existing backup metrics): `shamir_backup_last_success_timestamp_seconds` (gauge, unix seconds, 0 before the first success), `shamir_backup_last_duration_seconds` and `shamir_backup_last_bytes` (gauges of the latest successful copy), `shamir_backup_scheduled_runs_total{result="started|skipped_busy|skipped_window|failed|completed"}`, `shamir_backup_retention_deleted_total`, `shamir_backup_retention_failed_total`, `shamir_backup_retention_untouched` (gauge of foreign/unverifiable entries). Reuse what R2a already exports where it fits (do not duplicate the started/completed/failed/bytes counters); the last-success gauge must also be set by an ADMIN copy that succeeds.
4. **The alert rule**: a ready Prometheus rule file `deploy/alerts/shamir-backup.rules.yml` (the design of the metrics task puts alert rules under `deploy/alerts/`: create that folder, no other file goes in it in this step; the later metrics-guide task R4a-6 adds `deploy/alerts/shamir.rules.yml` next to it; check `ls` first and keep every folder at most 7 entries) with `BackupStale` (`time() - shamir_backup_last_success_timestamp_seconds > <threshold>` with a threshold variable documented as 1.5 × the interval and a `for` clause), `BackupFailing` (consecutive scheduled failures via the counter) and `BackupRetentionFailing`; the guide explains how to wire them. No Grafana work in this step (task R4a-6 owns dashboards).
5. **Tests (CI-only):** config parsing and validation (every refusal), the scheduler's decisions with an injected clock and an injected copy runner (window logic including overnight, interval, `run_on_start`, skip-while-busy, skip-outside-window, shutdown cancel), a real-server test that a scheduled copy appears in the destination, verifies, is counted in the metrics and that retention prunes to `keep_last` over several fast runs (use an injected short interval through a test-only seam; no sleeps for synchronization: await the scheduler's own completion signal), the retention safety cases of item 2, the metrics scrape through the real launcher `/metrics` route, the alert rule file parses (a Python or Rust test that loads the YAML and checks the three alert names and that every metric name it references is exported: reuse the CI scripts convention if a rules lint already exists).
6. **Guide (Russian, `docs/guide-docs/guide/07-operations.md`, §8 backup, a new subsection «Расписание и хранение копий»):** configuration with an example, what the scheduler does and does not do, retention rules and what it never deletes, the metrics table, the alert rules and thresholds, what to do when copies stop, the interaction with admin copies, restore of a scheduled copy (unchanged), object-storage delivery by the operator's own tools. Every statement must match the code. Example configuration in the server's config format (read how the neighbouring examples are written; no raw JSON).
7. **CI selection:** check `scripts/ci/matrix/` selects the changed crates' tests on the three OS; widen only where a target is not selected, and list it.

## Do not

Change the copy protocol, the manifest format, restore, the admin operations or their wire types, add a dependency, add persistence of schedule state, delete anything that is not a verified copy, run a scheduled copy concurrently with another, weaken an assertion, use sleeps for synchronization, or touch the TypeScript clients. Stop and list any engine-layer need instead of adding it.

## Layout and fixture lessons

Count every folder you add to with `ls` (many are at 7 entries: `python -I scripts/ci/check_layout.py` counts only tracked files, recheck after staging); at most 1000 lines per file, one primary item per file, `mod.rs` re-exports only (the rust-guard structure gate allows nothing else in a `mod.rs`: shared helpers go in a named file), tests in `tests/` folders, no inline `#[cfg(test)]` modules, no local `use`, no new `#[allow]`. Persistent stores, every `TempDir` alive for the whole test, close handles and wait for the server task to finish before reopening a directory (Windows holds Fjall locks until the dropped engine's background handles finish: reopen with a bounded retry on `Locked` only, like `init_waiting_for_locks` in the function-family crash tests), handshakes not sleeps, every await bounded by a generous timeout (at least 120 s: a hang detector, the Windows runner is up to 10x slower), a batch is at most 50 queries, per-session request rate limit 500 req/s (never poll in a tight loop: pace status polls at 20 ms or more), set `argon2_concurrent_max` and `auth_init_rate_per_second` to 64 in fixtures that open several sessions, debug-test stacks are small (call concrete handlers through `Box::pin`, run deep tests on a roomy thread, `on_big_stack`), assert on invariants and sets, `shamir-test-diag` marks for flake-prone tests.

## Rules that bind the change

* Machine memory: at most ONE cargo command at a time machine-wide (other executors run: if a cargo run is already in progress wait for its notification, never poll), ALWAYS as `bash /d/system_artefact/orch/cg.sh env RUSTC_WRAPPER= wnice -p idle -c 50 -t 8 -m 50 -- cargo ... -j 1 > <logfile OUTSIDE the repository> 2>&1` (the wrapper serializes cargo across executors; never `-j 2`; never piped through `tail`/`head`; `cargo fmt` rejects `-j`: run it with `CARGO_BUILD_JOBS=1` under the same wrapper); every worker you spawn must be told the same, and no worker may run cargo at all except `check`/`clippy`/`fmt` under these rules.
* Leave no scratch files in the tree and none outside it (edit only paths inside this worktree).
* Wrap-up: by 150 minutes bring the change to a compiling, formatted, clippy-clean state and stop; say in the final report what is missing.

## Policy (verbatim, binding)

Compilation, builds and tests run on GitHub CI, not on this machine. Banned locally: `cargo test`, `cargo nextest`,
`./scripts/test.sh`, `cargo build`, `cargo run`, `cargo bench`, `cargo doc`, npm/tsc builds, any build or test run.
Allowed locally only: `cargo check -p <crate> --all-targets`, `cargo clippy -p <crate> --all-targets -- -D warnings`,
`cargo fmt -p <crate>` (and `-- --check`), `python -I scripts/ci/check_layout.py`.

⛔ NEVER run `git reset` / `checkout` / `clean` / `stash` / `restore` / `rm`, or any git command that mutates the working
tree or index. Only edit files; the orchestrator commits. (For file moves use a plain filesystem move and say so in the report;
the orchestrator stages them so git detects the renames.)
