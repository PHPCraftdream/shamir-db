## Appendix — the second reviewer's report (verbatim)

VERDICT: FAIL

The original missing-source race is fixed, and the lease protects readers once the marker exists. **The remaining blocker is the transition from an unmarked root to a marked one:** retention can delete a snapshot while a reader that started before provisioning is still reading it. The guide tells operators to prevent that race, but the implementation does not enforce it.

**Evidence:** CONFIRMED means traced end to end in the branch, including dependency source where relevant; it does not mean reproduced at runtime. INFERRED marks platform behavior I did not establish from source. Paths below use `sync/` = `crates/server/shamir-sync/src/sync/durability/backup/`, `server/` = `crates/server/shamir-server/src/`, and `sched/` = `server/boot/config/diagnostics/backup_online/`.

## Findings

1. **P1 — CONFIRMED: First provisioning can make a snapshot eligible for deletion while an existing reader is unleased.** `sync/snapshot_lease.rs:98–126` treats an existing timestamped child as an export if its parent has no marker. That decision is final for both `verify_manifest` and restore. Boot, the scheduled runner, and prune can independently create the marker without knowing about the earlier reader (`server/engine/server/server_launcher/support/helpers.rs:38–66`, `sched/registry.rs:554–598`, `sched/schedule/retention/prune.rs:74–80,229–267`). **Scenario:** On the first boot after upgrade, start verifying old, already-owned snapshot A before the marker exists. Pause after the manifest read. Boot creates the marker; `run_on_start` publishes B with `keep_last = 1`; retention gets an uncontended exclusive lock and deletes A. The reader resumes and cannot open a payload. No held marker was unlinked and no snapshot was modified by the operator. Repair also has this window if the obstruction is removed before provisioning: an invalid marker refuses readers, but an **absent** marker does not. Adoption can put an outage copy into the deletion set in the first repaired pass. Export-only verification has the same transition exposure precisely because it never locks. The quiescence instructions at `docs/guide-docs/guide/07-operations.md:1434–1442` mitigate this operationally; they do not satisfy the unconditional guarantee.

2. **P2 — CONFIRMED: Adoption matches a pathname and a manifest timestamp, not the output that was recorded.** The record has no directory identity or manifest digest (`sched/registry.rs:124–140,711–718,744–763`). Prune compares the creation time from a currently valid manifest, then rereads the sidecar but not the manifest or directory identity before tagging and selecting the path (`sched/schedule/retention/preflight.rs:23–40,116–124`, `sched/schedule/retention/prune.rs:125–170,195–261`). **Scenario:** Between runs, replace the recorded untagged A with another valid untagged v2 online tree under the same name, with the same `created_at_unix_ns` but different payloads and matching hashes. Repair with B newer and `keep_last = 1`: the replacement acquires the scheduler’s tag and is deleted. A replacement after the scan can even have a different creation time; the tag loop still uses the scan’s time. A foreign tag present at either sidecar check blocks adoption, and a static untagged replacement with a different time does not match. These replacement scenarios violate the guide’s immutable-root rule; they nevertheless disprove the implementation’s stronger “exact output” claim. The configured owner in the memory record is not evidence of ownership of a replacement that has no tag.

3. **P2 — CONFIRMED: A crash during tagging leaves a root entry that counts against the scan cap.** The named `.tmp…` file now lives in the root, with no crash-recovery cleanup (`sched/schedule/retention/ownership.rs:83–104`; `tempfile` 3.27.0, `src/file/imp/windows.rs:26–40`). It is not a snapshot, but prune excludes only the marker before charging an entry, then counts non-timestamp names as `untouched` (`sched/schedule/retention/prune.rs:104–132,173–182`; `budget.rs:11`). **Scenario:** A complete scan sees 4,095 non-marker entries. The process dies after staging a sidecar but before replacement. The next successful copy brings the total to 4,097 instead of 4,096; prune refuses before tagging or deleting. Further successful backups grow the backlog until an operator clears space in the scan. On Unix the temp can survive a process kill; on Windows this is the named-file implementation, not the anonymous delete-on-close implementation.

4. **P2 — CONFIRMED: The restore library now checks staging before the legacy probe, but the CLI can still write inside the target first.** `server/main.rs:356–383,482–483` initializes file logging before dispatching restore. The logging sink opens its configured path with `create(true).append(true)` (`crates/server/shamir-server-security/src/security/observability/logging/mod.rs:340–344,402–412`). **Scenario:** Set `logging.file` to a nonexistent `server.log` inside an initialized target. A legacy restore that later returns `StagedFileMissing` has already created the log file, even if it never emits a log line. The supplied-probe test bypasses CLI initialization. The library guarantee also assumes an ordinary, non-root target: for a filesystem-root target the fallback at `sync/restore.rs:375–396` puts staging **inside** the target, with only best-effort cleanup at `sync/restore.rs:785–793`.

5. **P3 — CONFIRMED: The public retention verifier relies on its caller for the bounds in its contract.** `sync/offline.rs:678–691` accepts any path and byte slice, walks and hashes without a lease, and checks `kind` **after** the walk. The actual scheduler caller does the v2-online check, size and tree bounds, and accounting first (`sched/schedule/retention/preflight.rs:23–48,60–124`). **Scenario:** Another Rust caller supplies a v2-offline manifest and a large tree under a marked root. The helper reads the tree unleased before refusing the kind. No shipped reader uses this path, but the public helper is not intrinsically bounded or online-only at the point it starts payload I/O.

6. **P3 — CONFIRMED coverage gap; Windows overlap INFERRED:** The tagging race test finishes the verifier **before** the actual replacement (`sched/schedule/retention/tests/prune_tests.rs:645–668`, `ownership.rs:99–104`). It proves the temp file is invisible, not what happens when a Windows reader has the final sidecar open during replacement. The pinned `tempfile` uses Unix `rename` or Windows `MoveFileExW(MOVEFILE_REPLACE_EXISTING)`, with no cross-volume copy fallback (`tempfile` 3.27.0, `src/file/imp/unix.rs:94–97`, `src/file/imp/windows.rs:92–117`). Successful replacement publishes whole bytes; it is not an in-place rewrite or a power-loss guarantee. If Windows refuses replacement because of an open destination, metadata is not torn, but the pass fails. A fresh copy in that branch is not queued for adoption because pre-copy provisioning succeeded. Whether ordinary restore’s `CopyFileExW` overlaps in a way that triggers that failure needs Windows evidence.

### Guide corrections still needed

- `docs/guide-docs/guide/07-operations.md:1321–1343,1366`: distinguish **deletion passes** after successful copies from **pre-copy marker attempts**, whose failures count even if the copy fails or is cancelled.
