# Brief: R5 step 1 (PR1) — the administrative shell foundation: `shamir-server shell`, connection profiles with verified pins, TCP and IPC SCRAM, secret entry without echo, JSON Lines v1 output and exit codes, `ping` and the catalogue commands

Design (settled and LANDED, read all of it first): `docs/dev-artifacts/design/admin-shell.md` (543 lines). This step is exactly the **PR1 row of §9** and the decisions it cites: §2 (packaging: the `shell` subcommand of the production binary, dispatched before config and logging in the `main.rs` slot the design names, package-root module through the `#[path]` precedent, no new crate), §3.1–§3.2 (transport inventory and what stage R5a PR1 supports: TLS-TCP and IPC with SCRAM only, verified pin required, no plaintext, no resume, no `--accept-new-host`), §4.1 (connection commands), §4.3 (catalogue commands), §5 (modes and output: batch = exactly one argv command after `--`, JSON Lines v1 always in batch, human tables only on an interactive TTY, versioned output, the exit-code table, no history at all), §6 (safety: no client-side privilege, typed denials, no raw server strings or argv or handshake metadata in output), §7 (zero new registry crates, edges declared per PR), §8 (acceptance rows R5a for the PR1 head). The plan: `docs/dev-artifacts/release-1/05-admin-cli.md`. Re-open every path:line the design cites before relying on it (line numbers drift).

## Why

Operators need a tool that connects to a running server through the normal protocol, so that the release gate "an operator can check, inspect and repair" is served by commands and not by reading files. PR1 builds the foundation every later PR (R5-2 … R5-6) extends: the connection and secret handling, the output contract and the command registry, with the first read-only commands.

## What (this step only = PR1)

1. **Dispatch and module tree** exactly as §9 PR1 and §2: the early `shell` dispatch in `crates/server/shamir-server/src/main.rs` (the pre-config slot; `--config` stays required and validated on every pre-existing path, only `shell` and later `backup-verify` skip it), the package-root `shell/` module with `mod.rs` (declarations and re-exports ONLY), `output.rs`, `parser.rs`, `connect/` (`mod.rs`, `scram.rs`, `profile.rs`), `terminal/` (`mod.rs`, `unix.rs`, `windows.rs`, `secret.rs`), `commands/` (`mod.rs`, `catalogue.rs`). Use the folder counts of §9 as the plan and re-count every folder with `ls` after the change (the package root goes from 4 to 5 entries; all counts must stay at most 7); `python -I scripts/ci/check_layout.py` counts only tracked files, so recheck after the orchestrator stages. At most 1000 lines per file, one primary item per file, no local `use`, no new `#[allow]`, no inline `#[cfg(test)]` modules.
2. **Connection:** TLS-TCP SCRAM and IPC SCRAM through the existing Rust client library (`crates/client/shamir-client`) and its handshake; the SCRAM pin is verified-only (profile carries the captured pin; mismatch or absence is a hard typed refusal); strict profile file parsing as the design specifies (the format and allowlisted fields it names, fail-closed directory and file permission checks, never any secret in a profile); the typed refusals of §3.2 for everything not supported in PR1 (plaintext incl. loopback, token transports, resume, no-pin).
3. **Secrets:** TTY no-echo entry with terminal restore on every exit path, `--secret-stdin`, `--secret-fd` (Unix only), `--secret-env`, and a refusal of any secret on argv; secrets are zeroized (the workspace already uses `zeroize`) and never reach output, error text, panics or history; there is no history file.
4. **Modes and output:** interactive (line reader built from the standard library only: the design rejects new registry crates) and one-command batch after `--`; JSON Lines v1 with the documented schema, `--output-version 1` as a local assertion only, human tables only for an interactive TTY, one stdout record per command, human text on stderr only, the exit-code table of §5, hex for binary values; peer-supplied strings never reach the terminal unescaped (the design's malicious-peer-reflection rule).
5. **Commands (PR1 set):** `ping` and the catalogue group named in §9 PR1 and §4.3: `db list`, `repo list`, `table list`, `index list`, `function list`, `table describe`, `table schema` (`repo describe` is PR2). Each maps to the existing server operation the design names; every batch command carries the routing database floor as the design states; do not invent operations: if a mapping in the design turns out not to exist in the code, STOP that command, report the exact evidence, and leave a typed "unsupported" refusal (exit code per the table).
6. **Tests (CI-only; the in-package integration target `tests/admin/` per §8):** register `tests/admin/shell/` in the existing `tests/admin/main.rs` with `mod.rs` (module declarations ONLY: the rust-guard structure gate allows nothing else in a `mod.rs`), `harness.rs` (shared fixture and helpers), `transport.rs`, `output.rs` (counts: `tests/admin/` 5→6, `tests/admin/shell/` 4). Cover for the PR1 head: scripted one-shot scenarios "connect → ping → catalogue → describe" on TLS-TCP+SCRAM and IPC+SCRAM against the real server binary or the in-process launcher the neighbouring admin tests use (read `crates/server/shamir-server/tests/admin/` first: boot fixtures, persistent store, handshakes not sleeps, every await bounded); typed-refusal probes for every §3.2 row that PR1 refuses; output-schema golden tests (field table, `--output-version 1`, one stdout record, human text on stderr only); a secret-leak byte-scan over stdout, stderr, argv, the profile and the absence of any history file with a unique canary secret per run; parser and malicious-peer-reflection scans; no-echo/terminal-restore behaviour that can be tested without a real TTY (the terminal layer behind a small trait with a scripted fake) plus the Windows/Unix split compiled on all three OSes. Three-OS runtime proof is a later `workflow_dispatch` on the same head (design §8): say in the report which commands the orchestrator must dispatch.

## Do not

Add a registry dependency (declare only workspace-internal edges, each justified in the report), implement anything of PR2–PR6 (WSS, tokens, REST, `status`, `data`, rights, activity, backups, versions, schedule, export), read the data directory, bypass the server's authorization, print server error strings or peer-supplied text raw, keep any history, accept a secret on argv, add `--accept-new-host`, or construct wire values by hand (client library and builders only). Do not widen an existing item beyond what the shell needs (list every widening before doing it).

## Test fixture checklist (every item failed in CI on earlier steps)

* Persistent stores for server fixtures; keep every `TempDir` alive for the whole test; close handles before reopening a directory; one runtime per test; handshakes not sleeps; every await bounded by a generous timeout (at least 120 s: a hang detector, not a latency assertion; the CI Windows runner is up to 10x slower than a laptop); a batch is at most 50 queries; distinct aliases.
* Per-session request rate limit is 500 requests/s (`POST_AUTH_RATE_LIMIT_PER_SEC`): never poll in a tight loop; the server config used by fixtures must set `argon2_concurrent_max` high enough (64) for the number of sessions the test opens.
* Debug-test stacks are small: never call the giant `execute_admin` from a test thread; `Box::pin` large awaits; deep real-server tests run on a roomy thread (`on_big_stack` pattern of the `shamir-db` schema-migration tests) or the fixtures' own runtime.
* Concurrent outcomes: assert on invariants and sets, never on a join order.
* Use `shamir-test-diag` (`FlakeGuard` marks, `with_watchdog`) for tests that can hang or flake (it is already a dev-dependency of the server crate).

## Rules that bind the change

* Machine memory: at most ONE cargo command at a time machine-wide (other executors may be running: if a cargo run is already in progress, wait for it through the notification, never poll), ALWAYS as `RUSTC_WRAPPER= wnice -p idle -c 50 -t 8 -m 50 -- cargo ... -j 1` (never `-j 2`), output redirected to a file OUTSIDE the repository, NEVER piped through `tail` or `head`; every worker you spawn must be told the same.
* Leave no scratch files in the tree and none outside it (edit only paths inside this worktree).
* Wrap-up: by 150 minutes bring the change to a compiling, formatted, clippy-clean state and stop; say in the final report what is missing.

## Policy (verbatim, binding)

Compilation, builds and tests run on GitHub CI, not on this machine. Banned locally: `cargo test`, `cargo nextest`,
`./scripts/test.sh`, `cargo build`, `cargo run`, `cargo bench`, `cargo doc`, npm/tsc builds, any build or test run.
Allowed locally only: `cargo check -p <crate> --all-targets`, `cargo clippy -p <crate> --all-targets -- -D warnings`,
`cargo fmt -p <crate>` (and `-- --check`), `python -I scripts/ci/check_layout.py`.

⛔ NEVER run `git reset` / `checkout` / `clean` / `stash` / `restore` / `rm`, or any git command that mutates the working
tree or index. Only edit files; the orchestrator commits. (For file moves use a plain filesystem move and say so in the report;
the orchestrator stages them so git detects the renames.)
