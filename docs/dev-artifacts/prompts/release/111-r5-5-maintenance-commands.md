## Why

An operator must be able to start, watch and cancel an online copy, see the format-stamp state and a database's migration status, and be told precisely how to run the offline tools (restore, doctor, format migration, logical export/import, verify) — without the shell ever touching the data directory or running anything destructive itself.

## What (this step only = PR5)

1. **Backups (SCRAM only).** `backup start --to DIR` (`StartBackup`: the path is passed unmodified and is not resolved, created or checked locally; I/O-heavy: confirmation in a TTY or `--yes` in batch before anything is sent), `backup status` (`BackupStatus`: prints the typed status; never reaches the follower write gate), `backup cancel` (`CancelBackup`: no id; wording always "current run"; confirmation or `--yes`). On a follower the server's `online_backup_follower_read_only` surfaces as a typed shell error. Output through the existing typed result records; paths in output follow the shell's sanitizer; nothing raw from the server. `backup schedule show` is NOT here (PR6): until it lands the command is registered as unsupported (exit 6) with the documented message, not a placeholder success.
2. **Versions.** `version stamp` (the P1 `status` DTO's observed format-stamp state: epoch and the stamp outcome as the server reports it; no disk read by the shell; `version show` of PR3 stays), `version migrate` (explained only: the server's `format-migrate` with `--plan` for a plan and `--yes --from-backup …` to apply as a MANUAL operation; the shell never applies), `schema-migration status --database-id ID` (one line; `--database-id` required; the existing `ApplicationSchema` Status sub-operation built through the builder; `Read(DB)`; refused on a follower with the stable follower code; typed output).
3. **Explained-only commands.** `backup verify SNAPSHOT`, `backup restore`, `backup snapshot`, `export logical`, `import logical`, `diag integrity`: each prints (a) the exact manual command line with the CURRENT flags of the server subcommand (read the server `MAIN` argument parsing and the subcommand modules and print what they accept TODAY; never document or suggest `--force`), (b) the OS rights the invoking user needs (ownership of the data directory, a stopped server where required), (c) the destructive effects of the manual command (restore swaps the live data directory, doctor `--apply` repairs in place, format migration rewrites stamps), (d) for logical export/import the documented implementation limits. The shell executes none of them and opens nothing. Their text lives in ONE place (a data table or constants file in `shell/commands/`) so the guide can quote it and a test can pin it against the server's accepted flags (see item 6).
4. **Diagnostics.** `diag wal` and `diag durability`: the WAL watermark/pending/commit telemetry and effective-vs-stored durability from the P1 status DTO and the existing `DescribeRepo` operation (superuser + `Read(repo)`); typed output with the documented caveats. No raw WAL access.
5. **`shamir-server backup-verify SNAPSHOT`.** A new top-level subcommand dispatched EARLY in `MAIN` (the pre-config slot beside `format-migrate`; it does NOT require `--config`, boots nothing, opens no data directory, reuses no bootstrap stdin path) calling the real library verify of the offline backup module (`offline.rs` region named in the design: re-open it). It hashes content (never call it cheap), runs with the OS rights of the invoking user, is read-only, and prints a typed result and an exit code per §5. The only edits are inline in `MAIN` parsing plus the existing library call: no new files beyond the plan's list; recount the folders.
6. **Tests (CI-only; `tests/admin/shell/maintenance.rs` is ADDED here: the folder goes from 6 to 7 entries; recount with `ls`; `mod.rs` declarations only).** On the harness: `backup start/status/cancel` against the real server (a started online copy appears in `status`, completes or is cancelled; without `--yes` in batch nothing is sent and the exit code is per §5; a follower fixture gives the typed follower refusal; a relative `--to` is refused BY THE SERVER, not by the shell: assert the shell sent it unmodified); `version stamp` golden against a fixture data directory stamped at boot; `schema-migration status` against a database with an applied migration and the follower refusal; every explained command prints the documented sections and executes nothing (assert no server request, no file created or opened: run the shell with a data directory that must stay byte-identical, hash before and after); a PIN test that every flag a printed manual command line mentions is accepted by the server's argument parser TODAY (so the explanations cannot drift from the real subcommands: use the server's parser entry, not a subprocess build); `backup-verify`: a valid snapshot verifies, a corrupted one fails with the right exit code and typed corruption class, the subcommand works with no `--config`, no data directory and no network, and the pre-existing dispatch paths still require `--config` (unchanged behaviour test); token sessions refused with zero requests for every SCRAM-only command; the secret-leak and malicious-peer scans extended.
