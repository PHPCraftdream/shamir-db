# Brief: R2d-FIX-B — an online backup of a data directory that `restore` produced must succeed: exclude the two reserved ROOT control files from the whole-data-dir passes of the online copy

Path prefixes used below: `sync/` = `crates/server/shamir-sync/src/sync/durability/backup/`. Re-open every path and line before relying on it (lines drift).

## Why (verified by a read-only trace of the landed code on 2026-11-21; not yet reproduced: this task's first test proves it in CI)

`restore` (`sync/restore.rs`, copier `copy_dir_recursive` in `sync/offline.rs`) copies EVERYTHING from the snapshot into the new live data directory except the root `cache` directory, including the snapshot's control files `manifest.json` and `backup.meta.json`. A later ONLINE backup of that data directory enumerates files with `list_files` (`sync/online/copy_engine.rs`, around the "File names skipped in every listing pass" comment), which skips only the file names `lock` and `.shamir.lock`. The final residual pass of the online protocol (`sync/online/protocol.rs`, `sync/online/copy_engine.rs` residual copy, re-hash and return of the digests) therefore copies and hashes the two inherited root files as ordinary payload and returns the OLD digests under the root-relative names. The protocol puts those entries into the manifest `files` list unchanged; `manifest::build_v2` keeps them; the two writers then replace `manifest.json` and `backup.meta.json` in the destination; `self_verify` hashes EVERY listed entry with no name exception and fails with `Failed(Verifying, Verify(hash mismatch))` whenever the new bytes differ from the inherited bytes (the manifest always differs; `backup.meta.json` differs when the inherited one is a retention-tagged sidecar of the scheduled backups). The offline verifier does not rescue this: v2 verification exempts the two names only in its later "unmanifested file" sweep, not from hashing a listed entry. Net effect: after the disaster-recovery workflow the guide recommends (restore a scheduled copy, boot it), every online backup of the restored installation, manual or scheduled, ends in a verification failure and no new copy exists. Existing tests miss it: `full_run_produces_a_verifiable_snapshot` starts from ordinary payload, `restored_online_copy_matches_source_at_seal_on_fresh_target` never backs the restored copy up again.

## What (this step only)

1. Put the two EXACT ROOT paths `manifest.json` and `backup.meta.json` into the exclusions of BOTH whole-data-dir passes of the online copy (the initial pass and the residual pass; use the existing exclusion mechanism that already skips `cache` and the captured store and WAL directories, extending it with a root-relative file-name exclusion; read how the two passes build their skip lists and keep them consistent). Only the ROOT files are excluded: a nested file with the same name stays payload. Do not weaken `self_verify` or the verifiers, do not change the manifest format, do not change `restore` (it keeps copying everything), do not change what the protocol writes. This also fixes data directories that were restored before the fix, because the exclusion is applied at backup time.
2. **Tests (CI-only; add to the existing test files, registered in their `tests/mod.rs`).** `online_backup_after_restore_omits_inherited_control_files` in `sync/online/tests/protocol_tests.rs`: reuse `TestPort` and `run`; build a snapshot of the test payload with a NON-default root `backup.meta.json` (a retention-tagged sidecar, see `crates/server/shamir-server/src/boot/config/diagnostics/backup_online/schedule/retention/ownership.rs` for its form), restore it into a fresh directory through the real restore function, then run the online protocol against the restored directory: require success, require that neither root control name appears in the new manifest `files`, and require that the standalone verifier accepts the new snapshot. A second test: a NESTED file named `manifest.json` below a payload directory is still copied and listed. If `launch_with_backup_test` (in `crates/server/shamir-server/src/engine/server/server_launcher/tests/backup_schedule_tests.rs`) makes a full "scheduled backup, restore, scheduled backup" case cheap, add it; otherwise say so in the report. Before the fix the first test fails at `Verifying`.
3. **Guide.** Only if `docs/guide-docs/guide/07-operations.md` mentions a restore-then-backup limitation or workaround: remove it and describe the true behaviour in one sentence (Russian). Otherwise no guide change.
