## Why

The release gate property is: a copy taken while the server keeps accepting writes restores on a clean machine to a consistent state, loses no acknowledged write, and a failed or cancelled copy never damages the live source. Until a test proves it under real concurrent write load, the claim is unverified; and the operator guide still says there is no online mode.

## What (this step only)

1. **Gate test (design §6.1; requirements R1, R2, R4-via-restore).** Boot the real server with a persistent store (the e2e harness style). N writer clients (4 is enough) each run a SEQUENTIAL loop of inserts into one indexed table: each write carries `(writer id, sequence number, value derived from both)` and is recorded in an in-memory oracle ONLY after its acknowledgement; a writer never issues write k+1 before the ack of k. Mid-stream, issue `StartBackup` through the client with the typed builder (find the Rust builder/client entry for the three backup operations; no raw wire values), keep writing until `BackupStatus` reports `Done` (bounded wait, no fixed sleeps), stop the writers, stop the server gracefully, `restore` the snapshot into a FRESH data directory (clean-machine path: target absent), run `verify` on the snapshot, boot a server on the restored directory and read back through the client. Assertions: (a) EVERY oracle entry acknowledged before the `StartBackup` request was sent is present with its exact value (R2, a sound lower bound: the capture barrier is after the request); (b) per writer the restored sequence numbers form a contiguous PREFIX `1..m` of that writer's acknowledged-or-attempted sequence with `m` ≥ the count acknowledged before `StartBackup` (the cut is one consistent instant; the order of commits is total and the drain is version-ordered); (c) no torn or partial record, every row's value matches its derivation, and the indexed lookup by the indexed field returns exactly the rows a full scan returns (derived structures agree); (d) the manifest of the snapshot is `kind = online` with a per-repository `wal_position` and the restore report lists no unexplained exclusion. Do not assert on writes acknowledged after `Done` or between request and capture. A variant exercises catalogue churn during the copy: a second table is created and written while the backup runs (design Q9: a repository created after capture is excluded and reported; nothing created mid-copy may make the restore refuse a consistent snapshot).
2. **Writer-block bound (§6.2; R3).** The reserved metric `shamir_backup_writer_block_seconds` is documented as NOT exported yet; do not export it in this step. Assert R3 black-box instead: during the copy, each writer records the gap between consecutive acknowledgements and the test asserts the maximum gap stays below a deliberately generous CI bound (state the bound and its derivation from design R3's 2 s p99 on CI-sized data plus scheduling slack; e.g. 10 s) while the copy actually overlapped the writes (assert that at least a stated number of writes were acknowledged between `Captured` and `Done` as seen by `BackupStatus`, so the test cannot pass vacuously). A compaction-pressure variant (larger batches forcing flushes during the barrier) is included if it stays within the budget below.
3. **Failure-injection suite (§6.3; R4).** The protocol runs over a port with capture/seal hooks in `shamir-sync`; add the missing cases there (list the existing cases first): failure at each stage A–G (pin acquisition/teardown, capture flush error → no destination directory, mid-file copy error and a deleted source file, a hash mismatch on the re-pass → output removed and source untouched, seal error → `Failed(Sealing)` with the WAL consistent, manifest write failure → no success report, cancel at EVERY stage boundary → cleanup). Each case asserts R4: before/after directory snapshot of the source is identical, the truncation pin/permit is released (observable through the port or the registry), the partial output directory is gone, and `BackupStatus` carries the failed stage and error. Where a server-level case adds value (a failed run leaves the engine open and a second `StartBackup` succeeds afterwards), add it next to the existing registry tests. Use the existing seam style; if a stage has no injectable seam, add the narrowest test-only seam and list it as a widening.
4. **Restore/verify acceptance gaps (§6.5).** Check which of these already have a test and add only the missing ones: v2 snapshot restores on a clean machine (covered by item 1 end to end); `verify` refuses a checksum mismatch, a WAL sequence gap, a manifest/stamp epoch mismatch and an unmanifested file; a v1 offline snapshot still restores and verifies unchanged; offline `backup --to` against a live source is refused with the typed error pointing at the online operation. The step-3b-2 report named two gaps: no dedicated fixture for a captured repository dropped after capture (tolerated orphan, its WAL still replays strictly) and none for store contents above `V*` (tolerated). Add them if a DETERMINISTIC fixture is possible with existing seams; otherwise say so in the report (the gate test covers the above-`V*` case statistically only).
5. **Guide (Russian, in `docs/guide-docs/guide/07-operations.md`, section `## 8. Backup`).** The section currently states that no online mode exists, that `backup` must never run against a live server and that online backup is "planned P2"; these statements are now FALSE and must be replaced, not appended to. Write: when to use the online copy (admin operation, server keeps running) versus the offline `backup --to` (server stopped; against a live source it is now refused with a pointed error, there is no force flag); the procedure through the typed client/builder (builder-only examples, no raw JSON; superuser required; follower refuses start/cancel; one copy at a time; status and cancel); what the manifest's consistency point means (per-repository `wal_position`, `kind`, `format_epoch`, `binary_version`, which writes a restore is guaranteed to contain, what is NOT promised: writes acknowledged after capture); `verify` (file-only, what it checks and what it does not: it does not validate WAL contents, restore does); restore of an online copy (offline action on a stopped target, replay, consistency check, exclusion of a repository created after capture, failure leaves `data_dir` untouched); the Windows sharing-violation note and the share-tolerant copy; metrics: list exactly the series that ARE exported today and say the reserved series are not yet exported (verify against the code, do not guess); HOW TO ENCRYPT COPIES WITH YOUR OWN MEANS (the snapshot is an opaque directory plus `manifest.json`: encrypt/decrypt the whole directory outside the server, never edit files inside, decrypt before `verify`/`restore`; built-in encryption is a separate later feature, R2c); boundary notes: no point-in-time recovery, retention/rotation and schedule are the later R2d feature (append-only destination today). If the module doc of `crates/server/shamir-server/src/backup.rs` still says online backup is a future P2 enhancement, correct that doc comment only.

## Test fixture checklist (every item failed in CI on earlier steps)

* Persistent stores; keep every `TempDir` alive for the whole test; close every handle before reopening a directory; one runtime per test; handshakes not sleeps; every await bounded; a batch is at most 50 queries; distinct aliases.
* Windows holds Fjall locks (`FjallError: Locked`) until the background tasks of a dropped engine finish: after the server is stopped, wait for the server task/handle to complete (no sleeps) before `restore` or reopening the directory; if a bounded retry on `Locked` is needed follow `export_waiting_for_locks` in `crates/server/shamir-server/tests/admin/logical_dump/fixture.rs`.
* Debug-test stacks are small: do not call the giant `execute_admin` from a test thread; keep async runners small and `Box::pin` large awaits; deep real-server tests run on a roomy thread (`on_big_stack` pattern of the `shamir-db` schema-migration tests) or use the e2e harness's own runtime.
* Budgets (§6.4): data directory ≤ 200 MB, retained WAL ≤ 32 MB, the gate test ≤ 3 minutes per OS and below the 180 s nextest per-test kill: if the single test cannot fit, split boot / backup / restore phases into separate tests sharing a fixture; the nextest configuration stays untouched.
* Concurrent outcomes: assert on sets and invariants (prefix property, lower bound), never on a join order or exact counts of racing writes.
* A new test that can hang or flake carries failure-only diagnostics: use `shamir-test-diag` (`FlakeGuard` timeline marks per phase, `with_watchdog`) — it is already a dependency of `shamir-e2e` — and register the test in `docs/dev-artifacts/design/flake-failure-logs.md` only if the repository rule for new flake-prone tests requires it (read the file's header rule first).
