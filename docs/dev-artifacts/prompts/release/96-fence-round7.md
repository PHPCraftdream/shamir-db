## Findings

1. **P1 — CONFIRMED: an in-doubt table reserves its database but does not stop REPLACE or RENAME.** `V/binding_scan.rs:111–120` puts the database in `dbs` and `in_doubt_dbs`. REPLACE consumes only `dbs()`, and a vacant fence slot is successfully reserved; execution then saves the replacement and swaps the artifact (`V/validator_management.rs:459–479,549–561,577–607`; `M/fence.rs:133–144`). Wire RENAME has the same outcome; migration RENAME also proceeds if its proof covers the database (`V/validator_rename.rs:46–69,88–110`). **Scenario:** Ordinary UNBIND on B fails after the forward write lands and all three compensations fail. B still validates with the old binding. The ordinary reservation drops; B has no migration fence. An authorized REPLACE served by A now reserves B successfully and changes the artifact B invokes. This violates F2 even if the backing envelope happens to look coherent. Direct embedder REPLACE/RENAME skip the scan entirely. DROP is different: it uses `is_empty()`, so an in-doubt user table alone blocks it even when its database is free (`V/validator_drop.rs:56–83`).

2. **P1 — CONFIRMED: restart clears the flag, not necessarily the inconsistency.** Two outcomes remain possible when the forward envelope survives and compensation does not:
   - **Declarative schema:** First `SET TABLE SCHEMA` writes a fresh binding ID, then flush fails and compensation never replaces that envelope. Activation removes the fresh artifact and the handler restores the pre-schema catalogue row (`DB/shamir_db/db/schema_management.rs:642–645,683–727`; `DB/execute/admin_ddl/admin_schema.rs:489–496,563–576`). Reopen loads the binding with a clear flag and skips boot compilation for a table with no catalogue schema. A successful schema retry mints a different ID and appends it; it does not remove the orphan. Validated writes still fail resolving the old ID (`ET/table_manager/admission/domain/barrier/write_domain_barrier.rs:206–212,239–243`; `DB/shamir_db/db/schema_management.rs:756–762`; `TV:92–100,484–493`).
   - **Migration UNBIND:** If the empty envelope survives, reopen makes live and stored bindings agree on *absence*. The registry and catalogue still carry the old reverse reference: the facade returned before removing it, and boot restores it from the catalogue (`V/validator_management.rs:827–836`; `DB/shamir_db/core.rs:603–622`). Resume rejects that mismatch before it can prove completion or replay (`M/function_family/binding.rs:67–85,169–222`). Repeated restarts do not change that evidence. If the **old** envelope survives instead, the exact original can be replayed after restart. The new flag is not itself permanently stuck; the recovered records can require operator repair.

3. **P2 — CONFIRMED: a successful table rename can discard the in-doubt state without a restart.** The facade takes replication control but does not check binding doubt before renaming a non-schema table (`DB/shamir_db/db/table_management.rs:266–276,412–449`). The repo copies and flushes the info store, removes the old manager registration, and installs a fresh table mapping (`E/repo/instance/repo_instance/catalog.rs:630–676,687–710`; `E/repo/instance/repo_instance/table_store/copy.rs:7–22`; `ET/support/storage/catalog.rs:79–95`). **Scenario:** A failed UNBIND leaves the old binding live and a forward empty backing envelope. Storage recovers; rename on the free database copies that empty envelope. The scan no longer sees the old flag; the new manager opens unbound. A subsequent DROP can succeed, and the renamed table no longer validates with the old binding. This is the successful **table** rename path, not a claim about non-atomic database or validator rename.

4. **P2 — CONFIRMED: an already-in-doubt schema retry can change the validator artifact before refusing.** `REMOVE SCHEMA RULE` saves the catalogue and calls activation without the schema-activation barrier used by SET/ADD (`DB/execute/admin_ddl/admin_schema.rs:789–808,875–920`). Activation replaces an existing artifact *before* `add_validator_binding_admitted` checks the flag, and restores it only on error (`DB/shamir_db/db/schema_management.rs:658–696,722–727`; `TV:88–92`). **Scenario:** On a free table whose old schema requires a field, a failed binding operation leaves the manager in doubt. REMOVE of that rule reaches the artifact swap; a concurrent INSERT can validate against the temporarily weakened artifact and stage a row before the refusal restores the old rules (`TV:484–493`; `ET/write/insert.rs:303–341`). The new flag creates a refusal on this path even when storage has recovered. Separately, if the catalogue rollback fails, schema migration resume can accept the desired **catalogue** rules without checking activation; that is an existing recovery limitation, not a new postcondition check (`M/apply/apply_operations.rs:817–852`; `M/apply/ddl_postconditions.rs:178–212`).

| Future dropped at an await | At repo admission or `bindings_lock`, this call has not mutated anything. At **forward `set`, forward flush, any compensation `set`, or any compensation flush**, the live vector remains old and the flag stays raised; backing may show old, forward, or compensating data depending on what landed. A dropped Fjall `spawn_blocking` await or MemBuffer drain can finish afterward. The repo permit precedes `bindings_lock`; clones share the lock, snapshot and flag. Facade bind/unbind and wire schema activation hold replication control across the table operation, so an admitted holder scan cannot interleave in the middle of their compensation. The atomic flag is **not** a substitute for that exclusion when a trusted caller mutates a raw `TableManager` concurrently. The normal validated INSERT path uses the live vector and registry, not the flag; a failed or pending ordinary UNBIND does not remove the validator from that path. This does not override a separate database migration fence or storage failure (`V/validator_management.rs:739–786,820–839`; `DB/execute/admin_ddl/admin_schema.rs:374–378,591–595,793–797`; `ET/table_manager.rs:550–553`; `TV:305–323`; `M/fence.rs:433–480`).

The facade propagates the table error before changing reverse refs and does not retry. Wire bind/unbind retain the existing uncoded query-error mapping; schema DDL rolls back best-effort and returns `internal_error`. Migration BIND remains deferred; UNBIND errors after intent are recorded as migration in doubt, without completion. Same-process resume can flush and compare evidence, but replay still refuses while the table flag is set. Reopen makes a fresh manager with a clear flag and reloads the surviving envelope; it does not reconcile reverse refs or clear the separate durable migration fence (`DB/execute/admin_ddl/admin_validator.rs:295–327,350–381`; `M/function_family/admission.rs:85–102`; `M/apply/apply_operations.rs:263–276,364–393`; `M/function_family/binding.rs:148–222`; `M/fence.rs:342–356,405–417`).

Count every folder you add to with `ls` (many are at 7 entries: `python -I scripts/ci/check_layout.py` counts only tracked files, recheck after staging); at most 1000 lines per file, one primary item per file, `mod.rs` re-exports only (the rust-guard structure gate allows nothing else in a `mod.rs`: shared helpers go in a named file), tests in `tests/` folders, no inline `#[cfg(test)]` modules, no local `use`, no new `#[allow]`. Persistent stores, every `TempDir` alive for the whole test, close handles and wait for the server task to finish before reopening a directory (Windows holds Fjall locks until the dropped engine's background handles finish: reopen with a bounded retry on `Locked` only, like `init_waiting_for_locks` in the function-family crash tests), handshakes not sleeps, every await bounded by a generous timeout (at least 120 s: a hang detector, the Windows runner is up to 10x slower), a batch is at most 50 queries, per-session request rate limit 500 req/s (never poll in a tight loop: pace status polls at 20 ms or more), set `argon2_concurrent_max` and `auth_init_rate_per_second` to 64 in fixtures that open several sessions, debug-test stacks are small (call concrete handlers through `Box::pin`, run deep tests on a roomy thread, `on_big_stack`), assert on invariants and sets, `shamir-test-diag` marks for flake-prone tests.

## Rules that bind the change
