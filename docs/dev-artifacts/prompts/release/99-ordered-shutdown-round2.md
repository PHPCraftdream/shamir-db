## Findings

- **P1 — Audit timeout is not reliable.** `audit/audit_appender.rs:440–459` and `server/boot/scheduler.rs:240–256` leave both blocking paths in async tasks. In the new test’s current-thread runtime, the shutdown wake can send the flusher into the held mutex on the only runtime thread. It then cannot poll the 10-second timer or advance to repository teardown.
- **P1 — Final close violates the existing persistence ordering.** `audit/audit_appender/shutdown.rs:75–82` calls two helpers that require the caller to own the gate (`audit/audit_appender.rs:634–643`; `audit/audit_appender/checkpoint.rs:105–115`). The server does not await the scheduler join until after final flush (`server/engine/server/audit_teardown.rs:75–84,139–142`). A checkpoint can therefore interleave with final log sync and anchor persistence, undermining the durability ordering this task was meant to preserve.
- **P1 — Embedding ownership and fairness remain unimplemented.** The outer timeout can still drop the scheduled join and data-directory guard while native work continues; there are no retention-only cancellation checks between reads. The global-only queue still lets one principal consume all 256 slots. The scheduled-worker, both rollback-bind, and fairness regression tests are absent.
- **P1 — The layout pass excludes a new violation.** `ls` shows eight entries under `server/engine/server/` with `audit_teardown.rs`. `scripts/ci/check_layout.py:11–22` permits seven and ignores untracked files. The reported exit 0 does not cover the tree as it would be staged.
- **P2 — Reporting is neither typed nor fully truthful.** `crates/engine/shamir-db/src/shamir_db/shamir_db/catalog/shutdown_report.rs:4–7,29–35` still stores strings only. Final-anchor errors are misclassified, and a flusher-join error already obtained can be lost if the subsequent final flush times out, because both results are held until the same future returns (`server/engine/server/audit_teardown.rs:75–84,103–134`).
- **P2 — Queued-job discard races with registration and adds a lock to the reply path.** `repo_audit.rs:187–209,343–365` spawns before registering the abort handle, so a submission that reserved before closure can register after the discard sweep. The same tracking mutex is acquired before the cancellation reply returns (`activity/cancel.rs:61–74`), contrary to the new field comment.
- **P2 — The timeout test can hang on its own failure path.** `shutdown_audit_teardown_tests.rs:81–145,206–222` uses unbounded condition-variable waits, asserts before releasing the gate, and discards the inner checkpoint result. Its watchdog only emits diagnostics (`crates/devtools/shamir-test-diag/src/guard.rs:86–91`); it cannot release the holder. The test also duplicates launcher setup instead of reusing the requested refusal-drain fixture. The existing fixture’s assertions are unchanged, but its probe now fires on any pending audit-stage poll, not specifically a pending refusal drain (`audit_teardown.rs:88–99`).
- **P3 — The guide overstates the guarantee.** `docs/guide-docs/guide/07-operations.md:1119–1123` describes the blocking paths as off the async poll path and says an unclean report exits the process with 70. The foreground and service paths still drop their runtimes normally (`server/main.rs:344–348`; `server/boot/policy/windows_service.rs:179–215`), so the exit code does not establish a bounded process exit. The guide also names a `server.json` metadata store; the launcher opens `data_dir/server_meta` (`server/engine/server/server_launcher/support/durable_stores.rs:115`).
