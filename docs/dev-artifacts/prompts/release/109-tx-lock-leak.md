# Brief: INTERACTIVE-TX-LOCK-LEAK — an interactive transaction that ends outside the commit pipeline (owner rollback, idle or deadline reaper, session close, a request that loses a race with them) releases the pessimistic record locks it holds

Path prefixes used below: `server/` = `crates/server/shamir-server/src/`; `sync/` = `crates/server/shamir-sync/src/sync/durability/tx/`; `engine/` = `crates/engine/shamir-engine/src/`; `tx/` = `crates/storage/shamir-tx/src/`. Re-open every path and line before relying on it (this branch starts from `origin/master` after R4b-3 (#645) has LANDED; R4b-4 shape statistics is being written in parallel by another executor in other files: do not touch `engine/repo/instance/support/metrics/`, the query runner, the wire types or the observability export). The defect is PRE-EXISTING and was found by the independent review of R4b-3, round 2: R4b-3 added `shamir_db::engine::tx::release_interactive_tx_locks` (`engine/tx/commit/pipeline/phase/commit/legacy_and_lockfree.rs`, a thin public entry over `release_pessimistic_locks`) and calls it from the operator cancel only (`server/engine/db_handler/repo_admin/activity/cancel.rs`, `release_tx_locks`). The review's statement, not yet reproduced: `TxContext` has NO `Drop` that frees Level-3 pessimistic record locks (they live in the per-table `MvccStore` and are freed only by explicit calls), so every path that ends an interactive transaction without going through the commit pipeline leaves its record locks held forever and any other transaction that needs one of those records waits on it forever (the record-lock wait has no timeout). The tests below prove it in CI before the fix: each new test must FAIL on the parent commit for exactly that reason.

## Why

An interactive transaction (`TxBegin` ... `TxExecute` ... `TxCommit` / `TxRollback`) takes pessimistic record locks when it updates or deletes. Today only commit and the operator cancel release them. Ordinary events leak them: a client that calls `TxRollback`, a client that disappears (the idle reaper, the absolute deadline), a connection that closes (`cleanup_session`). After a leak, a second transaction touching the same record blocks without a bound: an availability defect reachable by any authenticated client with write rights, no operator needed. This is P1 before release.

## Ends of an interactive transaction to cover (find each one; the list is a starting point, prove completeness by reading every caller of the registry's removal API and every place an `InteractiveTx` / its `TxContext` is dropped)

1. **Owner rollback:** `tx_rollback` in `server/engine/db_handler/repo_admin/tx_handlers.rs` (identity-checked `remove_owned`, then a plain drop).
2. **Reaper:** `spawn_reaper_task` and `TxRegistry::reap_expired` / `remove_expired` in `sync/tx_registry.rs` (synchronous, no repository access); wired in `server/engine/server/server_launcher/launch.rs`.
3. **Session close:** `cleanup_session` in `server/engine/db_handler/repo_admin/native_handler.rs` (a SYNCHRONOUS trait method: `remove_for_session` then a drop) and every other caller of `remove_for_session` / `remove`.
4. **A request in flight at the moment of 2 or 3:** the registry entry is removed while the owner's `TxExecute` still holds the `Arc<InteractiveTx>` and the context lock; when that request returns, the last `Arc` drops and the context is dropped with its locks. Decide whether this path is covered by the mechanism you choose and prove it.
5. **Batch error arm, begin/register rejection arms, commit failure paths in `tx_handlers.rs`:** read them (the comment at the abort arm says "RAII rollback"): record for each whether it already releases (cite `path:line`) or needs the fix. Do not change what already works.

## Mechanism (decide, justify with `path:line`, state the rejected alternative)

Recommended: ONE uniform release at the point where the last reference to the transaction's context goes away, so no present or future end path can forget it. For example `impl Drop for InteractiveTx` (or a small owned guard field next to the context) that takes the `TxContext` out of the mutex with `get_mut()` (no lock needed in `Drop`), and when it holds record locks (non-empty `locked_keys`) spawns the async `release_interactive_tx_locks(&ctx, &repo)` on the current Tokio runtime with an OWNED `Arc` of what it needs (repository core, the context), then drops the context after the release. `Drop` cannot await: when no runtime is current, fall back to the cheapest correct behavior (document it; never panic in `Drop`). If `shamir-sync` cannot see the repository core cleanly, pass a small trait object (a release callback) into the registry or the transaction when it is registered; do NOT add a dependency edge that does not exist yet, and do not move code between crates. The alternative (explicit release calls at each of the ends 1 to 3, an async reaper hook, a spawned task in `cleanup_session`) is acceptable only if it provably covers end 4 and every other end that the read finds; say why the drop-based form was rejected if you reject it.

Hard requirements of either form:

* **Idempotent and owner-checked.** After R4b-3's cancel (release then drop) a second release for the same transaction must be a harmless no-op, and a release for a transaction id must never free a lock that belongs to another transaction (read `MvccStore::release_locks` and how `locked_keys` is kept: prove both by reading and by a test).
* **No double work with commit.** A transaction that went through the commit pipeline (which releases its own locks and takes the context out) must not release again or must do it harmlessly; the commit path is NOT changed.
* **No blocking in `Drop` or in the reaper loop.** The release is async and short; a stuck release must not stall the reaper's next tick or shutdown (bounded, spawned; track what you spawn so that shutdown does not leak a task: say how).
* **No lock held across the release await** (a registry or `scc` entry guard, the context mutex): clone what you need out first.
* The release resolves the repository by the transaction's stored names (`db()`, `repo()`) the same way `release_tx_locks` does; a repository that is gone means there is nothing to release (not an error).
