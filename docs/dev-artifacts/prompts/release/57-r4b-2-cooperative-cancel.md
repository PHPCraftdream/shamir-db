## Why

Release gate: "an operator can find and cancel a stuck query". Step 1 lets an operator list what runs; this step lets a second session cancel one running request safely: the request stops at its next checkpoint or wakes from its wait, releases everything by unwinding, and answers with the typed code `cancelled`; a cancel that races the commit either wins before any WAL write or is refused with `already_committing` (exactly one CAS wins).

## What (this step only = §7 row 2)

1. **The D8 state word and wake handle.** `RequestEntry` already carries `state: AtomicU8` (`Running`/`Done` in step 1). Extend to `Running → Committing → Done` and `Running → Cancelled` (terminal), with `waiting: AtomicU8` (`waiting_lock`, `waiting_visibility`, `waiting_budget`, none) written before a park and cleared after (D17), all lock-free; an `Arc<CancelHandle>` (the state word + `tokio::sync::Notify`) passed down as a parameter alongside `ExecScope` (design 3.2: instance → query → tx, downward only; add no dependency: shamir-tx already has tokio `sync`). If the state machine can be extracted into a small module of a crate with the loom convention (design §6 and open question 8), do it and model it under loom; otherwise write the named stress test with `shamir-test-diag` (`FlakeGuard`, `with_watchdog`).
2. **The commit CAS (the linearization point, design 3.4 item 4):** the executor CASes `Running → Committing` ONCE, in the commit driver immediately after the tail-barrier enter and BEFORE the path branch, so both commit paths are covered (re-open `tx/commit/pipeline/phase/commit/entry.rs`; the interactive twin site in `interactive_tx.rs`); a cancel that loses reports `already_committing`, an executor that loses aborts at its next checkpoint. List the exact edit sites with their layer (this is an engine edit: `shamir-engine`, query/batch + commit driver) and any rust-guard consequence.
3. **Checkpoints and wake arms** exactly as design 3.2 and the §3.7 table: every checkpoint is an EXISTING deadline checkpoint plus the flag test (scope entry, nested batches, per-iteration read arms, the too-many-iterations pre-flight site, the final checkpoint before commit); the wait sites gain a Notify arm: the record-lock park `lock_key` in `shamir-tx` (`mvcc_locks.rs`; the ONLY tx-layer edit, list it with the layer consequence), the as-of visibility wait (`observe_gate_with_budget`), the byte-budget acquire (server layer only). A running WASM call is NOT interrupted (bound = fuel): say so in the guide. Waiting states are recorded by the wait sites and surfaced by `ListActivity`.
4. **`BatchError::Cancelled` and the wire code `cancelled`** in the error-code vocabulary and `error_code()`; the client sees the ordinary error path.
5. **`CancelRequest(RequestExecId)` end to end:** typed `BatchOp`/DTO in `shamir-query-types` (`CancelOutcome { cancelled | already_finished | already_committing | not_cancellable }`), builder in `shamir-query-builder`, `Client::cancel_request` in `shamir-client` (the Rust client only; the TypeScript client is a separate task), server handler. Permission default (design 5.2 and defaults 2, 5): own-request cancel needs only authentication; cross-user cancel needs `ActivityView:Manage` through the normal authorization path (add the op to the coarse-admin-gate exemption like `ListActivity`); `not_cancellable` for replication-apply work on a follower (3.6); an unknown or already finished id answers `already_finished`; the refusals `already_committing` and `not_cancellable` append to the audit chain with the same entry shape as other admin ops (default 7). No raw JSON anywhere (builders only).
6. **Tests (CI-only)** — the named tests of design §6 for this step: `state_word_commit_vs_cancel`, `cancel_wakes_parked_lock_wait`, `cancel_releases_all_under_concurrency`, `durable_phase_commit_refusal`, `cancelled_code_on_error_path`, the cancel half of `permission_denial_activity`, `follower_apply_not_cancellable`; plus wire/serde and builder tests and the HMAC/policy test the activity op got. Real-server tests use TWO sessions (a cancel cannot arrive on the connection it targets). Use persistent stores, bounded awaits (≥120 s), handshakes not sleeps, `argon2_concurrent_max` and `auth_init_rate_per_second` 64 in multi-session fixtures, status/poll pacing ≥20 ms.
7. **Guide** (Russian, `docs/guide-docs/guide/07-operations.md`, a new short subsection next to the activity text if present, otherwise after the migrations section; do not touch §8 Backup): how to find and cancel a stuck request (list → cancel from a second session), what a cancel can and cannot interrupt (checkpoints, parked waits, not a running WASM call, not a committing request), the outcomes table, permissions, what the cancelled client sees. Typed-client examples only. Every statement must match the code.
8. **CI selection:** check `scripts/ci/matrix/` selects the changed crates' tests on three OS; widen only where a target is not selected, and list it.

## Do not

Implement tx/cursor cancellation (`CancelTx`: R4b step 3), shape statistics (step 4), the TypeScript client, the `shamir_cancellations_total` counter (step 3), change the commit protocol's semantics for uncancelled requests, take a lock or the gate commit mutex on any cancel path (design 3.4 item 3), add a dependency, weaken an assertion, use sleeps for synchronization, construct wire values by hand, or edit files outside the layers listed in items 2, 3, 5 (stop and list any other engine-layer need).

## Layout and fixture lessons

Count every folder you add to with `ls` (many are at 7 entries: `python -I scripts/ci/check_layout.py` counts only tracked files, recheck after staging); at most 1000 lines per file, one primary item per file, `mod.rs` re-exports only (the rust-guard structure gate allows nothing else in a `mod.rs`: shared helpers go in a named file), tests in `tests/` folders, no inline `#[cfg(test)]` modules, no local `use`, no new `#[allow]`. Persistent stores, every `TempDir` alive for the whole test, close handles and wait for the server task to finish before reopening a directory (Windows holds Fjall locks until the dropped engine's background handles finish: reopen with a bounded retry on `Locked` only, like `init_waiting_for_locks` in the function-family crash tests), handshakes not sleeps, every await bounded by a generous timeout (at least 120 s: a hang detector, the Windows runner is up to 10x slower), a batch is at most 50 queries, per-session request rate limit 500 req/s (never poll in a tight loop: pace status polls at 20 ms or more), set `argon2_concurrent_max` and `auth_init_rate_per_second` to 64 in fixtures that open several sessions, debug-test stacks are small (call concrete handlers through `Box::pin`, run deep tests on a roomy thread, `on_big_stack`), assert on invariants and sets, `shamir-test-diag` marks for flake-prone tests.

## Rules that bind the change

* Machine memory: at most ONE cargo command at a time machine-wide (other executors run: if a cargo run is already in progress wait for its notification, never poll), ALWAYS as `bash <orch>/cg.sh env RUSTC_WRAPPER= wnice -p idle -c 50 -t 8 -m 50 -- cargo ... -j 1 > <logfile OUTSIDE the repository> 2>&1` (the wrapper serializes cargo across executors; never `-j 2`; never piped through `tail`/`head`; `cargo fmt` rejects `-j`: run it with `CARGO_BUILD_JOBS=1` under the same wrapper); every worker you spawn must be told the same, and no worker may run cargo at all except `check`/`clippy`/`fmt` under these rules.
* Leave no scratch files in the tree and none outside it (edit only paths inside this worktree).
* Wrap-up: by 150 minutes bring the change to a compiling, formatted, clippy-clean state and stop; say in the final report what is missing.
