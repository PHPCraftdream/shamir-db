# Brief: R3 step 2b — the online export job in the running server (StartExport / ExportStatus / CancelExport), server-wide maintenance gate, and the remaining export refusals that block real data

Design (settled, read first, the "Review" section included): `docs/dev-artifacts/design/logical-dump.md` — §0 decisions 3 and 7, §2 requirements 1 (one logical instant), 6 (secrets and authorization), 9 and 10 (atomic failure, cancellation), §3.3 (portable content and exclusions), §4.1 (export protocol: gate held for the whole initial export, 600 s maximum, timeout or cancellation releases it, superuser plus read/manage ACL checks, the server never accepts an arbitrary output path and writes only under a configured private export root, returns an opaque artifact name, temp name then rename after trailer verification), §5 (budgets), §6 (placement constraints: every natural host folder is at the 7-entry cap, so name each touched folder with counted entries before you add to it), §8 (owner defaults). Steps 1–4 of R3 have LANDED: the codec and verifier, the read facade `crates/engine/shamir-engine/src/db_instance/logical_export/`, the offline `logical-export` command (`crates/server/shamir-server/src/boot/config/diagnostics/logical/logical_dump/`), the import, the budgets and the guide section "Logical dump: offline export and import" in `docs/guide-docs/guide/07-operations.md`. Read the brief `31-r3-2-export-facade.md` and the R2a-3a online-backup operations (`StartBackup` / `BackupStatus` / `CancelBackup`: types in `shamir-query-types`, builders in `shamir-query-builder`, the registry/session machinery in `crates/server/shamir-server/src/boot/config/diagnostics/backup_online/`, the handlers, the Rust client methods, the permission model). The export job must follow that precedent wherever it fits, not invent a second shape.

## Why

The release gate says an operator can export a logical dump of a running database. R3 step 2 delivered the offline command only; the design's online path (an administrator job on a live server under a server-wide maintenance gate) and the removal of the conservative refusals that block real data are the remaining halves. The administrative shell (R5) will drive this job.

## What (this step only)

1. **Audit first (report it).** Establish by reading code what R3 step 2 actually shipped: is there any server-wide maintenance gate usable inside a RUNNING server (writes, DDL, buffer maintenance, replication apply, identity/ACL changes blocked and drained), or only the offline exclusive-ownership path? List every remaining value kind, object kind and scope the export still refuses (strings and arrays were lifted in R3 step 3; check schemas, validators, functions, function folders, indexes, groups, settings, ACLs, guest modules) and what each refusal costs a real database. The final report carries this table.
2. **The server-wide maintenance gate for the online job** (design §0.3, §4.1): the primitive must block and drain every write path the design lists, record the logical instant and the included `V_r` only after the drain, be held for the whole export, have the 600 s ceiling, and be released on EVERY exit path (success, error, cancellation, timeout, session or server shutdown, panic of the job task). If a primitive for this already exists from step 2, reuse it; if the running server lacks one, add the narrowest one in the `db_instance` layer (design §6 placement) and list each engine-layer touch with its rust-guard consequence. Reads stay available while the gate is held. Prove release on every path in tests (R2a-4 had the same obligation for the backup pins).
3. **The job: `StartExport`, `ExportStatus`, `CancelExport`** as typed admin operations end to end, following the backup operations: wire types, builders, Rust client methods with typed receipts (no blind retry of an uncertain start: a lost response is answered by `ExportStatus`), server handlers, the session-bound job registry and its resolution, permissions (superuser plus the included-scope read/manage checks of design §4.1; denial aborts before the gate is taken), stable error codes. Scope options are those of the offline command (`--repo`, `--table`, `--schema-only`; `--include-artifacts` only if the offline command already has it). Status reports the phase (waiting for the gate / exporting / verifying / done / failed / cancelled), the progress counts that exist (sections, items, bytes), the opaque artifact name when done, and the typed failure reason; nothing in status or errors carries a filesystem path outside the export root name, a secret, or peer-supplied text.
4. **The export root:** a new optional server configuration entry (follow how the backup destination root is configured, validated and permission-checked at boot: private directory, never inside the data directory, created or refused by the same rules). Without it the operations refuse with a typed "not configured" code. The job writes a unique temp name under the root and renames to the final name only after the trailer verification; an existing final name is never replaced; a failed or cancelled job removes its temp file; a stale temp file left by a crashed job is cleaned at the next start (only files matching the job's own pattern). Artifact retention and removal by an operator is out of scope: state in the guide that the operator removes artifacts and that the server never serves them over the protocol (the transfer path is later work: say so, do not invent one).
5. **Lift the refusals that block real data** found in item 1, in the order the design implies, only those the facade can do correctly now; each lifted kind gets a round-trip test (export → import into an empty directory → export again → canonical content equal, design §2 requirement 2) in the existing offline/import test homes. A kind you cannot lift stays a typed refusal naming the kind; list it as not covered.
6. **Tests (CI-only).** In `crates/server/shamir-server/tests/admin/` (read the folder first: boot fixtures, persistent stores, handshakes not sleeps, bounded awaits; the backup operations' tests are the model) and in `shamir-e2e` where a real client is needed: start → status → done → the artifact verifies with the existing verifier and imports offline; writes issued during the gate wait and complete after release (assert on outcome sets, not order); cancel mid-export releases the gate and leaves no artifact and no temp file; the 600 s ceiling with an injected small ceiling releases the gate (a test-only seam is allowed, no sleeps for synchronization); denial for a non-superuser and for an unreadable scope with the gate never taken; the "not configured" refusal; two concurrent starts (the second refused with the typed in-progress code, never two gates); a lost start response answered by status; a secrets scan over the whole artifact (no hash, salt, key, token, ticket, cursor); a server restart with a stale temp file. Keep the tests' cost modest (the large 64 MiB / 1 GiB budgets stay in the existing budget tests).
7. **Guide** (Russian, `docs/guide-docs/guide/07-operations.md`, extend the logical dump section, do not touch §8 Backup): the online export job — when to use it versus the offline command, what the gate blocks and for how long (the design's 600 s and what a writer sees), configuration of the export root, the order start → status → (cancel) → verify → import, the typed errors table, the artifact handling, what is still not covered. Builder/typed-client examples only, no raw JSON. Every statement must match the code.
8. **CI selection**: check with `scripts/ci/matrix/` (`edges.toml`, `selection.py`, the selection tests) that a change in the new paths selects the server, e2e and db targets on the three OS; add a declared edge and its matrix test only where a target is not selected, and list it as a widening.

## Do not

Change the dump format, the codec, the verifier, the import, the wire protocol of existing operations, the backup operations, the TypeScript client (a follow-up task adds it), add a dependency, weaken an assertion, use fixed sleeps for synchronization, or construct wire values by hand (builders only). Do not add engine-layer primitives beyond item 2 (stop and list them instead). Do not serve artifacts over the protocol.

## Layout and fixture lessons

Count every folder you add to with `ls` (many are at 7 entries: `python -I scripts/ci/check_layout.py` counts only tracked files, recheck after staging); at most 1000 lines per file, one primary item per file, `mod.rs` re-exports only (the rust-guard structure gate allows nothing else in a `mod.rs`: shared helpers go in a named file), tests in `tests/` folders, no inline `#[cfg(test)]` modules, no local `use`, no new `#[allow]`. Persistent stores, every `TempDir` alive for the whole test, close handles and wait for the server task to finish before reopening a directory (Windows holds Fjall locks until the dropped engine's background handles finish: reopen with a bounded retry on `Locked` only, like `init_waiting_for_locks` in the function-family crash tests), handshakes not sleeps, every await bounded by a generous timeout (at least 120 s: a hang detector, the Windows runner is up to 10x slower), a batch is at most 50 queries, per-session request rate limit 500 req/s (never poll in a tight loop: pace status polls at 20 ms or more), set `argon2_concurrent_max` and `auth_init_rate_per_second` to 64 in fixtures that open several sessions, debug-test stacks are small (call concrete handlers through `Box::pin`, run deep tests on a roomy thread, `on_big_stack`), assert on invariants and sets, `shamir-test-diag` marks for flake-prone tests.

## Rules that bind the change

* Machine memory: at most ONE cargo command at a time machine-wide (other executors run: if a cargo run is already in progress wait for its notification, never poll), ALWAYS as `RUSTC_WRAPPER= wnice -p idle -c 50 -t 8 -m 50 -- cargo ... -j 1` (never `-j 2`), output redirected to a file OUTSIDE the repository, NEVER piped through `tail`/`head`; every worker you spawn must be told the same, and no worker may run cargo at all except `check`/`clippy`/`fmt` under these rules.
* Leave no scratch files in the tree and none outside it (edit only paths inside this worktree).
* Wrap-up: by 150 minutes bring the change to a compiling, formatted, clippy-clean state and stop; say in the final report what is missing.
