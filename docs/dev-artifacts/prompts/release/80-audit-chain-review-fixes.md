## Findings

1. **P1 — CONFIRMED: Supported retention can remove the only usable anchor boundary.** Rotation and retention do not advance an anchor before pruning, and clean shutdown flushes the log without checkpointing the final position. For example, both stores can still hold `next_seq=101` when a clean stop finishes with rows 101–150 archived and 151–160 active. If the operator prunes the oldest archives under the supported out-of-band retention policy, the genuine suffix 151–160 has neither an anchor at its start nor one inside it. Boot returns `UnanchoredSuffix` even though every retained record authenticates. Recovery does accept a legitimately pruned suffix **if** a usable anchor survives; the defect is that the supported pruning workflow does not ensure one does. [Rotation and retention](crates/server/shamir-server-security/src/security/observability/logging/audit_appender.rs:625), [shutdown](crates/server/shamir-server/src/engine/server/server_handle.rs:297), [anchor check](crates/server/shamir-server-security/src/security/observability/logging/audit_appender/recovery.rs:465).

2. **P1 — CONFIRMED: The offline token CLI can erase the evidence of truncation that blocks server boot.** On any `verify_chain` failure, including the expected non-genesis start of a retained suffix, the CLI skips **both** checkpoint checks. It uses the parsed tail, and even `token list` calls `finish`, which writes that position to both stores. If a retained log contains rows 41–80 and loses rows 76–80 while a trusted anchor still records `next_seq=81`, server boot initially refuses. The CLI can instead record `next_seq=76` in both stores; the next boot then accepts the shortened history. This fallback predates the branch, but it defeats the new boot guarantee. On a healthy **genesis-containing** history after restart, the CLI does work: `verify_against_checkpoint` checks the predecessor at each recorded position, not just the last row. [CLI open](crates/server/shamir-server/src/boot/policy/token_cli/commands/create.rs:189), [CLI finish](crates/server/shamir-server/src/boot/policy/token_cli/commands/create.rs:239), [token list](crates/server/shamir-server/src/boot/policy/token_cli/commands/list.rs:6), [checkpoint verifier](crates/net/shamir-connect/src/server/infra/audit_chain.rs:349).

3. **P2 — CONFIRMED: Wall-clock rollback can make untampered rotations fail verification.** The writer names archives using `SystemTime`, but recovery assumes filename order is chain order. If one rotation saves rows 1–100, then the clock steps backward before the next rotation saves rows 101–200, recovery reads the latter archive first and then returns `SequenceGap` when it reaches row 1. A matching anchor does not help. Fixed-width decimal sorting itself is correct; the timestamps are not monotonic sequence numbers. [Rotation naming](crates/server/shamir-server-security/src/security/observability/logging/audit_appender.rs:612), [discovery and sorting](crates/server/shamir-server-security/src/security/observability/logging/audit_appender/recovery.rs:276), [sequence check](crates/server/shamir-server-security/src/security/observability/logging/audit_appender/recovery.rs:413).

4. **P2 — CONFIRMED: The CLI and boot disagree on an authenticated final row missing only LF.** Boot refuses the row without changing it. The CLI’s `lines()` reader accepts it, and the HMAC and checkpoint checks can all pass. A normal token creation then appends its audit record directly to the unterminated row; the next boot rejects the combined line as malformed. A recoverable framing problem has become damage to two records. [Boot framing](crates/server/shamir-server-security/src/security/observability/logging/audit_appender/recovery.rs:325), [CLI reader](crates/server/shamir-server-security/src/security/observability/logging/audit_appender/recovery.rs:118), [CLI strict append open](crates/server/shamir-server/src/boot/policy/token_cli/commands/create.rs:203), [strict writer](crates/server/shamir-server-security/src/security/observability/logging/audit_appender.rs:586).

5. **P2 — CONFIRMED: The recovery size limit is smaller than the writer’s accepted record size.** The read ceiling is 22,502,883 bytes, derived from a 16 MiB protocol frame. The audit writer is not bounded by that frame: its canonical encoder permits a `u32` details length and the appender adds base64 without a matching limit. A valid MessagePack byte string with a 17 MiB payload written through the public audit writer is accepted and persisted, then refused on reopen with `RecordTooLarge`. I did not establish that a shipped server event can generate a record that large. [Read ceiling](crates/server/shamir-server-security/src/security/observability/logging/audit_appender.rs:50), [writer length check](crates/net/shamir-connect/src/server/infra/audit_chain.rs:82), [line encoder](crates/server/shamir-server-security/src/security/observability/logging/audit_appender.rs:176), [typed refusal](crates/server/shamir-server-security/src/security/observability/logging/audit_appender/recovery.rs:311).

6. **P2 — CONFIRMED: An online backup can pass its manifest checks but fail audit recovery after restore.** The residual copy does not capture `audit.log` and its checkpoint store at one point in time. If it finishes copying and hashing `audit.log`, then an audit flush and checkpoint land before the checkpoint journal’s final hash/re-copy, the snapshot can contain the earlier log and the later anchor. The manifest authenticates those files individually; staged restore checks the engine catalogue, not the audit chain. The first full boot of the restored directory then returns `AnchorPastTail`. On a filesystem that can lose an unsynced directory update, a power cut after a checkpoint covering the newly created active file can lose that file’s name while preserving the checkpoint. The next boot correctly refuses, but the system created the inconsistency itself. This is separate from an ordinary process kill between rename and reopen, which recovery handles. Log contents are streamed, with memory bounded by one record’s working buffers plus the list of archive paths. ## What the boot trace confirms

Server boot takes the same exclusive `.shamir.lock` as offline maintenance before opening the stores, holds it across recovery, and transfers it to the live handle. Two normal boots cannot scan or append concurrently. The verifier checks every retained row with the persisted key and the same canonical bytes the writer signs, using constant-time comparisons for MACs and links. It checks both anchors at their authenticated positions, refuses a non-genesis anchor on empty history, refuses a missing middle segment through the sequence/link checks, and never uses a stale anchor as the writer position. Filename timestamp gaps alone are not errors. The appender opens **after** verification; the appender checkpoint is persisted before the meta checkpoint, and both before publishing the writer. A process crash between the two writes is safe if the verified history remains: the new tail anchor and older compatible anchor can coexist. [Lock](crates/server/shamir-sync/src/sync/durability/maintenance_lock.rs:13), [verification and anchor checks](crates/server/shamir-server-security/src/security/observability/logging/audit_appender/recovery.rs:395), [writer signing](crates/net/shamir-connect/src/server/infra/audit_chain.rs:258), [checkpoint order](crates/server/shamir-server/src/engine/server/server_launcher/support/durable_stores.rs:104), [lock transfer](crates/server/shamir-server/src/engine/server/server_launcher/launch.rs:784).

A parseable final row without LF is **not** silently dropped by boot. An unparseable bounded fragment is physically removed only after the complete prefix and anchor checks pass. If complete rows **after** the latest trusted anchor were removed and a fragment remains, boot can discard the fragment and resume from the older verified prefix, including genesis if no non-genesis anchor exists. That is the documented rollback limit, not acceptance of an invalid HMAC or truncation behind an anchor. [Fragment classification](crates/server/shamir-server-security/src/security/observability/logging/audit_appender/recovery.rs:319), [mutation after verification](crates/server/shamir-server-security/src/security/observability/logging/audit_appender/recovery.rs:60).
