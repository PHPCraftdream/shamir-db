# Brief: AUDIT-CHAIN-RESTART — the audit HMAC chain must continue from the verified tail of the existing `audit.log` after every restart (a routine clean restart currently breaks verification of the whole history)

Re-open every path and line before relying on it (lines drift). Verified by a read-only trace of the landed code on 2026-11-21 (not yet reproduced: this task's first test proves it in CI).

## Why

Boot (`crates/server/shamir-server/src/engine/server/server_launcher/launch.rs`, the audit setup around the places that read `meta.audit_checkpoint()` and construct the chain) takes the chain position ONLY from `ServerMetaStore::audit_checkpoint()` (`crates/server/shamir-server/src/engine/server_meta.rs`). With no value there, `AuditChain::new` starts at sequence 1 with an all-zero predecessor (`crates/net/shamir-connect/src/server/infra/audit_chain.rs`). The live appender (`crates/server/shamir-server-security/src/security/observability/logging/audit_appender.rs`) opens `audit.log` with `create(true).append(true)` and does NOT recover the chain, and its online checkpoints (every 1000 entries from the writer and every 60 s from the scheduler in `crates/server/shamir-server/src/boot/scheduler.rs`) go to its OWN Fjall keyspace `audit_checkpoint`, never to `ServerMetaStore`. The only production writer of the meta checkpoint is the offline token CLI (`crates/server/shamir-server/src/boot/policy/token_cli/commands/create.rs`). Failing sequence, no crash needed: fresh data directory, rotation off, boot, one successful SCRAM login (`auth_success` is audited before `auth_ok`), clean shutdown: the log holds sequence 1. Boot the same directory, another login, clean shutdown: the log holds `[1, 1]` and `verify_chain` returns `SequenceGap { at: 1, expected: 2, found: 1 }`. Existing tests do not catch it: `chain_verifies_after_restart` rereads one run's log, `audit_writer_continues_seq_after_restart_checkpoint` hands the checkpoint in manually, the same-directory relaunch test (`crates/server/shamir-server/tests/e2e/core/shutdown_release_e2e.rs`) asserts only repository persistence. There is no standalone audit verifier command in this tree; the offline token CLI runs `verify_chain` and on failure only warns and resumes from the parsed tail.

## What (this step only)

1. **Recover the writer position before the live appender opens** (under the existing data-directory lock, in the boot path; the appender and `AuditChain` APIs may gain the narrowest helper they need, listed in the report): read the appender's own checkpoint store and the legacy meta checkpoint as truncation ANCHORS; authenticate the on-disk chain with the audit key; resume from the VERIFIED TAIL (sequence + 1, predecessor = the tail entry's HMAC), never from a possibly stale checkpoint; use genesis only for an empty history that is consistent with the anchors (an empty log with a non-empty anchor is a truncation: refuse). For rotated and retained logs verify the retained suffix against a usable anchor. If the history cannot be authenticated (bad HMAC, gap, truncation behind an anchor, unreadable tail) the boot fails with an explicit typed audit boot error; it never appends a new genesis and never trusts an unverified tail. Reading a large log must be bounded in memory (stream entries), and a torn final line from a crash (partial write at the tail) must be handled by a documented rule: say which (for example: an incomplete final record is discarded only if everything before it verifies and no anchor lies beyond it) and test it.
2. **Keep the two checkpoint stores honest**: after recovery the meta checkpoint and the appender checkpoint must not contradict the resumed position (read how `verify_against_checkpoint` is used by the offline CLI and do not break it).
3. **Tests (CI-only; registered in their `tests/mod.rs`).** `clean_restart_continues_persisted_audit_chain` in `crates/server/shamir-server/tests/e2e/core/shutdown_release_e2e.rs`: reuse its `launch` and `connect`; two boot/login/clean-stop cycles on ONE temporary directory with rotation off; read the log after each stop; assert the first new entry has `seq == old_tail.seq + 1` and `prev_hmac == old_tail.hmac`, and that the whole log verifies with the persisted audit key. Before the fix it sees sequence 1. Unit tests for the recovery routine: empty history, valid history, history with a flipped bit (boot error), a gap (boot error), truncation behind an anchor (boot error), a torn tail under the documented rule, rotated history. A crash-style test (kill without a clean stop, simulated by dropping the writer without the final flush) that the next boot resumes correctly.
4. **Guide.** In `docs/guide-docs/guide/07-operations.md` (Russian) state what the audit chain guarantees across restarts and what an unauthenticatable history does at boot (the typed error and the operator's options). Only statements that match the code.
