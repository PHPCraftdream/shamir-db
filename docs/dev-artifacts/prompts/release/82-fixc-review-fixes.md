## What (this step only), by reviewer finding number

1. **Finding 1 (P1): a snapshot absent at the first lookup is read without a lease.** `sync/snapshot_lease.rs` returns `Ok(None)` when `canonicalize` hits `NotFound`; `verify_manifest` and restore then open the original pathname and never retry the lease, so a snapshot that appears right after the lookup is read unleased and retention can delete it under the reader. Make a missing source a refusal at lookup time (the reader reports not-found and reads nothing), and never read a snapshot path that was not resolved under the decision the lease made. Test: a seam that makes the child appear between the lookup and the manifest open must end in a refusal, not an unleased read.
2. **Finding 2 (P1): a persistent marker error disables retention without tripping the failure metric.** `sched/registry.rs` (~511-523, 555-574) logs a warning on provisioning failure, still runs the backup, and skips the whole prune call including its metrics; snapshots produced during the failure stay untagged and are never pruned, so the disk fills while the retention-failure alert stays quiet. Count a provisioning failure as a retention failure (the same outcome and metric a failed prune uses), keep the backup itself succeeding, keep deletion fail-closed, and make later passes able to tag and prune the untagged snapshots after the marker is repaired (read how `tag_fresh` and the eligibility rule treat untagged children; if repair needs a one-time adoption rule, state it and test it). 3. **Finding 3 (P2): tagging races a leased verifier.** `sched/schedule/retention/prune.rs` (~118-119) calls `tag_fresh` BEFORE any lease; `ownership.rs` (~55-64) creates a named temp file INSIDE the snapshot, which a verifier holding the shared lease then sees as an unmanifested file and reports `UnmanifestedFile` for a valid snapshot. Take the same non-blocking exclusive lease before tagging (skip tagging of a busy snapshot this pass, counted like a skipped deletion), or write the temp file outside the snapshot directory: choose the narrower change and say why. Test: a verifier holding the lease while the scheduler tags never sees the temp file.
4. **Finding 4 (P2): a reader can create a marker in a foreign directory or fail on a read-only one.** `sync/snapshot_lease.rs` (~47-86, 141-172) classifies a timestamped child as managed from a syntactically valid owner tag alone and READERS create the marker lazily, so exporting a scheduled snapshot to read-only media makes `verify`/`restore` fail with an I/O error before reading anything, and on a writable foreign parent the reader creates the marker and then classifies timestamped siblings as managed; `server/migrate/execution.rs` (~70-83, 187-193) and `backup_gate.rs` (~28) call `verify_manifest` for `--plan --from-backup`, which the guide says takes no lock and writes nothing. A snapshot with an owner tag in a parent WITHOUT the marker is read lock-free (an export). Tests: a read-only parent holding a tagged export verifies and restores; a reader never creates the marker; `--plan --from-backup` writes nothing.
5. **Finding 5 (P2): the unleased verification API and the bypass are broader than the writer needs.** `sync/offline.rs` (~608-676) publishes an unrestricted unleased verifier and a doc-hidden public closure `with_backup_writer_verification` that disables leasing for EVERY direct child of the root on that thread; a direct caller of `run_online_backup` on a marked root waits behind retention in its own self-check because only the server wrapper installs the bypass. ## Appendix — the reviewer's report (verbatim)

VERDICT: FAIL

The lock primitive is correct on Unix and Windows. The blockers are in the paths that decide whether to take the lease, and in retention’s handling of lease failures. **CONFIRMED** below means traced end to end in source, including the relevant dependency implementation; no scenario was run.

Path prefixes: `sync/` = `crates/server/shamir-sync/src/sync/durability/backup/`; `sched/` = `crates/server/shamir-server/src/boot/config/diagnostics/backup_online/`; `server/` = `crates/server/shamir-server/src/`.

## Findings

1. **P1 — CONFIRMED: A snapshot absent at the initial lookup can be read without a lease after it appears.** `sync/snapshot_lease.rs:40–45` returns `Ok(None)` on `canonicalize` returning `NotFound`. Both `verify_manifest` and restore then open the original pathname, and neither repeats lease acquisition (`sync/offline.rs:583–589`, `sync/restore.rs:259–288`). **Scenario:** With a valid marker already present, a verifier starts just before the scheduled writer creates the named child. Its lookup returns `NotFound`; it is descheduled. The backup completes and is tagged. The verifier resumes, reads the manifest, and pauses before opening a payload. The next successful backup pushes that snapshot out of `keep_last`; retention gets the exclusive lock and deletes it under the verifier. No marker removal, forged tag, or second writer is needed. This is distinct from a reader that loses the race to an already-running deletion and correctly refuses afterward.

2. **P1 — CONFIRMED: A persistent marker error disables retention without tripping the retention-failure metric.** `sched/registry.rs:511–523,555–574` logs a warning on provisioning failure, still runs the backup, and skips the entire prune call, including its metrics. **Scenario:** An otherwise valid private destination contains a directory at `.shamir-snapshot.lock`. Scheduled runs can keep succeeding but never tag or delete anything; the retention-failure counter stays flat. Even after repair, snapshots produced during the failure remain untagged and are excluded by `sched/schedule/retention/prune.rs:89–98`. The skip is correctly fail-closed for deletion, but successful backups can fill the disk while `BackupRetentionFailing` stays quiet.

3. **P2 — CONFIRMED: Retention can make a valid fresh snapshot fail standalone verification while the verifier holds the lease.** `sched/schedule/retention/prune.rs:118–119` calls `tag_fresh` before any exclusive acquisition. `sched/schedule/retention/ownership.rs:55–64` creates and syncs a named temp file **inside** the snapshot before replacing `backup.meta.json`; `sync/offline/v2_verify.rs:262–272` exempts the final sidecar, not the temp file. **Scenario:** Pause the scheduler after the temp file is created. A verifier takes the shared lease, hashes the valid payloads, sees the temp file on its final walk, and returns `UnmanifestedFile`. This is a tagging race, not a deletion race.

4. **P2 — CONFIRMED: An exported snapshot can create a marker in a foreign directory or become unreadable solely because that directory is read-only.** `sync/snapshot_lease.rs:47–86,141–172` recognizes a plain timestamped child with either a normal marker in its canonical parent or a syntactically valid owner tag. It checks neither the configured owner nor the parent’s privacy; retention checks both (`sched/schedule/retention/prune.rs:49–56,89–98`). **Scenario:** Export a complete scheduled snapshot to read-only media without renaming its timestamped directory. The retained sidecar makes both verify and restore attempt a write-capable marker open or creation; they return an I/O refusal before reading the manifest. On a writable foreign parent the same operation creates the marker, and timestamped siblings can then be classified as managed too. This also regresses the documented read-only migration plan: `server/migrate/execution.rs:70–83,187–193` calls `verify_manifest` through `server/migrate/backup_gate.rs:28`, so `--plan --from-backup` can take a lock and create the marker even though it does not take the target maintenance lock.

5. **P2 — CONFIRMED: The unleased verification API is broader than the writer needs, and direct protocol callers do not get the writer bypass.** `sync/offline.rs:608–609` publishes an unrestricted verifier that never leases. The doc-hidden but public `with_backup_writer_verification` lets any closure bypass leasing for **every** direct child of the chosen root on that thread (`sync/offline.rs:629–676`). **Scenario:** An embedding invokes that closure to self-check a new copy and also verifies an older sibling inside it. The older read is unleased and can race deletion. Conversely, a direct caller of public `run_online_backup` on a marked root waits in its normal `verify_manifest` call if retention has the exclusive lease; only the server wrapper installs the bypass (`sync/online/protocol.rs:280–296,355–382`; `sched/registry.rs:524–541`). The shipped registry’s own self-check is safe from *its* retention: the child was atomically created for the run, is not yet tagged, and that run does not prune until the protocol returns. No production use of the broad bypass for an old child was found.

6. **P2 — CONFIRMED: `StagedFileMissing` exposes the staging path, and a legacy CLI refusal can occur after modifying the target.** `sync/restore/staged_listing.rs:27–35` puts the joined staging path in the error; `sync/restore.rs:168–178` displays it. An absolute target produces a message containing its absolute staging sibling, not just `users/keeper.bin`. Separately, legacy restore runs the supplied probe first (`sync/restore.rs:312–324`); the CLI probe opens `server_meta` via `open_or_init`, which updates and persists `last_started_at` (`server/boot/config/diagnostics/restore.rs:10–29`; `server/engine/server_meta.rs:228–243,327–339`). **Scenario:** Restore an offline copy to a stopped, initialized target; a listed source file then disappears before enumeration. The new check refuses and never swaps, but the probe has already written to the target. The check invokes best-effort staging cleanup; it does not guarantee cleanup if removal fails (`sync/restore.rs:415–418,735–742`). The online path uses the read-only probe and does not have this target-write issue.

7. **P2 — CONFIRMED by code and filesystem semantics: The staged presence check does not detect Windows case collisions.** `sync/offline/v2_verify.rs:92–117,262–273` accepts two exact, distinct names on a case-sensitive source. Restore copies by directory entry, and `fs::copy` can overwrite an existing destination (`sync/offline.rs:867–896`). **Scenario:** Restore a valid snapshot containing different `payload/Foo.bin` and `payload/foo.bin` from a case-sensitive source to ordinary case-insensitive Windows staging. Both names resolve to the one surviving staged file, so both `symlink_metadata(...).is_file()` checks pass (`sync/restore/staged_listing.rs:27–38`). This is a pre-existing copy limitation that the new presence check does not catch, not a new false refusal.

## Locking, coverage, and failure modes

- **Same-process exclusion works.** The pinned `fs4` is **0.12.0** (`Cargo.lock:1405–1413`). Its Unix implementation uses `flock(LOCK_SH)` and `flock(LOCK_EX | LOCK_NB)` through `rustix`, not POSIX process-associated `fcntl` record locks (`fs4-0.12.0/src/unix.rs:3–35`). Windows uses `LockFileEx` over the same byte range for both modes, with `LOCKFILE_EXCLUSIVE_LOCK | LOCKFILE_FAIL_IMMEDIATELY` for the try (`fs4-0.12.0/src/windows.rs:1–45`). On the supported local filesystems a separately opened handle conflicts in the same process just as it does across processes. The code maps `EWOULDBLOCK` / `ERROR_LOCK_VIOLATION` to `None`; other errors do not authorize deletion.
- **Normal reader lifetime is correct once the lease is acquired.** The server re-exports the same standalone `verify_manifest`; there is no separate backup `verify` CLI. Restore holds its handle through classification, hashing, the stamp gate, and the source copy. It releases the lease **before** the staged check. That is safe: the check reads staging only, and replay’s store and WAL paths both come from staging (`sync/restore.rs:339–424`; `sync/restore/catalogue.rs:296–304`; `sync/restore/online.rs:64–73`). Restore opens the source manifest for classification and again for full verification, but the staged check uses the **exact decoded manifest returned by verification**; it does not reopen the manifest for its list. Restore copies regular files including the root controls and any listed lock files. The online producer, not restore staging, omits inherited root controls, cache, and source locks; online replay recreates Fjall locks later. Ordinary producer-generated slash-normalized names do not introduce a false refusal.
- **Other reads without a full lease:** retention’s sidecar/tree/hash preflight is deliberately unleased (`sched/schedule/retention/preflight.rs:23–47,116–123`); the writer self-check and the registry’s final progress reread concern the just-written child, which its own pass never deletes (`sched/registry.rs:581–584,813–819`). The migration gate releases the lease when `verify_manifest` returns, then rereads the source manifest and stamp unleased (`server/migrate/backup_gate.rs:28–33,63–67`); retention can win between those reads if the gate is pointed at an eligible scheduled copy. The supported migration recipe takes a separate offline backup. `BackupStatus` reads in-memory state, not the filesystem. I found no repository snapshot-listing command or guide count script to update. External `cp` and directory walks are unleased. A directory-only count ignores the marker; a raw directory-entry count does not. Retention explicitly excludes it from both the root-entry cap and `untouched`.
- **Deletion and starvation:** Retention opens and tries the exclusive lease for **each** selected deletion and holds it through `remove_dir_all` (`sched/schedule/retention/prune.rs:125–159`). Contention increments `skipped_in_use` only; it is a per-pass outcome and a debug log, **not** an exported metric. A skip or lease error makes no deletion attempt. An actual recursive-delete failure can leave a partial tree—for example, deletion removes some files before a Windows sharing violation on another; the next preflight can reject the remainder as unverifiable. This is an existing in-place deletion limitation. The registry releases `BackupPermit` before prune; `record.running` still rejects new registry work until completion (`sched/registry.rs:310–320,551–565,607–618`). A hung reader or readers spanning every deletion attempt can starve the **whole root** while backups continue to accumulate. If the backlog crosses an existing scan cap, later passes can refuse even after readers drain. The guide states the root-wide skip but does not explain this disk-growth or cap consequence.
- **Marker lifecycle:** Process exit releases the OS lock; a stale *file* is not a stale lock. Two ordinary first opens converge through `create_new` and the `AlreadyExists` reopen. Unix requests `0600` and repairs a restrictive umask through the created handle. There is a small fail-closed window before that repair: a concurrent opener can get permission denied, and a crash in that window can leave an inaccessible marker. Existing file permissions are not repaired. On Windows the owner-only inheritance claim holds for a validated scheduled root, whose sole ACL entry is inheritable (`crates/foundation/shamir-private-dir/src/windows.rs:46–59,232–253`), not for a foreign root. Stable source symlinks are canonicalized; a marker already observed as a symlink or reparse point is refused. The subsequent open is nevertheless by pathname, not an atomic no-follow open. On Unix, if a same-account operator unlinks a **held** marker, retention can recreate it and lock a different inode. That is a real failure mode outside the documented stable-marker contract, not a claim that a normal reader or retention itself unlinks it. A missing marker alone, or a missing tag alone, does not defeat classification for an existing retention-eligible child under the cooperating protocol.
