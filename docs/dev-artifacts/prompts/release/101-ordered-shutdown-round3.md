## Findings

- **P1 — Final close can begin before the scheduler has stopped.** `audit_teardown.rs:101–132` records a scheduler or flusher timeout and then submits final close anyway, even if the deadline is already exhausted. The gate prevents simultaneous writes; it does not make final close happen last. A checkpoint already submitted but not yet through the gate can run after final close. The report and `07-operations.md:1119` claim an ordering that only holds when the joins succeed.
- **P1 — The current-thread deadline can still be stalled by other work it waits on.** Counter GC still runs inline in the scheduler being joined (`boot/scheduler.rs:155–171,329–355`), and its Fjall implementation takes a synchronous lock and can call `SyncAll` (`shamir-connect/src/server/infra/durable_counters.rs:244–277`). The root cancellation path also wakes synchronous final metadata writes (`engine/server/meta_sinks.rs:107–124`); those writes and the audit metadata hook share `ServerMetaStore::write_lock` (`engine/server_meta.rs:831–836,899–915`). These are source-level paths that can block the only runtime thread, not observed hangs.
- **P1 — Scheduled-backup completion is incomplete.** Retention checks cancellation only around the verifier (`retention/preflight.rs:125–131`); `shamir-sync/.../offline.rs:73–86,683–698` still hashes without checking between reads. Tests (c) and (d) are absent. Also, extracting the schedule handle means `serve` bypasses the former pre-repository join: it now waits for the backup only after repository flush and the store-release barrier have completed or timed out (`server_handle.rs:290–294,369–384,420–430`; `boot/runtime.rs:69–77`). The lock lifetime improves, but the earlier teardown ordering is not preserved.
- **P2 — Discard registration remains non-atomic, and the reply comment is still false.** A request can reserve, pause across `close()` and the sweep, then spawn. The blocking job can start before `track_or_abort` obtains the mutex; abort cannot stop started blocking work (`repo_audit.rs:217–269,378–427`). `activity/cancel.rs:61–74` constructs the client response **after** that synchronous enqueue and mutex acquisition, contrary to `repo_audit.rs:139–145`.
- **P2 — A bucket limit is not per-principal fairness.** At `repo_audit.rs:149–171,430–435`, two distinct usernames in the same bucket share one counter. One principal can exhaust that bucket and deny the other despite free global slots. The “at least eight principals keep their full share” claim in the report and guide is not guaranteed.
- **P2 — The new blocking flusher can lose an error.** Security `audit_appender.rs:462–474` logs an inner blocking-job `JoinError` as “latched fail-closed” without latching it or returning it through `join_flusher`. If the job panics after the buffer is taken (`audit_appender.rs:666–672`), a subsequent empty final drain can succeed and the report can miss the failed job.
- **P3 — The guide and timeout message still disagree with the implementation.** `boot/runtime.rs:94` says “forcing exit”; neither executable path forces exit. The guide at `07-operations.md:1123–1125` attributes queued-job discard to the audit deadline rather than the three-second drain expiry, understates the scope of the 30-second outer timeout, and implies the instance lock is still held after `serve` returns. It is dropped before return. The guide also omits the requested statement that `ShutdownReport` stores strings, not typed variants.

## Policy (verbatim, binding)

Compilation, builds and tests run on GitHub CI, not on this machine. Banned locally: `cargo test`, `cargo nextest`,
`./scripts/test.sh`, `cargo build`, `cargo run`, `cargo bench`, `cargo doc`, npm/tsc builds, any build or test run.
Allowed locally only: `cargo check -p <crate> --all-targets`, `cargo clippy -p <crate> --all-targets -- -D warnings`,
`cargo fmt -p <crate>` (and `-- --check`), `python -I scripts/ci/check_layout.py`.

⛔ NEVER run `git reset` / `checkout` / `clean` / `stash` / `restore` / `rm`, or any git command that mutates the working
tree or index. Only edit files; the orchestrator commits. (For file moves use a plain filesystem move and say so in the report;
the orchestrator stages them so git detects the renames.)
