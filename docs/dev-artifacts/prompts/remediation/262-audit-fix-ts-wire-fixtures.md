# 262 — audit-fix-ts-wire-fixtures (P1 audit follow-up: H5 guard stage C0, tests/fixtures only)

Source: post-merge audit of PR #323 + design decision by @oh (2026-10-29, binding). Stage C (263) will reject unknown keys in every request-side type under v4. Before it lands we need a guard that proves no FIRST-PARTY producer sends keys the Rust DTOs do not know. This stage adds the guard and is GREEN on the current code (it must not change any decoding behaviour).

Read first: `CLAUDE.md`, the existing parity pattern: `crates/shamir-query-builder/tests/fixtures/{create_index_matrix,repl_ddl_msgpack,vector_filter_msgpack}.json` + `crates/shamir-query-builder/tests/{create_index_matrix,repl_ddl_msgpack,vector_filter_msgpack}.rs` and the TS side `crates/shamir-client-ts/src/core/builders/read/__tests__/vector_filter_parity.test.ts`, `.../stream/__tests__/repl_parity.test.ts`. Producers: `crates/shamir-client-ts/src/core/builders/**` (TS) and `crates/shamir-query-builder/src/**` (Rust). Decoder: `crates/shamir-query-types` (`BatchOp`, `BatchRequest`).

## Change
1. A shared fixture `crates/shamir-query-builder/tests/fixtures/wire_ops_matrix.json` (multi-line, indented JSON literal; one entry per case: `{ "name": ..., "builder": "<how it is built>", "wire": <the exact op JSON the builder emits> }`) covering the request-side ops a client really sends. Derive each `wire` object BY READING the builders (do not guess): Rust builder emission is authoritative via `serde_json::to_value(op)` in the Rust test; the TS side by reading the TS builder source for the same call. Cover at least: read (from, select, where with eq/and/or/not/in/like/regex, order_by, pagination/limit/offset, group_by+having, joins if the builder has them), insert_into, update (set + where + expected_version), delete_from, upsert, create_table, create_index (the existing matrix covers part - reuse, do not duplicate), drop_index, rename, schema/validator ops the builders produce, sub_batch / for_each / call, subscribe, and a full `BatchRequest` with `queries` map entries carrying `return_result`, `after`, `when`, plus `limits`.
2. Rust test `crates/shamir-query-builder/tests/wire_ops_matrix.rs`: for every fixture entry (a) build the op with the Rust builder where the entry names one, serialize and assert it equals `wire` (parity), and (b) decode `wire` as `shamir_query_types::batch::BatchOp` (or `BatchRequest` for the request entry) through BOTH `serde_json` and `rmp_serde::to_vec_named` -> `from_slice`, then re-serialize and assert the re-serialized JSON equals `wire` EXACTLY (this equality is what proves there is no key the DTO ignores: an unknown key would be dropped on the round trip and the comparison fails). Treat `null`-valued optional keys carefully: normalise only what the builder itself omits when unset (look at the `skip_serializing_if` attributes), never blanket-strip.
3. TS parity test `crates/shamir-client-ts/src/core/builders/__tests__/wire_ops_matrix_parity.test.ts` (new dir only if the folder rule allows; check entry counts) that loads the same JSON fixture and asserts the TS builders produce deep-equal `wire` for every entry that names a TS call. Follow the import/fixture-loading pattern of the existing parity tests exactly. The TS tests run in CI (`ts unit`), never locally.
4. Any mismatch you find between a builder and the DTO (a key a builder emits that the DTO does not model, or the reverse) is a FINDING: do NOT fix production code, do NOT drop the case; record it in the fixture as `"known_gap": "<one line>"`, exclude it from the strict equality assertion in a clearly named test that lists the gaps, and report every gap in your final message. This list decides the scope of stage 263.
