## 11. Risks and open questions for the owner

1. **Durable identity for hybrid — DECIDED (A11):** `StorageOwnership` is written into hybrid's durable fjall metadata/interner tier. Replication lineage stays per-boot for hybrid and is explicitly distinct from storage ownership. Per-boot minting of ownership was rejected: it would weaken journal/destruction identity (INFERRED from repo_identity.rs:24-34).
2. **Windows reseed — DECIDED (A12):** Windows reseed is refused before any install mutation in the 8b-3 series and certified on Windows CI (case 15). Windows destruction and name release remain required. "Windows seed install" is a mandatory end-state follow-up, not a permanent product limitation.
3. **System-store flush granularity vs crash windows:** the system store is a Fjall `RepoInstance`; `remove_repository` commits via the implicit tx then flushes (**OBSERVED** `crates/shamir-db/src/shamir_db/system_store/catalogue.rs:101-123`, flush at :122) while `remove_database` currently does not flush (`crates/shamir-db/src/shamir_db/system_store/catalogue.rs:33-45` — **fixed in 8b-3a per A7**, not 8b-3c). Confirm the accepted Prepare-flush-then-anchor-flush window and that boot replay tolerates each intermediate ordering.
4. **Supervisor integration contract for lease drain — DECIDED (A6):** the executor calls the NEW targeted drain API `drain_targets(targets, generations) -> DrainReceipt`, never `stop_all`. Under control it invalidates/drains affected leases via `quiesce_subscription_lease_locked` and marks subscriptions `retiring`; outside control it stops/joins only those loops with bounded timeout (timeout → `Blocked`, fail-closed); re-takes control, verifies generations unchanged and no lease remains. `stop_all` is rejected for destruction (**OBSERVED** sync/replication/supervisor.rs:389 `stop_all`, :311 `reconcile`, :428 `start_subscription` with control acquisition at :434, :459 `take_subscription_lease`).
5. **`destination_incidents` location — DECIDED (A2 item 5):** system store table, permanently. No separate journal.
6. **Interaction with the online migration API — DECIDED (A8):** migration is interlocked NOW (the API is reachable through config today; **OBSERVED** core.rs field :144, `enable_experimental_migration_api` :706). It acquires both namespace admissions in global `(db, repo)` order before control and write locks, re-validates identity after acquisition, and refuses reserved targets. The CI case "migration during reserved name" is MANDATORY in 8b-3c, not conditional.
7. **Blocked-operation capacity/backpressure — DECIDED (A2, DEC-3 item 7):** `destruction_archive` NEVER releases protection. Eligible only for Repo/Database `Destroyed` + fully acked, and SubscriptionRemoval `Completed`. Archival replaces the row with a permanent compact tombstone `{operation_id, kind, final_state, frozen storage_object_ids, sha256(full row), archived_at, archived_by, subscription, binding_generation, incident_refs}`; operation ids are never reusable. A final `Blocked` operation exits only through `destruction_retry` → `Destroyed`. A `Blocked` SubscriptionRemoval at `RowDeleted` whose re-verification found data converts that data into an R2' target or an incident, never a release. Backpressure: a quota on concurrent non-terminal operations; new destruction is refused when the quota is reached; nothing protected is ever evicted.
8. **Audit chain dedup semantics:** **DECIDED — the closed durability-proof rule.** The ONLY proofs that a barrier event is durable are: (a) the original append's own successful sync (ack returned); (b) a FRESH append of the SAME event_id that succeeded (idempotent by event id — duplicates are tolerated by the verifier and deduplicated on read; this includes the reconciliation RE-WRITE); (c) an ack record written by `checkpoint_durable` AFTER its own successful flush+sync that names a durable-through seq ≥ the event's seq (the watermark is only advanced by successful syncs, item 0b). A found-but-unconfirmed entry in the log tail is NOT evidence and must never be adopted; `AuditSink::contains`/`read_durable_tail` are only allowed to answer (c)-style watermark questions and to locate entries for the (b) RE-WRITE, never to authorize adoption by themselves. Restart: the executor holds no memory of (a); it uses (b) by re-appending the pending entry (idempotent by event id) or (c) by reading the persisted `checkpoint_durable` ack record (which survives in the checkpoint keyspace) — never by trusting the log tail alone. The outbox replay is idempotent by event id `(operation_id, transition_ordinal)`; NEVER `AuditChain::snapshot` (in-memory test helper; a restart starts with an empty in-memory vector — **OBSERVED** BOTH `from_checkpoint` (entries `Vec::new()`) at audit_chain.rs:170-177 AND `AuditChain::snapshot` (the test helper) at :227-228). The durable-through seq advances only on a contiguous-prefix write+sync; the chain poisons on failure. **Poison attribution:** a poison is set ONLY by a durability failure attributed to a specific append (the synchronous barrier/append path — the caller learns the id); a BACKGROUND-flusher failure (**OBSERVED** audit_appender.rs:346/:349, now at `crates/shamir-server/src/security/observability/logging/audit_appender.rs`) is NOT a poison — the batched flusher must RETAIN the failed batch in the buffer (fixing the take-before-write loss at audit_appender.rs:469) and mark the sink degraded; the next successful flush of the retained batch advances the watermark; if it cannot be re-flushed, the NEXT attributed barrier append fails and poisons normally. When the barrier's batch flush fails, ALL co-batched entries' seqs stay unadvanced in the watermark (contiguous-prefix rule only); their owners learn via their own ack paths; no per-entry action is required. A poison that survives reconciliation retries surfaces as `AuditSinkError::Poisoned` on every append and requires operator/ops action — never silent clearing. **The unpoison path (DECIDED):** the poison has an EXACT resolution — a poisoned chain admits exactly ONE append class, the reconciliation RE-WRITE of the failed event id (poison check bypassed for that single event id, tracked by the chain), and unpoisons upon that entry's own successful `write_all` + `sync_all`; any other append during poison returns `AuditSinkError::Poisoned`; poison is never silently cleared (fail-closed: either the entry is re-written durably or the sink stays poisoned). Chain duplicates are bounded — at most one per CLASSIFIED-AMBIGUOUS OUTCOME, bounded in total by the attempt cap (`append_attempts`, 131 §3e item 6b) — acceptable and documented; the journal, not the chain, is the recovery authority (I10). No dedup index is added to the chain format.
9. **Batched-mode flush-before-return cost:** the barrier call force-flushes the shared audit buffer; a bursty deployment could see latency spikes at Prepare. Acceptable (Prepare is rare, correctness-critical); latency is exposed as a metric per A10.
