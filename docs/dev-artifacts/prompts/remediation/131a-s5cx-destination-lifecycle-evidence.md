## 11. Risks and open questions for the owner

1. **Durable identity for hybrid:** write `StorageOwnership` into hybrid's durable fjall metadata/interner tier, or accept per-boot minting for hybrid like in_memory? Recommendation: write into the durable tier (identity stability is worth the work); per-boot minting would weaken journal/destruction identity (INFERRED from repo_identity.rs:24-34).
2. **Windows reseed stays unsupported** — destruction + name release supported, reseed not. Accept as documented product limitation? (Recommendation: yes, for this series.)
3. **System-store flush granularity vs crash windows:** the system store is a Fjall `RepoInstance`; `remove_repository` commits via the implicit tx then flushes (**OBSERVED** system_store.rs:330-352) while `remove_database` currently does not flush (:262-275 — fixed in 8b-3c). Confirm the accepted Prepare-flush-then-anchor-flush window and that boot replay tolerates each intermediate ordering.
4. **Supervisor integration contract for lease drain** (Quiesce step): depends on #188's final lease/`stop_all` shapes (**OBSERVED** round 5: supervisor.rs `stop_all` :389, `start_subscription` :428, generation lease under control :434, `reconcile` :311 (**Citation re-verified (round 5)**); **REQUIRES #188** for the lease gate). Decide whether the executor calls supervisor `stop_all`-scoped or a new per-target drain API.
5. **`destination_incidents` location:** system store vs a dedicated journal table/file. Recommendation: system store table for stage 2; revisit if write contention shows up.
6. **Interaction with the online migration API:** migration admits two repos per instance (core.rs field :141-143, `enable_experimental_migration_api` :672+ — **Citation re-verified (round 5)**); confirmed the design routes both admissions through seam (4) — CI should add a migration-during-reserved-name case if the experimental API ships.
7. **Blocked-operation capacity/backpressure:** `Blocked` operations accumulate and hold reservations indefinitely. Recommendation: no automatic expiry; admin-visible listing + owner-approved archival (**round 6, C8:** `destruction_archive` accepts a FINAL-`Blocked` + fully-acked row as well as `Destroyed` + fully-acked, and EXPLICITLY releases the `Blocked` row's reservations as part of the same owner decision — reservations lapse only via this explicit owner-approved act, never silently, I1; see surface Appendix B).
8. **Audit chain dedup semantics (round 3; revised rounds 4-6):** **DECIDED — the closed durability-proof rule (round 6; identical text in M §3e item 6 and S A.7a/A.7b).** The ONLY proofs that a barrier event is durable are: (a) the original append's own successful sync (ack returned); (b) a FRESH append of the SAME event_id that succeeded (idempotent by event id — duplicates are tolerated by the verifier and deduplicated on read; this includes the reconciliation RE-WRITE); (c) an ack record written by `checkpoint_durable` AFTER its own successful flush+sync that names a durable-through seq ≥ the event's seq (the watermark is only advanced by successful syncs, item 0b). A found-but-unconfirmed entry in the log tail is NOT evidence and must never be adopted; `AuditSink::contains`/`read_durable_tail` are only allowed to answer (c)-style watermark questions and to locate entries for the (b) RE-WRITE, never to authorize adoption by themselves. Restart: the executor holds no memory of (a); it uses (b) by re-appending the pending entry (idempotent by event id) or (c) by reading the persisted `checkpoint_durable` ack record (which survives in the checkpoint keyspace) — never by trusting the log tail alone. The outbox replay is idempotent by event id `(operation_id, transition_ordinal)`; NEVER `AuditChain::snapshot` (in-memory test helper; a restart starts with an empty in-memory vector — **OBSERVED** BOTH `from_checkpoint` (entries `Vec::new()`) at audit_chain.rs:170-177 AND `AuditChain::snapshot` (the test helper) at :227-228). The durable-through seq advances only on a contiguous-prefix write+sync; the chain poisons on failure. **Round 6 (C-A1) — poison attribution:** a poison is set ONLY by a durability failure attributed to a specific append (the synchronous barrier/append path — the caller learns the id); a BACKGROUND-flusher failure (audit_appender.rs:346/:349 drops errors today) is NOT a poison — the batched flusher must RETAIN the failed batch in the buffer (fixing the take-before-write loss at audit_appender.rs:469) and mark the sink degraded; the next successful flush of the retained batch advances the watermark; if it cannot be re-flushed, the NEXT attributed barrier append fails and poisons normally. When the barrier's batch flush fails, ALL co-batched entries' seqs stay unadvanced in the watermark (contiguous-prefix rule only); their owners learn via their own ack paths; no per-entry action is required. A poison that survives reconciliation retries surfaces as `AuditSinkError::Poisoned` on every append and requires operator/ops action — never silent clearing. **Round 6 (C3):** the poison has an EXACT unpoison path — a poisoned chain admits exactly ONE append class, the reconciliation RE-WRITE of the failed event id (poison check bypassed for that single event id, tracked by the chain), and unpoisons upon that entry's own successful `write_all` + `sync_all`; any other append during poison returns `AuditSinkError::Poisoned`; poison is never silently cleared (fail-closed: either the entry is re-written durably or the sink stays poisoned). Chain duplicates are bounded — at most one per ambiguous append — acceptable and documented; the journal, not the chain, is the recovery authority (I10). No dedup index is added to the chain format.
9. **Batched-mode flush-before-return cost:** the barrier call force-flushes the shared audit buffer; a bursty deployment could see latency spikes at Prepare. Acceptable (Prepare is rare, correctness-critical); document the latency characteristic in the audit ops notes.
