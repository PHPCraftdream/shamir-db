## 1. Goal and non-goals

**Goal.** Give quarantined replication destinations a safe, crash-recoverable, source-independent exit: explicit physical destruction of a destination's storage, release of its reserved name, and removal of the (otherwise immortal) subscription row — without ever serving destroyed or half-destroyed data, and without ever deleting anything but the frozen target set.

**DECIDED — authority staging (stated once here, applied everywhere).**

- **Stage 1 (PRs 8b-3a..3c)** introduces storage-object ids + ownership descriptors, backend lifecycle contract, destruction journal, reservations, admission guard, DDL/error surface, audit barrier/outbox and creation exclusion. Incident authority remains the merged #188 terminal/quarantined subscription-row coverage. R1-stage-1 requires destination absence.
- **Stage 2 (8b-3d)** moves incident authority to the **incarnation**: a catalogue incident record (`destination_incidents`) plus repository-carried versioned consistency evidence (`MetaKey::ConsistencyIncidents`); subscriptions are reduced to provenance. R1-stage-2 (subscription deletion) then proceeds by the **ordered incident handoff** (§4c) and no longer depends on destination absence; R1-stage-1 collapses into ordinary destruction completion.
- **Permanent from stage 1:** storage-object id format, ownership descriptor format, destruction journal schema + location, reservation semantics, NamespaceAdmission guard, backend lifecycle contract, the eleven typed lifecycle error codes (the eleven-row table already includes `destruction_target_changed`), the DDL surface, the v2 canonical confirmation encoding, the audit outbox semantics. **Deliberately replaceable:** the R1-stage-1 absence precondition (relaxed in 8b-3d by the incident handoff); quarantine coverage derivation from subscription rows; the journal's `incident_ref` starts empty and is filled by 8b-3d. **No throwaway work:** every stage-1 artefact is consumed unchanged by stage 2 — descriptors become the incarnation's component list, reservations become incident-derived, and the executor/boot-replay/audit-outbox machinery is identical in both stages.

**DECIDED — what stage 1 makes permanent vs what stage 2 replaces (the F2 table).**

| Row | Stage 1 (8b-3a..3c) | Stage 2 (8b-3d) | Permanence |
|---|---|---|---|
| Incident authority | Terminal/quarantined subscription-row coverage (merged #188, **OBSERVED** derived from terminal rows in `repl_binding/coverage.rs`) | `destination_incidents` row **and/or** repo-carried `MetaKey::ConsistencyIncidents`; subscription row is provenance | Stage-2 form permanent |
| Reservation source | Anchor coverage + non-`Destroyed` operation targets | Same union, anchor contribution derived from incidents (unresolved incident ⇒ its cause still reserves) | Source list permanent; anchor entry re-derived |
| R1 precondition | Every bound destination absent, pending work resolved, lease drained (§4b) | Ordered handoff (§4c): incident durable → lease drained → row delete → reservation release; absence not required | Stage-2 protocol permanent |
| Journal `incident_refs` | `Vec<IncidentRef>`, always empty | Refs (`cause {subscription, generation}`, `storage_object_id`, `incident_id`) of the causes the destruction resolves | Field permanent, populated in stage 2 |
| Coverage derivation | Boot rebuild from terminal subscription rows (core.rs:624 routine) | Boot rebuild from terminal rows **and** incident rows **and** repo-carried evidence; either unresolved copy blocks | Union permanent |

**Non-goals (this series).**

- Identity-preserving RENAME of replication destinations; splitting source coordinates from destination identity. That is the PR8b-4 series (§12 in the evidence file). R3 stays a restriction; the `replication_destination_bound` message must say the restriction is a **format limitation**, not permanent.
- Ordinary (non-destructive) DROP/RENAME becoming crash-atomic catalogue transactions. Ordinary DROP/RENAME must respect reservations and storage ownership, but a full atomic-DDL rewrite is out of scope.
- In-place reseeding and multi-target seed recovery are out of scope. **DECIDED (A12, Windows):** Windows reseed is REFUSED before any install mutation in this series and is certified on Windows CI (case 15); Windows destruction and name release ARE required and supported. "Windows seed install" is recorded as a MANDATORY END-STATE FOLLOW-UP entry, not a permanent product limitation.
- In-place replacement of a destroyed destination's storage into the CURRENT incarnation. **DECIDED:** this series supports exactly ONE recovery path — destroy (R2') → R1 → fresh install into the ABSENT target as a NEW incarnation (surface file §8); in-place replacement is listed as a follow-up.
- Online migration; enterprise/tamper-evident audit subsystems.

## 2. Invariants

Numbered, each independently testable (CI assertions in the evidence file §9; stage attribution there too).

1. **I1 — Protection outlives configuration deletion.** A destination whose consistency is unresolved stays protected (unreadable, unreservable, uncreatable-over) until its data is durably destroyed or a validated recovery clears quarantine. Deleting a subscription row never by itself clears protection — in stage 2 the row delete is preceded by a durable incident write precisely so this holds (§4c).
2. **I2 — Authorization precedes destruction and outlives partial action.** No destructive step runs before (a) a `Prepared` destruction record (operation id, frozen target set, storage-object ids + component descriptors, actor, reason, nonce) is persisted **and flushed**, and (b) the `destruction_prepared` audit event is durably appended (§3e) through the `AuditSink` seam (**DECIDED**: a small trait in `shamir-db`, surface A.7b, implemented by the server over its batched appender; the appender exposes a REAL durability watermark advanced only by a successful write+sync of a contiguous prefix). **DECIDED:** an audit failure at the barrier NEVER leads to `Rejected` by inference — the strict append is `write_all` + `flush` + `sync_all` (**OBSERVED** `crates/shamir-server/src/security/observability/logging/audit_appender.rs:499-519` `append_strict`), so a failed final sync does NOT prove the write is absent. The operation STAYS `Prepared` with reservations PUBLISHED (a non-terminal row always reserves — published with the Prepare write at (i), before the barrier) and nothing deleted; the caller receives the NEW retryable wire code `destruction_audit_unavailable` (surface §6c), and the SAME event id is retried per the §3e reconciliation-read rule. The intent (journal + audit chain) remains the recovery authority across every crash, cancellation and restart, until the record reaches `Destroyed` or `Blocked`.
3. **I3 — Boot loads intents before any repository loader.** `ShamirDb::init` reads (a) all non-`Destroyed`/non-`Rejected` rows AND (b) ANY row with NON-EMPTY `audit_pending` (ANY state, incl. `Destroyed`, for outbox replay) — clause (b) is KIND-SCOPED per §4d step 1: `SubscriptionRemoval` records load for the §4c/K3 phase-based resume, never for a 4b audit-barrier resume (their `audit_pending` is empty by construction) — from `destruction_operations` BEFORE the repository-open loop; a target covered by an open operation is never opened, recovered, or published.
4. **I4 — Reserved names reject creation on every publication path.** Reservation sources include terminal/quarantined anchors, nonterminal `Repo|Database` operations, and `Destroyed` operations with nonempty audit outbox. All publication paths enforce reservations. **DECIDED:** the 8b-3c installer boundary requires a new authority-only reader, not reordered `init_seed` or `ShamirDb::init`; the concrete contract and fail-closed rules are normative in surface §8b. It runs after exclusive maintenance-lock acquisition and before `find_complete`, and the lock remains held through install. Refuse nonterminal destruction before any candidate open/mutation, including rebind and install without optional subscription. The authoritative control-locked recheck at catalogue.rs:161 uses the same predicates and typed refusal mapping. The full wrapper/preflight remains 8b-3e. **DECIDED (A14 — staging gate):** the 8b-3b executor and `DestructionAuthority` are `pub(crate)` and NOT dispatchable from wire or admin; destructive dispatch becomes reachable only in 8b-3c, together with all publisher wiring. This is an ACCEPTANCE CRITERION of 8b-3b and of 8b-3c.
5. **I5 — Destruction is complete and verified.** Completion requires every component in the ownership descriptor (repository store, interner/meta, transaction state, changelog, identity/bookmarks, seed receipts, the **sibling `.shamirwal` WAL directory and its segments**, persistent tiers of cache/hybrid backends, seed staging remnants per surface-file §8) to be destroyed and verified absent.
6. **I6 — Retry never deletes anything but the frozen target set.** All destructive work is bound to storage_object_id + recorded descriptors, never to "whatever occupies the name now". A retry against a live replacement is an error (`unsafe_storage_ownership`), never a deletion.
7. **I7 — No control lock across slow deletion.** The replication control lock is held only for short critical sections (§4e lock order): validation, reservation publication, state transitions, the final destructive catalogue write. Component destruction runs under a per-operation executor token plus per-target lifecycle exclusion. **DECIDED (A6):** a task is never joined while control is held — the targeted drain releases control before joins (§4a step 2).
8. **I8 — R1 never orphans protection.** R1-stage-1 permits DROP SUBSCRIPTION of an anchor only when **every** bound destination is absent and no incomplete operation covers any of them. R1-stage-2 permits it only after every bound destination's incident evidence is durably handed off (§4c), **and no unresolved pending terminal cause for any referencing generation**. The deletion itself NEVER resolves an incident — only validated recovery (the §3d predicate) or destruction completion does. In both stages the union of protections is non-increasing until the handoff/destruction completes.
9. **I9 — Destination-by-destination and cause-by-cause.** Multi-destination subscriptions are destroyed destination by destination; there is no implicit graph-wide destruction, and surviving destinations keep their protection. Incident causes are independent: one incident per (cause, storage_object_id); clearing a cause clears exactly that cause's copies.
10. **I10 — Audit is a barrier at Prepare, an in-record outbox afterwards; the journal is authority.** The `Prepared` transition requires a durable audit append (I2). Later transitions enqueue their audit event INTO THE OPERATION RECORD in the SAME durable CAS write as the state change (§3e); an un-drained `audit_pending` only withholds retirement of the operation and the lapse of the reservations it anchors — it never rolls back a transition.
11. **I11 — Only validated recovery or destruction completion clears quarantine on surviving data.** Operator acknowledgement, subscription deletion, rename, and destruction of a *sibling* destination never clear quarantine on a surviving incarnation; only a replacement verified against the incident's recorded baseline (§3d predicate) or destruction completion resolves an incident (stage 2: the handoff writes the incident BEFORE the row delete, so deletion is provably never the cure).
12. **I12 — No clean checkpoint required.** Destruction never requires successfully checkpointing or opening corrupt data; it requires workers stopped and handles closed.
13. **I13 — Admission closes the check-vs-publish race.** Every publication path takes the admission guard for its (db, repo) namespace before validation and holds it until publication or abort (RAII; cancellation-safe; no durable trace); the per-target lifecycle exclusion is the SAME merged guard object (§4e; surface file §7a). **DECIDED:** 8b-3b delivers and tests only the admission-registry/control primitive and destruction-side reservation publication; 8b-3c wires every real publisher and tests publisher-versus-reservation races end to end (surface §7b; evidence §10). No composed-path guarantee applies before 8b-3c. The installer early authority check is separate (surface §8b); 8b-3e adds its outer wrapper. I13's control-lock serialization applies to reservation mutations and live publication check/use paths. The installer precheck is read-only (no reservation mutation), so it uses no replication-control lock and relies instead on the existing exclusive instance maintenance lock, held through install; without that exclusion it would be only an optimistic read and insufficient. The authoritative `install_seed_subscription` re-check at catalogue.rs:161 remains under control and uses the same predicates and typed refusal mapping. (`remove_db` db_management.rs:87, `remove_repo` :553, `rename_db_as` :165, `rename_repo_as` :622, DROP DB/REPO handlers admin_db_repo.rs:118/:433, every subscription/profile/publication handler admin_replication.rs:65/:132/:170/:245/:295/:400/:454, `install_seed_subscription` execute/replication_seed/catalogue.rs:161, `mark_subscription_terminal_generation` quarantine_helpers/admin_replication.rs:121) — so the control lock is the single serializer of the reservation set: a publisher's check and a reservation's publication cannot interleave. **EXCEPTION — creation:** the premise "control first on every lifecycle mutation path" is FALSE for creation in merged code — `create_db_as` (db_management.rs:50-80) and the generic `add_repo_as` path take NO control today. The design ADDS the short control section around reservation check, mirror write and registry/catalogue publication on CREATE paths. Mirror writes land in 8b-3a; 8b-3b supplies only the reservation/control primitive; 8b-3c wires and tests the real CREATE check-through-publication path. The section is held THROUGH publication, so `dbs.insert`/`repos.insert` runs inside it; **DECIDED:** the check-to-publish window is closed by holding through publication, not merely check (surface §7b rows 1-2 and 7). **DECIDED:** the db-level gate is acquired ONCE, up front, in its FINAL mode and held to the end — never upgraded shared → exclusive, never released/reacquired while repository mutexes are held (§4e).
14. **I14 — Unknown is not success.** Ambiguous I/O (a write/flush that errored but may be durable) is reconciled by re-reading durable state; until reconciled, conservative fencing (reservations + fail-closed reads for the target) stays in force. A failed acknowledgement is never a rollback (§4f).

### 3a. Storage-object id + ownership descriptor

**DECIDED.**

- New per-repository durable meta record `MetaKey::StorageOwnership` in the repo info store, codec versioned like the `MetaEnvelope` usage in `crates/shamir-engine/src/repo/meta/repo_identity.rs:79-117` (the type is defined in `crate::meta`; the cite demonstrates the versioned-codec usage; version 1; **DECIDED (DEC-3 item 1, A11): ownership is minted ONLY on the controlled creation path and published durably BEFORE the repository is exposed — never minted lazily. A missing or corrupt record at open gives `unsafe_storage_ownership` and refuses opening (and deletion); it is never minted on demand at open, during destruction, or anywhere else.**).
  Format v1: `{ storage_object_id: [u8;16], durable: bool, components: Vec<ComponentDescriptor>, created_at: u64, format_version: u16 }` where `ComponentDescriptor = { component_id: u32, kind: ComponentKind, path: Option<PathBuf>, bytes_repr: Option<String> }`; `component_id` is stable per descriptor (assigned once at descriptor creation, never renumbered) and is what `destruction_blocked` diagnostics and the record's `blocked_component` reference — **DECIDED** (an index into the frozen `components` vector is not stable across retry-time re-derivation, so the id lives in the descriptor). `ComponentKind` enumerates: PrimaryStore, Interner, Meta, TransactionState, Changelog, IdentityBookmarks, SeedReceipts, Wal{dir, segments}, CacheTier, HybridDurableTier, MemoryInstance, SeedStagingDir, SeedInstallMarker, SeedReceiptStore (the last three per surface-file §8; all seed remnants of a seeded target are owned components).
- **Mirror:** the system-catalogue `repositories` row carries the FULL descriptor — `storage_object_id: [u8;16]`, `ownership_digest: [u8;32]` (hash of the descriptor) AND the full `components: Vec<ComponentDescriptor>` list (**DECIDED:** the catalogue mirror is a complete copy of the descriptor, not only id + digest, so a repo that CANNOT be opened can still be inspected from the catalogue row). On open, record vs row disagreement fails closed with `unsafe_storage_ownership`. This catches catalogue/live aliasing (RENAME keeps the old directory while CREATE derives paths from names — **OBSERVED** admin_db_repo.rs:314, :339 `create_dir_all` from name-derived dirs; db_management.rs rename re-keys rows best-effort; **INFERRED**: without the mirror, a renamed-then-recreated repo is indistinguishable from the old storage). **DECIDED:** mirror writes on the open/admission path PROPAGATE ERRORS (never warn-only) from 8b-3a onward — a best-effort write plus a fail-closed disagreement check would make a transient write failure permanently unopenable; mirror-write errors and record/mirror disagreement fail closed exactly as before. **EXACTLY ONE OWNERSHIP RULE (DEC-3 item 1, A11 — superseding any earlier mirror-authorizes-deletion exception):** a missing or corrupt `StorageOwnership` RECORD yields `unsafe_storage_ownership` and refuses BOTH opening AND deletion — the catalogue mirror never authorizes destruction of a repository whose ownership record cannot be read; the name stays reserved by any anchor pending operator investigation. Boot skip-and-fences: a repo covered by an anchor/open operation that FAILS TO OPEN is skipped and fenced (fail-closed quarantined, catalogued-only) instead of aborting `ShamirDb::init` — the boot repository loop (core.rs:361-411, `seed_boot_gate` :396, publication :409) currently opens with `?`; 8b-3a changes the anchor/operation-covered branch to log + fence + continue. **DECIDED:** 8b-3a lands the skip-and-fence as a STRUCTURAL HOOK in the boot loop — an EMPTY reservation-view consult, inert until 8b-3b wires the view (least churn; the change is not deferred to 8b-3b). Acceptance criterion: the hook exists AND a unit test drives it with a SYNTHETIC non-empty view.
- **Pre-8b-3a data directories — DECIDED (A3):** refused with a typed `storage_format_unsupported` error. There is NO legacy backfill, NO grandfathering, and NO migration path for data directories created before 8b-3a; the product is unreleased and the owner standard accepts the break.
- `durable:false` for `in_memory`: id minted per boot, recorded only in the catalogue row; no on-disk components exist and no fs absence proof is possible. **DECIDED:** the storage-object id must NOT reuse `RepoIdentity::lineage_id`: **OBSERVED** repo_identity.rs:24-34 — `in_memory` AND `hybrid` keep `__tx__` in RAM only, so every process start mints a new lineage at epoch 0 by design; a hybrid's lineage_id is unstable across boots and would make journal/destruction identity meaningless. **DECIDED (DEC-3 item 1, A11): hybrid writes `StorageOwnership` into its durable fjall metadata/interner tier. STORAGE OWNERSHIP IS DISTINCT FROM REPLICATION LINEAGE, which stays per-boot for hybrid** (open risk in §11 of the evidence file).
- Writers: minting happens ONLY on the controlled CREATION path — the creation/admission path mints the `StorageOwnership` record and publishes it durably BEFORE the repository is exposed (§3a, A11). OPENING EXISTING STORAGE NEVER MINTS: the open/admission path only READS and VALIDATES the record (a missing or corrupt record at open is `unsafe_storage_ownership`, never a lazy mint). The other writers are the destruction executor (record retirement) and boot replay (which writes retirement/clears only, never a fresh mint). Nobody else may mutate.

### 3b. Destruction operation record

**DECIDED.** New system-catalogue table `destruction_operations` (a new table on the `SYSTEM_REPO` Fjall system repo, alongside `subscriptions` — **OBSERVED** system_store/store.rs:55 `TABLE_SUBSCRIPTIONS` (comment :52-54), table registration at store.rs:103-119), keyed by `operation_id` (caller-generated string, bounds and reuse rules in §4f / surface-file Appendix A).                                         //   removed from audit_pending; advanced by the AuditBookkeeper in the

                                        //   { event_id: {operation_id, transition_ordinal}, kind,
                                        //     payload_digest, audit_seq: Option<u64>,

                                        //   audit_seq ≤ ack_watermark are removed by the AuditBookkeeper

                                        //   append_attempts is the DURABLE DUPLICATE BUDGET — incremented inside
                                        //   the SAME commit_durable transaction that precedes each re-write
                                        //   (§3e item 6b); duplicates of an event ≤ append_attempts - 1;

  audit_next_ordinal: u32,              // DURABLE monotonic transition-ordinal counter (initial 1); incremented

                                        //   practically unreachable); ordinals START AT 1, never 0

                                        //   the winner becomes the executor for this epoch. The CAS is CONDITIONAL

                                        //   of the executor task is IMMEDIATELY ADJACENT to the successful CAS (no

Field additions and why — **DECIDED**:

- `targets[].subscription_anchors` carries **generations**, not just names: anchor coverage and incident attribution are generation-scoped (surface-file §8 pending-cause model, `MetaKey`-level attribution); a name alone cannot distinguish a replaced binding.
- `audit_pending` implements the **in-record outbox** (§3e): each transition enqueues its audit event INTO the operation record in the SAME durable CAS write as the state change; an append success writes the chain seq into the pending entry (diagnostic); the `AuditBookkeeper` REMOVES entries whose `audit_seq ≤ ack_watermark` (one durable CAS batch per checkpoint, §3e step 5). The row-level `audit_seq_emitted`/`audit_seq_acked` fields are DROPPED. Boot/recovery selects replay work by NON-EMPTY `audit_pending` (never by seq comparison), and retirement requires `state = Destroyed` AND empty `audit_pending`.
- `record_version` is the optimistic-concurrency token for executor self-replacement after crash. It is NOT part of the audit event id — `event_id = (operation_id, transition_ordinal)`, independent of `record_version` (§3e). **DECIDED:** the claim/heartbeat protocol is `executor_epoch`: every claim path (same-id submission of an authorized stranded `Prepared`, `destruction_retry`, periodic pass, boot, **and the INITIAL executor spawn: the spawning request performs the CAS; a loser returns the current status and does not spawn**) performs ONE CAS `(record_version, executor_epoch): (v, e) → (v+1, e+1)`; the winner runs the operation for that epoch, losers receive the current status instead of blocking; the checkpoint hook delivers the ack watermark to the **`AuditBookkeeper`** (§3e step 5) — which, BESIDES the executors, is the only writer of an operation row, RESTRICTED TO THE AUDIT FIELDS (`audit_pending`, `audit_acked_ordinal`, `audit_next_ordinal`); the operation token excludes executors from each other, NOT the bookkeeper. The claim CAS is CONDITIONAL on the claimer's OBSERVED `(v, e)` (a compare-and-swap on the full pair — a stale observer loses); the spawn of the executor task is IMMEDIATELY ADJACENT to the successful CAS (no await point between); and the executor RE-CHECKS `executor_epoch` currency (a cheap read) before EACH destructive durable step and aborts to status if superseded. **The operation token provides exclusion; epochs only detect stale work (A5).**
- `Rejected` is a **terminal** state reserved for DEFINITIVE PRE-WRITE REFUSALS (authorization, validation, reservation conflict) BEFORE any audit append and BEFORE any Prepare write. No reservation is ever published for a `Rejected` row, no destructive step ever ran, and the only audit event is `destruction_rejected` (best-effort, exempt from the retirement gate). **DECIDED:** that event is written best-effort DIRECTLY — it is NEVER enqueued in `audit_pending`, which stays EMPTY for a `Rejected` row (the enqueued-then-exempt contradiction is removed). **An audit failure at the barrier does NOT produce `Rejected`** — the operation stays `Prepared` (I2). **DECIDED:** `Rejected` rows NEVER reserve, at boot or at runtime (§3c member (ii) excludes them; §4d step 1 loading excludes them); `Rejected` is INSERT-IF-ABSENT only — a `Rejected` row is never written over a live row of the same id (§4f).
- **DECIDED (A4):** `Blocked(Phase::Prepare)` is UNREACHABLE: backend support (the `DestructibleBackend` capability and per-component destructibility) is determined at PREFLIGHT, and an unsupported backend is refused there with `storage_destruction_unsupported` — it never becomes a row of any kind. `error_class = UnsupportedBackend` does not exist on the operation row: the row's `ErrorClass` enum is `ExternalLock | PermissionDenied | OwnershipMismatch | UnknownIo | AuditUnavailable` ONLY (the unreachable `UnsupportedBackend` variant is deleted, not kept for schema stability; `AuditUnavailable` is the cap-exhaustion/audit-parking class, §3e item 6b).

State meanings and durability rules — **every transition persists the new row and flushes before the next step starts** (every multi-record transition through `SystemStore::commit_durable`, §3e):

| State | Meaning | Durability rule |
|---|---|---|
| `Prepared` | Authorized — DEFINED AS: the durable authorization transaction committed (challenge DELETE-IF-MATCHES consumed + `Prepared` PUT-IF-ABSENT succeeded, A1); targets, ids, descriptors frozen; reservations published. | `Quiescing` | Admission closed, leases drained, workers/followers stopping. | Persisted on entry, with the `destruction_quiesced` event enqueued in the SAME write; re-entering is idempotent. |

NEVER via `AuditChain::snapshot` (an in-memory test helper: the chain stores the entry in memory BEFORE the appender call, and a restart starts with an EMPTY in-memory vector — **OBSERVED** BOTH `from_checkpoint` (entries `Vec::new()`) at audit_chain.rs:170-177 AND `AuditChain::snapshot` (the test helper) at :227-228 — a memory match is neither durable evidence nor available after restart). **Restart case:** after a crash the executor holds no memory of (a); it uses (b) by re-appending the pending entry (idempotent by event id) or (c) by reading the persisted `checkpoint_durable` ack record (which survives in the checkpoint keyspace) — never by trusting the log tail alone. After an AMBIGUOUS append (an error whose durability is unknown — including a failed final sync) the executor therefore RE-WRITES the entry: the reconciliation append is a FRESH successful `write_all` + `sync_all` of that line (never "the old sync error is now proof", and never "another fsync made the found line durable"); the duplicate is benign and bounded. **The journal, not the chain, is the recovery authority** (I10). **DECIDED (A9) — the log contract:** the event id `(operation_id, transition_ordinal)` is BOUND to a SHA-256 of the canonical payload; the SAME id with a DIFFERENT digest is CORRUPTION: poison PLUS incident, NEVER dedup. The record framing is defined: each record carries LENGTH + CHECKSUM. On open, the sink TRUNCATES an incomplete or bad-checksum FINAL record before any append; a corrupt MIDDLE record fails closed (poisoned chain). EXACTLY ONE serialized writer with SAME-EVENT COALESCING. AT MOST ONE DUPLICATE per CLASSIFIED-AMBIGUOUS OUTCOME, bounded in total by the attempt cap (item 6b). "Found after restart" is NEVER proof.
6b. **Single serialized sink writer, same-event coalescing, ambiguous/timed-out append ownership, durable duplicate budget, bounded-join failure — DECIDED (A9, closes the DEC-3 audit-sink gaps).**
   - **ONE SERIALIZED WRITER.** All `append_durable` calls for destruction-lifecycle events are serialized through ONE writer task/queue OWNED BY THE LIFECYCLE MODULE (executors and boot replay SUBMIT to that queue; they never call the sink directly). No other caller submits lifecycle appends concurrently — independent executors, the periodic recovery pass and boot replay all funnel through the same queue, so two submitters can never race the same event id into two log records.
   - **SAME-EVENT COALESCING (in-flight table).** The serialized writer keeps an IN-FLIGHT TABLE `event_id -> shared completion`. A second submission of an event id that is IN FLIGHT JOINS that shared completion — NO second append is issued — and receives the SAME result (the same ack, or the same failure classification) as the original submission. After an `Acked` completion, a LATER submission of the same event id returns the result VARIANT `AlreadyAcknowledged` WITHOUT appending — explicitly NOT a reconstructed `DurableAck` (no `seq`/`checkpoint_position` recovery from an ordinal; §3e step 5): the durable source is the operation row itself — an event id `(operation_id, k)` with `k ≤ audit_acked_ordinal` is ACKNOWLEDGED (its entry was removed by the `AuditBookkeeper`, §3e step 5, which advanced the ordinal in the same write), an event id still present in `audit_pending` is coalesced / replayed under the budget below, and an id above both is a new event. **Post-append / pre-checkpoint interval — DECIDED:** after a SUCCESSFUL append (proof (a)) the writer RETAINS the completion in its table in the state `Appended{audit_seq}` until the bookkeeper's acknowledgement write supersedes it (`audit_acked_ordinal` then covers the ordinal); a submission for an event id in `Appended` returns the retained `Appended{audit_seq}` result WITHOUT appending. The queue's result type is distinct from the sink's `DurableAck`: `InFlight` -> `Appended{audit_seq}` (in-process, volatile) -> `AlreadyAcknowledged` (durable, ordinal covered). After a PROCESS RESTART the volatile state is gone and an unacknowledged pending entry is classified AMBIGUOUS by the closed durability-proof rule (the executor holds no memory of proof (a)) — the only case where a duplicate follows an in-reality-successful append, bounded by the attempt cap. Serialization alone does not prevent two records for one event id; the coalescing table is the mechanism that does. A duplicate record can therefore arise ONLY from a re-write after a CLASSIFIED-AMBIGUOUS outcome (a failed or timed-out append, or a crash before an acknowledgement is recorded).
   - **OWNERSHIP OF AMBIGUOUS/TIMED-OUT APPENDS.** A `spawn_blocking` append that TIMES OUT (A10) is NOT abandoned: the lifecycle writer RETAINS OWNERSHIP of that event id, WAITS for the blocking task to actually complete (bounded join), and only then classifies the outcome — acked / failed-not-durable / unknown → the RECONCILIATION RE-WRITE of item 6. NO further append for that event id and NO new event is submitted while an earlier append is in flight or unreconciled — the queue blocks until the in-flight append resolves (a poison set by the failed append enforces the same rule at the sink level, item 0b).
   - **BOUNDED-JOIN FAILURE → `Parked` (DECIDED).** If the BOUNDED JOIN of a timed-out blocking append ALSO times out, the sink writer enters the `Parked` state: it accepts NO further appends for ANY event (not only the stuck event id), and NEW requests FAIL FAST with the bounded wire error `destruction_audit_unavailable` — the caller NEVER waits on the still-running blocking task (the blocking task's ownership of the thread is not the caller's concern; the client-visible response is the immediate typed error, never an unbounded wait). The writer RETAINS the blocking-task handle and RE-POLLS it NON-BLOCKINGLY on an interval; on completion it classifies the outcome per the rules above (acked / failed / unknown → reconciliation re-write) and RESUMES normal operation (the `Parked` state lifts; queued submissions then proceed, still subject to the coalescing table and the attempt budget). A process RESTART treats the in-flight append as AMBIGUOUS, and boot replay applies the same coalescing + budget rules (below) to it. Operation rows stay `Prepared`/`Blocked` exactly as the §4b state machine already says — the `Parked` state is a SINK-WRITER state, never a new operation-row state.
   - **DURABLE DUPLICATE BUDGET (DEC-3: `dec3-owner-rulings-2026-10-21.md:175`, restated).** Every `audit_pending` entry carries `append_attempts: u8` (§3b), STARTING AT 1 (the original append is attempt 1, accounted when the entry is created in the transition's own CAS — no extra transaction before the original append). Before each RECONCILIATION RE-WRITE (or boot replay of a pending entry) the executor increments `append_attempts` INSIDE THE SAME `SystemStore::commit_durable` transaction that precedes the re-write — the budget is durable, so it survives crashes and restarts (no silent retry loop across boots). The number of duplicates of an event is at most `append_attempts - 1`. `MAX_APPEND_ATTEMPTS = 3`: a re-write is permitted only while `append_attempts < cap`, where `cap = (1 + append_budget_extensions) * MAX_APPEND_ATTEMPTS` (initially 3: attempts 2 and 3 are the permitted re-writes and the increment to 4 never happens without an audited extension; after k extensions the cap is `(1 + k) * 3` and the counter simply continues from its current value); when a further classified-ambiguous outcome occurs at `append_attempts = cap` the operation PARKS as `Blocked` with `error_class = AuditUnavailable` (wire code `destruction_audit_unavailable`, S §6c) and `failed_phase` = the CURRENT phase (per §3b) until an operator acts — NO further appends are attempted and there is NO silent retry loop. **DECIDED (P1-2) — operator recovery is the audited `destruction_retry` carrying an explicit BUDGET EXTENSION:** each extension adds `MAX_APPEND_ATTEMPTS` to the row's cap via the NEW durable field `append_budget_extensions: u8` (§3b; recorded as an audited operator act), so the stated bound becomes **`duplicates <= (1 + extensions) * MAX_APPEND_ATTEMPTS - 1`**; `append_budget_extensions` is capped at 10 (checked arithmetic, the 11th extension is refused), so the cap is at most 33 and `append_attempts: u8` cannot overflow. Before extending, the retry FIRST runs the read-only (c)-proof: a covering `checkpoint_durable` ack watermark (`audit_seq ≤ ack_watermark`) resolves the entry WITHOUT any append. The duplicate guarantee is therefore: AT MOST ONE DUPLICATE PER CLASSIFIED-AMBIGUOUS OUTCOME, BOUNDED IN TOTAL BY `(1 + extensions) * MAX_APPEND_ATTEMPTS` (previously stated as "at most one duplicate per ambiguous append").
7. **Replay and retirement.** Boot/recovery selects operations by NON-EMPTY `audit_pending` (ANY state, incl. `Destroyed`) — NEVER by seq comparison — and replays every pending entry in `transition_ordinal` order, idempotently (same event id; item 6 governs duplicates). Retirement — **DECIDED, the predicate is PER-KIND.** A `kind: Repo | Database` record (and its name reservations) is retired ONLY when `state = Destroyed` (event kind `destroyed`) AND `audit_pending` is empty (the `Rejected` row's best-effort event is exempt). A `kind: SubscriptionRemoval` record is retired when its `phase: Completed` is reached (no `audit_pending` by construction — the record emits no audit events). **DECIDED (A2, DEC-3 item 7) — archival NEVER releases protection:** the owner-approved `destruction_archive` act is eligible ONLY for `kind: Repo | Database` rows with `state = Destroyed` AND fully acked, and for `SubscriptionRemoval` records with `phase = Completed`. A live row whose generation ≠ the record's means a recovery LANDED: the executor marks the record `Completed` WITHOUT deleting (the transaction's delete matches nothing) and releases ONLY its own generation's claims. The 8b-3c change to the merged handler: the `DeleteOp` at admin_replication.rs:420-428 gains the `binding_generation` `Eq` filter, taken from the record (first submission: from the live row's generation at record-persist time), and the delete runs inside the same transaction as the `phase = RowDeleted` write. Source availability is NOT required at any step (upstream may be gone — `validate_seed_resume`'s network probe, **OBSERVED** `crates/shamir-db/src/shamir_db/execute/replication_seed/control.rs:255` with `probe_seed_upstream` at :328, is never invoked on this path).

**Failed re-verification — DECIDED (amended by A2).** A resumed `RowDeleted` removal whose frozen-destination re-verification fails (a live NEW incarnation occupies a frozen name) sets `phase` unchanged (`RowDeleted`), `state = Blocked` with `error_class = OwnershipMismatch`, `blocked_component` unset, and `last_error` naming the live incarnation's `storage_object_id` — the operator investigates. **DECIDED (P1-3): there is NO remove-or-rename-the-squatter remedy.** Renaming or removing the new incarnation away from the frozen name proves NEITHER destruction of the found data NOR a durable transfer of its protection, and NEVER allows completion or reservation release. A blocked `RowDeleted` removal resolves ONLY through: (a) VERIFIED DESTRUCTION of the found incarnation — the found data is CONVERTED into an R2' destruction TARGET (`destruction_retry` re-runs the frozen-destination re-verification only after that destruction COMPLETED, `verify_absent` true), or (b) a DURABLE IDENTITY-BOUND PROTECTION HANDOFF — the found incarnation is recorded as an Unresolved INCIDENT (row + repo-carried copy, §3d) whose cause carries this binding's `(subscription, generation)`; after the incident is durably in place the record's causes are cured for THIS generation and `destruction_retry`/completion proceeds — the found data stays protected by the incident. **What the MERGED DROP SUBSCRIPTION handler does today (OBSERVED, `crates/shamir-db/src/shamir_db/execute/admin_db/admin_replication.rs`):** `handle_drop_subscription` (:394) takes control (:400), refuses quarantined drops (`ensure_drop_allowed` :413), quiesces the lease (:417), deletes via `delete_repl` (:429 → :774-803, `Ok(result.affected > 0)` at :802) and returns `{ "dropped_subscription", "existed": bool }` (:436-440) — **a missing row returns `existed: false` as a SILENT NO-OP** (the delete matches nothing, `affected == 0`, no error). The exact 8b-3c change: route the handler through the operation record — BEFORE `delete_repl`, look up `SubscriptionRemoval` by `(name, generation)`; record found ⇒ resume from the recorded phase (row already deleted ⇒ skip to destination-absence re-verification and completion; the missing-row case must COMPLETE a resumed removal, never report the silent no-op); record absent ⇒ first submission, persist the `Pending` record, then the existing delete path. Consistent with id-lookup-before-challenge (§4a step 0) and the ≥1-referencing-row predicate (applies to FIRST submission only — a resumed removal revalidates against the RECORD because its referencing row is by then gone).

(b) the generation-fenced subscription delete + `phase = RowDeleted` in ONE `commit_durable` (§4c step 5, unchanged). (c) `RowDeleted -> Completed` after verifying DURABLE PROTECTION for every surviving destination — an `Unresolved` incident row or a covering destruction operation exists and reads back — instead of the stage-1 universal-absence predicate. Crash recovery for every durable prefix (each incident-copy prefix and each removal-record phase) is the stage-aware crash table above.** The ordered handoff is numbered (2a)-(2d) to keep it distinct from the transaction boundaries (a)-(c) above; boundary (a) persists ONLY the removal record, the permanent binding index and the frozen incident REFERENCES; (2a) is a SEPARATE durable step after it (idempotently persists and verifies the incident rows and the applicable repo-carried copies); (2c) is boundary (b); and the verification in (c) replaces the stage-1 absence check. **Protection predicate — ONE definition, used identically by (2a) completion, boundary (c), surface A.4 and CI case 10:** for each bound destination `d`, `protected(d)` holds iff (1) `d` is ABSENT with a COMPLETED covering destruction operation, OR (2) the catalogue incident row for `d` (variant `Known` for a live or catalogued destination, `UnresolvedProvenance` for an absent never-destroyed one) reads back AND — only when `d` is LIVE AND OPENABLE — the repo-carried copy also reads back. Each step with its crash behaviour:

- **(2a) Write the incident record durably and VERIFY the write.** For every bound destination: upsert the `destination_incidents` row for `(cause, storage_object_id)` (state `Unresolved`, reusing the existing incident id for the same cause pair — idempotent) for every bound destination that is STILL LIVE or CATALOGUED at the time of removal — **DECIDED:** for an ABSENT destination whose covering destruction operation has COMPLETED, R1 records NOTHING and releases the reservation (the destruction already resolved that destination's incidents with `Resolved(by destruction)`, §4a step 6; upserting an incident for an absent destination would re-reserve a destroyed name and then refuse the fresh install); **for an ABSENT destination with NO covering destruction operation (never destroyed — provenance unknown):** R1 upserts the Unresolved incident row in the **`UnresolvedProvenance` variant (P1-4, §3d): key `(cause, destination_name, binding_generation)`, `storage_object_id: None`, no receipt/bookmark baseline, reserved BY NAME** (catalogue-only, no repo copy is possible) and the reservation REMAINS — an absent destination must never silently lose protection; the name is released only by a validated recovery (§3d predicate) or an explicit destruction (R2'); archival never releases protection (DEC-3 Q3 item 7). Write the repo-carried `MetaKey::ConsistencyIncidents` copy ONLY if the repo is openable (for an absent destination the catalogue row alone is authoritative and sufficient — surface A.4's degraded-copy rule is stated identically there); then VERIFY what was written: read back both copies and pass a flush barrier on each store. Crash after (2a) incomplete (row written, evidence write failed): retry is safe — the upsert is idempotent by cause pair and incident ids are **reused**; the row alone already quarantines (§3d boot derivation). Crash after (2a) complete: protection has moved to the incarnation; the subscription row is now redundant.
- **(2b) Invalidate + drain the subscription lease** (merged lease write gate; generation-scoped to this binding's generation).
- **(2c) Delete the subscription row + durability barrier** (flush system store). Crash after (2c): the quarantine union rebuild **no longer derives protection from the deleted row**; it derives it from `destination_incidents` + repo-carried evidence instead (exact boot derivation in §3d: unresolved incident row over a live storage_object_id quarantines reads; repo-carried unresolved evidence quarantines even without a catalogue row — either copy blocks). This is precisely why (2a) precedes (2c).
- **(2d) Release reservations for this binding** (in-memory; the incident-derived entries remain while incidents are unresolved; the reservation entries for ABSENT destinations with a completed destruction operation are released here — nothing was recorded for them in (2a)).

**Overlapping / multi-destination independence.** One incident per `(cause, storage_object_id)`; clearing a subscription clears only the incident whose `cause` is THAT `(subscription, generation)`; validated recovery clears exactly one incident **by incident id** and rewrites only that incident's copies (row + repo-carried record). A destination with two causes keeps the second incident after the first clears (I9, I11).

### 4d. Boot-time replay ordering

Exact insertion in `ShamirDb::init` (**OBSERVED** core.rs: control lock field :75, built :287, `lock_replication_control` :675 with lock acquisition :676; repository-open loop :361-411 with `seed_boot_gate` :396 and publication via `add_repo_with_durability` :409):

Selection is NEVER by seq comparison. **This loading clause is KIND-SCOPED: clause (a)/(b) loading for a 4b resume applies to `kind: Repo | Database` only; `kind: SubscriptionRemoval` records are loaded for the §4c phase-based resume (§4d step 5), never for a 4b audit-barrier resume.**
2. Publish targets **per §3c membership only** — (i) #188 anchor coverage, (ii) non-`Destroyed`/non-`Rejected` operations, (iii) `Destroyed` with unacked terminal event — stage 2: plus incident rows and repo-carried evidence per §3d — into the reservation view (§3c); (ii) excludes `Rejected`, so `Rejected` rows' targets are never published. **DECIDED: a boot-loaded `kind: SubscriptionRemoval` record in `phase: Pending | RowDeleted` PUBLISHES its frozen `destinations` into the reservation view for the duration of the resume — released at `Completed` (§4c failed-re-verification rule; surface Appendix B) — closing the window in which a publication could otherwise land on a frozen name while the record sits unloaded between boots.** Boot publishes reservations BEFORE the server accepts requests, while the admission registry is empty (no contention); post-boot the executor acquires admission locks normally (§7a of the surface file).
3. Run the audit-outbox boot replay for every pending entry in `transition_ordinal` order (§3e step 7); the `checkpoint_durable` hook subsequently hands the ack watermark to the `AuditBookkeeper`, which removes pending entries whose `audit_seq ≤ ack_watermark` (§3e step 5) — including from boot-loaded `Blocked`/`Destroyed` rows that have NO executor.
4. Repository loop (:361-411): skip any target covered by an open operation **fail-closed** — log, do not open, do not recover, do not publish; the `seed_boot_gate` check (:396) stays as-is for non-reserved targets.
5. `Blocked` rows are REPLAYED, NOT RESUMED: boot re-publishes their reservations (§4d step 2) and leaves the executor PARKED — no executor is spawned and no work is resumed automatically — until an explicit `destruction_retry` (or a same-id submission) claims the row. Continue-the-executor applies to `Quiescing`/`Destroying`/`Cataloguing` — **and `Prepared`** — resuming from the recorded state per 4b; run the outbox replay pass before retirement considerations. The PERIODIC recovery pass additionally claims `Prepared` rows older than 5 minutes (barrier stranded) and re-runs the barrier (§3e item 3) — it NEVER auto-resumes a `Blocked` row. The 4b-resume path is KIND-SCOPED to `kind: Repo | Database`; `kind: SubscriptionRemoval` records resume via the §4c phase-based path (their `audit_pending` is empty by construction — no audit-barrier re-run).
6. Quarantine-cache rebuild stays at the END, :624.

### 4f. Cancellation, duplicates, bounds

- The request handler **spawns the executor BEFORE returning the operation id immediately after Prepare** (so a cancelled future can never strand a successfully-prepared operation without an executor); the HTTP/wire future can be cancelled freely at any point. The executor task owns the work and is detached: when the caller's future is dropped, the executor continues to the next durable boundary. The INITIAL executor spawn passes through the SAME `(record_version, executor_epoch)` claim CAS as every other claim path (§3b) — the spawning request performs the CAS; if it LOSES, it returns the current status and does NOT spawn (the CAS is conditional on the observed `(v, e)`, the spawn is immediately adjacent to the successful CAS, and the executor re-checks epoch currency before each destructive durable step). External cancellation is implicit: when a caller's future is dropped the executor continues to the next durable boundary; there is no admin-cancel API in this series (`destruction_retry` refuses terminal rows (`Destroyed` → status; `Rejected` → a new operation is required) and concurrent re-execution, per surface-file Appendix B; it does not cancel). **DECIDED:** `destruction_retry` also accepts an authorized stranded `Prepared` row (barrier failed): it re-runs the audit barrier (idempotent by event id) and spawns the executor; a same-id submission does the same (§3e item 3). It CANNOT create authorization: a row exists only if the original challenge DELETE + PUT-IF-ABSENT transaction succeeded (A1).
- Ambiguous I/O per I14 (§4b). Audit failure per §3e (withholds retirement, never rolls back).
- Duplicate submit — **DECIDED:** the `operation_id` lookup happens BEFORE the challenge/digest check (§4a step 0). Same operation id + identical frozen parameters (targets, kind, actor, reason, nonce — challenge/digest EXCLUDED from the comparison) → return the current status (idempotent; an authorized stranded `Prepared` is claimed per §3e item 3); same id with different parameters → `destruction_operation_conflict`. A `Rejected` row is INSERT-IF-ABSENT ONLY: it is never written over a live (`Prepared`/`Quiescing`/`Destroying`/`Cataloguing`) row — the challenge/digest checks apply to the FIRST submission of an id only, and the 60 s challenge expiry applies only to NEW submissions, never to a resubmission of an existing id (the frozen row is the authority).
- Field bounds (normative, full table in surface-file Appendix A): reason 1..=512 chars, printable UTF-8, no NUL/control; names ≤ 255 bytes; paths ≤ 4096 bytes; operation_id ≤ 64 chars matching `[0-9A-Za-z._-]+`; storage_object_id 16 bytes; generation u64; timestamps u64 ns since UNIX_EPOCH. Validation rejects NUL and C0 control chars in `reason`/`operation_id`/`actor` (also enforced by the v2 confirmation encoding, surface §6).
- R1 retries — **DECIDED:** `destruction_retry` accepts a `SubscriptionRemoval` record as well: looked up FIRST through the permanent `destruction_bindings` table `(subscription, binding_generation) -> operation_id` (§4c step 4; surface A.2e) — which survives compaction and after archival resolves to the tombstone — then by the record's own `operation_id`, resumed from the recorded `phase` (**STAGE-AWARE (P1-3):** stage 1 — `RowDeleted` ⇒ destination-ABSENCE re-verification + completion from the RECORD's frozen predicates; stage 2 — `RowDeleted` ⇒ durable-PROTECTION verification for every surviving destination (an `Unresolved` incident row or a covering destruction operation exists and reads back) + completion; for a DIFFERENT live generation, neither stage completes — see the P1-5 rule in the crash table), same claim/epoch-CAS discipline as §3b; a `Completed` record returns status. For a cap-exhausted (`AuditUnavailable`) operation the retry FIRST runs the read-only (c)-proof (a covering ack watermark resolves the entry WITHOUT any append) and only then may it carry a budget extension (§3e item 6b). The R1 lookup key is `(name, generation)` — NEVER the subscription row, which is deleted mid-removal (§4c).
