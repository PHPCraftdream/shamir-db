## 1. Goal and non-goals

**Goal.** Give quarantined replication destinations a safe, crash-recoverable, source-independent exit: explicit physical destruction of a destination's storage, release of its reserved name, and removal of the (otherwise immortal) subscription row — without ever serving destroyed or half-destroyed data, and without ever deleting anything but the frozen target set.

**DECIDED — authority staging (stated once here, applied everywhere).**

- **Stage 1 (PRs 8b-3a..3c)** introduces storage-object ids + ownership descriptors, the backend lifecycle contract, the destruction journal, name reservations, NamespaceAdmission guard (round 3: ONE mechanism with the per-target lifecycle exclusion — surface file §7a), the DDL/error surface, the audit Prepared-barrier + in-record durable outbox, and creation exclusion. Incident authority **remains** the #188 terminal/quarantined subscription-row coverage. R1-stage-1 is gated on destination **absence** (not live, not catalogued, no owned component) — a deliberately temporary precondition. **DECIDED (round 6, C7):** 8b-3c ALSO lands a MINIMAL seed-install reservation check — see I4 — so I4 holds from the first install path that exists; the full lifecycle preflight + the §4e boundary-(i) wrapper remain 8b-3e. **DECIDED (round 6, X1): the minimal 8b-3c check evaluates the §7c recovery-exception predicates that EXIST at that stage — the row's own quarantined state + destination match (the re-install-over-existing-row branch of the merged code, execute/replication_seed/catalogue.rs:227-251) COUNTS as the authorized recovery — so the minimal check refuses only a destination that is reserved WITHOUT a quarantined covering row; this keeps the AUTHORIZED install-retry path (which `install_seed_subscription` already supports, caller args.rs:66) working until 8b-3e. The full §7c four-item evaluation arrives with the 8b-3e preflight; until then the minimal check exempts exactly the merged rebind flow.**
- **Stage 2 (8b-3d)** moves incident authority to the **incarnation**: a catalogue incident record (`destination_incidents`) plus repository-carried versioned consistency evidence (`MetaKey::ConsistencyIncidents`); subscriptions are reduced to provenance. R1-stage-2 (subscription deletion) then proceeds by the **ordered incident handoff** (§4c) and no longer depends on destination absence; R1-stage-1 collapses into ordinary destruction completion.
- **Permanent from stage 1:** storage-object id format, ownership descriptor format, destruction journal schema + location, reservation semantics, NamespaceAdmission guard, backend lifecycle contract, the eleven typed error codes (round 4: added `destruction_target_changed`), the DDL surface, the v2 canonical confirmation encoding, the audit outbox semantics. **Deliberately replaceable:** the R1-stage-1 absence precondition (relaxed in 8b-3d by the incident handoff); quarantine coverage derivation from subscription rows; the journal's `incident_ref` starts empty and is filled by 8b-3d. **No throwaway work:** every stage-1 artefact is consumed unchanged by stage 2 — descriptors become the incarnation's component list, reservations become incident-derived, and the executor/boot-replay/audit-outbox machinery is identical in both stages.

**Non-goals (this series).**

- Identity-preserving RENAME of replication destinations; splitting source coordinates from destination identity. That is the PR8b-4 series (§12 in the evidence file). R3 stays a restriction; the `replication_destination_bound` message must say the restriction is a **format limitation**, not permanent.
- Ordinary (non-destructive) DROP/RENAME becoming crash-atomic catalogue transactions. Ordinary DROP/RENAME must respect reservations and storage ownership, but a full atomic-DDL rewrite is out of scope.
- In-place reseeding, multi-target seed recovery, Windows seed installation (8b-3e documents them as unsupported; destruction + name release ARE supported on Windows).
- In-place replacement of a destroyed destination's storage into the CURRENT incarnation. **DECIDED:** this series supports exactly ONE recovery path — destroy (R2') → R1 → fresh install into the ABSENT target as a NEW incarnation (surface file §8); in-place replacement is listed as a follow-up.
- Online migration; enterprise/tamper-evident audit subsystems.

## 2. Invariants

Numbered, each independently testable (CI assertions in the evidence file §9; stage attribution there too).

1. **I1 — Protection outlives configuration deletion.** A destination whose consistency is unresolved stays protected (unreadable, unreservable, uncreatable-over) until its data is durably destroyed or a validated recovery clears quarantine. Deleting a subscription row never by itself clears protection — in stage 2 the row delete is preceded by a durable incident write precisely so this holds (§4c).
2. **I2 — Authorization precedes destruction and outlives partial action.** No destructive step runs before (a) a `Prepared` destruction record (operation id, frozen target set, storage-object ids + component descriptors, actor, reason, nonce) is persisted **and flushed**, and (b) the `destruction_prepared` audit event is durably appended (§3e) through the `AuditSink` seam (**DECIDED (round 5)**: a small trait in `shamir-db`, surface A.7b, implemented by the server over its batched appender; the appender exposes a REAL durability watermark advanced only by a successful write+sync of a contiguous prefix). **DECIDED (round 3):** an audit failure at the barrier NEVER leads to `Rejected` by inference — the strict append is `write_all` + `flush` + `sync_all` (**OBSERVED** audit_appender.rs:498-519 `append_strict`), so a failed final sync does NOT prove the write is absent. The operation STAYS `Prepared` with reservations PUBLISHED (round 5, P1-6: a non-terminal row always reserves — published with the Prepare write at (i), before the barrier) and nothing deleted; the caller receives the NEW retryable wire code `destruction_audit_unavailable` (surface §6c — the TENTH retryable code, added in round 3; round 4 added `destruction_target_changed` as the ELEVENTH), and the SAME event id is retried per the §3e reconciliation-read rule. The intent (journal + audit chain) remains the recovery authority across every crash, cancellation and restart, until the record reaches `Destroyed` or `Blocked`.
3. **I3 — Boot loads intents before any repository loader.** `ShamirDb::init` reads (a) all non-`Destroyed`/non-`Rejected` rows AND (b) ANY row with NON-EMPTY `audit_pending` (ANY state, incl. `Destroyed`, for outbox replay) — **Round 6 (Y5): clause (b) is KIND-SCOPED per §4d step 1: SubscriptionRemoval records load for the §4c/K3 phase-based resume, never for a 4b audit-barrier resume (their `audit_pending` is empty by construction)** — from `destruction_operations` BEFORE the repository-open loop; a target covered by an open operation is never opened, recovered, or published.
4. **I4 — Reserved names reject creation on every publication path.** While a terminal/quarantined anchor or a non-`Destroyed` **and non-`Rejected`** operation — or a `Destroyed` operation with non-empty `audit_pending` (released when the pending set drains, §3e/§4d) — covers a name, CREATE DATABASE / CREATE REPO / config add-repo / engine publication / seed install / subscription binding / rename-into are all rejected with `destination_name_reserved` (full matrix + NamespaceAdmission guard: surface file §7). **DECIDED (round 6, C7):** for SEED INSTALL this holds from **8b-3c**, not from staged 8b-3a code: `install_seed_subscription`'s EXISTING control section (replication_seed/catalogue.rs:161) gains a MINIMAL `destination_name_reserved` check for each bound destination of the row it is about to write (one lookup, no new wrapper); the full lifecycle preflight + the boundary-(i) wrapper stay 8b-3e (surface §7b row 8). **Round 6 (X1): the minimal check evaluates the §7c recovery-exception predicates that EXIST at that stage — the row's own quarantined state + destination match (the re-install-over-existing-row branch of the merged code, catalogue.rs:227-251) counts as the authorized recovery — so it refuses ONLY a destination reserved WITHOUT a quarantined covering row; the AUTHORIZED install-retry-over-quarantined-row flow `install_seed_subscription` already supports (execute/replication_seed/catalogue.rs:155/:161, caller args.rs:66) keeps working until the 8b-3e full preflight supersedes the minimal evaluation. No seed-install path exists in staged 8b-3a code (residual gap stated in evidence §10 non-goals; **until 8b-3c the installer runs in CI only through the 8b-3e cases; from 8b-3c the authorized install-retry case exercises it under the minimal check (X1) (CI case 15, 8b-3c portion)**).
5. **I5 — Destruction is complete and verified.** Completion requires every component in the ownership descriptor (repository store, interner/meta, transaction state, changelog, identity/bookmarks, seed receipts, the **sibling `.shamirwal` WAL directory and its segments**, persistent tiers of cache/hybrid backends, seed staging remnants per surface-file §8) to be destroyed and verified absent.
6. **I6 — Retry never deletes anything but the frozen target set.** All destructive work is bound to storage_object_id + recorded descriptors, never to "whatever occupies the name now". A retry against a live replacement is an error (`unsafe_storage_ownership`), never a deletion.
7. **I7 — No control lock across slow deletion.** The replication control lock is held only for short critical sections (§4e lock order): validation, reservation publication, state transitions, the final destructive catalogue write. Component destruction runs under a per-operation executor token plus per-target lifecycle exclusion.
8. **I8 — R1 never orphans protection.** R1-stage-1 permits DROP SUBSCRIPTION of an anchor only when **every** bound destination is absent and no incomplete operation covers any of them. R1-stage-2 permits it only after every bound destination's incident evidence is durably handed off (§4c), **and no unresolved pending terminal cause for any referencing generation**. The deletion itself NEVER resolves an incident — only validated recovery (the §3d predicate) or destruction completion does. In both stages the union of protections is non-increasing until the handoff/destruction completes.
9. **I9 — Destination-by-destination and cause-by-cause.** Multi-destination subscriptions are destroyed destination by destination; there is no implicit graph-wide destruction, and surviving destinations keep their protection. Incident causes are independent: one incident per (cause, storage_object_id); clearing a cause clears exactly that cause's copies.
10. **I10 — Audit is a barrier at Prepare, an in-record outbox afterwards; the journal is authority.** The `Prepared` transition requires a durable audit append (I2). Later transitions enqueue their audit event INTO THE OPERATION RECORD in the SAME durable CAS write as the state change (§3e); an un-drained `audit_pending` only withholds retirement of the operation and the lapse of the reservations it anchors — it never rolls back a transition.
11. **I11 — Only validated recovery or destruction completion clears quarantine on surviving data.** Operator acknowledgement, subscription deletion, rename, and destruction of a *sibling* destination never clear quarantine on a surviving incarnation; only a replacement verified against the incident's recorded baseline (§3d predicate) or destruction completion resolves an incident (stage 2: the handoff writes the incident BEFORE the row delete, so deletion is provably never the cure).
12. **I12 — No clean checkpoint required.** Destruction never requires successfully checkpointing or opening corrupt data; it requires workers stopped and handles closed.
13. **I13 — Admission closes the check-vs-publish race.** Every publication path takes the admission guard for its (db, repo) namespace before validation and holds it until publication or abort (RAII; cancellation-safe; no durable trace); the per-target lifecycle exclusion is the SAME merged guard object (§4e; surface file §7a). **DECIDED (round 5):** RESERVATION MUTATION (and the reservation CHECK on every publication path) happens under a short **replication-control-lock** section — the merged code already takes control first on every lifecycle mutation path (`remove_db` db_management.rs:87, `remove_repo` :553, `rename_db_as` :165, `rename_repo_as` :622, DROP DB/REPO handlers admin_db_repo.rs:118/:433, every subscription/profile/publication handler admin_replication.rs:65/:132/:170/:245/:295/:400/:454, `install_seed_subscription` execute/replication_seed/catalogue.rs:161, `mark_subscription_terminal_generation` quarantine_helpers/admin_replication.rs:121) — so the control lock is the single serializer of the reservation set: a publisher's check and a reservation's publication cannot interleave. **EXCEPTION — creation (round 6, D1): the premise "control first on every lifecycle mutation path" is FALSE for creation — `create_db_as` (db_management.rs:50-80) and the generic `add_repo_as` path take NO control in merged code. The design ADDS a short control section around the reservation check + mirror write on the CREATE paths (mirror write 8b-3a; control-section check 8b-3b; surface §7b rows 1-2 and 7).** **DECIDED (round 4):** the db-level gate is acquired ONCE, up front, in its FINAL mode and held to the end — never upgraded shared → exclusive, never released/reacquired while repository mutexes are held (§4e).
14. **I14 — Unknown is not success.** Ambiguous I/O (a write/flush that errored but may be durable) is reconciled by re-reading durable state; until reconciled, conservative fencing (reservations + fail-closed reads for the target) stays in force. A failed acknowledgement is never a rollback (§4f).

### 3a. Storage-object id + ownership descriptor

**DECIDED.**

- New per-repository durable meta record `MetaKey::StorageOwnership` in the repo info store, codec versioned like the `MetaEnvelope` usage in `crates/shamir-engine/src/meta/repo_identity.rs:79-117` (the type is defined in `crate::meta`; the cite demonstrates the versioned-codec usage; version 1; NotFound at open → mint lazily only via a controlled admission path, never during destruction).
  Format v1: `{ storage_object_id: [u8;16], durable: bool, components: Vec<ComponentDescriptor>, created_at: u64, format_version: u16 }` where `ComponentDescriptor = { component_id: u32, kind: ComponentKind, path: Option<PathBuf>, bytes_repr: Option<String> }`; `component_id` is stable per descriptor (assigned once at descriptor creation, never renumbered) and is what `destruction_blocked` diagnostics and the record's `blocked_component` reference — **DECIDED** (round 2; an index into the frozen `components` vector is not stable across retry-time re-derivation, so the id lives in the descriptor). `ComponentKind` enumerates: PrimaryStore, Interner, Meta, TransactionState, Changelog, IdentityBookmarks, SeedReceipts, Wal{dir, segments}, CacheTier, HybridDurableTier, MemoryInstance, SeedStagingDir, SeedInstallMarker, SeedReceiptStore (the last three per surface-file §8; all seed remnants of a seeded target are owned components).
- **Mirror:** the system-catalogue `repositories` row carries the FULL descriptor — `storage_object_id: [u8;16]`, `ownership_digest: [u8;32]` (hash of the descriptor) AND the full `components: Vec<ComponentDescriptor>` list (**DECIDED (round 5, P1-8):** the catalogue mirror is a complete copy of the descriptor, not only id + digest, so destruction of a repo that CANNOT be opened works from the catalogue row alone). On open, record vs row disagreement fails closed with `unsafe_storage_ownership`. This catches catalogue/live aliasing (RENAME keeps the old directory while CREATE derives paths from names — **OBSERVED** admin_db_repo.rs:314, :339 `create_dir_all` from name-derived dirs; db_management.rs rename re-keys rows best-effort; **INFERRED**: without the mirror, a renamed-then-recreated repo is indistinguishable from the old storage). **DECIDED (round 5, P1-8):** mirror writes on the open/admission path PROPAGATE ERRORS (never warn-only) from 8b-3a onward — a best-effort write plus a fail-closed disagreement check would make a transient write failure permanently unopenable; and the preflight for a repo whose OWNERSHIP RECORD is unreadable: if the catalogue mirror row exists and is intact, the mirror descriptor is authoritative and destruction proceeds from it (no corrupt open is needed, I12); if BOTH the record and the mirror are unreadable/absent, preflight fails closed with `unsafe_storage_ownership` (operator investigation; the name stays reserved by any anchor). Boot skip-and-fences: a repo covered by an anchor/open operation that FAILS TO OPEN is skipped and fenced (fail-closed quarantined, catalogued-only) instead of aborting `ShamirDb::init` — the boot repository loop (core.rs:329-397, `seed_boot_gate` :381, publication :394) currently opens with `?`; 8b-3a changes the anchor/operation-covered branch to log + fence + continue. **DECIDED (round 6, C9):** 8b-3a lands the skip-and-fence as a STRUCTURAL HOOK in the boot loop — an EMPTY reservation-view consult, inert until 8b-3b wires the view (least churn; the change is not deferred to 8b-3b). Acceptance criterion: the hook exists AND a unit test drives it with a SYNTHETIC non-empty view.
- **Legacy rows under the fail-closed mirror check (round 6, D3):** repositories created BEFORE 8b-3a have catalogue rows WITHOUT mirror fields; on first open, a row with NO mirror fields is grandfathered: the record is minted via the controlled admission path AND the full mirror row is written (error-propagating, per P1-8) BEFORE the disagreement check applies — the check is active only once BOTH sides exist. No compatibility shims beyond this one-time backfill (permitted: the product is unreleased, but master users' existing data dirs must open).
- `durable:false` for `in_memory`: id minted per boot, recorded only in the catalogue row; no on-disk components exist and no fs absence proof is possible. **DECIDED:** the storage-object id must NOT reuse `RepoIdentity::lineage_id`: **OBSERVED** repo_identity.rs:24-34 — `in_memory` AND `hybrid` keep `__tx__` in RAM only, so every process start mints a new lineage at epoch 0 by design; a hybrid's lineage_id is unstable across boots and would make journal/destruction identity meaningless. StorageOwnership instead is written into the **durable metadata/interner tier** for hybrid (open risk in §11 of the evidence file).
- Writers: only the repository open/admission path (mint), the destruction executor (record retirement), and boot replay. Nobody else may mutate.

Round-2 additions and why — **DECIDED**:

- `targets[].subscription_anchors` carries **generations**, not just names: anchor coverage and incident attribution are generation-scoped (surface-file §8 pending-cause model, `MetaKey`-level attribution); a name alone cannot distinguish a replaced binding.
- `audit_pending` implements the **in-record outbox** (§3e, DECIDED round 3): each transition enqueues its audit event INTO the operation record in the SAME durable CAS write as the state change; an append success writes the chain seq into the pending entry (diagnostic); the periodic checkpoint ack hook REMOVES entries whose `audit_seq ≤ ack_watermark` (one durable CAS batch per checkpoint). The row-level `audit_seq_emitted`/`audit_seq_acked` fields are DROPPED. Boot/recovery selects replay work by NON-EMPTY `audit_pending` (never by seq comparison), and retirement requires `state = Destroyed` AND empty `audit_pending`.
- `record_version` is the optimistic-concurrency token for executor self-replacement after crash. **Round 3:** it is NO LONGER part of the audit event id — `event_id = (operation_id, transition_ordinal)`, independent of `record_version` (§3e). **DECIDED (round 5, P2-2):** the claim/heartbeat protocol is `executor_epoch`: every claim path (same-id submission of a stranded `Prepared`, `destruction_retry`, periodic pass, boot, **and the INITIAL executor spawn — round 6, C4: the spawning request performs the CAS; a loser returns the current status and does not spawn**) performs ONE CAS `(record_version, executor_epoch): (v, e) → (v+1, e+1)`; the winner runs the operation for that epoch, losers receive the current status instead of blocking; the ack hook posts "entries acked" TO the current executor (a notify), it does NOT write the row — the executor is the only writer (single-writer model; the old "second CAS writer" ack hook is removed). **Round 6 (C-A2): the claim CAS is CONDITIONAL on the claimer's OBSERVED `(v, e)` (a compare-and-swap on the full pair — a stale observer loses); the spawn of the executor task is IMMEDIATELY ADJACENT to the successful CAS (no await point between); and the executor RE-CHECKS `executor_epoch` currency (a cheap read) before EACH destructive durable step (Quiesce/Detach/Destroy/Catalogue/Complete entry) and aborts to status if superseded. These three together give the single-writer property.**
- `Rejected` is a new **terminal** state reserved for DEFINITIVE PRE-WRITE REFUSALS (authorization, validation, reservation conflict) BEFORE any audit append and BEFORE any Prepare write. No reservation is ever published for a `Rejected` row (round 5, P2-5), no destructive step ever ran, and the only audit event is `destruction_rejected` (best-effort, exempt from the retirement gate). **DECIDED (round 6, C2):** that event is written best-effort DIRECTLY — it is NEVER enqueued in `audit_pending`, which stays EMPTY for a `Rejected` row (the enqueued-then-exempt contradiction is removed). **An audit failure at the barrier does NOT produce `Rejected`** — the operation stays `Prepared` (I2). **DECIDED (round 5, P2-5):** `Rejected` rows NEVER reserve, at boot or at runtime (§3c member (ii) excludes them; §4d step 1 loading excludes them); `Rejected` is INSERT-IF-ABSENT only — a `Rejected` row is never written over a live row of the same id (§4f).
- **DECIDED (round 5, P3):** `Blocked(Phase::Prepare)` is UNREACHABLE: backend support (the `DestructibleBackend` capability and per-component destructibility) is determined at PREFLIGHT, and an unsupported backend is refused there with `storage_destruction_unsupported` — it never becomes a permanent `Blocked` row. `error_class = UnsupportedBackend` consequently never appears on a row; the variant is kept in the enum for schema stability only.

State meanings and durability rules — **every transition persists the new row and flushes before the next step starts**:

| State | Meaning | Durability rule |
|---|---|---|
| `Prepared` | Authorized; targets, ids, descriptors frozen; reservations published; `destruction_prepared` audit event durably appended (barrier, §3e — its pending entry stays in `audit_pending` until the ack hook drains it). | Row + flush, then barrier append, BEFORE any destructive action (I2). |

### 4f. Cancellation, duplicates, bounds
