# TOKEN-AUTH1 - server endpoints `POST /shamir/v1/auth/begin` and `/auth/finish` (password login over HTTP issuing an API token)

State: this branch starts from master `f11889057`: token core (T2a), `TokenService` (T2b, `crates/shamir-server/src/security/tokens/`), the HTTP transport (T3a, `crates/shamir-transport-http`), the REST listener, gate, executor and launcher wiring (T3b), and the native-auth prerequisites (AUTH-PRE: IPv4-mapped normalisation in `subnet_of`, the bounded 8,192-slot `InMemoryLockoutStore` under `crates/shamir-connect/src/server/limits/{lockout.rs,lockout_storage/}`, client KDF lower bounds). Online token administration (T5a) is NOT on master: do not depend on it (issue tokens with `TokenService::create(NewToken)` as it exists today). The TypeScript client that talks to these routes is already written on branch `fix/p34-auth2-login-ts` (`crates/shamir-client-ts/src/login/`, not on master: read it with `git show fix/p34-auth2-login-ts:crates/shamir-client-ts/src/login/core.ts` and `.../protocol.ts`); it fixes what the client sends and what it accepts. The WebSocket token channel (T6) is built in parallel on another branch and also edits `crates/shamir-transport-http/src/server/service.rs`, `accept.rs` and `framing/guarded_io.rs`: keep your edits there small and put new logic in new files as the layout section says, so the branches merge cleanly.

## Goal

On a `kind: http` listener with `login.enabled: true`, `POST /shamir/v1/auth/begin` and `POST /shamir/v1/auth/finish` implement TOKEN_LOGIN_HTTP exactly: strict MessagePack bodies, the protocol-local transcript `T` (binding mode `0x03`, security class `0x00`/`0x01`/`0x02` per section 5.1), proof verification against the stored SCRAM verifier without any server-side Argon2, the server signature `HMAC(server_key, T)`, and issuance of an ordinary TOKEN_API bearer token for a regular (non-superuser, non-replicator) account with the BEGIN-bound scope and a TTL of at most 24 hours. Every admission, deadline, budget, lockout, enumeration-hardening, audit and metric rule of the document is enforced; routes return `404` before the body when login is disabled; bearer behaviour of the listener does not change.

## Decisions taken (the spec leaves these open; the orchestrator owns design)

1. **Crate split.** Wire-independent crypto goes to `shamir-connect` (it already has `hmac`, `sha2`, `subtle`, `rand`, `precis-profiles`): the scope encoder and transcript builder with all length bounds, proof verification over `T` (reuse the HMAC/SHA-256/constant-time helpers and the key schedule; do NOT reuse the SCRAM `auth_message` builder, the spec forbids it; if `AuthMessage` cannot wrap arbitrary bytes, add a sibling verifier over `&[u8]`), the server signature. Everything HTTP, admission, pending state and issuance goes to `shamir-server`. The transport crate only routes. Reason: `shamir-server` has no `hmac`/`subtle`/`rand` dependency and no `Cargo.toml` may change.
2. **Transport hook.** In `shamir-transport-http` add a login hook trait (suggested `LoginRoutes`) with two phases: `admit_head(route, head, peer) -> Result<LoginPermit, LoginResponse>` (all header-only checks and debits, see decision 6) and `handle(route, permit, body: Bytes) -> impl Future<Output = LoginResponse> + Send`; plus `body_limit(route)` (`4096` begin, `256` finish). The service routes `/shamir/v1/auth/begin` and `/shamir/v1/auth/finish` BEFORE the bearer gate (today an unknown path without `Authorization` gets `401` from the gate; login paths must never reach it). `serve` keeps its signature with a built-in `NoLogin` (answers `404` with body `{error: "not_found"}` only when the listener runs with login error bodies, else today's behaviour); add `serve_with_login(...)` for the launcher. `LoginResponse` carries status, the exact msgpack body built by the application, optional `Retry-After`; the transport adds `Content-Type: application/msgpack`, `Cache-Control: no-store`, `Pragma: no-cache`, `X-Content-Type-Options: nosniff`, `Connection: close`, HSTS on TLS, never CORS/cookies/`WWW-Authenticate`. A transport-owned `LoginHead<'a>` view exposes method, path and all values of a header as `&[u8]` (duplicates visible). Reason: one place routes, the application owns the protocol, hyper types do not leak.
3. **Body reading.** The login route reads the body itself (not the bearer body-budget path): stop at the route's limit (`413 request_too_large`, connection closed), 3-second body deadline counted from the end of admission (`408 request_timeout`), `Content-Length` larger than the limit rejected before reading. Hyper sends `100 Continue` only on the first body poll, so polling the body only after `admit_head` returned a permit gives exactly the spec order (head checks, ARRIVAL, CREDIT, input slot, then `100`).
4. **Deadlines.** Header deadline = the listener's `head_timeout` (default 5 s); config validation rejects `login.enabled` with an effective head timeout above 5000 ms (the head deadline is armed before the route is known). Total deadline = `min(listener request_timeout, 120 s)`. Response-write deadline 5 s: add to `GuardedIo` a per-connection write-timeout override (`Arc<AtomicU64>` milliseconds, `0` = none) that the login route sets before returning its response; safe because every login response closes the connection, so the override cannot reach a later bearer response.
5. **Error bodies before routing.** `GuardedIo` canned rejections (`400` framing, `408` head timeout, `413`, `431`) have empty bodies today. On a listener with login enabled they carry `{error: "invalid_request" | "request_timeout" | "request_too_large" | "request_headers_too_large"}` (msgpack) via a `GuardedIo` builder flag set from the listener config; bearer-only listeners stay byte-identical. Reason: the client checks those exact bodies; existing transport tests keep passing.
6. **Admission order at the head** (spec section 4 fixes ARRIVAL -> CREDIT -> slot and "header checks precede body"; the order among header checks is ours): route enabled (`404 not_found` for every method when disabled) -> method (`405 method_not_allowed`, `Allow: POST`) -> `Content-Type` exactly `application/msgpack` without parameters and no `Content-Encoding` header at all (`415 unsupported_media_type`) -> framing (`Transfer-Encoding` + `Content-Length` together or a coding other than `chunked` -> `400`) -> Host (decision 8) -> Origin (`403 origin_forbidden`) -> proxy profile for class `0x02` (untrusted socket peer `403 proxy_forbidden`; bad/missing/all-trusted XFF `400`) -> effective source -> ARRIVAL debit -> CREDIT debit (`429 rate_limited`) -> input slot (source cap `429`, global pool `503 server_busy` with `Retry-After: 1`, no state allocated). Secret-free stateless checks come first; nothing user-dependent before the body.
7. **Order after the body.** BEGIN: strict parse and validation (`400 invalid_request`, including a non-canonical username: `NormalizedUsername` of the input must equal the input byte for byte, the server never normalises) -> body-dependent policy (`read_write` with `tokens.login_allow_read_write = false` -> `403 login_write_forbidden`; `tokens.allow_self_service = false` -> `403 token_self_service_disabled`; read-only replica -> `403 login_read_only_replica`), all before lookup, pair accounting, CSPRNG or state -> pair gate (`429` with `Retry-After = ceil(remaining lock or backoff seconds)` clamped `1..=3600`) -> verifier snapshot (real, or fake for unknown/ineligible, decision 11) -> pending allocation (decision 12) -> `200` challenge. FINISH: strict parse -> atomic claim (live, unexpired, same effective /24 or /64 and family, same listener and security class; otherwise generic `401 authentication_failed` and a wrong-source finish neither consumes nor refreshes the entry) -> pair recheck (active lock, active backoff, or `last_fail_at_ns > begin_time_ns` strictly -> `401` without verifying and without registering a failure) -> proof verification against the retained `stored_key` (fails, or fake/ineligible entry even if the math matched -> register exactly one pair failure -> `401`) -> policy recheck (same three as BEGIN) -> privileged account (superuser or replicator now) -> `403 login_account_denied` (no pair failure) -> snapshot recheck (same user id, same `stored_key`, same `tickets_invalid_before_ns`, eligibility true; else `401`) -> issuance (decision 13). Success clears the pair (`reset_on_success`) only after durable issuance.
8. **Host and Origin.** Host: exactly one, lowercase hostname, IPv6 in brackets, default port normalised (443 on TLS, 80 on plaintext), no userinfo/path/whitespace/fragment; missing/duplicate/malformed `400 invalid_request`; not in `login.authority_allowlist` `403 authority_forbidden`; the default allowlist is the loopback aliases `127.0.0.1:<port>`, `localhost:<port>`, `[::1]:<port>` at the ACTUAL bound port (computed after bind, so port `0` works). Origin: absent accepted; present must be exactly one serialized origin equal to an entry of the listener's `browser_origin_allowlist`; duplicate, `null`, malformed or unlisted `403 origin_forbidden`. `X-Forwarded-Host`/`-Proto` are never trusted. The same canonicaliser is being written in T6 for `host_authority_allowlist`; deduplication is a follow-up, write yours in the login module.
9. **Configuration keys.** Per listener (in `HttpListenerSettings`, flattened): `login: { enabled: bool = false, authority_allowlist: [string], listener_id: string? }` (its own struct with `deny_unknown_fields` in a new file) and `external_tls: bool = false`. Global: `tokens.login_ttl: u32 = 86400` (validated `1..=86400`; expiry uses `min(login_ttl, max_ttl_days * 86400)` with checked arithmetic) and `tokens.login_allow_read_write: bool = false` in `TokensConfig`; `security.login_enumeration_hardening: bool = true` in `SecurityConfig` (the spec says "global" without a section; `security` holds the other authentication knobs). Startup errors exactly as section 5.1 lists (login on plaintext with `allow_plaintext_remote`; direct non-loopback plaintext; actual TLS with `external_tls`; class `0x02` without loopback bind, non-empty `trusted_proxies`, explicit non-empty `authority_allowlist` and non-empty HTTPS-only origin list; direct non-loopback TLS without explicit `authority_allowlist`; `kdf_override` on a login listener; malformed or duplicate `listener_id` (exactly 32 lowercase hex characters); `login_ttl` out of range; head timeout above 5 s, decision 4). Class: TLS -> `0x01`; plaintext loopback without `external_tls` -> `0x00` (a non-loopback socket peer on such a listener is refused at the head with `403 proxy_forbidden`); plaintext loopback with `external_tls` -> `0x02`.
10. **`listener_id` persistence.** When not configured, a CSPRNG 16-byte id is created once and stored in `server_meta` under a key derived from the listener's configured `addr` string (new `ServerMetaStore` get-or-create method next to `token_key`); a configured value overrides it. Reason: `addr` is the operator-visible identity of a logical listener; the value itself is random, never derived from Host, path, forwarding or client data.
11. **Eligibility and fake verifier.** Hardening `true`: eligible iff the stored tuple equals the global `kdf_defaults` exactly; `false`: eligible iff the stored tuple is client-usable (version `0x13`, memory 19,456..262,144 KiB, time 2..8, parallelism 1..8). Other tuples are ineligible in both settings. Unknown and ineligible users get the deterministic fake salt / `stored_key` / `server_key` from `FakeBlob::derive(server_secret, username)` and the CURRENT default KDF tuple in the challenge; the snapshot work (one directory lookup, one fake derivation computed in every branch, same allocations) is equivalent in all three branches, and every BEGIN response produced after the body is padded to 50 ms plus a CSPRNG-uniform integer jitter of 0..=25 ms measured from body receipt. At startup with any login listener enabled, count users whose stored tuple makes them ineligible (no ids) into the gauge `shamir_login_http_kdf_ineligible_users` and log the count at WARN; there is no interactive acceptance knob (the spec's "explicit operator acceptance" is a runbook step, recorded in the note).
12. **Pending state and admission tables.** All in-process, volatile. Pending: fixed capacity 1,024; per-source caps IPv4 /24 16, /16 256, IPv6 /64 16, /56 64, /48 256; TTL 60 s on the monotonic clock, not sliding; each entry stores `T` itself (<= 933 bytes; username and scope are recovered from `T` at the fixed offsets, which also satisfies "store scope once"), user id, `stored_key` and `server_key` (`Zeroizing`), `tickets_invalid_before_ns`, eligibility, effective source prefix keys, listener index, class, `begin_time_ns` (the checked Unix clock that `LockoutStore` uses for `last_fail`), claimed flag; payload asserted <= 1,536 bytes. Expiry is purged lazily on every admission and claim from an insertion-ordered queue (fixed TTL, so insertion order is expiry order; no new background task). At capacity: choose with the CSPRNG (rejection sampling, no modulo bias) among UNCLAIMED entries whose principal (/16 or /48) occupancy is at least `ceil(1024 / active principals)`; none -> `429`; claimed entries are never evicted. Handshake ids and server nonces: OS CSPRNG 32 bytes, nonce non-zero and different from the client nonce, collision-checked, three retries then `503 server_busy`. ARRIVAL and CREDIT: two tables of 4,096 entries each with the tiers, per-parent child quotas (32 children per /48 per child tier, 32 /24 per /16), own-parent charging for excess children, atomic all-tiers-or-nothing debit, no refunds, the eviction and pinning rules and the "drop only that source's accounting" fallback exactly as section 3. Input slots: global 1,024 and the per-source caps of section 3, released exactly once by an RAII permit on every terminal path. Concurrency: each structure sits behind ONE `tokio::sync::Mutex` (CLAUDE.md "bounded contention" primitive), locked with `.lock().await` so queued requests park instead of blocking runtime threads, with a bounded allocation-free critical section and NO `.await` inside; document the contention model inline. Every structure takes an injectable clock so unit tests drive time without sleeping. Memory: fixed-capacity arrays/`Vec::with_capacity` at construction, no growth after start, the budget of section 3 asserted in a unit test from the type sizes you chose (state the per-entry charge you use).
13. **Issuance.** `TokenService::create(NewToken { owner_user_id, owner_roles: current roles read now, label, ttl_secs: Some(min(login_ttl, max_ttl_days*86400)), mode, channels, databases })`; map `LabelExists` -> `403 token_label_exists`, `LimitReached` -> `403 token_limit_reached`, `ReadOnlyNode` -> `403 login_read_only_replica`, store/clock/entropy errors -> `503 server_busy` (no token). After creation re-read user id, `stored_key`, threshold and privilege and require `created_at_ns > tickets_invalid_before_ns`; on any change `TokenService::revoke` the fresh token and answer `401` (if that revoke fails: no secret in the response, critical audit, `503`). Scope rights are not pre-checked against the account at creation: the token session intersects with the owner's live rights at use time (TOKEN_API section 6), as for `CreateApiToken`. The success map has exactly the 11 keys of section 1.2, `owner` = the canonical username, `id` = the 16 token-id bytes.
14. **Label and database caps.** `TokenService::create` and `TokenRecord::validate_shape` cap labels at 64 bytes and database names at 128 bytes today; the login spec allows labels 1..128 and database names 1..255. Raise both caps to 128 / 255 for every creation path (existing tests that assert the old caps are updated; records within the old caps stay valid, the msgpack format is unchanged). Database syntax for login is `^[A-Za-z0-9_-]+$` (the client's rule; the engine validator is not reachable from here). Reason: one shared cap across creation paths, as TOKEN_API section 3 requires for label semantics.
15. **LockoutStore.** Add to the trait (and to every implementor: `rg "impl LockoutStore for"`) one read method returning the pair's state without mutating it, e.g. `pair_status(key, now_ns) -> PairStatus { locked_until_ns: Option<u64>, backoff_until_ns: Option<u64>, last_fail_at_ns: Option<u64> }`, using the existing curve (backoff active while `now < last_fail + backoff_ms(count)`). It is an O(1) probe like `is_locked_out`. Native handshake code is not changed (AUTH-PRE decision). Pair key = `(subnet_of(effective source ip), username_hash(lockout_secret, canonical username))`.
16. **Transcript vectors.** "Publish test vectors before implementation": add `crates/shamir-connect/test-vectors/http_login_transcript_v1.json` with at least two hand-derived cases (databases `null`; two sorted databases), giving every input and the expected `scope_bytes` and `T` as hex, and a Rust test asserting the builder reproduces them byte for byte and the length formula `166 + user_len + scope_len`. HMAC/Argon2 vectors are added by the orchestrator after CI can run code; until then proof/signature correctness is covered by round-trip tests (client key schedule from `scram.rs` -> proof -> server verify; flipped bits fail).
17. **Audit.** A bounded queue (1,024 events / 1 MiB; overflow drops and counts) feeding the existing audit chain writer from one task owned by the login service and stopped with the listener: events `http_login_issued` (token id only) and a per-minute aggregate `http_login_failures` (counts by fixed result class only). Never password, proof, token secret or MAC, nonce, raw body, handshake id, username or address. `TokenService::create` keeps writing its own `api_token_created`.

## Acceptance (each item testable; CI runs the tests)

1. Routes: login disabled -> `404 {error: not_found}` before the body for every method on both paths; enabled: non-POST -> `405` with `Allow: POST`; wrong/parametrised `Content-Type` or any `Content-Encoding` (including empty) -> `415`; body over 4,096 (begin) / 256 (finish) -> `413`; slow body -> `408` after 3 s; every login response carries the five mandatory headers and closes the connection; HSTS on TLS; bearer routes on the same listener behave exactly as before.
2. Strict wire: duplicate, missing, unknown or mistyped keys, trailing bytes, arrays instead of maps, signed integer markers (including non-negative ones), out-of-range integers, wrong `bin` lengths, invalid UTF-8, `protocol_version != 1`, `binding_mode != 0x03`, all-zero client nonce, non-canonical username, label outside 1..128 or with C0/DEL, empty databases array, more than 4 databases, unsorted/duplicate/invalid database names, scope over 512 bytes -> `400 {error: invalid_request}`; positive fixint and every applicable unsigned width, including non-shortest encodings, accepted.
3. Challenge: exactly the 12 keys of section 1.1 with `security` matching the listener class, the stable `listener_id` (same after a restart on the same data directory, configured value honoured), the user's real salt and tuple for an eligible user, fake salt and the default tuple for unknown and ineligible users; the response bytes have the same shape and length class for all three, and BEGIN takes at least 50 ms.
4. Successful login: the Rust test client derives keys from the challenge, sends the proof, verifies `server_signature = HMAC(server_key, T)`, and the returned token works on `POST /shamir/v1/request` (`Ping`, and a read on a table after the explicit grants of the test plan); `id` equals the token's id bytes, `owner` equals the user, `expires_at_ns - created_at_ns <= 86_400 s`, scope equals BEGIN's.
5. Failures: wrong password, unknown user and ineligible user each give `401 {error: authentication_failed}` and register exactly one pair failure (the following BEGIN's `429`/`Retry-After` is identical for the three); replayed, unknown, expired (61 s, via the injected clock in unit tests) or already-claimed handshake id -> `401`; finish from another /24 -> `401` and the entry is still claimable from the right source; pair in lock or backoff, or `last_fail > begin_time` -> `401` without verifying or registering.
6. Policy: `read_write` with the flag off -> `403 login_write_forbidden` with no state, no pair accounting, no CSPRNG; self-service off -> `403 token_self_service_disabled`; read-only replica -> `403 login_read_only_replica`; superuser and replicator accounts get a normal challenge and, after a valid proof, `403 login_account_denied` with no pair failure; duplicate active label -> `403 token_label_exists`; `max_per_user` reached -> `403 token_limit_reached`; a password or role change between BEGIN and FINISH -> `401` and no token.
7. Admission: ARRIVAL and CREDIT tiers, child quotas, atomic debit and no refunds, input-slot caps (`429` per source, `503 {error: server_busy, retry_after: 1}` with `Retry-After: 1` for the global pool, existing pending state untouched), pending caps, fair-share eviction and all-claimed `429`, table churn fallback - all as unit tests with the injected clock; one e2e case shows `429 {error: rate_limited, retry_after}` with `Retry-After` equal to the body after the loopback /24 CREDIT is spent.
8. Security classes and proxies: every startup error of decision 9 is a config validation test; class `0x02` accepts a trusted loopback peer with a valid XFF chain, rejects an untrusted peer with `403 proxy_forbidden` before the body, rejects malformed/missing/all-trusted chains with `400`; Host and Origin rules of decision 8 (including the default loopback aliases at the bound port).
9. Lockout: pair failures go to the shared `LockoutStore` (native and HTTP see the same pair); curve 100 ms x 2^(count-1) capped at 30 s, 50th failure locks for one hour, five-minute idle reset, `admin_unlock_user` clears the user's pairs; untracked pairs under table pressure drop accounting and are bounded by CREDIT only.
10. Metrics (fixed vocabularies, no identity labels): `shamir_login_http_total{endpoint,result}`, `shamir_login_http_pending`, `shamir_login_http_evictions{reason}`, `shamir_login_http_accounting_dropped{reason}` (`pair_quota`, `pair_table_full`, `arrival_table_full`, `credit_table_full`), `shamir_login_http_pair_slots`, `shamir_login_http_begin_duration_seconds`, `shamir_login_http_finish_duration_seconds`, `shamir_login_http_kdf_ineligible_users`.
11. Audit and redaction: the events of decision 17 appear; a log-capture test (style of `crates/shamir-server/src/security/perimeter/http_rest/tests/redaction_tests.rs`) over success and failure shows no password, proof, nonce, handshake id, token secret, MAC, username or address in logs, spans, errors or audit details.
12. Transcript vectors of decision 16 pass; T length bounds 173..933 enforced; the builder rejects every out-of-range field.

## Non-goals

The TypeScript client (AUTH2, done); native SCRAM behaviour (no pre-challenge backoff on native, AUTH-PRE decision); online administration (T5a); a configuration knob for any budget, deadline, tier or padding (all fixed constants, section 5.1); a DNS check of Host; mTLS or proxy authentication; HMAC/Argon2 vectors (decision 16); deduplicating the Host canonicaliser with T6.
