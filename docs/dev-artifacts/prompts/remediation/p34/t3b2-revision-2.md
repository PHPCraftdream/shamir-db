# TOKEN-T3b-2 revision 2 - behaviour gaps found by the second independent review

State: this branch now contains master (with the landed token store/service and the offline CLI), slice T3b-1 (listener configuration) and slice T3b-2 revision 1 (REST gate/executor), merged cleanly. Read `t3b2-revision-1.md`, `t3b2-rest-gate-executor.md`, `t3b-http-listener.md` and the audit note `docs/dev-artifacts/audits/2026-11-01-token-t3b2-gate-executor/DESIGN.md` first. A second review found no compile errors in revision 1 beyond two test defects that the orchestrator has already fixed (`Query::from`, `.is_ok()`), and these behaviour gaps (paths under `crates/shamir-server/src/security/perimeter/http_rest/` unless noted). Fix them in this order.

1. `api_token_exposed` can be lost under a failure flood (spec section 11, security-relevant): failure and exposure notices share one 256-slot channel; `record_exposed` uses `try_send` and drops silently when full (`maintenance.rs`), and the flusher awaits `spawn_blocking` inside the tick arm of `select!`, so the channel is not drained while audit writes run. Give exposure notices their OWN bounded channel or reserved capacity, never block the receive loop on the blocking write (run the blocking write as a separate task and keep receiving, or double-buffer), and COUNT drops (a dropped-notices counter that appears in the next summary event).
2. The aggregator must produce ONE sampled summary event per window, not one event per subnet (today up to 16 audit writes per second, about 1.4M chained writes a day under a distributed attack; unauthenticated traffic must not drive audit I/O, and an I/O error latches `persistence_failed` for the whole audit writer): per window write at most one `api_token_auth_failures` summary with total count, distinct-subnet count, a few sampled subnets (bounded, e.g. 4), the dropped count; failures beyond the tracked-subnet cap are COUNTED, not silently dropped; include the token id only when known and only for the exposure event.
3. Failure limiter memory (`maintenance.rs`, `FailureLimiter`): every tracked subnet owns an `InMemoryRateLimiter` with its own `DashMap` (a dashmap with `cores*4` cache-padded shards per subnet: tens of MiB at the 4096 cap, an attacker fills it with IPv6 /64s) and re-arms the section 8.6 warm-up per subnet. Store per-subnet state directly (a small struct of atomics: window start, count, last seen) in ONE bounded map, with the same observable semantics the existing tests assert (threshold of 2 failures in the first 60 s, then 10 per second; read `gate_tests.rs` and keep them valid or update the oracle with a comment if the semantics are intentionally the same but the construction changed). Keep periodic gc and the cap; when the cap is hit, evict the oldest-idle entry before rejecting.
4. Session-bucket cache (`bucket.rs`): the sweep only removes expired/revoked entries; once 4096 distinct live tokens were used every new token gets 503 until some expire (up to 365 days) and each such request pays an O(N) `retain` that write-locks every shard. A bucket idle for >= 1 s is already full (capacity is one second of refill), so eviction is lossless: track `last_used`, evict entries idle for more than 1 s when the cap is reached BEFORE returning 503, and do the sweep only when the cap is reached (or periodically from the maintenance task), never per request.
5. Flusher shutdown (`maintenance.rs`): on stop/service_stop it exits without a final flush; do one final drain and flush (bounded in time) so up to one second of aggregates and pending exposure events are not lost.
6. Metrics: `revalidate` counts `unavailable` after `authenticate` already counted `success` (one request counted twice); scope-level 403s from the executor are not counted; `count_auth_result` hardcodes `channel = "rest"` in `security/tokens/model/token_counters.rs` (make the channel a parameter so WS can reuse it). Keep the fixed vocabulary of labels.
7. Cleanups: `FailureLimiter::new(_now_ns)` ignores its argument (remove it); `aggregates.iter().next()` plus `shift_remove` is O(n): use `shift_remove_index(0)`; the executor classifies each request twice (once itself, once in `ScopedHandler::handle`): keep the guarantee, but share the result if it is cheap and safe.
8. Tests (cannot be run, must compile): flood test proving exposure events survive a failure flood; aggregator emits one summary per window with bounded size and counts drops; limiter bounded memory and gc; bucket eviction of idle entries instead of 503; final flush on stop; no double counting in revalidate; the gate-level 429 `Retry-After` header on the wire. Replace weak oracles: the `gate_tests` check of "count unchanged" must wait for the blocking pool to drain deterministically (join the flush task handle or use the final-flush API from item 5), and the test named as proving that the executor "cannot call the native handler" must actually assert that (a handler double that panics/counts when called). Rewrite `DESIGN.md` of this stage to match the code (the file:line references there are stale and `### Validation incidents` is empty).
