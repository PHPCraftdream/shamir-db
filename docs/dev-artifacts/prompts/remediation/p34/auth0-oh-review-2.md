## Blocking (P1)

N1 (section 3, the LockoutStore paragraph, and the AUTH_PROTOCOL 5.2.5 amendment): the 256 shared overflow shards re-create a global password-auth off-switch, for native TCP/WS logins too. The 7,936 exact subnet aggregates are never evicted; excess subnets fold by hash into the 256 overflow shards, and both BEGIN and native auth honour the "applicable subnet aggregate lock/backoff". Native auth has no stacked /48 caps, so one IPv6 /48 can mint 7,936 /64 subnets with 65 usernames each and then saturate all 256 shards with about 12,800 more failures; after that every new subnet is backed off or locked everywhere. FIX (all of it): (a) no cross-subnet shards: an overflowing /64 folds into its OWN /56 or /48 parent aggregate, never into shared state with unrelated subnets; (b) aggregates impose backoff gates only, never a 1-hour lock; (c) aggregates are evictable (lowest count / oldest first), like pairs; (d) when every slot is hot, drop accounting for the new subnet and rely on the BEGIN credit limit, never share state across unrelated subnets; (e) any hashing is keyed with `lockout_secret`. Rewrite the AUTH_PROTOCOL 5.2.5 amendment text to match.

N2 (section 3, the "Dedicated arrival table" paragraph): the arrival and credit tables have the same flaw. New sources beyond 4,096 keys share one fixed overflow bucket, and entries are reclaimable only after five idle minutes. One /48 can mint 4,096 /64 keys in about 26 s at the /48 arrival rate (160/s); requests later rejected for credit still touch arrival keys. From then on every new source lands in the overflow bucket, which the attacker keeps drained: global HTTP login denial from a single /48, or from ~4,096 IPv4 /24s every 5 minutes. FIX (all of it): (a) hierarchical per-parent quotas: at most k /64 keys per /48 and k /24 keys per /16 (choose k and state the arithmetic); any excess is charged to the PARENT bucket, never to a global bucket; (b) reclaim an entry as soon as its bucket is full again and it has no outstanding handshakes (a full bucket is identical to a fresh one, the 5-minute wait is unnecessary); (c) when the table is full, evict the fullest or least-recently-used entry instead of falling back to a shared bucket. Re-do the byte-budget arithmetic of section 3 after the change.

## P2

N3 (section 3, pending caps and eviction): the global pending cap can still be filled with nothing evictable: holding every prefix at or below half its cap (8 per /64, 32 per /56, 128 per /48) fills all 1,024 pending entries with 8 /48s (or 128 /24s at 8 each); no entry is "overrepresented", nothing is evicted, every client gets 429. Credit cost stays within the limits (8/min per /64, 128/min per /48). FIX: when the global table is full, evict a uniformly random UNCLAIMED entry from prefixes at or above fair share (global cap / number of active prefixes); state the remaining Sybil bound explicitly (an attacker with many prefixes can still degrade, and say by how much).

N4 (sections 5 and 7): `login_write_forbidden` / "requested read_write policy" is dangling: no config key or condition defines it (a leftover of the deleted "read_write on plaintext" rule). FIX: define `tokens.login_allow_read_write` (default false; when false a begin that requests `read_write` is rejected at BEGIN with 403 `login_write_forbidden`, no state), and list it in the config table of N7. If you find no other use, drop the code instead and keep login tokens `read_only` only; pick one and make the whole spec consistent (error table, config, tests, amendments).

N5 (section 5 and the TOKEN_API section 12 rule 3 amendment): label uniqueness has two definitions. Login uses active-only uniqueness, but TOKEN_API section 3 ("unique among the owner's tokens") and 12.1 ("uniqueness of label") are not amended, and `CreateApiToken` and login share one atomic uniqueness check. FIX: amend TOKEN_API section 3 and 12.1 to active-only uniqueness (unexpired, unrevoked) for ALL creation paths, and refer to `tokens.max_per_user` instead of a hard-coded 20.

N6 (sections 1.1 and 3): remote plaintext is forbidden but no mechanism is specified. FIX: define what a `kind: http` listener with `tls: false` and `allow_plaintext_remote: true` (TOKEN_API section 11) does with the login routes: they are NOT served there (startup error if login is explicitly enabled on it, otherwise 404). Security class 0x00 requires a loopback bind AND a loopback socket peer.

N7 (sections 5 and 7): the login route switch has no config key and no default. FIX: add a config table (new subsection) listing, with name, type, default, scope (listener or global) and validation: `login.enabled` (default false, opt-in per listener), `external_tls` (with its loopback/trusted_proxies/HTTPS-only-Origins preconditions), `login_enumeration_hardening`, the exact Host/authority allowlist and its loopback default, the source of `listener_id`, `tokens.login_ttl`, `tokens.login_allow_read_write` (N4), the budget constants that are configurable (if any). Everything else stays constant and is said so.

N8 (section 3 LockoutStore and the AUTH_PROTOCOL 5.2.5 amendment): the subnet aggregate has no defined threshold or scope. As written about 114 failures (64 usernames plus 50 folded) lock every user of a NAT'd /24 for an hour, natively too (new insider/NAT amplification), and `unlockUser` (AUTH_PROTOCOL 12.3) cannot clear failures folded into an aggregate. FIX: aggregate gates (backoff only, see N1) apply only to usernames that have NO retained pair; define the threshold, the decay and the backoff curve; define how `unlockUser` interacts with aggregates (it clears the pair and subtracts nothing from the aggregate, state that explicitly, or define a per-user contribution counter, your choice, but be explicit).
