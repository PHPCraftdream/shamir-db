# TOKEN-T6 - server side of the bearer-token WebSocket channel (ws and wss, native and browser)

State: this branch starts from master `f11889057`, which holds the token core (T2a, `crates/shamir-connect/src/server/auth/token/`, `state/token_session.rs`, `state/origin.rs`), `TokenService` (T2b, `crates/shamir-server/src/security/tokens/`), the HTTP transport (T3a, `crates/shamir-transport-http`), the REST gate/executor/maintenance (T3b-2, `crates/shamir-server/src/security/perimeter/http_rest/`) and the launcher wiring of `kind: http` (T3b-3, `crates/shamir-server/src/engine/server/server_launcher/http/`). Online token administration (T5a) is NOT on master and must not be depended on: revocation in tests goes through `ServerHandle::token_service` (`revoke`, `revoke_user`) directly. HTTP login (AUTH1) is being built in parallel on another branch and touches `crates/shamir-transport-http/src/server/service.rs` and `framing/guarded_io.rs` too: keep your edits there small and put new logic in new files (see the layout section) so the two branches merge cleanly.

## Goal

A `kind: http` listener serves `GET /shamir/v1/ws` (native bearer: `Authorization` header checked before `101`) and `GET /shamir/v1/ws/browser` (browser bearer: Host/Origin checked and pre-auth permits reserved before `101`, the token arrives in the single first binary frame), over plaintext (channel 2) and TLS (channel 4). After the upgrade the connection is bound to ONE token session with a fresh random 32-byte `sid` (binding frame `{ok, sid, expires_at_ns}`), runs a duplex request loop over the same native handler path as SCRAM (deny-by-default scope with the WS column of TOKEN_API section 7: transactions, cursors and subscriptions allowed), closes `4010` on a foreign `sid`, `4011` on revocation or owner invalidation, `4012` on token expiry or `tokens.session_max_age_hours`, `1000` on server shutdown, and on every exit removes the session from `TokenSessionStore`, unregisters subscriptions, rolls back the open transaction and closes the session's cursors. Exactly what the JS client in `crates/shamir-client-ts/src/entry/ws/` and `src/platform/token/socket-*.ts` sends and expects must work unchanged.

## Decisions taken (the spec leaves these open; the orchestrator owns design)

1. **Split of responsibilities.** `shamir-transport-http` does routing, the `101` response assembly from application-supplied headers, the hyper upgrade plumbing, the GuardedIo tunnel switch and connection lifecycle; it stays free of tungstenite, SHA-1 and token semantics. `shamir-server` owns everything WebSocket-semantic (RFC 6455 head validation, `Sec-WebSocket-Accept` via `tokio_tungstenite::tungstenite::handshake::derive_accept_key`, Origin/Host policy, auth, admission, framing, the loop). Reason: tungstenite is already a dependency of `shamir-server` and `shamir-transport-ws` only, and no `Cargo.toml` may change.
2. **Transport hook shape.** Add a trait (suggested name `WsUpgrade<G>`, in a new file) with three phases: `check_head(route, head, peer) -> Result<HeadOk, WsReject>` (no secrets; 400/403/404/503), `admit(route, head_ok, grant: Option<G>, peer) -> Result<(Session, Vec<(name, value)>), WsReject>` (native: called after the existing `TokenGate::authenticate` with `Endpoint::Ws`; browser: `grant = None`), and `run(session, io: UpgradedIo, shutdown: CancellationToken) -> impl Future<Output = ()> + Send`. `WsReject` carries status, optional `Retry-After`, and whether to close. `UpgradedIo` is a transport-owned newtype over `hyper_util::rt::TokioIo<hyper::upgrade::Upgraded>` implementing `AsyncRead + AsyncWrite + Unpin + Send` so `shamir-server` never names hyper types. A transport-owned `UpgradeHead<'a>` view gives `path`, method and all values of a header by name as `&[u8]` (repeated headers visible). Names may differ; the three-phase split and the "no hyper types leak" property may not. `serve` keeps its current signature (it passes a `NoWs` implementation that answers `404` for both WS paths); add `serve_with_ws(...)` used by the launcher. Reason: the transport tests (`src/tests/transport_tests.rs` and others) call `serve` and must not churn.
3. **Where the upgraded session runs.** Inside the existing per-connection task of `serve` (already in its `JoinSet`, already holding the global/per-IP admission permit): use `serve_connection(...).with_upgrades()`; the service hands the `OnUpgrade` future to the connection task through a per-connection one-shot slot; after hyper finishes the HTTP part the task awaits the upgrade and runs `ws.run(...)` with a child of the listener shutdown token. The post-connection rejection drain/linger code must not run on an upgraded stream. Reason: no untracked `tokio::spawn`, the T3b-3 shutdown bound and the per-IP connection cap keep covering WebSocket connections for their whole life.
4. **GuardedIo tunnel.** `GuardedIo` scans every read as an HTTP head and arms head/request/write deadlines; after `101` that would corrupt WebSocket traffic. Add a terminal `Tunnel` state entered when the observed response head is `HTTP/1.1 101`: from then on reads and writes pass through unmodified, all HTTP deadlines are disarmed and never re-armed, no holds are consumed. Bytes the client sends BEFORE the `101` was written stay subject to HTTP scanning (fail closed, the client is non-conforming). Keep the change local to `guarded_io.rs` plus tests.
5. **Wire framing.** Token WebSocket messages carry plain msgpack with NO inner 4-byte length prefix (the JS client and TOKEN_API section 10); the SCRAM WS framing keeps its prefix. Add unprefixed variants to `crates/shamir-transport-ws/src/framing.rs` sharing the existing receive loop (control-frame budget, heartbeat pong matching, text rejection): e.g. an internal prefix mode parameter on `ws_recv_into_stream_inner` plus public `ws_recv_raw_into_stream_observing` and `ws_send_sink_raw`. A new token framer in `shamir-server` implements the existing `FrameReader`/`FrameWriter` traits on top of them; `write_frame_prereserved` strips the 4-byte prefix the shared writer path produces (`buf[4..]`, after checking the declared length). Reason: one copy of the control-frame and heartbeat logic.
6. **Shared loop parts.** Extract the writer task body of `run_request_loop` (heartbeat ping/pong deadline, `WriterMsg` handling, budget-guard release after the write, coded close from `CloseIntent`) into one shared `pub(crate)` function in a new file and call it from both loops; behaviour of the SCRAM loop must stay identical (same select arms, same timeouts, same order). Add `CloseIntent::set_code(u16)` and reasons in `close_reason` for `4000 authentication_failed`, `4010 token_sid_mismatch`, `4011 token_revoked`, `4012 token_expired`, `4013 token_channel_denied`, `4014 token_plaintext_write_denied`, `1013 server_busy`. The token reader loop is a new function (it compares the frame `sid` instead of looking it up). Reason: design risk "drift between the two copies".
7. **Ordering before `101`.** Native: method (`405`, `Allow: GET`) -> upgrade head (`Upgrade: websocket`, `Connection` contains `upgrade`, `Sec-WebSocket-Version: 13`, a syntactically valid 16-byte base64 `Sec-WebSocket-Key`, `Sec-WebSocket-Protocol` offering `shamir-v1`; otherwise `400`) -> optional Origin (present: must match `browser_origin_allowlist` exactly, empty list rejects any Origin, `403`) -> `TokenGate::authenticate(Endpoint::Ws)` (`401` uniform, `429` limiter, `403 token_channel_denied` / `token_plaintext_write_denied`) -> active cap (`503`, `Retry-After: 1`) -> `101`. Browser: method -> route availability (decision 9) -> upgrade head (`400`) -> Origin exactly one, not `null`, well formed (`400`), in allowlist (`403`) -> Host exactly one, valid authority, in `host_authority_allowlist` (`400`) -> pre-auth permit (`503`) -> `101`. The response sets `Upgrade`, `Connection: Upgrade`, `Sec-WebSocket-Accept`, `Sec-WebSocket-Protocol: shamir-v1` and never `Sec-WebSocket-Extensions` (no compression). Cheap secret-free checks first so a malformed upgrade never touches the token mirror.
8. **Host authority.** New listener key `host_authority_allowlist: [string]` in `HttpListenerSettings` (default empty = every browser request gets `400`/rejected, so the browser route is off by default). Canonical form: lowercase host, IPv6 in brackets, port kept unless it is the scheme default (80 for `ws`, 443 for `wss`), no userinfo/path/whitespace; compare exactly, no DNS. `X-Forwarded-Host` is never honoured in T6 (the spec only permits it from trusted proxies; Host-only is the smaller surface). Validated at config load (entries must already be canonical). Origin uses the existing `ListenerConfig::browser_origin_allowlist`, validated for `kind: http` with `shamir_transport_ws::BrowserOriginPolicy::try_allow` as `kind: ws` already does.
9. **Browser route availability.** `/shamir/v1/ws/browser` is served on TLS listeners and on plaintext listeners whose bind address is loopback; on a plaintext non-loopback listener (`allow_plaintext_remote`) it answers `404` (route absent). Reason: TOKEN_API section 1 and TRANSPORT_WS: browser `ws://` is loopback only and does not inherit `allow_plaintext_remote`.
10. **First browser frame.** Read by hand from `UpgradedIo` before any `WebSocketStream` exists: parse the frame header, require FIN, opcode binary, RSV = 0, mask bit set, payload length <= 256 checked BEFORE allocating, unmask; accept at most 8 control frames of <= 125 bytes during the wait (ping/pong ignored, close = terminal), all within one 5-second deadline that control frames do not extend; any violation, timeout, text/continuation frame, or a payload that is not exactly a one-entry msgpack map `{"token": str(71)}` (no other or repeated keys, no trailing bytes) ends with close `4000`. Then build the stream with `WebSocketStream::from_partially_read` (any bytes read past the first frame) or `from_raw_socket`, config `max_message_size`/`max_frame_size` 16 MiB; for the `4000` path write the close frame through such a stream too. Confirm the exact tokio-tungstenite 0.30 signatures in the cargo registry sources. Reason: tungstenite cannot change `max_frame_size` after construction, and the 256-byte bound must hold before allocation.
11. **Browser verification order** (TOKEN_API sections 5 and 10): parse -> `TokenService::verify(token, Endpoint::Ws, now)`; `Invalid | Revoked | Expired | OwnerInvalid` and every frame defect -> `4000` and the subnet failure limiter/aggregated audit is fed (the limiter never produces HTTP `429` after the upgrade and never rejects a verified token); `ChannelDenied` -> `4013`; plaintext-write rail -> `4014` plus `api_token_exposed`; active cap -> `1013`; then publish (decision 13); release the pre-auth permit on success and on every terminal path; only then the binding frame.
12. **Pre-auth accounting.** Exactly the permits the spec numbers: 256 global and 8 per subnet (`subnet_of` of the TCP peer, or of the trusted-proxy-resolved address when `trusted_proxies` applies), atomic counters, RAII release. The "proposed" byte accounting (64 KiB per socket etc.) is not implemented: the 256-byte first-frame bound times 256 sockets already bounds pre-auth payload memory. Reason given in the note.
13. **Revocation fan-out.** New `TokenWsCancelRegistry` implementing `SessionCanceller`: `scc::HashMap<TokenId, CancellationToken, THasher>` of per-token parent tokens plus a per-connection child; entries removed when the last connection of that token ends (counter in the entry). Installed once in `launch.rs` with `TokenService::open(..).await?.with_canceller(registry.clone())` BEFORE the `Arc::new`, and passed to the listener through a new `ListenerEnv` field. Race rule (publish-then-cancel on the service side, register-then-recheck on the connection side): the connection first registers its child token, THEN re-checks `TokenService::still_valid`; revoke publishes the mirror revocation before `cancel_token`, so a revoke that races the upgrade is always observed by one of the two. Owner invalidation (password, role, flag change, `revoke_user_tickets`, deletion, restore) has no push hook: each connection re-checks `still_valid` every `TOKEN_WS_REVALIDATE_INTERVAL = 1 s` (one Acquire load plus one directory cache lookup per socket per second) in addition to the per-request check. Close code: expiry (token or session deadline) -> `4012`, any other invalidity -> `4011`.
14. **Session lifetime.** Deadline `min(token.expires_at_ns, opened_at_ns + session_max_age_hours * 3_600_000_000_000)` with checked arithmetic, hours converted to nanoseconds before the addition; `expires_at_ns` in the binding frame is this deadline. A `sleep_until` arm closes `4012` at the deadline. No idle timer (SCRAM `SESSION_IDLE_TTL` does not apply); heartbeat as TRANSPORT_WS section 7 (reuse the configured ping interval/pong timeout the SCRAM loop uses).
15. **Replies.** Successful handler output -> `{rid, res: bin}` (`ResponseEnvelope`). Scope denials (`token_read_only`, `token_database_denied`, `token_request_denied`) -> `{rid, res: bin(DbResponse::Error{code, message: code})}`, the same taxonomy as the REST `403` body, and `shamir_token_request_denied_total{endpoint="ws"}` +1. Envelope-level failures -> `{rid, error: <code>}`: `rate_limited` (post-auth limit, `Session::check_post_auth_rate_limit` of the connection's session; the socket stays open), `invalid_request` (inner `req` fails `validate_request_alias_caps` or decoding), `internal_error`. A malformed outer envelope -> `{error: "invalid_envelope"}` without `rid` (SCRAM parity; the JS client ignores rid-less frames). A frame whose `sid` differs from the connection's -> close `4010`, no reply. Application errors go through `application_error_boundary` as on the SCRAM path. Post-auth rate limiting uses the per-session bucket, not the REST per-token `BucketCache`: the socket caps (`max_sockets_per_token`) already bound the amplification.
16. **Per-request re-check.** Each dispatch task checks `still_valid` (Acquire) and the deadline immediately before calling the handler; on failure it does not call the handler, sets the close intent (`4011`/`4012`) and stops the reader (the in-flight request gets no reply). A request that passed the check may finish after a concurrent revoke (spec: "запрос, уже прошедший проверку, может завершиться").
17. **Teardown.** One RAII guard owned by the connection: `TokenSessionStore::remove(sid)` (idempotent with the service's own removal), cancel-registry unregister, `SubscriptionRegistry::close_all` (before the push sink is dropped, as in the SCRAM loop), rollback of the session's interactive transaction (the `TxRegistry` `by_session` handle, using the same rollback routine as `TxRollback`), removal of the session's cursors (add a teardown-only `CursorRegistry::remove_all_for_session(sid)`; an O(N cursors) scan on disconnect only, documented), `shamir_token_active_ws` gauge decrement. Runs on every exit path including panic unwinding of the loop task and shutdown.
18. **Scope classifier.** Make `classify_request` endpoint-aware (`Endpoint::Rest | Endpoint::Ws` from `shamir_connect::server::token`): WS allows `TxBegin`, `TxExecute`, `TxCommit`, `TxRollback`, `CreateCursor`, `FetchNext`, `CancelCursor` and `Subscribe`/`Unsubscribe` leaves; read-only tokens are denied `token_read_only` on `TxExecute` with any write leaf and on `TxCommit` (`TxBegin`/`TxRollback` allowed); `databases` allowlist applies to the `db` of every request carrying one. REST behaviour must stay byte-identical (all existing scope/executor tests keep passing). `ScopedHandler::handle` takes the endpoint too. Keep the exhaustive `match` without `_` arms.
19. **Gate.** `RestGate::authenticate` becomes endpoint-aware: `Endpoint::Ws` verifies with `TokenEndpoint::Ws` and counts `shamir_token_auth_total{channel="ws"}` (pre-register the `ws` label set at zero like `rest`). Add a `pub(crate)` method for the browser path that verifies a token presented in a frame and returns a typed verdict (`Verified | Failed | ChannelDenied | PlaintextWriteDenied`) while feeding the same failure limiter/aggregator but never yielding `RateLimited`. The failure aggregator and exposure notices in `maintenance.rs` take the channel (`rest`/`ws`) instead of the hard-coded `"rest"` in the audit summary.
20. **WS endpoint switch.** No new `endpoints` key: both WS routes are enabled on every `kind: http` listener (`EndpointSet { rest: true, ws: true }` in `launcher.rs`), the browser route gated by decisions 8 and 9. Reason: TOKEN_API section 1 assigns both channels to `kind: http` without a toggle.

## Acceptance (each item testable; CI runs the tests)

1. Native upgrade: valid token with `channels` `ws` or `both` -> `101` with `Sec-WebSocket-Protocol: shamir-v1`, no extension header, then one binary frame decoding to exactly `{ok: true, sid: bin(32) non-zero, expires_at_ns}`; `expires_at_ns` equals decision 14.
2. Native refusals before `101`: missing/duplicate/malformed `Authorization`, unknown id, wrong secret, revoked, expired -> identical `401` responses (status, headers except `Date`, body); `rest`-only token -> `403 token_channel_denied` without `101`; wrong or missing subprotocol / bad upgrade head -> `400`; non-GET -> `405` with `Allow: GET`; Origin present with an empty or non-matching allowlist -> `403`; active cap exhausted (`max_sockets_per_token`, `max_sockets_per_owner`) -> `503` with `Retry-After`; repeated failures from one subnet -> `429` with `Retry-After` while a valid token from the same subnet still upgrades; a missing header does not feed the limiter.
3. Plaintext rails: on a remote-plaintext listener without `allow_plaintext_write` a `read_write` token gets `403 token_plaintext_write_denied` before `101` and an `api_token_exposed` audit notice; a `read_only` token upgrades.
4. Browser route: `400` for missing/`null`/duplicate/malformed Origin and for missing/duplicate/malformed/unlisted Host; `403` for an unlisted Origin; `404` on a plaintext non-loopback listener; pre-auth caps (256 global, 8 per subnet) -> `503`; after `101` no binding frame and no application frame before the first frame is verified.
5. Browser first frame: a valid 80-byte frame -> binding frame; 5-second timeout, text frame, fragmented frame, RSV bit, unmasked frame, payload of 257 bytes (and 256 accepted by the size check), extra/repeated/missing keys, trailing bytes, non-string or wrong-length token, unknown id, wrong secret, revoked, expired -> close `4000` with the same reason string in every case and no handler call; `rest`-only token -> `4013`; plaintext-write rail -> `4014`; active cap -> `1013`; pre-auth permit released on every path (assert the counters return to zero).
6. Session loop: `Ping`, `Execute` (read and, with a `read_write` token, write on a table the test created through the native SCRAM harness), `TxBegin`/`TxExecute`/`TxCommit`, `CreateCursor`/`FetchNext`/`CancelCursor`, `Subscribe` with push frames `{push, sub, seq, ...}`; read-only token: write `Execute`, write `TxExecute` and `TxCommit` -> `token_read_only` inside `res`; admin `DbRequest` variants and admin batch leaves -> `token_request_denied`; database outside the allowlist -> `token_database_denied`; replies have exactly `rid` + `res` or `rid` + `error`.
7. `sid` isolation: a frame with another connection's token `sid`, a SCRAM `sid` or an all-zero `sid` over a token connection -> close `4010`; a token `sid` sent over a SCRAM connection -> `session_expired` (the SCRAM store never contains token sessions); token sessions never appear in the SCRAM `SessionStore`.
8. Revocation: `TokenService::revoke` while a subscription is live -> the socket stops receiving pushes and closes `4011` without any client frame; `revoke_user` likewise; owner role change through the native admin session -> `4011` within the revalidation interval; a token with `ttl_secs = 2` -> `4012`; after every close the token's session count in `TokenSessionStore`, the cancel registry entry, the open transaction (rolled back: its staged write is not visible) and the cursors are gone.
9. Text frame after authentication -> `1003`; data frame over 16 MiB -> `1009`; heartbeat as SCRAM (Ping every interval, `4003` without a matching Pong); server shutdown -> close `1000`, `ShutdownReport` without errors, shutdown within the existing drain bound.
10. Accounting: token sockets never count against the SCRAM per-user session cap (16 open token sockets of an owner do not block that owner's SCRAM login; use small configured caps if 16 is too heavy, the property is what matters).
11. Metrics and audit: `shamir_token_auth_total{channel="ws",result}`, `shamir_token_active_ws` (up on activation, down on teardown), `shamir_token_request_denied_total{endpoint="ws"}`, `shamir_token_request_duration_seconds{endpoint="ws"}`; `api_token_auth_failures` summaries carry `channel = ws` for WS failures; no token, secret, MAC, first-frame bytes or `Authorization` value in any log field, span, metric label, audit record, close reason or error string (redaction test covering success and failure on both WS routes).
12. SCRAM path unchanged: every existing test of `request_loop`, the framer, `shamir-transport-ws` framing and the REST scope/executor passes without edits to its assertions (signature updates only where a function gained a parameter).
