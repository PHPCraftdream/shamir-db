## Problem (confirm it with a red test first)

A table's three physical stores are named after the LOGICAL table name: `__data__<name>`, `__info__<name>`, `__history__<name>`. DROP TABLE and the source of a RENAME orphan the old stores; a later CREATE or RENAME into the same name opens or copies INTO those orphans, so stale rows can merge into the new table, and a retry after a failed `copy_store` keeps the partial copy. The tests in section "Tests" must show this on the old code (red) and be green after the change.

## Owner decision (binding, 2026-11-01)

Use unique on-disk store names. The disk name of a table's stores carries a unique identifier with a time stamp, generated by the existing time-stamped id generator (`shamir_types::RecordId::new()`, `crates/shamir-types/src/types/ids/record_id.rs`; verify it is the right function and render it with its existing text form, no new id scheme). The identifier is ONLY part of the disk name. Logical table names stay unique per repository exactly as today; the new rule is that two different tables (for example a dropped one and a re-created one) may have disk names that are equal once the identifier is stripped, so they never collide on disk.

## Binding behaviour

1. Disk name = the existing prefix + the logical name + a fixed separator + the id text, for all three stores (and for any other store derived from the table name; find them all). The prefix routing in `repo_types.rs` (`starts_with("__info__")` etc.) must keep working; prove the separator and id characters are legal for every backend (fjall key space names, in-memory, hybrid, cached) with a test per backend that exists in the engine tests.
2. The id is generated ONCE when a table is created and persisted with the table, so every later open (also after restart, also on a follower) finds the same stores. Persist it where the table already persists its configuration and catalogue row; the design note decides the exact place. The field is optional on disk: a table that has no id (every table created by an older binary) keeps its old, id-less store names forever. No data migration, no renaming of existing stores. Old data directories open unchanged; a new binary's data written for a table with an id is not required to open in an old binary (state this in the design note and in `docs/guide-docs/KNOWN_LIMITATIONS.md` if that file lists format compatibility).
3. The disk id is node-local. It must not travel through replication or the replication seed export/import/verify as if it were part of the logical table definition: a follower or an imported seed generates its own id when it creates the table. Read `table_record.rs`, `exporter.rs`, `verifier.rs` and `fence.rs` in `shamir-server` and say in the design note how each treats the new field (ignore it explicitly; do not let it break artifact equality checks).
4. CREATE after DROP of the same logical name generates a new id, so it opens fresh empty stores; the orphaned stores of the dropped incarnation are never read again. Deleting orphaned stores is NOT part of this task (keep the current "orphan on drop" disposition); the design note states whether a follow-up purge is now safe and what it would need.
5. RENAME: with a persisted logical-to-disk mapping a rename no longer needs to copy data. Decide in the design note between (a) metadata-only rename (re-key the catalogue row and the in-memory config, keep the same stores) and (b) keeping the copy but into stores with a NEW id. Prefer (a) if the existing invariants hold (the force-drain of the MVCC overlay into history before the rename, `table_token_for(name)` keys, `per_table_mvcc`, the WAL and replay path that resolve a table by name or token, change-feed and index metadata that embed the table name, vector snapshot keys that live in `__info__<table>`). If you choose (a), `Repo::copy_store` stays for other callers and keeps its documented partial-copy semantics. Either way a retry after an injected failure must end with exactly the source rows.
6. Every place that builds a store name from a table name today (the list in `git grep -n "__data__\|__info__\|__history__" -- crates ':!*/tests/*'`: `repo_membership_impl.rs`, `catalog.rs`, `stage.rs`, any drop path in `db_management.rs`, and tests/helpers) goes through ONE function that maps the table to its disk names. No second place may rebuild the name.
7. Logs and error messages keep showing the logical name.

## Tests (must fail on the old code, red first in CI; no sleeps; never assert the ordering of generated ids)

- drop a table that has rows, create a table with the same name: the new table is empty (old code: stale rows visible);
- rename `a -> b`, create a new table `a`, rename-swap back and forth: no row of one incarnation shows up in another;
- injected failure in the middle of a rename (use a store wrapper that fails the second batch), then retry: the destination holds exactly the source rows (or, for design (a), the rename leaves the source intact and nothing half-visible);
- cold restart (durable fjall repository in a temporary directory) after create, rename, drop and re-create: the table finds its own stores; a table created by the old naming scheme (build the fixture by writing the old-named stores directly) still opens with its rows;
- the disk-name function: stripping the id of two tables with the same logical name yields equal text, the full names differ; an id-less table keeps exactly the old name;
- replication/seed: the id is not part of the equality or export of the logical table record.
