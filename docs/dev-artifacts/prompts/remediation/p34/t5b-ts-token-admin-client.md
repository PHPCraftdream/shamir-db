# TOKEN-T5b-TS - online API-token administration in `shamir-client-ts` (canonical HMAC, builders, SCRAM client methods)

State: this branch starts from `fix/p34-t5a-token-admin` (T5a, not yet on master). T5a added the server side of the four `DbRequest` operations `create_api_token`, `list_api_tokens`, `revoke_api_token`, `revoke_user_tokens` (responses `api_token_created`, `api_tokens_listed`, `api_token_revoked`, `api_user_tokens_revoked`), the canonical HMAC v2 encoding for them (op tags `0x0020..=0x0023`) and extended the shared fixture `crates/shamir-query-types/test-vectors/admin_hmac_v2.json` to 35 vectors. ## Goal

A TypeScript caller holding a SCRAM `ShamirClient` can create, list and revoke API tokens (its own, or on behalf of another user as a superuser) through typed builders and typed methods, with every request signed by the session HMAC key exactly as `createScramUser` / `setSuperuser` are, with the created secret returned only inside the existing redacting `ApiToken` handle, with typed listing rows that never carry a secret, and with server error codes surfaced as typed `ShamirDbError`s. The TS canonical encoder reproduces all 35 shared vectors (no skipped tags). Token clients (`connect({ auth: 'token', ... })`) get nothing: token sessions are denied these operations by the server (`token_request_denied`, TOKEN_API sections 6-7).

## Decisions taken (the orchestrator owns design; deviations go into the note with a reason)

1. **Encoder.** Extend `hmac.ts`: TAGS `create_api_token: 0x20, list_api_tokens: 0x21, revoke_api_token: 0x22, revoke_user_tokens: 0x23`; extend `DbCanonicalOp` with the four op shapes (the `hmac` field optional and ignored); `canonicalDbRequest` encodes in the Rust/Python order: create = `str(label)`, `opt(ttl_secs, u64)`, `opt(mode, u8: read_only 0, read_write 1)`, `opt(channels, u8: rest 0, ws 1, both 2)`, `opt(databases, list)`, `opt(for_user, str)`; list = `opt(for_user, str)`; revoke = `str(id)`; revoke-user = `opt(user, str)`. `null` and `undefined` are both `None`; `[]` is `Some([])`. Replace the current fall-through `set_replicator` default with an explicit branch per op plus an exhaustive `never` check, so an unknown op cannot silently encode as `set_replicator`. Keep the file's existing compact style; stay under 1000 lines.
2. **Builders** in a new file `src/core/builders/admin/token-admin.ts`, re-exported by `admin/index.ts` (so they reach the flat barrel): `createApiToken(signer, spec)`, `listApiTokens(signer, opts?)`, `revokeApiToken(signer, id)`, `revokeUserTokens(signer, opts?)`, each returning the exact signed wire op (`{ op: 'create_api_token', label, ttl_secs?, mode?, channels?, databases?, for_user?, hmac }` etc.), canonicalised and signed exactly like `setSuperuser`. Spec field names are the wire's snake_case (`ttl_secs`, `for_user`, as the existing admin builders use wire names). Absent options are OMITTED from the wire object (never `undefined` values, never `null`): build the object conditionally. `ttl_secs` accepts `number | bigint`; a `number` must be a safe non-negative integer, a `bigint` must be in `0..=2^64-1`, otherwise `RangeError` before signing; `mode`/`channels` are checked against their literal sets at runtime (`TypeError`). `databases` is copied (`[...spec.databases]`) so later caller mutation cannot desynchronise wire and signature. Usernames are passed raw (no NFC/case mapping: section 12 signs the raw UTF-8 and the server normalises).
3. **Always sign.** Every builder output carries `hmac` even for self-service: the server checks the tag only on delegated/foreign paths and ignores it otherwise (T5a `handlers/token_admin/logic.rs`), and the client cannot know whether a revoked id is foreign. Same convention as `createScramUser`.
4. **Types** in a new file `src/core/types/access/token-admin.ts` (a closely-coupled group, like `admin.ts`), exported from `src/core/types/index.ts`: `ApiTokenMode = 'read_only' | 'read_write'`, `ApiTokenChannels = 'rest' | 'ws' | 'both'`, `CreateApiTokenSpec`, `CreateApiTokenOp`, `ListApiTokensOp`, `RevokeApiTokenOp`, `RevokeUserTokensOp`, `CreatedApiToken` (`{ id: string; token: ApiToken; label: string; owner: string; mode; channels; databases: string[] | null; created_at_ns: bigint; expires_at_ns: bigint }`), `ApiTokenInfo` (listing row: same without `token`, plus `revoked_at_ns: bigint | null`), and the `ApiTokenAdmin` interface (decision 5). Type-only imports of `ApiToken` (`import type`) so the types file stays declaration-only. Check every new name against the flat barrels (`rg -n "<Name>" src`) before adding; record any rename.
5. **Client surface: `client.apiTokens`.** `client.ts` is at exactly 1000 lines, so four new methods cannot be added directly. Add ONE accessor `get apiTokens(): ApiTokenAdmin` (one-line JSDoc naming TOKEN_API section 12) that returns `apiTokenAdmin((req) => this.sendDbRequest(req), (canonical) => this.hmacTagHex(canonical))` from `client-internals.ts`; the returned object has `create(spec): Promise<CreatedApiToken>`, `list(opts?: { for_user?: string }): Promise<ApiTokenInfo[]>`, `revoke(id: string): Promise<void>`, `revokeUser(opts?: { user?: string }): Promise<bigint>` (count as `bigint`, decision 7). To pay for the accessor and its imports, move the body of `getDdlOpStatus` (lines 959-979) into an exported `getDdlOpStatus(db, repo, table, opId, sendDbRequest)` in `client-internals.ts` and keep `ShamirClient.getDdlOpStatus` as a one-line delegation with the SAME signature, JSDoc and behaviour (same thrown errors and messages). This is the only edit to unrelated code, made solely for the line limit; record it in the note. `client.ts` must end at or below 1000 lines (measure with `wc -l`). Reason: methods stay on the SCRAM client, grouped, and the private `sendDbRequest` is injected by closure (the `CursorIterator` / `createScramUser` pattern) instead of widened.
6. **Token clients untouched.** No file under `src/entry/` and `src/platform/` changes; `TokenHttpClient` / `TokenWsClient` / `PublicTokenClient` gain nothing.
7. **Response validation** in `client-internals.ts` (one helper per response kind): check `kind`, then every field's type (`id` 22-char string, `label`/`owner` strings, `mode`/`channels` in their literal sets, `databases` `null` or string array, `*_ns` as `bigint` or safe non-negative `number` normalised to `bigint`, `revoked_at_ns` `null`/absent or as above, `count` likewise). The created secret is wrapped with `ApiToken.from(r.token)` (its `TypeError('Malformed API token')` carries no secret) and must satisfy `token.slice(5, 27) === id` checked on the raw string BEFORE wrapping; any failure throws `Error('malformed api_token_created response')` (fixed text; never interpolate the response object, the token or `r.kind` of a created reply into a message). Unexpected `kind` on other replies: `Error('unexpected DbResponse kind for <op>: <kind>')` as the existing functions do. Delete the local reference to the raw response object after wrapping (JS strings cannot be zeroed; do not create extra copies, no logging).
8. **Error mapping.** No new error class: server errors already arrive as `ShamirDbError` with `.code` through the read loop. Add to `src/core/support/errors.ts` a `TOKEN_ADMIN_ERROR_CODES: ReadonlySet<string>` holding exactly the section-12 codes (`permission_denied`, `token_not_found`, `token_browser_session`, `token_request_denied`, `token_self_service_disabled`, `read_only_replica`, `hmac_required`, `hmac_mismatch`, `session_invalidated`, `invalid_username`, `not_found`, `not_supported`, `internal`, `token_label_exists`, `token_limit_reached`, `token_ttl_invalid`), the matching union type `TokenAdminErrorCode`, and `isTokenAdminError(err: unknown, code?: TokenAdminErrorCode): err is ShamirDbError` (narrowing helper). Do not change `RETRYABLE_ERROR_CODES` (`read_only_replica` stays retryable there). Export these from `src/index.ts` and `src/browser.ts` next to `ShamirDbError` (append names only).
9. **Browser.** No client-side default for `channels`: TOKEN_API rule 1's "browser SDK SHOULD default to `rest`" targets issuance from the browser, and a browser SCRAM session (binding mode `0x02`) is refused creation by the server (`token_browser_session`); list and revoke work from the browser. Document this in the `create` JSDoc. No `node:` import in any new file (all new code is platform-agnostic; `ApiToken` is already in the browser graph).

## Acceptance (each item testable; CI runs `tsc --noEmit` strict and vitest 1.6)
