# TOKEN-AUTH0 - revision 1: independent security review (@oh) and owner decisions

The independent reviewer (@oh) attacked `docs/guide-docs/client-server-protocol-spec/TOKEN_LOGIN_HTTP.md` and ruled on the owner-decision list. Verdict: not approvable as written; the crypto core is sound (domain-separated transcript, scope bound into the proof, server-chosen handshake id so no fixation, no server-side Argon2), the problems are in guessing controls, DoS levers, proxy deployment and the enumeration precondition. Apply everything below to the spec file. Line numbers refer to the file as it was reviewed (331 lines).

## Owner decisions (binding; the owner delegated them to @oh)

- D1 binding_mode 0x03 / separate transcript: APPROVE WITH CHANGE. `0x03` is a constant of this protocol only and is never parsed through `BindingMode`. Clients MUST enforce the KDF floor (F9). A non-canonical `user` is rejected with 400, never normalised by the server (otherwise the client's transcript does not match and counts as a wrong password). Test vectors are published before implementation starts.
- D2 remote plaintext opt-in: REJECT. Delete `allow_plaintext_login` and the "read_write on plaintext" rule. Allowed security classes: loopback plaintext, TLS, and TLS terminated at a trusted proxy (F6). This also resolves the conflict with TOKEN_API section 12 rule 3 (token secret only over TLS or loopback).
- D3 `tokens.login_ttl` 86,400 s (range 1..86,400), `read_only` default: APPROVE WITH CHANGE. Label uniqueness and `max_per_user` count ACTIVE tokens only; distinct after-proof error codes (F14). The browser SDK defaults to `channels: "rest"` (browsers cannot send bearer tokens on WS).
- D4 fresh-proof-only exception to "browser sessions cannot create tokens": APPROVE WITH CHANGE. State honestly that this channel is WEAKER than binding mode 0x02 and that the 24 h TTL is the compensating control (F15). Refuse superuser and replicator accounts (F16). Check self-service, read-only replica and route policy at begin (F13).
- D5 strict Origin: APPROVE WITH CHANGE. Origin absent: accepted as a non-browser client. Present: exactly one value, exact allowlist match (reuse the existing `browser_origin_allowlist`); `null`, duplicate or malformed: 403. Add an exact Host/authority allowlist against DNS rebinding on loopback.
- D6 caps and bounded lockout extension: APPROVE WITH CHANGE: bounded state yes, but it must degrade differently (F2, F3, F4, F5, F10, F11, F17).
- D7 `login_enumeration_hardening` default true: APPROVE WITH CHANGE: replace the global fail-closed invariant with per-user ineligibility (F7); forbid `kdf_override` on login listeners; delete the claim that password change can upgrade a KDF tuple (it cannot today: it keeps the stored tuple); document the leak that remains through native TCP/WS listeners (F12a).

## Findings to fix (P1 are blocking)

F1 P1 (L144, L151) Locked-pair timing oracle. A pair locked at begin still gets a real challenge; a correct proof on a locked pair is released at the 50-75 ms floor while wrong proofs wait ~30 s, so guessing continues through the lockout (~32 guesses/min per subnet). Native SCRAM rejects a locked pair before any challenge (`crates/shamir-server/src/sync/connection/handshake.rs:219-237`), so this is a regression. FIX: for `locked_at_begin` or a lockout found at the finish recheck, skip proof verification (or ignore its result) and take the SAME failure path every time: register a failure, delay `max(target, BACKOFF_CAP_MS)`; response and timing must not depend on proof correctness.

F2 P1 (L150, L153, L195) The aggregate failure bucket only turns 401 into 429, it never stops a guess (valid proofs bypass it, so 200 versus 429 still reveals correctness); password spraying (one password, many usernames) is limited only by the arrival limiter (~36,000 guesses/hour per /24 or /64). FIX: check the bucket at BEGIN; when depleted return 429 before issuing a challenge and create no state (accept that NAT neighbours can be denied login). State the resulting spraying limit explicitly.

F3 P1 (L128-132, L155) Cheap global login DoS: caps keyed per /64 and never-evicted live state; 1,024 pending / 16 per /64 = 64 /64s fit in one /56; delayed-response workers 256 / 16 per /64 = 16 /64s, each pair at 30 s backoff. FIX: make the per-pair backoff a GATE AT BEGIN (if `now < last_fail + backoff` return 429 with Retry-After and allocate nothing, as `lockout.rs` documents: "the next request must be delayed"); failed finishes then need only the 50-75 ms floor so no 30 s workers are held; stacked IPv6 caps (/64, /56, /48); allow evicting the oldest UNCLAIMED entries of over-represented prefixes.

F4 P1 (L128) The bounded LockoutStore becomes an unauthenticated off-switch for ALL password login (at capacity "reject new password-auth admission" also hits TCP/WS; ~55 failed finishes/s with unique fake usernames fills 16,384 entries). It also changes native SCRAM without amending AUTH_PROTOCOL. FIX: when full, evict pre-threshold failure entries (lowest count / oldest first), never refuse admission globally; cap pairs per subnet and fold the excess into one per-subnet aggregate pair; keep active locks; amend AUTH_PROTOCOL section 5.2.5 explicitly in the proposed amendments.

F5 P1 (L134) The forwarding header fails open to the proxy address: a client-controlled malformed entry makes the whole header ignored, so the source becomes the proxy (e.g. nginx `$proxy_add_x_forwarded_for` turns `not-an-ip` into `not-an-ip, 203.0.113.7`); then 50 failures lock `(127.0.0.0/24, alice)` for everyone behind the proxy and for native loopback logins, and the attacker escapes its own per-source caps. Duplicate header lines are legal (RFC 9110 joins them with commas). FIX: join duplicate lines; walk right to left, skip trusted entries, take the first valid untrusted address, stop at the first malformed one; if no valid untrusted address precedes it, reject with 400; NEVER fall back to the proxy address for accounting.

F6 P1 (L51, L98, L171) The recommended same-origin deployment cannot log anyone in: it needs a reverse proxy (the admin UI is on a separate listener, `ADMIN_UI_HOSTING.md:82`, and `kind: http` answers 404 for `/admin/*`); behind a TLS-terminating proxy the listener is plain on loopback so it emits `security=0x00`, while an `https://` client expects `0x01` and must reject. FIX: add a listener setting declaring external TLS, allowed only with a loopback bind, `trusted_proxies` set and HTTPS-only Origins; emit a distinct security class ("TLS terminated at trusted proxy") bound into the transcript; document honestly that the proxy-to-server hop is plaintext loopback.

F7 P1 (L53-55, L140) The hardened-mode precondition cannot be met with today's code and is a global off-switch: password change keeps the user's existing KDF tuple (`crates/shamir-server/.../admin.rs:584-597` passes `record.kdf_params`; `changepw.rs:166-168` stores it); AUTH section 13.4 says the only upgrade is re-creating the user (new `user_id`, tokens and resource ownership lost); per-listener `kdf_override` (`boot/config.rs:364`) makes "configured defaults" ambiguous; bootstrap rotation writes the listener's tuple (`handshake.rs:240,600-605`). FIX: replace the global fail-closed rule with PER-USER INELIGIBILITY: a user whose tuple differs from the global current KDF parameters runs exactly the unknown-user path (fake blob salt and keys, default tuple, generic failure, protected-audit reason); forbid `kdf_override` on login listeners; report the ineligible-user count at enablement and as an operator metric; delete the false upgrade claim.

F8 P1 (L201, L9/L82) Remote plaintext opt-in: token secret over plaintext contradicts TOKEN_API section 12 rule 3; passive observer gets a 24 h token plus (T, proof) for an offline Argon2 dictionary attack; an active attacker corrupting proofs locks victims out (each counts as a failure on the victim pair; 50 locks, including native from that subnet); KDF downgrade (F9). FIX: remove the opt-in (D2).

F9 P1 (L51, L118) Clients do not enforce a minimum KDF strength (`kdf_params.rs:validate_client_limits` checks upper bounds only). A MITM with a valid certificate (corporate inspection proxy) or on plaintext swaps the begin response to `memory_kb=8, time=1`; the client produces a proof over a near-free KDF; the server rejects it, but the attacker cracks the PASSWORD offline at raw-hash speed - permanent compromise. Native clients share the gap (pre-existing). FIX: the client MUST reject parameters below AUTH_PROTOCOL section 3.7.2 floor (19,456 KiB, t=2, p=1) before running Argon2; in hardened mode it SHOULD also require the exact expected tuple from configuration.

F10 P2 (L144) The lockout description is wrong: "50 failures/hour" is not what the code does; `LOCKOUT_WINDOW_NS` is unused and the counter resets to 1 after any 5-minute gap (`crates/shamir-connect/src/server/limits/lockout.rs:404-424`), so guesses spaced >= 5 min per pair never lock (12 guesses/hour per pair indefinitely). FIX: describe the real behaviour; either require fixing the code to a real 1-hour window (list it as a prerequisite) or do not rely on lockout as a guessing limit.

F11 P2 (L134) "Exact same accounting" with TCP/WS is false: the spec normalises IPv4-mapped IPv6 addresses but `subnet_of` (`lockout.rs:89-102`) does not; on a dual-stack `[::]` bind native code puts all IPv4 clients in one `::/64` (a pre-existing bug), so HTTP and native compute different pair keys. FIX: normalise inside `subnet_of`; list as a separate native prerequisite fix.

F12 P2 (L53, L161, L136) Enumeration leaks remaining after the mitigation: (a) a reachable native TCP/WS listener still sends stored KDF tuples (AUTH section 13.5), so hardening HTTP only helps where HTTP is the only exposed auth surface - state it; (b) begin has no latency padding and does extra snapshot reads only for known users - pad begin to the 50-75 ms floor and do equal work in both branches; (c) salts change over time (fake salts on `server_secret` rotation, real salts on password change) - document as accepted.

F13 P2 (L163, L185, L193) Checks that do not depend on the password run after a valid proof: `allow_self_service=false`, read-only replica, `read_write` policy. FIX: check them at BEGIN (403, or 404 when the route is disabled) and create no state; only label collision and `max_per_user` stay after the proof.

F14 P2 (L163, TOKEN_API section 3) Label uniqueness and the token cap must be over unexpired, unrevoked tokens only (records are kept 30 days after expiry, so `http-login` would otherwise be blocked for 30 days). Replace the single `login_forbidden` after a valid proof by TOKEN_API's distinct codes (`token_label_exists`, `token_limit_reached`, `token_self_service_disabled`) so the client can react.

F15 P2 (L243, SECURITY_MODEL section 4.15) The rationale contradicts itself: browser mode 0x02 is barred from creating tokens because it is weaker, yet this ceremony is weaker still but is called "not a browser session". FIX: say plainly that it is weaker than 0x02 and the compensating control is the <= 24 h TTL; rewrite the last sentence of the proposed SECURITY_MODEL section 4.15 text and the TOKEN_API section 12.1 text accordingly.

F16 P2 (L163) Superuser and replicator accounts: refuse them at finish (403 after a valid proof, no token); admins use native CLI with a pin (SECURITY_MODEL section 4.9).

F17 P2 (L128, L130, L153) Budget gaps: (a) "reuse the shared arrival limiter instance" points at an unbounded DashMap (`rate_limit.rs`), contradicting the 4,096-entry bound - use a dedicated bounded instance; (b) the per-subnet active index (<= 1,024 keys) is not counted in the 2,686,976-byte total; (c) say that login has its own slot/task pool, separate from TOKEN_API bearer traffic.

F18 P3 (L161) The "per-user mutation fence" and the "verifier generation" field do not exist (`UserRecord` has only salt/keys/kdf/threshold). TOKEN_API section 12's pattern is enough: write durably, re-check stored key and threshold, revoke durably if changed, disclose the secret only after the re-check passes. Allow that pattern; compare `stored_key` plus the threshold.

F19 P3 small items: (a) non-canonical `user` -> 400 (see D1); (b) read-only replica returns 403, not 503 with Retry-After (a permanent condition); (c) add HSTS on TLS (TOKEN_API section 9 has it); (d) drop the `argon_queue` metric (no server Argon2 runs); (e) add a response-write timeout; (f) finish body cap 256 B instead of 8 KiB (the body is ~115 B); (g) Argon2 `time` is an iteration count, not seconds - fix the TTL formula's unit mix-up; (h) `Connection: close` puts begin and finish on separate connections, so the client IP can change between them (Happy Eyeballs v4/v6, mobile) and full-IP binding fails spuriously - bind to the /24 or /64 instead, or state the failure mode; (i) the Node SDK should prefer native exporter-bound SCRAM plus `CreateApiToken` when a native listener is reachable; (j) scope fields can sum to 1,161 B against the 512 B cap - state that it is a 400.
