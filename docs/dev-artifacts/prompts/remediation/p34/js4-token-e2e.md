# TOKEN-JS4 - end-to-end tests of the JS token client against a real server (http, https, ws, wss; Node and browser)

Base: JS1-JS3 (HTTP and WS token transports and the public `connect` API in `crates/shamir-client-ts`), T3b (REST), T5 (token admin), T6 (WebSocket token channel, native bearer and browser first-frame) and AUTH1 are landed. Read `docs/guide-docs/client-server-protocol-spec/TOKEN_API.md` (and `TRANSPORT_WS.md`), the TS client sources (`crates/shamir-client-ts/src/` token connect, transports, errors, `core/client/client.ts` `apiTokens`), the existing real-server harness `crates/shamir-client-ts/src/__tests__/e2e-harness.ts` (`SERVER_AVAILABLE`, `serverBinPath()`, spawn helpers) with one existing `e2e-*.test.ts` as the template, the nightly lane `.github/workflows/ts-e2e-nightly.yml`, and the server e2e fixtures `crates/shamir-server/tests/e2e/http_rest/common.rs` and `http_ws/` for how a token owner and grants are seeded (the token session is an ordinary non-superuser principal: it needs grants on `db://default` and `default/main`; interactive transaction commit authorizes Write on the database). CLAUDE.md applies (layout: at most 7 entries per folder, 1000 lines per file; queries only through the typed builder of `shamir-client-ts`, never raw JSON).

## Deliverable

A new e2e suite `crates/shamir-client-ts/src/__tests__/token/` (self-skipping with `describe.skipIf(!SERVER_AVAILABLE)` like the existing e2e suites) that spawns a real `shamir-server` configured with an HTTP listener (plain and TLS with a generated test certificate, as the existing harness already does for its TLS case) and covers, with the TS client only:

1. Token creation: admin creates a token over the SCRAM channel with `client.apiTokens.create`, receives the secret once; `list` never shows the secret; `revoke` and `revokeUser`.
2. Connect by token over **http**, **https**, **ws** and **wss** (Node transports): ping, a write batch, a read batch, a transaction begin/execute/commit, a cursor create/fetch/cancel (where the channel supports it per the spec table); the channels/mode (`read_only`) restrictions: write denied with the typed error for a read-only token; a token restricted to http cannot open ws and vice versa with the documented status/close code (4010-4012 on ws).
3. Browser-style WebSocket (first-frame token, no `Authorization` header) using the browser transport entry (`src/browser.ts`) under Node with the `ws` package; Origin allow-list accept and reject.
4. Revocation: revoke while a ws session is open -> the session is closed with the documented code; subsequent http request with the revoked token -> 401 typed error; expiry behaves the same (use a short TTL token).
5. Error mapping: wrong token, malformed token, unknown channel, request over the size cap: typed `ShamirError`/token error codes as documented.
6. Login by password over HTTP (AUTH2 client against the AUTH1 server): `login(...)` returns a working token client; wrong password -> typed error; the 429 case last.

Validation is by the nightly lane: add a `workflow_dispatch` input or reuse the existing dispatch so CI can run `ts-e2e` on the branch (`gh workflow run ts-e2e-nightly.yml --ref <branch>`); make sure `ts-e2e` builds `shamir-server` release and exports `SHAMIR_SERVER_BIN` so the new suite really runs. Do not weaken or skip any assertion to make the suite pass; if an assertion contradicts the server behavior, record it in the report with the evidence instead of editing the test to match a bug.

## Rules

Only `python -I scripts/ci/check_layout.py` (and `cargo fmt -p <crate> -- --check` for Rust files if you touch any). A child that runs them violates the policy (three children already did and left 2 GB `target/` directories): say so in every child prompt. Every network wait has an explicit timeout; no `setTimeout`-based sleeping to wait for server state (poll with a bounded deadline on observable state).
- NEVER run `git reset` / `checkout` / `clean` / `stash` / `restore` / `rm`, or any git command that mutates the working tree or index; only edit files; the orchestrator commits. No machine-local absolute paths in any file.
- Children only edit files, are awaited, and every touched file is re-read as tsc strict / vitest would. Never finish with a child outstanding.
- Time: run `date` first; stop editing at the time in the run file and report per item DONE / PARTIAL with file:line; write the report to `docs/dev-artifacts/audits/2026-11-02-token-js4/DESIGN.md`.
