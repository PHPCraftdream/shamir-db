## The defect (verified by an independent reviewer)

`rename_table_transition` holds the repository write-admission permit while it drains and copies the source stores and calls `persist` (the catalogue transaction `rename_table_row` followed by the durability flush). If `persist` returns an error AFTER the catalogue transaction committed (for example the system-repo durability flush fails), the `?` returns, the permit is released, and the registration is NOT switched: the table `from` stays registered on the OLD stores and accepts writes, while the durable catalogue already maps `to` to the COPIED stores. After the next boot, or after a retry through `recover_table_rename_with` (which neither drains nor re-copies), the copy wins and every write made in between is lost.

## Required design (use it unless you find a flaw; write any deviation into the note)

Fence, do not re-copy. The copy made under the permit is complete as of that moment. If no write can reach the old stores after it, the copy stays equal to the source and the existing recovery (which switches the registration) is correct.

1. Add an in-memory "rename in doubt" fence to `RepoInstance` (a lock-free set of table names, `scc` or `DashMap` with the Fx hasher per CLAUDE.md; a plain struct field, initialised in the constructor; grep the WHOLE workspace for struct literals of `RepoInstance` and its builders if you add a field to a literal-constructed type).
2. Raise the fence for `from` (and remember `to`) as soon as `persist` has been entered and returned an error, BEFORE the permit is dropped. While the fence is up, every path that resolves the table by name or by token for new work (`get_table`/`table_by_token`/`table_by_token_if_live` and whatever the write path uses to obtain a `TableManager`) fails with a retryable `DbError` that names the in-doubt rename (reuse an existing error variant such as `DbError::Conflict` or `Internal` with a stable message prefix; do not invent a public variant unless needed). Reads that already hold a `TableManager` are not affected.
3. Clear the fence: in `recover_table_rename_with` after the registration switch succeeded (and after the catalogue row check), and in a successful normal rename of the same names. A process restart clears it by construction and is safe: at boot the catalogue (committed) maps `to` to the copied stores and `from` has no row, and nothing could write to the old stores while the fence was up.
4. Distinguish the clearly-uncommitted failure so availability does not degrade needlessly: if `persist` fails with an error that is known to have happened BEFORE the catalogue transaction committed (validation, conflict, injected fault before commit), do not raise the fence. Implement this with a small typed marker (for example `persist` returns `DbResult<bool>` and the closure in `table_management.rs` wraps only the post-commit failure, i.e. the durability-tail flush, in a dedicated error constructor or variant that `rename_table_transition` recognises). If that classification cannot be made reliable from the code, raise the fence on EVERY `persist` error and document that a failed rename needs a retry or a restart.
5. Tests (extend `durability_tail_failure_retry_...`, one topic per file under the existing `tests/catalogue/`): (a) tail failure injected after the commit, then a write to `from` is rejected with the in-doubt error, then the retry via the recovery path succeeds and `to` contains exactly the rows that existed at the failure, `from` is gone; (b) failure injected BEFORE the commit leaves `from` fully writable and `to` absent (if you implemented the classification); (c) after (a) without a retry, a simulated restart (drop and reopen the database on the same directory, as the existing tests do) finds `to` with all rows and no `from`; (d) a successful normal rename after a failed one clears the fence; (e) the missing RENAME rejection regression for an over-long generated store name (revision 1 added the validation but no rename-specific test).
