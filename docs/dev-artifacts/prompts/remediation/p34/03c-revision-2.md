## Goal

Ship a sub-stage that is strictly safer than master on every interleaving and touches only `shamir-engine`:

1. From the moment a table rename freezes its source until the rename returns, the source accepts no write through any path that resolves the table while it is registered. Covered paths: non-tx CRUD, the tx commit pipeline (including transactions whose only effect on the source is index postings, counter deltas or staged vectors), and DDL through a `TableManager` clone obtained before the rename.
2. On success, the old source stays frozen and detached forever. A pre-rename clone then fails every CRUD write and every DDL with `DbError::MigrationFrozen` instead of silently writing into orphaned stores.
3. The copied stores contain every version allocated before the freeze (visibility wait before the drain) and the live record count (counter flush before the copy).
4. Every failure, including an error from `persist` and cancellation of the rename future, ends in master's state: the source is attached, unfrozen and writable, the destination stores are orphaned, and the original error is returned unchanged.

The only behaviours this adds are explicit rejections (`MigrationFrozen`, a retryable visibility-timeout conflict). It never acknowledges a write that master would not, and it never leaves a registration or catalogue state that master could not reach.

## Verdict on stop E (orchestrator re-verification; do not redo)

- **Stop E is real, but narrow.** The commit pipeline gates a table only if its token is in `write_set` or `unique_guards` (`prelock.rs:261-284`). Four sidecar sets are materialised for their own tokens with no freeze check: `index_write_set` (5c), `counter_deltas` (5b), `staged_vectors` and `staged_vector_deletes` (5d delta into the table's `info_store`). A `TxContext` whose sidecar tokens are not a subset of `write_set` therefore mutates a frozen table.
- **Reachability.** Every production staging path in `shamir-engine` keeps "sidecar token implies a `write_set` entry": `stage_mutation` calls `ensure_table_staging` first (`tx_support.rs:159-178`), the bulk inserts call it before merging (`tx_insert.rs:367,388`, `:582,591`), and the prelock re-derivations append only for tables with staged rows (`base_index.rs:77-80` documents this). The invariant is broken by direct pushes to the `pub` field, which today only tests and benches make (all of them for a token they also staged; verified by reading every `index_write_set.push` site). It is also broken by one production shape: `insert_tx_many*` and `update_tx*` call `tx.stage_vector` before `ensure_table_staging` / `stage_mutation`, with fallible `?` and `.await` points in between (`tx_insert.rs:323-361`, `tx_update.rs:278-356`). An error or cancellation there leaves `staged_vectors[token]` without `write_set[token]`, and if the caller then commits the transaction, Phase 5d writes a vector delta into that table's info store, ungated. Whether an interactive transaction can commit after a failed statement was NOT verified.
- **Fix.** Make the prelock token set the union of `write_set` keys and every sidecar token (decision S1). The fix is behaviour-neutral for every existing test (all manual pushes reuse a staged token), adds one O(|index_write_set|) pass to the commit (the same order as the WAL encoding the commit already does), and closes stop E for the rename freeze and for the existing online-migration freeze at once.
- **Q7 (revision 1):** accepted. Stop D is not established. `version_allocation_high_water_mark()` read after the freeze returns, then `await_visible` on it, covers every version allocated before the freeze (the floor waits for orphans awaiting replay too). The vector-delta half of 5d runs after the drain guards drop but before settlement, so the wait covers it.
- **Q9:** accepted, recorded. **Q10:** accepted as the work list for S2 below. The orchestrator re-derived it with `rg -n "fn \w+_admitted" crates/shamir-engine/src/table` (35 hits, non-test) and classified all of them in S2.
- **New gap M5 (missed by the original brief and revision 1):** after a SUCCESSFUL rename, a transaction staged through a pre-rename clone and committed afterwards is not gated. `remove_table_inner` drops the source token from `token_names` (`repo_membership_impl.rs:330-334`), so `table_by_token_if_live` returns `None` and the prelock skips it. The rows land in the orphaned source stores. Master behaves identically, and so does DROP TABLE. This is out of scope here and listed for 03d.

### Failure modes that remain (write this table into the note's design section)

| # | Situation | Sub-stage behaviour | Master behaviour |
|---|---|---|---|
| M1 | `persist` fails after the catalogue tx committed (WAL outcome unknown, `WalDurability` turned into `Ok` and then the flush fails, flush error) | Source reattached and unfrozen, `Err` returned. Writes and DDL accepted by `a` afterwards are lost on restart (boot registers `b` on the stores copied at the failure) or on a retry that takes the recovery branch (switch without re-copy). | Identical |
| M2 | After M1, `b` is free in memory | Create / drop / rename touching `b` can overwrite or remove the committed destination row. | Identical |
| M3 | Rename future cancelled during `persist` | As M1 (abort on drop). | Identical (no freeze at all) |
| M4 | Repo rename during M1 | The committed destination row can be stranded (revision-1 R9 analysis). | Identical |
| M5 | Tx staged through a pre-rename clone, committed after a successful rename | Not gated (the token no longer resolves); rows land in orphaned stores. | Identical (also DROP TABLE) |
| M6 | Wire code of rename errors | `code: None` (`admin_table_index.rs:255-259,294`). | Identical |
| M7 | `RecordCounter` writes through a stale handle | Land in the orphaned `__info__`; metric only. | Identical |

New, all explicit and retryable: writers to `a` during a rename get `MigrationFrozen` (master accepts them, and on success silently loses those that miss the copy); stale-clone CRUD and DDL after a successful rename get `MigrationFrozen` (master: silent loss into orphaned stores); a rename can fail with the visibility-timeout conflict while an unrelated version stays unsettled (Q11), with no state change; renaming a table under online migration fails with `MigrationFrozen`; a sidecar-only commit to a frozen table fails with `CommitError::MigrationFrozen` (master: applied ungated). Why this is strictly better: every failure path restores the exact pre-call state master leaves, and every other new behaviour replaces either a silent loss with an explicit error or an ungated mutation with a rejection.
