# TOKEN-JS0 - revision 1: the browser MUST get WebSocket (owner requirement)

Your note `docs/dev-artifacts/design/token-client-js.md` is good work, but its recommendation for the browser WebSocket question ("browser HTTP-only") contradicts the owner's requirement. The owner asked explicitly: the JavaScript client needs BOTH transports, HTTP and WebSocket, for the BROWSER and for Node.js. HTTP-only for browsers may be an interim step, never the end state. A browser `WebSocket` cannot set `Authorization`, so the existing header-authenticated endpoint `/shamir/v1/ws` does not work for browsers; therefore design a browser-capable token WebSocket and make it the recommendation.

## The design to work out (recommended by the owner's delegate, you detail and attack it)

Mirror the pattern the project already uses for SCRAM (TRANSPORT_WS.md section 1: two endpoints, the endpoint determines the policy, no user-agent sniffing):

- `GET /shamir/v1/ws` (existing, native clients incl. Node.js): bearer in the `Authorization` header, verified before `101`. Unchanged.
- NEW `GET /shamir/v1/ws/browser` (browsers): the token travels as the FIRST binary frame after `101`, never in the URL, never in `Sec-WebSocket-Protocol`, never in a cookie. Everything the header path guarantees must still hold, so specify precisely:
  1. **Origin is REQUIRED** and must exactly match the listener's `browser_origin_allowlist` before `101` (a browser always sends it; an empty allowlist rejects every request); missing/mismatching Origin: `403`/`400` before the upgrade, exactly as the SCRAM browser endpoint does (TRANSPORT_WS.md section 9). Reject cross-site WebSocket hijacking by construction. Also bind `Host`.
  2. **Pre-authentication limits** (the socket exists before the token is checked): a global cap and a per-subnet cap on upgraded-but-unauthenticated sockets (numbers with memory arithmetic), a short first-frame deadline (propose 5 s, reuse `auth_init_timeout_ms` naming conventions), the first frame is exactly one binary frame of at most a few hundred bytes (propose the wire shape: msgpack map `{ "token": <71-byte string> }`, strict decoding, unknown keys rejected, no trailing bytes), a pre-auth frame size limit enforced by the transport BEFORE allocation, no database handler is reachable before authentication, pings allowed but no data frames.
  3. **Verification** follows TOKEN_API.md section 5 exactly (same MAC check, same dummy-work for unknown ids, same state checks, same strict owner floor), the same separate per-subnet failure limiter (never rejects a verified token), the same uniform failure: on ANY failure close with ONE registered code (reuse `4000 authentication_failed` or propose a new code; justify), identical timing class, no distinguishing detail; audit event with the same sampling/aggregation rules; a token whose `channels` excludes `ws` is a closed socket with a distinct, post-verification code (like `token_channel_denied`).
  4. **Success**: the server answers with the same binding frame as the header path (`{ ok, sid(bin32), expires_at_ns }`) and the connection continues exactly like the header path (same envelopes, same single accepted `sid`, same cancellation/revocation codes 4010-4012, same socket accounting).
  5. **Redaction**: the first frame is never logged, never echoed, never put into spans/audit; add the redaction test to the checklist.
  6. **Honest comparison** with the header path: the bearer is equally exposed to anything that can read the TLS stream or the page; the extra cost is an unauthenticated upgraded socket, bounded by 2; there is no URL/log/Referer exposure. State what remains worse than the header path and why it is acceptable. Also state the plaintext rule: the same listener-level rules as TOKEN_API.md section 11 apply, a browser on `ws://` loopback only.
  7. **Replay/idle**: a stolen frame is a stolen token (bearer), no new weakness; the frame carries no extra signature in v1.
- Node.js keeps using the header endpoint (preferred); it MAY use the browser endpoint only if you see a reason (say so).
