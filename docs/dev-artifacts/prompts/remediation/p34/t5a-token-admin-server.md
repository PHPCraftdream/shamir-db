## Acceptance

1. Four new `DbRequest` variants with wire structs in `shamir-query-types` (field names from section 12: `label`, `ttl_secs?`, `mode?`, `channels?`, `databases?`, `for_user?`, `hmac?`; list: `for_user?`, `hmac?`; revoke: `id`, `hmac?`; revoke-user: `user?`, `hmac?`) and matching response structures (the create response carries the secret `token` exactly once; list rows never carry secret, MAC or hash; `id` encoded as in the CLI: base64url of 16 bytes). Update EVERY exhaustive match on `DbRequest` across the workspace (`rg "DbRequest::"` including tests, benches, client crates, the WASM bridge) and every struct literal of changed types; the msgpack wire encoding follows the neighbouring variants (look at how an existing admin variant such as `CreateScramUser` is encoded and tested, including any wire-compat/golden tests that enumerate variants).
2. Handler implementation wired to the shared `TokenService` held by the server handle:
   - self-service without HMAC;
   - `for_user` / listing others / revoking others / `RevokeUserTokens` of another user require superuser AND a valid HMAC (reuse the `CreateScramUser` mechanism; add the canonical encoding for these operations as section 12 asks, documented in the spec: update `TOKEN_API.md` section 12 with the exact field names and the HMAC canonical encoding, no change of semantics);
   - non-superuser with `for_user` -> `permission_denied`; foreign `id` revoke by a non-superuser -> `token_not_found`; `RevokeUserTokens` of another user by a non-superuser -> `permission_denied`;
   - `tokens.allow_self_service: false` blocks only self creation; `tokens.max_per_user`, `max_ttl_days`, `default_ttl_days` and label uniqueness among active tokens (the service/CLI already enforce what they enforce: reuse, do not duplicate);
   - a browser-bound session (binding mode 0x02) cannot create (`token_browser_session`);
   - the race re-check after creation (session still valid against the owner floor; if not, revoke the fresh token and fail with the session error);
   - a TOKEN session can call none of the four (`token_request_denied`);
   - read-only replicas: create/revoke refused with the appropriate existing "read-only node" error, list still allowed (check how node mode is exposed to the handler);
   - audit events `api_token_created`, `api_token_revoked`, `api_token_user_revoked` through the existing audit writer (section 13 fields, no secrets) and the existing counters.
3. Password change / role change / user deletion invalidation (rule 4) is already handled by the owner floors of T2b: verify by reading that the hooks exist and add a test only if cheap; do not redesign.
4. Tests (you cannot run them; they must compile and be sturdy): unit tests of the wire (round trip, golden bytes where neighbours have them); handler tests for every rule above using the existing in-process handler fixtures (see how `CreateScramUser` and the TokenService tests build a handler and a store), including: the secret appears once and never in list; label uniqueness; limits; HMAC missing/wrong for superuser-on-behalf; self-service disabled; token session denied; browser session denied; replica read-only; the race re-check (use the service's clock/seam if one exists, otherwise test the re-check function directly).

Out of scope: builders and clients (T5b), HTTP login issuance (AUTH1), the REST/WS channels, spec parts other than section 12.
