# AUTH-PRE - native authentication prerequisites for login over HTTP

Normative source: `docs/guide-docs/client-server-protocol-spec/TOKEN_LOGIN_HTTP.md` (sections "Shared LockoutStore", the prerequisites paragraph near the end) and `AUTH_PROTOCOL.md` 5.1.1 (KDF bounds). Read both first, then CLAUDE.md. Scope is only the three prerequisites below; HTTP endpoints, `kdf_override` handling and handshake changes belong to AUTH1.

Decision for the open point (4): native login does NOT adopt the HTTP-style pre-challenge backoff. Native keeps exactly today's behaviour (only an active pair lock is rejected before the challenge, backoff is applied as post-proof padding). Do not touch `crates/shamir-server/src/sync/connection/handshake.rs`.

## Items (in this order, each fully with its tests before the next)

1. `crates/shamir-connect/src/server/limits/lockout.rs` `subnet_of`: IPv4-mapped IPv6 (`::ffff:a.b.c.d`) must normalize to the IPv4 /24 prefix (and IPv4-compatible forms are NOT mapped). Table-driven test (multi-line literals): mapped and plain IPv4 of the same /24 give the same key; real IPv6 /64 unchanged; boundary addresses.
2. Bounded `LockoutStore` (same file area; keep the public API used by the native handshake source-compatible): exactly 8,192 fixed pair slots; pair key = existing username digest + normalized prefix; at most 64 pairs per base prefix (/24 IPv4, /64 IPv6) and 512 per parent (/16 IPv4, /48 IPv6); no aggregates; active hour-locks count against both quotas and are never evicted; on an exhausted source quota evict the lowest-count then oldest unlocked pre-threshold pair within every exhausted owner quota; at global capacity with no exhausted source quota evict the globally lowest-count then oldest unlocked pre-threshold pair; if there is no eligible candidate DROP the accounting for the new pair (never deny, never claim a proof was verified); updates of already retained pairs continue when full; quota checks by a bounded scan of the fixed slots (no separate quota map); snapshot load applies the same caps (active locks first, then highest-count pairs, overflow dropped, active lock and failures of the same key use one slot). Existing curve (100 ms x 2^(count-1) capped 30 s, 50th failure locks one hour, five-minute idle reset) and `unlockUser` semantics unchanged. If the current store is a map, replace the storage, keep behaviour for the existing tests; if the file would pass 1000 lines, split into a new subfolder module (`mod.rs` re-exports only). Tests: eviction order, quota exhaustion, active lock never evicted, drop when no candidate, snapshot load caps, existing behaviour preserved.
3. Client KDF lower bounds before Argon2: Rust `crates/shamir-client` (see `src/client/connect.rs` and where `kdf_params` are validated; today only the upper bounds are checked) and TypeScript `crates/shamir-client-ts` (`src/core/protocol/scram.ts` / `protocol.ts` / `client-internals.ts`): reject `memory_kb < 19456`, `time < 2`, `parallelism < 1`, version != 0x13 and the existing upper bounds, before any Argon2 work, with the local error `kdf_params_rejected` (reuse the existing error path/name); both ends of every range accepted. Tests on both sides (boundary values, Argon2 never invoked on rejection: use a spy/counter where the code allows it). Check that existing tests and the test servers use parameters at or above the floor; raise test parameters only if they are below the floor and say so in the report.
