# TOKEN-T3b - shamir-server: the HTTP listener (`kind: http`), ScopedHandler, REST integration

Sources, read in this order: `docs/guide-docs/client-server-protocol-spec/TOKEN_API.md` (normative and already amended: sections 1 channels, 3-4 record/representation, 5 verification, 6 principal and rights, 7 allowlist (deny by default), 8 error codes, 9 REST, 11 transport security, 13 audit/metrics/logs, 15 test checklist; sections 10 (WebSocket) are context only: WS is stage T6), `docs/dev-artifacts/design/token-api-rest-ws.md`, then the code this stage connects: `crates/shamir-transport-http/src/{lib.rs,gate.rs,config.rs,server/*}` (stage T3a: `serve`, `TokenGate`, `RestExecutor`, `ConnAdmission`, `HttpServerConfig`, `HttpLimits`, `EndpointSet`, `GateDecision`, `ExecOutcome`, `ExecStatus`, `PeerInfo`, `AuthHeader`), `crates/shamir-server/src/security/tokens/*` (stage T2b: `TokenService`, `verify`, counters, audit, the session store, `SessionCanceller`), `crates/shamir-connect/src/server/auth/token/*` (token core: `verify_token`, `Verified`, `VerifyFailure`, `TokenRecord`, `TokenMode`, `TokenChannels`, `Endpoint`), the listener plumbing of the server (`src/boot/config.rs` `ListenerKind` and `ListenerConfig`, `src/engine/server/server_launcher/{launch.rs,listeners.rs,accept_loops.rs}`, `ServerHandle`), the existing request handler and permission path used by native connections (find how `DbRequest` is executed under a session's principal: `DbHandler`, `handle_request`, the coarse gate and the per-operation permission checks), `CLAUDE.md`.

## Goal

A running `kind: http` listener that serves, for a bearer token, exactly the REST surface of TOKEN_API sections 5-9, on top of the already merged T3a transport and T2b service. Observable acceptance: the unit and integration tests below pass in CI and, with a listener configured, `POST /shamir/v1/request` with `Authorization: Bearer <token>` executes an allowed `DbRequest` as the token's principal and answers with the specified msgpack body and status.

In scope:
- `ListenerKind::Http` in the server config (parse, validate, defaults, example in `deploy/` only where the other listener kinds are documented the same way): bind address, TLS (reuse the existing TLS configuration pieces; TLS 1.3 only for this kind), `allow_plaintext_remote` / `allow_plaintext_write` rails as TOKEN_API section 11 says, `browser_origin_allowlist` is NOT used for REST, limits mapped onto `HttpLimits`, `trusted_proxies` only if section 11 requires it for REST (check the text; WS and login own the rest). Startup validation errors with clear messages (plaintext on a non-loopback bind without the explicit flag; the read-only/write rails).
- The gate: an implementation of `TokenGate` over `TokenService::verify` (header bytes from `AuthHeader`, `Endpoint::Rest`, current clock), returning the `GateDecision` variants with the uniform 401 for every failure class of section 5, 403 with the application error code for verified-but-denied cases, 429/503 for the cases section 8 names; `still_valid` revalidates the grant against the service/mirror (revoked, expired, owner floor) without touching storage.
- The executor: an implementation of `RestExecutor` that decodes the msgpack request, applies the allowlist of section 7 (deny by default, a single closed enum of permitted operations, databases allowlist of the token, mode read_only/read_write, plaintext-write rail), runs the request through the SAME handler path as a native connection under the token owner's principal and roles snapshot (a `ScopedHandler` wrapper type that owns the scope checks and delegates to the existing handler; no duplicate permission logic: reuse the existing coarse gate and per-operation checks), maps the outcome to the response body and `ExecStatus`, keeps the hold value until the response has been written (so counters and sessions release), and never returns the token, MAC or internal error text.
- Audit, metrics and logs of section 13 for this path (fixed vocabulary labels, no secrets, no peer-controlled strings), using the T2b counters and the existing audit writer and metrics registry.
- Wiring into `ServerLauncher::launch`/`listeners.rs`: build the listener from config next to the other kinds, hand it the `TokenService` from the handle, shut it down with the server cancellation token, release the data dir lock and stores in the same order as the existing listeners (look at the shutdown-truth tests), and expose nothing else.

Out of scope (separate stages): WebSocket channel (T6), the login routes (AUTH1), online token administration requests (T5), the offline CLI (T4), `shamir-client` changes, JS client.

## Tests (write them; you cannot run them)

Unit: the gate decision table (every failure class of section 5 yields the same 401 body and status; revoked and expired and owner-floor cases; channel and mode denials; plaintext-write rail), the executor allowlist (every permitted operation, a representative sample of denied ones including admin and token-management operations, database allowlist, read-only mode rejecting writes with the specified code), body and status mapping, secret redaction in errors and logs. Integration (tokio, loopback plaintext listener with an explicit test config, one TLS case if the existing helpers make it cheap): create a token with `TokenService`, call ping and an allowed request, revoke and see the next request fail with the uniform 401, shut the listener down and see the stores released. Follow the layout rules: tests under `tests/` folders, one topic per file.
