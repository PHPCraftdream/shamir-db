1. P1 - rename failing after the catalogue commit loses writes. In `RepoInstance::rename_table_transition` (`crates/shamir-engine/src/repo/instance/repo_instance/catalog.rs`, the function around line 360-395) the `persist` callback performs the atomic catalogue transaction (`SystemStore::rename_table_row`). If `persist` returns an error AFTER that transaction committed (for example `flush_system_repo_durable` fails: the "durability tail"), the in-memory registration is not switched and the write permit is released: writes to `from` keep landing in the OLD stores, while the durable catalogue already maps `to` to the COPIED stores. At the next boot, or on a retry through `recover_table_rename_with` (which neither drains nor re-copies), the stale copy wins and later writes are lost. Required behaviour, pick the smaller correct design and write it down in the note: (a) once `persist` has been entered and returned an error, the source table is fenced for writes (a retryable `DbError` that names a rename in doubt) until the rename is resolved by a retry/recovery or the process restarts, so no write can land in the old stores; and (b) `recover_table_rename_with` re-drains the live source (if still registered) and re-copies the source stores into the destination ids before it switches registration, so the retry converges even if rows were written between. Extend the existing durability-tail test (`durability_tail_failure_retry_...` in `crates/shamir-db/src/shamir_db/shamir_db/tests/catalogue/unique_store_names_tests.rs`) with a write attempted between the injected failure and the retry (it must be rejected with the in-doubt error, or, if you chose to allow it, it must be present under `to` after the retry), and with a restart-style variant if the harness allows.
2. P2 - brand-new inline repository tables still use raw names forever. Tables created through the `add_repo` inline configs (`crates/shamir-db/src/shamir_db/shamir_db/db/db_management.rs`, around the `inline_tables` capture, line ~432) and through `CREATE REPO ... TABLES` (`crates/shamir-server/src/.../admin_db_repo.rs`, around line 415; find it with grep) keep `store_id: None`, so the original stale-data resurrection bug still applies to them. Assign `with_new_store_id()` to inline table configs that lack an id BEFORE the `inline_tables` capture and before `db.add_repo`, so the catalogue rows carry the id. Two tests (`unique_store_names_tests.rs`, around lines 446 and 491) use inline tables as their "legacy" fixture: rebuild that fixture with an explicit legacy catalogue row (no `store_id`) written through the system store, so they still test the legacy path.
3. P3 - longer store names. The generated suffix (`--<base58>`) adds up to 24 bytes against fjall's 255-byte store-name limit (`crates/shamir-engine/src/repo/instance/repo_instance/table_store/names.rs`). Validate at CREATE/RENAME time, before anything is persisted: the longest of the three generated store names (data, info, history) for the new id must fit 255 bytes, otherwise return `DbError::Validation` that says the table name is too long. Test it at the boundary (a name that just fits and one byte more).
