# TOKEN-JS3 - public token connect API for shamir-client-ts

Goal: glue JS1 (HTTP token transport, `src/entry/token-*.ts`, `src/platform/token/http-*.ts`) and JS2 (WebSocket token transport, `src/entry/ws/*`, `src/platform/token/socket-*.ts`) into the public API. Read first: `docs/dev-artifacts/prompts/remediation/p34/js0-token-client-design.md` and its revisions (the design is normative, in particular the section on the public API), the audit notes `docs/dev-artifacts/audits/2026-11-01-token-js1-http/DESIGN.md` and `.../token-js2-ws/DESIGN.md`, `docs/guide-docs/client-server-protocol-spec/TOKEN_API.md` (client rules), `CLIENT_BROWSER.md`, then CLAUDE.md. Then read the current public entry points `crates/shamir-client-ts/src/index.ts` (Node), `src/browser.ts`, `src/platform/{node,browser}.ts`, `src/core/types` (`ConnectOptions`), the existing SCRAM `connect` implementation and its tests.

## Acceptance (observable)

1. `ConnectOptions` gains an authentication-by-token variant (an `ApiToken` or token string accepted via the existing `ApiToken` handle; the secret is never logged) with channel selection `http | ws`: explicit option or derived from the URL scheme (`http(s)://` -> REST, `ws(s)://` -> WebSocket); contradictory or unsupported combinations (token + SCRAM credentials, token over a scheme without TLS where the design forbids it, browser + `allow_self_signed` etc.) are rejected with typed configuration errors BEFORE any I/O.
2. `connect(...)` in Node (`src/index.ts`) and in the browser (`src/browser.ts`) return the one public `ShamirClient` model over both token transports: db/execute/subscription methods work where the transport supports them; what HTTP cannot do (cursors, subscriptions, interactive transactions - see JS1 rejection list) throws the typed error already defined in JS1, never silently degrades. Platform factories live in `src/platform/{node,browser}.ts`; the browser bundle graph has no Node modules (the existing `token-browser-graph` test style must still pass and be extended to the new entry).
3. New types and errors are exported from the right entry points (no leaking of internals); `ApiToken` redaction (`toString`, `toJSON`, `util.inspect`, error messages, structured clones) is covered by a test over the public surface.
4. The existing SCRAM path is untouched in behaviour: all existing tests keep their meaning; add a backward-compatibility test that SCRAM `connect` overloads still type-check and run as before.
5. Tests (vitest, under `__tests__/`, multi-line literals): connect contract for both platforms with fake platforms/transports (no network): channel selection by scheme and explicit, configuration errors, token redaction, unsupported-over-HTTP operations, browser/Node entry isolation, SCRAM compatibility. End-to-end against a real server is stage JS4, not here.

Non-goals: login by username/password over HTTP (AUTH2), new transports, new dependencies, `package.json` version changes, docs (JS5). `package.json` `exports`/`browser` fields may be touched only if the design requires a new public entry; justify it in the note.
