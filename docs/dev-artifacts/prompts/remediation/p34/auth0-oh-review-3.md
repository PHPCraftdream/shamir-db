## Blocking

NEW-1 (section 3 LockoutStore aggregate paragraph, section 4 BEGIN gate, AUTH_PROTOCOL 5.2.5 and 8.4 amendments). The aggregate gate applies only to usernames with NO retained pair, so an honest user with a clean history is permanently in the gated class, while an attacker who fails once per (username, subnet) gets a retained pair and is exempt. About two failures per minute from one address keep a parent aggregate armed: HTTP BEGIN answers 429 for every clean-history username under that /16 or /48, and native logins get a +30 s pad. A NAT'd /24 with more than 64 users reaches this state from ordinary typos. DECISION: DELETE THE AGGREGATES. Pairs only. There is no aggregate state, no aggregate threshold, no aggregate gate, no aggregate eviction, no "fold into parent", no aggregate snapshot. When the pair table (or a source's pair quota, see NEW-2) is full: evict unlocked pre-threshold pairs lowest-count/oldest first, never an active lock; if nothing is evictable, DROP accounting for the new pair (state this plainly). The guessing-rate bound for pairs that are not tracked is the CREDIT hierarchy at BEGIN (state this residual explicitly: brute force against an untracked pair is limited by credits only). Rewrite the AUTH_PROTOCOL 5.2.5 and 8.4 amendments and the `unlockUser` paragraph (it now simply clears the pair) accordingly; remove every mention of aggregates from the config table, metrics, tests, checklist and byte budget, and redo the byte-budget arithmetic of section 3 once at the end (the LockoutStore memory shrinks: say the new figure and re-sum the total).

NEW-6 (section 3 "concurrent login tasks 1,024" and section 7 `Expect: 100-continue`). The concurrent-task/input-slot pool is global with no per-source cap, no eviction rule and no full-pool response, and it is reserved BEFORE `100 Continue` and therefore before any body-dependent charge. Only ARRIVAL (160/s per /48) bounds occupancy, and 160/s x 10 s body timeout = 1,600 slot-seconds exceeds 1,024: one /48 holding `Expect: 100-continue` requests shuts HTTP login off for everyone. FIX (all of it): (a) debit the source-keyed ARRIVAL and CREDIT buckets (both are body-independent) BEFORE reserving the slot; (b) per-source concurrent-slot caps mirroring the pending caps (state the numbers for every tier: IPv6 /64, /56, /48 and IPv4 /24, /16, symmetric where the address space is comparable, with arithmetic that shows no single /48 or /16 can take more than a fixed fraction of the 1,024 slots); (c) the response when the pool is full: HTTP 503 `server_busy` with `Retry-After`, no state allocated; (d) the body deadline is short (state it) and slots are released on every terminal path.

## P2

NEW-2 (section 3 LockoutStore pair paragraph): the per-parent quota used for ARRIVAL/CREDIT (k=32) is missing for the 8,192 pair slots; "at most 64 pairs per normalized subnet" lets 128 subnets of one /48 or one /16 fill the table, and active locks are never evictable for an hour. FIX: a per-parent pair-slot quota with arithmetic (for example at most 512 pair slots per /48 and per /16, so at least 16 parents are needed to fill the table); active locks count against the owner's quota; overflow of a quota drops accounting for the new pair (NEW-1).

NEW-3 (section 4, the finish-time `last_fail > begin_time` path): "skip proof and register failure" counts a failure for a proof that was never verified, double-counts the triggering failure and lets an honest retry drive its own pair to the one-hour lock. FIX: on that path return the generic 401 WITHOUT registering a failure and WITHOUT advancing `last_fail`; only a verified-bad proof registers.

NEW-4 (section 3 credit tiers and the acceptance checklist): the IPv4 /16 credit tier equals the sum of its 32 permitted /24 children (32 x 10 = 320), so it never binds, and an IPv4 attacker gets twice the IPv6 /48 spraying rate. FIX: set the IPv4 /16 tier to 160/160 like the IPv6 /48 (or justify an asymmetry in one sentence), and list every tier (IPv6 and IPv4) in the checklist.

NEW-5 (section 3 pending entries): two different per-base-prefix limits for the same quantity ("per-source caps /24 16, /64 16" and "outstanding handshakes 10/base prefix"). Keep one number, delete the other.

NEW-7 (section 4 gate order vs section 3 credit debit): state the order once: ARRIVAL, then CREDIT debit, then the pair backoff/lock gate, then state allocation; the CREDIT debit is not refunded on a 429.

NEW-8 (section 9, "Pair backoff and active lock precede challenge; native response stays silent"): wrong for the code. `crates/shamir-server/src/sync/connection/handshake.rs` (around line 219) checks only the active pair lock before the challenge; the backoff is applied after the proof as a latency pad (`target_ms = target_constant_time_ms().max(backoff_ms)`, around line 936). Re-read both places and reword: native checks the active lock pre-challenge and pads after the proof; the HTTP pre-challenge backoff gate is new behaviour for HTTP only and native adoption is a separate decision (task AUTH-PRE).

NEW-9 (section 10): AUTH_PROTOCOL 14.4 says lockout state is never disclosed; HTTP BEGIN 429 with `Retry-After` discloses it. Add a 14.4 amendment with the same transport-scoped exception wording as the 8.4 amendment (anchor quoted from the current file).

NEW-10 (sections 3 and 10): the LockoutStore snapshot (`LockoutSnapshot { failures, lockouts }`, persisted about every 60 s, rehydrated at boot, see `lockout.rs`) is not mentioned. State: pairs and active locks are snapshotted as today; on load the same caps apply in priority order (active locks, then highest-count pairs), overflow is dropped; add the same note as an amendment to the AUTH_PROTOCOL/IMPLEMENTATION_GUIDE paragraph that describes the snapshot (find it, quote the anchor).

NEW-11 (section 1.1 username canonicality): the SDK must apply AUTH_PROTOCOL 15.3 (NFC and case mapping, Unicode version pinned there) locally before sending; a 400 for a non-canonical username then indicates a client bug and not an authentication failure. Say so, cite the pin.

NEW-12 (section 4 metrics): add `shamir_login_http_accounting_dropped{reason}` (fixed reason vocabulary: pair_quota, pair_table_full, arrival_table_full, credit_table_full, pending_full) and an occupancy gauge for the pair table (count only, no identity).
