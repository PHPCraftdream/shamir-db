# TOKEN-T5b-Rust - Rust builders and typed `shamir-client` methods for online API-token administration

State: this branch starts from `fix/p34-t5a-token-admin` (T5a, not yet on master). T5a added the server side: four `DbRequest` variants `CreateApiToken`, `ListApiTokens`, `RevokeApiToken`, `RevokeUserTokens` and the responses `ApiTokenCreated`, `ApiTokensListed`, `ApiTokenRevoked`, `ApiUserTokensRevoked` (inline variants in `crates/shamir-query-types/src/wire/db_message.rs`), the typed `ApiTokenMode`, `ApiTokenChannels`, `ApiTokenView` (`crates/shamir-query-types/src/security/auth/token_admin/`, re-exported as `shamir_query_types::wire::token_admin`), the canonical HMAC v2 encoding with op tags `0x0020..=0x0023` (`canonical_db_request` in `crates/shamir-query-types/src/security/hmac.rs`), and the shared 35-vector fixture `crates/shamir-query-types/test-vectors/admin_hmac_v2.json`. No Rust client and no builder exists for the four operations yet.

## Goal

A Rust caller holding a SCRAM `shamir_client::Client` can create, list and revoke API tokens (its own, or on behalf of another user when it is a superuser) without assembling any `DbRequest` by hand and without knowing the HMAC plumbing: the requests are produced by builders in `shamir-query-builder`, the client signs every one of them with the session-derived HMAC key exactly as `create_scram_user` / `set_replicator` do, sends it, and returns typed results. The creation result is a typed struct whose secret is a redacting `SecretString` that appears exactly once; listing rows never carry a secret. The canonical bytes and tags the client produces are proven equal to the shared vectors, and the wire bytes the builders produce are proven equal to the existing golden bytes.

## Decisions taken (the orchestrator owns design; deviations go into the note with a reason)

1. **Typed creation payload on the wire.** Add `CreatedApiToken` (fields exactly as today's inline variant: `id`, `token: SecretString`, `label`, `owner`, `mode`, `channels`, `databases`, `created_at_ns`, `expires_at_ns`; derives `Debug, Clone, Serialize, Deserialize`, no `deny_unknown_fields`) in a new file `crates/shamir-query-types/src/security/auth/token_admin/created.rs`, re-export it next to `ApiTokenView`, and change the variant to `DbResponse::ApiTokenCreated(CreatedApiToken)`. Reason: one typed value for server, Rust client and the later napi binding (T9); DbResponse is internally tagged (`tag = "kind"`), so a newtype variant over a struct serializes to the same map as the struct variant - this must be PROVEN by a test (acceptance 2), not assumed. Update every construction and match site (item 7 of "Read first" plus whatever `rg` finds).
2. **Builders return `DbRequest` and carry an optional `.hmac(tag)`; `build()` is infallible.** Unlike the `ddl` builders (which fail with `MissingHmac`), `hmac` is optional on the wire and only the server can know whether it is required (a `RevokeApiToken` id may belong to another user). Builders derive `Clone` so a signer can build the unsigned request, canonicalise it, and rebuild with the tag. No client-side validation of label/ttl/id in the builders (the server is the authority; T5a returns `token_ttl_invalid`, `token_not_found`, etc.).
3. **The client always signs all four operations.** Self-service calls do not need the tag, but the server ignores a supplied tag on paths that do not require it (`logic.rs`: `verify_hmac` runs only for delegated/foreign targets) and the client cannot know whether a revoked id is foreign. Always signing keeps one code path and matches `create_scram_user`/`set_replicator`.
4. **Builders live in `crates/shamir-query-builder/src/wire/token_admin/`**, exposed as `shamir_query_builder::token_admin` (re-export in `lib.rs`), with a module doc explaining why this is a second narrow exception to the crate's "no `DbRequest`" rule (same argument as `read/cursor.rs`: without it callers would hand-assemble `DbRequest` literals, which the builder-only rule forbids). Update the crate doc's module list and its "Scope boundary" paragraph by one sentence each. Reason: `src/` (7), `src/read/` (7), `src/ddl/` (7) and `src/batch/` (7) are full; `src/wire/` has 5 entries.
5. **Builder API** (names may be adjusted only if `rg` finds a collision; record any change):
   - `create_api_token(label) -> CreateApiToken` with `.ttl_secs(u64)`, `.mode(ApiTokenMode)`, `.channels(ApiTokenChannels)`, `.databases(impl IntoIterator<Item = impl Into<String>>)` (sets `Some(list)`; an empty iterator gives `Some([])`, which is distinct from the default `None` = all databases, TOKEN_API section 12), `.for_user(name)`, `.hmac(tag)`, `.build() -> DbRequest`.
   - `list_api_tokens() -> ListApiTokens` with `.for_user(name)`, `.hmac(tag)`, `.build()`.
   - `revoke_api_token(id) -> RevokeApiToken` with `.hmac(tag)`, `.build()`.
   - `revoke_user_tokens() -> RevokeUserTokens` with `.user(name)`, `.hmac(tag)`, `.build()`.
   Usernames are passed through raw (no normalisation; the canonical encoding signs the raw UTF-8, section 12).
6. **Client methods** on `Client` (signatures fixed; doc comments name TOKEN_API section 12 and the error codes):
   - `create_api_token(&self, request: shamir_query_builder::token_admin::CreateApiToken) -> Result<CreatedApiToken, ClientError>`
   - `list_api_tokens(&self, for_user: Option<&str>) -> Result<Vec<ApiTokenView>, ClientError>`
   - `revoke_api_token(&self, id: &str) -> Result<(), ClientError>`
   - `revoke_user_tokens(&self, user: Option<&str>) -> Result<u64, ClientError>`
   Each builds through the builders, signs through ONE private helper (decision 7), round-trips, maps `DbResponse::Error` through the existing `roundtrip`/error mapping (no new `ClientError` variants: the section-12 codes surface as `ClientError::Db { code, .. }`, as every other server code does), and returns `ClientError::Protocol` on an unexpected `kind`. Protocol error strings must never contain the secret (`DbResponse`'s `Debug` already redacts `SecretString`; do not `format!` the token anywhere).
7. **One signing helper**, a private free function in `api.rs`: `fn admin_request_tag(session_id: &[u8; 32], request: &DbRequest) -> Result<String, ClientError>` (canonical via `shamir_query_types::hmac::canonical_db_request`, key via the same `derive_session_hmac_key` the existing methods use, tag via `compute_tag_hex`). Exposed to tests through the existing `#[cfg(test)] pub(crate) use` pattern in `client/mod.rs`. Do not refactor `create_scram_user`/`set_replicator` onto it (out of scope).
8. **Creation-response sanity check in the client.** Before returning, `create_api_token` checks that `token.reveal()` is 71 bytes, starts with `shk1.`, has `.` at byte 27 and that bytes 5..27 equal `id`; otherwise `ClientError::Protocol("malformed api token in creation response")` (fixed text, no secret). Reason: cheap guard against server/client drift; never echoes the secret.
9. **Placement in `shamir-client`.** `src/` (7) and `src/client/` (7) are full. The four methods and the helper go into `src/client/api.rs` (797 lines now) as a new `impl Client` section, with a hard budget: the file must stay at or below 990 lines. If it cannot, STOP that item and report PARTIAL with the measured count; do not create a folder or move files.
10. **Golden HMAC test without a JSON parser.** `shamir-client` has no `serde_json` dev-dependency and no `Cargo.toml` may change. The client golden test hardcodes the four vector INPUTS (session id `000102...1f`; `create_api_token`: label `café-token`, ttl `9007199254740993`, mode `read_write`, channels `both`, databases `["café-db","db"]`, for_user `bob`; `list_api_tokens`: for_user `bob`; `revoke_api_token`: id `AAECAwQFBgcICQoLDA0ODw`; `revoke_user_tokens`: user `None`) and reads the EXPECTED `canonical_hex`/`tag_hex` from the shared fixture via `include_str!` (relative path from the test file to `crates/shamir-query-types/test-vectors/admin_hmac_v2.json`; compute it from the file's location and double-check it) plus a small string-search extractor written in the test file (find the object whose `"op_tag": "0020"` ... appears, then the next `"canonical_hex": "` and `"tag_hex": "` values). Re-derive the inputs from the JSON by reading it before writing them. If the fixture's inputs ever change, the test fails, which is the point.
