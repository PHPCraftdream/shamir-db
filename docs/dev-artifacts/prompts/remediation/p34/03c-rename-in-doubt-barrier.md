## Goal

A table rename can no longer lose or resurrect data when its catalogue persistence fails or its outcome is unknown. From before the source drain until the rename is resolved, the source table accepts no write through ANY path (name lookup, token lookup, a stale `TableManager` clone, the tx commit pipeline). When `persist` fails under the held permit, the engine asks the catalogue owner for the durable truth and either rolls forward (the rename committed and is durable: switch the registration and report success), rolls back (the rename provably never reached the catalogue transaction: unfreeze the source, report the error), or fences the pair as "rename in doubt" (both names refuse new work with a retryable error) until a retry of the same rename or a process restart resolves it. Because the source is frozen from before the copy until resolution, the copied stores equal the source at every durable outcome, so whichever outcome boot replay picks is lossless.

## Decisions taken (the orchestrator owns design; deviations go into the note with a reason)

1. **Freeze, not fence-by-name only.** Every rename transition (`rename_table_transition`, `rename_table_stores_admitted`, `recover_table_rename_with` when the source is still registered) instantiates the source with `get_table_admitted` under the held permit and takes its freeze with `begin_migration_freeze_admitted` BEFORE `drain_to_history` and the copy. Reason: name lookups alone miss writers holding a clone (the wip failure); the freeze is the existing writer gate already proven against the fast-path drain race and checked by both CRUD and the tx prelock. The freeze reuses the `MIGRATION_FREEZE` bit: writers racing a rename get `DbError::MigrationFrozen` / wire `table_migrating`; a rename of a table under migration freeze fails at `try_set` (map `CommitError::MigrationFrozen` to `DbError::MigrationFrozen`, anything else to `DbError::Internal`). Adding a dedicated bit would touch the shared flag word, six writer checks and three error enums for no safety gain; record the wire-code consequence in the note. This also closes the pre-existing lost-write window of a SUCCESSFUL rename (writes landing in the source overlay after the drain).
2. **Typed persist outcome.** New engine enum (own file) `RenamePersistOutcome { Committed, NotCommitted(DbError), InDoubt(DbError) }`, re-exported where `TableConfig`/`RepoInstance` are exported to `shamir-db`. `rename_table_stores_with` and `recover_table_rename_with` take `persist: FnOnce(TableConfig) -> Fut` with `Fut: Future<Output = RenamePersistOutcome>`. Engine semantics (still holding permit and freeze):
   - `Committed` -> switch the registration (`remove_table(from)`, `add_table(to)`), retire the freeze (decision 4), clear any fence for the pair, return `Ok(true)`.
   - `NotCommitted(e)` -> drop the freeze (source writable again), clear any fence for the pair, the destination stores stay orphaned (fresh id, never referenced), return `Err(e)`.
   - `InDoubt(e)` -> move the freeze guard into the fence (decision 3), return `Err(DbError::Conflict(format!("rename in doubt: '{from}' to '{to}': {e}")))` (stable prefix `rename in doubt:`; wire `tx_conflict`, retryable; no new public error variant).
   `rename_table_stores` / `rename_table_stores_admitted` (no persist) keep their signatures and gain only the freeze.
3. **Fence registry.** A new `RepoInstance` field `rename_fence: Arc<scc::HashMap<String, Arc<RenameInDoubt>, THasher>>` (the Fx hasher from `shamir_collections`), keyed by BOTH table names of the pair; the shared `RenameInDoubt` (own file) holds `from`, `to`, the destination `TableConfig` and the retained `MigrationFreezeGuard` (the guard behind a non-cloneable owner taken out exactly once; if `scc` value ownership makes that awkward, keep the guard in a small one-shot slot such as an `arc_swap::ArcSwapOption` or `std::sync::Mutex<Option<_>>` justified inline as a DDL-only guard set, category 2 of CLAUDE.md). While a name is fenced, `get_table` (BOTH the `initialized_table` fast path and the admitting path), `get_table_admitted`, `table_by_token`, `table_by_token_if_live`, `add_table`/create of either name, `drop_table`, and any rename involving either name with a DIFFERENT pair fail with the `rename in doubt:` conflict. A retry of the SAME pair takes the guard out of the fence and runs the transition with it (no second `try_set`, which would fail on the still-set bit). A restart clears the fence by construction (Q5). Initialise the field in every `RepoInstance` constructor (`rg -n "RepoInstance \{" crates/` for literals).
4. **Retire on success.** After a successful switch the OLD source `TableManager` keeps its freeze forever: add `MigrationFreezeGuard::retire(self)` (consumes the guard without clearing the bit; implement with a private `armed: bool` checked in `Drop`, no `mem::forget`). Reason: a stale clone of the old table must fail instead of reporting success for a write into orphaned stores. Confirm in the note that no other table shares those flags (Q4).
5. **Who decides the durable truth: `shamir-db`.** Split `SystemStore::rename_table_row` along its commit point without changing what it reads: everything before `run_implicit_batch_tx` (fault gate, id checks, source re-read and identity check, op construction, `persist_table_interner`) is the pre-commit stage; an error there is `NotCommitted`. An error from `run_implicit_batch_tx` or `flush_system_repo_durable` goes to a new `SystemStore::resolve_table_rename(...) -> RenamePersistOutcome` (new file `system_store/catalogue/rename_resolution.rs`): re-read the destination and source rows; if the destination row is exactly the expected one (`table_name = to`, `store_id = new id`, `rename_from = from`, `rename_from_store_id` as expected) and the source row is absent, call `flush_system_repo_durable` once more: `Ok` -> `Committed`, `Err` -> `InDoubt`; every other observation (rows unchanged, rows partially changed, a read error) -> `InDoubt`. Treating "not visible" as `InDoubt` rather than `NotCommitted` is deliberate (Q2: a failed commit may still replay at boot); a retry resolves it. Apply the same classification to `complete_table_rename_row` in the recovery branch. The success path must not add a catalogue read (the read-count test stays at 2).
6. **Retry and recovery convergence.** `rename_table_as(from, to)` after an in-doubt result: if the catalogue shows the destination row (rename committed but not proven durable), the existing recovery branch runs `complete_table_rename_row` (rewrite + flush) under the fenced freeze -> `Committed` -> switch; if the catalogue still shows only the source row, the normal branch runs again: the engine reuses the fenced freeze, drains and copies again into a FRESH destination id (03b behaviour), persists, and resolves as above. Both are idempotent: running the same retry twice ends in the same registration and rows (the existing idempotence assertions stay).
7. **Fault seam for the durability tail.** Add to `SystemStore` a countdown seam mirroring `catalogue_write_faults`: an always-present `durability_tail_faults: Arc<AtomicUsize>` field and `#[cfg(any(test, feature = "test-util"))] #[doc(hidden)] pub fn arm_durability_tail_faults(&self, n: usize)` that makes the next `n` calls of `flush_system_repo_durable` fail with `DbError::Storage("injected durability-tail failure")` (count down, not "the n-th"). `n = 1` exercises roll-forward through the second flush; `n = 2` exercises in-doubt.
8. **Existing tests change shape, not intent.** `durability_tail_failure_retry_reconciles_registration_and_is_idempotent` and `precommit_persist_failure_retry_uses_fresh_destination_id` call `rename_table_stores_with` with hand-written closures: keep both names and intents, return `RenamePersistOutcome::InDoubt(..)` / `NotCommitted(..)` from the closures, and update their assertions to the new semantics (in-doubt: both names refused until the retry; not-committed: unchanged). No test is deleted or weakened.
9. **Repo rename is analysed, not changed.** It has no permit, no store copy and a different failure mode (in-memory re-key before N catalogue writes); fixing it needs its own atomic catalogue transaction. Phase 0 Q6 produces the matrix; the orchestrator opens a follow-up card.
