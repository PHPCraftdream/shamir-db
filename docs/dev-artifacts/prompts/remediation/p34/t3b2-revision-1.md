## Findings to fix (spec: `docs/guide-docs/client-server-protocol-spec/TOKEN_API.md` sections 5, 8, 9, 11, 13)

1. Audit on the failure path (section 5 step 8 and 13). `gate.rs` calls `TokenService::audit_auth_failure` -> `AuditChainWriter::append` synchronously on the tokio worker for every failure: `append` takes the `durable_gate` mutex, does appender I/O and checkpoints every 1000 entries; existing callers wrap it in `spawn_blocking`. There is no queue and no aggregation/sampling of malformed or unknown-id failures; it also writes while the subnet is already rate-limited (429), but the specification says the limiter controls audit writing too. An appender I/O error latches `persistence_failed` and fail-closes the whole audit writer for later events (token create/revoke included), so unauthenticated traffic must not be able to drive it. Required: a bounded in-memory aggregator (per-subnet counters with a cap and a periodic or threshold-driven flush of ONE summary event, sampled), emitting off the request path (`spawn_blocking` or a dedicated flusher task that stops with the service), no audit write when the request is rejected by the limiter, canonical `rmp_serde` details like the other token events (not raw `b"rest"`), no secrets or peer-controlled strings.
2. `api_token_exposed` (section 11): a plaintext read_write denial in `gate.rs` must write the `api_token_exposed` audit event with the token id (via the same off-path writer; never the secret).
3. Failure limiter lifecycle (memory bound): `gate.rs` creates a per-gate `InMemoryRateLimiter` and never calls `gc()`; entries grow without bound (one per /24 or /64, attacker-controlled on IPv6). Give it a bounded size and a periodic `gc` driven by a task that stops with the service, or share the limiter with the service so WS can reuse it later; document the choice.
4. `bucket.rs`: `self.buckets.retain(..)` runs on EVERY request (an O(N) sweep that write-locks every shard). Sweep only when the cap is reached or periodically. A full cache must not reject valid tokens with 429: either evict least-recently-used entries or return 503 `server_busy`; an RNG failure must map to 503 as well, not to 429 (`Err(1)`).
5. `shamir-transport-http/src/server/service.rs`: an executor `Unavailable` outcome is sent as 503 without `Connection: close`; TOKEN_API section 9 table says what a 503 does: align it (read the table).
6. Metrics (section 13): register and describe the `shamir_token_auth_total`-style counters with fixed-vocabulary `result` and `channel` labels; count Forbidden outcomes too; use the T2b `TokenCounters` instead of ad-hoc macros where they exist; reduce the per-failure `tracing::warn!` (log flood on unauthenticated traffic): sample or demote.
7. `RestGate::still_valid` returns 401 on clock failure; 503 fits better; the executor's plaintext check duplicates the gate's and cannot trigger: remove the dead branch or document why it stays. Classification order: when a DDL op comes from a read_only token the denial code should be `token_read_only` (not `token_request_denied`) and `TxBegin` on a database outside the allowlist must not give 403 before `not_supported_over_rest`: make the classification order explicit and tested.
8. `ScopedHandler::handle` must enforce the classification by construction (no path to the inner handler that skips it); `conn_id` derived from `session_id[0]` has only 256 values: use a proper unique id if the engine uses it, else say so in a comment.
