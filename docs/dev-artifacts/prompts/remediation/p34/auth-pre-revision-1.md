Fix in this order, each with its tests.

1. Stale pairs must count as free (`lockout.rs`, the slot scans for admission/eviction, around the quota counting and candidate selection): a pair idle for five minutes or more with no active lock is effectively count 0. Today it counts against the 64/512 quotas, occupies a slot even when the table has room, and competes in eviction with its raw `failure.count` (a fresh count-1 pair can be evicted while a dead count-10 pair stays; when a base's active locks expire, their slots keep count >= 50 and are not eviction candidates, so every new pair of that base is dropped until `gc` runs). Fix: in both scans treat `occupied && failure.is_stale(now) && lock not active` as a free slot; rank and test eligibility on the effective count (`0` when stale). Tests: a stale high-count pair is replaced without eviction accounting against quotas; expired locks free their quota without waiting for `gc`.
2. Lookup cost: every handshake does a linear scan of all 8,192 slots (1 MiB) under the one mutex, including the unauthenticated pre-challenge `is_locked_out` (`crates/shamir-server/src/sync/connection/handshake.rs` calls it). Make exact-key lookup O(1)-ish while keeping the fixed 8,192 x 128-byte table and the single mutex: open addressing inside the fixed slot array (hash of `PairKey` with the existing fixed hasher -> home slot, bounded linear probe with a small fixed probe limit such as 32, tombstone or backward-shift deletion), or any other scheme that keeps lookups bounded and allocation-free. The quota counting and eviction candidate selection stay bounded scans but only on NEW-pair admission, never on lookup of an existing pair or on `is_locked_out`. If the probe window is full for a new pair, treat it like "no eligible candidate" unless an eligible eviction exists inside the probed window; keep all spec semantics (quotas, never evict an active lock, drop accounting when no candidate, updates of retained pairs continue when full). Fix the inline comment at the `slots` field so it states the real cadence: the lock is taken on every handshake (pre-challenge check), the critical section is bounded and allocation-free. Tests: lookups of existing pairs do not depend on table fullness; heavy collision keys still behave; all existing store tests stay valid.
3. Test oracles in `lockout_storage_tests.rs`: (a) "active locks first on load": lock users 6..69 (not 0..63) so priority matters, and in the global-capacity case add one more higher-count failure so the table overflows and assert the locked key (lowest count) is kept; (b) "lowest count before oldest": give the count-2 value to the OLDEST entry (u=63) and assert u=62 is evicted and u=63 kept; (c) gc of stale failures: first `register_failure(k, NOW)`, then `gc(NOW + BACKOFF_RESET_NS)` and assert the slot is freed.
