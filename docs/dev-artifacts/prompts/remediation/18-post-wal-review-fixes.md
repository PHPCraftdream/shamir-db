BLOCKER B1 (performance, hot path). In `crates/shamir-engine/src/tx/drainer.rs` `drain_step` (the two prefix-collection loops that `break` at a gap, around the places that test `is_active_post_wal` / `(*k > visible && !is_orphaned_post_wal(*k))`): when the first key `dur+1` is a version that is merely ACTIVE post-WAL (its commit future is still running phases 5b-5d) or not yet completed, the loop breaks with an EMPTY prefix and the code then takes the "gap -> reseed" path = a full `wal.recover()` that decodes every un-truncated segment (up to 8 MiB each). With two or more concurrent commits almost every `drain_all` ends in such a recover. Fix: distinguish a real GAP (key != expected: missing version -> reseed as before) from "blocked by an in-flight / not-yet-completed version" (-> do NOT reseed: just stop with the prefix collected so far, possibly empty, and return `Ok(drained)`). Keep the existing behaviour for genuine gaps.

BLOCKER B2 (correctness of `drain_all`). `drain_step` now starts with a `replaying: AtomicBool` compare-exchange and returns `Ok(0)` if it is already set. `drain_all` then exits without having drained anything and violates its documented contract ("flush the in-flight tail fully"); `flush_buffers` (graceful shutdown), `purge_history`, cursor creation and temporal reads call it, and tests of the form "drain_all then assert durable == last_committed" become racy on a multi-thread runtime. Fix: make a second caller WAIT for the running pass instead of returning early. Replace the AtomicBool by a `tokio::sync::Mutex<()>` (sanctioned: guard held across `.await`, bounded contention) acquired at the start of `drain_step`, with an inline comment naming that contention model; the guard releases on every exit path (return, `?`, panic, future drop) by construction. Make sure nothing that holds the lock can wait on a caller of `drain_step` (check callers of `drain_step` / `drain_all` for re-entrancy: the background loop, `settle_and_truncate`, shutdown, tests) — if a re-entrant call exists, restructure instead of deadlocking.

BLOCKER B3 (liveness). Completing an ORPHAN version in `drain_step` currently propagates every error with `?`: the `counter().increment(..)` replay, `table_by_token(..)?`, the orphan's history write, and `persist_markers(..)?`. On the client path the counter is explicitly "metric only, drift accepted", but here its failure blocks `durable_watermark` forever (and `increment` fails deterministically with "cannot go below zero" when the counter already drifted below), so WAL truncation stops and every commit hits the 5 s backpressure. Fix: (a) counter replay failure -> `log::warn!` and continue (still mark the entry as counter-applied so it is not retried forever); (b) `persist_markers` failure -> warn and continue (markers are monotone; the next commit rewrites them); (c) a failed `table_by_token` lookup or a failed history write for an orphan is data-relevant: do NOT mark the version durable and do NOT return `Err` for the whole pass — warn and stop the pass cleanly at that entry (`Ok(drained so far)`), consistent with the existing "stop at the first entry with a failed table (contiguity)" rule used for normal entries, so a later pass retries it. Remove the `fail_orphan_markers` test hook if it no longer makes sense or adapt it (it currently makes markers failure an `Err`).
