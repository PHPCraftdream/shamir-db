## S5c-X DESIGN (BINDING; two independent reviews agreed on the core, the owner approved the FULL plan PR1-PR4 on 2026-10-13)

Evidence labels: OBSERVED = read in source by the reviewers (line numbers drift: re-grep every claim), INFERRED = consequence/proposal.

### 1. Problem

After an unclean shutdown the repository certifies [J+1, H] as a replication-journal GAP (`certify_cold_start`, `repo_instance.rs` ~1895-1906; J = persisted clean horizon, H = recovered gate floor = max(marker, max surviving WAL version)). J is written only by `record_clean_horizon` (`changefeed.rs` ~534-548; adapter `changelog_store.rs` ~64-87) and advanced in exactly three places: cold certification, `shutdown_clean`, seed install. It never advances at runtime, so the window is the WHOLE UPTIME. A follower stops on any gap >= its cursor (`follower_loop.rs` ~328-343; `gap_at = Some(max(from, first))` in `changefeed.rs` ~649-653), so nearly every follower must be reseeded after every unclean stop, even when the journal tail was fully persisted. Making the window narrower does not help followers; EXACTNESS does.

What is missing at recovery: for a version in (J, H], recovery cannot tell (1) a committed mutation whose journal event was lost, (2) an eventless/aborted allocation, (3) evidence already erased by WAL truncation / history GC. WAL entries lack the event header (actor, implicit/public tx_id, table names, projection timestamp: `wal_entry_v2.rs` ~142-160) and the WAL keeps only RecordId-keyed data ops (`commit.rs` ~536-560) while projection keeps every Set/Remove (`changefeed.rs` ~807-841).

### 2. Principle: the WAL is the source of truth for journal events (PostgreSQL slot / logical-decoding pattern)

- **I1 Derivable**: every journal event is a pure function of its WAL entry: `event = event_from_wal_entry(entry)`; ONE function used by the live commit path and by recovery (no second projection). Entries of the old format mean "unknown" -> conservative GAP fallback.
- **I2 Retained**: a WAL segment is never unlinked until the journal has durably checkpointed (flushed events + persisted gaps + persisted J) past every entry in it. Cheapest cadence: checkpoint J right before each truncation attempt (so the segment size is the cadence). If the checkpoint fails, do not truncate.
- **I3 Serve-durable**: followers are only served versions whose WAL entry is already fsynced: replication pulls are bounded by `min(W, S)`, S = the fsynced prefix. Without I3 exact repair would remove the accidental protection of the conservative GAP and followers could be ahead of the recovered H. OBSERVED today: the WAL append is `Buffered` (no fsync) outside tests (`commit.rs` ~430-440, ~1046-1068), the background fsync is every 250 ms (`repo_instance.rs` ~1069-1074); replication pulls are bounded by `min(confirmed, W)` (`repo_instance.rs` ~1634-1640): a COMPLETION bound, not a durability bound. INFERRED latent hole: after a power loss versions above the recovered H that followers already applied are re-allocated and followers skip them silently, with no GAP covering them.
- Rejected: obligation ledger + WAL bit + provenance + legacy scan (a second durable log that only detects, never repairs; under I1 the "requires event" bit is just `event_from_wal_entry(e).is_some()`); repair from history (keys are per record, no transaction grouping, GC deletes); writing the journal inside the WAL fsync (different files; an extra fsync on the commit path is forbidden); a runtime checkpoint alone (narrows the window but followers still stop).
- Events carry only NEW bytes for Put and nothing for Delete (`changefeed.rs` ~67-73), so old values are never needed for repair.
- Backward compatibility is NOT a constraint (alpha), but old WAL entries must be handled safely (unknown -> conservative).

### 3. Settings (owner decision: reliability/speed behaviour must be SETTINGS, not hard-coded)

Technically correct level = the REPOSITORY (WAL, journal, gate, drainer, J and the follower bookmark all exist once per repository; one WAL entry / one commit version can span several tables, `wal_entry_v2.rs` ~142-160). A per-table or per-store switch is impossible. There is no config path from the server into the engine today and no per-repo settings record: `ShamirDb::init(SystemStoreConfig)` is all the engine gets (`server/` launcher ~348), repos load inside `init`, `RepoConfig` is `{name, factory, tables}`. So: a NEW server config section `durability:` (server-level DEFAULTS), parsed and validated at boot like `transactions:` (`deny_unknown_fields`; `transactions_config.rs`, `config.rs` ~740), passed INTO `ShamirDb::init` (new policy argument), held as a plain field on each `RepoInstance`; a per-repo override can be added later without touching the hot path. The top-level `Config` does NOT reject unknown sections (`config.rs` ~74): the new section must still be strict inside.

Existing knobs for context: per-request `durability` (`buffered|synced|async_index`, `batch_request.rs` ~67-81; only string-compared at `batch_execute.rs` ~215/~820; an unknown value silently behaves as `buffered`; `synced` runs `synced_flush` + `sync_wal` after the commit); repo engine `in_memory|fjall|hybrid` chosen at CREATE REPO and persisted; `shamir-tunables` constants (WAL segment 8 MiB with env override `SHAMIR_WAL_SEGMENT_MAX_BYTES`, `MAX_UNDRAINED_VERSIONS` 10000, journal channel 4096); `transactions:` (VIS-2 keys). The doc `02-durability.md` says "~500 ms MemBuffer": stale, the real power-loss window is the 250 ms WAL fsync.

Keys:
- `durability.wal_commit: buffered | synced`, DEFAULT `buffered`. I3 is an INVARIANT (always on), not a setting; the setting only chooses how the durable prefix advances. With `buffered`: followers lag by at most one fsync; PR1 adds a coalesced `sync_now` when a pull is held back by S, so the lag is usually far below 250 ms with no commit cost. With `synced`: commits use `WalDurability::Synced` through the existing seam `commit_wal_durability(repo)` (`commit.rs` ~430-440; called from `commit.rs` ~1051 and `pre_commit.rs` ~2781), S == W. A request can only make things STRONGER (a request `buffered` cannot weaken server-level `synced`); a request `synced` must sample W before its `sync_wal` so its write becomes servable immediately; `async_index` unaffected.
- `durability.wal_retention_max_bytes`, DEFAULT 1 GiB (128 segments of 8 MiB); validated at repo open to be at least 2 x the effective segment size (after the env override).
- `durability.on_wal_retention_exceeded: refuse_writes | declare_gap`, DEFAULT `refuse_writes`. `refuse_writes` = new commits fail fast with a retryable typed error, checked by ONE atomic load at admission next to the existing reopen-required check (`commit.rs` ~650-666); it clears by itself when J catches up; it must NOT park committers (the soft brake never wedges writers, `acknowledgement.rs` ~270-374). `declare_gap` = durably record a real GAP and unlink the old WAL (followers reseed); if the journal writer is dead the gap cannot be recorded, so it falls back to refusing writes. Boot logs a WARN when `declare_gap` is configured (precedent `server_launcher` ~435-444). A per-request `durability` value does not bypass this.
- No other knob: checkpoint cadence = before each truncation (segment size); the I1 event header has NO toggle (it is part of correctness); the 250 ms fsync interval stays a constant.
- `in_memory` and `hybrid` repos: nothing survives a restart (repo identity is regenerated, Hybrid keeps `__history__`, `__tx__`, `__changelog__` in RAM only, `repo_types.rs` ~157-163); they get a Mem WAL sink without background fsync: S == W, `wal_commit` is ignored with one log line, the I2 truncation gate and cold reconciliation do not apply (no WAL to recover from); I1 still writes the event header (one code path). Followers of such a repo are protected only by the seed identity fence (`fence.rs` ~176-197), which runs only with a seed receipt: outside S5c, add one test.

# Reviewer design answer: PR6b follower retry convergence (binding)

## Verdict

**Recommend PR6b as a durable redo-receipt protocol with persistence-before-publication—not a receipt bolted onto today’s apply path.** Ordinary I/O failures should pause/resume the same allocation; corruption and unexpected partial publication must remain fail-closed. “Never terminal under any failure” is incompatible with preserving the invariants.

**OBSERVED scope:** conclusions below come from this checkout’s code, not execution. No files changed; no builds or tests run.

## 1. Existing mechanism and necessary correction

**OBSERVED:** batch apply allocates fresh local guards, reserves the floor, then applies events (`crates/shamir-engine/src/tx/apply_replicated.rs:698–715`). The underlying primitive actually publishes **before** its fallible history write, despite contradictory nearby documentation (`crates/shamir-tx/src/mvcc_store/mvcc_history.rs:425–441`). It also raises the published floor (`:518–522`).

Journal enqueue/guard commit precedes the durability barrier (`crates/shamir-engine/src/tx/apply_replicated.rs:599–617`). Batch completion then verifies/flushes the journal, flushes history, and stores bookmark plus J (`crates/shamir-engine/src/tx/follower_durability/batch.rs:45–74`).

**INFERRED:** replay can produce extra history versions. Counter duplication is **not established generally**: apply already computes net existence deltas from current pre-images (`crates/shamir-engine/src/tx/apply_replicated.rs:491–539`). Its real counter weakness includes lost durable accounting across reopen.

## 2. Exact recommended design

**PROPOSED:**

Maintain one outstanding receipt per upstream subscription, in a **separate replication-receipts metadata keyspace**, not inside the bookmark:

- Identity: upstream lineage, epoch, predecessor bookmark, upstream range.
- ID: domain-separated hash of that identity plus canonical ordered events and field bindings.
- Exact upstream-event → local-version mapping; ranges alone cannot represent skipped/noncontiguous inputs safely.
- Immutable translated operations, local interner bindings, downstream event bytes, history timestamps.
- Per-table counter before/after values.
- Phase: `Prepared`, `Materialized`, `Checkpointed`.

Bookmark **v3** retains fence/bookmark/J and references the outstanding receipt. Preserve a compact completed identity until superseded safely.

### Algorithm

1. Serialize follower apply, local writes, DDL and counter persistence within the affected repository’s write-admission domain. Validate upstream ordering/fence; consult durable bookmark/receipt **before allocation**.
2. Prepare translations and exact deterministic downstream events. Atomically write `Prepared` receipt, allocation reservation and bookmark-v3 reference; sync. No data publication.
3. Build one repository-scoped atomic batch containing **all history rows/timestamps, absolute durable counters, downstream journal records, and receipt→Materialized**. Commit and sync before exposing anything.
4. Read back/validate journal coverage; atomically checkpoint bookmark+J and receipt phase, then sync. Advance J only across proven contiguous coverage; preserve existing gaps.
5. Publish prepared RAM state using an infallible, non-awaiting, reader-gated publication routine; settle visibility/durability trackers once. Broadcast afterward. Resume never allocates replacement versions.

**OBSERVED:** fjall has `Database::batch()`/atomic commit, and stores share their repository’s `Database` (`crates/shamir-storage/src/storage_fjall.rs:164–176,214–244`). `flush()` calls database-wide `persist(SyncAll)` (`:510–524`). However, current `Store::transact` addresses one store; its default is merely a loop (`crates/shamir-storage/src/types.rs:243–254`).

**PROPOSED:** expose a capability-checked repository-wide atomic-write API. Do not emulate it with separate store transactions or shared flushes. Wrapper caches must participate/invalidate correctly. Reject unsupported persistent backends before allocation.

**INFERRED:** this is feasible with the existing fjall API; exact crash/error guarantees still require dependency-source audit and CI fault tests.

### Invariants

- **I1:** local-WAL events remain solely WAL-derived. The WAL-less follower’s receipt becomes its immutable redo authority; downstream bytes never derive from mutable current rows.
- **I2:** leave local WAL retention rules unchanged; retain follower redo receipts until journal/history/checkpoint durability is established.
- **I3:** neither history readers nor feed pulls may expose materialized-but-unpublished versions. Refactor current floor-raising helpers and enforce publication bounds on history reads.

## 3. Failure matrix and recovery

| Failure | Required outcome |
|---|---|
| Preparation/interner persistence | Retry; monotonic unused bindings need no rollback. |
| Prepared-write or sync uncertain | Reconcile/rewrite the identical receipt and reservation; block new allocation meanwhile. |
| Materialization commit/sync failure | Resume identical batch and versions; never undo or blindly assume absence. |
| Journal/checkpoint I/O failure before publication | Retry from receipt; no RAM counter increment or visibility rollback. |
| Cancellation | Repository-owned bounded worker retains the operation; caller cancellation does not abandon guards. |
| Partial RAM publication, mismatched receipt/journal, corrupt identity | Quarantine/reopen; never continue blindly. |
| Failure after successful publication | Resume checkpoint/notification bookkeeping only; do not reapply data. |

**OBSERVED:** enqueue failures can create gaps (`crates/shamir-engine/src/tx/publish_journaled.rs:39–46`). Therefore journal retry requires a serialized durable-install command integrated with the sole writer—not repeatedly enqueueing through this lossy path.

**PROPOSED:** cold recovery completes `Prepared` receipts and reconstructs exact journal bytes **before PR6c gap classification**. Only then certify exact receipt-covered versions. Preserve conservative GAP handling for legacy/unproven ranges; current PR6c classifies the outstanding interval conservatively (`crates/shamir-engine/src/tx/cold_reconcile/algorithm.rs:150–159`).

## 4. Counters and indexes

**OBSERVED:** `RecordCounter.increment` changes RAM only; persistence is separate (`crates/shamir-engine/src/table/record_counter.rs:115–149,174–192`). Best-effort increment errors are logged by apply, not repaired.

**PROPOSED:** compute checked final per-table counts sequentially across events, persist absolute values atomically with history, and hydrate/update cache once under write admission. Coordinate periodic persistence so stale caches cannot overwrite committed counts. Attempt/retry metrics may increase; applied metrics must be receipt-transition keyed.

**OBSERVED:** ordinary, unique, sorted and index2 descriptors are rejected before allocation (`crates/shamir-engine/src/tx/apply_replicated.rs:324–359`). Vector promotion is explicitly skipped (`:63–95`). PR6b should preserve these restrictions; claim no exactly-once posting/vector maintenance support. Future index support needs atomic durable membership plus replay-safe derived-cache reconstruction.

## 5. Compatibility, proof, delivery

**PROPOSED:** read legacy/v1/v2; write v3 only after explicit migration. Existing decoding rejects unknown versions (`crates/shamir-engine/src/meta/tests/follower_bookmark/v2.rs:38–85`), providing fail-closed downgrade behavior. Rollback requires offline completion of receipts and validated conversion or snapshot restore—not deleting receipt keys. No upstream wire change is necessary if fence identity and canonical events suffice; tolerate changed pull boundaries by matching outstanding receipt events, not batch hashes alone.

CI must kill subprocesses without graceful shutdown at every persistence/publication boundary, reopen twice, replay twice, and assert unchanged allocation, exact history keys/timestamps/journal bytes, counters, tombstones and snapshots. Include multi-table/repeated-key batches, changed batch boundaries, identity/hash rejection and injected uncertain commits. Negative control: disable receipt lookup and require extra-version assertions to fail. Existing “crash” tests explicitly use graceful reopen (`crates/shamir-engine/src/tx/follower_durability/tests/apply_crash_tests.rs:98–101`).

**PR split:** (1) repository atomic capability, publication-safe primitives and format codecs, inactive; (2) receipt apply/resume, counter integration, writer coordination, cold recovery and crash proofs **together**; (3) migration/rollback tooling and activation. Main risks: publication leaks, competing counter writers, cache coherence and oversized receipts—bound batch size rather than weakening atomicity.
