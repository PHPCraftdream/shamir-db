## P1

**P1-1 Deadlock: PR #188 lifecycle paths take control BEFORE admission.** M:261 fixes admission -> control; the site inventory M:308 lists only sites (1)-(7); S:112/119/120/123 require admission + a reservation check in rename, CREATE/RESUME subscription, `register_seed_image` without an order. In #188 all of these take `lock_replication_control()` first: `rename_db_as` 188:db_management.rs:165, `rename_repo_as` :621, `remove_repo`/`remove_db` :552/:87, DROP DB/REPO handlers 188:admin_db_repo.rs:118/:424, CREATE/DROP/ALTER SUBSCRIPTION 188:admin_replication.rs:310/:375/:429, `install_seed_subscription` holds control for the whole install 188:replication_seed/catalogue.rs:161. Interleaving: repo-destroy A holds the db1 gate (shared) + mutex(db1,r) and waits for control at step 5; `RENAME db1/x -> db1/r` holds control and waits for mutex(db1,r) for the reservation check. Fix: add every control-first site to the inventory with a mandated restructure admission (db gates sorted, then repo mutexes sorted) -> control; name the dispatch split point BEFORE 188:admin_db_repo.rs:424/:118 (otherwise R2' runs under control and `ensure_destinations_unbound` refuses it).

**P1-2 The lease-gate order is the reverse of #188's.** M:261 orders lease gates -> control; M:289/294/304 drain "OUTSIDE control"; M:308 site (4) calls terminal marking a leaf. 188:lease.rs documents "control lock -> apply_gate.write()"; `quiesce_subscription_lease_locked(name, &ReplicationControlGuard)` requires the guard; `mark_subscription_terminal_generation` (188:admin_replication.rs:845) takes control THEN quiesces, so it waits on apply-gate readers while holding control (not a leaf). Interleaving: the executor holds S's `apply_gate.write` during Quiesce, then takes control to persist `Quiescing` (M:54); a #188 terminal retry for S holds control and awaits `apply_gate.write`. Fix: adopt #188's order (control -> lease) everywhere; drain under control with `quiesce_subscription_lease_locked`; followers never take control while holding the read guard; delete the "drain outside control" rationale.

**P1-3 Step 3 (Detach) cannot start as specified.** M:199 says R2' calls the #188 `_locked` guarded variants; M:272 says control is not held in step 3. 188:db_management.rs:560-588 `remove_repo_locked` first calls `ensure_destinations_unbound(db, Some(repo), "DROP")`, which always refuses an R2' target (anchors remain until R1, M:228), requires `&ReplicationControlGuard`, and removes the catalogue row best-effort (contradicts "catalogue rows kept" in step 3 and "errors propagated" in step 5). Fix: step 3 uses the registry-only `DbInstance::remove_repo` (db_instance.rs:161-163) under the operation's guards; state explicitly that R2' bypasses R2.

**P1-4 D2: the evidence for an ambiguous barrier append is unsound.** M:174 accepts "forced fsync via flush_buffer/sync_all" or "audit_seq <= durable ack watermark"; S:248 sets the watermark to next_seq-1. audit_chain.rs:185-215 `append` advances next_seq/prev_hmac BEFORE the appender runs, no rollback; the appender only logs a failed write (audit_appender.rs ~:691-698); `flush_buffer` returns Ok immediately in Strict mode (:468) and batched `flush_buffer` takes the buffer before writing so a failed flush silently drops entries (:469). Sequence (strict): seq 100 gets `destruction_prepared`, `write_all` ok, `sync_all` EIO, `checkpoint_durable` flushes an empty buffer (Ok), writes next_seq 101, watermark 100 -> reconciliation sees 100 <= 100 and destruction runs; a crash loses entry 100 (I2 violated, chain gap). A retried fsync after EIO may report success without durable data. Fix: the appender tracks a durable-through seq advanced only by a successful write+sync of a contiguous prefix; the chain poisons itself on appender failure (no new seq until the entry is re-written durably); reconciliation re-writes the entry and requires a fresh successful write_all+sync_all of that line; a sync error is never retried as proof.

**P1-5 A same-id resubmission / lost-response retry can overwrite a live operation with `Rejected`.** M:196 step 0 verifies the challenge is unconsumed and the digest matches, and a mismatch writes a `Rejected` row keyed by operation_id (M:76); the duplicate rule (M:314) is not ordered before preflight. Sequence: the response to a successful Prepare is lost, the client retries; the challenge is consumed and the target set no longer matches the digest -> `destruction_target_changed` + a `Rejected` upsert over the `Destroying` row; boot skips `Rejected` (M:248) so the half-destroyed target is opened and recovered (I3 violated) = evidence case 2. Fix: look up the operation id FIRST: existing row + identical frozen parameters (excluding challenge/digest) -> return status or claim a `Prepared` one; different -> `destruction_operation_conflict`; `Rejected` is insert-if-absent only; challenge/digest checks apply to the first submission only.

**P1-6 A stranded `Prepared` row is executable but unprotected.** M:171/197: after a barrier failure reservations stay unpublished and guards drop; M:131 member (ii): every non-terminal row reserves — contradiction. Claim paths (periodic pass after 5 min, same-id, `destruction_retry`, boot) re-run only the barrier, not preflight. Sequence: barrier fails, guards drop, no reservation; an operator RESUMEs/rebinds the subscription (S:119 passes); 5 min later the periodic pass destroys the destination of a now-active subscription. Fix: publish reservations at (i) for any persisted `Prepared` row; every claim path re-runs full preflight against the frozen `target_digest` before Quiesce.

**P1-7 No in-flight handle drain; the cited write fence does not exist; a stale handle can resurrect the WAL.** M:135/S:125 claim write fencing via `RepoWriteDomain`/`RepoWritePermit`; M:198 "close repo admission". `RepoWriteDomain::admit` is called only from db_instance.rs:224/:246 and repo_membership_impl.rs:56 — NOT on the table-write or commit path; `get_repo` hands out clones (db_instance.rs:156-158); WAL init is best-effort and retryable (repo_instance.rs:883-887) and the lazy `repo_wal()` does `create_dir_all(<repo>.shamirwal)` on first commit (:963-976; tx/commit.rs:617). Sequence: request R holds a cloned `RepoInstance` whose WAL init failed; steps 3-6 destroy everything and reach `Destroyed`; R commits and recreates `<repo>.shamirwal/00000000.wal`; R1 releases the name; a same-name CREATE (path from the name, admin_db_repo.rs:266/:291) runs `SegmentSet::open` on that directory and replays the old incarnation's commit into the new one (violates case 6). On Windows the live clones keep destruction `Blocked`. Fix: Quiesce installs a per-instance revocation that EVERY `RepoInstance` entry point (commit, lazy WAL init) checks and waits for the outstanding handle/permit count to reach zero; lazy init refuses on a revoked instance.

**P1-8 The exit is unreachable for an unopenable destination.** The component list lives only inside the repo (`MetaKey::StorageOwnership`, M:68); the catalogue mirror holds only id + digest (M:70); preflight rejects unknown ownership (M:196); I12 promises no corrupt open is needed. Boot opens every catalogued repo with `?` (core.rs:303/:316): an unopenable destination fails `ShamirDb::init`, so DESTROY can never be issued. Fix: mirror the FULL descriptor in the catalogue row; at boot skip-and-fence an anchor-covered repo that fails to open (read-fenced, catalogued-only) instead of aborting init.

## P2

1. No audit sink exists inside `shamir-db` (no `shamir-connect`/`shamir-server` dependency), yet `ShamirDb::init` must replay the outbox (M:250) and the executor runs the barrier; production uses the batched appender (server_launcher.rs:137) and calls init at :349. The injection trait, the init signature and the scheduler hook (scheduler.rs:204-216) are unspecified.
2. Writer/ownership contradictions: M:127 "single executor is the only writer" vs M:173 the ack hook as a second CAS writer (a CAS conflict looks like "another executor took over" and strands the operation); the "operation token" (M:261) is undefined; periodic pass, same-id, retry and boot can all claim at once and the barrier may run past 5 min; duplicates block on the token for the whole run instead of getting status.
3. D5: re-reading after a flush error (M:233, M:201) observes committed in-memory state, not durable state — require a successful flush after the re-read; "re-run from step 1" hits #188's handler which looks the row up by name (188:admin_replication.rs:375) so steps 5-6 are never reached — specify a resume path keyed by the binding.
4. D4 executability: the seam (admin.rs:652-659) cannot build tag 0x0A (targets not in the DTO, S:19; S:58 "from the Prepared operation" does not exist yet) — drop 0x0A (0x0B already commits to the list) or carry the list in the DTO; the challenge store/format is undefined and the single-use claim cannot be enforced with a per-operation `challenge_consumed` boolean; the client-side `actor` value is unspecified (today both sides derive the HMAC key locally and the actor is not in the canonical bytes, hmac.rs:20-31); S:32 says ALL destructive confirmations switch to v2 but the field table (S:45) covers only drop_repo/drop_db; preview input semantics and authorization undefined.
5. `Rejected` rows can reserve names at boot: rows with a non-empty `audit_pending` are loaded at boot and "reservations stay published" (M:248, M:47) — including `Rejected` rows (M:113 enqueues their event), so a refused DESTROY of a healthy repo can make boot skip that repo.
6. I13 is false for anchor reservations: terminal marking grows coverage under control only (M:308 site 4), not under the admission guard as I13 (M:57) claims; a publisher can pass its check and publish into a name that has just become reserved.
7. Staging (E:29-37): the end-to-end forms of cases 2, 4, 5, 6 appear in no PR's case list; cases 1 and 2 gated at 8b-3b assert the audit barrier that lands in 8b-3c; R1-stage-1 (8b-3b) depends on §3f pending causes (8b-3c); 8b-3a makes a mirror mismatch fail closed while mirror writes stay best-effort until 8b-3c (S:114, db_management.rs:455-460) — a failed warn-only write makes the repo unopenable on master.
8. Predicate/state gaps: the step-0 check "every referencing row quarantined" (M:196) is vacuously true with zero rows and would physically destroy a healthy unbound repo; the stage-2 rule for incident-only coverage is undefined; R1-stage-2 does not cover absent destinations with no destruction operation; for catalogued-but-not-live destinations S:228 requires a repo copy that M:237 forbids writing; §7c item 2 is impossible for an absent target so item 4 (S:136-138) is dead text; R1-stage-1's step-1 reservations (M:226) are never released, including on revalidation abort.
9. Inconsistencies: the terminal event is `destruction_completed` in M:170 but `destroyed` in S:242; CREATE REPO takes the db gate shared (M:308 site 7) but the mode rule M:263 says exclusive for "create/replace a repository"; the db-gate type/fairness is unspecified — with tokio's write-preferring `RwLock` proof invariant (3) at M:287 ("publishers never block each other's gates") is false, and the order across several db gates (multi-db bindings, 188:binding.rs) is unspecified.

## P3

A torn audit line makes `read_log_for_verify` fail for the whole log so reconciliation stalls permanently; retention sweeps can delete the log that holds the barrier entry (re-append is benign, document it); `admissions` DashMap entries are never removed; the recovery-clear predicate (§3d) is unreachable in this series; `Blocked` with `Phase::Prepare` is unreachable; unsupported backends should be refused at preflight instead of becoming a permanent `Blocked`.
