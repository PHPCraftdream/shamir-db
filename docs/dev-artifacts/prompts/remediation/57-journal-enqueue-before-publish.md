### S5b design (ox review at master d5ed4666; binding for all S5b leaf tasks)

DEFECT (N1, P0, real on master). The journal event of a commit is queued AFTER the version is published and OUTSIDE the commit lock; the journal writer persists in channel order; reads are not bounded by any watermark. Interleaving: tx A gets v10, tx B v11 (disjoint tables, lock-free path). A is delayed between allocation and the post-publish emit (`finalize.rs:99`), B publishes (`materialize.rs:228`) and emits v11 (`changefeed.rs:315-316` try_send). A follower with bookmark 9 pulls from 10: `repl_handler.rs:171-173` -> `changelog.rs:151-167` -> `repo_instance.rs:341-346` -> `repo_instance.rs:1401-1408` -> `changefeed.rs:391-429` = unbounded `range_from(10)` with no watermark -> returns `[v11]`, `gap_at = None`; the follower applies v11, bookmarks 11 (`follower_loop.rs:351-361`), v10 is journaled later and never requested (`apply_replicated.rs:207` would skip it anyway) => silent event loss. The same defect exists on the AsyncIndex path (`commit()` at `commit.rs:959`, emit at `:975`) and on the follower's own downstream feed (`apply_replicated.rs:507` commit, `:538` emit after `persist_markers().await` at `:520`). Even with both versions published the window stays open because the writer persists in commit-completion order.

RULES.
1. W (the read bound) is `gate.completion().watermark()` (`repo_tx_gate.rs:~1030`, `completion_tracker.rs:~59`): the highest V such that every version k <= V is Materialized or Aborted. It MUST NOT be `last_committed()` (Phase 5a `mvcc_history.rs:~522` raises it early and out of order).
2. Enqueue at the point of no return: after the last step that can still abort the version, immediately before `version_guard.commit()`, with NOTHING that awaits or can fail between the two. One helper holds the invariant, e.g. `publish_journaled(guard, Option<PreparedJournal>) -> Option<Arc<ChangelogEvent>>`: `try_send(Event(arc.clone()))`, then `guard.commit()`, returns the Arc for the later broadcast. The live broadcast STAYS after publish (same Arc); do not move it under any lock.
   Publish sites to cover (all three): lock-free (`materialize.rs`, between the crash seam ~:217 and `commit()` ~:228; event passed into `materialize`; broadcast stays at `finalize.rs:99`), AsyncIndex (immediately before `commit.rs:959`; broadcast at `:975`), `apply_replicated` (after the failure exit ~:465-485, immediately before :507; broadcast :538). For `apply_replicated` enqueueing BEFORE the apply loop is wrong (it would journal an event whose version then aborts).
3. Invariant after the fix: for every version v that has an event, one of two things is sequenced before v is marked Materialized: the event is in the channel (`try_send` Ok), or `gap.first <= v` has been set (Full, Closed, or the orphan drainer).
4. NO event is ever enqueued for a version that never publishes (abort is only possible before WAL success; WAL failure/pending/unknown/requires-reopen all return before the enqueue; after WAL success `materialize` never aborts). No tombstones/skip entries. The gap is the only signal. B02-R already marks the changefeed gap for replayed orphans (`drainer.rs` `mark_changefeed_gap`).
5. The enqueue+commit pair has no await between them, so CommitDriver cancellation cannot separate them. Resolve the changefeed handle (`repo.changefeed()`) BEFORE the synchronous block (after `project_event` ~`commit.rs:1210` / `:919`; at `apply_replicated.rs:~387`). Changefeed init failure is silent today (`repo_instance.rs:~1436-1445`) and must not stay silent: keep a pending gap (an `AtomicU64` minimum on `RepoInstance`), apply it inside the `changefeed()` init closure via `new_with_gap(min(marker, pending))`, and re-check `changefeed.get()` after storing it to close the race with a concurrent init.

BARRIER PROTOCOL (replaces the `enqueued`/`persisted` counters, which are UNSOUND: channel slot order is not counter-increment order).
- Channel item: `enum JournalMsg { Event(Arc<ChangelogEvent>), Barrier(u64) }` (no new allocation). Add `confirmed_through: AtomicU64` and a `barrier_notify: Notify` to the feed.
- Writer: on dequeuing `Barrier(w)` every message ahead of it has finished `persist_one` (written, or gap marked); then `confirmed_through.fetch_max(w, Release)` + `notify_waiters()`. Handle `Barrier` at ALL receive sites: `recv`, the `try_recv` batch loop, and `drain_and_persist` (`changefeed.rs:~631-667`, `:~678`).
- Reader (replication Pull, `changes_since`, bridge backfill — all go through `repo_instance.rs:~1401-1408`): (1) `w = completion.watermark()` (Acquire), first thing; (2) if `confirmed_through >= w` go to (4) (idle long-polls cost nothing); (3) otherwise send `Barrier(w)` with `timeout_at(deadline, journal_tx.send(..))`, register `notified` (with `enable()`) BEFORE re-checking `confirmed_through >= w`, wait with select on that notification or the deadline; (4) `bound = w`; on timeout or Closed `bound = confirmed_through` (still safe, just older); (5) `range_from(from, limit)`, decode, stop at the first event with `commit_version > bound` (the result is a prefix, so `limit` cannot break it); (6) do the gap check (`changefeed.rs:~422-427`) AFTER the barrier.
- Memory ordering: Acquire/Release is sufficient (every link is a release->acquire hand-off); SeqCst, loom, locks, an overflow queue, a blocking send are all unnecessary.
- Reply when the writer is behind/stalled: the normal `Pull` shape with events <= bound, possibly empty; no new wire code (the long-poll retries every 50 ms, the follower treats an empty batch as idle). Log a warning and count confirm timeouts. Fixed engine constant budget ~1 s; NOT a tunable.
- No deadlock: the commit path only `try_send`s, the reader holds no lock, the writer never waits for readers, the reader's wait is bounded. Full keeps today's policy (count the drop + `mark_gap(v)`; now guaranteed visible before W passes v). Closed (writer task gone) is silently ignored today (`changefeed.rs:~328-330`) and MUST also `mark_gap(v)`. A barrier occupies one of the 4096 slots (bounded by concurrent pulls) - accept and document.

LIVE BROADCAST is NOT fixed by S5b and not made worse (broadcast order = tail-completion order; `bridge.rs:411-415` drops live events with version <= the bridge watermark; the bridge seeds its watermark from `last_committed`, `bridge.rs:390-400`) - tracked separately as N1-live. After S5b's read-side change the journal-backfill -> live hand-off boundary (`bridge.rs:229`, `:314-316`) is correct.

CRASH WINDOW is NOT fixed by S5b (recovery does not check the journal, WAL truncation is not gated on journal persistence) - tracked as S5c.
