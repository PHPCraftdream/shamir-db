## Task

B02-D — the post-WAL commit tail must not die with the caller (step 2 of B02; design by a read-only review, 2026-10-11). Today, after `begin_grouped` returns Ok, the committing future itself runs materialize phases 5a-5d, changefeed emission, vector delta/HNSW promote, Level-3 lock release and holds the uwl/drain/cell guards. If the future is dropped (client disconnect, timeout, server shutdown via `run_until_cancelled`), the drainer replays only the WAL ops. Symptoms: (1) a stale posting resurrected when a later tx updated/deleted the record before the drainer replays its IndexPut; (2) a unique duplicate after LWW replay because the uwl guards were released on cancel and the unique re-check reads postings only (`pre_commit.rs` ~:907); (3) the orphan loses changefeed + vector replay (`finalize.rs` ~:99, `materialize.rs` ~:208); (4) Level-3 pessimistic locks are never released on cancel. PR #69 (merged) keeps data recoverable via `orphaned_post_wal`; that machinery STAYS as the fallback.

REJECTED designs (do not implement): a `tokio::spawn` of the tail after `wal_accepted()` for every commit (task allocation + forced yield + cross-task wake; the repo measured +22% for a per-append hop in `wal_group_commit.rs`'s module doc, and it breaks the single-poll Mem commit atomicity on current-thread runtimes); an inline tail with a drop guard that "restarts from the last phase" (`collect_data_batches` consumes the staging store, changefeed/vector appends are not idempotent).

DESIGN (implement exactly this):
1. `CommitDriver` (new file) owns `Option<Pin<Box<dyn Future<Output = Result<TxOutcome, TxError>> + Send>>>`, an `in_poll: bool`, a `tokio::runtime::Handle` captured when the driver is built, and a snapshot of `locked_keys` that is `Some` only for Level-3 transactions. `Future::poll` sets `in_poll`, polls the inner future, clears the flag — the happy path polls in the SAME order as today: no spawn, no extra yield. `Drop`: if the inner future is unfinished and `in_poll` is false, move the suspended box into `handle.spawn(AssertUnwindSafe(fut).catch_unwind())` and log a panic from it. `Drop` with `in_poll == true` means a panic is unwinding out of the tail: never poll that future again; drop it and spawn a best-effort `release_locks` from the snapshot.
2. The boundary sits in `commit_tx_inner` right after `pre_commit_prelock` returns and covers both `commit_tx_lockfree` and `commit_tx_inner_legacy_async`. The `async move` block owns `tx`, the uwl/drain guards, the `Arc<RepoTxGate>`, the `Arc<RepoWalManager>` and a FOREGROUND repo clone (`live = Some`, so the drainer loop stays alive until the tail ends). `commit_lock` and `_serializable_guard` are taken INSIDE the block. `apply_backpressure` stays OUTSIDE the driver (flow control for the caller only).
3. Semantics (document on `commit_tx`): cancelling during prelock (uwl waits) is still a clean abort; AFTER prelock cancelling only stops the wait — the commit runs to completion. This matches the existing contract in `batch_execute.rs` (#666) "commit_tx always runs to completion". PR #69's pre-WAL control test must be revisited accordingly: a cancel BEFORE the boundary still aborts; flip only what the new contract changes and say which assertions changed.
4. `CommitTailBarrier`: `AtomicUsize` + `Notify` (same pattern as `table/writer_drain_barrier.rs`), a field of `RepoInstance`, `RepoInstance::quiesce_commits(timeout)` that waits for zero in-flight tails (inline AND detached count: the guard is created inside the box). It is NOT called from `flush_buffers` (`synced_flush` calls that while commits run; waiting for zero there would starve). A separate task wires it into shutdown.
5. Panics: an inline panic propagates to the caller and the tail is not re-run; a detached panic is caught and logged. In both cases the `VersionGuard` post-WAL drop registers an orphan (existing behaviour). Add a counter `post_wal_orphans_total` (metrics struct that already holds the tx counters) that should stay 0 in normal operation.
6. Cost per commit must be O(1): one Box, one `RepoInstance` clone, one atomic inc/dec. No allocation per row. Do not run benches (no local runs); state in the PR that the go/no-go bench gate (`tx_pipeline` mem N=1, `tx_concurrent` N=64 within +3%) is still owed.

Required tests (deterministic: `Notify`/oneshot handshakes with `TEST_POST_WAL_PRE_PUBLISH_HOOK`, no sleeps; concurrent parked/committing transactions must use `IsolationLevel::Snapshot` unless they are the Serializable one under test, because a parked Serializable committer holds `commit_lock`): (a) abort the caller at the post-WAL hook -> `orphan_max` stays 0, the tail finishes after `resume`, a concurrent unique insert of the same value blocks until resume and then gets `UniqueViolation`, exactly ONE changefeed event for the version, a younger Level-3 transaction gets the lock only after resume, and after a later update + drain there is no stale posting; (b) cancelling a parked group-commit follower still publishes the commit; (c) the barrier counts both an inline and a detached commit and `quiesce_commits` returns when they finish and times out when one is wedged; (d) an injected panic in the tail falls back to an orphan (the drainer completes it), the barrier returns to 0 and the Level-3 locks are released; (e) the existing current-thread SSI tests are unchanged and still pass.
