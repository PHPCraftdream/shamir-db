## 6. DDL / wire / builder / client surface

### 6a. Grammar and DTOs

**Grammar sketch (DECIDED):**

```text
DROP REPOSITORY <name> [CASCADE] [IF EXISTS] [DESTROY QUARANTINED DATA '<reason>' OPERATION ID '<op-id>' NONCE '<32 hex chars>' DIGEST '<64 hex chars>' CHALLENGE '<preview challenge>'];
DROP DATABASE <name> [CASCADE] [IF EXISTS] [DESTROY QUARANTINED DATA '<reason>' OPERATION ID '<op-id>' NONCE '<32 hex chars>' DIGEST '<64 hex chars>' CHALLENGE '<preview challenge>'];
```

**DECIDED:** the `DESTROY QUARANTINED DATA` modifier additionally carries `digest` + `challenge` from the mandatory preceding `destruction_preview` call (below); the HMAC covers the digest (§6b tag 0x0B).

- `CASCADE` controls child scope only; it never authorizes crossing replication bindings or physical destruction.
- **DTO (wire):** optional field `destroy_quarantined_data: Option<{ reason: String (nonempty, 1..=512, printable UTF-8), operation_id: String (≤64, [0-9A-Za-z._-]+), nonce: String (exactly 32 lowercase hex chars — the hex form of 16 bytes), digest: String (exactly 64 lowercase hex chars), challenge: String (from destruction_preview) }>` on `DropRepoOp` (**OBSERVED** crates/shamir-query-types/src/admin/types/repo_ops.rs:43-55: no `deny_unknown_fields` on the Drop ops) and `DropDbOp` (**OBSERVED** crates/shamir-query-types/src/admin/types/db/db_ops.rs:27-40). Unknown-field tolerance on Drop ops is intentional for forward-compatible builders; the new field is `#[serde(default, skip_serializing_if = "Option::is_none")]`.
- **Builder (Rust):** `.destroy_quarantined_data(reason, operation_id, nonce, digest, challenge)` on the drop builders — **OBSERVED** current locations `crates/shamir-query-builder/src/ddl/repo/drop_repo.rs` and `crates/shamir-query-builder/src/ddl/db/drop_db.rs` (panel paths `ddl/drop_repo.rs` are stale). HMAC computation moves behind the modifier check.
- **TS client:** `.destroyQuarantinedData(reason, operationId, nonce, digest, challenge)` on the drop builders in `crates/shamir-client-ts/src/core/builders/ddl/` (**OBSERVED** `ddl-schema.ts` holds `dropDb` at :83-97 and `dropRepo` at :99-113, both computing the canonical bytes via `canonicalDropDb`/`canonicalDropRepo` imported from `core/protocol/hmac.ts`); request flows through `crates/shamir-client-ts/src/core/client/client.ts` unchanged.
- `IF EXISTS` semantics per 131 §4a (inspect incomplete operations first; **OBSERVED** early exits admin_db_repo.rs:106-112 and :415-423, `if op.if_exists` at :416).
- `nonce`: supplied by the caller; the wire DTO carries `nonce: String` (32 hex chars) inside `destroy_quarantined_data`; **echoed verbatim in the response** (`{ operation_id, state, nonce }`), and bound into the v2 canonical encoding (the canonicalizer encodes the 16 decoded bytes) — a replayed confirmation over different nonces fails, and a lost response cannot be confused with a different request. The nonce is still consumed ONCE per terminal outcome (existing rule); the CHALLENGE (below) is a separate, server-issued single-use credential.
- **Destruction preview — DECIDED (the two-step confirmation exchange):** new admin wire op `destruction_preview(targets, cascade)` → response `{ targets: Vec<{db, repo, storage_object_id}> (canonical order: sorted by (db, repo)), digest: [u8;32] — SHA-256 over the canonical length-prefixed encoding of the target list (the encoding described in §6b for tag `0x0B`; the same encoder, used standalone), challenge: String — short-lived, server-issued, SINGLE-USE, expires_at_ns (≤ 60 s ahead) }`. The client MUST call `destruction_preview` first and sign the returned digest + challenge.
- **TS client:** new method `.destructionPreview(targets, cascade)` (returns the preview response); `.destroyQuarantinedData(reason, operationId, nonce, digest, challenge)` — the builder carries the preview's digest + challenge into the DTO and the canonical encoding (§6b fields 0x0B/0x0C).
- **Builder (Rust):** `.destroy_quarantined_data(reason, operation_id, nonce, digest, challenge)` on the drop builders, plus a Rust admin-call analogue of `destruction_preview(targets, cascade)`; `digest` is the 32-byte value (hex on the wire).
- **Challenge rules:** expiry ≤ 60 s, single use, consumed at Prepare. **DECIDED: the challenge store/format** — a new system-store table `destruction_challenges` (v1): `{ challenge_id: [u8;32] /* random */, digest: [u8;32], session_binding: [u8;32] /* HMAC-key fingerprint of the issuing session */, created_at_ns: u64, expires_at_ns: u64 }`. SINGLE USE is enforced by a durable DELETE-IF-MATCHES (challenge_id + digest) at the Prepare write — not by a per-operation `challenge_consumed` boolean (a boolean cannot stop two concurrent prepares; a durable delete is atomic). **A1 — authorization is atomic:** the challenge DELETE-IF-MATCHES and the `Prepared` PUT-IF-ABSENT occur in ONE system-store transaction under the held admissions, followed by one flush. A failed challenge writes NO row and authorizes no execution; the remedy is re-run `destruction_preview` and retry with a FRESH operation id (or `destruction_retry` only if a prior authorized row genuinely exists). Expired rows are swept opportunistically; deletion is the single-use mechanism.
- **Preview authorization — DECIDED:** `destruction_preview` requires the SAME authority as the destroy it precedes (Delete + replication-management), and the challenge it mints is SESSION-KEYED (`session_binding` above) — a challenge minted in one session is unusable in another; the digest is otherwise a pure read.
- **Actor — DECIDED:** the actor is ALREADY in the canonical bytes (tag `0x08`); the SERVER recomputes the canonical encoding from the authenticated session's canonical actor string and REJECTS a client-supplied actor that differs (the client value is informational); the TS client obtains the actor from the session/hello response (the exact server actor string is exposed there — if the hello does not currently carry it, 8b-3c adds it to the hello payload; the shared test vectors pin the string).
- **Verification seam:** **DECIDED (v2, not current behavior):** the digest is what `check_destructive_hmacs` will verify WITHOUT a Prepared operation once the v2 encoding lands (8b-3c, §6b) — the HMAC will be over the digest (not only the logical names), so the seam verifies it session-keyed. **OBSERVED today:** the current match arms at `crates/shamir-server/src/engine/db_handler/handlers/admin.rs:656-659` sign the LOGICAL NAMES (`canonical_drop_db(&op.drop_db)` / `canonical_drop_repo(db_name, &op.drop_repo)`) — the digest-keyed behavior is the DECIDED end state (8b-3c future work, §6b/§6c vectors), NOT an observed fact; the executor's re-resolution of the live/catalogued set against the signed digest at Prepare (131 §4a preflight) is the second half.

### 6b. Injective canonical confirmation encoding (v2) — DECIDED (F8)

**DECIDED:** replace the NUL-concatenation canonical forms for ALL destructive confirmations with a length-prefixed, injective encoding. The product is unreleased: **replace outright, no dual-form, no migration**.

```text
version(1B) = 2
field_count(1B)
for each field, in FIXED order:
    tag(1B) || len(u32 LE) || bytes
```

Fields, fixed order (omitted fields are simply absent; `field_count` counts present fields):

| # | tag | Field | Present | Content |
|---|-----|-------|---------|---------|
| 1 | 0x01 | operation_kind | always | `"drop_repo"` \| `"drop_db"` (UTF-8) |
| 2 | 0x02 | db | always | db name (UTF-8) |
| 3 | 0x03 | repo | `drop_repo` only | repo name (UTF-8) |
| 4 | 0x04 | cascade | always | 1 byte, 0 or 1 |
| 5 | 0x05 | destroy_flag | always | 1 byte, 0 or 1 |
| 6 | 0x06 | destroy_reason | when destroy_flag = 1 | reason (UTF-8) |
| 7 | 0x07 | operation_id | when destroy_flag = 1 | operation id (UTF-8) |
| 8 | 0x08 | actor | always | actor (UTF-8) |
| 9 | 0x09 | nonce | when destroy_flag = 1 | exactly 16 bytes |
| 10 | 0x0B | digest | when destroy_flag = 1 | exactly 32 bytes — SHA-256 over the canonical encoding of the target list (**tag `0x0A` is DROPPED/UNASSIGNED — the wire seam cannot build a targets field because the frozen target list is not in the drop DTO; the digest (0x0B) alone commits to the list, and the executor compares its recomputed digest of the resolved live/catalogued set against the signed digest at Prepare**) |
| 11 | 0x0C | challenge | when destroy_flag = 1 | challenge string (UTF-8) |

Injectivity: length prefixes make distinct field sequences encode distinctly (no NUL-delimiter ambiguities); fixed field order + explicit `destroy_flag` makes a plain DROP (`destroy_flag = 0`, fields 6-7 absent) byte-distinct from any destruction confirmation. **v2 scope — DECIDED: v2 replaces the NUL forms for the drop_db/drop_repo confirmations ONLY in this series**; other destructive confirmations (if any exist) are out of scope and keep their current encodings. Plain drops get `destroy_flag = 0` and omit the optional fields; a plain-DROP HMAC therefore can never authorize destruction. Plain drops carry no nonce — the nonce exists only inside `destroy_quarantined_data`, so it is encoded only when `destroy_flag = 1` (fields 6-7, 9-11 all absent for a plain drop). **The v2 canonical encoding BINDS the digest + challenge** — the HMAC covers the DIGEST (tag `0x0B`, 32 bytes of SHA-256 over the canonical length-prefixed target-list encoding — the same encoding `destruction_preview` uses, computable at the server seam from the preview response), not only the logical names, and the server-issued single-use challenge (tag `0x0C`); a stale preview (the live/catalogued set changed after `destruction_preview`) fails closed at Prepare with `destruction_target_changed`. The frozen target list itself lives in the `destruction_preview` response, the `destruction_challenges` row (below) and the `Prepared` operation — never in the drop DTO.

**Validation (server and client):** reject NUL and C0 control characters in `reason`, `operation_id`, `actor`; enforce the Appendix-A bounds; `nonce` must decode from exactly 32 hex chars to 16 bytes; `digest` must decode from exactly 64 hex chars to 32 bytes; `field_count` and `version` must match this table exactly (unknown tags/versions → reject).

### 6c. Error codes — the eleven typed wire codes (DECIDED, normative)

Survive dispatch incl. rename (**OBSERVED** `db_error_to_batch` at execute/core/helpers.rs:85). Each `DbError` variant maps 1:1 to its wire code; the remedy contract is what the client/operator does on receipt:

| DbError variant | Wire code | Remedy contract |
|---|---|---|
| `ReplicationDestinationBound` | `replication_destination_bound` | The name is bound by live replication bindings; release via R2'/R1 first (rename: format limitation per 131 §1). |
| `QuarantinedSubscriptionDestinationsRemain` | `quarantined_subscription_destinations_remain` | Destroy each remaining bound destination, then retry R1 (stage-1 semantics; I9); a catalogued destination with ZERO referencing rows is destroyed via the explicit unbound-repo destruction path (131 §4a step 0). |
| `QuarantinePersistencePending` | `quarantine_persistence_pending` | A pending terminal cause for a referencing generation is unresolved (§3f of 131); retry after the flush is confirmed. |
| `DestinationNameReserved` | `destination_name_reserved` | The name is reserved (anchor or non-`Destroyed`/non-`Rejected` operation of `kind: Repo | Database`; a `Completed` `SubscriptionRemoval` never reserves); or a `Destroyed` operation with non-empty `audit_pending` (released when the pending set drains); only the §7c recovery exception admits publication. |
| `DestructionInProgress` | `destruction_in_progress` | An incomplete operation covers the target; poll `destruction_status`, then `destruction_retry`/wait. |
| `DestructionBlocked` | `destruction_blocked` | External block; clear the cause, then `destruction_retry(operation_id)`. |
| `StorageDestructionUnsupported` | `storage_destruction_unsupported` | The backend cannot destroy this component; no retry path until the backend gains support. |
| `UnsafeStorageOwnership` | `unsafe_storage_ownership` | A live replacement/foreign object occupies the recorded identity; never deleted (I6); operator investigation required. |
| `DestructionOperationConflict` | `destruction_operation_conflict` | Same operation id with different frozen parameters; issue a new operation id. |
| `DestructionAuditUnavailable` | `destruction_audit_unavailable` | The audit chain could not durably record the intent; retry the same operation id — the resubmission RE-RUNS the audit barrier (idempotent by event id) and spawns the executor — or call `destruction_retry` (accepts `Prepared`). (The operation STAYS `Prepared`, reservations PUBLISHED, nothing deleted — 131 §3e.) |
| `DestructionTargetChanged` | `destruction_target_changed` | The resolved live/catalogued target set no longer matches the signed preview digest, OR the challenge is stale/expired/consumed. **Because challenge consumption is atomic with the Prepared PUT-IF-ABSENT (131 §3b), a failed challenge means NO row was written**; the remedy is re-run `destruction_preview` and retry with a FRESH operation id. `destruction_retry` applies only when a prior authorized row genuinely exists (from an earlier successful Prepare). |

`ErrorClass` mapping (journal `error_class` field → wire code, 131 §3b): `OwnershipMismatch → unsafe_storage_ownership`; `ExternalLock` / `PermissionDenied` / `UnknownIo → destruction_blocked`; **`AuditUnavailable → destruction_audit_unavailable`** (the cap-exhaustion/audit-parking class, 131 §3e item 6b). Unsupported backend is refused at preflight and has no row variant.

**Distinct diagnostic code (NOT one of the eleven lifecycle DDL codes above) — DECIDED:** `StorageFormatUnsupported` → wire/diagnostic code `storage_format_unsupported`. Surface: repository OPEN path, the installer, and the admin surface (open/admin diagnostics; it is not a lifecycle DDL refusal and is not part of the eleven-row table above). Remedy: the data directory predates 8b-3a (no `StorageOwnership` support); there is NO migration path (A3) — the operator must EXPORT or DESTROY the data manually with out-of-band tooling; the server refuses to open the directory. This code is deliberately kept OUTSIDE the eleven lifecycle codes so lifecycle retry/DDL semantics cannot be confused with a pre-8b-3a format refusal.

## 7. Creation exclusion matrix — complete (F3)

Reservation check = `(db, repo)` covered by anchors, non-`Destroyed`/non-`Rejected` operations **of `kind: Repo | Database`** (a `Completed` `SubscriptionRemoval` record never reserves; 131 §3c), or a `Destroyed` operation with non-empty `audit_pending` (released when the pending set drains) (131 §3c; `repo = "*"` = database-scope reservation covering every `(db, *)`).

### 7a. Proposed NamespaceAdmission guard and lifecycle exclusion

- **Proposed TWO-level hierarchy:** a per-database RW-style gate plus per-(db, repo) admission mutexes beneath it, held in an in-process registry on `ShamirDb`: `admissions: DashMap<(String, String), Arc<tokio::sync::Mutex<()>>>`. A publication acquires db gate then sorted target mutexes before validation; cancellation-safe RAII holds through publication/abort. Scope modes and complete path compositions appear below.
- **DECIDED:** Reclaim an entry only while holding the same map-entry/shard lock used by all get-or-create and Arc-clone operations, and only if `Arc::strong_count(&entry) == 1`; do not create a temporary clone for counting. No Weak, external-clone, or bypass path may retain/manufacture handles; the registry is the sole synchronized source. Count 1 then proves no user retains the old mutex when a new identity is installed. At capacity, backpressure/refuse; never evict a referenced entry.
- **Stage boundary:** 8b-3b delivers and tests only the admission-registry/control primitive and destruction-side reservation publication; 8b-3c wires every real publisher and tests publisher-versus-reservation races end to end. No composed-path guarantee applies before 8b-3c. **8b-3b executor and authority are `pub(crate)` and not wire/admin dispatchable (A14); destructive dispatch becomes reachable only in 8b-3c together with all publisher wiring.**
- **Proposed scope modes:** the database gate is acquired once at final mode and held through the operation; no upgrade. Repository-scope work (including CREATE REPO) is SHARED; database-scope work (including CREATE DATABASE) is EXCLUSIVE.
- **Proposed order and R1 exception:** proposed admission gates/mutexes precede control, then lease write gate, then write admission. Reservation mutation and authoritative runtime check/use paths use a short control section; the installer precheck is read-only and uses maintenance-lock exclusion instead, without control.
- **Lifetime:** the proposed guard lives only within one operation; cancellation drops it (RAII); it is not persisted or needed at boot. On Blocked/exit the set releases; retry reacquires after revalidation.
- **Boot/executor guard:** boot publishes/skips reservations before request acceptance; runtime executor uses the same proposed admission guard.

Remove/rename/destroy/R1 take scope-appropriate gates and sorted repo mutexes before control. **Admission-registry reclamation:** remove an entry only while holding the same registry map-entry/shard lock used by every Arc clone/get-or-create path and iff `Arc::strong_count(&entry) == 1`, without a temporary clone. The registry is sole source; no Weak/external cloning/bypass may retain old mutex. Capacity uses backpressure, never eviction of a referenced entry.


**Proposed path order:** CREATE DATABASE exclusive `(db, *)` → control through insert. CREATE REPO shared db → repo mutex → `repo_create_locks` → control through publication. Generic add-repo shared db → target mutex → control through publication. CREATE SUBSCRIPTION/RESUME shared db + sorted bound mutexes → control. Remove/rename/destroy/R1 scope gate(s) + sorted target mutexes → control. Seed full wrapper is 8b-3e; 8b-3c early check is maintenance-lock based; full wrapper remains 8b-3e.

### 7c. Recovery exception — RESUME / replacement-rebind into a reserved destination (F3-iii)

**Recovery path boundary:** R2' (destroy) → R1 (release the name) → fresh install into ABSENT target as NEW incarnation. In-place replacement into CURRENT incarnation is out of scope.

1. The subscription row already binds THIS destination (name match at bind time).
2. **(Applies ONLY when the destination is LIVE or CATALOGUED):** the live-or-catalogued `storage_object_id` **equals** the id recorded in the binding/incident (no replacement incarnation). For an ABSENT destination this item is vacuous and the exception reduces to items 1, 3 and 4 (there is no live object to compare).
3. The installed receipt/incident evidence matches (same receipt digest / incident evidence; the exact retry-identity tuple is (db, repo, receipt `artifact_digest`, lineage_id) per §8c).
4. No non-terminal destruction operation covers the name; a `Destroyed` operation covering it is permitted exactly when its recorded target (db, repo) equals the install target (the destroyed-then-reinstall path of §8). **(This item is LIVE text because item 2 no longer requires a live/catalogued object — an absent target whose covering operation completed passes item 4, which is precisely the fresh-incarnation reinstall.)**


**Payload identity (P1-2, normative):** the canonical payload is FROZEN at event creation; the annotation `outcome ∈ { emitted, replayed, acked }` is a RECORD-LEVEL field OUTSIDE the digest (it annotates the outbox record, not the canonical payload above), so a replay never changes the digest.

**Id note:** `event_id = { operation_id, transition_ordinal }` — `record_version` and `target_state` are NOT part of the id (`target_state` remains a separate payload field). **Ordinals START AT 1** (the durable counter is `audit_next_ordinal: u32`, initial 1, 131 §3b/A.2). A retried `Blocked` emits a second `blocked` event for the same state, so distinct ordinals are required for idempotent replay/reconciliation (131 §3e reconciliation rule).

Enums (normative): `event_kind ∈ { prepared, rejected, quiesced, catalogued, destroyed, blocked }` — there is NO `destroying` event kind: the `Destroying` transition emits no dedicated audit event (131 §3e); **`destroyed` is THE terminal event kind for `Destroyed`**; retirement is gated ONLY by successful completion (a `Repo | Database` record retires at `state = Destroyed` + empty `audit_pending`; a `SubscriptionRemoval` at `phase = Completed`; a final `Blocked` operation retires ONLY via `destruction_retry` → `Destroyed`, 131 §3e item 7 — there is NO separate "retired Blocked" operation or Blocked-retirement-gating event). The `rejected` kind is emitted best-effort DIRECTLY at the pre-write refusal and is NEVER enqueued in `audit_pending` (which stays empty for `Rejected`). The event kind names map to the operation state whose completion they record (`prepared` records `Prepared` reached, `catalogued` records `Cataloguing` finished, etc.). `target_state ∈` operation states (the 3b state enum); `outcome ∈ { emitted, replayed, acked }` — a RECORD-LEVEL annotation OUTSIDE the digest (payload identity, A.5 above).

**A.6 Wire DTO `destroy_quarantined_data`** — `{ reason: String(1..=512, printable), operation_id: String(≤64), nonce: String (32 hex chars), digest: String (64 hex chars — the `destruction_preview` digest), challenge: String (from `destruction_preview`) }`; echoed back as `{ operation_id, state, nonce }`. **The preview exchange (new admin wire op):** `destruction_preview(targets, cascade) -> { targets: Vec<{db, repo, storage_object_id}> (sorted by (db, repo)), digest: [u8;32], challenge: String (single-use), expires_at_ns }`; the challenge is consumed at Prepare and the executor re-resolves the live/catalogued set against the signed digest (fail-closed `destruction_target_changed`, §6c).

**A.7 `AuditAck`** — `{ seq: u64, checkpoint_position: [u8;32] }` (131 §3e).

**A.7a `checkpoint_durable` (DECIDED):** `checkpoint_durable() -> Result<AckWatermark, AuditError>` — flushes + fsyncs the log FIRST and FAILS if the flush failed (unlike the OBSERVED void `appender.checkpoint()`, audit_appender.rs:706-713, which logs the flush failure and still writes the checkpoint), then writes the checkpoint keyspace durably (SyncAll) and returns `AckWatermark = next_seq − 1` — the highest assigned seq covered by the durable log + checkpoint, advanced ONLY by a successful write+sync of a contiguous prefix (131 §3e item 0b); the chain poisons on appender failure. **Poison attribution:** ONLY by a durability failure ATTRIBUTED to a specific append (the synchronous barrier/append path — the caller learns the event id); a BACKGROUND-flusher failure is NOT a poison: the batched flusher RETAINS the failed batch in the buffer (never drops it) and marks the sink DEGRADED; the next successful flush of the retained batch advances the watermark; if it cannot be re-flushed, the NEXT attributed barrier append fails and poisons normally. When the barrier's batch flush fails, ALL co-batched entries' seqs are NOT advanced in the watermark (contiguous-prefix rule only); their owners learn via their own ack paths; no per-entry action is required. A poison that survives reconciliation retries surfaces as `AuditSinkError::Poisoned` on every append and requires operator/ops action — never silent clearing. **CLOSED RULE — the ONLY proofs that a barrier event is durable are** (a) the original append's own successful sync (ack returned); (b) a FRESH append of the SAME event_id that succeeded (idempotent by event id — duplicates tolerated by the verifier, deduplicated on read; includes the reconciliation RE-WRITE); (c) an ack record written by `checkpoint_durable` AFTER its own successful flush+sync naming a durable-through seq ≥ the event's seq. A found-but-unconfirmed entry in the log tail is NOT evidence and must never be adopted; `AuditSink::contains`/`read_durable_tail` only answer (c)-style watermark questions and locate entries for the (b) RE-WRITE — never authorize adoption by themselves. Restart: the executor holds no memory of (a); it uses (b) by re-appending the pending entry or (c) by reading the persisted checkpoint_durable ack record (which survives in the checkpoint keyspace) — never by trusting the log tail alone. An outbox event is acknowledged only when `ack_watermark >= event.audit_seq`; the periodic scheduler (scheduler.rs:204-216) switches from void `appender.checkpoint()` to `checkpoint_durable` + an ack notification to the resident `AuditBookkeeper` (131 §3e step 5), which for EVERY loaded row with pending audit — including boot-loaded `Destroyed`/`Blocked` rows that have no executor — removes the acknowledged entries and advances `audit_acked_ordinal` in ONE `commit_durable` CAS on `record_version` (executors own the state/phase transitions; the bookkeeper is the only other row writer and is restricted to the audit fields; 131 §3b). **The unpoison path:** a POISONED chain admits exactly ONE append class — the reconciliation RE-WRITE of the failed event id (the sink bypasses the poison check for that single event id, tracked by the chain) and UNPOISONS upon that entry's own successful `write_all` + `sync_all`; any other append during poison returns `AuditSinkError::Poisoned`. Invariant: poison ⇒ either the failed entry is re-written durably or the sink stays poisoned (fail-closed), never silently cleared. `checkpoint_now` (audit_chain.rs:436-441) is a manual force, NOT a durability barrier.

**A.7b `AuditSink` (NEW — deliverable of 8b-3b):** the `shamir-db`-side seam, no new crate dependency:

**Poison attribution:** a poison is set ONLY by a durability failure ATTRIBUTED to a specific append (the synchronous barrier/append path — the caller learns the event id). A BACKGROUND-flusher failure is NOT a poison: the batched flusher RETAINS the failed batch in the buffer (never drops it) and marks the sink DEGRADED; the next successful flush of the retained batch advances the watermark; if it cannot be re-flushed, the NEXT attributed barrier append fails and poisons normally. **A.9 Log framing + sink-writer discipline (A9, normative):**
- **Record framing (concrete, DECIDED):** each audit log record is `len: u32 LE ‖ payload ‖ crc32c: u32 LE`, where `len` counts PAYLOAD bytes only and the CRC32C covers `len` field + payload (the 4 length bytes then the payload bytes). Maximum record size 1 MiB — payload ≤ 1 MiB − 8 bytes; a longer payload is rejected at encode time, never written. On open: an incomplete FINAL record (`len` overruns EOF) or a bad-checksum FINAL record is TRUNCATED before any append; a corrupt MIDDLE record FAILS CLOSED (poisoned chain). Same event id + different payload SHA-256 = corruption: poison plus incident, never dedup.
- **Single serialized writer (DEC-3):** all destruction-lifecycle `append_durable` calls go through ONE writer task/queue owned by the lifecycle module; no other caller submits lifecycle appends concurrently (131 §3e item 6b).
- **Same-event coalescing (in-flight table, DECIDED):** the serialized writer keeps an IN-FLIGHT TABLE `event_id -> shared completion`; a second submission of an in-flight event id JOINS that completion (NO second append) and receives the same result; after an `Acked` completion a later submission of the same event id returns the result VARIANT **`AlreadyAcknowledged`** WITHOUT appending — explicitly NOT a reconstructed `DurableAck` (no `seq`/`checkpoint_position` is ever recovered from an ordinal; the durable source is `audit_acked_ordinal`, 131 §3e step 5/6b). A duplicate record can arise ONLY from a re-write after a CLASSIFIED-AMBIGUOUS outcome (failed or timed-out append, crash before an acknowledgement is recorded) (131 §3e item 6b).
- **Timed-out append ownership (A10):** a timed-out `spawn_blocking` append is NOT abandoned — the writer retains the event id, joins the blocking task (bounded), classifies acked/failed/unknown, and only then (unknown ⇒ the single RECONCILIATION RE-WRITE) submits anything further; no append is in flight unreconciled while another is submitted (131 §3e item 6b).
- **Bounded-join failure → `Parked` (DECIDED):** if the bounded join of a timed-out blocking append ALSO times out, the writer enters `Parked` — it accepts NO further appends for ANY event; new requests FAIL FAST with `destruction_audit_unavailable` (bounded: the client never waits on the blocking task); the blocking-task handle is RETAINED and RE-POLLED non-blockingly on an interval; completion → classify → resume. A process restart treats the in-flight append as AMBIGUOUS and boot replay applies the coalescing + budget rules. Operation rows stay `Prepared`/`Blocked` exactly as the §4b state machine says (131 §3e item 6b).
- **Durable duplicate budget (DECIDED):** every `audit_pending` entry carries `append_attempts: u8` (starting at 1 — the original append is attempt 1), incremented inside the SAME `commit_durable` transaction that precedes each re-write (permitted only while `append_attempts < (1 + extensions) * MAX_APPEND_ATTEMPTS`); the operation row carries `audit_acked_ordinal: u32` (advanced by the **`AuditBookkeeper`**, 131 §3e step 5 — the only writer besides executors, restricted to the audit fields `audit_pending`/`audit_acked_ordinal`/`audit_next_ordinal`, incl. for boot-loaded `Destroyed`/`Blocked` rows without an executor) and `append_budget_extensions: u8` (audited operator extensions; each adds `MAX_APPEND_ATTEMPTS` to the cap); duplicates of an event ≤ `append_attempts - 1`; `MAX_APPEND_ATTEMPTS = 3`; at the cap the operation PARKS as `Blocked` with `error_class = AuditUnavailable` (wire `destruction_audit_unavailable`, §6c) and `failed_phase` = the current phase; operator recovery is the audited `destruction_retry` carrying a budget extension — which FIRST runs the read-only (c)-proof (a covering ack watermark resolves the entry WITHOUT any append). No silent retry loop. The duplicate guarantee: `duplicates <= (1 + extensions) * MAX_APPEND_ATTEMPTS - 1`, at most one per classified-ambiguous outcome (supersedes the earlier "at most one duplicate per ambiguous append" wording; 131 §3e item 6b). The barrier I/O runs on `spawn_blocking` with a bounded timeout; on timeout the row stays `Prepared` with `destruction_audit_unavailable`. Group commit is allowed only if each acknowledgement covers its own sequence number (A10). Latency is exposed as a metric. Fault-injection CI cases: 131a §9 cases 16-20.

The server (shamir-server) implements it over the batched appender; the launcher injects `Arc<dyn AuditSink>` into `ShamirDb::init_with_env_policy(config, audit_sink: Option<Arc<dyn AuditSink>>)` BEFORE replay; outbox replay waits for the sink. Invariant protected: the barrier proves durable intent without in-memory chain state and without a server dependency in shamir-db.

## Appendix B — administrative inspect/retry API (F7-iv, DECIDED)

On the existing admin surface (wire DTOs alongside the other `destruction*` operations; the HTTP/wire handler returns immediately — status is a pure read, retry spawns a detached executor per §4f of 131):

- `destruction_status(operation_id) -> { state, failed_phase?, error_class?, safe_restart_phase?, targets: Vec<{db, repo, storage_object_id}>, progress: Vec<{component_id, kind, absent: bool | "unknown"}> — **DERIVED** from `verify_absent` probes at status time, not durably stored, audit_acked: bool — true when `audit_pending` is empty (all outbox entries drained), anchors_remaining }` — a **pure read of `destruction_operations`** (+ a `verify_absent` probe only when the caller asks for `?verify=true`); a lost response is answered by re-issuing the call (idempotent, no side effects).
- `destruction_retry(operation_id)` — resumes a `Blocked` operation from `safe_restart_phase`, **or claims a stranded `Prepared` operation (audit-barrier failure) by re-running the barrier (idempotent by event id) and spawning the executor (131 §3e)**; **also accepts a `SubscriptionRemoval` operation (the R1-stage-1 record) — looked up FIRST through the permanent `destruction_bindings` table `(subscription, binding_generation) -> operation_id` (A.2e; survives compaction — after archival it resolves to the tombstone); the record's `operation_id` is accepted too, resumed from the recorded `phase` (**STAGE-AWARE (P1-3):** stage 1 — `RowDeleted` ⇒ destination-ABSENCE re-verification + completion, predicates from the RECORD; stage 2 — `RowDeleted` ⇒ durable-PROTECTION verification for every surviving destination (an `Unresolved` incident row or a covering destruction operation exists and reads back) + completion); `Completed` ⇒ status**; refuses on terminal states (`Destroyed` → status; `Rejected` → new operation required); **a resumed `Pending`-phase removal whose live row's `binding_generation` ≠ the record's NEVER deletes — but a generation bump is NOT a cure (P1-5): the fence keeps the NEW generation from being deleted; the OLD generation's protection is retired ONLY by (i) validated recovery of the old cause (the §3d predicate) or (ii) a durable identity-bound transfer of that cause's protection (**OBSERVED** `execute/replication_seed/catalogue.rs:213-226` — the rebind preserves the quarantined row; only a post-reseed `Resume` may lift the quarantine); if neither is proved the record stays protected and INCOMPLETE (`Pending`/`RowDeleted`) until (i)/(ii) is proved — the operator investigates**; the delete predicate is `(name, binding_generation == record.binding_generation)`**; authorization required. **Claim enumeration: every claim path INCLUDING the INITIAL executor spawn — initial spawn, same-id resubmission, `destruction_retry`, periodic pass (`Prepared` older than 5 min), boot — performs ONE CAS `(record_version, executor_epoch): (v, e) → (v+1, e+1)`; the winner runs the operation for that epoch, losers get the current status immediately (never block for the run; the initial-spawn loser returns the current status and does NOT spawn); every claim path re-runs FULL PREFLIGHT against the frozen `target_digest` before Quiesce. The claim CAS is CONDITIONAL on the claimer's observed `(v, e)`; the executor spawn is IMMEDIATELY ADJACENT to the successful CAS (no await between); and the executor RE-CHECKS `executor_epoch` currency before EACH destructive durable step (Quiesce/Detach/Destroy/Catalogue/Complete entry), aborting to status if superseded — the operation token is the exclusion mechanism (one executor per operation id); the epoch CAS detects and supersedes stale work (131 §3b).**
- **Destruction-authority surface (NEW PRODUCTION CODE, deliverable of 8b-3b; `pub(crate)` per A14, NOT dispatchable from wire or admin):** `pub(crate) struct DestructionAuthority { operation_id: String(≤64), targets: Vec<(String, String)>, /* + opaque minted token */ }` minted by the executor per operation id + frozen target set; `pub(crate) fn remove_repo_locked_destructive(db, repo, &DestructionAuthority, &ReplicationControlGuard)` (db_management.rs, beside the merged `remove_repo_locked` :561) skips `ensure_destinations_unbound` (validate.rs:143) EXACTLY for the token's targets — the destruction path is the only caller that may remove a repo referenced by a durable binding; every other caller stays refused. The executor takes control for the detach section (131 §4a step 3). **A14: destructive dispatch becomes wire/admin reachable only in 8b-3c, together with all publisher wiring.**
- `destruction_preview(targets, cascade)` — returns the frozen target list (sorted by (db, repo)), its SHA-256 digest, a single-use challenge (≤ 60 s) and `expires_at_ns`; the client signs the digest + challenge on the subsequent `DESTROY QUARANTINED DATA` statement. A pure read + challenge mint; no durable lifecycle state.
- `destruction_list(limit: u32, pagination_token: Option<String>) -> { items: Vec<{ operation_id, state, targets }>, next_token: Option<String> }` — bounded (≤ `limit` items), ordered by `created_at`, paginated via the opaque `pagination_token`/`next_token` pair.
- Optional (8b-3d+): `destruction_archive(operation_id)` — owner-approved archival. **DECIDED (A2, DEC-3 item 7): `destruction_archive` NEVER releases protection.** Eligible only for Repo/Database `Destroyed` + fully acked, and SubscriptionRemoval `Completed`. Archival REPLACES the row with a permanent compact tombstone `{operation_id, kind, final_state, frozen storage_object_ids, sha256(full row), archived_at, archived_by, subscription, binding_generation, incident_refs}` (the removal identity + the incident ids of the removal record, A.2d — so the binding-keyed lookup through `destruction_bindings` (A.2e) remains answerable after compaction); operation ids are NEVER reusable. A final `Blocked` operation exits ONLY through `destruction_retry` → `Destroyed`. A `Blocked` SubscriptionRemoval at `RowDeleted` whose re-verification found data converts that data into an R2' target or an incident, NEVER a release; **there is NO remove-or-rename-the-squatter remedy (131 §4c): the found incarnation must be VERIFIED DESTROYED (R2' target conversion) or durably handed off as an identity-bound INCIDENT before `destruction_retry`/completion — renaming it away proves neither and never allows completion or reservation release.** The tombstone's "frozen storage_object_ids" are taken from the `SubscriptionRemoval` record's frozen `destinations[].storage_object_id` (A.2d) — never from name resolution at archival time. Backpressure: a quota on concurrent non-terminal operations; new destruction is refused when the quota is reached; nothing protected is ever evicted. No automatic expiry. This supersedes the earlier C8/F1b archival-eligible-with-release forms (now marked superseded in 131c/131d).

**Authorization:** same **Delete** authority as DROP **plus** replication-management authority. **Idempotence/safety:** status/list are pure reads; retry is idempotent for an already-running operation (returns current state); no admin call can bypass the audit barrier or delete a journal row with an unacked terminal event.
