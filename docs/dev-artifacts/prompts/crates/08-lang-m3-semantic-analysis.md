# PROC-2 M3: shamir-lang name resolution and semantic analysis (MVP stage)

Milestone 3 of `docs/dev-artifacts/design/shamir-lang-design.md`. Read fully first: section 1 (grammar, reserved names, precedence), section 2 (type system, typed boundaries, arithmetic, definite initialization, returns, scope, mutation) and section 3 (entry points, effects, the validator contract and its builtin constructors) are the binding specification; section 4 only for the names it reserves; section 6 (crate tree: `sem/`), section 7 (bounds), section 8 (diagnostic codes), section 9 (testing plan) and the worked examples at the end. Where this brief and the design differ in detail the design wins and you say so in your final message. The crate `crates/wasm/shamir-lang` already has milestone 1 (`src/back/`: guest runtime emitter), milestone 2 (`src/api/`: `Span`, `Diagnostic`, `CompileLimits`, `Stage`, `CompileOptions`; `src/front/`: lexer, flat AST arena, parser, `parse(source, &CompileLimits) -> Result<Module, Diagnostic>`). This milestone adds `src/sem/`: it takes the parsed module and either returns a fully typed, resolved module or diagnostics, so that invalid source can never reach lowering (milestone 4). No IR, no emission, no wasm.

## Deliverables

1. `src/sem/` (design tree: `resolve.rs`, `types.rs`, `effects.rs`, `flow.rs`, `tests/`; split along real seams where a file approaches 1000 lines: scopes, builtin catalog, expression checking, statement checking, call graph; one primary export per file, `mod.rs` re-exports only, tests in `sem/tests/` with `mod.rs` manifest registered by the owner). Entry point `check(module: &front::Module, limits: &CompileLimits, stage: Stage) -> Result<TypedModule, Vec<Diagnostic>>`, `pub` and `#[doc(hidden)]` (nothing in the production API consumes it before milestone 4; do NOT add `#[allow]` for dead code, reachability through the hidden public entry is the mechanism, as milestone 2 did for `front`).
2. The typed representation consumed by milestone 4 (all in flat arenas, no `Box` trees, no recursion in `Drop`, deterministic ordering, no hash-map iteration order leaking into any output):
   - an interned type table: `TypeId` newtype, structural identity by interning (records canonicalised by field name in UTF-8 byte order so equality is O(1) id equality; `T?` as `Optional(TypeId)`; lists `List(TypeId)`; primitives; opaque `Validation`/`Batch`/`Request`/`Response`);
   - the type of every expression (a table parallel to the AST expression arena), the resolved target of every identifier (local slot id, parameter, function id or builtin id) and of every call, the effective type chosen for every literal (including the i32/i64 literal rule), and for every function: its locals (slot, name, type, mutability), its inferred effect set, its entry kind, and a topological order of the call graph (callees before callers) usable by the emitter;
   - builtin identity as an enum or table (not strings), so later milestones do not re-resolve names.
3. Name resolution (`N001` unresolved name, `N002` duplicate binding): lexical scopes with shadowing in nested blocks, same-scope duplicates of parameters, locals and record fields rejected; a declaration's initializer is resolved BEFORE the new binding becomes visible (`let x = x;` sees the outer `x` or is `N001`); function names are module-global and may be used before their declaration; builtin names are reserved in the global namespace (a user function, parameter or local named like a builtin, or a parameter named `args`, is `N002`); every name the design reserves for stage 2 (`db_get`, `db_insert`, `db_query`, `batch`, `batch_id`, `batch_read`, `batch_insert`, `request`, `db_execute`, `response_rows`, `response_inserted`) is reserved too, but not callable in this milestone (see effects).
4. The MVP builtin catalog with exact signatures, as the design gives them: `len(string|bytes|list) -> i32`, `is_null(T?) -> bool` (no refinement), `unwrap(T?) -> T`, the named casts `to_i64(i32)`, `to_f64_i32(i32)`, `to_f64_i64(i64)`, `to_i32(i64)`, `to_i32_f64(f64)`, `to_i64_f64(f64)`, and the validator constructors `accept()`, `reject(field, code)`, `reject_path(path: [string], code)`, `record_error(code)`, `with_error(v, field, code)`, `with_record_error(v, code)`, `stop(v)`. Polymorphic builtins (`len`, `is_null`, `unwrap`) are resolved by the checker from the actual argument types; there is no generic syntax. Arity and argument type errors are `T004`/`T001`.
5. Type checking, bidirectional (expected type flows into literals, record and list literals, conditionals, call arguments, returns, annotated `let`): `T001` type mismatch (expression, argument, return, initializer), `T002` conversion (no implicit conversion exists except injection `T -> T?` and `null -> T?`), `T003` operation (operators and operand types: numeric `+ - * / %` need identical numeric operand types, `%` integers only, `!` bool, conditions bool, unary minus numeric, equality only where the underlying types support it and `null` compares only against optional or null, ordering only for same-type numerics and strings, short-circuit `&&`/`||` bool, `?:` branches identical after injection), `T004` call (arity, target must be a function or builtin, calling another `@entry` is rejected), the integer literal rule (default `i64`, suffix selects, an expected type may select `i32` when representable, the exact negative minimum accepted in unary-minus context, out-of-range is `T001` or `T003` with a message naming the range), record literals (expected structural record type required, duplicate/unknown/missing fields rejected), empty list literals (expected list type required), field access (field must be statically present), list indexing (`i32` index), `T009` unsupported type position (`null?`, opaque types optional or as list element or record field, `Validation` anywhere but a validator result or an internal helper, see section 2 and 3). The record, list and optional rules of section 2 apply exactly (no width subtyping, lists invariant).
6. Entry boundary rules (`T009`): scalar and procedure params/results use wire-safe types only; a validator entry has exactly the two optional record parameters `record` and `old_record` and result `Validation`; exactly one entry per module is already guaranteed by the parser.
7. Flow (`T005`) and mutation (`T006`): every non-`null` function must return on every reachable path (join branches; `throw` terminates a path but is not a return; a return in one branch only does not complete the function); `return;` only in `-> null` functions; `break`/`continue` only inside loops and only the innermost loop; unreachable code is still type-checked; assignment only to a mutable `let` local (never a parameter, `const`, range variable, loop item, function, field or list slot); `throw` requires `string`; range `for` bounds identical `i32`/`i64`, range and item variables immutable, loop item scoped per iteration.
8. Effects and call graph (`T007` entry capability violation, `T008` recursion): effects inferred from reachable calls; the entry kind is a capability ceiling (scalar: pure builtins only; validator: pure builtins and the validator constructors; procedure under `Stage::Procedures`: accepted by the checker but every stage-2 builtin is still `T007` "not available" until milestone 7; a `procedure` entry under `Stage::Mvp` is `T007`); helpers carry inferred effects; direct and mutual recursion are `T008` (report the cycle once, deterministic order, with the call span primary and the related span at the first function of the cycle); call chain length bounded by `max_call_chain` (`B001`).
9. Bounds: `max_locals_per_function` and `max_call_chain` enforced before the work they bound (`B001`); the analysis walks the AST, whose depth is already capped by the parser (`max_ast_depth`), so recursion in the checker is bounded by that cap: add a depth counter anyway and fail with `B001` rather than overflow. Compiler fuel may be charged per node visited if the milestone-2 budget makes that trivial; if it does not, say so and do not invent a new mechanism.
10. Diagnostics: collect all errors found, deterministically ordered by primary span start then code, at most 64, each message at most 1024 bytes, no hash-map order, addresses or Debug formatting in text; continue after an error inside the same function only when it cannot cascade (for example after a bad initializer give the local its annotated type or an internal error type that suppresses follow-on errors for that local), and never report two diagnostics for the same span and code.
11. Tests (registered by the owner `tests/mod.rs`, files by topic: `resolve_tests.rs`, `type_tests.rs`, `effect_tests.rs`, `flow_tests.rs`; NOT run locally, CI runs them): every code `N001 N002 T001 T002 T003 T004 T005 T006 T007 T008 T009 B001` with at least one positive and one negative case per rule listed above, spans at the offending token and the rendered `CODE:line:column: message` string asserted for a representative subset; the two worked examples of the design (scalar, typed validator) check clean and produce the expected function, local and effect tables; the integer literal rule table; the equality, ordering and operator tables; each cast builtin; optional injection and `unwrap`/`is_null`; record literal rules; flow join cases (return in one branch, in both, after a loop, `throw` paths); shadowing and `let x = x`; determinism (same input, same typed tables and diagnostics); a hostile-input sweep that runs `parse` then `check` on every prefix and every single-byte deletion of the worked examples asserting no panic. Tests build input through `front::parse`, not by constructing AST nodes by hand, except where a rule is unreachable from source.

## Constraints

Behaviour is judged by CI later and you cannot run tests, so favour small functions, named constants, simple control flow, exhaustive `match` on the AST kinds (so a later added node kind is a compile error, not a silent fallthrough), and no clever indexing: every table access is by checked arena id or `get`, no `unwrap`/`expect`/`panic!`/slicing that can panic on any input, checked arithmetic on every `u32` id and counter. No recursion in `Drop` or in any traversal beyond the capped AST depth. No `unsafe`. No new production dependencies (none are needed). `shamir_lang` stays free of `std::process`, filesystem and network APIs. Do not edit existing milestone-1 or milestone-2 behaviour except for additive reachability or an accessor the checker needs; if a parser or AST change is unavoidable, make it minimal and list it in the final message.

Layout rules: at most 7 entries per folder, 1000 lines per file, one primary export per file, no local `use`, no inline test modules, no new `#[allow]`, no visibility widening of existing items. Update the `shamir-lang` paragraph in `CLAUDE.md` and `AGENTS.md` with one sentence only if the current text becomes false.
