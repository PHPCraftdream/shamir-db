# PROC-2 M2: shamir-lang lexer, flat AST and parser

Milestone 2 of `docs/dev-artifacts/design/shamir-lang-design.md` (read it fully first: section 1 "Surface syntax and complete grammar" is the binding specification of this milestone; section 6 for the crate tree and the `Span`/`Diagnostic` shapes, section 7 for bounds, section 8 for the stable diagnostic codes, section 9 for the testing plan, the worked examples at the end of the document as parser fixtures; where this brief and the design differ in detail the design wins and you say so in your final message). The crate already exists: `crates/wasm/shamir-lang` (milestone 1 landed the guest runtime emitter under `src/back/` and the feature-gated `testsupport`). This milestone adds the front end only: source text to tokens to a flat AST. No name resolution, no types, no flow analysis, no emission (milestones 3 and 4).

## Deliverables

1. `src/api/` (the design tree lists seven files; this milestone adds only what the front end needs): `span.rs` (`Span { start_byte: u32, end_byte: u32, start: Position, end: Position }`, `Position { line: u32, column: u32 }`; byte ranges half-open, 1-based line and Unicode-scalar column, CRLF is one newline, a lone CR or LF is one newline), `diagnostic.rs` (`Diagnostic { code: &'static str, message: String, primary: Span, related: Option<RelatedSpan> }`, `RelatedSpan { span: Span, message: String }`, deterministic rendering `CODE:line:column: message`, related location printed after the primary), and `options.rs` holding `Stage`, `CompileLimits` and `CompileOptions` as one closely coupled group. `CompileLimits` has exactly the design's named fields with the design's hard ceilings as `Default` (`max_source_bytes=1048576`, `max_tokens=200000`, `max_ast_nodes=200000`, `max_ast_depth=128`, `max_type_depth=128`, `max_functions=256`, `max_parameters=32`, `max_record_fields=128`, `max_single_literal_bytes=65536`, `max_total_literal_bytes=4194304`, the remaining fields of design section 6 as well, so later milestones do not change the struct) with a method that clamps every field to the hard ceiling and rejects a zero value outside tests as the design says. `mod.rs` re-exports only. `CompileError`, `CompiledModule` and `compile` are NOT part of this milestone (milestone 4).
2. `src/front/lexer/`: `token.rs` (token kinds, including every keyword, operator, delimiter, `@entry`, the typed literal forms), `scan.rs` (the scanner: longest valid token, UTF-8 aware, spans as byte ranges converted to `Position` through a line index, every lexical rule of section 1: integer forms with `i32`/`i64` suffix and no leading zeros, hex, floats with exponent and `f64` suffix and the NaN/infinity rejection, strings with the listed escapes and `\u{..}` of one to six hex digits encoding one scalar, byte literals `b"..."` with only the listed escapes and one-byte unescaped scalars, rejection of raw U+0000..U+001F and U+007F inside strings and byte literals, line and block comments (unterminated block comment is `L003`), whitespace, identifiers, the reserved keyword set). Diagnostics use the design table: `L001` invalid character, `L002` malformed literal or escape (overflow of an integer literal for its suffix or default type included), `L003` unterminated string, byte literal or comment, `B001` for exceeding `max_source_bytes`, `max_tokens`, `max_single_literal_bytes`, `max_total_literal_bytes` (each checked BEFORE the work it bounds, never allocate-then-check).
3. `src/front/ast/`: `node.rs` and whatever siblings are needed (one primary export per file; the design shows `node.rs`, split along real seams: expression, statement, type, function, module, ids): a FLAT arena AST (vectors of nodes addressed by `u32` newtype ids, no `Box` trees, no recursion in `Drop`), every node carries its byte span, node and depth counters feed `max_ast_nodes` and `max_ast_depth`. Types: primitive and opaque names including `Validation`, `Batch`, `Request`, `Response`, postfix `?`, list `[T]`, record `{ f: T }` types. Expressions per the grammar: conditional, `||`, `&&`, equality, comparison, additive, multiplicative, unary `! - +`, postfix call (target must be an identifier), field, index, primary (literals, list and record literals, parenthesised). Statements: `let`/`const` with optional type, assignment (lvalue is identifier, field or index; assignment is a statement, never an expression), `if`/`else if`/`else` (else takes only a block or an `if`), `while`, range `for`, list `for`, `return`, `break`, `continue`, `throw`, expression statement, block. Functions: `@entry <kind> name(params) -> type { }` and `fn name(params) -> type { }`; a module is a list of functions; trailing commas where the grammar allows them.
4. `src/front/parser/`: `parse.rs` (and siblings if it grows near 1000 lines: expressions, statements, types, declarations are natural seams): hand-written recursive descent with precedence climbing for the precedence table of section 1 (comparison and equality do not chain: `a < b < c` and `a == b == c` are `P003`; `a < b == c` is allowed by the table; unary operators right-associative; conditional right-associative). Recursion depth is bounded: increment a depth counter BEFORE each nested construct and reject with `B001` at `max_ast_depth` (the compiler later runs on a fixed-size worker stack, so unbounded recursion is a security defect); declarations and counts bounded by `max_functions`, `max_parameters`, `max_record_fields`, `max_type_depth`. Exactly one `@entry` per module (`P002` for none or a second one, with the second's span primary and the first as related). An unmarked `scalar`/`validator`/`procedure` declaration is rejected (the design text says `S001`, its own table has no `S` category: use `P002` and report the inconsistency in your final message). Errors: `P001` expected token (missing delimiter or type, the message names what was expected and what was found), `P002` declaration or entry errors, `P003` malformed statement or expression. The parser stops at the first error (deterministic single diagnostic) and the lexer likewise; collect nothing speculatively.
5. Reachability without `#[allow]`: nothing in the production API consumes the front end yet, so clippy `dead_code` would fire on the new items. Do not add `#[allow]`. Make the entry points `pub` and the modules reachable from `lib.rs` with `#[doc(hidden)]` and a one-line doc stating they are unstable until the compile API of milestone 4. Do not widen any visibility of existing items.
6. Tests (registered by the owning parent `mod.rs`, in `tests/` folders per the design tree, files split by topic, never inline `#[cfg(test)]` modules; they are NOT run locally, CI runs them): lexer tests per token class and every lexical rule above with exact and over-limit boundaries; span and position tests (CRLF, lone CR, multi-byte scalars, positions of tokens after comments); parser acceptance tests for the grammar, the three worked examples of the design (scalar, typed validator, and one multi-function helper module you write), each precedence and associativity row of the table, trailing commas, empty parameter list, nested records and lists, list `for` versus range `for`; rejection tests for each of `L001`, `L002`, `L003`, `P001`, `P002`, `P003`, `B001` (the spans point at the offending token; assert the rendered `CODE:line:column: message` string for a few); determinism (same input same AST and same diagnostics); a panic-freedom sweep that feeds every prefix and every single-byte deletion of the worked-example sources to lexer and parser and asserts `Ok` or a `Diagnostic`, never a panic; a depth test just under and over `max_ast_depth`. JSON-like literals in tests multi-line.

## Constraints

Behaviour is judged by CI later and you cannot run tests, so favour small functions, named constants, simple control flow, and no clever indexing: every slice access must be provably in range (use `get`, checked arithmetic on `u32` spans, saturating or erroring conversions; a source over 1 MiB is rejected before any `u32` conversion can overflow). No `unwrap`/`expect`/`panic!`/indexing that can panic on any input. No recursion in AST drop or in any traversal you add. No `unsafe`. No new production dependencies. `shamir_lang` stays free of `std::process`, filesystem and network APIs.

Layout rules: at most 7 entries per folder, 1000 lines per file, one primary export per file, no local `use`, no inline test modules, no new `#[allow]`, no visibility widening. `front/` mod.rs re-exports only. Update the `shamir-lang` paragraph in `CLAUDE.md` and `AGENTS.md` with one sentence about milestone 2 only if the current text becomes false.
