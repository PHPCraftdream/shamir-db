# R4. Наблюдаемость

Статус: предложение. Приоритет: R4a и R4b — важно для релиза, R4c — после
релиза либо за флагом сборки.

## 1. Что есть сейчас

Проверено по коду и `guide-docs/guide/07-operations.md`.

- Отдельный HTTP-сервер наблюдаемости: `/healthz`, `/readyz`, `/metrics`
  (формат Prometheus), `/info`.
- Метрики процесса, аутентификации, транзакций (начато, зафиксировано,
  конфликты SSI, истёкшие), сборки мусора версий, видимости и подтверждений,
  снимок шлюза репозитория, часть метрик репликации и долговечности.
- Журнал медленных запросов, audit log, перезагрузка настроек журналирования
  без перезапуска.
- `explain` в query builder.
- Пример связки Prometheus и Grafana в руководстве.

Наблюдение по коду: метрики публикуются только из серверных крейтов
(`shamir-server-security`, `shamir-sync`, `shamir-server`). Движок, хранилище,
WAL, индексы и хост функций своих сигналов не отдают. Там, где данные движка
всё же видны, работает один и тот же приём: движок хранит состояние, а
серверный модуль экспорта его опрашивает
(`security/observability/visibility_export.rs`, `durability_export.rs`).

Административной операции «показать активные запросы» и «отменить чужой запрос»
в коде не найдено. Признак отмены сейчас используется только для остановки
сервера и его подсистем.

## 2. Принцип

Крейты движка не получают зависимости от библиотеки метрик. Движок ведёт
счётчики и гистограммы на атомарных переменных — это соответствует идеологии
кода (lock-free, без блокировок на горячем пути), — а публикует их серверный
модуль экспорта, как уже сделано для видимости и долговечности. Для гистограмм
нужен один общий примитив: гистограмма с фиксированными границами на атомарных
счётчиках.

Каждая метрика на горячем пути измеряется: стоимость добавленного учёта
проверяется существующими бенчмарками до и после.

## 3. R4a. Метрики движка

| Область | Сигналы |
|---|---|
| Запросы | гистограммы длительности по видам операций (чтение, запись, пакет, транзакция, вызов функции); счётчики ошибок по кодам; записей просмотрено и возвращено |
| Хранилище | размер на диске по репозиторию и таблице; число записей; объём версий, ожидающих сборки мусора |
| WAL | размер, число сегментов, скорость записи, длительность `fsync`, отставание усечения |
| Индексы | размер по индексу, длительность построения и перестроения, для векторных — состояние снимка |
| Интернер | число имён полей по репозиторию (рост без верхней границы — известный риск) |
| Нагрузка | активные соединения и сессии, очередь допуска, отказы по лимитам частоты и числа соединений |
| Функции | длительность вызова, расход fuel, попадания и промахи кэша компиляции, отказы проверки модуля, глубина вложенных вызовов |
| Репликация | отставание в версиях и во времени, состояние потока, число переподключений |
| Копии | время последней успешной копии, длительность, объём (R2d) |

К метрикам прилагаются: обновлённая панель Grafana и набор правил оповещения
(диск, отставание реплики, давно не было копии, рост доли ошибок, длительный
закреплённый снимок).

## 4. R4b. Операционные представления и отмена запроса

Зрелые СУБД дают оператору ответ на вопросы «что сейчас выполняется» и «что
выполняется чаще и дольше всего». Нужны три вещи.

**Активность.** Административная операция, возвращающая текущие сессии,
запросы и транзакции: актор, база, вид операции, время начала, длительность,
состояние (выполняется, ждёт блокировки, ждёт подтверждения). Доступ — право
управления сервером; значения из запросов в выдачу не попадают.

**Отмена.** Административная операция отмены запроса или транзакции по
идентификатору. Отмена кооперативная: запрос проверяет признак отмены в точках,
где это безопасно, и завершается обычной ошибкой. Отдельно проверяется, что
отмена освобождает закреплённый снимок и блокировки.

**Статистика по формам запросов.** Накопленные счётчики и суммарное время по
«форме» запроса — операциям builder'а без литералов. Память ограничена:
фиксированное число форм с вытеснением. Сброс — административной операцией.

## 5. R4c. Трассировка

- Экспорт трасс по протоколу OTLP: запрос как корневой интервал, внутри —
  планирование, чтение, запись, фиксация, вызов функции.
- Приём контекста трассировки от клиента, чтобы запрос СУБД был виден внутри
  трассы приложения.
- Трассировка тянет за собой заметные зависимости, а цель проекта — один
  бинарник меньше 50 МБ. Поэтому она включается флагом сборки и **требует
  решения владельца о зависимостях**. До этого решения остаётся журнал
  медленных запросов, дополненный идентификатором запроса, общим для журнала,
  audit и ответа клиенту.

## 6. Этапы и приёмка

| Этап | Содержание | Приёмка |
|---|---|---|
| R4a-1 | Примитив атомарной гистограммы; метрики запросов и нагрузки | метрики видны в `/metrics`; бенчмарки горячего пути без значимого замедления |
| R4a-2 | Метрики хранилища, WAL, индексов, интернера, функций, репликации | значения сверяются с фактическим состоянием в тестах |
| R4a-3 | Панель и правила оповещения, раздел руководства | руководство описывает каждую метрику и её нормальный диапазон |
| R4b-1 | Представление активности | длительный запрос виден с верной длительностью; значения запросов не раскрываются; доступ ограничен |
| R4b-2 | Отмена | отменённый запрос завершается ошибкой, снимок и блокировки освобождены, запись не оставляет частичного результата |
| R4b-3 | Статистика по формам | объём памяти ограничен; одинаковые формы с разными литералами сводятся в одну |
| R4c | Трассировка за флагом сборки | бинарник без флага не меняется в размере |

## 7. Открытые вопросы для дизайна

- Число меток у метрик по таблицам и индексам: при тысячах таблиц нужен предел
  кардинальности (например, только N крупнейших и остаток).
- В каких точках пакетного исполнения безопасно проверять отмену.
- Нужен ли доступ к представлениям активности обычным пользователям в пределах
  их собственных сессий.
