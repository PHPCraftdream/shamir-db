# План первого релиза

Дата: 2026-11-11. Статус: **предложение**. Ни одно направление отсюда ещё не
спроектировано в деталях и не реализовано; перед реализацией каждое проходит
обычный цикл проекта: документ дизайна, независимое ревью, бриф, реализация,
полный прогон CI, посадка.

Этот документ отвечает на вопрос «чего не хватает СУБД до первого релиза, если
смотреть на неё глазами человека, привыкшего к зрелым СУБД» и раскладывает
ответ на направления. Детализация лежит рядом:

## 1. Исходная точка

Функциональное ядро для первого релиза уже широкое: транзакции MVCC/SSI, WAL и
настраиваемая долговечность, индексы (hash, sorted, векторные, полнотекстовые),
TTL, подписки и `changes_since`, экспериментальная репликация, хранимые процедуры
(WASM и язык `shamir`), ACL и SCRAM, TLS, audit log, ограничение частоты и числа
соединений, журнал медленных запросов, `/healthz`, `/readyz`, `/metrics`,
`/info`, `explain` в query builder.

Не хватает в первую очередь не функций, а **эксплуатационной части**: того, что
позволяет доверить СУБД данные надолго и пережить с ними обновление версии.

## 2. Принципы

1. **Релиз — это обещание совместимости.** Начиная с первого релиза данные
   пользователя обязаны переживать обновление бинарника. Поэтому версионирование
   и миграции (R1) идут первыми и считаются критичными: без них любое следующее
   изменение формата становится несовместимым.
2. **Сначала эксплуатация, потом новые возможности.** Резервная копия, перенос
   данных и наблюдаемость важнее очередной функции языка запросов.
3. **Шифрование данных на диске — не задача СУБД** (решение владельца,
   2026-11-11). Доступ к каталогу данных ограничивают политики ОС и файловой
   системы; действующая модель описана в
   [`guide-docs/security/data-protection.md`](../../guide-docs/security/data-protection.md).
   СУБД защищает то, что покидает машину: **резервные копии шифруются
   автоматически** (R2).
4. **Версии не поднимаются и зависимости не добавляются без отдельного решения.**
   Там, где направление требует новой зависимости, это явно помечено как решение
   владельца.
5. **Запросы строятся только через query builder** — это относится и к
   миграциям схемы приложения, и к инструментам экспорта и импорта.

## 4. Порядок работ

Волны подобраны так, чтобы внутри волны работы не пересекались по файлам и шли
параллельно.

0. **Волна 0 (по итогам ревью спринта, уже в работе).** R6 (атомарный батч
   процедур) и R7 (долговечность записей каталога).
1. **Волна 1.** R1a (штамп и правила запуска) и R4a (метрики движка).
2. **Волна 2.** R1b (каркас миграций и тест совместимости) и R2a (онлайн-копия).
3. **Волна 3.** R1c (журнал миграций приложения), R2c и R2d (шифрование и
   расписание копий), R3 (экспорт и импорт).
4. **Волна 4.** R4b (представления и отмена запроса), R5 (оболочка).

R1a идёт первым, потому что форматы копии (R2) и экспорта (R3) записывают в свои
манифесты эпоху формата и версию схемы приложения.

## 5. Ворота первого релиза

Релиз возможен, когда одновременно выполняется всё перечисленное:

- каталог данных несёт штамп формата; бинарник отказывается открывать данные
  более новой эпохи и не изменяет данные более старой эпохи без явной команды
  оператора;
- существует хотя бы один проверенный в CI путь «данные предыдущей эпохи →
  текущая» (первый релиз фиксирует эпоху, с которой начинается обещание);
- резервная копия снимается без остановки сервера, восстанавливается на чистую
  машину, и это проверяется тестом под нагрузкой записи;
- при заданном ключе каждая копия зашифрована, восстановление с неверным ключом
  отклоняется до записи первого файла;
- логический экспорт одной версии загружается следующей;
- оператор видит задержки запросов, размер данных и WAL, состояние копий и
  репликации в `/metrics` и может найти и отменить зависший запрос;
- документация эксплуатации (`guide-docs/guide/07-operations.md`) описывает
  обновление версии, копирование, восстановление и ротацию ключей по шагам.

## 6. Решения по умолчанию (владелец может изменить)

Это продуктовые развилки. Чтобы план не зависал, для каждой записан вариант по
умолчанию; он действует, пока владелец не решит иначе.

1. **С какой эпохи начинается обещание совместимости.** По умолчанию: с формата
   на момент первого релиза. Данные более ранних сборок переносятся только
   логическим экспортом и импортом (R3).
2. **Откуда берётся ключ шифрования копий.** По умолчанию: файл ключа на сервере
   как стартовый вариант; открытый ключ получателя (сервер умеет только
   шифровать) — следующий шаг, он требует новой зависимости. Подробности в
   файле 02.
3. **Нужен ли текстовый язык запросов в оболочке.** По умолчанию: нет, оболочка
   административная; интерактивные запросы к данным остаются за клиентскими
   библиотеками до отдельного решения. Подробности в файле 05.
4. **Откат версии.** По умолчанию: откат формата на месте не поддерживается,
   откат выполняется восстановлением копии, снятой перед обновлением.
