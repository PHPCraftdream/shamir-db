# R1. Версионирование и миграции

Статус: предложение. Приоритет: **блокер релиза, выполняется первым.**

## 1. Зачем

После первого релиза у пользователей появятся каталоги данных, которые нельзя
потерять при обновлении бинарника. Сейчас каждое изменение формата решается
на месте («отсутствующее поле читается как значение по умолчанию»), и это
работает, пока все данные принадлежат разработчикам. С релизом нужны три вещи:

1. СУБД всегда знает, в каком формате лежат данные перед ней.
2. Переход между форматами выполняет проверяемый код — модуль миграции, а не
   россыпь условий в читателях.
3. У приложения пользователя есть такой же механизм для его собственной схемы.

Версионируются две части:

- **системная часть** — всё, что принадлежит движку: формат WAL, раскладка
  хранилища, строки системного каталога (таблицы, функции, пользователи, группы,
  токены), мета индексов, снимки векторных индексов, интернер имён полей;
- **пользовательская часть** — схема приложения внутри базы данных: таблицы и их
  правила, индексы, функции и валидаторы, права.

Третья, отдельная ось — версия сетевого протокола (раздел 6).

| Пространство имён кэша компиляции функций | `crates/wasm/shamir-wasm-host/src/wasm/compile_cache/namespace.rs` | |

Совместимость «отсутствующее поле читается как значение по умолчанию» уже
применяется для полей `kind`, `artifact_id` и `call_signature` строки функции.

Чего нет:

- единого штампа формата у каталога данных;
- правила, что делает бинарник с данными другой версии (сейчас он просто
  пытается их открыть);
- каркаса миграций и журнала их выполнения;
- журнала миграций схемы приложения;
- теста «данные предыдущего релиза открываются текущим бинарником».

Два обстоятельства, которые влияют на дизайн:

- **Транзакционного DDL нет** (`guide-docs/KNOWN_LIMITATIONS.md`, раздел 1).
  Миграция схемы приложения не может быть одной атомарной транзакцией.
- **Слово «migration» уже занято** операцией переноса репозитория между
  движками (`MigrateRepo` / `StartMigration`). В этом плане используются термины
  «миграция формата» (системная часть) и «миграция схемы приложения»
  (пользовательская часть); имена команд и типов должны отличаться от
  существующей операции.

## 3. Системная часть

### 3.1 Штамп формата

В корне каталога данных появляется файл штампа. Поля:

| Поле | Смысл |
|---|---|
| `format_epoch` | целое, монотонно растёт; единственное число, по которому бинарник решает, может ли он работать с данными |
| `components` | версии отдельных компонентов (WAL, хранилище, системный каталог, мета индексов, снимки векторных индексов, интернер, audit) — для диагностики и для выбора шагов миграции |
| `created_by` | версия бинарника, создавшего каталог |
| `last_opened_by` | версия бинарника, последним открывшего каталог на запись |
| `last_migration` | идентификатор последней выполненной миграции и время |
| контрольная сумма | защита от частичной записи |

Штамп пишется атомарно: временный файл, `fsync`, переименование, `fsync`
каталога. Штамп — последнее действие миграции.

### 3.2 Правила запуска

| Состояние | Действие |
|---|---|
| Штампа нет, каталог пуст | создаётся каталог текущей эпохи |
| Штампа нет, данные есть | данные «до штампа» считаются базовой эпохой; штамп записывается |
| Эпоха равна эпохе бинарника | обычный запуск |
| Эпоха больше, чем знает бинарник | **отказ запуска** с понятным сообщением; данные не изменяются |
| Эпоха меньше | **отказ запуска** с указанием команды миграции; миграция выполняется только по явной команде оператора |

Автоматическая миграция при обычном запуске не выполняется: обновление версии
должно быть осознанным действием с резервной копией.

### 3.3 Когда поднимается эпоха

Эпоха поднимается при любом изменении, после которого **предыдущий бинарник мог
бы прочитать данные неверно или испортить их при записи**. Это шире, чем
«изменился формат файла». Пример из текущего кода: строка функции получила поле
`call_signature`; предыдущий бинарник не знает о нём и при замене функции
запишет строку без подписи. Чтение при этом «совместимо», а запись теряет
данные. Такое изменение обязано поднять эпоху, даже если модуль миграции пуст
(миграция «только штамп»).

Изменения, которые эпоху не поднимают, перечисляются в журнале изменений
формата с обоснованием, почему предыдущий бинарник безопасен. Журнал ведётся в
репозитории рядом с модулями миграций.

### 3.4 Модули миграций

- Каждый модуль переводит данные ровно на один шаг: из эпохи `N` в `N+1`.
  Переход через несколько эпох — цепочка шагов; пропуски запрещены.
- Модуль описывает: имя, что меняется, оценку объёма работы, шаги. Шаги
  идемпотентны.
- Перед первым шагом в каталоге данных создаётся журнал выполнения: «шаг начат»,
  «шаг завершён». После сбоя повторный запуск команды продолжает с
  незавершённого шага.
- Миграция выполняется при остановленном обслуживании клиентов (первая версия —
  только такой режим). Онлайн-миграции больших таблиц — отдельная будущая работа.
- Перед миграцией команда требует свежую резервную копию: до R2 — существующую
  `backup` с остановкой, после — онлайн-копию.
- После последнего шага выполняется проверка целостности, затем пишется штамп.
- Режим проверки без изменений показывает план: какие шаги будут выполнены и
  что они затронут.

Расположение кода — решение дизайна. Ограничение проекта «не больше 7 записей в
папке» означает, что модули нужно группировать, а не складывать в одну папку.

### 3.5 Откат

Откат формата на месте не поддерживается. Откат версии — это восстановление
копии, снятой перед миграцией. Это записывается в руководство эксплуатации как
обязательный шаг обновления.

### 3.6 Репликация

- Узлы сообщают эпоху формата при установлении репликации.
- Первая версия: узлы разных эпох не реплицируются между собой; обновление
  выполняется с остановкой ведомых. Обновление без простоя («сначала ведомые,
  потом лидер») — после релиза, вместе с остальной работой по доступности.
- Seed-артефакт уже несёт `format_version`; к нему добавляется эпоха формата
  источника.

### 3.7 Тест совместимости

Ворота релиза. Для каждой выпущенной эпохи в репозитории хранится небольшой
эталонный каталог данных, созданный бинарником того релиза по фиксированному
сценарию: таблицы со схемами, индексы каждого вида, функции каждого вида,
пользователи, группы, права, токены, незавершённый WAL. CI открывает эталон
текущим бинарником, выполняет цепочку миграций и сверяет содержимое с
ожидаемым. Эталоны создаются скриптом в момент выпуска и лежат среди тестовых
данных.

### 3.8 Запасной путь

Если миграция на месте невозможна или слишком дорога, остаётся логический
экспорт предыдущим бинарником и импорт новым (R3). Формат экспорта поэтому
версионируется отдельно и меняется редко.

## 4. Пользовательская часть

### 4.1 Модель

У каждой базы данных есть **журнал миграций схемы приложения** — системная
таблица в самой базе. Запись журнала:

| Поле | Смысл |
|---|---|
| идентификатор | упорядоченный, задаёт порядок применения |
| имя | для человека |
| контрольная сумма | от содержимого миграции; изменение уже применённой миграции обнаруживается |
| состояние | выполняется, применена, сбой |
| кто и когда | актор и время |
| эпоха формата | эпоха системной части на момент применения |
| длительность | для диагностики |

Версия схемы приложения базы — идентификатор последней применённой миграции.

### 4.2 Применение миграции

Операция принимает идентификатор, имя, контрольную сумму и набор операций
(DDL и DML), построенный query builder'ом. Правила:

- предыдущие миграции применены, их контрольные суммы не изменились;
- одновременно в базе выполняется не больше одной миграции (тот же приём, что
  замки DDL функций по имени);
- так как транзакционного DDL нет, перед началом в журнал пишется состояние
  «выполняется», а операции миграции обязаны быть идемпотентными; повтор после
  сбоя продолжает выполнение, а не начинает заново;
- право на применение — управление базой данных.

Существующий `schema_version` таблицы остаётся: он защищает отдельное изменение
схемы от гонки. Журнал отвечает на другой вопрос — в каком состоянии схема
приложения целиком.

### 4.3 Инструмент

- Каталог миграций живёт в проекте приложения пользователя.
- Команды «применить», «состояние», «проверить» — в Rust-клиенте и
  TypeScript-клиенте, затем в административной оболочке (R5).
- Миграции пишутся через query builder; сырой JSON не используется.

### 4.4 Функции и валидаторы

Замена процедуры может изменить её подпись (`call_signature`); вызывающие
процедуры тогда откажут в рантайме на проверке подписи. Инструмент миграции
должен уметь до применения проверить зависимые процедуры операцией
`check_function`. Это улучшение второй очереди.

### 4.5 Только вперёд

Обратные миграции в первой версии не поддерживаются. Рекомендуемый путь —
миграции только вперёд и резервная копия перед применением.

## 5. Связь частей

- Запись журнала миграций приложения хранит эпоху формата, при которой она
  применялась.
- Логический экспорт (R3) и резервная копия (R2) записывают в манифест и эпоху
  формата, и версию схемы приложения каждой базы.
- Системные таблицы внутри пользовательской базы (включая сам журнал)
  принадлежат системной части и мигрируют модулями формата.

## 6. Протокол

Версия сетевого протокола — отдельная ось. К релизу фиксируется правило:
клиент и сервер сообщают версию при рукопожатии, сервер поддерживает текущую и
предыдущую версии, матрица совместимости ведётся в
`guide-docs/guide/client-matrix.md`.

## 7. Этапы и приёмка

| Этап | Содержание | Приёмка |
|---|---|---|
| R1a | Штамп, правила запуска, журнал изменений формата, раздел в руководстве эксплуатации | бинарник отказывается открывать данные более новой эпохи; данные более старой не изменяются без команды; каталог без штампа получает штамп; тесты на частично записанный штамп |
| R1b | Каркас модулей миграций, журнал выполнения, режим проверки, первая (пустая) миграция, тест совместимости с эталоном | сбой посреди миграции → повтор завершает её; эталон предыдущей эпохи открывается и сверяется в CI |
| R1c | Журнал миграций приложения, операция применения, команды в клиентах | повтор после сбоя; изменённая применённая миграция отклоняется; две одновременные миграции не выполняются |
| R1d | Эпоха формата в рукопожатии репликации и в seed-артефакте | узлы разных эпох не реплицируются, сообщение понятно |

## 8. Открытые вопросы для дизайна

- Точная граница базовой эпохи: какие именно сборки до релиза считаются
  совместимыми с ней (по умолчанию — только формат на момент первого релиза).
- Где физически лежит штамп для конфигураций с несколькими каталогами
  репозиториев и для репозиториев в памяти.
- Размер и состав эталонных каталогов, чтобы тест совместимости оставался
  быстрым.
- Время миграции на больших данных и необходимость индикации прогресса.
