# R3. Логический экспорт и импорт

Статус: предложение. Приоритет: блокер релиза.

## 1. Зачем

Резервная копия отвечает на вопрос «как вернуть этот сервер». Логический
экспорт отвечает на другие:

- перенести одну базу или таблицу на другой сервер;
- перейти между версиями, когда миграция формата на месте невозможна (запасной
  путь из R1);
- загрузить данные из другой СУБД или выгрузить их для анализа;
- получить читаемый снимок схемы для ревью и хранения в системе контроля версий.

Сейчас такого инструмента нет. Ближайшее — seed-артефакт репозитория
(`guide-docs/architecture/SEED_FORMAT.md`), но он предназначен для запуска
ведомого узла и намеренно не содержит индексов, системных репозиториев и прав.

## 2. Состав экспорта

| Раздел | Содержимое |
|---|---|
| Манифест | версия формата экспорта, эпоха формата источника, версия схемы приложения (R1), точка снимка, перечень разделов с хэшами |
| Схема | репозитории, таблицы, правила схемы, определения индексов всех видов |
| Функции | процедуры и валидаторы: исходный текст, вид, настройки безопасности; готовые артефакты — по флагу |
| Права | владельцы, группы, режимы ресурсов; пользователи и группы — по флагу |
| Данные | записи таблиц потоком |

Формат данных — поток MessagePack (родной для СУБД, без потери типов) и, как
альтернатива для обмена с внешними системами, построчный JSON с явной
оговоркой о типах, которые JSON не различает (большие целые, байты, десятичные).

## 3. Свойства

- **Согласованность.** Экспорт читает данные под закреплённым снимком, как
  онлайн-копия (R2a), и использует тот же механизм ограничения времени снимка.
- **Потоковость.** Ни экспорт, ни импорт не держат таблицу в памяти целиком;
  для импорта действуют те же границы размеров, что у установщика
  seed-артефакта.
- **Избирательность.** База, репозиторий, таблица; только схема или только
  данные.
- **Импорт под другим именем** и в существующую базу; поведение при конфликте
  (отказ, пропуск, замена) задаётся явно.
- **Права.** Экспорт требует права чтения на всё выгружаемое и права управления
  для разделов прав и функций. Экспорт не обходит ACL.
- **Через query builder.** Импорт выполняет операции, построенные builder'ом, а
  не собранные вручную сообщения.
- **Индексы** при импорте создаются после загрузки данных.
- **Секреты и токены не экспортируются.**

## 4. Связь с другими направлениями

- Кодек потока и проверки целостности общие с seed-артефактом и онлайн-копией:
  три формата не должны разойтись в трёх реализациях.
- Формат экспорта версионируется отдельно от эпохи формата каталога данных и
  меняется редко: это запасной путь между эпохами.
- Экспорт можно шифровать тем же конвертом, что и копии (R2c).
- Команды экспорта и импорта доступны из сервера и из административной
  оболочки (R5).

## 5. Этапы и приёмка

| Этап | Содержание | Приёмка |
|---|---|---|
| R3a | Экспорт и импорт данных и схемы одной базы в MessagePack | после импорта содержимое и схема совпадают с источником на точке снимка; экспорт под нагрузкой записи согласован |
| R3b | Функции, права, избирательность, импорт под другим именем | процедура после импорта вызывается и проходит проверку подписи; права совпадают |
| R3c | Построчный JSON, шифрование | типы, не представимые в JSON, либо сохраняются по описанному правилу, либо экспорт отказывает |
| R3d | Тест «экспорт предыдущей эпохи загружается текущей» | выполняется в CI вместе с тестом совместимости R1 |

## 6. Открытые вопросы для дизайна

- Экспортировать ли историю версий и удалённые записи (по умолчанию — нет,
  только состояние на точке снимка).
- Сохраняются ли идентификаторы интернера имён полей или имена передаются
  текстом (по умолчанию — текстом: формат не должен зависеть от внутренних
  идентификаторов).
- Как экспортируются таблицы с TTL: срок жизни переносится абсолютным временем
  или остатком.
