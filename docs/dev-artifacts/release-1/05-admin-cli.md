# R5. Административная оболочка

Статус: предложение. Приоритет: важно для релиза, выполняется после R1–R4,
потому что состоит из их команд.

## 1. Зачем

Первое знакомство со зрелой СУБД обычно происходит через её оболочку: ею
проверяют, что сервер жив, смотрят, что внутри, и чинят то, что сломалось. Сейчас
у СУБД есть команды самого сервера (запуск, установка службы, копия с
остановкой) и клиентские библиотеки, но нет инструмента, которым оператор
подключается к работающему серверу. Отдельного крейта оболочки в workspace нет.

## 2. Что должна уметь

| Группа | Команды |
|---|---|
| Соединение | подключение по тем же транспортам и способам входа, что у клиентов; профили соединений; ввод секрета без эха, не через аргументы командной строки |
| Состояние | версия сервера, эпоха формата, время работы, роль в репликации, отставание |
| Каталог | список баз, репозиториев, таблиц, индексов, функций; описание таблицы и её схемы |
| Права | пользователи, группы, права ресурса, изменение владельца и режима |
| Активность | текущие сессии и запросы, отмена запроса (R4b) |
| Копии | снять, проверить, восстановить, состояние расписания, ротация ключа (R2) |
| Версии | штамп формата, план и запуск миграции формата, состояние миграций схемы приложения (R1) |
| Экспорт и импорт | выгрузка и загрузка базы или таблицы (R3) |
| Диагностика | проверка целостности, сведения о WAL и долговечности |

Режимы: интерактивный и пакетный (одна команда, машинно-читаемый вывод, код
возврата) — для скриптов и автоматизации.

## 3. Запросы к данным

У СУБД нет текстового языка запросов: запросы строятся query builder'ом. Поэтому
оболочка первой версии — **административная**: она не выполняет произвольные
запросы к данным. Для просмотра данных достаточно узких команд:

- показать запись по ключу;
- показать первые N записей таблицы;
- посчитать записи.

Интерактивные запросы произвольной формы остаются за клиентскими библиотеками.
Если понадобится большее, это отдельное решение владельца: текстовая форма
запросов означала бы второй способ их строить и противоречила бы правилу
«только builder». Исследование по операторной форме записи лежит в
`dev-artifacts/roadmap/oql/` и может стать основой такого решения.

## 4. Требования

- Оболочка — клиент: она использует клиентскую библиотеку и обычный протокол, а
  не читает каталог данных напрямую. Исключение — команды, которые по своей
  природе работают при остановленном сервере (миграция формата, восстановление);
  они остаются командами сервера, а оболочка лишь объясняет, как их запустить.
- Любая команда проверяется правами на сервере; оболочка не даёт ничего сверх
  прав вошедшего пользователя.
- Разрушительные команды (удаление, восстановление, отмена чужого запроса)
  требуют подтверждения в интерактивном режиме и явного флага в пакетном.
- Секреты не печатаются и не попадают в историю команд.
- Оболочка поставляется вместе с сервером и не увеличивает число внешних
  зависимостей развёртывания.

## 5. Этапы и приёмка

| Этап | Содержание | Приёмка |
|---|---|---|
| R5a | Соединение, состояние, каталог, пакетный режим | сценарий «подключиться и описать таблицу» проходит по каждому транспорту |
| R5b | Права, активность, отмена | команды отклоняются без нужных прав; отмена работает |
| R5c | Копии, версии, экспорт и импорт | каждый раздел руководства эксплуатации выполним командами оболочки |

## 6. Открытые вопросы для дизайна

- Отдельный исполняемый файл или подкоманда сервера. Отдельный файл удобнее
  ставить на рабочее место администратора; подкоманда сохраняет принцип одного
  бинарника.
- Формат машинно-читаемого вывода.
- Нужна ли история команд и где она хранится.
