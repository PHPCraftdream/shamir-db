# Wave R0 — correctness freeze (блокирует тег)

> Правило волны: **никаких новых возможностей DDL/OQL до закрытия R0.** Оба отчёта
> настаивают на этом независимо; расширение поверхности поверх дырявого lifecycle
> умножает площадь дефектов.

## R0-A. Один источник монотонности для реестра (#1006 + #1012)

### Зачем (что ломается без этого)

`IndexRegistry` — это гейт, который решает, нужно ли транзакции пересчитывать
план индексных операций на коммите. Гейт читается как `reg.generation() == stage_gen`
(**проверено**, `crates/shamir-engine/src/tx/pre_commit.rs:825`). Если поколение
не изменилось — пересчёт пропускается целиком.

В реестре два независимых счётчика (**проверено**, `crates/shamir-index/src/registry.rs:64-97`):

- `insert_ticket` — выдаёт тег новой записи (`:164`, `fetch_add`);
- `generation` — публикуемый watermark: `fetch_max(my_gen)` на insert (`:198`),
  `fetch_add(1)` на remove (`:275`).

**Два инварианта, записанных в самом коде, — ложные.** Это сильнее того, что
утверждали оба ревью, и это ключ ко всей связке:

1. `registry.rs:92-94` заявляет: *«starts at 0 — independent from `generation`. Its
   absolute values never need to match `generation`'s; only the `fetch_add`
   uniqueness matters.»*
   Это **неверно**: `backends_newer_than(threshold_gen)` сравнивает `entry.gen >
   threshold_gen` (**проверено**, `:237-248`), то есть кладёт тикет и поколение в
   одно числовое пространство. Как только `remove_by_id` двигает `generation`, не
   двигая `insert_ticket`, пространства расходятся — и сравнение теряет смысл.

2. `registry.rs:78-81` заявляет: *«a reader observing `generation() == N` is
   guaranteed every entry tagged `<= N` is already visible in `by_id`»*.
   Это **неверно** при внеочередной публикации: A берёт тикет 1 и задерживается,
   B берёт тикет 2 и публикуется (`generation = 2`), читатель видит 2, но запись
   A с тегом 1 ещё не видна.

**Детерминированный отказ** (не гонка, воспроизводится последовательно):
`CREATE A` (тикет 1, gen 1) → `DROP A` (gen 2, тикет всё ещё 1) → tx стейджится при
gen 2 → `CREATE B` (тикет 2, `fetch_max(2)` — no-op, gen остаётся 2) → коммит видит
то же поколение → пересчёт пропущен → **строка закоммичена, но навсегда отсутствует
в индексе B**. Это ровно тот класс, который задача #958 (P0-2 прошлой волны)
объявляла закрытым.

### Как решается

Два кандидата, **предложение** — брать (b), потому что он же закрывает второй
ложный инвариант:

**(a) Дешёвый: одно числовое пространство.** Один счётчик `seq` обслуживает и теги
записей, и watermark; `remove_by_id` тоже берёт тикет и делает `fetch_max` после
снятия публикации. Чинит последовательный сценарий, **не чинит** внеочередную
публикацию (инвариант 2).

**(b) Полный: сериализованная публикация.** Резервирование тикета и публикация
происходят под одной критической секцией — тогда `fetch_max` корректен по
построению, а оба инварианта становятся истинными. Это ровно то, что даёт #1012
(единый DDL-координатор): если все CREATE/DROP/RENAME всех семейств проходят через
одну точку входа, реестр мутируется по одному, и внеочередной публикации не
существует.

**→ Поэтому #1006 и #1012 — одна связка, а не две задачи.** Делать #1006 в
варианте (a) в отрыве от #1012 значит гарантированно переписывать этот код второй
раз. Если оператор решит разделить — фиксируем (a) как временную меру и открываем
явный долг на (b).

**#1012 отдельно** (**проверено**): `drop_sorted_index` зовёт менеджер напрямую,
без `begin_write_barrier` (`crates/shamir-engine/src/table/table_manager_sorted_index.rs:297-304`);
по обоим отчётам то же для `drop_index2` и обоих RENAME-путей (**из ревью**,
`table_manager_index_mgmt.rs:863-970,1437-1690`). Итог: заявление «per-table DDL
admission» шире фактической гарантии, и для sorted/index2 DROP остаётся окно, в
котором writer со снятым до retire снимком допишет posting после sweep.

Фикс #1012: все DDL всех четырёх семейств — через `begin_write_barrier` /
координатор; внутренние API менеджеров сделать `pub(crate)` или требующими
guard-токен, чтобы обход был невозможен синтаксически, а не по договорённости.

## R0-B. Идентичность инстанса и provenance плана (#1007 + #1008)

### Зачем

**#1007 (проверено):** `SortedIndexManager` бампает `generation` при регистрации
(`sorted_index_manager.rs:615`) и при drop (`:924`), но **не бампает при rename** —
`rename_definition` (`:1024-1055`) делает RCU-замену `name_interned`, переносит
epoch-запись и персистит, и на этом всё. А sorted-пересчёт на коммите гейтится
именно на `sorted_mgr.generation() == stage_gen` (**проверено**, `pre_commit.rs:1028`).

Отказ: tx стейджит sorted-операции под `old_id` → RENAME переносит postings →
tx коммитится → поколение не изменилось → пересчёт не запускается → `SetPosting`
уходит под `old_id`. Итог двойной: **строка отсутствует в переименованном индексе**
и **orphan postings в снятом namespace**. Причём sorted-id — это `name_interned`
(**проверено** по doc-комментарию `sorted_index_manager.rs:1075`, «orphaned under
the `SORTED_TAG || old_id` prefix»), поэтому повторный `CREATE` под старым именем
унаследует чужие ghost-postings.

**#1008 (проверено):** пересчёт асимметричен. Для index2 (`pre_commit.rs:890,930`)
и sorted (`:1070,1077,1102`) — только `appended.extend`, снятия устаревших операций
нет вообще. Для base ретракция есть, но идентифицирует операции по
`(is_unique, name_interned)` (**проверено** по doc-комментарию `:1140-1145`), то есть
**по имени** — а имя переживает DROP+CREATE. Классический ABA: tx планируется для
`x` по полю `a` → `x` удаляется → создаётся `x` по полю `b` → на коммите старые
операции сохраняются, потому что имя снова живо → загрязнение нового индекса, а для
unique — ложные конфликты.

### Как решается

**#1007 — узкая часть:** бамп `generation` в `rename_definition`, симметрично drop.
Механически это почти однострочник. **Но сам по себе он недостаточен:** бамп
заставит пересчёт добавить корректные новые операции, при этом старые операции под
`old_id` останутся в наборе и тоже применятся. То есть #1007 закрывается только
вместе с ретракцией из #1008 — отсюда `blockedBy`.

**#1008 — широкая часть.** Перестать опознавать staged-операции эвристикой по
байтам и именам. Каждой `IndexWriteOp` — типизированный provenance: семейство +
неизменяемый идентификатор инстанса + версия определения. Тогда пересчёт
**заменяет план инстанса целиком**: снять операции снятых инстансов, вывести
операции для новых.

**Важная развилка (предложение), которой нет ни в одном отчёте.** «Неизменяемый
instance id» имеет две принципиально разные цены:

- **In-memory identity** — идентификатор живёт только в плане транзакции и в
  каталоге в памяти; физический префикс ключа остаётся `name_interned`.
  Закрывает ABA в плане tx (это и есть корректностный дефект), **не требует
  миграции на диске**.
- **Physical identity** — идентификатор становится префиксом физического ключа.
  Дополнительно убирает ghost-postings при повторном использовании имени, но это
  **смена формата на диске** → миграция, версия формата, риск для alpha.

**→ Для R0 брать in-memory identity.** Physical — отдельная задача после alpha,
и её частично закрывает корректный DROP (#1011/R0-E) плюс единый namespace (#1010).

`crates/shamir-index/src/base_index/sorted_index_manager.rs:1024-1055` (+ `:615`, `:924` как образец бампа),

- [ ] `stage → DROP → commit` для всех четырёх семейств: postings не воскресают.
- [ ] `stage → DROP → CREATE same name / different field → commit`: новый индекс не
      загрязнён; для unique — нет ложного конфликта.
- [ ] Несколько lifecycle-переходов между stage и commit.
- [ ] Rollback после частично применённых пересчитанных операций.
- [ ] Байтовая эвристика ретракции (`p02c_retain_filter_key_collision_tests`) удалена
      вместе с породившим её кодом, а не «улучшена».

## R0-C. Атомарность каталога и единство имён (#1009 + #1010)

### Зачем

**#1009 (проверено):** `IndexRegistry::insert` публикует в `by_id`
(`registry.rs:178-190`), затем в `by_name` (`:191-196`); при занятом имени
возвращает ошибку **без отката `by_id`**. К этому моменту CREATE index2 уже мог
сохранить Building-дескриптор, выполнить backfill и создать физические postings.
Результат: бэкенд жив по id (виден обходам `all_backends`/`backends_newer_than` и
планировщику, выбирающему по полям), но недоступен по имени; `DROP` по имени снесёт
другой инстанс.

Хуже: на старте ошибка вставки **проглатывается** —
`let _ = mgr.index2_registry.insert(backend).await;` (**проверено**,
`crates/shamir-engine/src/table/table_manager.rs:511`), после чего Building-ветка
переводит дескриптор в Ready и переперсистит (`:515-518`).

**#1010 (проверено):** имя индекса не уникально между семействами. CREATE проверяет
существование только в своей ветке (`crates/shamir-db/src/shamir_db/execute/admin_table_index.rs:352-357`),
а DROP резолвит имя короткозамкнутым `||` по семействам, возвращая первое
попадание — это прямо написано в комментарии (`:593-618`). Значит: DROP оставляет
тёзок из других семейств; RENAME может переименовать несколько семейств подряд;
ошибка в середине RENAME оставляет частично изменённый каталог. Пробел признан и в
коде (`in_flight_create_guard.rs:39-47`).

> **Расхождение ревью, требует решения оператора.** codex-отчёт считает #1010
> P0-блокером тега; финальный @fh-отчёт понижает до R1 (сразу после
> correctness-freeze). Консервативно — делать в R0 вместе с #1009: обе задачи про
> одно и то же («что такое одна успешная регистрация»), и preflight-проверка
> уникальности имени из #1009 всё равно должна знать, в каком namespace проверять.

### Как решается

- Preflight глобальной уникальности имени (по единому namespace) **до** persistence
  и backfill — тогда коллизия отсекается до дорогой работы, а не после неё.
- Вставка в обе проекции атомарно либо обязательный откат `by_id` при ошибке `by_name`.
- Открытие таблицы — fail-closed на дубликат метаданных: ошибка открытия либо
  дескриптор в `Failed` (см. R0-D), но не молчаливый `let _`.
- Инвариант-проверка `by_id ↔ by_name ↔ persisted descriptors` в `verify()`.
- Startup doctor детектирует уже существующие коллизии имён и требует явного
  repair/rename — молча выбирать семейство нельзя.

### Файлы

`crates/shamir-index/src/registry.rs:178-198`,
`crates/shamir-engine/src/table/table_manager.rs:466-520`,
`crates/shamir-db/src/shamir_db/execute/admin_table_index.rs:352-357,593-618`,

### Закрыто, когда

- [ ] Вставка дубликата в реестр не оставляет запись только в `by_id`.
- [ ] Старт с дублирующимися дескрипторами: отказ либо `Failed`, но не `Ready`.
- [ ] CREATE отклоняет имя, занятое любым из четырёх семейств.
- [ ] `verify()` сообщает о расхождении `by_id ↔ by_name ↔ persisted`.

### Делегируемость

пользовательскую семантику DDL, нужен явный ответ по приоритету и по обратной
совместимости с уже созданными коллизиями.

## R0-D. Fail-closed при восстановлении (#1013 + #1023)

### Зачем

**#1013 (проверено):** в open-path две ошибки лечатся логом и продолжением.
`drop_all` при self-heal Building — `log::warn!` и дальше backfill, причём сам лог
признаёт «partial postings may persist» (`table_manager.rs:491-503`); для FTS это
ещё и двойной учёт статистики, потому что stats не перезаписываются начисто.
`restore_on_open` — `log::warn!`, и бэкенд остаётся в реестре со статусом Ready
(`:579-585`), то есть planner-visible с пустым или неполным состоянием. Для vector
это означает молча неполные результаты поиска.

Для базы данных молчаливый неверный результат хуже отказа открыться.

**#1023 (из ревью):** backfill `create_unique_index` молча пропускает записи с
ключом ≠16 байт и недекодируемые (`index_manager_unique.rs:372-380`) — такая строка
не попадает в unique-индекс, и её значение позже может быть принято за свободное.
Прямо противоречит fail-closed-политике, введённой в #960 для corrupt unique posting.

### Как решается

**Хорошая новость (проверено):** `IndexState` сейчас двухвариантный
(`crates/shamir-index/src/state.rs:50-60`), и его собственная документация говорит,
что **добавление варианта обратно совместимо** (bincode тегирует варианты
порядковым номером; append безопасен, ломает только перестановка). Значит
`Failed` добавляется дёшево и это не форматный риск.

- Неудачное восстановление → `Failed` (planner-invisible), а не `Ready`.
- Инфраструктура для сигнала оператору **уже есть**: `Failed` автоматически попадёт
  в `shamir_degraded_indexes_total` (#984/#1003/#1005) — то есть эта задача
  доводит до конца уже построенную наблюдаемость, а не строит новую.
- Причина и рекомендуемое действие — через operator API (см. #1014).

## R0-E. Решение: DROP под живыми readers (#1011)

**Это задача-решение, не задача-код. Не делегировать.**

**Проверено:** ограничение честно задокументировано в самом коде как KNOWN GAP
(`crates/shamir-index/src/base_index/index_manager.rs:1616-1630`): reader,
разрезолвивший индекс до retire, держит `Arc<backend>`, но postings лежат в общем
`info_store`, который `drop_all`/`remove_many` физически чистит — `Arc` не даёт
снимка данных. Результат неполный, но не искажённый. Barrier сериализует DROP
против writers, но не против readers. Sorted и index2 — тот же класс.

Варианты:

- **(a) Документировать** как известное ограничение alpha (`KNOWN_LIMITATIONS.md` +
  release notes) — сейчас признание живёт только в doc-комментарии, куда
  пользователь не смотрит. Дёшево, честно, разблокирует тег.
- **(b) Реализовать** read-side grace period / reader-epoch перед физическим GC.
  Существенная отдельная работа; механизма в кодовой базе нет.

@fh-отчёт настаивает: решение должно быть принято **явно**, а не оставлено по
умолчанию. Для тега достаточно (a); (b) — после alpha.

# Рекомендуемый порядок

**Предложение**, оба отчёта согласны в главном (сначала R0, спорят только о месте #1010):

1. **R0-D** (#1013 + #1023) — самая изолированная связка, даёт быструю победу и
   доводит до конца уже построенную наблюдаемость degraded-gauge.
2. **R0-A** (#1006 + #1012) — принять решение (a)/(b), затем реализовать связкой.
3. **R0-C** (#1009 + #1010) — после A, потому что preflight имени опирается на
   единый namespace; требует ответа по приоритету #1010.
4. **R0-B** (#1008 → #1007) — самая крупная и рискованная; делать последней в R0,
   когда каталог и координатор уже стабильны. **Перед стартом проверить влияние на
   формат WAL.**
5. **R0-E** (#1011) — решение оператора, можно принять в любой момент, но до тега.
6. Затем R1, R2; R3 — после alpha.

**Гейт выхода из R0:** двенадцать детерминированных regression-тестов из обоих
отчётов зелёные, плюс `cargo fmt --check`, `cargo clippy --workspace --all-targets
-D warnings`, `./scripts/test.sh --full` на замороженном SHA.
