## 0. Summary and decisions

R1a landed the stamp and the refusal rows: an older-epoch directory is refused with `StampError::OlderEpoch` (`server/shamir-sync/src/format_stamp/model/stamp_error.rs:77-82`) and the message already names "the format-migration command (R1b)" — which does not exist. This design adds: a framework of one-epoch-step modules with a const registry, an execution journal in the data directory, a `format-migrate` subcommand of the existing `shamir-server` binary with a plan mode and a fresh-backup requirement, the first (empty) migration proved in CI, and the reference-directory compatibility test. The stamp is written only after the last step and the integrity check; while a chain is in flight the stamp still carries the old epoch, so a plain start keeps refusing (rows 9/12 of the stamp design). The command resolves rows 9, 12 and 5b; rows 8, 11, 6, 18, 19, 20 remain refused.

Decisions (owner-level ones are repeated in section 11 with defaults):

### 1.3 Locks, backup and restore

* Data-dir lock: `maintenance_lock::acquire` / `acquire_with` (`server/shamir-sync/src/sync/durability/maintenance_lock.rs:9-13`, lock file `:22`), `fs4` exclusive try-lock on `<data_dir>/.shamir.lock`; the server uses `acquire_server` (`launch.rs:120`, held for the process lifetime). A second `acquire` while a server runs fails — this is the "is the server stopped" probe the command reuses. The kernel releases the advisory lock when the holder dies, so a crashed run never leaves the directory locked.
* Backup: `backup --to <dir>` copies every top-level entry except `cache/` (`copy_dir_recursive`, `backup.rs:591`, cache exclusion `:603`) and writes `manifest.json` (`MANIFEST_FILE_NAME`, `backup.rs:75`; `Manifest.created_at_unix_ns` at `:169-171`, set at `:336`; per-file sha256 via `hash_file_streaming`, `backup.rs:58`; `verify_manifest` at `backup.rs:411` rejects checksum mismatch, unmanifested files and cache-subtree paths, error variants `:85-123`). Offline only ("Server should be stopped first", `main.rs:130`). The stamp is copied byte for byte (stamp design S-5.2).
* Restore: verifies the snapshot manifest before touching `data_dir`, stages and swaps, keeps `.pre_restore_backup_<ts>` (`main.rs:144-167`); an older-epoch snapshot is allowed and the next start refuses until the format-migration command runs (stamp design S-3.5). The snapshot carries the journal of the interrupted run together with the old stamp, so the restored directory is still resumable or still refuses — never silently clean (4.4d).

## 2. The framework

Everything in this section is PROPOSED except where it cites observed code.

### 2.1 Home (decision M1)

New folder `server/shamir-sync/src/format_stamp/migration/` inside the stamp module. The `shamir-sync` `src/` folder is ALREADY at its 7-entry limit (`config_error.rs`, `format_stamp/`, `lib.rs`, `meta_port/`, `subscriptions/`, `sync/`, `version.rs` — verified), so a top-level `format_migration/` would make 8 and violate the layout rule; instead `format_stamp/` drops the moving change log (7 → 6) and takes `migration/` as its 7th entry, and `format_stamp/mod.rs` gains one `pub mod migration;` line. `shamir-sync` is chosen for the same reasons as the stamp module (stamp design S-2.2): it owns the lock, backup, restore and seed paths, it depends downward on nothing engine-side, and its dependencies already cover the encoding (serde, serde_json, thiserror — `server/shamir-sync/Cargo.toml`; no new dependency, README principle 4). Layout (each folder ≤ 7 entries):

* `migration/mod.rs` — re-exports only.
* `module.rs` — `FormatStep` trait, `StepDescriptor`, `ModuleDescriptor` (2.2).
* `registry.rs` — the const registry `FORMAT_MODULES` + the chain builder (2.3).
* `error.rs` — `MigrationError` (2.4).
* `journal/` — record model, reader, writer (section 4).
* `runner.rs` — plan/execute loop (section 5 backing code).
* `change_log.rs` — MOVED here from `format_stamp/change_log/` as one file (`FormatChange` + `FORMAT_CHANGES` are one closely-coupled group; executes stamp-design D12: "R1b moves it next to the format-migration modules"). `format_stamp/` drops to 6 entries and re-exports nothing extra; `format_stamp/mod.rs` loses the `change_log` lines and gains the `migration` module line. `FORMAT_CHANGES[i].migration_module` is filled with the registry id of the module that carries each epoch bump.

Tests live in `format_stamp/tests/migration/` (the existing `tests/` folder goes 6 → 7 entries; `format_stamp/tests/mod.rs` gains the manifest line).

The command wrapper lives in `shamir-server/src/migrate/` (new 7th entry of `src/`, see 1.2): `mod.rs`, `cli.rs` (arg struct), `plan.rs` (plan rendering), `backup_gate.rs` (fresh-backup check), `tests/`.

### 2.2 Modules, steps, idempotence (decision M2)

One module moves the data exactly one epoch step, `N` → `N+1`. A chain is the sequence of steps from the stamp's epoch to `CURRENT_FORMAT_EPOCH`; gaps are refused by construction (2.3) and by a CI test (9).

```rust
pub struct ModuleDescriptor {
    pub id: &'static str,          // matches FormatChange::migration_module
    pub from_epoch: u64,
    pub to_epoch: u64,             // == from_epoch + 1
    pub summary: &'static str,
    pub touches: &'static [&'static str], // surfaces of 1.4, for plan output
    pub work_estimate: &'static str,      // e.g. "rewrites every WAL sidecar; O(segments)"
}
pub trait FormatStep {
    fn descriptor(&self) -> &ModuleDescriptor;
    /// Apply the step. Must be idempotent; must not touch format.stamp.
    fn apply(&self, ctx: &mut StepContext) -> Result<(), MigrationError>;
    /// Dry run: report what would change; must not write anything.
    fn plan(&self, ctx: &StepContext) -> Result<Vec<PlanLine>, MigrationError>;
}
```

`StepContext { data_dir: &Path, journal: &JournalWriter, policy: EpochPolicy }`. A step reaches data **without opening the engine**: it works on plain paths under `data_dir` and, when it needs structured access, opens the specific backend directory directly (the same path-based fjall open the storage backend uses, `storage/shamir-storage/src/stores/storage_fjall/repo.rs:126` — `Database::builder(path).open()`), never `ShamirDb::init`, which runs WAL recovery and would assume the old format everywhere at once (decision M3; the engine cannot open the old format — that is why the stamp refuses, rows 9/12). The empty first module needs none of this.

Idempotence rules a step must obey (checked by review + a mandatory per-module test, section 9):

1. Running `apply` on already-migrated data changes nothing observable (file listing, bytes, mtimes) — the test framework asserts this with the `DirSnapshot` helper already in `format_stamp/tests/support/dir_snapshot.rs`.
2. The step detects "already applied" from the data itself (a marker row, a renamed file, a sidecar version), never from the journal alone: the journal proves the runner's progress, the data must survive a step being re-run after any crash point (4.4).
3. Before its first mutation the step records its intent in the journal ("step started" is written by the runner, 4.1 — a step never writes journal records itself).
4. The step never writes `format.stamp` and never opens a second data directory.

Framework help: the test-side helper `apply_twice_is_noop(step, fixture_dir)` lives in `format_stamp/tests/support/` (NOT in production `runner.rs` — the repository test-organisation rule keeps test helpers out of production code): it runs `apply`, snapshots, runs `apply` again, and asserts snapshot equality; every module's test folder must call it (9).

### 2.3 Registry and the chain (decision M2)

`registry.rs` holds `pub const FORMAT_MODULES: &[&dyn FormatStepDesc]` — a const table like `FORMAT_CHANGES` (`change_log/format_changes.rs:8`), ordered by `from_epoch`. The chain builder walks `stamp_epoch → CURRENT`: at each epoch `N` it requires exactly one module with `from_epoch == N` and `to_epoch == N+1`; zero or two modules, or `to_epoch != from_epoch + 1`, or a final epoch below `CURRENT`, is `MigrationError::BrokenChain`. Unit tests assert: ids unique, epochs consecutive and gapless from `BASE_FORMAT_EPOCH` to `CURRENT_FORMAT_EPOCH`, every module id appears in exactly one `FORMAT_CHANGES` entry with `bumps_epoch = true` and `epoch_after == to_epoch`, and `CURRENT_FORMAT_EPOCH == BASE + number of bump entries` (this extends the invariant the stamp design stated at S-4.1). Because the registry is a table whose length grows one entry per epoch, the 7-entry folder rule is met by giving each module its own subfolder when it has more than one file (`modules/e0001_0002/`); a module that is one file is one entry in `registry.rs` itself. When `migration/` would exceed 7 entries, completed modules group under a per-release subfolder (e.g. `modules/rel1/`) — noted here so the limit is never an afterthought.

Test-only chains: the registry constructor `chain_for(policy, &[...])` is a plain public function over a module slice, so tests (6, 9) compose custom chains — a test-only policy with a higher current epoch plus a test module — without any visibility widening or `cfg` hook (same approach as `EpochPolicy::new`, `model/epoch_policy.rs:23-25`).

### 2.4 Errors

`MigrationError` (thiserror, `error.rs`): `Refused { source: StampError }` (the pre-check of 5.3), `BrokenChain { from, expected, found }`, `Journal { dir, source }`, `StepFailed { module, source }`, `BackupGate { message }`, `ServerRunning`, `Io { dir, source }`. `shamir-server` maps it onto `anyhow` in the subcommand arm like the other offline arms (`main.rs:371-383` pattern); no new `BootError` variant is needed because the command never runs inside `launch()`.

## 3. What a run looks like (PROPOSED)

State machine of a data directory during a format migration:

1. Resting: stamp epoch `N < CURRENT`; every start refuses rows 9/12 (stamp design S-3.4); `backup` is allowed with the observation attached (S-3.5). NOTE: `backup` does not take the data-dir lock, so a backup started during an in-flight migration captures a half-migrated directory (old stamp + journal). It is never silently dangerous (restore of it refuses or resumes consistently, 4.4d), but the guide must say: take the backup BEFORE starting `format-migrate`.
2. The operator runs `format-migrate` (5): the command takes `.shamir.lock` (`maintenance_lock::acquire`, `maintenance_lock.rs:9`), re-checks the stamp in Inspect mode (accepts only `OlderEpoch`/`AbsentOlderBase`), verifies the fresh backup (5.4), creates the journal, runs the chain.
3. In flight: the stamp still carries epoch `N` (M6 — never rewritten early), so a plain start during the migration (or after a crash) keeps refusing with exactly the row-9/12 message; the journal is the only sign a migration is partial. `.shamir.lock` is held for the whole run, so no second command and no server can open the directory concurrently.
4. Finished: after the last step and the integrity check the runner writes the stamp at the new epoch (read-back-verified atomic write, `write_stamp`, `io/atomic_write.rs`), sets `last_format_migration` (`model/format_stamp.rs:21` — the field already exists), appends the final journal record, releases the lock, and exits 0. The next plain start takes row 7/10 (`Unchanged`).

## 4. The execution journal (decision M4)

### 4.1 Name, location, records, encoding

File: `<data_dir>/format_migration.journal` (next to `format.stamp`, so `backup` copies it and `restore` carries it with the snapshot — both copy every top-level entry except `cache/`, `backup.rs:591-607`; a restored half-migrated directory is therefore still resumable or still refuses, never silently clean). Encoding: JSON lines, UTF-8, one record per line, LF-terminated. A torn LAST line (no LF, or not valid JSON) is treated as never written (4.3, last row); an invalid line that is NOT the last line (bit rot, external editing) is `MigrationError::Journal` — refuse, never silently truncate a middle record (4.4). Record kinds:

| kind | fields |
|---|---|
| `chain_started` | `from_epoch`, `to_epoch`, `binary_version`, `modules: [id…]`, `unix_ms` |
| `step_started` | `module` (id), `from_epoch`, `to_epoch`, `unix_ms` |
| `step_finished` | `module`, `unix_ms` |
| `chain_finished` | `to_epoch`, `unix_ms` |

(The chain, the epochs and the binary version ride in `chain_started`; each `step_*` record repeats its epochs so a truncated journal is still interpretable.) A missing or empty journal file with an old-epoch stamp simply means "no migration in flight".

### 4.2 Atomic append and fsync per OS

Each append: `OpenOptions::new().append(true).open(...)`, write the full record line in one `write_all`, then `file.sync_all()` — per record, not batched (a migration is slow by nature; one fsync per record is negligible and bounds the crash window to one record). Any append/open/sync ERROR is fatal for the run: the runner refuses (exit 1, journal left in place); it never skips a record or degrades to buffered writes. This covers the practical OS cases: antivirus or another process holding the file without share permissions fails the `open` before any mutation of that step's record; a full disk fails `write_all`/`sync_all` and leaves at most a torn last line (treated as never written, 4.3); a read-only volume fails journal CREATION, which happens before the first step mutates anything (5.3 order), so the refusal leaves the directory untouched (state 1). File creation is fsynced into the directory: strict dir fsync on Unix (the pattern already in `io/atomic_write.rs:23-27`); on Windows there is no directory flush, the creation is synced via the file handle and the residual risk is the same one the stamp design accepted for the first stamp write (S-2.4, S-6 Q6): after power loss the journal file may be absent, which degenerates to state 1 (resting, refusal) — safe by construction because the stamp was never touched.

### 4.3 Crash table (every journal point)

| Crash point | State on disk after restart | What the resumed run does |
|---|---|---|
| before `chain_started` is fsynced | old stamp, no (or empty) journal | state 1; rerun from scratch; nothing was modified |
| after `chain_started`, before first `step_started` | journal says a chain began, data untouched | rerun: existing `chain_started` for the same from/to/version is reused (append a second one only if the module list differs → `BrokenChain` refuse); steps run from the first |
| inside a step (after `step_started`, before `step_finished`) | partial step | the runner re-enters the SAME module first (4.4); the step's own idempotence rule (2.2 rule 2) completes or no-ops it |
| after `step_finished`, before next `step_started` | completed prefix | resume at the next module in the chain |
| inside the LAST step | partial last step | as "inside a step": re-enter the last module |
| after last `step_finished`, before integrity check/stamp | all data migrated, stamp still old | integrity check, then write the stamp; no step re-runs |
| stamp written, `chain_finished` not yet | new stamp, journal lacks the final record | plain start now succeeds (row 7/10); the leftover journal is deleted by the next successful writer start (same treatment as a stale `format.stamp.tmp`, row 21 of the stamp design); a resumed `format-migrate` run sees stamp == CURRENT and exits 0 "nothing to do" |
| torn last line (power loss mid-record, or disk full mid-`write_all`) | journal minus the torn record | the record is treated as never written; the corresponding point above applies |
| invalid NON-final line (bit rot, external edit) | journal unreadable as a whole | refuse `MigrationError::Journal`; no step runs; recovery is the guide's rollback (restore the pre-migration backup); never skip a middle record |
| journal append/open/sync fails at run time (antivirus holding the file, disk full, read-only volume) | state unchanged up to that record | fatal refusal before the failing record's step completes; the directory stays in the refused old-epoch state; operator frees the resource and re-runs (resume rule 4.4) |
| two runs racing (or a run while a server is up) | second process fails `.shamir.lock` acquisition (`maintenance_lock.rs:9-22`); the kernel releases the lock when the first holder dies, so a crashed run never wedges the lock | the loser exits "stop the server first"; only one writer ever progresses |

The invariant: the stamp moves only at the very end (M6), so every crash leaves the directory in a state the decision table already refuses safely (rows 9/12) until the migration completes.

### 4.4 The resume rule

On start the runner reads the journal: (a) no/empty journal → run the whole chain; (b) `chain_started` with a module list that differs from the current registry's chain for those epochs, or a different `binary_version`, or epochs that do not match the stamp → refuse `BrokenChain` (the operator re-runs after re-checking; the guide's rollback is restore, stamp design S-3.5 / plan 3.5 — in-place format rollback is not supported); (c) otherwise the resume cursor is: the first module whose `step_started` has no matching `step_finished`; all earlier modules are skipped. (d) A directory restored from a backup of an interrupted run carries BOTH the old stamp and that run's journal: it refuses on a plain start (rows 9/12) and resumes consistently under `format-migrate` — the journal, the stamp and the partial step state always travel together because `backup`/`restore` copy the whole top level (`backup.rs:591-607`). A journal whose `binary_version` is newer than the running binary (operator downgraded the binary mid-way) is case (b) and refuses. This makes "repeat completes the migration" (plan 7, acceptance row R1b) hold by construction.

### 4.5 When the stamp is written (decision M6)

Only after: (1) the last `step_finished` is fsynced; (2) the integrity check passes (the existing `doctor`-level scan invoked as a library step over the migrated directory — table health and index rebuild-check, `diagnostics/doctor.rs:214` — PROPOSED to reuse its check-only path); (3) the new stamp is built with `FormatStamp::with_epoch(CURRENT, ver, now)` plus `last_format_migration = { id: last_module, from_epoch, to_epoch, unix_ms }` and written via `write_stamp` (read-back verified). Never before, never per step. While the chain is in flight the stamp holds the old epoch, so a plain start keeps refusing (rows 9/12) — stated in section 3, point 3.

## 5. The command (decision M5)

| arg | meaning |
|---|---|
| `--plan` | plan mode: change nothing (5.2) |
| `--from-backup <dir>` | path to a `backup --to` snapshot root (with `manifest.json`) proving a fresh backup (5.4) |
| `--max-backup-age-hours <N>` | freshness window; default `24` |
| `--i-have-a-backup` | override the backup gate (5.4) |
| `--yes` | required for the actual run; without it the command prints the plan and exits (interactive confirmation is avoided on purpose: CI and scripts) |

### 5.2 Plan mode

`format-migrate --plan` prints, without taking any write action (it takes neither the lock nor any Inspect-mode stamp — it never creates a file): current stamp state and epoch, the resolved chain (module id, summary, `touches` surfaces, work estimate — from `ModuleDescriptor`), the journal state (no journal / partial chain with resume cursor), the backup-gate verdict, and what remains refused if it is not run. Plan mode changes nothing: asserted by a `DirSnapshot`-style test (9).

### 5.3 Preconditions, locking, exit codes

Order of checks, each failing closed with exit code `1` and a message on stderr (the `main.rs:268-276` error convention of the other offline arms): (1) stamp Inspect check — only `OlderEpoch` or `AbsentOlderBase` may proceed; `NewerEpoch`, `Corrupt`, `NewerLayout`, `TornTmp` are printed as-is and refused (these rows are NOT resolved by the command); stamp == CURRENT → exit `0` with "nothing to do"; if the stamp's actor is `adopted` (stamp design S-2.4 / Q6 boundary note) the chain REFUSES unless `--yes` is also given and the refusal is logged loudly — an adopted stamp means the epoch evidence is the weakest kind the stamp module produces. (2) lock: `maintenance_lock::acquire(data_dir)`; failure means a server (or another command) holds the directory → "stop the server first"; the first version supports only a stopped server (plan 3.4) and there is no online path (R2 online backup is a separate direction). (3) backup gate (5.4) unless `--i-have-a-backup`. (4) chain build (`BrokenChain` refuse). (5) the journal is CREATED and its `chain_started` record fsynced BEFORE the first step mutates anything — a read-only volume or an unwritable directory refuses here with the data untouched; then steps, integrity check, stamp (sections 3-4). Exit codes: `0` success or nothing-to-do, `1` any refusal or failure, `2` usage error (clap default). Output: one line per step on stdout (`[3/7] e0003_0004 wal-sidecar … ok (12s)`) plus a final summary; `--plan` output is stable text suitable for change records.

### 5.4 The fresh-backup requirement (default safe)

Until R2's online backup exists the gate uses the existing offline `backup` (plan 3.4: "before R2 — the existing backup with a stop"). The command REQUIRES `--from-backup <dir>` and verifies: (a) `<dir>/manifest.json` parses and `verify_manifest` passes (`backup.rs:411`, error variants `:85-123`, sha256 of every file); (b) the snapshot contains a copy of `format.stamp` whose format EPOCH equals the data directory's current epoch, AND whose `created_by` actor equals the live stamp's, AND whose set of top-level entry names (from the manifest's file list) covers the live directory's top level — epoch equality ALONE does not prove identity: any two directories of the same epoch carry the same epoch, so a backup of ANOTHER directory of the same epoch would otherwise satisfy the gate (the backup copies the stamp byte for byte, S-5.2); (c) `Manifest.created_at_unix_ns` is within `--max-backup-age-hours` (default 24 h; field at `backup.rs:169-171`, set at `:336`). A backup that passes (a)-(c) but was taken of an EMPTY directory (adopted stamp, no data) satisfies the letter of the gate while containing no data — it is rejected because the live directory's stamp would be `OlderEpoch` with data present while the snapshot's stamp would be absent-or-adopted; the epoch/actor/name-set comparison of (b) catches this. Any failure → refuse with the instruction to run `backup --to <dir>` first. `--i-have-a-backup` skips (a)-(c) and prints an explicit warning; the default is safe (gate on). PROPOSED: a snapshot of a directory in an older epoch is exactly what is wanted (the backup is taken before the migration); the epoch comparison is against the pre-migration stamp, not against `CURRENT`. Full identity proof needs a per-directory UUID in the stamp — deferred to open question Q9.

### 5.5 Interaction with the stamp decision table

| Row (stamp design S-3.4) | Resolved by the command? |
|---|---|
| 9, 12 (`OlderEpoch`) | YES — the command's purpose; stamp advances to CURRENT. If the stamp's actor is `adopted`, only with the extra confirmation of 5.3 (stamp design Q6 boundary note) |
| 5b (`AbsentOlderBase`) | YES, with explicit confirmation: the stampless directory is treated as `BASE`, `--yes` plus the backup gate apply, and the final stamp write also creates the first stamp (`created_by` records the migrating binary, not `adopted`) |
| 8, 11 (`NewerEpoch`), 20 (`NewerLayout`), 6 (`TornTmp`), 18 (`Corrupt`) | NO — printed and left refused; recovery stays restore/manual (guide) |
| 7, 10 (equal) | not an error: "nothing to do", exit 0 |
| 15 (corrupt, empty dir) | NO — the stamp check already repairs it on the next start |

## 6. The first, empty migration (decision M7)

`CURRENT_FORMAT_EPOCH` is still `1` (`model/epochs.rs:11`), so the shipped binary has no real chain. The chain machinery is nevertheless proved in CI before any real format change exists:

* A test-only policy: `EpochPolicy::new(2, 1)` (the constructor exists, `model/epoch_policy.rs:23-25` — stamp design S-6.1). A stamp with epoch 1 in the fixture is then "older".
* A test-only registry: `chain_for(policy, &[empty_step])` where `empty_step` is a module `e0001_0002` with an `apply` that writes nothing (its idempotence test then trivially asserts the double-run no-op) — proving registry walk, journal, resume, integrity-check call and the final stamp write end to end on a real temporary directory.
* A step that fails halfway on purpose (`failing_step`): writes a marker file, then returns `Err`. Tests assert: the journal ends with `step_started` and no `step_finished`; a plain `check_data_dir(Writer)` still refuses (`OlderEpoch`, stamp untouched, `DirSnapshot` equal except the journal and the step's own partial artefact); a rerun with the failing step replaced by the empty step (resume rule 4.4c) completes and writes the stamp at epoch 2.

These live in `format_stamp/tests/migration/` (the test folder of 2.1; `#[cfg(test)] mod tests;` stays in `format_stamp/mod.rs` as today, with the manifest line added per the repository test-organisation rule). Nothing test-only reaches the production registry: `FORMAT_MODULES` stays empty while `CURRENT == BASE`, and the CI test of 2.3 asserts `BASE == CURRENT` iff `FORMAT_MODULES` is empty.

## 7. The compatibility test (plan 3.7) (decision M8)

### 7.1 What the reference directory contains

A data directory written by the binary of a released epoch, containing: tables with schemas (at least two, one with `schema_version > 1`), every index kind the release supports (hash, sorted, vector, full-text — README section 1 lists them), every function kind (WASM-compiled and `shamir`-source, one with `call_signature`), users, groups, rights (ACL rows), tokens, an unfinished WAL (a `.shamirwal/` with a segment whose content was not yet checkpointed, so open-with-recovery exercises the WAL path), and a valid `format.stamp` at that epoch. Excluded: `cache/` (derived), TLS material, logs.

### 7.2 Who creates it, when, and where it lives

A script `scripts/release/make_reference_datadir.py` (new file, design-only here) run at release time: it starts the release binary against an empty data dir, applies the fixed scenario via the admin/SQL surface, stops the server cleanly, prunes `cache/`, and asserts the size cap. The result is committed as a fixture directory `crates/server/shamir-server/tests/fixtures/reference_epoch_<N>/` (cargo integration-test area, outside `src/`, so it is not compiled or counted by the source-folder limits; the layout checker's rules for source files do not apply to test fixtures). Size stays small (the repository rule is that committed binary artefacts must be justified and minimal): the scenario writes only tiny tables, fjall directory overhead dominates, and the script fails if the tree exceeds ~1 MiB; the fixture is regenerated, never edited by hand, and the script is its documented generator. The generator must be DETERMINISTIC: a fixed scenario sequence (no wall-clock-derived data, no random ordering), and it records the generating binary version alongside the fixture so a fixture can never silently drift from what produced it — fixture rot is caught because 7.3 re-runs the SAME scenario against a freshly generated directory in CI whenever the script changes (the committed tree and a fresh run must compare equal). If a future fixture still grows past the cap, the fallback is a single compressed archive unpacked by the test — a decision deferred until needed (open question Q5).

### 7.3 What CI runs

An integration test (`crates/server/shamir-server/tests/reference_compat.rs`) that: copies the fixture to a temp dir; runs Inspect checks (stamp state equals the recorded epoch); runs the chain — today "the chain" is empty because `CURRENT == BASE`, so the run asserts the command path returns "nothing to do" and the content is byte-identical; once real epochs exist it runs `format-migrate --yes --i-have-a-backup` against the copy; compares content with the expected tree — the comparison is semantic, not byte-wise (fjall layout is not stable across runs): tables re-read through a freshly opened server fixture, row counts and values per table, index meta present per kind, function rows including signatures, principals/rights/tokens counts and key fields, WAL fully recovered, stamp epoch == `CURRENT` and `last_format_migration` correct. Runs on Linux, macOS and Windows (the journal fsync/rename paths differ per OS; the runner, not the fixture, is what varies). In the first release, with one epoch, the test proves: the fixture is openable by the current binary, the pipeline (fixture → check → compare) works, and the epoch refuses nothing — i.e. the machinery is exercised and green before the first real bump, which is exactly the release-gate wording of README section 5 ("at least one CI-checked path old-epoch → current") instantiated trivially.

## 8. The fallback path (plan 3.8) — boundary only (decision M9)

When a step cannot be written as an in-place module (too expensive, or the old layout is unreadable without the old binary), the fallback is: export with the OLD binary via the logical export of R3, import with the new binary. Consequences fixed here: the export format is versioned on its own axis and changes rarely (plan 3.8); R3's manifest will record the format epoch and the schema version (plan section 5); a directory that can only be moved by R3 gets a change-log entry with `migration_module` pointing at no registry module and the change-log test extended so that such an entry must state the fallback in `reason`. R3 itself is not designed in this document.

## 11. Open questions (each with a default)

* **Q1. Command name.** `format-migrate` vs `format-upgrade`. Default: `format-migrate` (5.1); it matches the refusal messages' "format-migration command".
* **Q2. Integrity check scope.** Reuse of the `doctor` check-only path vs a lighter per-module declared check. Default: reuse the doctor path (4.5); a step may declare a cheaper check later.
* **Q3. Freshness window.** Default: 24 h, operator-overridable via `--max-backup-age-hours` (5.4).
* **Q4. AbsentOlderBase confirmation UX.** Separate flag vs reusing `--yes`. Default: `--yes` plus the backup gate suffice (5.5); the stampless case is logged loudly.
* **Q5. Compatibility fixture packaging.** Plain committed directory tree vs compressed archive. Default: plain tree under `tests/fixtures/` with a ~1 MiB script-enforced cap (7.2); archive only if the cap proves unrealistic.
* **Q6. Journal retention.** Delete the journal after a successful stamp write vs keep it as history. Default: delete on the next successful writer start after completion (4.3, last row); `last_format_migration` in the stamp is the durable history.
* **Q7. Progress output for long steps.** Plan section 8 asks about migration time on large data. Default: per-step start/finish lines only; per-step progress is a later refinement, not a blocker.
* **Q8. Reference fixture per epoch vs rolling.** Keep one fixture per released epoch forever vs prune all but the last two. Default: keep every released epoch (plan 3.7 says "for each released epoch"); revisit when size or CI time forces pruning.
* **Q9. Backup identity proof.** 5.4(b) compares epoch + `created_by` + the top-level name set, which is strong but not mathematical (a same-epoch directory with identical names would pass). Recommended default: keep 5.4(b) for R1b; add a per-directory UUID to the stamp body when R2 online backup lands and switch the gate to UUID equality then.
