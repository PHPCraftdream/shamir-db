### 2.1 Byte math re-derived independently

`RecordId::system(name)` (`crates/shamir-types/src/types/record_id.rs:95-103`) is

Both DDL dispatch sites now mint with real entropy:

  (moved **before** the family dispatch, which is required so the tombstone can carry it).
* `crates/shamir-db/src/shamir_db/execute/admin_table_index.rs:824` — same for RENAME.

`RecordId::new()` = `[0..8]` BE µs-since-custom-epoch + `[8..16]` Xoshiro256++ random
tail (`record_id.rs:41-53`). Genuinely unique.

`ddl_op_log::op_status_key` (`crates/shamir-engine/src/table/ddl_op_log.rs:34-39`) now

(`crates/shamir-storage/src/key_bytes.rs:79`), so the new key is still alloc-free

Key-namespace safety of the new 23-byte shape, checked against every prefix scan that
runs over `info_store`:

* hash postings — `IndexRecordKey::to_prefix_bytes()` is 9 bytes with `bytes[0] ∈ {0,1}`
  (`crates/shamir-index/src/base_index/index_record_key.rs:95-101`); `b'd' = 0x64`. No overlap.
* index2 postings — 4-byte `id.to_le_bytes()` prefix; `b"ddl_"` as LE u32 is
  `1_601_466_468`, and `IndexRegistry::next_id` starts at 1 (`crates/shamir-index/src/registry.rs:151`).
  Unreachable. (Worth noting the *old* key started with the 4 zero bytes of the system
  prefix, i.e. it lived inside `RecordId::system`'s namespace; the move out is safe, not
  a regression.)
* interner delta chunks — `chunk_scan_prefix()` = `[0,0,0,0] ++ CHUNK_TAG_PREFIX`
  (`crates/shamir-engine/src/table/interner_manager.rs:99-104`). No overlap.

### 2.2 End-to-end reproduction of the original defect's *absence*

Reproduced through the public API (scratch crate outside the repo, `ShamirDb::init_memory`
+ `Batch`/`ddl` builder, since deleted; the #1048 review's exact scenario):

```
op_id(DROP idx_city) = 116VtBHsRqvVwBCraKJVB
op_id(DROP idx_zip)  = 116VtBHsfvji7aHqFdupH
identical op_ids for two DIFFERENT DDL ops? false
client A polls its own op_id -> DropHashIndex { index_name: "idx_city" }, Succeeded
client B polls its own op_id -> DropHashIndex { index_name: "idx_zip"  }, Succeeded
op_id(RENAME q->z) = 116VtBHt7zesGrniA33Ys
poll RENAME op                       -> RenameHashIndex { old_name: "q", new_name: "z" }, Succeeded
re-poll DROP idx_city after RENAME   -> DropHashIndex { index_name: "idx_city" }, Succeeded
```

Compare the #1048 review's output on the same scenario (identical op_ids, client A
handed `idx_zip`'s result, then handed the RENAME's `Failed`). **The CRITICAL finding
is closed, cross-kind clobbering included.**

Note the two op_ids share their first **8** base58 characters (`116VtBHs` vs `116VtBHt`).
The pre-fix `op_status_key` retained only 5 base58 characters after `"ddl_op:"` — so both
levels of the original bug were load-bearing and both had to be fixed. They were.

### 2.3 Backward compatibility of the two new tombstone shapes — verified, but unpinned

* hash DROP: `Vec<u64>` → `Vec<(u64, Option<String>)>`
  (`crates/shamir-index/src/base_index/index_manager.rs:653-753`)
* index2 DROP: `Vec<u32>` → `Vec<(u32, String, Option<String>)>`
  (`crates/shamir-index/src/persistence.rs:312-384`)

Both load paths try the new shape first and fall back to the old on `Err`. I checked the
decode-ambiguity question two ways.

*By construction*: with bincode 1.3's fixint encoding, the new hash entry costs ≥ 9 bytes
(8 + 1 Option tag) against the old's 8, and the new index2 entry costs ≥ 13 bytes
(4 + 8 string-len + 1 tag) against the old's 4. Decoding N old entries as the new shape
therefore always runs out of input — the ambiguity can only ever fail *closed*, into the
fallback. The N = 0 case encodes identically in both shapes (8 zero bytes) and decodes to
the same empty vec either way.

*Empirically* (scratch crate, bincode 1.3.3, since deleted): length sweeps N ∈ [0,14) ×
adversarial base values, plus exhaustive small-value sweeps (hash: all 3-tuples over
[0,4); index2: all 4-tuples over [0,6)) — **0 misdecodes, 0 errors**. The claim in the
commit message and CHANGELOG is true.

It is, however, entirely untested inside the repo — see finding 3.

## 4. Findings

### 1. HIGH — the three "hand-fixed" op_id tests re-introduce the tautology, against the precise regression #1051 removes

`crates/shamir-engine/src/table/tests/p1048_hash_drop_durability_tests.rs:83`, `:193`
`crates/shamir-engine/src/table/tests/p1048_index2_drop_durability_tests.rs:114`

```rust
// p1048_hash_drop_durability_tests.rs:82-83
let index_name = "by_email";
let op_id = RecordId::system(&format!("ddl_drop_index_{}", index_name));
```

The commit message says these three sites were "fixed by hand" after the blind `, None`
sweep defeated them. They were fixed *only in the argument they pass* — the **value** they
pass is still produced by `RecordId::system(&format!("ddl_drop_index_{name}"))`, the
formula this commit deleted from production precisely because it is degenerate.

**Failure scenario (test-blindness).** Revert `write_hash_drop_recovery_status`
(`table_manager_index_mgmt.rs:1124-1200`) and `write_index2_drop_recovery_status`
(`:1287-1320`) to the pre-#1051 behaviour — ignore `op_id_str` from the tombstone and
recompute `RecordId::system(&format!("ddl_drop_index_{name}"))`. All three tests still
pass, because the value they poll under is byte-identical to the recomputed one. The
tombstone-carries-the-op_id mechanism — the single largest piece of this commit — is not
pinned by any of the three tests that exist to pin it. Worse, because
`RecordId::system("ddl_drop_index_by_email") == RecordId::system("ddl_drop_index_uniq_email")`,
the value is *also* the same constant in both hash tests, so the assertion is insensitive
to the index name as well.

The brief's DoD item 7 — "All four #1048 recovery tests' `status.op_id == op_id` assertion
is now genuinely discriminating (two ops on one table, cross-check)" — is **unmet**. The
delivery substituted a new standalone test (which is good, and which does discriminate)
for rewriting the four, and did not declare the substitution.

Consequential documentation drift in the same two files: the module docs and step-2
comments still read "under the SAME **deterministic** op_id the client received at
dispatch time" (`p1048_hash_drop_durability_tests.rs:5`, `:49`, `:53`, `:81`;
`p1048_index2_drop_durability_tests.rs:5`, `:74`, `:79`, `:112`). Post-#1051 the op_id is
not deterministic and is not regenerated; a reader following these comments would
reconstruct the deleted design.

Fix direction: mint `RecordId::new()` in all three tests (matching what production now
does), and add a `status.kind` assertion so the record's identity — not just its presence
— is checked.

### 3. MEDIUM — the advertised tombstone backward compatibility has no test

`crates/shamir-index/src/base_index/index_manager.rs:686-716`, `:723-753`
`crates/shamir-index/src/persistence.rs:324-355`

The commit message ("Backward compatible: old-format tombstones without the op_id field
still deserialize, treated as `op_id: None`") and the CHANGELOG both advertise this. The
brief's Tests section asked for it explicitly ("Update or add a backward-compat test for
whatever decision you made in step 2"). `grep -rn "1051" crates/ --include=*.rs` shows no
test file other than `p1051_op_id_uniqueness_tests.rs`, which does not exercise either
load path.

I verified the behaviour holds today (§2.3). The concern is that its correctness rests
entirely on an invisible **byte-count** argument — new-shape entries must consume strictly
more bytes than old-shape ones, so the new-first decode attempt always fails cleanly on
old data.

**Failure scenario.** A future change makes the new shape decodable from old bytes — e.g.
index2's `String` name is dropped again, or `Option<String>` becomes a bare `u128`, or the
tuple is swapped for a struct with `#[serde(default)]` fields. An old `Vec<u32>` tombstone
then decodes as the *new* shape with garbage ids, `remove_by_id`/`sweep_index2_postings_by_id`
run against ids that were never dropped (sweeping live postings), and the tombstone is
cleared as if recovered. Zero test signal. Two ~15-line tests (seed
`bincode::serialize(&vec![1u64, 2u64])` under `system:idx_drop`, assert
`load_dropping_set(false)` returns `[(1, None), (2, None)]`; same for `Vec<u32>` under
`system:_m.idx.drop`) close it.

`crates/shamir-engine/src/table/table_manager_index_mgmt.rs:986`, `:1291-1305`

### 5. LOW — an unparseable op_id string in a tombstone makes the first reopen of the table fail outright

`crates/shamir-engine/src/table/table_manager_index_mgmt.rs:1129-1133`, `:1163-1167`, `:1291-1295`
`crates/shamir-engine/src/table/table_manager.rs:433-441`, `:655-663`

```rust
let op_id = std::str::FromStr::from_str(op_id_str).map_err(|e| {
    shamir_storage::error::DbError::Codec(format!("#1051: failed to parse op_id '{op_id_str}': {e}"))
})?;
```

The `?` propagates out of `write_hash_drop_recovery_status` / `write_index2_drop_recovery_status`,
which `TableManager::create` maps to `DbError::Internal` and returns. A corrupt op_id string
in a tombstone therefore fails the whole table open — even though the actual index recovery
has already completed successfully at that point. This is inconsistent with the sibling
failure mode three lines below, where a failed `write_op_status` is only `log::error!`d and
execution continues; a cosmetic status-log value is treated as more fatal than the status
write itself.

**Failure scenario.** A torn/bit-flipped `system:idx_drop` blob whose bincode still decodes
but whose op_id string is not valid base58. `TableManager::create` returns `Err`; the table
is unopenable. Self-healing in practice — the tombstone is durably cleared by
`IndexManager::new` / `recover_index2_drops` *before* the status write, so the second open
succeeds — but the operator sees one hard, unexplained open failure with no indication that
retrying will work. `log::error!` + `continue` matches the surrounding best-effort contract.
