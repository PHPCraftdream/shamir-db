## 2. Verdict on production-code correctness

**The mechanical work in the diff is correct. The feature it implements does not
work.**

What is correct:

* The `tokio::spawn` fire-and-forget race from round 2 is genuinely gone — both
  `write_hash_drop_recovery_status` and `write_index2_drop_recovery_status` are
  awaited inline inside `TableManager::create`, so a client polling immediately
  after restart cannot observe `Unknown`.
* `op_id` threading into `HashRenameTombstone` (both the create-first and the
  barrier-held construction sites) is real and correct; `RecordId` is `Copy`, so the
  `Some(op_id)` pass at `admin_table_index.rs:830` followed by reuse at `:850`/`:873`
  is sound. The dispatch-side reorder (mint before the call instead of after) is
  required and correct.
* The `op_id.to_string()` / `RecordId::from_str` round-trip through the tombstone is
  lossless (`Display` = base58 of all 16 bytes, `FromStr` = `decode16`).
* The `#967` structured `Failed { detail }` writes sit on exactly the two branches
  that have `op_id` in scope, and they are additive (the `Err` return is preserved).
* `DdlOpKind` selection on the recovery side matches the dispatch side for all four
  cases (regular → `DropHashIndex`, unique → `DropUniqueHashIndex`, index2 →
  `DropIndex2`, renames → `Rename{,Unique}HashIndex`).
* Scope is clean: every file outside the five production files is a pure
  call-site update for the new `rename_index` arity (`, None`) plus the `tests/mod.rs`
  manifest. **No out-of-scope production edits ride along.**

What is not correct — see finding 1. The `op_id` values this whole feature keys on
are not unique, and the storage key they are written under is not unique either. The
result is one op-status slot per table, shared by every DDL operation ever executed
against it. The threading, the deterministic regeneration, and the recovery writes are
all individually well-built on top of a foundation that collapses them into a single
overwritten record.

## 3. Verdict on test genuineness

**Partly genuine, with one tautological core assertion repeated in all four new
recovery tests.**

Genuine and load-bearing:

* `p1048_e2e_index2_drop_op_id_recovery` — real crash simulation via
  `set_drop_index2_post_sweep_hook` + `tokio::select!` cancellation, a real
  precondition check (postings present before DROP), a real panic-arm if the drop
  completes instead of parking, and a real post-restart assertion that the index2 is
  gone. Removing the production `write_index2_drop_recovery_status` call would fail
  it at `status.is_some()`.
* `p967_rename_hash_index_failure_writes_structured_error` /
  `..._unique_...` — the fault-injection rewrite is correct and non-trivial. Arming
  the one-shot fault *after* `wait_until_parked()` lands it precisely inside
  `drop_index(old_id)` (regular) / `create_unique_index_body` (unique), i.e. on the
  exact branch the `Failed { detail }` write lives on. The one-shot (`swap(false)`)
  arming is necessary and correctly reasoned about in the file's own doc comment —
  a sticky fault would also kill the status write it is trying to observe. The
  assertions check the structured variant, the enriched text, the injected cause
  string, and the `DdlOpKind` — not merely "an error happened". These are the best
  tests in the delivery.
* `p1048_e2e_unique_rename_severe_case_op_id_threading` — the tombstone assertion
  `tombstone.op_id == Some(op_id.to_string())` **is** discriminating: it would fail
  against the pre-#1048 hard-coded `op_id: None`.
* `p1048_backward_compat_none_op_id_recovers_cleanly` — genuine; seeds a `None`-op_id
  tombstone and proves recovery completes without erroring and without writing status.

Not genuine:

* The read-back assertion `assert_eq!(status.op_id, op_id)` — present in all four
  recovery tests — is **vacuous**, for the reason in finding 1: every
  `RecordId::system("ddl_drop_index_<anything>")` is the same value, and the
  `ddl_op_log` key derived from it is the same key for every DDL op. The assertion
  would hold if recovery had written the status for a completely different index, of
  a completely different family, on a completely different operation. These tests
  therefore verify "*a* `SucceededViaCrashRecovery` record was written to this
  table's single op-status slot", not "the record is retrievable under *the client's*
  op_id" — which is the entire proposition #1048 exists to establish.

No race or parallelism hazard found in the new tests: `BackfillPauseHook` uses
`Notify::notify_one()` (permit-storing, so `wait_until_parked()` cannot miss an
early arrival), the parked task performs no `Store::set` between announcing and
parking, and nothing else touches `info_store` during the armed window. Five
consecutive runs were clean.

## 4. Findings

### 1. CRITICAL — every DDL `op_id` on a table collapses to the same value, and every op-status record to the same storage key

`crates/shamir-types/src/types/record_id.rs:95`
`crates/shamir-engine/src/table/ddl_op_log.rs:32`
`crates/shamir-db/src/shamir_db/execute/admin_table_index.rs:696`, `:824`
`crates/shamir-engine/src/table/table_manager_index_mgmt.rs:1114`, `:1145`, `:1272`

`RecordId::system(name)` copies at most **12 bytes** of `name` into `bytes[4..16]`:

```rust
let len_to_copy = std::cmp::min(name_bytes.len(), 12);
bytes[4..4 + len_to_copy].copy_from_slice(&name_bytes[..len_to_copy]);
```

`"ddl_drop_index_"` is 15 characters and `"ddl_rename_index_"` is 17 — **the index
name never enters the id at all.** Every DROP INDEX op on every table mints the same
`op_id`; every RENAME INDEX op mints the same (different) one.

It compounds one level further: `ddl_op_log::op_status_key` re-wraps the op_id through
`RecordId::system(format!("ddl_op:{op_id}"))`. `"ddl_op:"` is 7 chars, leaving 5 chars
of the base58 string — and every system `RecordId` base58-encodes with a leading
`"1111"`, so the surviving prefix is `"ddl_op:11112"` for *all* of them. DROP and
RENAME records therefore land on the **same physical key** despite having different
op_ids.

Reproduced end-to-end through the public API (scratch crate outside the repo,
now deleted; `ShamirDb::init_memory` + `Batch`/`ddl` builder, two DROP INDEX ops on
one table):

```
op_id(DROP idx_city) = 11112tt4VUv265bVat1BR
op_id(DROP idx_zip)  = 11112tt4VUv265bVat1BR
identical op_ids for two DIFFERENT DDL ops? true
client A polls its own op_id -> kind = DropHashIndex { index_name: "idx_zip" }
```

And at the `ddl_op_log` layer, cross-kind clobbering:

```
op_id(DROP alpha) == op_id(RENAME q->z) ? false
status_key collision (different op_ids, same storage key) ? true
client-1 polled op_id for DROP alpha, server returned:
  kind  = RenameHashIndex { old_name: "q", new_name: "z" }
  state = Failed { detail: "rename blew up" }
```

**Failure scenario.** Client A issues `DROP INDEX idx_city` on `main/items`; it
succeeds and A is handed op_id `11112tt4VUv265bVat1BR`. Client B then issues
`DROP INDEX idx_zip` on the same table, which crashes mid-flight; on restart #1048's
recovery writes `SucceededViaCrashRecovery` for `idx_zip` — to the same key. A polls
`GetDdlOpStatus` with its own op_id and is told its `idx_city` drop
"SucceededViaCrashRecovery", with `kind.index_name == "idx_zip"`. Swap the second op
for a failing RENAME and A is told its successful DROP `Failed { detail: "…" }`.
Retention is also degenerate: the `DDL_OP_LOG_CAP = 10000` FIFO cap is meaningless
because the log physically holds one record per table.

The root cause predates `f40ab4fd` (the minting formula and the key derivation are
#1015/#1025 code). But #1048's entire premise — "under the SAME op_id it received at
dispatch" — is unachievable while it stands, and #1048's own tests pass *because* of
it. This is the single reason #1048 cannot be treated as delivering its stated value.

Fix direction (not applied): make the op_id carry entropy or a hash rather than a
truncated literal prefix (e.g. `RecordId::new()` at dispatch, persisted in the
tombstone, exactly as the RENAME family already does — which would also remove the
need for the "deterministic regeneration" mechanism entirely), and make
`op_status_key` derive from the op_id's 16 raw bytes rather than from a re-truncated
`RecordId::system` of its base58 text.

### 2. HIGH — the op_id identity assertion in all four new recovery tests is tautological

`crates/shamir-engine/src/table/tests/p1048_hash_drop_durability_tests.rs:141`, `:254`
`crates/shamir-engine/src/table/tests/p1048_index2_drop_durability_tests.rs:201`
`crates/shamir-engine/src/table/tests/p997_hash_rename_durability_tests.rs:1066`

Direct consequence of finding 1. `assert_eq!(status.op_id, op_id)` cannot fail for
any index name, because both sides are computed from the same name-independent
constant. Equally, `read_op_status(&info_store, &op_id)` in these tests is really
"read this table's only op-status record".

**Failure scenario (test-blindness).** Change
`write_hash_drop_recovery_status`'s op_id line to
`RecordId::system(&format!("ddl_drop_index_{}", "WRONG_NAME"))` and every one of these
tests still passes. Change it to `DropUniqueHashIndex` for the regular family and
they still pass (nothing asserts `status.kind`). The tests are non-vacuous on
"*a* recovery status write happened" and vacuous on "it is addressable by the
client's op_id" — which is the requirement.

A discriminating version would need two DDL ops in one table and an assertion that
polling op A does not return op B's record. That test does not exist and would fail
today.

### 3. MEDIUM — index2 `SucceededViaCrashRecovery` is written *before* the recovery it attests to runs

`crates/shamir-engine/src/table/table_manager.rs:649-668`

```rust
if !dropping_index2_before.is_empty() {
    TableManager::write_index2_drop_recovery_status(...).await.map_err(...)?;   // :655
}
mgr.recover_index2_drops().await?;                                             // :668
```

The status claiming the drop "succeeded via crash recovery" is durably persisted
before `recover_index2_drops` has removed the backend, swept the postings, persisted
the reduced metadata, or cleared the tombstone. The hash family does this the right
way round (the write at `:429` runs *after* `IndexManager::new`, which performs
`recover_in_progress_drops` internally) — the two paths are inconsistent for no
stated reason. Nothing forces this ordering: `dropping_index2_before` is read at
`:645` and the write could equally follow `:668`.

**Failure scenario.** `sweep_index2_postings_by_id` returns a transient
`DbError::Storage` for one of the tombstoned ids. `TableManager::create` returns
`Err` (fail-closed, #1013) — but the store now permanently contains
`SucceededViaCrashRecovery` for every id in the tombstone, including the one whose
sweep failed. The table is unopenable, so the lie is not immediately pollable; once
an operator repairs the underlying store and reopens, the log has been asserting
success for a drop that had not happened for the whole intervening window, and any
out-of-band reader of the info-store (doctor, backup inspection, a future
op-log-export tool) sees it. Low blast radius today, but it is a durable false
claim of completion, written by design rather than by accident.

### 4. MEDIUM — index2 recovery silently writes no status in one of the three documented crash windows, and the code comment misdiagnoses why

`crates/shamir-engine/src/table/table_manager_index_mgmt.rs:1291-1300`

```rust
} else {
    // Name not found in persisted descriptors — this can happen if the crash
    // occurred before the descriptor was persisted (during CREATE, not DROP).
    log::warn!(...);
}
```

The stated cause is not the real one. `recover_index2_drops`'s own crash-state matrix
(`table_manager_index_mgmt.rs:1188-1191`) documents row 3 explicitly:

| crash point | registry has backend? | postings? | tombstone? |
|---|---|---|---|
| after persist, before clear | **no (not in persisted)** | gone | yes |

`drop_index2` persists the reduced metadata at `:1060` and clears the tombstone at
`:1075`. A crash in that window leaves the tombstone on disk with the descriptor
already *removed* from persisted metadata — so `id_to_name.get(&id)` returns `None`,
and #1048 logs a warning and writes nothing. The client polls `Unknown` forever:
precisely the defect #1048 was created to close, still open for one of the three
windows the design itself enumerates.

**Failure scenario.** `DROP INDEX lower_name` (index2). Process is killed between
`save_index2_metadata` and `clear_from_dropping_index2`. On restart
`recover_index2_drops` correctly finishes the drop (sweep no-op + tombstone clear),
but no `SucceededViaCrashRecovery` is written. A client polling
`GetDdlOpStatus` for that op sees `Unknown` indefinitely.

The hash family does not have this gap, because it resolves names through the
**interner** (which retains the name independently of `IndexInfo`), not through the
metadata blob the drop removes. The asymmetry is undocumented. A fix would capture
the id→name mapping from `dropping_index2_before` against the *pre-drop* descriptor
set, or store the name in the tombstone (which is what "thread the op_id into the
tombstone" would have achieved).

### 5. LOW — both tombstone pre-loads swallow real read errors with `unwrap_or_default()`

`crates/shamir-engine/src/table/table_manager.rs:407`, `:414`, `:647`

`load_dropping_set_standalone(...).await.unwrap_or_default()` and
`load_dropping_index2(...).await.unwrap_or_default()` map a `DbError::Codec`
(corrupt tombstone) or a transient `DbError::Storage` to "no in-progress drops", so
the status write is skipped with no log line at all. In the corrupt case the
subsequent real recovery load will error and fail the open, so the swallow is
masked; in the transient case the second load may succeed, recovery completes, and
the status write is silently lost. Given the write is already best-effort per-entry,
at minimum this deserves a `log::warn!` on the `Err` arm rather than `unwrap_or_default`.

## 6. Verdict

**NO-GO** for treating #1048 as done, on the strength of finding 1 alone: the
op_id it threads is not unique, and the key it writes under is not unique, so the
client-facing contract the whole slice exists to deliver ("poll `GetDdlOpStatus`
under the op_id you were handed and see `SucceededViaCrashRecovery`") is not
achievable in any table that has seen more than one DDL operation. This is
demonstrable end-to-end through the public API, not a theoretical concern. The
mechanical work in the commit is otherwise sound and the delivery is genuinely
green — but the two remaining correctness gaps (findings 3 and 4) plus the fact
that finding 1 makes the new tests' central assertion tautological (finding 2)
mean the slice should stay open, or a follow-up task should be filed for the
op_id-uniqueness fix and #1048 re-verified against a test that discriminates
between two concurrent DDL ops on one table.
