# shamir-bench-utils -- Performance & O(x->0)

## Summary

The crate is a thin bench-helper (two modules: `vector_data` fixture generation, `peak_mem` RSS sampling) with no production hot path, so the O(x->0) exposure is confined to fixture-generation cost and the fidelity of the perf measurements this crate produces. The one substantive theme hit is the fixture generator's per-point `Vec` allocation (allocation-in-loop: n+1 heap allocations per call), which at the 1M-point bench rung inflates setup churn and pollutes the RSS footprints the V0.4 report tool publishes. Secondary: the `peak_mem` global reset-watermark API silently corrupts readings if two `measure` calls overlap (current consumers are sequential, so live numbers are sound), and the module docs still teach the removed Criterion integration. No hidden O(N^2) algorithms, no unbounded growth/buffering found.

## Findings

### 1. Fixture generator allocates one heap `Vec` per point (allocation-in-loop, n+1 allocations per call)

- **File:line:** `crates/shamir-bench-utils/src/vector_data.rs:199-207` (loop), `:115` (`ClusteredDataset::vectors: Vec<Vec<f32>>`)
- **Severity:** medium
- **Issue:** `clustered_vectors` builds the dataset as `Vec<Vec<f32>>`, allocating `Vec::with_capacity(dim)` inside the per-point loop — exactly the "allocation in loops" shape pillar 3 bans in helpers. Every call pays n separate heap allocations (plus the outer one), 24-byte per-`Vec` headers, allocator rounding, and heap fragmentation; the flat payload is scattered across the heap.
- **Failure scenario:** `benches/vector_search.rs:93` runs an optional n = 1_000_000 rung (`BENCH_VECTOR_1M`) at dim up to 768 — 1M allocations and ~24-40 B/vector of pure metadata overhead (≈8% of the payload at dim=128) before any index bytes. `examples/vector_report.rs` publishes RSS footprints computed over this structure, so the reported per-dataset memory overstates actual vector bytes and varies with allocator behaviour, weakening the OLD-vs-NEW comparability the tool exists for. Locality of consumers that iterate the cloud (brute-force ground truth, and `benches/vector_search.rs:121-126` which re-`clone`s every boxed row into a second boxed batch — each point copied twice, twice fragmented) is also degraded. Setup-only, so timed latencies are unaffected; the skew lands in memory reports and wall-clock setup.
- **Suggested fix:** Store a flat `Vec<f32>` slab of `n * dim` in `ClusteredDataset` with `row(i) -> &[f32]` accessors. Generation order is already row-major, so the LCG call sequence is unchanged and `(n, dim, k, σ, seed)` fixtures stay byte-identical (the crate's own determinism guarantee — add a `same_seed_is_byte_identical` assertion against the current layout to pin it). Keep the boxed-rows shape available as an explicit `to_vec_rows()` for consumers that need owned rows, so HNSW-ingestion call sites opt into the copy instead of getting it for free. The inline tests cover determinism/shape/clustering well but nothing pins the allocation profile; the flat slab makes the n-allocations-per-call property structurally impossible to regress.

### 2. `peak_mem::measure`/`measure_async` reset a single global watermark — overlapping use silently corrupts readings, and the sync variant omits the warning

- **File:line:** `crates/shamir-bench-utils/src/peak_mem.rs:57-59` (`reset`), `:85-93` (`measure`), `:102-110` (`measure_async`, caveat only at `:98-101`)
- **Severity:** low
- **Issue:** Peak tracking is one process-global counter; `reset()` clobbers it for the entire process and `measure`/`measure_async` are free functions with no ownership of the window between reset and read. `measure_async` documents that a multi-threaded executor interleaves foreign allocations into the peak; the sync `measure` doc says nothing, and neither variant detects or prevents a second concurrent caller whose `reset()` erases the first caller's in-flight peak.
- **Failure scenario:** A future bench calls `measure` from two worker tasks (or drops `measure_async` into the workspace's multi-threaded `bench_batched_async` pattern instead of the sequential `current_thread` shape the two live consumers use — `benches/streaming_topk.rs:114-119`, `benches/create_index_streaming.rs:179-187`): the later reset discards the earlier sample (silent underreport) and concurrent traffic inflates both peaks (silent overreport). The number is published as a heap-watermark with no error — precisely the kind of measurement artifact the F-78/F-53a reports are built on. Today's consumers are sequential on `current_thread` runtimes, so current readings are sound; this is a trap for the next consumer, not a live defect.
- **Suggested fix:** At minimum, copy the async caveat onto `measure` and state "not safe for concurrent use" on both. Better: make the window claimable — a process-wide `AtomicBool` guard where `measure`/`measure_async` CAS-claim the sampler for the window and return `None` (or panic) on an already-claimed sampler, turning silent corruption into a visible error. Note in the docs that `reset()`/`current_peak()` called manually (the pattern both live benches use) carries the same single-global-window constraint.

### 3. `peak_mem` module docs teach the removed Criterion integration; `vector_data` header still cites the "criterion bench"

- **File:line:** `crates/shamir-bench-utils/src/peak_mem.rs:10-30` ("Usage with Criterion `iter_custom`", `Duration::from_nanos` custom-measurement trick), `crates/shamir-bench-utils/src/vector_data.rs:3-4` ("criterion bench (V0.3, `benches/vector_search.rs`)")
- **Severity:** nit
- **Issue:** The workspace migrated off Criterion on 2026-07-07 (CLAUDE.md, "Bench cache isolation": no `criterion_group!`/`criterion_main!`, "do NOT reach for Criterion APIs"); benches use `bench_scale_tool::Harness`. The only documented integration path for this crate's peak-RSS sampler is a Criterion `iter_custom` closure that no longer has a home, so the module's how-to is orphaned.
- **Failure scenario:** A bench author copies the module-doc example, reaches for Criterion APIs that no longer apply per CLAUDE.md, or wires `measure` into a harness whose measured region doesn't match the reset window — producing numbers attributed to the wrong region. Documentation-only; no runtime cost.
- **Suggested fix:** Rewrite the `peak_mem` module example in the `bench_scale_tool::Harness` idiom the two live consumers already use (`setup()` once at top of `main`; `reset()` immediately before the cell; `current_peak()` immediately after), and drop the "criterion" wording from `vector_data.rs`'s header (it should reference `benches/vector_search.rs` on the Harness directly).
