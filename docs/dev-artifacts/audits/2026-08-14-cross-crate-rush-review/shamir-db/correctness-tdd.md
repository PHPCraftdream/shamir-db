# shamir-db -- Correctness & TDD-coverage

## Summary

The facade is large but internally disciplined: the Red/Green/Refactor convention is visibly honoured (e.g. `group_member_toctou_concurrent_mutations_lose_no_update` is a real barrier-synchronised race regression with a deterministic post-fix assertion; `coverage_matrix_tests` honestly pins *currently unenforced* ACL cells so a future fix turns the test red; #995 auth-before-existence is applied uniformly and commented per site). The findings below are concentrated in three families: (1) cross-object identity confusion and absent-record fallthroughs that silently fabricate or mutate the wrong catalogue entry, (2) a durability-policy inconsistency inside `SystemStore` where one DDL family skips the flush every other DDL write performs -- with a test comment asserting the opposite of the code, and (3) remove-before-save re-key orderings in rename paths that contradict the crate's own write-before-remove crash-safety convention. None of the vacuous-test pathologies (tautological asserts, tests that only exercise happy paths they themselves stub out) were found; the gaps are missing tests for specific reachable edge cases listed per finding.

## Findings

### 1. `DROP DATABASE ... CASCADE` executed against a different database destroys the *batch's* database's tables
- **File:line:** `src/shamir_db/execute/admin_db_repo.rs:126-141` (wrong arg at line 133); cf. `src/shamir_db/shamir_db/table_management.rs:118-137`
- **Severity:** high
- **Issue:** In `handle_drop_db`'s cascade loop, `repos`/`repo_name`/`tables`/`table_name` are enumerated from `db = self.shamir.get_db(&op.drop_db)`, but the table drop is invoked as `drop_table_cleaning_validators(&self.db_name, repo_name, table_name)` -- the first argument is the database the *batch* targets (`ShamirAdminExecutor::db_name`), not `op.drop_db`. Nothing ties `op.drop_db` to `self.db_name`: admin ops carry no `table_ref`, so a `DropDb("B")` op inside a batch executed on database "A" is authorized against "B" (correct) but then executed against "A" (wrong).
- **Failure scenario:** Admin runs `execute("A", batch{ drop_db("B", cascade=true) })` where B has repo `main`/table `items` and A also has repo `main`/table `items`. The cascade path calls `drop_table_cleaning_validators("A", "main", "items")`: (a) `validators.unbind_all_for_table("A/main/items")` unbinds A's *live* validator bindings and persists the stripped `bound_in` onto A's validators; (b) A's `items` table is dropped for real; (c) `remove_table("A","main","items")` deletes A's catalogue row. Then `remove_repo("B", ...)` removes B's repos. Net: the wrong database's data/catalogue/validator fabric is damaged while errors are swallowed by `let _ =` on every iteration.
- **Suggested fix:** Pass `&op.drop_db` as the db argument (or reject `op.drop_db != self.db_name` with a typed error, mirroring how other ops are scoped). Also drop the `let _ =` swallowing so a failed cascade step fails the op instead of silently proceeding to `remove_repo`.

### 2. `remove_group_member` on a nonexistent group *creates* a phantom group record (and the wire remove path lacks the existence guard the add path has)
- **File:line:** `src/shamir_db/system_store.rs:742-762` (also `add_group_member`, 712-734); wire gap at `src/shamir_db/execute/admin_access.rs:454-489` (guard exists only on the add path, lines 390-395)
- **Severity:** high
- **Issue:** `SystemStore::remove_group_member` uses `unwrap_or_default()` for members/name and `unwrap_or(Actor::System)` for owner when `load_group` returns `None`, then unconditionally calls `save_group`. A remove against a missing group therefore **writes** a record with empty `name`, empty `members`, owner System. The dispatcher `handle_add_group_member` explicitly guards this ("system_store::add_group_member would silently fabricate a phantom group record") via `group_id_exists`, but `handle_remove_group_member` performs only `resolve_group_id` (which passes `GroupRef::Id` through unchecked) + `authorize_group_manage_or_root` (which short-circuits `Ok` for Root-Manage actors *before* any existence check) -- no `group_id_exists` call. The test file even asserts the wrong invariant: `admin_access_validation_tests.rs:479-486` claims for remove that "Nothing is created or written that didn't already (potentially) exist", and the only remove test (`remove_group_member_nonexistent_user_is_harmless_noop`, line 570) removes a non-member *user* from an *existing* group -- the nonexistent-*group* case is untested.
- **Failure scenario:** `REMOVE GROUP MEMBER (group = Id{999_999}, user = 1)` via wire (System/admin actor) on an empty store returns `Ok` and silently fabricates group id 999999 with name `""`. `group_id_exists(999999)` is now true; the ghost id occupies the counter namespace, shows up as an unnamed group in `access_tree`, and cannot be addressed by name.
- **Suggested fix:** Make `SystemStore::add_group_member`/`remove_group_member` return `DbError::NotFound` when the record is absent (mirroring `set_group_owner`, which already does), and/or add the same `group_id_exists` guard to `handle_remove_group_member`. Add the Red test: remove-from-nonexistent-group must not create a row (`load_group(gid).is_none()` afterwards).

### 3. `save_database` / `remove_database` (and all replication-catalogue writes) skip the "Durable DDL" flush; a test comment asserts they don't skip it
- **File:line:** `src/shamir_db/system_store.rs:187-207` (`save_database`), `210-223` (`remove_database`); `src/shamir_db/execute/admin_replication.rs:87-101`, `168-182`, `278-292`, `393-407` (repl writes call `interner().persist()` but never `data_store().flush()`); wrong comment at `tests/rename_db_e2e.rs:309-314`
- **Severity:** medium
- **Issue:** Every other system-catalogue write in this file (`save_repository`, `remove_repository`, `save_table`, `remove_table`, `save_function`, `save_validator`, `save_group`, folders) ends with `table.data_store().flush().await` under the standing comment "Durable DDL -- ... a crash right after the admin op can't lose (or, for removes, resurrect) the catalogue entry". `save_database`/`remove_database` and all replication handlers stop at `interner().persist()` with no flush. The flush-intent is real, not decorative: `tests/rename_db_e2e.rs:312` states "save_database/save_repository/save_table_meta already call data_store().flush() internally" -- which is false for `save_database` -- and the test only survives reopen because it additionally calls `flush_all()` by hand before drop.
- **Failure scenario:** `DROP DATABASE x` (or `CREATE PUBLICATION`) followed by a crash inside the MemBuffer flush window (~500 ms, the exact window `flush_all`'s doc names) can resurrect the dropped database row on next boot (boot registers a `DbInstance` for every persisted `databases` record) or lose the replication definition, with no error anywhere.
- **Suggested fix:** Add the `data_store().flush()` (or route through `set_via_implicit_tx` + flush helper) to `save_database`, `remove_database`, `save_database_meta`, and the four replication write handlers; correct the `rename_db_e2e.rs` comment; ideally add a TDD test that opens/crash-simulates without an explicit `flush_all` and asserts the catalogue state.

### 4. Boot silently skips repository rows whose database row is missing -- no warning, data invisible forever
- **File:line:** `src/shamir_db/shamir_db/core.rs:210-219` (`if let Some(db) = shamir.get_db(db_name) { ... }` with no `else`)
- **Severity:** medium
- **Issue:** `init` loads `databases` rows first and registers a `DbInstance` per row; the subsequent `repositories` loop re-attaches each repo **only if** `get_db(db_name)` succeeds. A repo catalogue row whose `(db)` row is absent (crash between `save_repository` and `save_database`; `remove_database`'s unflushed delete per finding 3 resurrecting only the db row in the opposite direction; manual catalogue surgery) is skipped in total silence. The adjacent `add_repo`-failure branch (lines 243-252) does log a `warn!` -- the missing-db branch logs nothing.
- **Failure scenario:** A durable fjall repo with committed WAL data exists on disk and in `repositories`, but its db row was lost; every restart skips it without a line in the log. The operator sees "my database came back empty" with zero diagnostics, and a later `create_db` of the same name does *not* re-attach the orphaned repo (repos are only re-attached at boot).
- **Suggested fix:** `else { log::warn!("skipping orphan repo row '{db}/{repo}': database row missing") }`, matching the fail-loud convention used for native artifacts (`unresolved_native_artifacts`). Consider a `recover_orphans` helper that re-registers a missing db shell from the repo rows.

### 5. Boot "skipping" a builtin-name-colliding function row still overwrites its `function_meta`, and the live artifact diverges from the catalogue after restart
- **File:line:** `src/shamir_db/shamir_db/core.rs:318-333` (register-failure branch at 324-329, unconditional meta insert at 331-332)
- **Severity:** medium
- **Issue:** At boot, builtins are registered first (`FunctionRegistry::with_builtins()`), then catalogue rows are loaded. For a catalogue row whose `name` equals a builtin (creatable pre-restart via `create_function_with_opts_as` with `replace = true`, which *does* overwrite the builtin in the live registry), `functions.register(...)` fails, the log says "skipping catalogue load" -- but `function_meta.insert(name, from_record(rec))` runs anyway. After restart the registry serves the **builtin** artifact while `function_meta` (secret_grants/net_grants) and `effective_fn_actor`'s catalogue read (SECURITY DEFINER / setuid escalation to the *record's* owner) come from the **user's** row. Pre-restart, the same invocation ran the user's WASM.
- **Failure scenario:** `CREATE OR REPLACE FUNCTION argon2id ... SECURITY DEFINER` works and runs the replacement; after a restart, invocations of `argon2id` silently execute the builtin again, but escalated to the definer owner and with the replaced row's net/secret grants -- a quiet behavioural divergence that no test covers (no test creates a builtin-colliding row and re-opens).
- **Suggested fix:** On register failure, `continue` before touching `function_meta` (make the log line true), and surface the collision in `unresolved_native_artifacts`-style diagnostics. Longer term, make the boot loop honour `replace` semantics consistently with the create path.

### 6. `rename_function_as` / `rename_validator_as` re-key the catalogue remove-first, contrary to the crate's write-before-remove crash-safety convention
- **File:line:** `src/shamir_db/shamir_db/function_management.rs:335-347`; `src/shamir_db/shamir_db/validator_management.rs:373-385`
- **Severity:** medium
- **Issue:** Both renames do `remove_function(from)` / `remove_validator(from)` **then** `save_* (to, ...)`. Every db/repo/table rename in this crate deliberately does the opposite (`rename_db_as` "write-new-before-remove-old", `rename_repo_as` step 2, `rename_table_as` step 2 -- each with a crash-window comment). Here a crash (or a `save_*` error) after the remove has deleted the only durable copy of the artifact's row; the live registry entry still works until restart, then the function/validator is gone permanently. Additionally the live registry is renamed *before* the catalogue, so a catalogue error leaves registry=`to`, catalogue=`from` (resurrects under the old name on next boot).
- **Failure scenario:** `RENAME FUNCTION f TO g` where the `save_function(g)` write hits a transient store error: the wire returns an error, but `f` is already deleted from the catalogue; after restart `f` and `g` are both absent while the client believes the rename simply failed. No test exercises failure injection on the save half of a rename.
- **Suggested fix:** Reorder to save-new-then-remove-old (copying the `rename_table_as` pattern), and add a fault-injecting `Store` test (the `futures`/`#540` fault-injection seam already exists in dev-dependencies) asserting the catalogue retains `from` when the `to` write fails.

### 7. `create_db_as` / `create_db` silently overwrite an existing live `DbInstance`
- **File:line:** `src/shamir_db/shamir_db/db_management.rs:37-68`
- **Severity:** low
- **Issue:** The wire path (`handle_create_db`) holds `db_create_lock` and guards on `has_db` (task #546), but the public `create_db_as` -- the very method the dispatcher calls -- performs `self.dbs.insert(name, db)` with no existence check and no lock of its own. A second call with the same name (any non-dispatcher caller, parallel `create_db` from two tasks, or a caller following the `#[doc(hidden)]`-but-`pub` signature) replaces the registered instance, dropping every repo handle, open table, and in-memory record of the first; the catalogue row is overwritten via `save_database` (which also swallows its own errors as a `warn!`, leaving an in-memory-only db on persist failure).
- **Failure scenario:** Boot-time/tooling code calls `create_db("main")` while a wire-created durable `main` already exists: the live instance with attached fjall repos is dropped from the registry; subsequent reads see an empty database until restart.
- **Suggested fix:** Make `create_db_as` acquire `db_create_lock`, return `KeyExists` (or accept an `if_not_exists` flag), and propagate `save_database` errors instead of `warn!`-ing. The self-defense rationale in `access_control.rs::create_group_as` (task #546) applies verbatim here.

### 8. `drop_function_as` returns `existed = false` while deleting a durable catalogue-only function
- **File:line:** `src/shamir_db/shamir_db/function_management.rs:274-296`
- **Severity:** low
- **Issue:** `existed` is taken solely from `functions.remove(name)` (live registry). A `kind = Native` row is deliberately *not* materialised at boot (`core.rs:290-296`), so it lives only in the catalogue; dropping it removes the durable record but reports `{"existed": false}`. The doc contract ("Returns `true` if it existed") is violated, and `handle_drop_function`'s `if_exists` early-exit (`admin_function.rs:138`, also registry-only) makes the same mistake one level up: an `if_exists` drop of a catalogue-only function returns `existed: false` **and never deletes it**.
- **Failure scenario:** Operator lists a native function (visible via `list functions` from the catalogue), issues `DROP FUNCTION IF EXISTS`, gets `existed: false`, and the row still resurrects artifacts on next boot.
- **Suggested fix:** Base `existed` on `registry.remove(...) || load_function(name).is_ok_some()`, and include the catalogue in `handle_drop_function`'s `if_exists` probe.

### 9. `create_validator_inner` replace path resets `bound_in` and can mint `RecordId::default()` for catalogue-only validators
- **File:line:** `src/shamir_db/shamir_db/validator_management.rs:247-252` (id selection) vs the catalogue-aware fallback at `94-107` in `register_native_validator_as`; `bound_in` reset at `282-285`
- **Severity:** low
- **Issue:** Two asymmetries vs its sibling `register_native_validator_as`: (a) on `replace`, the id comes from `id_for_name(name).unwrap_or_default()` only -- a validator whose *live* registration failed at boot (compile error path, `core.rs:445-451`) but whose row persists gets a brand-new random id instead of the row's `_id` (the native path correctly falls back to `load_validator(name)`); (b) the freshly built record carries `bound_in: []`, so a replace **wipes** the persisted binding map while the *table-side* bindings (persisted on each table's info-twin) still reference the same id -- the registry's live `bound_in` is untouched, so live and durable binding state diverge until the next `persist_validator_bound_in`.
- **Failure scenario:** Replace a validator whose boot compile failed: its `_id` changes, table bindings persisted against the old id fail closed with "validator not found" after restart despite `CREATE OR REPLACE` having "succeeded".
- **Suggested fix:** Port the catalogue `_id` fallback from `register_native_validator_as`, and preserve the existing record's `bound_in` when reusing an id (or recompute it from `validators.bound_tables(id)` like `persist_validator_bound_in` does).

### 10. Panic paths in library code: `.expect("interner touch_ind")` and `.unwrap()` on `SystemTime`
- **File:line:** `src/shamir_db/execute/admin_schema.rs:1038`; `src/shamir_db/execute/helpers.rs:58-63`
- **Severity:** low
- **Issue:** CLAUDE.md's error-handling rules ("Return `Result<T, E>`; avoid `panic!` outside `unreachable!()`/programmer-bug invariants") are otherwise respected throughout the crate; these two sites are exceptions. `serialise_one_rule_catalogue` panics if `interner.touch_ind` fails -- the same failure one line away in `handle_interner_touch` (`admin_interner.rs:158-164`) is correctly mapped to a `BatchError`. `admin_result_with_op_id` `.unwrap()`s `duration_since(UNIX_EPOCH)`.
- **Failure scenario:** A poisoned/full interner during `SetTableSchema` panics the request task instead of returning a typed error; a clock set before the epoch panics every DDL response builder.
- **Suggested fix:** Map `touch_ind` through `err(...)` like the touch handler; use `.unwrap_or_default()` as done everywhere else for epoch time.

### 11. `foreign_key_dto_from_qv` silently coerces unknown `on_delete`/`on_update` strings to `NoAction` -- and then re-persists them
- **File:line:** `src/shamir_db/execute/admin_schema.rs:1332-1360` (read path) vs `src/shamir_db/shamir_db/schema_management.rs:371-397` (`parse_fk_action`, hard-error by design)
- **Severity:** low
- **Issue:** The F-4 campaign made present-but-unrecognised FK actions a **hard error** at boot-parse specifically so "garbled" can't be silently downgraded to `NoAction`. The DDL RMW read path (`dto_one_from_catalogue`) predates/coexists with a `_ => FkAction::default()` arm; because `handle_add_schema_rule`/`handle_remove_schema_rule` round-trip the *whole* rule list through this DTO and re-serialise it, one future/typo'd action string in any rule is silently normalised to `NoAction` and **written back durably** on the next unrelated `ADD SCHEMA RULE`.
- **Failure scenario:** A row persisted by a newer binary with an added action (`"set_default"`) is silently rewritten to `NoAction` by an older binary handling an unrelated schema edit -- referential semantics change without any error.
- **Suggested fix:** Reuse `parse_fk_action` (or return `Option<FieldRuleDto>` failure) in `foreign_key_dto_from_qv` so the RMW handlers reject instead of normalise, mirroring the boot path.

### 12. Nits
- **File:line:** `src/shamir_db/execute/db_tx.rs:82-85`; `src/shamir_db/execute/admin_schema.rs:860-876`; `src/shamir_db/execute/admin_schema.rs:77-98`
- **Severity:** nit
- **Issue:** (a) `tx_begin_as` maps *any* unknown isolation string to `Snapshot` silently -- a typo'd `"serialzable"` gets weaker isolation with no error (contrast the loud `Unsupported engine` error in `handle_create_repo`). (b) `handle_remove_schema_rule` bumps `schema_version` and rewrites the catalogue (with rollback machinery) even when `removed == false`. (c) `admin_user_locks` now multiplexes bare usernames and `"schema:db/repo/table"` keys in one namespace; a username literally shaped like `schema:a/b/c` would false-share a lock. Harmless today, but the map's doc says "keyed by user_name".
- **Suggested fix:** Reject unknown isolation levels with a typed error; skip the persist/version-bump when nothing was removed; give schema locks their own map (or document the shared namespace in `admin_user_locks`'s doc).

## TDD-coverage notes (what the suite does / doesn't pin)

- **Strong:** barrier-synchronised concurrency regressions with deterministic post-fix assertions (`group_tests.rs:262-347`); honest "currently unenforced" pins that turn red when the gap closes (`coverage_matrix_tests.rs:480-508`); uniformly applied and *tested* auth-before-existence ordering (#995 comments across drop/rename/index handlers); phantom-group coverage for the **add** path (`admin_access_validation_tests.rs:451-475`); schema activation rollback symmetry (`schema_rollback_tests.rs`, F-24/F-27b) and keyset-safe barrier tests (`keyset_safe_write_barrier_tests.rs`).
- **Gaps (mirroring findings above, none currently tested):** cross-db `DropDb` cascade (finding 1); remove-from-nonexistent-group phantom write (finding 2); catalogue durability *without* an external `flush_all` for the `databases` table + replication catalogues (finding 3, including the factually wrong comment in `rename_db_e2e.rs`); boot with an orphan repo row (finding 4); builtin-name-colliding function row across restart (finding 5); fault-injected rename save failure (finding 6); catalogue-only (native) function drop semantics (finding 8).
