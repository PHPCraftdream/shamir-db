# shamir-db -- Concurrency & lock-free invariants

## Summary

The crate is broadly compliant with CLAUDE.md's 5-pillar ideology: there is **no `std::sync::Mutex`, `std::sync::RwLock`, or `parking_lot::*` anywhere in production code**; every concurrent map is `DashMap::with_hasher(THasher::default())` (Fx, pillar 4); every `tokio::sync::Mutex` use carries an inline contention-model comment naming the rare/DDL op it serializes (the sanctioned exception); DashMap shard guards are consistently dropped before any `.await` (`.entry(k).or_insert_with(..).clone()` one-statement pattern), and lock ordering (`group_id_lock` nested inside a `group_member_locks` entry, never the reverse) is documented and held to. The weaknesses are on the O(x→0) and TOCTOU axes: the per-request authorization gate re-pays a full async catalogue traversal per batch op with **no** dedup cache even though the sibling interactive-tx path established exactly that pattern, and the #546 create-TOCTOU lock family covers create-vs-create only — drop/rename of dbs, repos, and tables still race their create counterparts through check-then-act windows (one of which is acknowledged by a `debug_assert!` in `rename_table_as`). No banned `scc::*::len()` calls exist (the crate uses no `scc` directly); `db_count()`'s `DashMap::len()` is O(shards), not banned.

## Findings

### 1. `execute_as` re-runs the full async ACL traversal per batch op — missing the inline dedup cache its sibling `tx_execute_as` already established

- **File:line:** `crates/shamir-db/src/shamir_db/execute/db_execute.rs:64-68` (per-op loop); contrast `crates/shamir-db/src/shamir_db/execute/db_tx.rs:140-167`
- **Severity:** high
- **Issue:** `execute_as` is the per-request hot path (every server batch). It calls `authorize_access` once at batch level (lines 35-43), then **again per (action, path) pair** from `collect_required_access` (lines 64-68) with no memoization. Each `authorize_access` on a non-`System` actor walks all ancestors (Root → Database → Store → Table), and each ancestor resolves `resource_meta` via a **separate async system-store read** (`load_setting("root_meta")`, `load_database`, `load_repository`, `load_table_record` — `access_control.rs:825-908`), plus `load_group` membership lookups when `meta.group` is set. For the common shape — a batch of N ops against the same table — every op re-pays the identical Root/Database/Store/Table reads: ~4-6+ storage round-trips per op before the query even starts, i.e. an O(N × catalogue-reads) cost where O(1) is achievable. Pillar-3 (O(x → 0)) violation on the hottest path in the crate.
- **Failure scenario:** non-System actors on an ACL-bearing deployment pay ~8-10 system-table reads per single-op request; under concurrent load this multiplies request latency and load on the system repo's store/interner for zero additional security (the answers are identical within the batch — `tx_execute_as`'s comment says exactly this: "the first call pays the full async traversal; subsequent calls for the same key hit a HashMap and cost ~50 ns").
- **Suggested fix:** port `tx_execute_as`'s stack-local `FxHashMap<(ResourcePath, Action), bool> acl_cache` (db_tx.rs:150-167) verbatim into `execute_as`'s per-op loop — it is stack-local, dropped at function exit, keyed on `(path, action)`, and the Fx hasher is already a dependency (`rustc-hash`). Also consider hoisting the batch-level `authorize_access(Database, Read)` result into the same cache. (A structural follow-up — a lock-free `ArcSwap` snapshot of ACL catalogue state per pillar 5 — is finding 4 below.)

### 2. Table-level DDL (CREATE/DROP/RENAME TABLE) has unserialized check-then-act races; the race is acknowledged by a `debug_assert!`

- **File:line:** `crates/shamir-db/src/shamir_db/execute/admin_table_index.rs:50-69` (create-table guard, no lock), `:104-297` (drop-table), `:299-350` (rename-table); `crates/shamir-db/src/shamir_db/shamir_db/table_management.rs:216-228` (guards), `:314-317` (`debug_assert!(existed, "rename_table_stores returned false despite has_table guard")`)
- **Severity:** medium
- **Issue:** Task #546 closed the create-db/create-repo TOCTOU with `db_create_lock`/`repo_create_locks`. Table ops received no equivalent: `handle_create_table` checks `db.has_table(...)` then calls `add_table_as`; `rename_table_as` checks `has_table(from)`/`!has_table(to)` then awaits `rename_table_stores` and two catalogue writes; `handle_drop_table` checks then drops — all with no lock serializing any of them against each other. `rename_table_as`'s own `debug_assert` codifies that a concurrent drop/rename landing between its guard and its mutation is an anticipated state.
- **Failure scenario:** two concurrent `RENAME TABLE from→to` calls both pass the guards, both call `rename_table_stores`; in debug builds the loser panics the task on the assert; in release the loser's `existed == false` is silently ignored and it proceeds to write a second `(db, repo, to)` catalogue row and remove the already-removed `from` row — duplicate/dangling catalogue state, or a `CREATE TABLE to` racing `RENAME TABLE x→to` producing two live registrations under one name.
- **Suggested fix:** extend the #546 per-name `tokio::sync::Mutex` pattern to a `DashMap<(String,String,String), Arc<Mutex<()>>, THasher>` keyed `(db, repo, table)` acquired by create/drop/rename table handlers around the guard→mutate window (same "entries leak by design, DDL is rare" contention-model comment), or route the whole handler through the engine's existing `ddl_admission` (`begin_write_barrier`) entry point used by the index path.

### 3. DROP/RENAME of databases and repos bypass the #546 create locks — asymmetric serialization axes

- **File:line:** `crates/shamir-db/src/shamir_db/execute/admin_db_repo.rs:215-221` (create-repo takes `repo_create_locks[db]`), `:77-149` (`handle_drop_db`, no lock), `:321-397` (`handle_drop_repo`, no lock), `:399-482` (rename handlers, no lock); `crates/shamir-db/src/shamir_db/shamir_db/db_management.rs:157-162` (`rename_db_as` `dbs.remove(from)`/`insert(to)` window), `:431-452` (`remove_repo`)
- **Severity:** medium
- **Issue:** The #546 TOCTOU fix serializes create-vs-create only. `handle_drop_repo`, `handle_drop_db`, `remove_repo`, `rename_repo_as`, and `rename_db_as` never acquire `db_create_lock`/`repo_create_locks[db]`, so drop-vs-create and rename-vs-create on the same name are unserialized. Additionally `rename_db_as` transiently removes the source key from `dbs` before re-inserting it under the target, and that window is not covered by the lock `handle_create_db` holds.
- **Failure scenario:** concurrent `CREATE REPO IF NOT EXISTS r` + `DROP REPO r` (same db): the create passes `has_repo == false` under its lock while the drop proceeds unlocked; the repo is removed after (or before) the create's `add_repo_as` lands, leaving an in-memory repo whose catalogue row was removed — it resurrects on next `init` from nothing, or the create's catalogue write lands after the drop's removal, resurrecting a "dropped" repo durably. Same shape for `CREATE DATABASE to` racing `RENAME DATABASE from→to` (the rename's `insert(to)` clobbers or collides with the create).
- **Suggested fix:** acquire the same `db_create_lock` / `repo_create_locks[db]` entry in the drop/rename handlers (they already exist; the comment in `core.rs:88-103` already frames them as the per-name serialization point for the db/repo namespace, so this is completing the pattern, not inventing one).

### 4. Per-request ACL metadata is re-read from storage on every authorization — no lock-free snapshot (pillar 5 `ArcSwap` fit)

- **File:line:** `crates/shamir-db/src/shamir_db/shamir_db/access_control.rs:122-179` (`load_setting("fn_namespace_meta"|"root_meta"|"wasm_compiler_meta")` per gate evaluation), `:55-91` (`load_database`/`load_repository`/`load_table_record` per ancestor)
- **Severity:** low
- **Issue:** Even after finding 1's dedup, every fresh authorization re-reads static-for-long-periods catalogue rows (root meta, namespace meta, db/repo/table meta) through the system store. CLAUDE.md's table maps "Snapshot-style RCU read → `arc_swap::ArcSwap<T>`", which is the natural fit for this read-mostly/write-rarely (DDL-chmod/chown only) state.
- **Failure scenario:** sustained non-System request load keeps a constant read stream on the system-repo store; a slow/flushing system store directly inflates every request's gate latency (and, per `authorize_access`'s fail-closed design, a transient storage error *denies* the request — coupling data-plane availability to system-store I/O).
- **Suggested fix:** an `ArcSwap<HashMap<ResourcePath, ResourceMeta, THasher>>` cache populated on miss and invalidated (or re-published wholesale) by `set_resource_meta`/DDL writes. Must be invalidated on every `set_resource_meta` arm — a stale-positive ACL cache is an auth bypass, so ship it together with an invalidation test; the fail-closed `Err` → deny semantics of `resource_meta` must be preserved for genuine storage errors.

### 5. Group existence is validated *before* acquiring the per-`group_id` RMW lock — a completed concurrent drop can be resurrected

- **File:line:** `crates/shamir-db/src/shamir_db/execute/admin_access.rs:390-395` (`group_id_exists` check precedes `add_group_member_as`); `crates/shamir-db/src/shamir_db/shamir_db/access_control.rs:573-586` + `:604-627` (`rename_group_as` resolves id → authorizes → *then* locks; `group_members`/`load_group` `None` → empty members, `unwrap_or(Actor::System)` owner → `save_group`); `crates/shamir-db/src/shamir_db/system_store.rs:712-734` (`add_group_member`'s `rec == None` branch fabricates a record)
- **Severity:** low
- **Issue:** The §81/#563 per-group lock correctly serializes the load→mutate→save RMW window, but existence/authorization happen before the lock is acquired. A `drop_group_as` that fully completes in that gap is not "in-flight" anymore, so the later `save_group` re-creates the record: `rename_group_as` resurrects it with empty members and a System owner; `system_store::add_group_member` resurrects it as `name=""`, members=[new user]. The in-file tests (`group_tests.rs:263-450`) cover the concurrent-mutation window but not this completed-drop-then-RMW sequence.
- **Failure scenario:** admin A drops group 7 while admin B's `rename_group 7 → "ops"` (or `add_group_member 7`) is mid-flight behind it → a zombie group record reappears with empty/System-owned fields, invisible to the operator who just deleted it.
- **Suggested fix:** re-load the group under the per-group lock in `rename_group_as`/`add_group_member_as` (and fail with `NotFound` if absent) instead of only re-deriving fields with `unwrap_or` defaults; `set_group_owner` already models the right shape (`ok_or NotFound` under the RMW).

### 6. `SystemStore::load_repository_record` full-catalogue scan + linear filter for a keyed lookup

- **File:line:** `crates/shamir-db/src/shamir_db/system_store.rs:334-354` (vs. the filtered `load_repository` at `:828-857`)
- **Severity:** low
- **Issue:** Loads every `repositories` row and linearly matches `(db_name, repo_name)` although the table is keyed by exactly that pair and a filtered single-row read (`load_repository`) already exists 500 lines below. Hidden O(N) helper in violation of pillar 3's "avoid hidden O(N) in helpers (full scans, repeated lookups)". Only used by the rename-repo path (rare), hence low.
- **Suggested fix:** replace the body with `self.load_repository(db_name, repo_name).await` (identical `Ok(None)` semantics) or delete it in favor of the direct call at its caller.

### 7. `handle_start_migration`'s duplicate-start guard is check-then-act over the `active_migrations` map

- **File:line:** `crates/shamir-db/src/shamir_db/execute/admin_migration.rs:91-101` (`iter().any(...)` probe) and `:193-195` (`insert` after the whole snapshot/drain await sequence)
- **Severity:** low
- **Issue:** Two concurrent `StartMigration` ops targeting the same table can both pass the `iter().any()` probe, both run the (long) snapshot/drain, and both insert coordinators — the probe and the insert are separated by many awaits with no `entry()`-based reservation or CAS. This is explicitly documented as a known gap of the experimental API (`core.rs:549-552`: "a second `StartMigration` can race in") and the whole API is dead until an operator calls `enable_experimental_migration_api()`, so it is acknowledged debt rather than an unnoticed defect — recorded here so it is not forgotten when the API is hardened.
- **Failure scenario:** double snapshot/drain against the same source table; two dst repos/one orphan (the rollback removes only its own `dst_repo_name` if names collide, `add_repo` errors the second start — messy but contained).
- **Suggested fix:** on enabling the API for real use, reserve the slot atomically before the snapshot: `active_migrations().entry(reservation_key).or_insert(...)`-style claim (or the coordinator's `try_lock` made distinguishable from "not started" via an explicit `AtomicBool` state machine), released on rollback.

### 8. `resolve_group_id(GroupRef::Name)` is a full `load_groups()` scan per call

- **File:line:** `crates/shamir-db/src/shamir_db/shamir_db/access_control.rs:775-783`
- **Severity:** nit
- **Issue:** Name→id resolution reads and linearly scans the whole groups table. Reached from `resource_meta`'s Group arm, so it runs during `authorize_access` for group-managed resources (admin-frequency, and the CLAUDE.md "annotate O(N) with why" convention is arguably satisfied by nothing here — the function is undocumented on cost). Cheap fix available since group names are unique (guarded by `group_id_lock` + name scan at create/rename).
- **Suggested fix:** an O(1) name→id point lookup — either a `Filter::Eq { "name" }` read via `load_group`-style query, or a `DashMap<String, u64, THasher>` mirror maintained at create/rename/drop (the `AtomicUsize`-mirror precedent from CLAUDE.md pillar 3).

## Test-coverage note (concurrency lens)

Coverage of the mechanisms that *do* exist is unusually strong and deterministic: `execute_tests.rs:779-997` proves the create-db/repo locks both statistically and by holding the lock externally and asserting a spawned request stays blocked; `group_tests.rs:64-500` covers concurrent id allocation, same-name create/create and create-vs-rename serialization, and the #563 multi-mutation RMW window with a concurrent chown; `keyset_safe_write_barrier_tests.rs:100+` proves the F-37 schema-activation barrier is actually acquired by the real DDL path. No test exercises the gaps above: drop-vs-create / rename-vs-create db/repo/table races (findings 2-3), the completed-drop group resurrection (finding 5), or ACL cost behavior under batch load (finding 1). The `p1065_ddl_status_contract_tests.rs` crash-window tests (spawned drop + concurrent reads) partially cover the drop-index axis but not the table/db/repo axes.
