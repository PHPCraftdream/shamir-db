# shamir-connect -- Style & CLAUDE.md structural conformance

## Summary

The crate is strongly conformed on the structural pillars: all three `mod.rs` manifests are re-export-only, there is not a single inline `#[cfg(test)] mod tests { ... }` in `src/`, the `common/tests/` and `server/tests/` directories follow the mandated layout (manifest-only `mod.rs`, topic-split files, feature-gated where needed), one-file-one-export holds (multi-type files are cohesive families, not grab-bags), and the `client/` flows are integration-tested. The real debt is comment discipline: a public API doc pair claims "functionally identical" where one variant silently skips the post-auth rate-limit gate, a public stub function's doc promises what its body does not do, several `Mutex` sites lack the inline contention-model comments CLAUDE.md names as the enforcement mechanism, and there are a handful of stale doc references and one mid-function `use`.

## Findings

### 1. `dispatch_request_view` doc claims "functionally identical" but only it enforces the post-auth rate gate
- **File:line:** `crates/shamir-connect/src/server/dispatch.rs:112-117` (doc) vs `dispatch.rs:150-160` (gate present only in the view variant); counterpart `dispatch.rs:69-110`
- **Severity:** high
- **Issue:** The doc on `dispatch_request_view` states it is "**Optim #4** zero-copy variant of `dispatch_request` ... Functionally identical: same §7.5 validity check, same handler dispatch, same outcome shape." That is false: only the view variant runs the `check_post_auth_rate_limit` choke point (task #608); the owning `dispatch_request` has no rate-limit block. The doc actively misleads about a security control on a public API pair.
- **Failure scenario:** Production currently routes through the gated variant (`shamir-server/src/connection/request_loop.rs:340`), but `dispatch_request` is `pub use`d at crate root (`src/server/mod.rs:28`) and is the variant used by tests/benches/`shamir-transport-tcp/tests/echo_e2e.rs`. An integrator who reads "functionally identical" and picks the owning variant (e.g. because they already own a `RequestEnvelope`) silently loses all per-session request-rate limiting; authenticated sessions can then hammer handlers unthrottled.
- **Suggested fix:** Either (a) add the same rate-gate block to `dispatch_request`, or (b) correct the doc on both functions to state the divergence explicitly ("the view variant additionally enforces the #608 post-auth rate gate; the owning variant does not — prefer the view variant"). Option (a) is preferable; the asymmetry has no principled reason.

### 2. `encode_details_canonical` is a public stub whose doc promises encoding it never performs
- **File:line:** `crates/shamir-connect/src/server/audit_chain.rs:351-361`
- **Severity:** medium
- **Issue:** The doc says "encode a `BTreeMap<String, msgpack-Value>` as canonical msgpack (lex-sorted keys) for use as `details_canonical_msgpack`", but the body is `let _ = map; // placeholder until callers supply real msgpack values` followed by `Vec::new()`. The signature is also incoherent with the doc: the map value type is `rmp_serde::config::DefaultConfig` (a serde config struct), not any msgpack value type. The function has zero callers in the workspace.
- **Failure scenario:** A caller implementing an `AuditAppender` who trusts the doc passes their details map and silently emits `details_canonical_msgpack = []` on every audit entry — audit records lose their detail payload with no error, degrading the audit chain the spec calls NORMATIVE (IMPL §3.3).
- **Suggested fix:** Delete the stub (it is dead, misleading scaffolding), or implement it for a real value type (e.g. `rmpv::Value`) with a doc that matches, plus a test pinning canonical byte output.

### 3. Lock sites on runtime structs missing the inline contention-model comments CLAUDE.md mandates
- **File:line:** `crates/shamir-connect/src/server/session.rs:416` (`cap_lock: Mutex<()>` — no comment at all); `crates/shamir-connect/src/server/audit_chain.rs:131` (`inner: Mutex<ChainInner>` — doc describes contents, never the contention model); `crates/shamir-connect/src/server/argon2_semaphore.rs:36` (`notify: (std::sync::Mutex<()>, Condvar)`); `crates/shamir-connect/src/server/admin.rs:298` (`next_id: parking_lot::Mutex<u128>`); `crates/shamir-connect/src/server/bootstrap.rs:49` (`inner: Mutex<BootstrapInner>`)
- **Severity:** medium
- **Issue:** CLAUDE.md (code ideology): "Every hot-path use must be justified inline with a comment that names the contention model", and for `std::sync::Mutex` the F-9/#1076 revision states a new instance "must fit one of these [three sanctioned] categories (with its own inline comment naming the model) ... it may NOT cite 'precedent' ... Each carries its own inline comment — **that is the enforcement mechanism**." None of these five sites carries such a comment. Strongest instance: `SessionStore::cap_lock` is taken on every per-user-capped session insert (the auth path) and its critical section includes a full `DashMap` iteration over ALL users' sessions (`session.rs:476-481`) — precisely the shape of use the rule exists to police — with zero justification. `argon2_semaphore.rs`'s `std::sync::Mutex` + `Condvar` on a long-lived runtime struct fits none of the three sanctioned categories and says so nowhere. Contrast: `durable_counters.rs:16-20` carries exactly the required comment ("replay-protection infrastructure, not a hot path (one call per session resumption)") — the convention is known in this crate but inconsistently applied.
- **Failure scenario:** The documented enforcement mechanism cannot distinguish sanctioned sites from drift — the exact recurrence CLAUDE.md's own F-9 revision warns about ("re-verify per-instance rather than assuming this list is exhaustive, the same drift that caused this revision can recur"). Future concurrency audits must re-derive each contention model from scratch, and an unwary editor can grow `cap_lock`'s critical section (it already scans the whole store) with no in-code signal.
- **Suggested fix:** Add the mandated one-line contention-model comment at each site (e.g. `cap_lock`: "per-auth admin op, critical section must stay O(sessions-of-user), contention nil"); for `argon2_semaphore` either document why a Condvar wait-queue is acceptable under the pillar rules (atomic fast path, mutex only on the saturated wait path) or migrate to `tokio::sync::Semaphore`; for the `SessionStore` scan-under-lock, note the O(total-sessions) cost explicitly or restructure to a per-user index (the concurrency-lens reviewer should rule on the primitive itself).

### 4. Dead suppressors keeping unused imports alive in `server/handshake.rs`
- **File:line:** `crates/shamir-connect/src/server/handshake.rs:232` (`let _ = constant_time_eq;`), `handshake.rs:388-390` (`#[allow(dead_code)] fn _doc_link_targets`), keeping alive the unused imports at `handshake.rs:17` and `handshake.rs:27-28`
- **Severity:** low
- **Issue:** `constant_time_eq` is imported but never actually used in the file; line 232 burns the import with a no-op statement placed directly under the "Branch ONLY on the accept/reject decision" comment, making dead code look like part of the constant-time discipline. Similarly, `_doc_link_targets` exists solely so `ResumeConfig`/`ServerIdentityState` imports don't warn — but nothing in the file (code or doc links) references them.
- **Failure scenario:** Readers of `verify_proof` may assume the `let _ =` line performs a timing-neutralization (it does nothing); future edits keep propagating the unused imports instead of deleting them.
- **Suggested fix:** Remove `constant_time_eq`, `ResumeConfig`, and `ServerIdentityState` from the import block and delete both suppressors. If intra-doc links to those types are wanted, use fully-qualified links (`[`crate::server::resume::ResumeConfig`]`) in doc comments — no import required.

### 5. Stale doc references to artifacts that don't exist under the given names
- **File:line:** `crates/shamir-connect/src/common/auth_message.rs:6`; `crates/shamir-connect/src/common/envelope.rs:89-90`
- **Severity:** low
- **Issue:** `auth_message.rs` says test vectors live in `crates/shamir-connect/test-vectors/auth_v1/` — a directory that never exists (vectors are `test-vectors/*.{json,toml}`; `test-vectors/README.md:19-23` itself records that the `auth_v1` name was spec prose that "never existed" as a file layout). `envelope.rs` cites the integration test `request_envelope_ref_wire_compat_with_owning`; the actual test is `request_envelope_ref_wire_compat_with_owning_and_view` (`tests/integration_session.rs:333`).
- **Failure scenario:** A reader following the `auth_v1/` path (e.g. a TS-SDK implementer verifying byte-exactness, which this file's doc says is mandatory) finds nothing and may conclude the vectors are missing.
- **Suggested fix:** Point `auth_message.rs` at `crates/shamir-connect/test-vectors/` (specifically `auth_message_default.{json,toml}`) and update the test name in `envelope.rs`.

### 6. `finalize_change_password` doc header is a stale merge from the verify function
- **File:line:** `crates/shamir-connect/src/server/changepw.rs:92-104` (doc on `finalize_change_password`)
- **Severity:** low
- **Issue:** The function's doc opens with "Step 2: server verifies the request and (on success) returns the new material to persist. The pending challenge is cleared regardless of outcome (single-use), and on success ALL sessions of the user must be killed by the caller..." — that text describes `verify_change_password_request_with_sid` (properly documented further down at lines 113-122), before the actual one-line description ("Helper: kill all sessions for a user..."). The function does none of the verify/challenge work: it snapshots and removes sessions and returns `now_ns`.
- **Failure scenario:** A reader wiring the changePassword flow may call `finalize_change_password` believing it consumes the pending challenge and validates the proof, and skip `verify_change_password_request_with_sid` — leaving the single-use challenge unconsumed (re-playable within TTL) and the proof never checked.
- **Suggested fix:** Delete the stale "Step 2 ..." paragraphs from the doc; keep the "Helper: kill all sessions..." description and the §12.5.3 citation.

### 7. Mid-function `use` statements violating the imports-at-top rule
- **File:line:** `crates/shamir-connect/src/server/admin.rs:324` (`use dashmap::mapref::entry::Entry;` inside `InMemoryUserDirectory::insert`); `crates/shamir-connect/src/server/tests/post_auth_rate_limit_tests.rs:98-99` (`use std::sync::{Arc, Barrier}; use std::thread;` inside the test fn)
- **Severity:** low (nit for the test file)
- **Issue:** CLAUDE.md: "All `use` statements live in the file header (or the enclosing module's header), never inside a function or block body", with three documented exceptions; none applies here (no collision-annotated trait import, not cfg-gated, not `use super::*` in a test module). `admin.rs:324` is the only non-test violation in `src/`. (For completeness: `ticket.rs:303` and `durable_counters_tests.rs:3-6` are compliant — each sits at its enclosing module's header.)
- **Failure scenario:** None functional; it erodes the convention that makes import blocks a reliable inventory of a file's dependencies.
- **Suggested fix:** Hoist `Entry` to `admin.rs`'s header (and `Arc`/`Barrier`/`thread` to the test file's header block at lines 10-12).

## Explicitly checked and conforming (no findings)

- **mod.rs re-export-only:** `src/common/mod.rs`, `src/client/mod.rs`, `src/server/mod.rs` contain module declarations + re-exports + doc comments only; no logic.
- **tests/ layout:** `common/tests/mod.rs` and `server/tests/mod.rs` are manifest-only (no test code); tests are topic-split (`auth_message_tests.rs`, `rate_limit_tests.rs`, ...); wiring is via `#[cfg(test)] mod tests;` in the parent `mod.rs`; zero inline `#[cfg(test)] mod tests { ... }` anywhere in `src/`; `durable_counters_tests.rs` is correctly cfg-gated behind `durable-fjall`. `client/` has no `src`-level tests dir, which the convention permits — its flows (bootstrap, handshake, changepw, rotation) are exercised by the crate-level `tests/integration_*.rs` files.
- **Test-coverage claims:** `lib.rs`'s claim that wire-level vectors live in `test-vectors/` holds — all 8 vector pairs are asserted byte-for-byte by `common/tests/test_vectors_tests.rs`; only the stale sub-path in `auth_message.rs` (finding 5) is wrong. `envelope.rs`'s wire-compat test exists (name drifted, finding 5).
- **One-file-one-export:** multi-type files (`envelope.rs`, `types.rs`, `session.rs`, `admin.rs`, `handshake.rs`) are each a single cohesive protocol concern (wire-envelope family, wire-tag family, session family, admin-command layer, handshake family), i.e. legitimate "closely-coupled groups" under the rule; no unrelated-public-type grabs found.
- **Error-enum style within the theme's scope:** `common/error.rs` and both snapshot-sink error enums (`lockout.rs`, `rate_limit.rs`) use `thiserror` as required. (The hand-rolled `AuditError` display-via-Debug in `audit_chain.rs` is noted here for the error-handling-lens reviewer.)
- **Benches:** `benches/hot_paths.rs` uses `bench_scale_tool::Harness` per the workspace mandate (header documents the migration; no Criterion APIs).
