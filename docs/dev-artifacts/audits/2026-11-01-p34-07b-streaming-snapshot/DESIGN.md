# P34-07b streaming snapshot design — IMPLEMENTATION STATUS: PARTIAL

The bounded dump and load paths, sidecar ownership move, metadata-last commit, verified-active orphan sweep, same-generation collision handling, and metadata-first bounded generation pruning are implemented. Streaming parity and failure-boundary tests were added or updated. No tests were executed locally; CI must verify them.

## Implementation findings and remaining work

- Dump reads files in 1 MiB chunks in `spawn_blocking`, serializes unchanged `ChunkHeader` records and updates CRC there, retaining no more than four records per batch. Empty files retain one empty record. The sidecar is serialized after integrity inputs are computed and its encoded bytes are moved into the final metadata transaction; metadata order is sidecar, integrity, manifest.
- Load requests one manifest-indexed key with `get_many` at a time (missing values remain `Corrupt`), validates and writes each payload on a blocking worker, and maintains section CRC in graph/data/qgraph/qdata order. It checks f32 lengths against the sidecar and moves decoded sidecar maps into adapter construction.
- Dump validates metadata before sweeping: it skips cleanup on absent/corrupt/untrusted metadata, only removes exact old generation sidecar/chunk key forms, and uses bounded transactions. A requested generation equal to the verified active generation rolls to its checked successor. Generation flips publish metadata before bounded old-generation and absorbed-delta pruning. The manifest is the commit point; prune interruption leaves harmless stale keys.
- Tests added/updated: chunk-index/CRC assertions in `streamed_quantized_chunks_preserve_header_and_crc`, `failed_before_manifest_keeps_previous_generation_loadable`, and `missing_and_corrupt_chunks_remain_corrupt_errors`; `dump_and_flip_publish_companion_before_bounded_prune` injects a prune failure after metadata commit and checks the new generation. These are not a full old-code byte-parity oracle; CI has not run them.
- NOT DONE: byte-for-byte comparison against the old straightforward dumper, a non-quantized multi-chunk parity case, and an allocator-backed peak outstanding-bytes oracle for dump and load. No memory figures are measured or claimed.
- DONE: bounded dump/load chunk flow, per-chunk and cross-section CRC order, sidecar ownership move, active-generation-safe orphan sweep, and bounded metadata-first pruning. NOT DONE: required memory oracle and full byte-parity tests. Overall acceptance awaits those tests and CI.

## Historical baseline (2026-11-01)

The following sections are the original investigation and proposal. Read the Implementation findings above for delivered behavior and explicit gaps.

`codec.rs` currently reads both f32 dump files with `std::fs::read` (368-371) and does the same for quantized graph/data (440-444). It holds all four byte vectors together where applicable, slices them into `Vec<KvOp>` in `slice_into_chunk_ops` (600 onward), then submits one transaction (592-594). Each `ChunkHeader` owns its bytes (codec.rs 135-145). The sidecar is materialized from adapter iteration (476-496), encoded as a complete envelope (535-538), then cloned to `Bytes` (539-542). Thus chunk payloads, vectors read from disk, serialized records, and the entire sidecar are separate memory costs.

`load.rs` does `get_many` for each section, retains all returned records and reassembles each section into a complete `Vec<u8>` (150-172, 193-227; helper 445-471). It writes those vectors to temp files only afterward (240-298). The loader then reads graph contents into the HNSW in-memory graph; that resulting graph and the persisted sidecar's intrinsic contents are not removable snapshot-transient costs. The sidecar is decoded at 120-121 and cloned map-by-map at 262-267 before rebuilding maps at 385-408.

## Bounded design

Dump each dump file using a fixed `CHUNK_SIZE` buffer and `Read::read_exact`/short-read handling in `spawn_blocking`. For each piece, calculate the same per-chunk CRC and serialize one unchanged `ChunkHeader`/record; update the cross-section hasher in current order: graph, data, qgraph, qdata. Preserve empty-section behavior and identical chunk indices/bytes. Submit a bounded `KvOp` batch, then clear/drop it before filling the next; never retain source file bytes or all chunk ops. The serialized sidecar remains one record and one encoded envelope necessarily exists in memory; move its encoded `Vec` into `Bytes` rather than cloning it. Its maps are already newly-built ownership, not clones of stored maps. The memory target is therefore O(CHUNK_SIZE × fixed batch) plus one persisted sidecar record and adapter graph/state. Do not claim strict O(chunk) independent of sidecar: a single-record format forces sidecar serialization memory proportional to sidecar size unless serialization-to-store can be made streaming without changing record atomicity/format, which these interfaces do not demonstrate.

Load sections in manifest index order, requesting/decoding one chunk (or a fixed small batch) at a time, checking header index and per-chunk CRC before writing payload directly to the section temp file and updating cross-section CRC. Track checked byte lengths and compare against `sidecar.graph_len`/`data_len`; retain current missing/short/corrupt error categories and useful section/index details. For quantized sections preserve ordering after f32 sections. Drop each record/header before advancing; flush/close files before handing paths to `HnswIo`. Do not keep complete section vectors. Prefer `Store::get` per key unless its cost is unacceptable; `get_many` means whole-section buffering. `Bytes`/key/record plus decoded `ChunkHeader.bytes` may coexist for one chunk, so bounded peak is a small constant multiple of CHUNK_SIZE, not literally one chunk allocation.

Sidecar loading is also a persisted single-record constraint: `Store::get` returns the entire sidecar, decode necessarily materializes vectors/maps, and adapter construction must retain the final state. Remove the redundant `.clone()` pairs at load.rs 262-267 by destructuring/moving the decoded sidecar fields after all metadata checks and graph load parameters have been copied. This cannot make sidecar bytes or decoded data O(chunk); document the unavoidable record-scale floor rather than misstate the aspiration.

## Publication, overwrite and crash behavior

There is no global orphan sweep. `flip_generation` at load.rs 679-731 transactionally removes only the explicitly supplied old generation's counted keys and absorbed delta entries while publishing new metadata. `publish_manifest_without_prune` (735-753) updates metadata only. Its comments (673-678) say prior interrupted-prune orphans are harmless and the next dump prunes idempotently, but the observed ordinary `dump_snapshot_with_gen` path does not scan/prune orphans: it writes the requested generation and manifest in one transaction; its “Wipe” comment at codec.rs 576-581 is not executable cleanup. Therefore the brief's orphan-sweep presumption is not present.

Changing dump into multiple chunk transactions widens the pre-publication crash window: partial or complete new-generation keys may remain while the previous manifest still points to its prior generation. Implement a bounded orphan sweep before writing: only when existing metadata decodes and verifies sufficiently to identify the active generation, scan the snapshot-specific key prefix, collect keys belonging to non-active generations, and remove them in bounded `transact` batches. Never touch delta or unrelated keys. Corrupt/missing/untrusted metadata must not authorize deletion; on such states skip sweeping and propagate/retain existing read/write error semantics. In particular, a sweep must not use a failed manifest decode as permission to delete all generations. Avoid active-gen writes: if requested generation equals active generation, transparently choose an unused inactive generation, while preserving the caller's requested generation for first publication and explicit inactive-generation behavior. This is a documented deviation from the literal requested generation on active collision, required for repeated `dump_snapshot` safety and compatibility.

Actual `flip_generation` currently places old-key and delta removals into the same transaction before metadata Sets; this differs from the brief's claim that prune follows the flip. Change it to publish integrity+manifest in the final metadata transaction first, then prune old generation and absorbed deltas in bounded removal transactions. Because the `Store::transact` default executes operations sequentially, failure within the metadata transaction can expose partial operations; tests must exercise that real behavior, not only an atomic fake. A later prune failure leaves harmless garbage and the newly published generation loadable. Preserve that backend-specific limitation in the contract; `transact` is not universal atomicity.

Current index test support has one global allocator already (`src/tests/support/allocation_counter.rs:19-67`), so do not add another. It counts cumulative allocation bytes only (alloc/realloc, lines 23-29, 56-60), not live outstanding bytes: dealloc is not accounted, realloc counts the new size without subtracting old, and its `Window` spans awaits (85-103). It is not a valid peak-live-memory oracle for this requirement. Extend its accounting only with a sound pointer/size ownership ledger (or equivalent) that records successful allocations, removes exact old pointer+layout on dealloc, and handles successful realloc as removal-old plus insertion-new; failed realloc retains old ownership. Avoid allocation in allocator bookkeeping, thread-local scope it, and ensure TLS teardown callbacks never panic. The measurement must run on the actual synchronous worker thread being measured; an async window on the caller thread cannot count `spawn_blocking` allocations. Use a test-only measurement hook/closure executed on that worker, or measure synchronous stream helpers directly. Exclude fixture construction by taking the baseline after it is built; assert high-water outstanding bytes, not cumulative traffic. State bound includes one encoded sidecar and the bounded records, and choose a fixture sufficiently large that old whole-file/all-op behavior exceeds it widely.

Tests: (1) byte-for-byte dump parity against a test-local copy of the old straightforward chunking/encoding algorithm, exercising f32 and quantized if feasible; compare exact keyed record bytes and manifest/sidecar format, never generated `RecordId` ordering. (2) peak outstanding bytes for dump and load with the same deterministic allocator and large fixture; old implementation must exceed the asserted bound. Be explicit that load's HNSW graph construction and sidecar floor are outside the transient section-buffer bound. (3) injected failure after chunk batches/before manifest: old generation loads; after manifest success/before prune: new generation loads. (4) flipped chunk byte and missing chunk retain `Corrupt` behavior, including index/section. Read existing snapshot fixtures end-to-end before editing tests; do not infer their contents from generated IDs.

No dependency, public signature, format, or error change is proposed. No compilation/tests run in this design stage per policy.
