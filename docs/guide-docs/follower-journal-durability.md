# Follower journal durability boundary (PR6)

A WAL-less follower publishes each translated batch into its local journal, confirms FIFO writer progress, verifies the expected event bytes and gap state, then explicitly flushes the journal store and history before advancing the upstream bookmark. A single versioned bookmark record stores both the upstream bookmark and follower-local clean horizon J; legacy u64 and v1 records have unknown J and retain conservative recovery behavior.

The durable record deliberately does not contain a resumable apply receipt. If apply becomes visible and a later barrier or persistence step fails, the follower gate remains `requires-reopen`; retry-safe recovery of partial batches and exactly-once counter updates are deferred to PR6b. The PR6c cold-certification wiring loads J with `meta::repl_bookmark::load_clean_horizon` and certifies only `tx::apply_replicated::follower_durability::in_flight_range(max(changelog J, record J), recovered floor)` as an uncertain GAP; with an unknown J the original conservative cold clean-horizon fallback applies unchanged. The remaining limitation is PR6b: without retry-safe batch receipts a crashed in-flight batch cannot be resumed, so its GAP still costs a reseed of the affected range.

The bounded crash-image matrix and negative control are implemented in `tx/follower_durability/tests/crash_image_tests.rs`. They exercise the production verification/flush helper and public bookmark/horizon metadata APIs against a dropping-unflushed fake Store; they do not exercise full engine replay or establish exactly-once application. PR6c wires the record into cold-start certification (`tx/cold_reconcile/follower.rs`); the cold-start tests reopen each crash point twice and assert the GAP is exactly the in-flight batch.


The production-path failure tests in `tx/follower_durability/tests/apply_failure_tests.rs` and `apply_crash_tests.rs` exercise injected barrier failures and phase pauses around history writes, journal flush, and bookmark persistence against Fjall, followed by graceful writer shutdown and repeated reopen checks. These are not abrupt power-loss simulations; the dropping-unflushed fake-Store crash-image tests above are the only power-cut model. PR6c cold-certification wiring is implemented; abrupt power loss is still modelled only by the fake-Store crash-image tests.

A certified GAP does not reject otherwise valid follower batches: the upstream bookmark advances while clean-history horizon J remains unchanged. Persisted gap intervals are read as a single snapshot; covered event versions may be absent, but bytes outside the interval are still verified. Runtime GAPs are flushed through the sole changefeed marker writer before acknowledgement, adding GAP-path I/O while leaving the healthy path at one journal flush. The v2 record stores an optional J with the bookmark when known; legacy u64 and v1 records have unknown J, and fence-only/no-horizon saves retain their legacy wire forms. The shared codec strictly rejects trailing bytes.


## PR6b-1 foundation (inactive)

Three infrastructure pieces land first, none of them reachable from any production path in this PR.

The repository-wide atomic write capability is `Repo::begin_atomic_batch` and its `AtomicBatch` handle, resolving to an `AtomicCommitOutcome` of `Committed | Uncertain`. `Store::supports_atomic_batch` reports capability; fjall commits one `Database::batch` followed by `persist(SyncAll)`, the in-memory and other wrapper stores report unsupported. An `Uncertain` outcome leaves the caller responsible for reconciliation; nothing in this PR consumes the capability.

The MVCC history write is split into materialize and publish: materialize writes rows and their timestamps without raising the published visibility floor, and publish raises the floor — an infallible, non-awaiting step. The legacy single-step wrapper remains byte-identical. This split is what lets a resumed receipt re-publish already-materialized rows idempotently.

The receipt codec lives in `meta::repl::receipt`. A `ReplicationReceipt` carries full identity (lineage id, upstream epoch, predecessor bookmark, inclusive upstream version range), an explicit upstream→local version mapping list (non-contiguous inputs representable), the translated ops, the exact downstream journal event bytes, timestamp updates, absolute before/after counter deltas, and a `Prepared → Materialized → Checkpointed` phase. `receipt_id` is a domain-separated, non-cryptographic Fx hash of the whole receipt; `decode_receipt` fails closed on unknown versions, oversized input, trailing bytes, invalid upstream ranges, and any receipt whose bytes do not hash to the id it is stored under. `meta::repl::bookmark_v3` adds bookmark v3 (fence + bookmark + clean horizon J + optional outstanding-receipt reference): read-capable, with no writer — v1/v2/u64 records fall back to the existing loaders with `outstanding_receipt: None`, unknown versions still fail closed.

PR6b-2 activates the writer/reader: the receipt is persisted before apply and consulted on resume, the phase machine drives idempotent re-materialization and re-publication, counter integration uses the absolute before/after deltas, writers coordinate through the atomic-batch capability, and a cold `Prepared` receipt is recovered (discarded to its predecessor bookmark) before PR6c classification sees it. PR6b-3 then brings the migration/rollback tooling, activates bookmark v3 writes, and retires the legacy read fallback path.

## PR6b-2a repository write-admission domain (inactive gating)

Every repository instance now owns a `RepoWriteDomain`: one `Arc<tokio::sync::Mutex<()>>` constructed before any recovery or publication runs and injected into every table (`TableManager::create_with_domain`), the per-repo record counter, and the registry-level admission helpers. Ordinary leader writes never acquire the domain — the leader commit path gains NOTHING from this PR. The crate boundary now makes that explicit: **inside shamir-engine the commit path writes stores without the permit by design; no other crate can**. The `test-util` feature is an explicit nonproduction exception for downstream test fixtures only; it is disabled by default and must not be enabled in shipped production builds. DDL, membership, counter-persistence and registry-flush paths use admission. A writable leader must not coexist with receipt apply on the same repository, since both would otherwise mutate concurrently with no shared gate.

Admission yields an opaque `RepoWritePermit` capability: it is unforgeable (private constructor, no `Clone`) and identity-bearing — its token is debug-asserted against the exact repository instance it is presented to, so a permit from one repository can never authorize a mutation on another, even one sharing the same name.

The lock order is binding: repo permit → marker persistence mutex → per-table DDL admission (in stable table-token order when multiple tables are involved) → raise-intent → drain-writers → unique-write locks → terminal `bindings_lock`/`persist_lock`. The reservation hook sits inside `admit`: while a `RepoWriteReservation` is outstanding (the future paused-receipt slot), ordinary mutations are REJECTED with `RepoWriteError::Reserved`; only close (`admit_for_close`) and already-held permits proceed.

Cross-repository mutations (online migration) admit both repositories through `RepoWriteDomain::admit_pair`, which acquires the two domains' mutexes in ascending unique-instance-token order — migration A→B and B→A therefore acquire in an identical global order and cannot deadlock. Equal identities (source and destination resolving to the same repository instance) are rejected outright with `RepoWriteError::SameRepository`: the design is "acquired once or rejected", never collapsed.
