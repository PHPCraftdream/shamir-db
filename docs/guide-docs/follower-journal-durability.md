# Follower journal durability boundary (PR6)

A WAL-less follower publishes each translated batch into its local journal, confirms FIFO writer progress, verifies the expected event bytes and gap state, then explicitly flushes the journal store and history before advancing the upstream bookmark. A single versioned bookmark record stores both the upstream bookmark and follower-local clean horizon J. Since PR6b-3 the receipt-only contract admits exactly ONE durable bookmark representation — bookmark v3. Legacy u64, v1 and v2 records and floor-evidence states are REFUSED with the typed `DbError::FollowerStateRefused { reason: LegacyBookmarkFormat | MalformedBookmark | LegacyFollowerState }`, both at repository open and at first follower admission; malformed or unknown encodings fail closed. Nothing is rewritten in place: a refused state keeps refusing until the operator reseeds through the existing seed/reseed workflow. A `LastCommittedVersion` allocation floor without a v3 bookmark still lets a LEADER open and recover normally — only follower adoption/apply is refused (`LegacyFollowerState`).

The durable record did not originally contain a resumable apply receipt: under PR6, if apply became visible and a later barrier or persistence step failed, the follower gate remained `requires-reopen` and a crashed in-flight batch cost a reseed of the affected range. That behaviour is SUPERSEDED by the PR6b-2 receipt pipeline (below): an ordinary I/O failure now pauses the batch instead of failing the repository. The PR6c cold-certification wiring loads J with `meta::repl_bookmark::load_clean_horizon` and certifies only `tx::apply_replicated::follower_durability::in_flight_range(max(changelog J, record J), recovered floor)` as an uncertain GAP; an in-flight-range GAP is certified from the durable record J, which every admitted follower now has.

The bounded crash-image matrix is implemented in `tx/follower_durability/tests/crash_image_tests.rs`. It proves the refusal side of the contract: every legacy bookmark fixture (u64, v1, v2, and a floor-only crash image) refuses REPEATEDLY — every loader and every subsequent open/admission returns the typed refusal, nothing is rewritten, no v3 record is minted over refused bytes, and counters/fences are left untouched — while a v3 crash image still classifies as Native. These tests use the production verification/flush helper and public bookmark/horizon metadata APIs against a dropping-unflushed fake Store; they do not exercise full engine replay or establish exactly-once application, and the former legacy subprocess-replay block and legacy flush-order matrix are gone. PR6c wires the record into cold-start certification (`tx/cold_reconcile/follower.rs`).

The graceful-termination tests in `tx/follower_durability/receipt/tests/crash_subprocess_tests.rs` exercise injected barrier failures and phase pauses around history writes, journal flush, and bookmark persistence against Fjall, followed by graceful writer shutdown and repeated reopen checks. These are not abrupt power-loss simulations; the dropping-unflushed fake-Store crash-image tests above are the only power-cut model. Abrupt power loss is still modelled only by the fake-Store crash-image tests.

A certified GAP does not reject otherwise valid follower batches: the upstream bookmark advances while clean-history horizon J remains unchanged. Persisted gap intervals are read as a single snapshot; covered event versions may be absent, but bytes outside the interval are still verified. Runtime GAPs are flushed through the sole changefeed marker writer before acknowledgement, adding GAP-path I/O while leaving the healthy path at one journal flush. Clean horizon J lives inside the v3 record itself. No legacy wire forms are saved anymore: fence-only/no-horizon saves are stored as v3 records with bookmark zero and no fence (bookmark-zero, fence-less v3), which is durable proof of follower provenance. The shared codec strictly rejects trailing bytes.


## PR6b-1 foundation (inactive)

Three infrastructure pieces land first, none of them reachable from any production path in this PR.

The repository-wide atomic write capability is `Repo::begin_atomic_batch` and its `AtomicBatch` handle, resolving to an `AtomicCommitOutcome` of `Committed | Uncertain`. `Store::supports_atomic_batch` reports capability; fjall commits one `Database::batch` followed by `persist(SyncAll)`, the in-memory and other wrapper stores report unsupported. An `Uncertain` outcome leaves the caller responsible for reconciliation; nothing in this PR consumes the capability.

The MVCC history write is split into materialize and publish: materialize writes rows and their timestamps without raising the published visibility floor, and publish raises the floor — an infallible, non-awaiting step. The legacy single-step wrapper remains byte-identical. This split is what lets a resumed receipt re-publish already-materialized rows idempotently.

The receipt codec lives in `meta::repl::receipt`. A `ReplicationReceipt` carries full identity (lineage id, upstream epoch, predecessor bookmark, inclusive upstream version range), an explicit upstream→local version mapping list (non-contiguous inputs representable), the translated ops, the exact downstream journal event bytes, timestamp updates, absolute before/after counter deltas, and a `Prepared → Materialized → Checkpointed` phase. `receipt_id` is a domain-separated, non-cryptographic Fx hash of the whole receipt; `decode_receipt` fails closed on unknown versions, oversized input, trailing bytes, invalid upstream ranges, and any receipt whose bytes do not hash to the id it is stored under. `meta::repl::bookmark_v3` adds bookmark v3 (fence + bookmark + clean horizon J + optional outstanding-receipt reference). In PR6b-1 it was read-capable with no writer; the legacy read fallback described then has since been retired — v3 is the only durable follower bookmark representation.

PR6b-2 activates the writer/reader: the receipt is persisted before apply and consulted on resume, the phase machine drives idempotent re-materialization and re-publication, counter integration uses the absolute before/after deltas, writers coordinate through the atomic-batch capability, and a cold `Prepared` receipt is recovered (discarded to its predecessor bookmark) before PR6c classification sees it. PR6b-3 completed the retirement: the legacy read fallback path and the activation selector are gone, bookmark v3 writes are the only follower bookmark writes, and no migration or rollback tooling was ever provided — unsupported durable follower states are refused and the operator reseeds.

## PR6b-2a repository write-admission domain (inactive gating)

Every repository instance now owns a `RepoWriteDomain`: one `Arc<tokio::sync::Mutex<()>>` constructed before any recovery or publication runs and injected into every table (`TableManager::create_with_domain`), the per-repo record counter, and the registry-level admission helpers. Ordinary leader writes never acquire the domain — the leader commit path gains NOTHING from this PR. The crate boundary now makes that explicit: **inside shamir-engine the commit path writes stores without the permit by design; no other crate can**. The `test-util` feature is an explicit nonproduction exception for downstream test fixtures only; it is disabled by default and must not be enabled in shipped production builds. DDL, membership, counter-persistence and registry-flush paths use admission. A writable leader must not coexist with receipt apply on the same repository, since both would otherwise mutate concurrently with no shared gate.

Admission yields an opaque `RepoWritePermit` capability: it is unforgeable (private constructor, no `Clone`) and identity-bearing — its token is debug-asserted against the exact repository instance it is presented to, so a permit from one repository can never authorize a mutation on another, even one sharing the same name.

The lock order is binding: repo permit → marker persistence mutex → per-table DDL admission (in stable table-token order when multiple tables are involved) → raise-intent → drain-writers → unique-write locks → terminal `bindings_lock`/`persist_lock`. The reservation hook sits inside `admit`: while a `RepoWriteReservation` is outstanding (the future paused-receipt slot), ordinary mutations are REJECTED with `RepoWriteError::Reserved`; only close (`admit_for_close`) and already-held permits proceed.

Cross-repository mutations (online migration) admit both repositories through `RepoWriteDomain::admit_pair`, which acquires the two domains' mutexes in ascending unique-instance-token order — migration A→B and B→A therefore acquire in an identical global order and cannot deadlock. Equal identities (source and destination resolving to the same repository instance) are rejected outright with `RepoWriteError::SameRepository`: the design is "acquired once or rejected", never collapsed.

## PR6b-2b worker lifecycle foundation (inactive)

The lifecycle split into three objects lands under `tx/cold_reconcile/lifecycle/`. The repository lifecycle owner (`RepoWorkerLifecycle`) is the sole sender of the job channel and the only place close state and the cached terminal result live — but it does NOT hold the join handle. `install_worker` spawns a SUPERVISOR task that owns the handle and the last lease `Arc` for the rest of the lifecycle: it joins the worker, drops the lease strictly AFTER the join, sets `supervisor_joined`, then publishes the terminal into a `watch` channel (first-write-wins). The worker execution state (`WorkerExecutionState`) holds the job receiver, the repository resource lease, a generation counter, and the shared publication/termination interlock — it carries no sender and no owner reference, so a worker cannot resurrect admission or join itself. The job envelope (`LifecycleJob`) is payload plus a one-shot reply, nothing more.

States are `Open -> Closing -> Joined(result)`, with sticky `quarantined` and reopen-required flags once tripped. Submission policy: no work is accepted before a worker exists — `submit` rejects with `NotInitialized` until `install_worker` succeeds. A caller that cancels while awaiting a submission drops only its reply receiver; the job itself stays queued if it was accepted.

The join happens exactly once, in the supervisor: it joins the worker and drops the lease, sets `supervisor_joined`, then publishes the terminal result first-write-wins for repeated or concurrent shutdown callers. A timed-out wait leaves ownership of the handle and lease with the supervisor, and cancelling a shutdown waiter does not cancel the close it already applied.

Publication uses `PubTermInterlock::publish` to hold the synchronous mutex across the publication callback; termination waits for any in-flight callback and prevents subsequent publication. Callbacks must remain synchronous and must not wait for async work.

`RepoInstance::shutdown_clean` closes worker admission, then awaits lifecycle shutdown/join. After worker shutdown succeeds, repository commit quiescence, buffer flush, and checkpoint run under the same absolute deadline. Worker exit performs only its owned cleanup; the supervisor drops the lease, sets `supervisor_joined`, then publishes the terminal result. Every shutdown failure quarantines an existing lifecycle. A repository without an installed worker completes lifecycle shutdown immediately but still performs quiescence, flush, and checkpoint.

The worker panic boundary uses `catch_unwind` to classify failure, but it does not make arbitrary handler-local destructors fail closed. `WorkerExecutionState::protect_guard` accepts only resources implementing `FailClosedResource`, and arms the resource before wrapping it; the `VersionGuard` implementation calls `visibility_started_without_wal`, so an unsettled follower version requires reopen on drop. On success, `FailClosedGuard<VersionGuard>::commit(self)` consumes the wrapper and calls the underlying guard's real `commit`; this advances completion but does not by itself advance durability. Omitting that call preserves fail-closed cleanup. Synthetic resources must explicitly implement the capability (usually as a no-op). Keep protected guards outside publication callbacks during unwind: quarantine takes the publication gate and would re-enter that same gate. This guarantee applies only to wrapped owned resources, not arbitrary locals. The supervisor alone publishes the terminal after joining the worker and dropping the lease. On `RepoInstance`, each foreground handle carries a `ForegroundLifecycle` owner token; clones share it, while background drainer clones omit it and cannot retain foreground ownership. A never-installed lifecycle shuts down immediately; repository commit quiescence, buffer flush, and clean-horizon checkpoint still run under the same absolute deadline.

Drop contract, stated exactly: dropping the last owner closes admission synchronously and cannot detach the task (no abort in `Drop`); physical lease lifetime ends strictly after the supervisor's join; explicit async `shutdown` guarantees the worker exited on success.

The worker is INACTIVE in this PR: production receipt apply is not wired. CI exercises the contracts with synthetic jobs under `tx/cold_reconcile/lifecycle/tests/`.

## PR6b-2c receipt apply (active)

**Retry convergence.** An ordinary I/O failure pauses the batch — the paused write reservation is kept — and the NEXT PULL RESUMES THE SAME RECEIPT with the identical local allocation: no extra versions, no lost counters, no new gaps. Only corruption or ambiguity is terminal (reopen/quarantine); ordinary failures no longer set the gate `requires-reopen`.

**Pipeline (per chunk).** Prepared receipt + allocation reservation + bookmark-v3 pointer, ONE atomic batch = history rows/timestamps + absolute counters + downstream journal records + receipt → Materialized; read-back + checkpoint of bookmark+J with receipt retirement in the same batch; then publish + broadcast. Batches are split at `MAX_RECEIPT_EVENTS`/`MAX_RECEIPT_OPS` rather than weakening atomicity. Publication only ever runs after durability: the Materialized batch must be committed before visibility is raised, and an `Uncertain` outcome is resolved by read-back reconcile, never by assuming absence.

**Failure matrix (brief).** Prepared-write uncertain → reconcile read-back. Materialization uncertain → read-back, never assume absence. Journal I/O before publication → retry from the receipt through the serialized writer install. Cancellation before publication is safe (guards abort, the receipt owns the versions). Corrupt identity/pointer, decode errors, double-Uncertain → reopen/quarantine.

**Hot path.** The LEADER commit path and the non-follower apply path are UNCHANGED. The follower apply path gains one receipt write + one atomic batch + one checkpoint sync per batch.

**Activation rule.** `admit_follower` classifies the durable state → `Native` (a valid v3 record exists) | `Fresh` (no follower record; Fresh self-adopts by writing the v3 baseline — upstream = source version, local J = 1, no receipt — before any apply). v1/v2/u64 bookmarks refuse with `LegacyBookmarkFormat`, malformed/unknown encodings with `MalformedBookmark`, and a `LastCommittedVersion` floor without a v3 bookmark with `LegacyFollowerState` — refusal happens at open AND at first follower admission; the floor-without-bookmark case still opens normally as a leader. A persistent backend without atomic-batch capability is rejected with `DbError::AtomicBatchUnsupported` before any allocation; wrapper/hybrid backends are excluded. Cold-open classification runs BEFORE the non-persistent-WAL and `h <= j` early returns.

**Admission.** Receipt apply admits through the repository write-domain permit in the established lock order (repo permit → marker persistence mutex): DDL and local writes are excluded for the pipeline's whole run. While a paused receipt holds a write reservation, ordinary admission is REJECTED with `RepoWriteError::Reserved` until the receipt resolves.

**Worker lifecycle.** The receipt worker is the repository-owned lifecycle from `tx/cold_reconcile/lifecycle/`: the owner holds the job-channel sender, jobs carry payload plus a one-shot reply, states run `Open → Closing → Joined`, and a shutdown timeout or worker panic quarantines unconditionally. Shutdown reaches either publication or a safe durable pause and reports failures to the caller.

**Cold recovery.** A crash between phases leaves an outstanding receipt behind the bookmark-v3 pointer; cold recovery COMPLETES both phases (a Prepared receipt is materialized and checkpointed exactly like the warm resume, a Materialized receipt skips straight to publication + checkpoint) BEFORE PR6c gap classification sees it.

**Journal installs.** Downstream journal installs ride the sole journal writer (`install_durable_events`, never `try_send`).

**Unchanged index/vector restriction.** Ordinary/unique/sorted/index2 indexes are still rejected before allocation; there is NO posting/vector maintenance exactly-once claim.

**PR6b-3 status: DONE — receipt-only.** There is no in-place conversion, floor clearing, bookmark deletion or force-continue. Unsupported durable follower states are refused with `DbError::FollowerStateRefused`; the operator action is to stop the affected subscription and reseed through the existing seed/reseed workflow. Durable follower provenance IS the presence of a valid v3 record: it survives receipt retirement, pause, subscription removal and restart; a zero-bookmark fence-less v3 still identifies the follower. Seed completion writes a v3 baseline (upstream = source version, local J = 1, no receipt); fresh adoption writes v3 before admitting apply; identity adoption updates the fence in place, preserving the bookmark, J and outstanding-receipt pointer.
