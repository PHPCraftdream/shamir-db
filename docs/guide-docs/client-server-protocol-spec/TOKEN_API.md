# Token API v1: REST и WebSocket по bearer-токену

Доступ к БД третьих программ по bearer token, без SCRAM и без клиентской библиотеки. Четыре канала: HTTP, WebSocket, HTTPS, WSS; REST bearer передаётся в заголовке, browser bearer WS — первым бинарным кадром выделенного endpoint.

Статус: **нормативная спецификация, реализация не начата** (задачи TOKEN-T2..T8). Дизайн-обоснование и трассировка ревью: `../../dev-artifacts/design/token-api-rest-ws.md` (revision 3). При расхождении этого документа с дизайном действует этот документ.

Версии: документ v1; формат токена `format_version = 1`; пути `/shamir/v1/...`; WS subprotocol `shamir-v1`. Для bearer token protocol **AUTH_PROTOCOL.md не меняется**: токены не участвуют в SCRAM-транскрипте и не расширяют shared enums. Отдельная HTTP login ceremony задана TOKEN_LOGIN_HTTP и не меняет shared SCRAM messages/enums; browser bearer WS и SCRAM client KDF bounds описаны соответственно здесь и в AUTH_PROTOCOL §5.1.1.

## 1. Каналы

| # | Канал | Listener | Эндпоинт |
|---|---|---|---|
| 1 | HTTP + Bearer | `kind: http`, `tls: false` | `POST /shamir/v1/request`, `GET /shamir/v1/ping` |
| 2 | WebSocket | `kind: http`, `tls: false` | `GET /shamir/v1/ws` (native bearer), `GET /shamir/v1/ws/browser` (browser bearer; plaintext loopback only) |
| 3 | HTTPS + Bearer | `kind: http`, `tls: true` | как 1 |
| 4 | WSS | `kind: http`, `tls: true` | как 2, endpoints `/shamir/v1/ws` и `/shamir/v1/ws/browser` |

«Сертификат» в каналах 3 и 4 = **серверный** TLS-сертификат. Клиентские сертификаты (mTLS) в v1 не поддерживаются.

Граница безопасности — **тип listener-а**, не путь. Listener `kind: http` обслуживает TOKEN_API bearer-маршруты и, только при явном включении, отдельные неаутентифицированные login `POST /shamir/v1/auth/begin` и `POST /shamir/v1/auth/finish`. Login не создаёт SCRAM-сессию базы данных и не аутентифицирует `/shamir/v1/request`. Listener `kind: tcp|ws|unix` не принимает API-токены. Нативный bearer `/shamir/v1/ws` и браузерный bearer `/shamir/v1/ws/browser` доступны только на `kind: http`; SCRAM `/shamir/v1` и `/shamir/v1/browser` остаются отдельными и не принимают токены. Остальные маршруты без токена (`/shamir/v1/health`, `/shamir/v1/version`, `/admin/*`, метрики) отсутствуют (404). Исключение browser WS ограничено upgrade и первым кадром bearer-аутентификации; DB недостижима до проверки. Login — отдельное узкое исключение, доступное только при явном включении.

## 2. Формат токена

```
shk1.<id>.<secret>
```

- `id` — 16 байт из OS CSPRNG, base64url без padding: 22 символа.
- `secret` — 32 байта из OS CSPRNG, base64url без padding: 43 символа.
- Разделитель `.` (вне алфавита base64url; допустим в `b64token` RFC 6750). Общая длина **ровно 71 символ**. Разбор позиционный по фиксированным длинам.
- Алфавит base64url: `A-Za-z0-9_-`. Разбор **каноничный**: ненулевые завершающие биты последнего символа (`id`: 4 бита, `secret`: 2 бита) → токен malformed (иначе у одного токена было бы несколько строковых представлений).
- Префикс `shk1` версионирует формат и делает утёкший токен находимым сканерами секретов.
- Секрет показывается **один раз** при создании. Сервер хранит только MAC, секрет не восстановим.

## 3. Запись токена и MAC

Хранится (msgpack), ключ `id`, вторичный индекс `owner_user_id -> [id]`:

| Поле | Тип | Смысл |
|---|---|---|
| `id` | bytes(16) | идентификатор |
| `owner_user_id` | bytes(16) | `user_id` владельца; у пересозданного аккаунта он новый, токены не наследуются |
| `label` | string | unique among the owner's active tokens (unexpired and unrevoked), across all creation paths; not secret |
| `mac` | bytes(32) | `HMAC-SHA256(token_key, "shamir-api-token" \|\| format_version \|\| key_id \|\| id \|\| secret)`, `format_version` и `key_id` по одному байту |
| `key_id` | u8 | 1 в v1 |
| `format_version` | u8 | 1 |
| `created_at_ns`, `expires_at_ns` | u64 | срок **обязателен**, не больше `tokens.max_ttl_days` |
| `mode` | `read_only` \| `read_write` | |
| `channels` | `rest` \| `ws` \| `both` | на каком эндпоинте токен принимается; по умолчанию `both` |
| `databases` | `null` \| [string] | allowlist баз; `null` = все базы, доступные владельцу |
| `roles` | [string] | роли владельца на момент создания: токен-сессия строится из них; смена ролей повышает порог владельца и убивает токен, поэтому снимок не расходится с живыми ролями |
| `revoked_at_ns` | `null` \| u64 | |

Секрет высокоэнтропийный, поэтому быстрый keyed MAC корректен (Argon2 стал бы рычагом CPU против сервера). `token_key` — 32 случайных байта в `server_meta` (IMPLEMENTATION_GUIDE §1.2), создаётся при bootstrap, **в v1 не ротируется** (`key_id` и `format_version` уже входят в MAC-вход, поэтому многоключевая схема потом добавится без смены формата). Утечка `token_key` или резервной копии `server_meta` = `token revoke-all` и перевыпуск всех токенов (IMPLEMENTATION_GUIDE §5.8). Снимок одного хранилища пользователей не позволяет проверять догадки офлайн.

Состояние токена хранится и в памяти (`scc`-карта `id -> TokenState`); на горячем пути fjall не читается.

**Порог инвалидации владельца — существующий `tickets_invalid_before_ns` пользователя** (`FjallUserDirectory::tickets_invalid_before_ns_by_user_id`: lock-free in-memory кеш, прогревается при `open`, вытесняется при `remove`). Отдельного порога в хранилище токенов нет; запись пользователя и AUTH_PROTOCOL не меняются, добавляется только чтение «известен ли `user_id`» из того же кеша. **Порядок отзыва токена:** durable-запись (fsync) в хранилище токенов, затем публикация в памяти, затем отмена сессий, и только после этого возврат вызова. Истёкшие и отозванные записи удаляются сборщиком через 30 дней после срока или отзыва (при старте и раз в час).

## 4. Представление токена

1. REST и нативный `GET /shamir/v1/ws` принимают ровно один заголовок `Authorization`, схему `Bearer` (регистр схемы не важен), один пробел и токен. Отсутствующий или повторный заголовок, иная схема, лишние пробелы, длина токена не 71 символ или неканоничный base64url обрабатываются по §5; отсутствие заголовка отдельно сохраняет действующее правило лимитера.
2. Только браузерный `GET /shamir/v1/ws/browser` получает токен из единственного первого бинарного WS-кадра после `101`. Кадр — одна msgpack-карта с единственным строковым ключом `token` и строковым значением каноничного токена §2: 71 ASCII-символ. Неизвестные/повторные ключи и завершающие байты запрещены; размер обычного кодирования — 80 байт, предел до выделения памяти — 256 байт. На этом маршруте заголовок `Authorization` не является источником токена.
3. На обоих маршрутах токен не принимается из URL, query string, cookie, HTTP-тела или `Sec-WebSocket-Protocol`. Единственное исключение из header-only аутентификации — первый браузерный WS-кадр из пункта 2; ошибки до и после upgrade определены в §5 и §10.
4. Отдельные login routes `POST /shamir/v1/auth/begin` и `POST /shamir/v1/auth/finish` по TOKEN_LOGIN_HTTP не являются bearer data routes и не используют bearer-аутентификацию. Они не принимают bearer, cookie, Basic или поле password, используют fresh SCRAM client proof и выдают обычный scoped bearer token с server signature. Клиент проверяет подпись до принятия токена; сервер не может знать, проверил ли клиент. Login не аутентифицирует `/shamir/v1/request`.

## 5. Проверка

Для REST и нативного `/shamir/v1/ws` шаги 1–8 выполняются по заголовкам до чтения тела и до `101`; действующие HTTP-статусы и правила лимитера сохраняются.

Браузерный `/shamir/v1/ws/browser` сначала проверяет Host/Origin и резервирует pre-auth ресурсы (§10), затем выполняет upgrade. Токен первого бинарного кадра проходит разбор и проверки шагов 2–5, включая фиктивный HMAC для неизвестного id, constant-time MAC, состояние владельца и строгое `created_at_ns > tickets_invalid_before_ns(owner)`. Политика шага 6 проверяется после подтверждения секрета: отсутствие `ws`/`both` в `channels` даёт close `4013 token_channel_denied`; plaintext policy — `4014 token_plaintext_write_denied`.

Любая ошибка непроверенного кадра или credentials (malformed, неизвестный id, неверный секрет, отзыв, срок, недействительный владелец) даёт только close `4000 authentication_failed` с одинаковыми публичными причиной и временным классом. Сохраняются subnet failure limiter и аудит aggregation/sampling; HTTP `429` после upgrade не выдаётся, прошедший проверку токен лимитер не отклоняет. До успешной проверки DB handler не вызывается. Сессия из шага 7 создаётся/публикуется только после резервирования общего active cap по последовательности §10.

Приведённые далее шаги 1–8 относятся к bearer data routes; они не определяют login аутентификацию, которая описана в TOKEN_LOGIN_HTTP. Для REST и нативного `/shamir/v1/ws` выполняются по заголовкам до тела и до `101`. Для browser WS шаги проверки токена 2–5 применяются к единственному первому бинарному кадру после upgrade, без обработки отсутствующего `Authorization` как ошибки.

1. Для обычного REST/native bearer request отсутствующий заголовок `Authorization` даёт `401` (отсутствие заголовка неудачей для лимитера не считается). Browser WS ожидаемо не имеет Authorization header; его token извлекается из первого кадра согласно §10.
2. Разбор (§4, §2). Ошибка → шаг 8 (неудача).
3. Поиск `id`. Если `id` неизвестен, всё равно вычисляется HMAC на фиктивных данных, чтобы unknown-id и wrong-secret занимали сопоставимое время.
4. Сравнение MAC за постоянное время.
5. Состояние: токен не отозван; срок не истёк; `user_id` владельца известен кешу директории (удалённый пользователь вытеснен, пересозданный аккаунт имеет новый `user_id`); `created_at_ns > tickets_invalid_before_ns(owner)` (строго, как у тикетов).
6. Только после успеха шагов 2–5 (секрет подтверждён): `channels` содержит эндпоинт, на котором токен предъявлен (иначе `403 token_channel_denied`); правило plaintext listener-а (§11) нарушено → `403 token_plaintext_write_denied`. Для browser WS проверенные отказы имеют коды закрытия, определённые в §10.
7. Строится токен-сессия (§6).
8. Для REST и нативного `/shamir/v1/ws` **неудача шагов 2–5 даёт единый `401`** без различий в теле и заголовках; запись аудита делается вне пути ответа (очередью), поэтому время ответа не зависит от того, известен ли `id`. Неудачи пополняют **отдельный** лимитер по подсетям (экземпляр `RateLimiter`); счётчик SCRAM `LockoutStore` токеном не трогается никогда (иначе знание `id` позволяло бы заблокировать SCRAM-вход владельца). Лимитер управляет **только** ответом на неудачу и записью аудита: подсеть, превысившая порог, получает на неудачные запросы `429` с `Retry-After` вместо `401`. Browser WS непроверенные ошибки закрываются общим `4000` без HTTP `429` согласно §10. **Токен, прошедший шаги 2–5, лимитером никогда не отклоняется**: общая подсеть NAT, облачный диапазон или прокси без `trusted_proxies` не должны закрывать валидные токены чужих клиентов, а проверка стоит один HMAC. Успех не сбрасывает счётчики других подсетей.

Порог владельца повышает директория при тех же событиях, что инвалидируют тикеты возобновления (AUTH §12.6): успешная смена пароля, реальное изменение ролей (`grant_role` / `revoke_role`; `updateUser` без изменений порог не трогает), смена флагов `superuser` / `replicator`, `revoke_user_tickets`. `invalidate_all_tickets` повышает порог **всех** пользователей; его вызывает `shamir-server restore` (`sync/durability/restore.rs`), поэтому восстановленная копия не воскрешает отозванные токены, а токены, созданные до восстановления, перевыпускаются. Удаление пользователя вытесняет его из кеша, и токены перестают действовать. Отдельных хуков и глобального порога для токенов нет; следствие общего порога: события, убивающие тикеты, убивают и токены. `RevokeUserTokens` порога не повышает (иначе пострадали бы SCRAM-тикеты): он отзывает записи токенов владельца.

`kick_session` закрывает одну SCRAM-сессию и токены не затрагивает.

## 6. Принципал и права

Токен действует как его владелец, но не как администратор:

- `Actor::User(principal64(owner))`.
- Права **строятся, а не копируются**: `SessionPermissions::new(is_superuser = false, is_replicator = false, roles = снимок ролей из записи токена)` независимо от флагов владельца. Все привилегированные проверки читают `session.permissions`, поэтому токен superuser- или replicator-владельца для обработчика — обычный пользователь.
- Эффективные права = пересечение живых прав владельца (движок проверяет на каждом запросе) и scope токена (`mode`, `channels`, `databases`). Токен никогда не может больше владельца и по умолчанию может меньше.
- Права на данные = права владельца **как обычного принципала**, включая владение ресурсами, которые владелец создал, действуя как администратор (`session_actor` отображает superuser на `Actor::Admin` и записывает его владельцем создаваемого). Токен не даёт административных операций, но не «слабее» владельца в его собственных данных. Для автоматизации рекомендуются отдельные сервисные аккаунты без `superuser`.
- Токен-сессия — серверная `Session` с `origin = Token { token_id, scope, cancel }` (SCRAM-сессия: `origin = Scram`). `origin` — серверное поле, не поле wire. Токен-сессии живут в **одном процессном** `TokenSessionStore` со своими лимитами (учёт сокетов и рассылка отзыва требуют общего хранилища); SCRAM `SessionStore` токен-сессий не содержит, лимит SCRAM «16 сессий на пользователя» токены не расходуют.
- Поля `Session`, существующие только для SCRAM (`transport_kind`, `binding_mode`, `channel_binding_at_auth`), у REST- и WS-токен-сессий принимают фиксированные значения `TransportKind::WebSocket`, `BindingMode::None`, нулевой binding. Они никому не показываются и не участвуют ни в тикетах, ни в авторизации; единственный различитель — `origin`.
- Токен-сессия не получает и не предъявляет resumption-тикеты (`origin == Scram` обязателен для тикетов).

## 7. Allowlist запросов (deny-by-default)

`ScopedHandler` оборачивает обработчик БД. Запрос декодируется один раз (те же проверки лимитов и alias caps, что на SCRAM-пути), затем классифицируется по таблице. Новый вариант `DbRequest` запрещён, пока его явно не классифицируют.

| `DbRequest` | REST | WS |
|---|---|---|
| `Ping`, `Execute`, `WaitForVisibility`, `GetDdlOpStatus` | разрешён | разрешён |
| `TxBegin`, `TxExecute`, `TxCommit`, `TxRollback` | `not_supported_over_rest` | разрешён |
| `CreateCursor`, `FetchNext`, `CancelCursor` | `not_supported_over_rest` | разрешён |
| `CreateScramUser`, `SetSuperuser`, `SetReplicator`, `ChangePasswordChallenge`, `ChangePasswordVerify`, `Repl` | `token_request_denied` | `token_request_denied` |
| `CreateApiToken`, `ListApiTokens`, `RevokeApiToken`, `RevokeUserTokens` (§12) | `token_request_denied` | `token_request_denied` |
| любой иной / новый вариант | `token_request_denied` | `token_request_denied` |

Внутри `Execute` и `TxExecute` batch обходится `BatchTreeVisitor` по **всем** листьям, включая статические тела `ForEach`:

- **Классификация листьев.** `ScopedHandler` относит **каждый** лист `BatchOp` к одному из трёх классов собственным **исчерпывающим `match` без ветки `_`**. `BatchOp::is_admin` для этого не годится: он написан через `matches!`, и новый вариант `BatchOp` молча оказался бы разрешённым. Классы: data-plane (`Read`, `Insert`, `Update`, `Set`, `Delete`, `Call`, `Subscribe`, `Unsubscribe` и контейнеры `Batch`/`ForEach` над разрешёнными листьями), четыре интроспекционные операции, всё остальное. Всё остальное запрещено с `token_request_denied`, включая read-only admin-листья (`GetBufferConfig`, `MigrationStatus`, `ListValidators`, `DescribeRepo`, `InternerDump`, `ChangesSince`, `ListPublications`, `ListSubscriptions`, `ReplicationStatus`), DDL, пользователей, роли, права, функции, валидаторы, репликацию.
- **Четыре интроспекционные операции** `List`, `AccessTree`, `DescribeTable`, `GetTableSchema` разрешены на тех же условиях, что в грубом admin-gate SCRAM-пути (`is_coarse_admin_gate_exempt`): **только как верхнеуровневая запись batch**. Внутри `Batch` или `ForEach` они запрещены (паритет со SCRAM-путём, где исключение применяется к верхнеуровневым записям); каждая проходит собственную авторизацию по таблице/пути. Следствие: токен не выполняет DDL и не управляет доступом, как и обычный не-superuser SCRAM-пользователь.
- `Subscribe` и `Unsubscribe`: на REST → `not_supported_over_rest` (push-канала нет, операция молча ничего бы не делала); на WS разрешены.
- Токен с `databases != null`: `List::Databases`, `List::Users`, `AccessTree` без указания базы внутри allowlist запрещены с `token_database_denied` (иначе метаданные других баз утекают через интроспекцию).
- `mode = read_only`: любой лист с `BatchOp::is_write()` запрещает batch целиком (`Call` классифицируется как запись); `TxExecute` с записью и `TxCommit` запрещены; `token_read_only`. `TxBegin` read-only токеном допускается (read-only транзакция).
- `databases != null`: поле `db` каждого запроса, несущего базу (`Execute`, `TxBegin`, `TxExecute`, `TxCommit`, `TxRollback`, `WaitForVisibility`, `GetDdlOpStatus`, `CreateCursor`), должно входить в allowlist, иначе `token_database_denied`.

Результат классификации типизирован (`Allowed` / `Denied(code)` / `NotSupported(code)`): REST-слой выбирает статус из него, не разбирая ответ обработчика повторно.

## 8. Коды ошибок

Ошибки приложения остаются единой таксономией `DbResponse::Error { code, message }` (TRANSACTION_OUTCOMES.md и `db_message.rs`). Токен добавляет коды:

| code | Когда | REST статус |
|---|---|---|
| `token_read_only` | запись при `mode = read_only` | 403 |
| `token_database_denied` | база вне allowlist | 403 |
| `token_request_denied` | запрос или лист вне allowlist | 403 |
| `token_channel_denied` | токен предъявлен на эндпоинте, не входящем в `channels` | 403 (также перед `101`) |
| `token_plaintext_write_denied` | `read_write` токен на удалённом plaintext listener-е без `allow_plaintext_write` | 403 (также перед `101`) |
| `not_supported_over_rest` | tx / cursor / Subscribe через REST | 400 |
| `invalid_request` | тело не декодируется в `DbRequest` (включая неизвестные ключи `BatchRequest`): только когда падает собственное декодирование `ScopedHandler` | 400 |

Административные операции (§12) добавляют `token_label_exists`, `token_limit_reached`, `token_ttl_invalid`, `token_not_found`, `token_self_service_disabled`, `token_browser_session`; для них действуют существующие `permission_denied`, `hmac_required`, `hmac_mismatch`. Ошибки, возникшие **после** декодирования внутри движка, остаются `200` с `DbResponse::Error` (в том числе `invalid_request`, выданный движком по содержимому).

Ни токен, ни секрет, ни MAC не появляются ни в одном `code`, `message`, логе, метрике или аудит-записи.

## 9. REST (каналы 1 и 3)

| Метод и путь | Смысл |
|---|---|
| `POST /shamir/v1/request` | тело: один msgpack `DbRequest`; ответ: msgpack `DbResponse` |
| `GET /shamir/v1/ping` | эквивалент `DbRequest::Ping`, ответ `DbResponse::Pong` |

`Content-Type: application/msgpack` на входе и выходе. JSON-тел в v1 нет (JSON не переносит числовые и бинарные типы движка, NUMERIC_WIRE_SEMANTICS.md).

**Аутентификация до чтения тела.** Токен проверяется по заголовкам (§5); тело читается только после успеха, под ограничениями `max_request_body_bytes` (по умолчанию потолок data-кадра, 16 MiB) **и** общего бюджета тел «в полёте» на все соединения. После чтения тела и **перед вызовом обработчика** состояние токена перепроверяется (Acquire, как в §10); при неудаче → `401`. Без этого запрос, читающий тело до дедлайна, мог бы авторизоваться после возврата отзыва.

Дедлайны три: `head_timeout_ms` (по умолчанию значение `security.connection.auth_init_timeout_ms`, 5 с), `body_timeout_ms` (на всё тело, по умолчанию 30 с) и `request_timeout_ms` (общий, по умолчанию 120 с); одно значение `auth_init_timeout_ms` не годится для тела в 16 MiB на медленном канале. Истечение → `408` и закрытие. Точные имена ключей фиксируются в T3.

**Инварианты запроса** те же, что у SCRAM-запроса: бюджет байтов ответа (`run_with_handoff`, guard держится до записи тела), пост-аутентификационный rate limit токен-сессии (bucket кешируется на `id` токена; каждый запрос получает новую токен-сессию со свежим случайным `sid`), лимиты запросов, редактирование внутренних ошибок.

| Ситуация | Статус | Тело |
|---|---|---|
| успех, в том числе `DbResponse::Error` движка | 200 | msgpack `DbResponse` |
| malformed / неверный / просроченный / отозванный токен (§5, шаг 8) | 401 | `{"error":"unauthorized"}` (msgpack), `WWW-Authenticate: Bearer` |
| `token_read_only`, `token_database_denied`, `token_request_denied`, `token_channel_denied`, `token_plaintext_write_denied` | 403 | `DbResponse::Error` |
| `not_supported_over_rest`, `invalid_request` | 400 | `DbResponse::Error` |
| неподдерживаемый метод / путь | 405 (`Allow`) / 404 | фиксированное |
| таймаут головы или тела | 408 | фиксированное, закрытие |
| тело больше лимита | 413 | фиксированное, закрытие |
| неверный `Content-Type` | 415 | фиксированное |
| голова больше 8 KiB или больше 64 заголовков | 431 | фиксированное, закрытие |
| rate limit (подсеть или токен-сессия) | 429 | `Retry-After` |
| остановка / перегрузка | 503 | `Retry-After`, `Connection: close` |

Любой ответ, отправленный до чтения тела (`401`, `403`, `415`, `429` и т.п.), несёт `Connection: close`, и соединение закрывается (на keep-alive остался бы непрочитанный хвост тела). `Expect: 100-continue` для bearer-запросов не отвергается: `100 Continue` отправляется только после успешной проверки токена, когда код впервые запрашивает тело; при неудаче клиент получает финальный ответ без `100`. Login следует TOKEN_LOGIN_HTTP §4: проверить head/source, списать ARRIVAL затем CREDIT, зарезервировать ограниченный input slot и лишь затем отправить `100 Continue`. Отключённые login routes возвращают 404 до тела; полный глобальный input pool — 503 `server_busy` с `Retry-After: 1`, без нового состояния. После разбора ограниченного канонического тела применяются body-dependent policy и pair gate до challenge/state. Сохраняются bearer body budgets и повторная проверка состояния токена после тела; CORS не добавляется.

**Framing** (только HTTP/1.1, без pipelining): запрос с одновременными `Content-Length` и `Transfer-Encoding`, повторным или нечисловым `Content-Length`, obsolete line folding, голым LF, `Transfer-Encoding` кроме `chunked` отвергается `400` с закрытием соединения; любая аномалия framing закрывает соединение. Ответы несут `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, на TLS ещё `Strict-Transport-Security`. **Заголовков CORS нет никогда**; браузерный кросс-доменный клиент вне scope v1.

## 10. WebSocket (каналы 2 и 4)

**Конечные точки и подпротокол.** Оба токен-маршрута используют подпротокол `shamir-v1`: нативный `/shamir/v1/ws`, браузерный `/shamir/v1/ws/browser`. Неверный upgrade или подпротокол даёт HTTP `400` до `101`.

**Нативное обновление соединения.** Нативный маршрут принимает `Authorization: Bearer <token>`; проверка по TOKEN_API §5 и атомарный общий лимит активных соединений выполняются до `101`. Настройки `tokens.max_sockets_per_token` (по умолчанию 8) и `tokens.max_sockets_per_owner` (по умолчанию 32) конфигурируемы, а не фиксированы клиентом. Невалидный токен сохраняет единый HTTP `401` и отдельный лимитер неудач; проверенные отказы политики канала/незашифрованного соединения дают `403`; исчерпание active cap — HTTP `503`. Нативный `Origin` необязателен; если задан, сверяется с `browser_origin_allowlist`; пустой список запрещает запрос с Origin (`403`). После успешного `101` сразу отправляется существующий кадр привязки. Нативный клиент не посылает кадр токена.

**Проверка Host/Origin и резервирование до browser upgrade.** Браузерный маршрут до `101` требует единственный корректный Origin и Host, нормализованный как authority и сверенный с `host_authority_allowlist`. Отсутствующий, `null`, повторный или некорректный Origin даёт HTTP `400`; несовпадение с точным allowlist Origin без wildcard — `403`; пустой список запрещает все запросы. Отсутствующий, повторный, некорректный или неразрешённый Host даёт `400`. Пересылаемый authority принимается только от настроенных доверенных прокси; `X-Forwarded-Host` без такого доверия не принимается. `X-Forwarded-For` для подсетевого лимитера используется только от доверенных прокси, иначе учитывается адрес пира. Cookie-аутентификации нет.

До browser upgrade атомарно резервируются предлагаемые разрешения учёта pre-auth: 256 глобально, 8 на подсеть; исчерпание даёт HTTP `503`. Эти числа не утверждают наличие существующих настроек. До проверки credentials разрешения не связываются с токеном/владельцем.

**Первый кадр браузера.** После `101` ожидается ровно один первый бинарный кадр не позднее 5 секунд; предел 256 байт проверяется до выделения буфера. Это одна msgpack-карта `{ "token": <71-символьный ASCII-токен> }`, без неизвестных или повторных ключей и завершающих байтов. Обычный размер — 80 байт: карта 1 + ключ 6 + префикс str8 2 + токен 71. Сжатие отключено, маскирование клиента обязательно; текстовые, фрагментированные, RSV, чрезмерно большие кадры и дополнительные application-кадры до проверки запрещены. Не более 8 управляющих кадров размером до 125 байт за период ожидания; они не продлевают срок ожидания. Не создавать неограниченных очередей.

**Непроверенные ошибки browser и перевод в активное состояние.** Выполняются разбор и проверки §5: фиктивный HMAC для неизвестного id, сравнение MAC за постоянное время, проверка состояния токена и порога владельца. Любая непроверенная ошибка кадра или учётных данных (неизвестный, неверный, истёкший, отозванный токен или недействительный владелец) закрывается общим `4000 authentication_failed` с одинаковыми публичной причиной и временным классом. Text/oversize framing до credentials не должны раскрывать отдельный класс: отклонить соединение общим `4000`, а не `1003`/`1009`. Сохраняются агрегация/сэмплирование аудита и отдельный лимитер подсетевых неудач; HTTP `429` после upgrade не выдаётся, проверенный токен лимитер не отклоняет. До проверки обработчик БД недостижим.

После проверки секрета отсутствие `ws`/`both` в `channels` закрывается `4013 token_channel_denied`; нарушение политики незашифрованного соединения — `4014 token_plaintext_write_denied`. Затем атомарно резервируется общий активный лимит. Его исчерпание после upgrade закрывается `1013 server_busy`. Сессия публикуется в TokenSessionStore с повторной проверкой отзыва/срока при переходе в активное состояние; отзыв в гонке, включая инвалидацию владельца (удаление, смену пароля, ролей или флагов, `revoke_user_tickets`, restore), даёт `4011 token_revoked`; истечение срока токена или `tokens.session_max_age_hours` — `4012 token_expired`. Разрешение pre-auth освобождается при успешном переходе и при любом терминальном исходе; активные разрешения освобождаются на каждом терминальном пути.

| Этап | Нативный `/shamir/v1/ws` | Браузерный `/shamir/v1/ws/browser` |
|---|---|---|
| До upgrade | Проверка Authorization и общего активного лимита до `101`; исчерпание → HTTP `503`. | Проверка Host/Origin и резервирование pre-auth ресурсов до `101`; исчерпание → HTTP `503`. |
| После `101` | Сразу кадр привязки; клиентский кадр токена не нужен. | Проверить первый кадр и общий активный лимит. При исчерпании: close `1013`, завершение без кадра привязки. При успехе: переход в активное состояние и кадр привязки. |

**Привязка и установленная сессия.** Кадр привязки `{ "ok": true, "sid": bin(32), "expires_at_ns": N }` отправляется нативному клиенту сразу после `101`, браузерному — только после проверки кадра и перехода в активное состояние; до этого браузер не получает кадр привязки или конверт приложения. Каждый последующий бинарный WS-кадр содержит одну msgpack-карту: запрос `{sid:bin(32),rid?:u32,req:bin(msgpack DbRequest)}`, ответ `{rid?:u32,res:bin(msgpack DbResponse)}`, ошибка `{rid?:u32,error:string}`; push использует `PushEnvelope` из SUBSCRIPTIONS.md. `sid` случаен, ненулевой, 32 байта, принадлежит одному соединению и хранится в общем TokenSessionStore; чужой sid закрывает `4010 token_sid_mismatch`. Лимит запросов после аутентификации возвращает конверт `rate_limited`, соединение остаётся открытым.

Перед каждым обработчиком состояние токена перепроверяется (Acquire). При отмене снимаются подписки и прекращается push, открытые транзакции откатываются, курсоры закрываются. Срок сессии — минимум из `token.expires_at_ns` и времени открытия плюс `tokens.session_max_age_hours`; часы переводятся в наносекунды до сложения. SCRAM `SESSION_MAX_AGE` (24 часа) и `SESSION_IDLE_TTL` не применяются; idle-таймера у token session нет. Heartbeat и data-frame предел 16 MiB соответствуют TRANSPORT_WS §7–8; после аутентификации text frame закрывается `1003`, oversized data frame — `1009`; остановка — `1000`. Отзыв сначала публикуется, затем отменяются сессии; опубликованный отзыв блокирует новые запросы, запрос, уже прошедший проверку, может завершиться. `tokens.max_sockets_per_token` (default 8) и `tokens.max_sockets_per_owner` (default 32) конфигурируемы; токен-сокеты не расходуют лимит SCRAM-сессий владельца.

### 10.3 Учёт сокетов

Общий активный лимит обоих bearer-маршрутов задаётся `tokens.max_sockets_per_token` (по умолчанию 8) и `tokens.max_sockets_per_owner` (по умолчанию 32). Нативный маршрут проверяет и резервирует лимит до `101`; исчерпание возвращает HTTP `503`. Браузерный маршрут проверяет и резервирует его после успешной проверки первого кадра и до публикации активной сессии; исчерпание после upgrade закрывается `1013 server_busy`. Значения остаются конфигурируемыми. Токен-сокеты не расходуют лимит SCRAM-сессий владельца.

**Остальные коды закрытия.** Коды TRANSPORT_WS §6 продолжают действовать с указанными исключениями. `4000` используется для непроверенной браузерной аутентификации и не применяется на нативном token-пути; `4001 unsupported_version` не используется ни одним token endpoint. `4010` — `token_sid_mismatch`, `4011` — `token_revoked`, `4012` — `token_expired`; `4013`/`4014` и `1013` определены выше. Остановка сервера закрывает соединения кодом `1000`.

**Предлагаемый учёт ресурсов.** Browser pre-auth payload accounting: 64 KiB на сокет, 16 MiB глобально и 512 KiB на подсеть. Отдельный admission accounting: 256 KiB на соединение, 64 MiB при 256; это не гарантия полной памяти процесса/ядра, накладные расходы измеряются при реализации. Browser `ws://` разрешён только для loopback; нативные bearer plaintext rails остаются по TOKEN_API §11. Этот browser порядок не меняет native HTTP статусы `401`/`403`/`429`/`503`.

## 11. Транспортная безопасность

**TLS (каналы 3 и 4).** Только TLS 1.3, без 0-RTT, ALPN `http/1.1`, тот же материал `TlsConfig`. Для токен-клиента единственная аутентификация сервера — сертификат (у него нет application-level Ed25519 pin SCRAM-клиента). Поэтому **TLS listener на не-loopback адресе отказывается стартовать с самоподписанным сертификатом** (issuer равен subject; автосгенерированный сертификат сохраняется на диск и после первого запуска неотличим от подложенного оператором, поэтому признак берётся из самого сертификата), если у listener-а не задано `allow_self_signed: true`; в этом случае при старте печатается SHA-256 от SPKI сертификата для раздачи клиентам. Для сторонних клиентов нужен сертификат от CA.

**Plaintext (каналы 1 и 2).**

- `tls: false` обязан биндиться на loopback (`127.0.0.0/8`, `::1`); `Config::validate` отвергает остальное, в том числе any-bind `0.0.0.0` и `::`, если не задан `allow_plaintext_remote`. Правила IMPLEMENTATION_GUIDE §2.2 относятся к `profile: plain` (TCP) и на `kind: http` не распространяются; для `kind: http` действует этот пункт.
- `allow_plaintext_remote: true` разрешает не-loopback bind: WARN при старте, gauge `shamir_token_listener_plaintext_remote = 1`. На таком listener-е принимаются **только `read_only` токены**, пока не задан `allow_plaintext_write: true`. Проверка идёт на шаге 6 §5 по конфигурации listener-а, **не** по адресу пира (за прокси правило по адресу пира бессмысленно). Секрет `read_write` токена к этому моменту уже прошёл по сети, поэтому отказ пишет аудит-событие `api_token_exposed` (с `id`), и оператору следует отозвать токен.
- `trusted_proxies: [cidr...]` — прокси, чей `X-Forwarded-For` учитывается **только для rate limit и лимитера неудач**: список читается справа налево, адреса из `trusted_proxies` пропускаются, берётся первый недоверенный. Лимит `max_active_connections_per_ip` считается при accept, до появления заголовков, и всегда использует TCP-адрес пира. Если пир не входит в `trusted_proxies`, заголовок игнорируется.
- Токен — bearer-секрет; по plaintext он виден каждому узлу пути. SECURITY_MODEL §4.15 говорит об этом прямо.

Login отделён от bearer-поведения. Listener `kind:http`, `tls:false`, `allow_plaintext_remote:true` MUST NOT обслуживать login routes: при `login.enabled=true` startup завершается ошибкой, иначе routes возвращают 404. Bearer plaintext поведение TOKEN_API не меняется. Class 0x00 login требует loopback bind и loopback socket peer.

## 12. Выдача и администрирование (по аутентифицированной SCRAM-сессии)

Операции — новые варианты `DbRequest`; доступны **только** SCRAM-сессии (токен-сессия не может выпускать или отзывать токены). Точные имена полей фиксируются в T5 и вносятся в эту таблицу без изменения семантики. Fresh-password HTTP login issuance — отдельное исключение вне `DbRequest`; он не позволяет токен-сессии выпускать/отзывать токены и не меняет эту таблицу или определения полей T5. Действуют self-service, active-token, TTL и durability правила; online issuance недоступна на read-only replica. Правила resumption-ticket не добавляются.

| Операция | Поля запроса | Ответ |
|---|---|---|
| `CreateApiToken` | `label`, `ttl_secs?` (по умолчанию `tokens.default_ttl_days`), `mode?` (по умолчанию `read_only`), `channels?` (по умолчанию `both`), `databases?` (по умолчанию `null`), `for_user?`, `hmac?` | `{ id, token, label, owner, mode, channels, databases, created_at_ns, expires_at_ns }`; поле `token` есть только здесь |
| `ListApiTokens` | `for_user?`, `hmac?` | список без секретов, MAC и хешей: `id`, `label`, `owner`, `mode`, `channels`, `databases`, `created_at_ns`, `expires_at_ns`, `revoked_at_ns` |
| `RevokeApiToken` | `id`, `hmac?` | подтверждение |
| `RevokeUserTokens` | `user?`, `hmac?` | число отозванных |

Правила:

1. **Самообслуживание.** Без `for_user` любой аутентифицированный пользователь создаёт, смотрит и отзывает **свои** токены, без HMAC-подтверждения (токен только сужает права, которые у пользователя уже есть). `tokens.allow_self_service: false` запрещает только **создание** собственных токенов пользователем (тогда создают только superuser через `for_user`); просмотр и отзыв своих токенов остаются доступны всегда. **Сессия браузерного пути (`binding_mode = 0x02`) создавать токены не может** (`token_browser_session`): такая сессия слабее по привязке канала (SECURITY_MODEL §4.9), а токен живёт до года. Fresh-password HTTP login — отдельный путь создания, слабее 0x02, запрещён для superuser/replicator и использует компенсирующий максимум TTL 24 часа. Browser SDK SHOULD default to `channels:"rest"`. Лимиты: `tokens.max_per_user` активных токенов (default 20), `tokens.max_ttl_days` (365), `default_ttl_days` (30); уникальность label действует только для активных (неистёкших и неотозванных) токенов по всем путям создания. Общий атомарный лимит активных токенов, включая CreateApiToken и HTTP login, — `tokens.max_per_user`; 20 — default, не отдельное жёсткое ограничение.
2. **Выдача администратором.** Superuser с HMAC-подтверждением (тот же механизм «did-you-mean-it», что у `CreateScramUser`, ключ выводится из session id) создаёт токен `for_user`, смотрит токены любого пользователя, отзывает любой токен, вызывает `RevokeUserTokens`. Не-superuser с `for_user` → `permission_denied`. Так выпускаются токены сервисным аккаунтам. Каноническое кодирование для HMAC добавляется в T5.
3. Пользователь не видит чужие токены; `RevokeApiToken` чужого `id` не-superuser-ом всегда отвечает `token_not_found` (иначе существование `id` проверялось бы). `RevokeUserTokens` без `user` относится к самому вызывающему; с чужим `user` у не-superuser-а → `permission_denied`. Секрет возвращается один раз по защищённому (TLS или loopback) SCRAM-каналу либо по отдельному защищённому HTTP-каналу входа согласно TOKEN_LOGIN_HTTP §5.1; это не даёт токен-сессии права выпуска или отзыва токенов. В CLI и в списках `id` печатается как base64url от 16 байт (22 символа), как компонент токена.

   **Гонка с инвалидацией.** После записи токена `CreateApiToken` перепроверяет, что вызывающая SCRAM-сессия всё ещё валидна (порог владельца не повышен после её создания). Если нет, свежесозданный токен тут же отзывается, вызов завершается ошибкой сессии: иначе токен, созданный сессией в момент смены пароля, пережил бы повышение порога.
4. Смена пароля, реальная смена ролей или флагов, `revoke_user_tickets`, удаление пользователя и restore повышают порог владельца (§5): смена пароля отзывает все токены пользователя, их нужно выпустить заново.
5. Хранилище токенов **локально для узла**; репликации токенов нет. Создание и отзыв онлайн работают на `ReadWrite` узле; на read-only реплике токены управляются офлайн-CLI `shamir-server token ...` на остановленном каталоге данных (`create`, `list`, `revoke`, `revoke-user`, `revoke-all`; секрет печатается один раз в TTY или в `--out-file` с правами 0600, в лог не попадает).

## 13. Аудит, метрики, логи

- Аудит (HMAC-цепочка, IMPLEMENTATION_GUIDE §3): `api_token_created`, `api_token_revoked`, `api_token_user_revoked`, `api_token_auth_failed`, `api_token_exposed`. Запись содержит `id` токена (если известен), владельца (только после успешной проверки MAC), канал и подсеть; **никогда** секрет или MAC. Запись идёт вне пути ответа. Неудачи malformed и unknown-id **агрегируются по подсети и сэмплируются**, не пишутся одна к одной (иначе запись на диск без аутентификации).
- Метрики (IMPLEMENTATION_GUIDE §6; значения `malformed`, `unknown` и `bad_mac` сведены в одну метку `invalid`, чтобы публичные метрики не различали существование `id`): `shamir_token_auth_total{channel,result}`, `shamir_token_active_ws`, `shamir_token_listener_plaintext_remote`, `shamir_token_request_duration_seconds{endpoint}`. Меток с токеном или владельцем нет.
- Редактирование: заголовок `Authorization` и любая подстрока токена вырезаются в самой ранней точке; HTTP-слой не передаёт сырой заголовок в поля логов, строки ошибок и spans. Обязателен тест редактирования логов в стиле `shamir-connect/tests/audit/integration_log_redaction.rs`, покрывающий успешные и неуспешные запросы (IMPLEMENTATION_GUIDE §4.3).

Браузерный WS: первый кадр токена, его байты и представления, подобные Authorization, не записываются в журналы, spans, метрики или аудит — ни при успехе, ни при ошибке. Сохраняются существующие агрегация и сэмплирование событий неудачной аутентификации; секрет и MAC не добавляются.

## 14. Вне scope v1

mTLS, OAuth/OIDC, JWT, cookies, CORS, JSON-тела, resource-style REST и OpenAPI, административные операции через токен, транзакции / курсоры / подписки по REST, репликация токенов между узлами, квоты сверх rate limit, статистика использования токена, ротация `token_key`, токен как параметр подключения в `shamir-client` (T9). Браузерный bearer WebSocket на выделенном `/shamir/v1/ws/browser` включён; браузерный SCRAM-путь не изменяется.

## 15. Test Checklist

Unit: парсер токена (все malformed-формы, огромный вход, не-UTF8, дубль `Authorization`, путаница разделителя, неканоничные завершающие биты); MAC и проверка (dummy-путь, `key_id` и `format_version` во входе MAC); переходы срока, отзыва, состояния владельца (пересозданный аккаунт не наследует токены, restore повышает порог); классификатор scope по каждому `DbRequest` и каждому `BatchOp` (исчерпывающий, deny-by-default); валидация конфигурации (plaintext + не-loopback, opt-in, обязательность `tls`, отказ самоподписанного); правила framing HTTP.

Интеграция (реальные сокеты, loopback, эфемерные порты, Windows и Linux):

- матрица {каналы 1-4} × {valid read, valid write, read-only токен пишет, база вне allowlist, неверный секрет, неизвестный id, просрочен, отозван после подключения (WS закрывается `4011`), владелец сменил роли или пароль, слишком большое тело, флуд заголовков, медленная голова, нет заголовка, токен в query игнорируется, два `Authorization`};
- подмена `sid`: токен-`sid` по SCRAM-соединению отвергается, SCRAM-`sid` по токен-соединению → `4010`; токен-сессии не видны в SCRAM `SessionStore`;
- права: superuser- и replicator-токены против каждого admin `DbRequest`, каждого admin `BatchOp`, `Repl`, `ChangePassword*`, `List::{Databases,Users}`, `AccessTree`;
- подписка: после отзыва WS перестаёт получать push без действий клиента;
- гонка: отзыв при запросах в полёте, ни один запрос не авторизован после возврата отзыва, в том числе REST-запрос, который читал тело в момент отзыва; отзыв сессии откатывает её транзакции и закрывает курсоры;
- лимитер: подсеть, исчерпавшая порог неудач, не отклоняет валидный токен из той же подсети; отсутствие заголовка в неудачи не засчитывается;
- учёт: 16 активных токен-сокетов владельца не мешают его SCRAM-входу;
- бюджеты: флуд телами до аутентификации не превышает общий бюджет, guard ответа держится до записи тела;
- выдача: `CreateApiToken` из браузерной сессии (`0x02`) отвергается; токен, созданный сессией в момент смены пароля, не переживает смену; пользователь видит и отзывает только свои токены, чужой `id` даёт `token_not_found`; `for_user` не-superuser отвергается; superuser выдаёт другому только с HMAC; `max_per_user`, TTL; `allow_self_service: false`; токен-сессия не вызывает ни одну токен-операцию; смена пароля отзывает токены; секрет виден ровно один раз;
- каналы: `rest`-токен на нативном WS → `403` без `101`, browser WS проверенный отказ канала → `4013` после `101`, `ws`-токен на REST → `token_channel_denied`, `both` работает на обоих;
- тест редактирования логов; `restore` (через `invalidate_all_tickets`) убивает токены; `Expect: 100-continue` без токена получает финальный ответ без `100`; push подписок и курсоры по WS; `not_supported_over_rest`.

Без sleep, через lifecycle-швы.

Браузерный WS проверить на реальных сокетах в Linux и Windows: Host/Origin и отказы до `101`; исчерпание нативного active cap → HTTP `503` до upgrade; browser pre-auth cap → HTTP `503`; browser active cap → `1013`; timeout, валидный кадр 80 байт, неверные/повторные/неизвестные ключи, завершающие байты и кадр больше 256 байт → общий `4000` без обращения к БД; проверенный отказ канала/незашифрованной политики → `4013`/`4014`; отзыв/истечение → `4011`/`4012`; освобождение разрешений и отсутствие кадра в журналах, spans и аудите.
