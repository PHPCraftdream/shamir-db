# Changelog

All notable changes to ShamirDB will be documented here.

The project is currently in alpha and has not published a stable release. Until the first tagged release, the `master` branch is the primary development line and compatibility is not guaranteed.

## Versioning scheme

During the alpha phase this project uses `MAJOR.MINOR.PATCH-alpha.N` (for example `0.1.0-alpha.1`). The `alpha.N` suffix is a SemVer pre-release identifier — incrementing `N` does **not** imply any compatibility guarantee between two alpha releases.

> **Workspace-version scope (Node client — documented gap, F-52):** the release pipeline's `version-consistency` job (`.github/workflows/release.yml`) verifies that every *Cargo* workspace crate's `version = "..."` agrees with the pushed `v*` tag. It deliberately does **not** cover `crates/shamir-client-node/package.json`'s `"version"` field: that crate is excluded from the Cargo workspace (`Cargo.toml` `exclude` — napi-rs cdylib, MSVC-only, built separately per `CLAUDE.md`), uses a different manifest format (Node `package.json`, never matched by the `crates/*/Cargo.toml` grep), and is versioned on its own cadence. Its `"version": "0.1.0"` therefore legitimately differs from the workspace's `0.1.0-alpha.1` — this is a documented scope gap, **not** a bug to "fix" by bumping it. There is currently no separate npm-publish workflow for it either (only `ts-e2e-nightly.yml`'s `node-e2e` job builds/tests the `.node` binding locally; no publish step exists yet); adding one is a separate, larger task.

> ⚠️ **Alpha-to-alpha compatibility: NOT guaranteed.** The on-disk storage format, the wire protocol, and the public API (Rust, TypeScript, and WASM) MAY change incompatibly between any two `0.1.0-alpha.N` releases. There is **no supported in-place upgrade path** between alpha versions yet — upgrading between alphas may require an **export/import cycle** (dump data with the old version, re-import with the new one). Treat each alpha as throwaway and keep independently verifiable backups. This is the single most important operational fact for an early adopter.

This file follows [Keep a Changelog](https://keepachangelog.com) conventions loosely and will adhere to [Semantic Versioning 2.0.0](https://semver.org) pre-release semantics once stable releases begin.

## [0.1.0-alpha.1] - 2026-08-07

- **PERF (#1093):** `Batch::try_build`'s `$query`-ref walk no longer pays a full msgpack encode+decode round-trip for the 5 op types that carry the bulk of real-world payload size — `Read`/`Insert`/`Update`/`Set`/`Delete` now walk their already-typed `Filter`/`FilterValue`/`QueryValue` fields directly via two new exhaustive visitors (`collect_filter_refs`, `collect_filter_value_refs`, 26 and 13 variants respectively, following this codebase's no-wildcard-match convention). `entry.when: Option<Filter>` needed no round-trip at all — already typed, walked directly. New tests prove `$query` refs inside a SELECT function's args and a `GROUP BY ... HAVING` clause are still found — two code paths with no prior test coverage.
- **MEDIUM fix (#1096):** closed the gap #1074 left open — `tx1: INSERT A {email:"x"}; COMMIT` then `tx2: DELETE A; INSERT B {email:"x"}` (and the equivalent UPDATE-off variant) previously failed with `DuplicateKey`, since `insert_tx`'s stage-time `validate_unique_for_create` reads only durable storage and had no visibility into the SAME transaction's own not-yet-committed `DELETE A`. - **SECURITY fix, found by a same-day follow-up `@oh` review (#1090):** the `Session::post_auth_bucket` lock-free migration below initially used `AtomicU64::swap` for `last_refill_at_ns`, which lets the refill watermark REGRESS under concurrent callers whose `now_ns` arrive out of order — the next call then re-credits an already-credited wall-clock interval, an unbounded over-refill with no aggregate cap. Verified via a compiled replica: at the shipped `POST_AUTH_RATE_LIMIT_PER_SEC=500`, one watermark inversion per call inflates admissions from the correct 1000/sec to 5500/sec. **Not a regression from this migration** — the pre-migration `std::sync::Mutex` version had the identical hazard (`now_ns` was captured outside its critical section in both versions); what the migration introduced was a FALSE invariant asserted in the doc comment ("can only under-refill, never over-refill"). Fixed with `AtomicU64::fetch_max` instead of `swap` — same `elapsed` computation, but the stored watermark can no longer regress, a genuine improvement over both the lock-free AND the original Mutex-guarded version. The same review found the new concurrency test spawned threads with no synchronization barrier, letting spawn overhead (tens of µs) dominate the sub-µs checked body — the assertion could pass vacuously even against a genuinely broken implementation (verified: a deliberately non-atomic replica passed the original test shape 10/10 runs, failed 7/10 once a `std::sync::Barrier` forced genuine contention). Added the barrier plus a new deterministic regression test for the `fetch_max` fix itself.

- **New capability (RFC, #1018; landed #1054-#1062): online `CREATE INDEX` for the regular/hash index family — writer latency no longer tracks the backfill scan.** Previously, `TableManager::create_index` acquired F-70's write barrier (`begin_write_barrier`) across the WHOLE Phase 1→2→3 backfill sequence — every concurrent writer queued on `unique_write_lock` until the build finished, so a `CREATE INDEX` on a large table was a full write outage for the scan's entire duration (the `f78_writer_latency` bench measured ~2.5 minutes at 100k rows, writer p95/p99 ≈ build duration). `create_index` now snapshots a pinned MVCC version and scans it barrier-free (Phase A), captures concurrent writes into a per-build dirty-set instead of blocking them (Phase B: a brief micro-barrier just to register the index at `Building` and mark the build in-flight), drains that dirty-set in a barrier-free catch-up loop that re-reads each touched row's pin-time AND current state to correctly diff and fix stale postings (Phase C — closes a real gap found mid-implementation: naively recomputing only from "current state," as an earlier revision of the design proposed, would permanently orphan the posting for any row that existed at the pin and was later updated to a different value or deleted, since the physical posting key embeds a hash of the indexed value), and only re-acquires the write barrier for a short, bounded final step (Phase D: apply the residual, flip `Building` → `Ready`). Falls back automatically to the old whole-barrier path for tables without an MVCC changefeed attached (system tables, directly-constructed test tables). Re-measured with the same bench, 2026-08-10: at 5k rows, writer p50/p95/p99 dropped from ≈135-160 ms (tracking build duration) to ≈0-1 ms; at 50k rows, build duration is ≈31.6-33.2 seconds (the scan itself is unchanged, still superlinear) while writer p50/p95/p99 stays at 0 ms — completely flat, independent of table size. Scope: regular/hash ONLY — `create_unique_index`, `create_sorted_index`, and `create_index_v2` (FTS/vector/functional) are untouched and remain on the whole-barrier path, for reasons specific to each family (unique: concurrent-duplicate-detection correctness under a barrier-free scan is a harder problem, deferred; sorted/index2: out of scope for this slice). `doctor::repair()`'s regular-family rebuild was deliberately NOT switched to the online path either — doing so per-index would release and re-acquire the DDL admission lock multiple times inside `repair()`'s single-barrier multi-family drop-then-recreate loop, reopening a serialization race (F-3, #1030) that the single barrier acquisition was specifically added to close; a safe fix needs its own bulk online-build entry point holding one outer admission guard across several inner short-barrier registrations, tracked as a follow-up. Crash recovery for an interrupted online build is intentionally conservative for this first landing: a crash at any point (verified via a 6-point crash-matrix test suite using `tokio::select!` to race each phase boundary against a deterministic pause hook, simulating a real process crash) leaves the index safely `Building` — never falsely `Ready` with incomplete postings — but does not resume; recovery is the same manual `TableManager::repair()` as before (there is no automatic self-heal-on-open for this index family at all, a pre-existing, unrelated design predating this work). See `docs/dev-artifacts/research/2026-08-07-online-index-build-rfc.md` for the full design (including a documented correction to the RFC's own Claim 2 found and fixed mid-implementation) and `docs/guide-docs/KNOWN_LIMITATIONS.md` §3 for the updated operational guidance (now split between the still-whole-barrier families and the newly-online regular/hash family). Delivered across `#1054`-`#1062` via ~15 rounds of `/crush`-delegated implementation, each independently re-verified (diff read, `cargo fmt`/`clippy`, targeted + full `shamir-engine`/`shamir-index` suite re-run) before acceptance — this caught and corrected several real issues along the way, including a barrier-guard-never-dropped deadlock, two batch-size/pause-hook test-authoring bugs, a genuine correctness gap in the original RFC's catch-up design, and two pre-existing tests that broke as an expected consequence of online build becoming the default path.

- **BUG fix (#1051, CRITICAL) + New capability, now genuinely complete (#1048, P1-2 sub-slice B): DDL `op_id` uniqueness fixed; tombstone `op_id` threading + crash-recovery status writes now deliver their stated contract for hash DROP, hash RENAME, and index2 DROP.** #1048's first pass (commit `f40ab4fd`, five delegation rounds — see the superseded CHANGELOG history for that saga) built sound mechanical plumbing on top of a foundation that silently didn't hold: `@oh`'s adversarial review (`docs/dev-artifacts/research/2026-08-09-1048-review.md`) found that `RecordId::system()` (pre-existing `#1015`/`#1025` code) truncates its argument to 12 bytes, and the DDL op-id dispatch prefixes (`"ddl_drop_index_"`, `"ddl_rename_index_"`) alone already consumed the whole budget — the index name never entered the id, so every DROP or RENAME on a table minted the SAME `op_id`, and `ddl_op_log::op_status_key` compounded it with a second lossy truncation, landing every op's status record on the same physical storage key. Reproduced end-to-end through the public API: a client polling its own op_id after a successful DROP could be handed back a completely different operation's result. Fixed (`044d443c`): both DDL dispatch sites now mint `op_id` via `RecordId::new()` (real entropy) instead of the truncated deterministic formula; both DROP tombstones (previously bare `Vec<u64>`/`Vec<u32>` with no field for it) now carry the real `op_id` per entry — hash DROP as `Vec<(u64, Option<String>)>`, index2 DROP as `Vec<(u32, String, Option<String>)>` (also folding in the index name, eliminating a separate descriptor-lookup mechanism entirely); recovery reads the `op_id` directly off the tombstone instead of regenerating it deterministically; `op_status_key` now derives its storage key from the `op_id`'s raw 16 bytes instead of a second `RecordId::system` pass. Backward compatible: pre-fix tombstones without the field still deserialize, treated as `op_id: None`. Also folds in both MEDIUM findings from the same review: index2's `SucceededViaCrashRecovery` write now runs *after* `recover_index2_drops()` actually completes (previously written before, risking a false success claim if recovery then failed), and the silently-skipped-status-write gap in one crash window is gone now that the tombstone carries the name directly. Independently verified: `cargo fmt`/`clippy` clean across the full workspace, full scoped suite (`shamir-types`, `shamir-index`, `shamir-engine`, `shamir-db`, `shamir-query-types --full`) 4099/4099 passed, 0 skipped. **A follow-up `@oh` review of the fix itself** (`docs/dev-artifacts/research/2026-08-09-1051-review.md`) gave a clean GO on production correctness — independently re-derived the byte math and reproduced the closed defect end-to-end with the opposite (correct) result — but found the test coverage had the same class of gap one level up: the three tests hand-fixed for the `None`-vs-`Some` regression above still minted their own op_id via the exact broken formula the fix deleted (passing `Some(op_id)` was necessary but not sufficient), and nothing anywhere pinned `RecordId::new()` at the actual dispatch site. Closed (`77d97f36`): those three tests now mint via `RecordId::new()` and assert on `status.kind`, not just `op_id` presence; a new dispatch-level test (`p1_2_ddl_result_contract_tests.rs`) drives two real `ShamirDb::execute()` DROP INDEX calls and asserts the returned op_ids differ and each polls to its own result; the advertised tombstone backward compatibility gained four direct tests (it had none); a fail-closed table-open on a corrupt op_id string became best-effort (`log::error!` + skip, matching the sibling write-failure handling); plus assorted stale-comment and duplicated-decode-logic cleanup the same review flagged. Once the final `DbResponse` is known, `ByteBudgetGuard::shrink_to` narrows the reservation down to the actual serialized size; a bounded few-byte overshoot past the estimate (e.g. enum-discriminator wire framing on top of the inner payload) is absorbed via a non-blocking `grow_unchecked` rather than a second blocking `acquire` (which would risk deadlocking against the budget slice the guard already holds). The `ReadQuery::with_version` flag (already accepted on the wire) now has a real result-side effect: when set, `QueryResult.versions` carries a per-record version array (index-aligned with `records`, sourced from the existing `MvccStore::version_of`). `UpdateOp`/`DeleteOp` gain an `expected_version: Option<u64>` field — when set, a mismatch on ANY matched row aborts the WHOLE operation with a new `version_conflict` typed error code (no partial application). The CAS check is a hybrid: an immediate `version_of` comparison at staging time (catching the common stale-read case) plus registration into the EXISTING SSI `record_read`/`validate_read_set` contour (closing the race window to commit). Both builders (Rust + TS) gain `.with_version()` / `.withVersion()` on the read builder and `.expected_version(v)` / `.expectedVersion(v)` on update/delete. The TS SDK surfaces `version_conflict` via a new `isVersionConflict(err)` helper alongside the existing `ShamirDbError.code === "version_conflict"` typed check. Fully backward-compatible: all three additions are opt-in (`None`/`false` by default); existing callers see no wire changes. **Isolation caveat noted at the time (since resolved by FG-7 above):** the commit-time race-window backstop originally only fired under `Serializable` isolation; FG-7 replaced it with an isolation-independent mechanism so the guarantee now holds on every entry path.
- **Correctness fix (FG-1):** unified `u64` decode contract — `u64 > i64::MAX` now promotes losslessly to the existing `Value::Big(BigInt)` / `QueryValue::Big(BigInt)` variant instead of silently wrapping (sign-flipping `u64::MAX` to `-1` via `value as i64`) or clamping (to `i64::MAX`). Applied at 6 sites: `ValueVisitor::visit_u64`, the `"u"` prefixed-key map branch, `From<u64>`, `QueryRecordVisitor::visit_u64`, the Rust `lit_u64` query-builder helper, and the TS `litU64` builder helper. The wire bytes for a `u64` field are unchanged (this is not a wire-format change) — only the decoded Rust/TS-side representation for previously-corrupted values is now correct. `lit_u64`/`litU64` represent the overflow case as an exact decimal string (matching how `Value::Big` itself serialises on the wire), replacing the old lossy `Number(v)` / `v as i64` casts. (The `Eq`-filter-vs-raw-`uint64`-storage gap this surfaced was fixed by FG-6, see above — see `docs/guide-docs/client-server-protocol-spec/NUMERIC_WIRE_SEMANTICS.md` for the full contract.)

- **New capability (RI-11):** `shamir-server restore --from <dir> [--force]` — backups now write a `manifest.json` (per-file SHA-256 + size) into every snapshot, verified before a restore touches `data_dir`; restore performs an atomic swap (current data renamed to a `.pre_restore_backup_*` sibling, not deleted, before the restored snapshot takes its place) with best-effort rollback on a partial failure; and every resumption ticket issued before the restore point is invalidated on the restored user directory so nothing can resume against stale pre-restore state. Liveness is checked by reusing fjall's own exclusive advisory file lock — no new PID-file mechanism. **Security fix (CR-B7):** ticket invalidation originally ran AFTER the atomic swap — a failure there left the new (restored) `data_dir` already live with pre-restore tickets never invalidated against it. Invalidation now runs INSIDE the staged temp copy, before the swap, so a failure there leaves the current `data_dir` completely untouched; the same task also hardened manifest verification (reject an unknown `format_version`, an absolute or `..`-containing entry path, or a duplicate entry) and made `backup --to` refuse a destination inside its own source `data_dir`. **Performance fix (CR-C4):** manifest generation/verification read each file's FULL contents into RAM (`fs::read`) purely to hash it — a needless memory spike on a large fjall SST/journal file. Both hash sites now stream through a fixed 1 MiB buffer into an incremental SHA-256 hasher instead, with byte-identical output. **Error-message fix (CR-D5, N-6):** a step-5 swap failure whose best-effort rollback SUCCEEDED previously returned the identical "operator must manually rename one of these two directories" message as the case where the rollback ALSO failed — misleading, since a successful rollback already leaves `data_dir` intact with nothing to rename. Split into two distinct `RestoreError` variants; the staged `*.restore_tmp_*` copy is now also best-effort removed on a step-3/step-4 failure (never on a step-5 swap failure, where it must survive for the error message's own "left at {temp_dir}" pointer). **Follow-up (W-5, found by an independent post-Wave-D review):** the step-5 swap's FIRST rename (`data_dir` → its `.pre_restore_backup_*` sibling) previously used a bare `?`, orphaning the fully-staged `temp_dir` with zero reference to it in the resulting error on failure — the same class of gap just missed for this specific sub-case; now reuses the same best-effort cleanup. The staged-temp-dir creation also switched from a separate `exists()` check followed by `create_dir_all` (a check-then-act race) to a single atomic `fs::create_dir` call, which itself fails with `AlreadyExists` if the target is already there — closing a same-second concurrent-restore TOCTOU with an identical operator-facing message.

The bootstrap token now auto-deletes itself — on the first successful login for the bootstrap username, or after a 24h TTL boot-time sweep, whichever comes first — instead of relying on the operator to delete it manually.
- **Security fix (CR-A6):** the bootstrap token is now truly one-time. RI-9 above only cleaned up the plaintext token FILE and a bookkeeping row — the account's underlying SCRAM credential (`stored_key`/`server_key`) was never rotated, so the same token kept authenticating indefinitely, exactly like a permanent password. Both consume points (first successful login, and the 24h TTL boot-time sweep for an unused token) now ALSO rotate the account's SCRAM credential to a freshly-generated random value that is never logged, returned, or persisted anywhere — after either event, the old token immediately stops authenticating.
- **Replication behavioral change (RI-10):** the leader now rejects a follower `Hello` whose `proto_ver` exceeds this build's `CURRENT_REPL_PROTO_VER` (`proto_ver_unsupported`) instead of accepting any version unconditionally. More importantly — **a follower that hits a journal gap now STOPS instead of silently skipping the missing range.** Previously, when the leader reported `gap_at` past the follower's requested `from_version`, the follower loop logged a warning, shifted its cursor past the gap, and kept running with permanently missing data and no visible signal. After this change the loop terminates and the subscription's row in `system/subscriptions` is marked `state = "resync_required"` (visible via the existing `ReplicationStatus`/`ListSubscriptions` admin responses); `reconcile()` will not restart a subscription in this state. **Operators who previously relied on the old keep-running-anyway behavior will see affected subscriptions come up stopped after upgrading** — recover by verifying/fixing the follower's data out of band, then issuing the existing `Resume` admin action. Full automated snapshot-based reseed remains roadmap (R2). Leader-follower replication is now explicitly documented as Experimental (`docs/guide-docs/guide/08-interconnect.md`).
- **Bug fix (CR-B6):** the TS SDK's optimistic-CAS surfaces (`QueryResult.versions`, `UpdateOp`/`DeleteOp.expected_version`, `UpdateBuilder.expectedVersion`, `setTableSchema`'s `expectedVersion` option) declared a plain `number`, but the wire decoder (`useBigInt64: true`) hands back a genuine `bigint` for any version outside the safe-integer range — forcing a caller to narrow via `Number(...)` before passing a version back for a later CAS, silently losing precision on exactly the value CAS correctness depends on. All four surfaces now accept `number | bigint` (mirroring the existing `CursorId` precedent); a `bigint` passes straight through unmodified, and a plain `number` is validated with `Number.isSafeInteger`, throwing a clear `TypeError` on an unsafe value rather than silently rounding it.
- **Performance fix (CR-C3):** the `AsOf` temporal read path (every cursor `FetchNext`/`CreateCursor` page) individually awaited an MVCC version lookup per record over its full-table enumeration — N sequential single-key store reads instead of one vectored call. `MvccStore` gains a batched `get_at_many`, using the existing (previously-unused-here) `Store::get_many` vectored-read API for the common case (no concurrent write since the pinned snapshot); disk backends collapse N `spawn_blocking` dispatches into one, measured at roughly 13–25x faster over a real fjall-backed store across 1k–100k keys. Behavior-identical — only how bytes are fetched changed, not what a page returns.

  - **Security fix (F-5, #795):** the online storage-migration API (`StartMigration`/`CommitMigration`/`RollbackMigration`/`MigrationStatus`) is now gated behind an explicit `ShamirDb::enable_experimental_migration_api()` opt-in, rejecting `StartMigration` with `experimental_feature_disabled` otherwise — the feature has several known gaps (no write interception, non-durable coordinator state, count-only commit verification; see `KNOWN_LIMITATIONS.md` §2) that make it unsafe as an always-on default.

  - **Correctness fix (F-7, #797):** `with_version: true` silently returned no per-record versions whenever a query also used `ORDER BY`, `DISTINCT`, `GROUP BY`, or an aggregate — those paths reorder/collapse rows after the version was read, and nothing carried the version alongside the reordering.   - **Correctness fix (F-8, #798):** `QueryValueSerializer::serialize_u64` wrapped (sign-flipped) a `u64 > i64::MAX` to a negative `i64` instead of promoting it to `QueryValue::Big`, reintroducing FG-1's original bug one layer into the batch-response serialization path specifically (FG-1 itself had already fixed the decode side; this was a second, independent encode-side site).
  - **Security fix (F-9, #799):** the cursor idle-timeout reaper could reap (unregister) a cursor while a `FetchNext` was still actively executing against it, since `last_activity_nanos` is only bumped once, at the END of a successful fetch — a long-running fetch looked identical to an abandoned cursor for the reaper's whole duration. `expired_ids` now also requires `cursor.state().try_lock().is_ok()` (the fetch handler holds this lock for its entire execution), so a cursor with an in-flight fetch is skipped regardless of how long that fetch takes. A small residual (a new fetch starting in the gap between the reaper's collect-then-remove passes) is documented, not fixed — several orders of magnitude smaller than the bug this closes.
  - **Correctness fix (F-10, #800):** a malformed/corrupt record encountered mid-scan was silently skipped, leaving the result set exactly one row short with no signal anything was wrong. `QueryResult` gains `corrupt_records: Vec<CorruptRecordRef>` (`{table, id}`, omitted from the wire when empty) — every one of `read_exec.rs`'s 14 decode-failure sites now reports the skipped record instead of silently dropping it. The two sibling table-manager files with the same pattern are explicitly out of scope for this fix and documented as a follow-up in `KNOWN_LIMITATIONS.md`.
  - **Resource-safety fix (F-11, #801):** the shipped `deploy/server.small.example.ktav` and `deploy/server.medium.example.ktav` profiles omitted `max_inflight_response_bytes` (RI-15) entirely, leaving that specific concurrency-limiting budget unbounded despite every other field in those profiles being deliberately memory-sized. Both are now fsync'd: file content sync failures propagate as errors (content correctness is the point), directory-fsync failures are logged only and are a documented no-op on non-unix (mirrors the existing `shamir-wal` precedent for the same guarantee).
  - **API consistency fix (F-13, #803):** three Rust/TypeScript query-builder parity gaps closed without breaking the ~800 existing `Query::build()` call sites: a new non-breaking `Query::try_build() -> Result<ReadQuery, QueryBuildError>` rejects `having()` without a preceding `group_by()` and `page`/`page_size == 0` (mirroring checks the TS builder already enforced in its own `build()`); and `Delete`/`Update`/`Upsert`/`AddSchemaRuleBuilder`/`AlterSubscriptionBuilder::build()` now return `Result<_, BuilderError>` instead of panicking via `.expect(...)` on a missing required field (`Update`/`Upsert` also fixed the underlying `QueryValue::Null`-as-both-"unset"-and-"a-real-null" representation ambiguity, not just added a check on top of it).
  - **Gap fix (F-15 follow-up, #808):** F-5's `ShamirDb::enable_experimental_migration_api()` opt-in had no exposure at all on the live `shamir-server` binary — surfaced by the F-15 release gate's own TS e2e run, which found the migration-lifecycle tests structurally unable to pass against a real server. A new `security.enable_experimental_migration_api` config field (default `false`, no CLI flag, never set in any shipped `deploy/*.ktav` profile) wires the existing opt-in into `ServerLauncher::launch` at boot.
