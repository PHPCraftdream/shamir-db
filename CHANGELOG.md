# Changelog

All notable changes to ShamirDB will be documented here.

The project is currently in alpha and has not published a stable release. Until the first tagged release, the `master` branch is the primary development line and compatibility is not guaranteed.

## Versioning scheme

During the alpha phase this project uses `MAJOR.MINOR.PATCH-alpha.N` (for example `0.1.0-alpha.1`). The `alpha.N` suffix is a SemVer pre-release identifier — incrementing `N` does **not** imply any compatibility guarantee between two alpha releases.

> **Workspace-version scope (Node client — documented gap, F-52):** the release pipeline's `version-consistency` job (`.github/workflows/release.yml`) verifies that every *Cargo* workspace crate's `version = "..."` agrees with the pushed `v*` tag. It deliberately does **not** cover `crates/shamir-client-node/package.json`'s `"version"` field: that crate is excluded from the Cargo workspace (`Cargo.toml` `exclude` — napi-rs cdylib, MSVC-only, built separately per `CLAUDE.md`), uses a different manifest format (Node `package.json`, never matched by the `crates/*/Cargo.toml` grep), and is versioned on its own cadence. Its `"version": "0.1.0"` therefore legitimately differs from the workspace's `0.1.0-alpha.1` — this is a documented scope gap, **not** a bug to "fix" by bumping it. There is currently no separate npm-publish workflow for it either (only `ts-e2e-nightly.yml`'s `node-e2e` job builds/tests the `.node` binding locally; no publish step exists yet); adding one is a separate, larger task.

> ⚠️ **Alpha-to-alpha compatibility: NOT guaranteed.** The on-disk storage format, the wire protocol, and the public API (Rust, TypeScript, and WASM) MAY change incompatibly between any two `0.1.0-alpha.N` releases. There is **no supported in-place upgrade path** between alpha versions yet — upgrading between alphas may require an **export/import cycle** (dump data with the old version, re-import with the new one). Treat each alpha as throwaway and keep independently verifiable backups. This is the single most important operational fact for an early adopter.

This file follows [Keep a Changelog](https://keepachangelog.com) conventions loosely and will adhere to [Semantic Versioning 2.0.0](https://semver.org) pre-release semantics once stable releases begin.

- **Security fix (F-46):** the F-40b RI (referential-integrity) barrier — added to serialize a concurrent FK-child writer against an in-flight parent-side FK action (CASCADE/SET NULL/RESTRICT) — previously left a forward race open: a child insert/update landing in the commit window AFTER the parent's own FK-action scan had already run could still slip through unserialized. Every FK-action probe site (`fk_actions.rs`'s cascade probes, `fk_on_update.rs`'s on-update probes) now records its child `table_token` into `TxContext.ri_barrier_tokens` regardless of isolation level, and every commit-pipeline Phase 2-bis guard (`pre_commit_locked_validate`, `pre_commit_locked`) re-checks those tokens via the existing `predicate_conflicts_batch`/`record_conflicts` machinery, aborting a concurrent committer that touched the same child table in the window with `PhantomConflict`/`tx_conflict`. Mirrors the existing S3-C `footprint_tokens` pattern applied to the validation direction.
- **Correctness fix (F-47):** the reverse-FK cache (`ReverseFkCache`) could publish a stale snapshot after `invalidate()` under a specific interleaving — a residual from F-36's original cache landing. Closed by re-checking the cache generation after the rebuild scan completes, discarding the rebuilt snapshot (rather than publishing it) if invalidation raced the rebuild.
- **New capability (F-48, F-48b):** a general `WriterDrainBarrier` primitive closing a check-then-act race on schema/index DDL (a reader could observe a schema/index mid-mutation between the "check" and the "act" of a DDL operation). F-48b wires it into the primary production DML path — the tx-commit prelock (`pre_commit.rs` Phase 2.5) — not just the code path F-48 originally covered.

- **New capability / correctness fix (F-50, full online-index-build-lifecycle campaign, plus a related DROP INDEX gap):** closes a "guaranteed miss" bug in the `index2` (functional/FTS/vector) online build lifecycle, where a transaction that began staging before a new `index2` backend was registered would permanently miss ops for it. `IndexRegistry` gains a generation counter and per-backend insertion-generation tags; `TxContext` tracks which generation each staged index2 op was derived against; a new pre-commit phase re-derives a tx's index2 ops plan against the current registry generation immediately before the WAL write, closing the staleness window without breaking the existing barrier-lock ordering. Extended to every mutation kind (insert/update/delete/upsert), vector-index staged ops, and the legacy sorted-index manager (which gained its own generation counter for the analogous residual). A persisted `Building`/`Ready` index2 lifecycle state closes the matching crash/restart gap — a crash mid-backfill now triggers a clean restart-from-scratch rebuild on next open (backfill has no checkpoint to resume from) instead of silently serving a half-built index; the query planner gates on `Ready` state so a query can never observe a `Building` index2. `doctor`'s verify pass gained `Index2Health` reporting. **Related gap closed in the same campaign:** `index2` backends (functional/FTS/vector) had no `DROP INDEX` support at all before this — `DROP INDEX` now correctly resolves and removes an `index2` backend, a sorted index, or either of the two legacy index mechanisms, in a single unified resolution order.

- **Performance fix (F-53a):** `ORDER BY ... LIMIT K` previously bounded only the SORT WORKSPACE to O(K) — the underlying WHERE-matched/projected row set was still fully materialized to O(N) before the top-K slice was ever taken, contradicting the code's own "O(K) memory" comment. A new `TopKHeap` merges WHERE-filtering, projection, and the sort-key comparison directly into a bounded heap DURING the scan, on both the `Temporal::Latest` and `Temporal::AsOf` read paths — bounding PEAK memory during the scan, not just after it. `count_total` and `with_version` compose correctly via an independent counter and an optional per-heap-item `RecordId`. Measured ~1.9× lower peak allocation and ~27% faster on the new `streaming_topk` bench. Behavior-identical — only how the top-K result is computed internally changed.
- **Performance fix (F-53b, full cursor AsOf index-seek campaign):** a server-side result cursor's `FetchNext` previously re-ran a full O(N) pinned-snapshot table scan on EVERY page, for every cursor shape — the `Keyset`/`Offset` bookmark schemes bound only the RESULT set, not the underlying scan cost, a gap already honestly documented in `KNOWN_LIMITATIONS.md`. Closed for one specific, real cursor shape: an UNFILTERED cursor (no `WHERE` clause at all) with a single-column `ORDER BY` on a sorted-indexed field. A new `TableManager::read_as_of_keyset_seek` walks the sorted index directly at O(page_size) cost per page, classifying each candidate against the pinned MVCC snapshot via a per-index mutation high-water gate (`SortedIndexManager::last_mutation_version`) that provably rules out the two cases a current-state index cannot correctly serve for an AsOf read (an UPDATE to the indexed field, or a DELETE, landing after the pin) — falling back to the existing full-scan path for any page where the gate can't prove safety. A new `PaginationMode::IndexSeek` (alongside the existing `Keyset`/`Offset`) is decided once, at `CreateCursor` time, for a query shape eligible for this fast path; a mandatory one-time fallback to `Offset` mode (reusing the existing `StuckAtCeiling`-style permanent-transition mechanism) covers the case where the fast arm declines mid-cursor-lifetime (e.g. a concurrent write trips the gate between two `FetchNext` calls) — proven with a negative test that a naive always-fast-path implementation would otherwise silently re-serve an earlier page forever. **Honest scope note:** this narrow (but real) optimization only benefits an unfiltered "browse the whole table sorted by one indexed column" cursor shape — any cursor with a `WHERE` clause (the majority of realistic filtered/multi-tenant application usage) is unaffected and continues to pay today's per-page scan cost; the shared sorted-index keyset-seek planner (`try_plan_keyset_seek`, also used by the pre-existing `Temporal::Latest` fast path) structurally excludes any query carrying a `WHERE` clause, and extending it to support one is out of scope for this campaign.
- **Performance fix (F-53c):** FK RESTRICT already had an index-aware fast path for checking whether a child row references a parent (`fk_restrict.rs`); CASCADE and SET NULL did not — both always ran a full child-table scan regardless of whether a supporting index existed on the FK column. The same index-aware classification mechanism is now shared across all three FK actions, gated on a correctness check that the index only reflects committed state (skipped when the current tx has staged writes to the child table, falling back to the scan in that case) and carefully preserving the F-40b RI barrier's token-recording ordering (still at function entry, unaffected by the new index-branch decision). Measured 17–23× faster on a new `fk_cascade_index` bench for the index-eligible case; scan-fallback behavior is unchanged for the non-eligible case.

Added `CreateIndex::try_build() -> Result<BatchOp, CreateIndexBuildError>` mirroring the existing `Query`/`Batch::try_build()` split (`build()` stays infallible for existing callers); new msgpack parity fixtures pin both the valid-shape wire format and the invalid-combination rejections against the server's own checks. - **New capability (FG-5):** server-side result cursors / streaming reads, reducing the wire/client-side impact of the "`QueryResult` materializes as a `Vec`" limitation noted in `KNOWN_LIMITATIONS.md` — the client no longer has to hold a full result set in memory at once, paging through it instead. New wire ops `CreateCursor`/`FetchNext`/`CancelCursor` open a cursor pinned to an MVCC snapshot at creation and page through results via keyset-style pagination — the server never holds a live engine stream open across round-trips, it re-runs the pinned-snapshot read with an advancing bookmark on each `FetchNext`, so each page still costs a full per-page pinned-version table scan server-side and the `QueryResult` for that page is still materialized as a `Vec` internally before serialization (server-side peak memory during a page's execution is unchanged; only wire/client-side memory is reduced). - **New capability (RI-15; upfront-reserve semantics since CR-B2):** a global cap on the SUM of in-flight response bytes across every concurrently-executing batch/connection (`security.query_limits.max_inflight_response_bytes`, default `None` = unbounded, preserving prior behavior). Previously only a per-batch `max_result_size_bytes` clamp existed — at `max_active_connections = 1000` × the 64 MiB per-batch default, worst-case in-flight response memory was ~64 GiB, unbounded relative to a typical 4–8 GiB container. The `ByteBudget` primitive (an `AtomicUsize` CAS-loop + `tokio::sync::Notify`, since `tokio::sync::Semaphore` counts permits, not bytes) now reserves a PESSIMISTIC estimate — the batch's (server-clamped) `max_result_size` — UPFRONT, before `execute_as` runs, so the budget genuinely gates EXECUTION: the (N+1)-th concurrent request now blocks at the reserve call, before its query ever runs, once the budget is saturated (the original landing only bounded write-path residency — N concurrent requests could all execute and serialize in full before any of them was throttled). Once the final `DbResponse` is known, `ByteBudgetGuard::shrink_to` narrows the reservation down to the actual serialized size; a bounded few-byte overshoot past the estimate (e.g. enum-discriminator wire framing on top of the inner payload) is absorbed via a non-blocking `grow_unchecked` rather than a second blocking `acquire` (which would risk deadlocking against the budget slice the guard already holds). Cursor pages (`CreateCursor`/`FetchNext`) get the same upfront-reserve-then-shrink treatment whenever `max_result_size_bytes` is actively configured (that cap is the page's natural upfront estimate); an inactive per-page cap keeps the prior post-hoc-only acquire, since there is no estimate to reserve against. - **Replication behavioral change (RI-10):** the leader now rejects a follower `Hello` whose `proto_ver` exceeds this build's `CURRENT_REPL_PROTO_VER` (`proto_ver_unsupported`) instead of accepting any version unconditionally. More importantly — **a follower that hits a journal gap now STOPS instead of silently skipping the missing range.** Previously, when the leader reported `gap_at` past the follower's requested `from_version`, the follower loop logged a warning, shifted its cursor past the gap, and kept running with permanently missing data and no visible signal. After this change the loop terminates and the subscription's row in `system/subscriptions` is marked `state = "resync_required"` (visible via the existing `ReplicationStatus`/`ListSubscriptions` admin responses); `reconcile()` will not restart a subscription in this state. **Operators who previously relied on the old keep-running-anyway behavior will see affected subscriptions come up stopped after upgrading** — recover by verifying/fixing the follower's data out of band, then issuing the existing `Resume` admin action. Full automated snapshot-based reseed remains roadmap (R2). Leader-follower replication is now explicitly documented as Experimental (`docs/guide-docs/guide/08-interconnect.md`).
- **Bug fix (CR-B6):** the TS SDK's optimistic-CAS surfaces (`QueryResult.versions`, `UpdateOp`/`DeleteOp.expected_version`, `UpdateBuilder.expectedVersion`, `setTableSchema`'s `expectedVersion` option) declared a plain `number`, but the wire decoder (`useBigInt64: true`) hands back a genuine `bigint` for any version outside the safe-integer range — forcing a caller to narrow via `Number(...)` before passing a version back for a later CAS, silently losing precision on exactly the value CAS correctness depends on. All four surfaces now accept `number | bigint` (mirroring the existing `CursorId` precedent); a `bigint` passes straight through unmodified, and a plain `number` is validated with `Number.isSafeInteger`, throwing a clear `TypeError` on an unsafe value rather than silently rounding it.
- **Performance fix (CR-C3):** the `AsOf` temporal read path (every cursor `FetchNext`/`CreateCursor` page) individually awaited an MVCC version lookup per record over its full-table enumeration — N sequential single-key store reads instead of one vectored call. `MvccStore` gains a batched `get_at_many`, using the existing (previously-unused-here) `Store::get_many` vectored-read API for the common case (no concurrent write since the pinned snapshot); disk backends collapse N `spawn_blocking` dispatches into one, measured at roughly 13–25x faster over a real fjall-backed store across 1k–100k keys. Behavior-identical — only how bytes are fetched changed, not what a page returns.
- Release pipeline hardening (CR-B9): the tag-triggered release workflow previously gated only on `fmt`/`clippy`/lib `test` — a tag could be released on a commit whose integration suite or TS unit suite was never actually green against that exact commit. `.github/workflows/release.yml` now also requires the full integration suite, the TS unit suite, a real TS e2e run against a freshly-built release binary, and a new tag-vs-workspace-version consistency check (plus a CHANGELOG sanity check), all wired into every downstream job's `needs:`.
- Registry/config hardening (CR-B8, part of the FG-5/RI-15 wave): `CursorRegistry`'s per-session open-cursor count entry was never removed once it reached zero, permanently leaking one entry per connection that ever opened a cursor on a long-lived server — fixed via an atomic decrement-and-maybe-remove. Both `CursorRegistry` and `TxRegistry`'s internal maps switched from the default hasher to this workspace's standard Fx hasher (an existing convention gap, no behavioral change). `security.cursors.idle_timeout_secs`/`max_cursors_per_session` are now validated at config load (reject `0`, which would otherwise silently disable the cursor feature) and documented in the operations guide.
- **Wave F hardening (F-1..F-13 plus a release-gate-surfaced follow-up, an independent release-readiness review performed post-Wave-E):**
  - **Correctness fix (F-2, #791):** the exact-comparison bounds-check-plus-floor/fract technique CR-D3/W-1 introduced for `Int`↔`F64` filter/`ORDER BY` comparison is now applied consistently across every fast path that previously had its own lossy-cast copy: `eval_bytes.rs`'s raw-byte comparator, `filter_node.rs`'s `set_contains_coercing`/`swap_remove_coercing_qv` (IN-list membership), and `aggregate.rs`'s `OwnedScalar::cmp_scalar`. Also found and fixed the identical bug in `shamir-types`' `record_view::scalar_ref_cmp`/`scalar_ref_cmp_qv` — the hottest of these paths, not covered by the original CR-D3 fix at all since it lives in a different crate that cannot depend on `shamir-engine`.
  - **Security fix (F-1, #792):** a keyset cursor's `ORDER BY` column safety gate (the `Null`/`Bin`/`List`/`Dec`/`Big` detection from CR-D2/W-2/W-3) now also covers schema-typed scalar columns declared via the declarative schema validator, closing the last known gap in that detection family — see `KNOWN_LIMITATIONS.md` §6 for the full current state.
  - **Security fix (F-3, #793):** bootstrap-credential rotation (RI-9/CR-A6) is now ordered rotate-before-consume-before-delete on both the login path and the 24h TTL sweep — previously the token file could be deleted before the underlying SCRAM credential rotation was confirmed durable, a narrow fail-open window where a crash between the two steps left the old credential still valid with no token file left to prove it.
  - **Correctness fix (F-4, #794):** the three declarative-schema DDL handlers (add/alter/drop rule) now validate and precompile the new rule BEFORE persisting or activating it, and roll back to a snapshot of the prior state if activation fails after the write — closing a window where a malformed rule could reach persisted storage in a half-activated state.
  - **Security fix (F-5, #795):** the online storage-migration API (`StartMigration`/`CommitMigration`/`RollbackMigration`/`MigrationStatus`) is now gated behind an explicit `ShamirDb::enable_experimental_migration_api()` opt-in, rejecting `StartMigration` with `experimental_feature_disabled` otherwise — the feature has several known gaps (no write interception, non-durable coordinator state, count-only commit verification; see `KNOWN_LIMITATIONS.md` §2) that make it unsafe as an always-on default.
  - **Correctness fix (F-6, #796):** `count_total: true` combined with `ORDER BY` + `LIMIT` previously took the bounded-heap top-K fast path unconditionally, which cannot produce an accurate total-matched count — the fast-path gate now excludes `count_total` queries, falling back to the full-scan path that can count correctly.
  - **Correctness fix (F-7, #797):** `with_version: true` silently returned no per-record versions whenever a query also used `ORDER BY`, `DISTINCT`, `GROUP BY`, or an aggregate — those paths reorder/collapse rows after the version was read, and nothing carried the version alongside the reordering. Record ids are now tracked in lockstep through the sort/dedup permutation so the returned `versions` array stays index-aligned with `records` on every path that can structurally support it.
  - **Correctness fix (F-8, #798):** `QueryValueSerializer::serialize_u64` wrapped (sign-flipped) a `u64 > i64::MAX` to a negative `i64` instead of promoting it to `QueryValue::Big`, reintroducing FG-1's original bug one layer into the batch-response serialization path specifically (FG-1 itself had already fixed the decode side; this was a second, independent encode-side site).
  - **Security fix (F-9, #799):** the cursor idle-timeout reaper could reap (unregister) a cursor while a `FetchNext` was still actively executing against it, since `last_activity_nanos` is only bumped once, at the END of a successful fetch — a long-running fetch looked identical to an abandoned cursor for the reaper's whole duration. `expired_ids` now also requires `cursor.state().try_lock().is_ok()` (the fetch handler holds this lock for its entire execution), so a cursor with an in-flight fetch is skipped regardless of how long that fetch takes. A small residual (a new fetch starting in the gap between the reaper's collect-then-remove passes) is documented, not fixed — several orders of magnitude smaller than the bug this closes.
  - **Correctness fix (F-10, #800):** a malformed/corrupt record encountered mid-scan was silently skipped, leaving the result set exactly one row short with no signal anything was wrong. `QueryResult` gains `corrupt_records: Vec<CorruptRecordRef>` (`{table, id}`, omitted from the wire when empty) — every one of `read_exec.rs`'s 14 decode-failure sites now reports the skipped record instead of silently dropping it. The two sibling table-manager files with the same pattern are explicitly out of scope for this fix and documented as a follow-up in `KNOWN_LIMITATIONS.md`.
  - **Resource-safety fix (F-11, #801):** the shipped `deploy/server.small.example.ktav` and `deploy/server.medium.example.ktav` profiles omitted `max_inflight_response_bytes` (RI-15) entirely, leaving that specific concurrency-limiting budget unbounded despite every other field in those profiles being deliberately memory-sized. Both now set it at the same 4× `max_result_size_bytes` ratio the operations guide's worked example already uses (small: 128 MiB, medium: 256 MiB) — comfortable headroom against each profile's own Argon2 worst-case allocation. The reference/all-fields profile (`server.example.ktav`) still has no explicit value set; flagged as an open follow-up.
  - **Durability fix (F-12, #802):** `backup`/`restore`'s file copy (`fs::copy`) and manifest write (`fs::write`) left bytes in the OS page cache with no `sync_all`; `restore`'s atomic swap performed up to three `fs::rename` calls with no fsync of the containing directory afterward — the classic "fsync'd the file but not the directory" gap that leaves a "successful" rename not actually durable across a real power loss. Both are now fsync'd: file content sync failures propagate as errors (content correctness is the point), directory-fsync failures are logged only and are a documented no-op on non-unix (mirrors the existing `shamir-wal` precedent for the same guarantee).
  - **API consistency fix (F-13, #803):** three Rust/TypeScript query-builder parity gaps closed without breaking the ~800 existing `Query::build()` call sites: a new non-breaking `Query::try_build() -> Result<ReadQuery, QueryBuildError>` rejects `having()` without a preceding `group_by()` and `page`/`page_size == 0` (mirroring checks the TS builder already enforced in its own `build()`); and `Delete`/`Update`/`Upsert`/`AddSchemaRuleBuilder`/`AlterSubscriptionBuilder::build()` now return `Result<_, BuilderError>` instead of panicking via `.expect(...)` on a missing required field (`Update`/`Upsert` also fixed the underlying `QueryValue::Null`-as-both-"unset"-and-"a-real-null" representation ambiguity, not just added a check on top of it).
  - **Gap fix (F-15 follow-up, #808):** F-5's `ShamirDb::enable_experimental_migration_api()` opt-in had no exposure at all on the live `shamir-server` binary — surfaced by the F-15 release gate's own TS e2e run, which found the migration-lifecycle tests structurally unable to pass against a real server. A new `security.enable_experimental_migration_api` config field (default `false`, no CLI flag, never set in any shipped `deploy/*.ktav` profile) wires the existing opt-in into `ServerLauncher::launch` at boot.
- **Known limitations accepted for this release** (see `docs/guide-docs/KNOWN_LIMITATIONS.md` for the full, citation-backed list): query results still do not stream at the storage-engine level — a cursor page still executes one full pinned-version scan server-side per page internally, only the wire/client-side memory footprint is reduced (§6); the online storage-migration API remains experimental and disabled by default pending write interception, durable coordinator state, and byte-level (not count-only) commit verification (§2). Both are deliberate scope cuts for `0.1.0-alpha.1`, not oversights — see the linked sections for the concrete reasoning and the tracking references.
